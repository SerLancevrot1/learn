## WebFlux, WebClient и блокирующие зависимости

Reactor Core предоставляет `Mono`, `Flux` и операторы. Spring WebFlux использует их в веб-слое. Reactor Netty часто обслуживает сетевой ввод-вывод под WebFlux и WebClient. В сервере с event loop несколько соединений делят один поток обработки событий. Если этот поток ждёт JDBC, читает файл или долго считает, задержка растёт и у соседних запросов. Любой синхронный клиент внутри `map` остаётся блокирующим.

Обработчик возвращает `Mono<Response>` или `Flux<Event>`. Подписка у инфраструктуры, которая знает об HTTP-запросе и может отменить обработку, когда клиент отключится. Вызов `subscribe()` внутри контроллера создаёт независимую подписку. Ответ может уйти раньше завершения операции, а ошибки, отмена и реактивный контекст исходного запроса перестают управлять этой работой. Для фоновой операции с гарантией доставки можно явно записать задачу или outbox-событие и дать отдельному обработчику взять его в работу. [Обзор Spring WebFlux](https://docs.spring.io/spring-framework/reference/6.2/web/webflux/new-framework.html)

Для обычного WebClient-запроса подходит `retrieve().bodyToMono(...)` или `bodyToFlux(...)`. По умолчанию `retrieve` оборачивает статусы 4xx и 5xx в ошибки. `onStatus` даёт настроить обработку. `exchangeToMono` или `exchangeToFlux` удобны, когда тело нужно декодировать по-разному в зависимости от статуса. Опиши чтение тела внутри обработчика ответа. Spring освободит оставшееся тело после завершения возвращённого publisher. Для SSE или NDJSON можно отдавать элементы постепенно. `collectList()` перед ответом накапливает всё в памяти и отсрочивает первый байт. Для уже начатого потокового ответа HTTP-статус обычно зафиксирован, поэтому ошибки после отправки заголовков требуют соглашения о поведении потока. [WebClient Exchange](https://docs.spring.io/spring-framework/reference/6.2/web/webflux-webclient/client-exchange.html)

Если синхронная зависимость пока необходима, изолируй её на границе. В примере ниже вызов остаётся блокирующим и занимает поток выделенного пула. Предел задач в очереди планировщика, конкурентность вызовов и таймауты драйвера надо выбирать совместно. `boundedElastic` защищает event loop, а размер пула соединений по-прежнему определяет, сколько операций реально пойдёт в БД.

```java
Mono<User> findUser(long id) {
    return Mono.fromCallable(() -> legacyJdbc.findUser(id))
            .subscribeOn(jdbcScheduler);
}
```

JDBC и JPA подходят для синхронной работы с БД. Для реактивных SQL-цепочек используют R2DBC с поддерживаемым драйвером и его пулом. Если большая часть стека синхронная, Spring MVC с виртуальными потоками Java 21 может дать более простой код для I/O-нагрузки. Ограничения БД, внешних API, памяти и CPU остаются и в этой модели. Reactive Streams полезен, когда нужен поток значений со спросом, отменой и композицией нескольких источников. Сравнивай варианты под рабочей нагрузкой по throughput, p95/p99 и расходу ресурсов. [Планировщики Reactor](https://projectreactor.io/docs/core/release/reference/coreFeatures/schedulers.html) · [Virtual Threads в Java 21](https://inside.java/2023/09/19/the-arrival-of-java-21/)

## Границы транзакции и срок жизни ресурса

`ReactiveTransactionManager` привязывает транзакцию к Reactor Context. `TransactionalOperator` может обернуть нужную цепочку. `@Transactional` с реактивным менеджером работает с возвращаемым publisher при вызове через Spring proxy. Для участия в транзакции все операции используют связанные ресурсы внутри той же реактивной цепочки. Для реактивной транзакции Spring обрабатывает отмену как причину отката. У транзакционного `Flux` нужно учитывать полное потребление. Если запросить несколько первых элементов через `take` снаружи транзакционной границы, отмена может привести к откату.

```java
Mono<Order> create(Order order) {
    return transaction.transactional(
            orders.insert(order)
                    .flatMap(saved -> outbox.insert(OrderCreated.from(saved)).thenReturn(saved)));
}
```

Здесь запись заказа и outbox-события делят транзакцию при условии, что репозитории используют тот же совместимый ресурс. Для многих драйверов одна транзакция работает на одном соединении. Последовательная композиция уменьшает риск конфликтов на соединении. Держи транзакцию короткой, особенно если возможны долгие сетевые вызовы. Для HTTP-платежа откат БД сам по себе ничего не отменяет. Нужен отдельный протокол согласования, например идемпотентный ключ у провайдера и обработка неопределённого исхода. [Декларативные транзакции Spring](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/tx-decl-explained.html) · [TransactionalOperator и отмена](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/programmatic.html)

Привязывай открытие и освобождение ресурса к подписке. `try-with-resources` вокруг `return body(resource)` закроет ресурс при возврате из Java-метода, а цепочка может использовать его позже. Для синхронного освобождения подходит `using`, для асинхронного — `usingWhen`. В `Mono.usingWhen` успешное значение ждёт завершения cleanup. Если cleanup упадёт, подписчик может получить ошибку вместо значения. `doFinally` удобно использовать для счётчиков и логов, у него нет возвращаемого publisher для ожидания асинхронной очистки. [Mono.usingWhen](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html#usingWhen(org.reactivestreams.Publisher,java.util.function.Function,java.util.function.Function,java.util.function.BiFunction,java.util.function.Function))

## Конкурентность, очереди и предельная нагрузка

В расчёте заказа `flatMapSequential(..., 2)` задаёт лимит на одну подписку. При ста одновременных запросах сервис теоретически может начать до двухсот загрузок цен. Ёмкость общих ресурсов ограничивают отдельно. Это могут быть пул соединений, очередь с явным пределом, rate limiter и общий лимит активных запросов на зависимость. Выбирай границу по тому ресурсу, который истощается первым.

Прикинуть порядок величин помогает закон Литтла. Если при устойчивой нагрузке на зависимость приходит 400 вызовов/с, а среднее время вызова 50 мс, одновременно там в среднем около 20 операций. Это среднее, а пики, медленные хвосты и ретраи поднимут требуемую ёмкость. Проверь по метрикам, сколько запросов активно, сколько ждёт соединения и какая часть общего времени уходит на ожидание.

Считай места накопления. `publishOn` держит очередь, `flatMap` запрашивает данные из внутренних источников заранее, `flatMapSequential` держит готовые результаты за медленной первой позицией, `collectList` ждёт весь поток. `buffer(n)` собирает списки, `window(n)` выдаёт внутренние `Flux`, а `groupBy` открывает подстрим для каждого встреченного ключа. Большое число групп и слабое потребление могут застопорить `groupBy` при ограниченном `flatMap`. Для неограниченного набора ключей потребуется схема, контролирующая число групп. [Batching, windowing и grouping](https://projectreactor.io/docs/core/release/reference/advancedFeatures/advanced-three-sorts-batching.html) · [Пул соединений Reactor Netty](https://projectreactor.io/docs/netty/release/reference/http-client.html#connection-pool)

Смежные операторы Reactor иногда договариваются о совместном чтении из очереди. Такая оптимизация называется *operator fusion*. Она может менять число внутренних вызовов и работу очередей. В тестах бизнес-кода проверяй наблюдаемые значения, границы спроса и отмену. Точные размеры внутренних запросов полезно проверять только там, где от них зависит заявленное поведение, например в отдельном тесте настройки `limitRate`. [Fuseable API](https://projectreactor.io/docs/core/release/api/reactor/core/Fuseable.html)

## Таймауты, ретраи и ошибки по бизнес-правилам

При выборе таймаута различай ожидание соединения из пула, установление соединения, чтение ответа и общий бюджет обработки. Таймаут Reactor действует на участок цепочки, где он поставлен. Таймауты уровня клиента помогают понять, какая стадия создаёт задержку. В учебном расчёте таймаут охватывает чтение **одной цены** и её повторы. Полный расчёт с несколькими партиями и запросом скидки может занять больше. Для полного бюджета вызывающая сторона ставит таймаут поверх результата расчёта.

Временные ошибки чтения часто допускают ограниченное число повторов. При перегрузке подойдут растущие паузы и jitter, чтобы клиенты не повторяли запросы одновременно. При HTTP 429 учитывай соглашение с сервисом, включая `Retry-After`, если он есть. Постоянные ошибки, такие как неверные входные данные, обычно сразу доходят до вызывающей стороны. Повтор вокруг целого заказа может повторить и уже успешные чтения. Выбирай участок сознательно.

На собеседовании разберись, что означает таймаут записи. Платёж мог произойти, а ответ потеряться. Новый запрос с тем же идемпотентным ключом должен обратиться к тому же логическому действию, если провайдер поддерживает этот контракт. Проверь, где хранится ключ и какой исход получит клиент после неопределённого ответа. У `Flux` повторная подписка также способна заново выдать уже прочитанные элементы. Для надёжного потребления могут понадобиться смещения, дедупликация и подтверждения обработки. [Retry в Reactor](https://projectreactor.io/docs/core/release/reference/coreFeatures/error-handling.html) · [Таймауты Reactor Netty](https://projectreactor.io/docs/netty/release/reference/http-client.html#timeout-configuration)

Разделяй пустой результат и отказ по доменной причине. В заказе пустая скидка означает ноль, а пустая цена делает расчёт невозможным. Если API отдаёт частичный результат, опиши его явно, например списком успешных позиций и списком отказов. Превращение всех ошибок в `Mono.empty()` скроет поломки сети и ошибки в коде.

## Диагностика в приложении

1. Для зависшего запроса проверь, была ли подписка, есть ли спрос и какой источник ещё не завершился. У `zip` проверь пустые ветки. При `collectList` проверь, конечен ли источник.
2. При росте p99 проверь загрузку CPU, блокировки event loop, очередь `boundedElastic`, число ожидающих соединение, длительность внешних вызовов и долю ретраев. Thread dump и JFR помогают связать очереди с конкретным блокирующим участком.
3. `log()` показывает сигналы на выбранной границе. `checkpoint("order-quote.price")` добавляет место для поиска в цепочке. `Hooks.onOperatorDebug()` полезен при диагностике, но захват стеков при сборке имеет цену. BlockHound может обнаружить поддерживаемые блокирующие вызовы на потоках, помеченных как неблокирующие.
4. Reactor Micrometer позволяет измерять поток сигналов и очередь планировщика. Собирай отдельно успешное завершение, пустые результаты, ошибки, таймауты и отмены. Для меток выбирай малое число значений, например имя операции. Идентификаторы заказов и запросов подходят для трасс и логов.
5. Для журналов и контекста проверь две подписки одного publisher с разными trace ID. Глобально закешированный `Mono.deferContextual(...)` может сохранить данные первой подписки и выдать их следующей. Размещай зависимую от подписчика обработку после общего кеша или используй подходящий ключ кеша.

## Как доказать поведение тестом

`StepVerifier` подписывается при `verify` и проверяет сигналы по порядку. Для спроса используй `create(publisher, 0)` и `thenRequest(n)`. Для отмены используй `thenCancel()`, затем проверь остановку источника через `PublisherProbe`. `TestPublisher` удобен, когда надо вручную отправить события и управлять моментом их прихода. Сам вывод в журнал бывает полезен, а контракт лучше проверять ожиданиями.

В `withVirtualTime(() -> ...)` собирай таймеры внутри supplier. Reactor подменяет стандартный Scheduler перед созданием publisher. Если таймер уже создан на реальном или явно переданном планировщике, виртуальные часы могут на него не повлиять. `expectSubscription()` позволяет начать интервал проверки тишины после получения подписки. Ограничь реальное время `verify(Duration)`, чтобы сломанный тест не завис. [Тестирование Reactor](https://projectreactor.io/docs/core/release/reference/testing.html)

```java
StepVerifier.withVirtualTime(() -> Mono.delay(Duration.ofMinutes(1)))
        .expectSubscription()
        .expectNoEvent(Duration.ofSeconds(59))
        .thenAwait(Duration.ofSeconds(1))
        .expectNext(0L)
        .expectComplete()
        .verify(Duration.ofSeconds(5));
```

В [OrderQuotesTest.java](src/test/java/ru/learn/reactor/OrderQuotesTest.java) отдельно проверяются старт, готовность и порядок выдачи. Цена второго товара готова раньше первой, а ответ сохраняет порядок входных позиций. В интеграционном тесте с реальным WebClient, R2DBC или SSE дополнительно проверяют транспортные таймауты, освобождение соединений и отмену при разрыве соединения. Эти эффекты зависят от клиента и сервера.
