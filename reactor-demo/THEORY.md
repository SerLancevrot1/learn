## 1. Что описывают Mono и Flux

Представь HTTP-клиент. При блокирующем вызове поток ждёт, пока придёт ответ. При неблокирующем вызове поток может заняться другой работой, а ответ будет обработан, когда транспорт сообщит о готовности. Reactor позволяет собрать такую обработку в цепочку и описать, что делать со значением, ошибкой или отсутствием результата. Синхронная цепочка `Flux.range(1, 5).map(i -> i * 2)` обычно целиком выполняется на потоке подписчика. Асинхронность появляется там, где её даёт источник, таймер или граница планирования. [Введение в реактивное программирование](https://projectreactor.io/docs/core/release/reference/reactiveProgramming.html)

`Stream<T>` из Java обходит элементы и выполняет операции при терминальном вызове. Один экземпляр рассчитан на один обход. `CompletableFuture<T>` представляет одну завершаемую операцию, а `supplyAsync` отправляет её в executor сразу. `Mono` и `Flux` вводят протокол подписки, запроса элементов, завершения и отмены. Это особенно заметно у `Flux`, который может выдавать значения постепенно. [Stream API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/stream/package-summary.html) · [CompletableFuture API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/CompletableFuture.html)

| Тип | Что наблюдает подписчик |
| --- | --- |
| `Mono<T>` | До одного значения. Например, карточку товара, отсутствие товара или ошибку поиска. |
| `Mono<Void>` | Завершение без значения или ошибку. Например, подтверждение записи. |
| `Flux<T>` | От нуля до многих значений. Подходит и для потоков, которые продолжают работать сколько угодно долго. |
| `Mono.empty()` | Успешное завершение без значения. |
| `Mono.never()` | После подписки источник молчит до отмены. |
| `Mono.error(e)` | Завершение сигналом ошибки. |

Успешный `Mono` со значением обычно посылает `onNext` и `onComplete`. Успешный пустой `Mono` посылает только `onComplete`. `onNext` с `null` запрещён. `Mono.justOrEmpty(null)` выражает отсутствие значения. `map`, вернувший `null`, обычно приводит к `NullPointerException`. [Mono API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html)

## 2. Сигналы и подписка

Reactive Streams задаёт протокол. `Publisher` принимает подписчика. `Subscriber` получает `Subscription`, через которую просит данные или отменяет работу. `Processor` совмещает стороны подписчика и издателя. Reactor реализует этот протокол и даёт операторы поверх него. [Спецификация Reactive Streams для JVM](https://github.com/reactive-streams/reactive-streams-jvm#specification)

```mermaid
flowchart LR
    A["Publisher / верхние операторы"] -->|"onSubscribe, onNext, onError / onComplete"| B["Subscriber / нижние операторы"]
    B -->|"request(n), cancel()"| A
```

1. Сначала подписчик получает `onSubscribe`. Потом он может запросить `n > 0` элементов. Невыполненные запросы складываются, а `Long.MAX_VALUE` означает практически неограниченный спрос.
2. Каждый `onNext` тратит единицу спроса. Источник вправе выдать меньше, если данных больше нет. `onComplete` и `onError` могут прийти и при нулевом спросе.
3. Ошибка или успешное завершение заканчивают обмен сигналами. Для подписчика сигналы сериализованы. Последовательные вызовы могут прийти с разных потоков при наличии связи happens-before.
4. `cancel()` просит прекратить работу вверх по цепочке. Подписчик может ещё увидеть сигнал, который уже был в пути. Реакция реальной внешней системы на отмену зависит от её API.

Подписка идёт снизу к источнику, поэтому участок ближе к источнику называется *upstream*, а ближе к конечному подписчику — *downstream*. `request` и `cancel` идут вверх. Данные и завершение идут вниз. При `Flux.just(...)` подписка и выдача элементов могут уложиться в один стек вызовов. [Спрос и его преобразование](https://projectreactor.io/docs/core/release/reference/coreFeatures/simple-ways-to-create-a-flux-or-mono-and-subscribe-to-it.html)

## 3. Когда выполняется код

**Сборка цепочки** происходит при вызове фабрик и операторов. **Выполнение** начинается при подписке, если источник отложенный. Операторы возвращают обёрнутый publisher. Если составить `source.map(...)` и вернуть исходный `source`, преобразование потеряется.

```java
Mono<User> eager = Mono.just(findUser());              // findUser вызывается сразу
Mono<User> lazy = Mono.fromCallable(() -> findUser());  // вызов при подписке
Mono<User> chosen = Mono.defer(() -> chooseSource());  // при подписке выбираем сам Mono
```

- `just` принимает уже готовое значение. Исключение из `findUser()` в первом примере вылетит из текущего метода.
- `fromSupplier` и `fromCallable` откладывают вычисление одного значения. `Callable` может объявлять checked exception. Обычное исключение вычисления станет `onError`.
- `defer` откладывает вызов фабрики publisher. Удобен для новой попытки, выбора из двух источников или создания отдельного состояния на подписку.
- `Mono.fromFuture(existingFuture)` оборачивает готовый future, который мог уже начать работу. `Mono.fromFuture(() -> startAsync())` откладывает создание future до подписки. Отмена обёртки обычно отменяет `CompletableFuture`, а фактическая остановка работы зависит от реализации задачи.
- `Flux.fromIterable` берёт элементы из коллекции. `Flux.generate` синхронно вызывает генератор по спросу и разрешает максимум один `next` за вызов. `Flux.create` подходит для адаптации API с callback. Если внешние события нельзя замедлить, задай стратегию переполнения и снимай слушатель в `sink.onDispose(...)`. Буфер `create` по умолчанию способен расти без границы.

Для холодного источника каждая подписка запускает своё выполнение. Два `subscribe()` или два `block()` могут вызвать два HTTP-запроса. В веб-коде контроллер возвращает publisher, и подписку делает фреймворк. На границе консольной утилиты можно осознанно ждать через `block(Duration)`. [Создание источников](https://projectreactor.io/docs/core/release/reference/coreFeatures/programmatically-creating-sequence.html) · [Mono API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html)

Если `map` захватил изменяемый список при сборке, его могут использовать разные подписки на тот же publisher. Сериализация сигналов для одного подписчика сама по себе не защищает такой список между подписками. Создавай состояние внутри `defer`, через фабрику `generate` или используй оператор вроде `reduce`. [Flux API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html)

## 4. Как выбрать оператор

Сначала определи форму результата и зависимости между шагами. Будет ли значение? Нужен ли старый результат для следующего вызова? Должны ли результаты идти в исходном порядке?

| Задача | Оператор и поведение |
| --- | --- |
| Вычислить `T → R` | `map`. Подходит для быстрой синхронной функции. |
| Отобрать значения | `filter`. `handle` позволяет за вызов выдать значение, пропустить его или завершить поток. |
| По значению вызвать операцию `T → Mono<R>` | `flatMap`. Он сам подпишется на внутренний publisher. С `map` получился бы вложенный тип `Mono<Mono<R>>`. |
| Из одного значения получить много | `Mono.flatMapMany`. Например, из пользователя получить `Flux<Order>`. |
| Собрать значения независимых источников | `zip`. Для каждого результата нужна пара значений. Для зависимого вызова используй `flatMap`. |
| Запустить операцию после успешного завершения предыдущей | `then(next)`. Пустое успешное завершение тоже запускает `next`, а значения первого источника отбрасываются. |
| Дождаться завершения нескольких операций | `Mono.when`. Возвращает `Mono<Void>`. |
| Подставить значение или другой источник при пустом результате | `defaultIfEmpty(value)` или `switchIfEmpty(other)`. Для дорогой фабрики используй `switchIfEmpty(Mono.defer(() -> load()))`. |
| Склеить готовые publishers | `concat` подписывается по очереди, `merge` смешивает значения активных источников по мере поступления. |
| Остановиться на первом элементе | `Flux.next()` возвращает `Mono<T>`. `take(n)` ограничивает число значений в `Flux`. |
| Собрать конечный поток | `collectList` хранит все элементы до завершения. `reduce` сворачивает их в один результат. `scan` выдаёт промежуточные результаты. |

### Три способа обработать элементы Flux

| Оператор | Когда начинают работать внутренние publishers | Порядок выдачи | Цена |
| --- | --- | --- | --- |
| `flatMap(f, concurrency)` | Одновременно активны до `concurrency` подписок. | По готовности, значения разных publishers могут смешаться. | Нужен предел нагрузки на зависимость. |
| `concatMap(f)` | Следующий стартует после завершения текущего. | Исходный порядок. | Медленный элемент задерживает старт остальных. |
| `flatMapSequential(f, concurrency)` | Несколько publishers стартуют заранее. | Исходный порядок. | Быстрые поздние результаты ждут медленных ранних. |

`switchMap` переключается на новый внутренний publisher и отменяет предыдущий при новом входном значении. Подходит для подсказок поиска, если важен последний запрос. Уже отданные результаты и совершённые внешние эффекты остаются.

`zip` с `Mono.empty()` завершается пустым. Поэтому `zip` с `Mono<Void>` обычно означает, что комбинирующая функция вообще не вызовется. Короткое замыкание, особенно при вложенных `zip`, может даже исключить подписку на часть источников. Если нужен успешный старт следующего действия — `then`. Если нужно передать маркер — `thenReturn(marker)`. Для явного отсутствия результата можно использовать `singleOptional()`. [Flux API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html) · [FAQ Reactor о пустом zip](https://projectreactor.io/docs/core/release/reference/faq.html)

## 5. Backpressure

Backpressure — обратная связь о том, сколько элементов готов принять получатель. Он выражен числом элементов. Ограничение «100 запросов в секунду» относится к rate limiting. Ограничение «не более 10 HTTP-вызовов одновременно» относится к конкурентности. Один сервис может использовать все три механизма.

Операторы могут менять спрос между участками цепочки. Если downstream хочет два результата от `buffer(10)`, оператору нужны до двадцати входных элементов. `prefetch` — объём опережающего запроса на некоторых границах, например из внутренней последовательности `flatMap`. `limitRate(highTide, lowTide)` дробит крупные запросы вверх по цепочке. С `lowTide = 0` пополнение идёт полными партиями. Даже при малом запросе снизу оператор может держать данные в очереди. Лямбда-вариант `subscribe(...)` по умолчанию запрашивает практически бесконечный объём. [Спрос и prefetch в Reactor](https://projectreactor.io/docs/core/release/reference/coreFeatures/simple-ways-to-create-a-flux-or-mono-and-subscribe-to-it.html)

Если внешний источник выдаёт события по часам или callback независимо от потребителя, выбери явную политику. `onBackpressureBuffer(max)` даёт временный запас памяти и на переполнении требует политики. `onBackpressureDrop` пропускает события, пока нет спроса. `onBackpressureLatest` сохраняет последнее. `onBackpressureError` заканчивает цепочку ошибкой. Последний статус датчика допустимо обновить новым, а событию списания обычно нужна надёжная доставка с подтверждением или возможность перечитать его из хранилища. [Flux API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html)

`Flux.interval` без оператора переполнения выдаёт ошибку, если пришло время тика и у него нет спроса. В примере `onBackpressureDrop` сам запрашивает тики и пропускает их, пока ниже нет спроса. Следующий запрос подписчика позволит получить новый тик, а пропущенные уже не вернутся.

## 6. Потоки и Scheduler

`Scheduler` предоставляет место и способ запланировать работу. Синхронный участок обычно выполняется на потоке, с которого пришёл сигнал.

- `subscribeOn(scheduler)` планирует подписку к источнику. Удобное место для обёртки блокирующего клиента — сразу после `Mono.fromCallable(...)`. `Mono.just(blockingCall()).subscribeOn(...)` уже выполнил вызов при сборке и не сможет перенести его задним числом.
- `publishOn(scheduler)` меняет поток обработки сигналов после этой границы до следующего переключения или асинхронного источника. У `Flux.publishOn` существует очередь. Дополнительная граница стоит времени и памяти.
- `Schedulers.boundedElastic()` подходит для временной изоляции блокирующего I/O. Поток на время ожидания занят, число потоков и очереди ограничены. `Schedulers.parallel()` подходит для вычислений без блокирующего I/O. `Schedulers.single()` полезен для последовательной работы на одном потоке.
- `parallel()` делит `Flux` на группы обработки. Для выполнения групп на потоках обычно используют `runOn(...)`, а `sequential()` склеивает их обратно. Если нужно сохранить исходный порядок, проверяй это отдельно.

Один `publishOn` сам по себе не распараллеливает последовательные `map`. `flatMap` управляет одновременными подписками, а реальный параллелизм зависит от внутренних источников и планирования. Операторы таймеров и клиенты I/O могут иметь собственные потоки. [Threading and Schedulers](https://projectreactor.io/docs/core/release/reference/coreFeatures/schedulers.html) · [ParallelFlux](https://projectreactor.io/docs/core/release/reference/advancedFeatures/advanced-parallelizing-parralelflux.html)

## 7. Общие источники и Sinks

Холодная цепочка запускает источник независимо для каждого подписчика. Горячая цепочка может делить уже существующий поток событий. Поздний подписчик получает то, что обещает её режим хранения истории. `just` отдельно показывает захват значения на этапе сборки. Это различие полезно объяснять через момент запуска работы и судьбу поздней подписки. [Hot Versus Cold](https://projectreactor.io/docs/core/release/reference/advancedFeatures/reactor-hotCold.html)

- `Flux.share()` делит одну активную подписку. Поздний подписчик подключается к текущему потоку, а уход последнего отключает активный источник.
- `publish()` создаёт `ConnectableFlux`. Можно вызвать `connect()` явно или начать при `autoConnect(n)`. `refCount(n)` подключается при наборе `n` подписчиков, а после ухода последнего отключается. Есть вариант с периодом ожидания новых подписчиков перед отключением.
- `replay(n)` позволяет хранить историю для поздних подписчиков. `Mono.cache(...)` может хранить значение, пустое завершение или ошибку. Первая загрузка `Mono.cache()` продолжится даже при отмене подписчика. Нужен осмысленный TTL и ключ кеша, если данные зависят от пользователя или параметров вызова.
- `Sinks.One` передаёт один результат или терминальный сигнал. `Sinks.Many` удобен для событий. `unicast` рассчитан на одного подписчика, `multicast` — на нескольких, `replay` хранит историю. `directBestEffort` пропускает событие для подписчика без спроса и может доставить его другим. Проверяй итог `tryEmitNext`. Например, конкурирующие вызовы могут дать `FAIL_NON_SERIALIZED`.

[ConnectableFlux](https://projectreactor.io/docs/core/release/reference/advancedFeatures/advanced-broadcast-multiple-subscribers-connectableflux.html) · [Sinks](https://projectreactor.io/docs/core/release/reference/coreFeatures/sinks.html)

## 8. Ошибки, отмена и ресурсы

Ошибка завершает исходную подписку. `onErrorResume` переключается на резервный publisher. Если поставить его снаружи `flatMap`, ошибка завершит обработку всей исходной последовательности. Если поставить внутри обработчика элемента, внешний `Flux` сможет продолжить работу с другими элементами.

| Оператор | Результат |
| --- | --- |
| `doOnError` | Наблюдает ошибку для журнала или метрики, ошибка продолжает путь. |
| `onErrorMap` | Заменяет исключение, например оборачивает его в доменное. |
| `onErrorReturn` | При ошибке выдаёт заданное значение. |
| `onErrorResume` | Выбирает источник восстановления. Фильтр по типу ошибки помогает сохранить неожиданные ошибки видимыми. |
| `retryWhen` | Повторно подписывается на участок до оператора. `Retry.max(2)` разрешает до двух повторов после первой попытки. |
| `timeout` | При истечении времени отменяет исходную работу и выдаёт ошибку либо переключается на указанный fallback. У `Flux.timeout(Duration)` таймер отслеживает первое значение и паузу между значениями. |
| `doFinally` | Получает причину окончания, включая `CANCEL`. Удобен для наблюдения. |
| `using` / `usingWhen` | Ведут жизненный цикл ресурса. `usingWhen` даёт отдельные асинхронные ветки освобождения на успех, ошибку и отмену. |

В `attempt.timeout(perAttempt).retryWhen(policy).timeout(total)` внутренний таймер начинается с каждой попыткой. Внешний покрывает попытки и интервалы ожидания. Если внутри `retryWhen` находится уже запущенный future, новая подписка может снова увидеть ту же ошибку. Перед ретраем подумай, выполнится ли удалённый эффект дважды. `onErrorContinue` поддерживается только отдельными операторами и влияет на участок выше него, поэтому для понятной обработки по элементам удобно локальное восстановление. [Handling Errors](https://projectreactor.io/docs/core/release/reference/coreFeatures/error-handling.html) · [Retry API](https://projectreactor.io/docs/core/release/api/reactor/util/retry/Retry.html)

## 9. Reactor Context

`Context` — неизменяемый набор пар ключ-значение, связанный с подписчиком. `contextWrite` делает запись видимой операторам выше себя. `deferContextual` читает её на подписке. У разных подписчиков одного publisher могут быть разные `traceId`. Смена потока сохраняет связь с подписчиком, поэтому запись остаётся доступна.

```java
Mono<String> trace = Mono.deferContextual(ctx ->
        Mono.just(ctx.getOrDefault("traceId", "missing")));
Mono<String> tagged = trace.contextWrite(ctx -> ctx.put("traceId", "A"));
```

При записи в контекст внутри `flatMap` изменение действует для внутреннего publisher. `ThreadLocal`, который использует обычный MDC, привязан к Java-потоку.
