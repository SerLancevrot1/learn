## История одного publisher

Publisher отправляет пять сообщений через один channel. До получения подтверждения может хранить карту «порядковый номер публикации → наше сообщение». Положительный confirm переводит запись в подтверждённую по оговорённому контракту. Если брокер возвращает подтверждение с признаком multiple, оно относится к группе ранее выданных номеров на этом канале. Для unroutable при mandatory учитывай `basic.return` отдельно. ID сообщения остаётся стабильным для бизнес-повтора.

При внезапной потере TCP часть отправленных байтов могла попасть в брокер и сохраниться. Отсутствие confirm оставляет неизвестный исход. После переподключения номера нового канала начинаются по его правилам и не принадлежат предыдущему каналу. Восстанови топологию и повтори непроверенные сообщения с тем же message ID. Если relay уже сохранил статус «отправлено» до получения нужного подтверждения, после рестарта может исчезнуть запись, которую надо повторить.

### По одному, партией или асинхронно

| Подход | Выгода | Цена |
| --- | --- | --- |
| Ждать каждого confirm | Просто сопоставлять результат с записью | Последовательные ожидания ограничивают throughput |
| Партия и ожидание подтверждений | Меньше ожиданий по одному сообщению | Обработка частичных результатов и повтор партии |
| Асинхронные confirms с ограниченным окном | Можно держать ограниченное число публикаций в полёте | Нужно хранить состояние и безопасно перестраивать его после сбоя |

Окно в полёте ограничивай числом записей и байтами. Если брокер стал принимать медленно, произвольный список pending в JVM может заполнить память. Публикация из Outbox позволяет приостанавливать чтение новых строк, оставляя ещё не отправленную работу в контролируемом хранилище. Установи метрики: скорость confirm, время от отправки до подтверждения, число unknown исходов, возраст старейшей строки outbox. Временные ошибки подключения обрабатывай согласно бюджету повтора. Не считай повторный publish новой бизнес-командой, если первоначально событие уже логически существовало.

RabbitMQ может применить flow control или блокировать публикацию при ресурсной тревоге. Перезапуск producer в этом случае может добавить новые подключения, но он не освобождает диск брокера. Проверь memory/disk alarms и очередь сообщений. Отдельные publisher и consumer connections помогают различать эти роли и не связывать обработку подтверждений с заторможенной публикацией, если это соответствует настройкам клиента.

## Как consumer закрывает канал с незавершённой работой

Consumer получил доставки с тегами 10–14. Worker 12 завершил бизнес-операцию первым. Применить `basicAck(12, true)` опасно, потому что такое подтверждение затрагивает меньшие ещё открытые delivery tags канала. При независимом исполнении используй подтверждение отдельной доставки или веди доказанно завершённый непрерывный префикс. Delivery tag относится к каналу, выдавшему доставку. Сразу после reconnect новые tags нельзя сопоставлять с оставшимися старого канала.

Для штатной остановки consumer отменяет приём новых доставок, даёт уже взятым ограниченное время и подтверждает только зафиксированные. Длительная операция может иметь неизвестный исход. При закрытии канала брокер может вернуть unacked работу в очередь. Флаг redelivered является подсказкой о доставке, он не заменяет стабильный event ID. Два похожих сообщения, заново опубликованных из outbox, могут быть первыми доставками с точки зрения брокера; для пользовательского эффекта они остаются дубликатами.

**Практика потребления.** Если подключено сто consumers с prefetch 20, потенциальный объём unacked может достигать порядка 2000 доставок при обычной per-consumer конфигурации. Если средний payload 500 КБ, только payload объём уже около 1 ГБ в распределённых клиентах и транспорте при полном окне. Метаданные, распакованный JSON и результаты увеличат расход. Подбирай размер окна по размеру входа и месту удержания, сравнивая задержку ack и заполнение.

## Dead-lettering и redrive отличаются по моменту

DLX выбирается политикой/аргументом очереди. При reject без requeue, истечении TTL или других поддерживаемых причинах сообщение может быть отправлено в DLX. Для переноса требуется, чтобы обменник, маршрут и целевая очередь были пригодны. Гарантии при их недоступности зависят от типа и конфигурации очереди, у quorum доступна специальная схема at-least-once dead-lettering. Заполни причину через подходящие заголовки и наблюдай число записей, дошедших до цели. Срок хранения DLQ отдельно влияет на восстановимость.

**Redrive** — управляемый возврат отложенных записей для обработки после исправления. Пример: в воскресенье изменился ожидаемый enum, часть сообщений попала в DLQ. В понедельник новый handler читает прежний и новый варианты. Перед повтором проверь несколько сохранённых записей и подтверждённый результат. Публикуй ограниченной скоростью, с тем же message ID, в рабочий маршрут. Старый callback может стать бессмысленным из-за текущего состояния заказа. Применение проверяет доменную версию и разрешённый переход.

Если повтор осуществляется чтением DLQ и публикацией новой копии, отметь два окна. При падении до подтверждённой публикации исходник остаётся доступным. При падении после confirm новой копии до ack старой исходник может появиться снова. Порядок «сначала ack DLQ, затем publish» рискует потерять отложенную запись. FIFO труднее сохранить при redrive. Если обязательны упорядоченные дельты, планируй пересчёт или корректное восстановление ключа перед возобновлением нормального потока.

### Ограничить цикл отказа

Retry-политика должна отличать временную ошибку и сообщение, которое в текущем коде обработать невозможно. Непосредственный requeue может снова доставить его сразу, потратить CPU и скрыть полезную работу. У отложенного retry задай интервалы, общий предел попыток и состояние после исчерпания. При перезапуске счётчик попыток в памяти теряется, поэтому общую политику храни в поддерживаемых метаданных или устойчивом состоянии. Для диагностики покажи время первой ошибки, изменившуюся версию handler и последнюю причину.

## Самопроверка

<details>
<summary>Publisher потерял соединение после publish. Почему можно увидеть две записи с одним message ID?</summary>

Первая запись могла сохраниться, а confirm потеряться. Повтор восполняет неизвестный исход. Consumer проверяет ID и сохраняет ровно предусмотренный локальный эффект.

</details>

<details>
<summary>Почему количество DLQ уменьшилось, но законченных эффектов не стало больше?</summary>

Записи могли удалиться по retention, перенаправиться без подходящего маршрута или снова потерпеть ошибку после повторной отправки. Сопоставь подтверждения публикации, события обработки и фактический результат.

</details>

<details>
<summary>Пакетный ACK подтверждает только задачу, чей тег передали?</summary>

При multiple подтверждение охватывает соответствующий префикс текущего channel. При завершении задач вне очереди отмечай отдельные теги или веди завершённый префикс.

</details>
