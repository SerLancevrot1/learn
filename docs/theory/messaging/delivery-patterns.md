# Доставка событий: Inbox, Outbox и CDC

[Брокеры сообщений](README.md) · [Практика на примере кошелька](../../labs/spring-postgres-outbox.md#кошелёк-outbox-kafka-и-inbox)

Читай этот конспект, когда нужно связать доставку сообщения с изменением бизнес-данных. Для подтверждений, смещений и повторов внутри брокера есть отдельные конспекты по [Kafka](kafka.md) и [RabbitMQ](rabbitmq.md).

## 8. Идемпотентный consumer и inbox

`[ ]` **Короткий ответ:** consumer идемпотентен, если повторная обработка того же события не меняет итоговый результат. При at-least-once дубликаты неизбежны: rebalance после обработки до commit, ретраи producer после перезапуска, повторная публикация из outbox или DLQ. Способы: уникальный id события и таблица обработанных (inbox), уникальное ограничение в БД, естественно идемпотентные операции (`SET status = 'PAID'` вместо `balance = balance + 100`), версия агрегата.

```sql
CREATE TABLE processed_events (
    event_id     uuid PRIMARY KEY,
    processed_at timestamptz NOT NULL DEFAULT now()
);

-- в одной транзакции с бизнес-изменением:
INSERT INTO processed_events(event_id) VALUES (:eventId)
ON CONFLICT (event_id) DO NOTHING;
-- если вставлено 0 строк — событие уже обработано, выходим
UPDATE orders SET status = 'PAID' WHERE id = :orderId;
```

<details>
<summary>Тонкости</summary>

- Проверка и бизнес-изменение должны быть в одной транзакции БД. «Проверить в Redis, потом записать в БД» оставляет окно гонки и потери.
- Ключ дедупликации — идентификатор события из payload или заголовка, а не offset: после повторной публикации (outbox, DLQ replay) у дубля будет другой offset.
- Таблицу нужно чистить: окно дедупликации должно быть больше максимального срока, через который может прийти дубль (retention, время replay).
- Внешний вызов (платёжный шлюз) делайте с idempotency key, который передаёте получателю, — тогда повтор безопасен на его стороне.

</details>

## 9. Outbox и CDC

`[ ]` **Короткий ответ:** проблема dual write — сервис пишет в БД и публикует событие в брокер, а общей транзакции нет. Если упасть между двумя операциями, БД и брокер расходятся: заказ создан, события нет, или наоборот. Outbox: в той же локальной транзакции, что и бизнес-изменение, записываем событие в таблицу `outbox`. Отдельный relay (polling или CDC, например Debezium) читает таблицу и публикует в брокер. Отправка становится at-least-once: relay может повторить событие после сбоя, поэтому consumer должен быть идемпотентным.

```sql
BEGIN;
INSERT INTO orders(id, status) VALUES (:id, 'CREATED');
INSERT INTO outbox(id, aggregate_type, aggregate_id, type, payload)
VALUES (gen_random_uuid(), 'order', :id, 'OrderCreated', :json);
COMMIT;
```

<details>
<summary>Polling или CDC</summary>

| | Polling relay | CDC (Debezium) |
|---|---|---|
| Как | Периодически `SELECT ... FOR UPDATE SKIP LOCKED`, отправка, пометка | Читает журнал транзакций БД (WAL, binlog) через Kafka Connect |
| Задержка | Интервал опроса | Меньше, почти поток |
| Нагрузка на БД | Запросы к таблице | Чтение журнала, слот репликации |
| Сложность | Код в приложении | Инфраструктура Connect, мониторинг слота |
| Порядок | Нужно сортировать и отправлять по агрегату | Порядок коммитов в журнале |

- Ключ сообщения = `aggregate_id`, чтобы сохранить порядок событий агрегата.
- Таблицу outbox чистят или архивируют; при CDC можно удалять строку сразу после вставки — событие уже попало в WAL.
- Нужен мониторинг lag relay: остановившийся relay — тихая поломка интеграции.
- Отправлять событие «после коммита» из кода (`@TransactionalEventListener`) — не outbox: падение процесса между commit и отправкой теряет событие.

</details>

**Уточняющие вопросы:**

- Зачем inbox, если есть outbox? Outbox решает проблему на стороне отправителя, inbox — дубли на стороне получателя. Вместе они дают «эффективно ровно один раз» для бизнес-результата.
- Чем outbox отличается от saga? Outbox — надёжная публикация одного события. Saga — последовательность локальных транзакций в разных сервисах с компенсациями; шаги саги обычно публикуются через outbox.
