## Какое обещание даёт каждый участник

Для операции «начислить 100» удобно нарисовать четыре сохраняемых результата. В БД отправителя появляется команда. В брокере появляется событие. В БД потребителя меняется баланс. Брокер получает подтверждение или новую позицию чтения. Это четыре разных момента, между которыми возможны падения.

| Что сохранили | Что теперь известно | Чего ещё ждём |
| --- | --- | --- |
| Команду и outbox в БД отправителя | Запрос принят, есть данные для возобновления отправки | Отправки в брокер |
| Событие в брокере | Брокер принял публикацию по своим настройкам | Бизнес-обработки |
| Эффект и inbox в БД потребителя | Эффект для этого ID зафиксирован | Подтверждения чтения |
| Позицию Kafka или RabbitMQ ACK | Брокер может продвинуть чтение группы или завершить доставку сообщения | Дальнейших шагов процесса, если они существуют |

Если клиент получил тайм-аут, он знает лишь, что готового ответа не было к дедлайну. Команда могла успешно сохраниться. Повтор с тем же ключом должен найти первую команду. Если клиент с тем же ключом прислал другую сумму, это конфликт параметров. Если он открывает новую операцию, понадобится новый ключ. Один ключ удобно привязать к клиенту и типу операции, чтобы совпадение строк у разных клиентов было безопасным.

**Три ID из примера.** `requestId` позволяет повторить запрос «начислить 100». `eventId` позволяет обработать опубликованный факт только один раз в пределах одного эффекта. `walletId` выбирает кошелёк и может стать ключом партиции. По одному `walletId` могут законно пройти тысячи разных начислений. У одного запроса может быть несколько разных событий, например `CreditRequested` и `CreditApplied`.

## 8. Идемпотентный consumer и inbox

**Короткий ответ.** Consumer идемпотентен, если повтор того же события сохраняет бизнес-результат. Дубликаты возможны при сбое после обработки, повторной публикации из outbox и повторном чтении из DLQ. Защититься помогают уникальный ID события, ограничение в БД, условный переход состояния и версия агрегата.

```sql
CREATE TABLE processed_events (
    event_id     uuid PRIMARY KEY,
    processed_at timestamptz NOT NULL DEFAULT now()
);

-- в одной транзакции с бизнес-изменением:
INSERT INTO processed_events(event_id) VALUES (:eventId)
ON CONFLICT (event_id) DO NOTHING;
-- если вставлено 0 строк — событие уже обработано, выходим
UPDATE orders SET status = 'PAID' WHERE id = :orderId AND status = 'NEW';
```

<details>
<summary>Тонкости</summary>

- Проверка и бизнес-изменение должны быть в одной транзакции БД. «Проверить в Redis, потом записать в БД» оставляет окно гонки и потери.
- Ключ дедупликации — идентификатор события из payload или заголовка, а не offset: после повторной публикации (outbox, DLQ replay) у дубля будет другой offset.
- Таблицу нужно чистить: окно дедупликации должно быть больше максимального срока, через который может прийти дубль (retention, время replay).
- Внешний вызов (платёжный шлюз) делайте с idempotency key, который передаёте получателю, — тогда повтор безопасен на его стороне.

</details>

### Почему проверку ставят в одну транзакцию с эффектом

Два worker получили одну запись. Оба успели выполнить `SELECT` и увидели, что ID ещё не обработан. Если проверка заканчивается на чтении, оба выполнят `balance = balance + 100`. Уникальный индекс переносит решение в атомарную операцию: один worker успешно вставляет ID, другой либо дожидается результата, либо получает конфликт. При rollback первого второй может обработать запись.

1. Начни транзакцию БД. Вставь `(consumer_name, event_id)` с уникальным ограничением.
2. Если ID вставлен, выполни бизнес-эффект. Проверь число затронутых строк и обработай неожиданный результат. Например, если кошелька ещё нет, сделай rollback и реши, можно ли повторить позже. Если событие должно считаться окончательно отклонённым, сохрани это как явный результат.
3. После commit подтверди обработку брокеру. Если ответ на commit потерялся, повтор должен снова пройти через дедупликацию.
4. Если ID уже есть, эффект был зафиксирован раньше. Заверши обработку согласно контракту дубля.

`consumer_name` нужен, если таблицу разделяют несколько независимых эффектов. Начисление и формирование отчёта обязаны обработать событие каждый у себя. Если тот же `eventId` внезапно пришёл с другим payload, это ошибка контракта. Сохрани отпечаток важных полей и подними сигнал, если такой сценарий возможен.

Окно Inbox выбирают по бизнес-риску. Если повторы приходят до семи дней, а расследование с replay возможно через месяц, семи дней мало. При бессрочном требовании «никогда не начисляй тот же перевод снова» полезнее доменный ledger с постоянным уникальным ID перевода. Перестроение производной витрины может использовать отдельный namespace или новую таблицу состояния.

### Когда достаточно условного изменения

Для `SET status = 'PAID'` повтор даёт то же значение лишь при выполнении нужных условий. Поздний дубль после `REFUNDED` способен вернуть заказ в прежний статус. Используй переход `NEW → PAID` и проверь `WHERE status = 'NEW'`, при необходимости добавь версию. Повтор той же версии можно пропустить, конфликтующий переход следует обработать по правилам домена. Если при каждом обновлении SQL-триггер пишет аудит или генерируется письмо, эти эффекты тоже включи в определение идемпотентности.

Для внешнего провайдера локальная БД не может атомарно зафиксировать его ответ вместе со своим commit. Храни состояние попытки и передавай стабильный ключ провайдеру, если он поддерживает такую гарантию. При тайм-ауте сверяй результат по ключу или ссылке операции. Назови срок действия ключа у провайдера и процедуру для неизвестного исхода. [Пример с платежом и поздним ответом](../architecture/cases/payments.md)

## 9. Outbox и CDC

`[ ]` **Короткий ответ:** проблема dual write — сервис пишет в БД и публикует событие в брокер, а общей транзакции нет. Если упасть между двумя операциями, БД и брокер расходятся: заказ создан, события нет, или наоборот. Outbox: в той же локальной транзакции, что и бизнес-изменение, записываем событие в таблицу `outbox`. Отдельный relay (polling или CDC, например Debezium) читает таблицу и публикует в брокер. Отправка становится at-least-once: relay может повторить событие после сбоя, поэтому consumer должен быть идемпотентным.

```sql
BEGIN;
INSERT INTO orders(id, status) VALUES (:id, 'CREATED');
INSERT INTO outbox(id, aggregate_type, aggregate_id, type, payload)
VALUES (gen_random_uuid(), 'order', :id, 'OrderCreated', :json);
COMMIT;
```

<details>
<summary>Polling или CDC</summary>

| | Polling relay | CDC (Debezium) |
|---|---|---|
| Как | Периодически выбирает или захватывает готовые записи, отправляет, отмечает результат | Читает изменения из журнала транзакций БД через коннектор |
| Задержка | Интервал опроса плюс очередь и отправка | Поток с задержкой коннектора, журнала и брокера |
| Нагрузка на БД | Запросы к таблице | Чтение журнала, слот репликации |
| Сложность | Код в приложении | Инфраструктура Connect, мониторинг слота |
| Порядок | Нужно сортировать и отправлять по агрегату | Порядок коммитов в журнале |

- Ключ `aggregate_id` направляет события в одну партицию при стабильной схеме партиционирования. Relay должен отправить их в нужном порядке.
- Таблицу outbox чистят или архивируют по согласованной политике. Для CDC учти начальный snapshot, восстановление слота и возможную необходимость повторной выгрузки.
- Нужен мониторинг lag relay: остановившийся relay — тихая поломка интеграции.
- Отправлять событие «после коммита» из кода (`@TransactionalEventListener`) — не outbox: падение процесса между commit и отправкой теряет событие.

</details>

### Что происходит при сбое relay

| Точка сбоя | Результат | Как восстанавливаемся |
| --- | --- | --- |
| Бизнес-транзакция оборвалась до commit | Отсутствуют и заказ, и строка outbox | Клиент при необходимости повторяет исходную команду |
| После commit, до первой публикации | Строка готова к отправке | Другой проход relay находит её |
| Брокер принял запись, подтверждение потерялось | Relay видит неопределённый исход | Повторяет с прежним `eventId`, consumer дедуплицирует |
| Confirm получен, отметка отправки не сохранена | У брокера есть запись, у relay работа всё ещё открыта | Повтор возможен, ID остаётся прежним |
| Отметили отправку до подтверждения, процесс упал | Запись может остаться только в БД с отметкой «отправлено» | Такой порядок ломает гарантию, применяй отметку после подтверждения |

**Polling.** Простая реализация захватывает строки `FOR UPDATE SKIP LOCKED` и удерживает блокировки до завершения пачки. При долгой сетевой отправке это увеличивает длительность транзакций и расход соединений. Альтернатива — в короткой транзакции назначить владельца и срок аренды, отправить вне неё, затем условно подтвердить результат с тем же токеном владельца. Истёкшую аренду можно перехватить. Если старый worker успел отправить событие после истечения, повтор возможен, поэтому идентификатор остаётся стабильным. Условная отметка блокирует устаревшего владельца только на стороне БД.

У outbox удобно хранить `id`, `aggregate_id`, версию, тип события, payload, время создания и состояние доставки. Для polling добавь `next_attempt_at` и число попыток, обоснуй индекс поиска готовых записей и договорись о судьбе непубликуемой записи. Одна проблемная запись должна быть видна в мониторинге. Если порядок по объекту обязателен, более поздние записи этого объекта могут требовать ожидания или явного решения о пропуске.

**CDC.** Debezium читает изменения БД, а Outbox Event Router превращает вставку из прикладной таблицы в контракт события. Это разделяет бизнес-схему таблиц и публичную схему. У PostgreSQL логический слот удерживает нужные WAL-сегменты, пока потребитель отстаёт. При длительном простое может вырасти занятое место на диске. Следи за отставанием и размером удержанного WAL. Восстановление из новых snapshot и слотов влияет на возможность replay. Опиши, откуда доставать события, если изменился исходный журнал. [Debezium, Outbox Event Router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html) · [PostgreSQL, логическое декодирование и слоты](https://www.postgresql.org/docs/17/logicaldecoding-explanation.html)

**Гарантия при оговорённых условиях.** Outbox оставляет сохраняемое намерение. Доставка зависит от работающего relay, доступности брокера, срока хранения и обработки окончательных ошибок. Измеряй возраст старейшей неопубликованной записи, число готовых записей, скорость успешных публикаций и длительность сбоя. Общее число строк слабее отражает задержку, если оно включает историю.

## Порядок, повторы и повторное чтение

Представь поток `OrderCreated(v1)`, `OrderPaid(v2)`, `OrderRefunded(v3)`. Если `v2` ждёт отдельного retry, а `v3` уже дошло, потребителю приходится выбрать политику. Для **снимка** состояния с полной информацией чаще можно записать более свежую версию и пропускать старые. Для **дельты** «прибавь 100» пропуск пропущенной версии теряет эффект. Дельты приходится применять последовательно, дочитывать пропуск или пересчитывать состояние из источника.

| Политика повторов | Что выиграли | Что проверяем |
| --- | --- | --- |
| Остановили партицию на проблемной записи | Последующие записи ждут, порядок сохраняется | Время блокировки остальных ключей в партиции |
| Отправили запись в retry topic или очередь | Остальной поток продолжает работу | Допустимость перестановки, число попыток, стабильный ID |
| Перенесли в DLQ | Изолировали окончательную ошибку | Кто расследует, исправляет и выполняет replay |

Сетевые тайм-ауты и временную недоступность разумно повторять с ограничением попыток, backoff и jitter. Ошибка разбора схемы редко исчезнет от повторения того же payload. При replay сохраняй ID и учитывай текущую версию сущности. Массовый replay запускай с ограниченной скоростью, чтобы он не вытеснил текущий трафик. Проверь, что после удаления Inbox старые дубликаты не могут повторно изменить деньги или права.

**На интервью.** Нарисуй простую шкалу: commit БД → publish → confirm → commit consumer → ack. Прерви процесс в любом промежутке и проговори, из какого сохранённого факта продолжится работа. Этого достаточно, чтобы обсудить стоимость дубля, недоступность брокера и границу exactly-once.

## Самопроверка

<details>
<summary>Broker confirm получен, relay не успел записать published_at. Повторит ли брокер начисление?</summary>

Relay может создать ещё одну запись в брокере. Consumer с транзакционным Inbox увидит уже обработанный ID и сохранит прежний баланс. Проверка касается двух разных состояний: числа доставок и числа зафиксированных эффектов.

</details>

<details>
<summary>Событие записали в Inbox, затем SQL изменения баланса вернул ошибку. Что будет после повторной доставки?</summary>

Если обе операции были в общей транзакции и она откатилась, ID снова можно вставить. Брокеру нельзя подтверждать исходную обработку до успешного commit или иного явного решения об окончательном результате.

</details>

<details>
<summary>Слот CDC отстал, свободное место на диске падает. Почему это связано?</summary>

Слот может удерживать WAL, который ещё нужен для чтения. Измерь удержание и отставание, восстанови продвижение коннектора и оцени предел диска. Пересоздание слота меняет точку чтения, поэтому нужен план восстановления событий.

</details>

**Дополнительные вопросы**

- Зачем inbox, если есть outbox? Outbox сохраняет намерение отправителя. Inbox защищает эффект получателя при повторах. В пределах общей транзакции обработчика и окна дедупликации это позволяет применить локальный эффект один раз для каждого ID.
- Чем outbox отличается от saga? Outbox — надёжная публикация одного события. Saga — последовательность локальных транзакций в разных сервисах с компенсациями; шаги саги обычно публикуются через outbox.
