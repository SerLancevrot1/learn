## Какой смысл у записи

Заказ может передаваться сообщением «заплатили 100», сообщением «текущий оплаченный остаток 100» или командой «начисли 100». Три payload могут содержать один и тот же ID и число, а при повторе и пропусках дают разный результат. Перед выбором retention и обработчика ответь, является запись самостоятельным фактом, изменением состояния или командой владельцу.

**Дельта** `BalanceCredited(amount=100)` должна примениться один раз. Если удалить промежуточную дельту, сумма больше не восстановится. **Снимок** `BalanceChanged(total=300, version=7)` можно применить по правилу максимальной версии, если его полей достаточно. Два события с одинаковой версией и разным содержимым — нарушение источника. **Команда** `CreditWallet` должна быть принята владельцем, проверяющим ограничения. Потребитель, строящий отчёт, не должен самостоятельно создавать списание из факта, если это не его явная роль.

### Delete retention и compaction

Kafka хранит данные сегментами. Политика delete освобождает сегменты после ожидаемого времени или объёма по правилам брокера. Это ограничивает срок, на котором consumer может возобновиться из старого offset. При out-of-range выбери явную политику: остановиться для восстановления, начать с доступного начала или перейти к новым данным. Автоматический переход к latest может молча перескочить работу.

При `cleanup.policy=compact` брокер старается сохранять последнюю запись для каждого ключа. Старые версии могут оставаться до выполнения compaction. Consumer обязан учитывать их и возможные пробелы в offsets. Tombstone — запись с ключом и значением null, выражающая удаление состояния. У него собственное окно хранения. Если consumer очень долго строит состояние из компактируемого топика, ему нужно успеть учесть удаления по предусмотренной политике. При `compact,delete` удаление старых сегментов ограничивает историю даже для ключа, который давно не обновлялся.

**Пример.** В компактируемом топике есть `customer:1 = address A`, `customer:1 = address B`, затем tombstone. Новый потребитель видит доступную историю и после tombstone должен удалить запись. Если сервис держит локальную копию из старого backup, а tombstone уже исчез, простой догон с неизвестно устаревшей позиции может оставить «воскресшего» клиента. Для восстановления выбирай пригодную точку, новую пустую витрину или явную сверку со снимком источника.

Compaction действует по байтовому ключу и порядку записей в партиции. Она не сравнивает доменное поле `version`. Если продюсер по ошибке записал v7 после v8, compaction может сохранить более позднюю запись с меньшей версией. В системе обеспечь корректный порядок в источнике или правила публикации. При изменении сериализации того же логического ключа возможны два разных байтовых ключа. Это затрагивает партиционирование, порядок и compaction.

## Kafka Streams как часть Java-приложения

В библиотеке Streams приложение описывает топологию: читает входы, преобразует записи, группирует по ключу, хранит локальное состояние и при необходимости пишет результат. Топология исполняется задачами, распределёнными по экземплярам того же application ID. Состояние агрегируемого ключа обычно принадлежит задаче. Локальный state store ускоряет чтение и обновление. Для восстановления он может использовать changelog topic, из которого новая задача восстановит состояние.

| Понятие | Как объяснить на заказах |
| --- | --- |
| `KStream` | Каждый вход — событие. Два платежа для одного ID дают два входа |
| `KTable` | Ключ соответствует текущему значению. Новая запись по ключу обновляет представление, tombstone его удаляет |
| Repartition topic | Нужен переместить записи по новому ключу, чтобы одинаковые ключи выполнялись в одной задаче |
| Changelog topic | Хранит изменения состояния, нужные для восстановления расчёта |
| Standby task | Поддерживает готовую копию состояния для более быстрого возобновления при переносе задачи |

**Пример группировки.** Вход хранится по ключу `orderId`, а надо считать выручку по `merchantId`. `selectKey` меняет логический ключ результата. Для группировки по нему записи должны перераспределиться по партициям. Это добавляет запись и чтение внутреннего топика. При большом количестве данных проверь стоимость и настройки. Если один крупный мерчант занимает 40% входа, все его записи направятся в одну партицию при едином ключе. Для ассоциативной суммы можно посчитать по частичным ключам и объединить, учитывая правила окна, порядок обновлений и появление промежуточных значений.

**Join потоков.** Для обычного join двух потоков нужно определить ключ и временное окно, в котором ищутся пары. Иначе пришлось бы помнить всю историю. Разное число партиций или разные правила выбора партиции мешают совместить пары на одной задаче. Справочник, представленный таблицей, позволяет обогатить событие текущим известным значением. Если задача требует курс валюты на момент сделки, текущего справочника может быть недостаточно. Нужны правила проверки времён и версия курса.

### Event time и поздние записи

Заказ создан в 10:57 у клиента, запись дошла до обработчика в 11:03. По времени события она относится к окну 10:00–11:00. По времени обработки — к 11:00–12:00. Для бизнес-отчёта выбери, какое время определяет группу. Grace period задаёт, как долго окно принимает допустимое опоздание по семантике Streams. Часы wall clock и прогресс stream time могут расходиться. Один вход с сильно ошибочным timestamp может сдвинуть расчёт и изменить судьбу последующих записей. Ограничь допустимый диапазон входного времени и наблюдай отброшенные поздние события.

Пример двухминутного окна: промежуточная сумма может меняться после каждой записи. Если downstream хочет одно окончательное значение, потребуется ждать закрытия окна или поддерживать upsert по ключу окна. Ожидание увеличивает задержку, буферизация требует памяти или state store, а пересчёт после grace должен быть предусмотрен отдельно. На интервью сравни «текущее значение окна» и «зафиксированный финальный отчёт» как два разных контракта.

### Exactly-once в топологии

При подходящей настройке Streams координирует обработку входных offsets, обновления состояния и вывод в Kafka с транзакциями Kafka. После сбоя вычисление может выполняться повторно, а результаты Kafka видны с учётом зафиксированных транзакций. Если оператор ещё вызвал JDBC или отправил email, этот ресурс не включён в транзакцию. Для таких эффектов применяй отдельного consumer с idempotency/inbox или другой явный протокол.

После масштабирования новое размещение задачи может восстанавливать state store. Время зависит от объёма changelog, наличия standby и доступных ресурсов. Поэтому расширение числа экземпляров может временно увеличить задержку. Измеряй длительность восстановления, состояние задач, отставание по партиции и свежесть результата, а не только число pod.

## Как менять схему событий

Старые записи живут дольше одного релиза. Совместимость нужно проверить в обе стороны. **Backward** обычно означает, что новый reader читает прежние записи. **Forward** означает, что старый reader может читать новые записи. Поддержка обеих полезна для смешанных версий. У конкретного registry настройки могут проверять одну предыдущую схему или всю историю. Для replay старых сегментов важна вся необходимая история.

### Условный пример Avro

Старая запись `OrderPaid` хранит `orderId`, `amountCents` и `currency`. Хочется добавить `channel`. Новый reader может дать значение по умолчанию, когда writer schema прошлого события не содержит поле. Старый reader пропускает поле из новой writer schema, если оно ему неизвестно. Это вопрос разрешения между схемами, поле с default не обязательно отсутствует в бинарной записи нового writer. Если хочется удалить поле, убедись, что старые reader, которым оно нужно, имеют подходящий default или перестали читать новые записи.

Миграция имени поля может потребовать alias в reader schema и проверки старого consumer. Изменение единицы, например переход от копеек к рублям, может пройти формальную проверку, если оба значения остаются long. Смысл при этом изменится и расчёт ошибётся в сто раз. Версионируй новое поле с явной единицей или новый вид события. Для денежных сумм не полагайся на то, что новые значения «отличатся по виду». Сохрани тест на реальные старые payload.

### Конвертация и событие, которое не читается

Deserialization failure происходит ещё до вызова части обычной бизнес-логики. Раздели отказ decode и отказ применения уже понятного события. Для decode сохрани координаты входа, тип схемы, исходные байты по политике данных и причину. Для применения сохрани event ID, версии и ошибку бизнес-правила. Классификация определяет, можно ли повторить без редеплоя. После исправления воссоздай поток по выбранной позиции или redrive с сохранением ID.

У публикации новой схемы перед rollout есть зависимость: иногда producer перестаёт работать, если registry недоступен и у клиента ещё нет нужного schema ID. У consumer после очистки кеша может возникнуть аналогичная зависимость на чтении. Ограничь тайм-аут, измеряй ошибки реестра отдельно от ошибок брокера и проверь восстановление после холодного старта.

## Самопроверка

<details>
<summary>В компактируемый топик пишут начисления по ключу кошелька. Можно ли восстановить баланс из доступной истории?</summary>

Для дельт compaction может удалить существенные начисления. Нужен полный журнал дельт в пределах контракта, либо актуальный снапшот баланса, версия и правила восстановления последующих изменений.

</details>

<details>
<summary>Почему добавление pod не распределило нагрузку одного мерчанта?</summary>

Группировка требует обработки ключа в соответствующей задаче. Один горячий ключ остаётся горячим даже при переносе. Измерь распределение, затем оцени разбиение только для операции, допускающей независимые частичные результаты.

</details>

<details>
<summary>Проверка совместимости схемы прошла, после деплоя отчёт увеличился в сто раз. Где искать?</summary>

Проверь семантику полей и единицы измерения. Совместимость типов позволяет прочитать байты. Тесты старых payload и бизнес-ожиданий должны отдельно подтвердить смысл.

</details>
