## 1. Что это и какую проблему решает

**Spec Kit** — открытый набор инструментов GitHub для организации работы с ИИ-агентом. Основной рассматриваемый здесь процесс — **spec-driven development, SDD**: сначала описываем требуемое поведение, затем техническое решение, задачи и реализацию.

Без такого процесса легко получить ситуацию: пользователь имел в виду одно, агент понял другое, тесты закрепили эту трактовку, а через день никто не помнит первоначальные условия. Spec Kit помогает вынести намерения и промежуточные решения в проверяемые файлы. Это инструменты и инструкции для агента; программирует по-прежнему Codex или другой выбранный агент.

Представь задачу «добавь экспорт истории кошелька». До реализации нужно решить:

- Какие операции попадут в экспорт?
- Сумма в рублях или копейках?
- Как обрабатывать пустую историю и неизвестный кошелёк?
- Как сортировать записи и различать одинаковое время?
- Должны ли повторно доставленные события появляться второй раз?
- Нужны ли ограничения размера выгрузки и права доступа?

Сам по себе длинный промпт не обеспечивает ответы. Полезен процесс, в котором ты читаешь спецификацию, замечаешь пропуски и исправляешь их **до** того, как агент построит реализацию вокруг догадок.

## 2. Как Spec Kit связан с Codex, AGENTS.md и skills

| Компонент | Его работа |
| --- | --- |
| Codex | Исследует код, выполняет инструкции, пишет реализацию, запускает проверки |
| `AGENTS.md` | Объясняет постоянные рабочие соглашения репозитория |
| Spec Kit CLI, команда `specify` | Устанавливает и обслуживает инфраструктуру процесса |
| Skills `speckit-*` | Проводят агента через этапы работы |
| `.specify/memory/constitution.md` | Хранит принципы, относительно которых оценивается решение |
| `spec.md` | Описывает требуемое поведение конкретной фичи |
| `plan.md` | Описывает технический подход |
| `tasks.md` | Разбивает работу на выполняемые задачи |

Пример различия: «используй Maven Wrapper» — рабочая инструкция; «повтор события не должен повторно менять баланс» — инвариант; «CSV использует UTF-8» — требование конкретной фичи. Не копируй весь текст между документами: указывай ссылки и устраняй противоречия.

В v1.4.2 интеграция Codex размещает навыки в `.agents/skills/speckit-<команда>/SKILL.md`; в чате они вызываются через **`$speckit-<команда>`**. Примеры `/speckit.specify` из других руководств не являются универсальным синтаксисом. Официальная интеграция описана для **Codex CLI**; в приложении сначала проверь обнаружение локальных навыков. Если интерфейс их не показывает, начни новую сессию или используй CLI. [Интеграция Codex v1.4.2](https://github.com/github/spec-kit/blob/v1.4.2/docs/integrations/codex.md).

## 3. Установка в Windows PowerShell

### Что потребуется

- Python 3.11 или новее и `uv` для показанного способа установки.
- Git для установки из репозитория и для обычной работы с этим проектом.
- Установленный и авторизованный Codex CLI для документированной интеграции.

PowerShell-скрипты поддерживаются без обязательного WSL. Сначала проверь инструменты:

```powershell
python --version
git --version
uv --version
codex --version
```

Если `uv` отсутствует, официальный Windows-вариант через WinGet:

```powershell
winget install --id=astral-sh.uv -e
```

После установки открой новый терминал и повтори `uv --version`. Источник: [установка uv для Spec Kit](https://github.com/github/spec-kit/blob/v1.4.2/docs/install/uv.md).

### Установить CLI фиксированной версии

```powershell
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@v1.4.2
specify version
specify check
specify init --help
```

`specify version` проверяет доступность и версию CLI, `specify check` — наличие окружающих инструментов. Это не проверка корректности твоего приложения. Обычный повтор `uv tool install` не обновляет уже установленную копию автоматически. Если CLI уже есть, сначала выясни его версию и способ установки. [Официальная установка](https://github.com/github/spec-kit/blob/v1.4.2/docs/installation.md).

### Самая простая проба: отдельный учебный проект

Из каталога, в котором хочешь создать новую папку:

```powershell
specify init wallet-export-demo --integration codex --script ps
Set-Location wallet-export-demo
codex
```

Здесь создаётся новый проект с инфраструктурой Spec Kit; исходный репозиторий `learn` эта команда не превращает в демо автоматически.

### Подключить к существующему learn

Сначала сохрани текущую работу обычным для себя способом и убедись, что понимаешь исходный diff. Затем создай отдельную ветку. Команды ниже — пример для выполнения пользователем, они не запускались при подготовке руководства:

```powershell
Set-Location C:\Users\limon\IdeaProjects\learn
git status --short
git switch -c codex/try-spec-kit
specify init --here --force --integration codex --script ps
git status --short
git diff
```

`--here` выбирает текущую директорию; `--force` разрешает инициализацию непустой папки и может перезаписать совпавшие управляемые пути. Поэтому сначала нужен сохранённый исходный результат, затем просмотр изменений. Новые неотслеживаемые файлы смотри отдельно: обычный `git diff` не показывает их содержимое.

Начни с одной ограниченной новой фичи, а не с просьбы автоматически описать весь старый проект. Официальное руководство рекомендует именно постепенное внедрение. [Spec Kit в существующем проекте](https://github.com/github/spec-kit/blob/v1.4.2/docs/how-to/existing-projects.md).

## 4. Какие файлы появляются

Примерная структура для процесса SDD; дополнительные файлы зависят от интеграции и установленных расширений:

```text
learn/
├── .agents/skills/
│   ├── speckit-constitution/SKILL.md
│   ├── speckit-specify/SKILL.md
│   └── ...
├── .specify/
│   ├── memory/constitution.md
│   ├── scripts/
│   ├── templates/
│   └── feature.json
└── specs/
    └── <каталог-фичи>/
        ├── spec.md
        ├── plan.md
        ├── tasks.md
        ├── research.md
        ├── data-model.md
        ├── contracts/
        ├── quickstart.md
        └── checklists/
```

`research.md`, модель и контракты относятся к проектированию; конкретные артефакты оценивай по задаче. Для простой фичи не нужно выдумывать отдельную сложную архитектуру ради заполнения шаблона. См. [шаблон этапа планирования v1.4.2](https://github.com/github/spec-kit/blob/v1.4.2/templates/commands/plan.md).

В текущем процессе активная фича выбирается через `.specify/feature.json`, с возможным переопределением `SPECIFY_FEATURE_DIRECTORY`. **Переключить Git-ветку недостаточно, чтобы переключить фичу.** Автоматические feature-ветки теперь относятся к опциональному расширению `git`; не рассчитывай на них как на обязательное поведение ядра. [Контекст фичи в Quickstart](https://github.com/github/spec-kit/blob/v1.4.2/docs/quickstart.md#recommended-process).

## 5. Сквозной пример: экспорт истории кошелька

Это новая учебная фича поверх существующей идеи `WalletLedger`. Текущий ledger хранит баланс и inbox; наличие полной истории операций нельзя предполагать. Её хранение и связь с зачислением нужно спроектировать отдельно.

Дальше каждый блок `text` отправляется **отдельным запросом в чат Codex**, после чтения результата предыдущего. Не вставляй `$speckit-*` в PowerShell: `$` там имеет значение переменной.

### Шаг 1. Constitution: принципы проекта

```text
$speckit-constitution Зафиксируй правила для учебного Java/Spring-проекта.
Корневой модуль остаётся совместимым с Java 17.
Суммы кошелька хранятся в целых копейках.
Повторная доставка одного события не должна повторно менять баланс.
Маркер обработки и бизнес-изменение должны фиксироваться атомарно.
Изменения поведения проверяются релевантными тестами.
Документация объясняет границы учебных упрощений.
Не добавляй микросервисы и новые брокеры ради этой фичи.
```

Прочитай `.specify/memory/constitution.md`. Здесь нужны немногочисленные принципы, которые ты готов соблюдать. Правило «всегда 100% покрытия и production-grade всё» обычно создаёт шум вместо ясности. Constitution создают в начале и обновляют при изменении принципов, а не заново для каждого запроса.

### Шаг 2. Specify: что должна делать фича

```text
$speckit-specify Добавь учебный экспорт истории зачислений кошелька в CSV.
Пользователь задаёт walletId и получает историю успешных зачислений.
Поля: eventId, walletId, amountKopecks, occurredAt.
Повторная доставка события не создаёт новую строку истории.
Для существующего кошелька без операций CSV содержит только заголовок.
Для неизвестного кошелька возвращается понятная ошибка.
Порядок: occurredAt по возрастанию, затем eventId по возрастанию.
Учебный запуск локальный: авторизация и массовые выгрузки вне объёма.
Не объявляй такой API готовым для публичного использования.
Уточни неоднозначные условия до технической реализации.
```

В `spec.md` проверь, что слова «успешное зачисление» и «повтор» имеют однозначный смысл. Что произойдёт, если один `eventId` придёт с другой суммой? Если текущая реализация уже задаёт поведение, новое требование должно явно его сохранить или изменить.

### Шаг 3. Clarify: закрыть неоднозначности

```text
$speckit-clarify Проверь правила времени, область уникальности eventId,
CSV-экранирование, ошибку неизвестного кошелька и верхнюю границу выгрузки.
Выдели решения, которые меняют существующее поведение WalletLedger.
```

Ответь на вопросы и прочитай обновлённую спецификацию. Например, можно согласовать такие **новые** условия:

- `occurredAt` — время приёма операции сервисом в UTC, формат ISO 8601.
- `eventId` уникален глобально, как в текущем inbox; повтор не создаёт операцию.
- CSV — UTF-8, запятая как разделитель, обязательное экранирование значений.
- Неизвестный кошелёк — HTTP 404, пустой идентификатор — HTTP 400.
- До 1000 операций; при превышении — HTTP 422 без частичной выгрузки.

Эти значения выбраны для упражнения. В рабочем продукте лимит и контракт ошибок определяются требованиями. Не позволяй агенту выдавать свои удобные предположения за уже согласованные решения.

### Шаг 4. Plan: техническое решение

```text
$speckit-plan Используй существующий стек корневого проекта:
Java 17, Spring Boot, JDBC, Maven Wrapper.
Сначала изучи WalletLedger, схему inbox и тесты.
Историю успешных зачислений сохраняй в той же транзакции,
что изменение баланса и inbox-маркер.
Предложи минимальные изменения схемы, слой чтения и HTTP endpoint.
Не меняй публичную сигнатуру applyOnce без отдельного обоснования.
Для времени предусмотрь управляемый Clock.
Для CSV выбери подход с учётом уже имеющихся зависимостей.
Запланируй тесты rollback, дубля, сортировки, ошибок и лимита.
Отдельно оцени, какие проверки требуют настоящего PostgreSQL.
```

Теперь можно обсуждать таблицы, классы и транзакции. Проверь ключевую связь: если баланс изменился, а история не записалась, экспорт не соответствует требованиям. Добавление новой таблицы само по себе этого не решает.

`plan.md` должен содержать подход и причины решений, а не просто список новых файлов. Если агент предлагает Kafka, S3 и отдельный сервис для учебного CSV, верни его к границам задачи.

### Шаг 5. Checklist: проверка качества требований

```text
$speckit-checklist Проверь полноту и однозначность требований экспорта:
пустая история, дубли, формат времени, порядок, CSV-экранирование,
лимит и контракт ошибок. Не расширяй согласованный объём.
```

Этот checklist оценивает качество требований. Он **не заменяет исполняемые тесты** и не доказывает готовность кода. Сгенерированные пользовательские checklist-файлы проверяет reviewer; галочку ставят после оценки критерия. Встроенный `checklists/requirements.md` имеет отдельный жизненный цикл у specify/clarify. [Различие checklist и реализации](https://github.com/github/spec-kit/blob/v1.4.2/docs/reference/agentic-sdd.md).

### Шаг 6. Tasks: исполнимые задачи

```text
$speckit-tasks Разбей согласованный план на небольшие задачи
с зависимостями, целевыми файлами и проверками.
Не считай изменение баланса и запись истории независимыми частями.
```

Пример **ожидаемой конкретности**, а не буквального вывода команды:

```text
[ ] Добавить схему истории и проверить её ключи/ограничения.
[ ] Добавить сохранение истории в существующую транзакцию.
[ ] Проверить, что ошибка откатывает и баланс, и историю, и inbox.
[ ] Добавить чтение с согласованной сортировкой и контролем лимита.
[ ] Добавить CSV и HTTP-контракт с тестами ошибок.
[ ] Обновить документацию запуска и ограничения учебного примера.
```

Если задачи требуют API, которого ещё не спроектировали, вернись к плану. Если два пункта меняют один метод, не называй их независимыми только ради параллелизма.

### Шаг 7. Analyze: согласованность документов

```text
$speckit-analyze
```

Проверь противоречия между требованиями, планом и задачами. Например: spec требует UTC, план хранит локальное время без зоны, задачи вообще не упоминают время. Analyze предназначен для анализа без изменения артефактов; исправления согласуй отдельно и повтори проверку. Механика этапа описана в [Agentic SDD](https://github.com/github/spec-kit/blob/v1.4.2/docs/reference/agentic-sdd.md#speckitanalyze).

### Шаг 8. Implement: реализация

```text
$speckit-implement Выполни согласованные задачи.
Проверяй поведение по требованиям, не ослабляй тесты ради зелёного запуска.
В отчёте перечисли реально выполненные команды и ограничения проверки.
```

Здесь Codex меняет код. Если checklist не закрыт, этап может запросить решение о продолжении. Лучше сначала разобраться с открытым критерием; автоматическое проставление всех галочек уничтожает смысл проверки. [Порядок реализации и checklist-gate](https://github.com/github/spec-kit/blob/v1.4.2/docs/quickstart.md#step-8-speckitimplement--build-it).

### Шаг 9. Converge: найти недоделанное

```text
$speckit-converge
```

Этот шаг сопоставляет текущую реализацию с намерениями в spec/plan/tasks и добавляет недостающие работы в `tasks.md`. Это **не** режим только для чтения и не сравнение Git-веток. Если появились задачи, снова запускай implement, затем converge. Если цикл повторяет одно и то же, остановись и разбери причину: противоречивые требования, недоступная среда или неверно сформулированная задача. [Шаблон converge v1.4.2](https://github.com/github/spec-kit/blob/v1.4.2/templates/commands/converge.md).

Статус `Converged` — вывод агента, а не формальное доказательство. Прочитай diff, проверь реальные команды и отдельно сопоставь результат с критериями. Для примера стоит увидеть, что повтор не создаёт строку истории, rollback не оставляет её без зачисления, а лимит не приводит к молчаливому усечению CSV.

## 6. Какой процесс выбрать

Сокращённый путь после настройки принципов:

```text
$speckit-specify → $speckit-plan → $speckit-tasks
→ $speckit-implement → $speckit-converge
```

Полный путь добавляет clarify, checklist и analyze в показанных выше местах. Для одного неверного условия в `if` весь SDD обычно избыточен: обычная задача Codex с воспроизведением и тестом проще. Эти пути соответствуют [Quickstart v1.4.2](https://github.com/github/spec-kit/blob/v1.4.2/docs/quickstart.md).

| Задача | Мой выбор |
| --- | --- |
| Ссылка, опечатка, маленькая локальная ошибка | Обычный запрос Codex |
| Небольшая понятная фича | Короткий план; Spec Kit по желанию команды |
| Новое API с несколькими сценариями и ограничениями | Spec Kit полезен |
| Изменение данных и совместимости | Полный процесс с явными решениями и проверками |
| Исследование неизвестной технологии | Сначала эксперимент, затем фиксирование требований |
| Полное описание всего legacy ради старта | Не делать обязательным первым этапом |

## 7. Планирование и субагенты внутри Spec Kit

`$speckit-plan` создаёт технические артефакты. **Plan mode Codex** управляет поведением текущей сессии до реализации. Это разные механизмы: команда Spec Kit может создавать документы, поэтому не ожидай, что режим «ничего не менять» позволит ей пройти все этапы без ограничений. Укажи, какие действия разрешены: например, писать только документы, исходники не менять.

Spec Kit не означает автоматический запуск роя. Пометка независимой задачи не создаёт субагента. Для параллельной работы дай явный запрос:

```text
Используй двух субагентов для read-only проверки текущей спецификации.
Первый проверяет полноту сценариев экспорта и контракт ошибок.
Второй сопоставляет технический план с текущим кодом и схемой.
Каждому передай путь активной фичи, constitution, spec.md и plan.md.
Дождись обоих и сведи противоречия. Файлы пока не меняй.
```

Для параллельной реализации сначала зафиксируй контракт и владение файлами. Учти общий `.specify/feature.json`: два агента, которые переключают активную фичу в одной копии, могут мешать друг другу. Изоляция через worktree помогает только тогда, когда каждый агент действительно работает в своей директории. Подробности организации — в [руководстве Codex](codex.md).

## 8. Поддержка, обновления и типовые проблемы

### Навык не находится

Проверь, что проект открыт в правильной директории, `.agents/skills/speckit-*/SKILL.md` существует, а интеграция действительно установлена для Codex. Посмотри доступные skills и начни новую сессию. Если старый туториал показывает `.codex/prompts` или `/speckit.*`, сверяйся с версией и официальной страницей интеграции.

### Команда не распознаётся в терминале

`specify ...` выполняется в терминале. `$speckit-...` отправляется агенту в чате. Если не находится именно `specify`, проверь PATH и способ установки:

```powershell
Get-Command specify
specify version
specify integration status
```

### Агент работает с другой фичей

Попроси показать активный каталог и прочитать `.specify/feature.json`. Не исправляй проблему одним `git checkout`: механизм выбора фичи в этой версии другой.

### Обновился CLI, а файлы проекта остались старыми

CLI и установленные в репозитории навыки обновляются отдельно. Сначала сохрани локальные изменения, прочитай описание выбранного релиза и проверь версию. Для обновления проектной интеграции:

```powershell
specify integration status
specify integration upgrade codex
```

Управляемые локально изменённые файлы требуют внимания; не используй `--force` по привычке. Повторный `init --here --force` — более широкий восстановительный путь, а не обычное обновление. На Windows `specify self upgrade` при установке через `uv tool` может только вывести команду для последующего запуска после завершения процесса. [Руководство обновления v1.4.2](https://github.com/github/spec-kit/blob/v1.4.2/docs/upgrade.md).

### Документы устаревают после реализации

Заранее реши, какие артефакты поддерживаются постоянно. Для этого учебного проекта я бы сохранял спецификацию значимой фичи как контракт, а план и задачи — как вспомогательные документы с понятным статусом. При изменении поведения сначала обновляй контракт; важные причины архитектурных решений переноси в поддерживаемую документацию.

Это моя рекомендация, а не обязательный режим Spec Kit. Официальная документация предлагает несколько стратегий хранения, включая исторические спецификации и сохранение только constitution из артефактов процесса. [Жизненный цикл спецификаций](https://github.com/github/spec-kit/blob/v1.4.2/docs/how-to/persisting-specs.md).

## 9. Моё мнение: насколько полезен и насколько сырой

**Я считаю Spec Kit полезной организационной надстройкой для фич с существенными требованиями.** Для этого репозитория попробовал бы его на одной ограниченной лабораторной, а не сделал обязательным для каждого изменения. Оценка ниже основана на документации и структуре v1.4.2; установка и сквозной эксперимент здесь не выполнялись.

### Что в нём ценно

- Решения выносятся из чата в файлы, которые можно читать и обсуждать до реализации.
- Разделение «поведение / технический подход / задачи» помогает заметить преждевременные решения.
- Общая структура облегчает передачу задачи между сессиями и участниками.
- Этапы проверки дают повод остановиться на противоречиях до написания большого объёма кода.
- Шаблоны уменьшают затраты на организацию повторяемого процесса.

Для примера кошелька самая большая польза — заранее обнаружить отсутствие истории операций и согласовать её атомарность с балансом, а не просто получить ещё три Markdown-файла.

### Где есть трение

**Интерфейсы продолжают меняться.** В текущих документах уже важны интеграции, skills и отдельное состояние активной фичи; старые инструкции могут вести к другой структуре. В релизе v1.4.2 есть исправления PowerShell, инициализации интеграций и вывода команд. Это конкретные признаки продолжающейся доработки, но по ним нельзя честно вычислить «процент сырости». [Изменения v1.4.2](https://github.com/github/spec-kit/releases/tag/v1.4.2).

**Автоматические проверки остаются агентными.** Analyze может пропустить логическое противоречие; converge может неверно оценить полноту. Красивый документ и закрытый checkbox не гарантируют правильную транзакцию или корректное CSV-экранирование. Нужны наблюдаемые проверки результата.

**Процесс может стать тяжелее задачи.** На локальное исправление уйдёт больше времени и токенов, чем на само изменение. На экспериментальной фиче слишком ранняя подробная спецификация может закрепить ещё не проверенные предположения.

**Документы требуют владельца.** Если никто не проверяет spec и не обновляет её при изменении требований, появляется вторая, устаревшая версия правды. Автоматическая генерация не снимает эту ответственность.

Моя оценка зрелости: инструмент уже достаточно оформлен для пробного и осознанного использования; считать весь процесс универсально отлаженным автопилотом оснований нет. Я бы проверял пользу на конкретной задаче: стало ли меньше переделок, легче ли ревью, сохранились ли решения после смены чата и оправданы ли затраты на артефакты.

### Как попробовать с минимальными затратами

1. Возьми одну ограниченную фичу на несколько связанных изменений.
2. Зафиксируй версию инструмента и исходное состояние Git.
3. Пройди этапы, читая результаты перед продолжением.
4. Сравни код и проверки с первоначальными критериями.
5. После завершения оцени, какие документы реально помогли, и выбери правила их хранения.

Если главный выигрыш дали просто чёткая спецификация и список проверок, можно оставить облегчённый процесс в Codex. Если стандартизованные этапы помогают регулярно — имеет смысл продолжать со Spec Kit.
