## 1. Что именно хранит Git

Git — распределённая система контроля версий. У тебя на компьютере есть собственная история проекта. Коммит, просмотр истории, ветки и слияние обычно работают без интернета. GitHub, GitLab и другие серверы помогают обмениваться этой историей, обсуждать изменения и запускать проверки.

Коммит — снимок отслеживаемых файлов плюс сведения об авторе, времени, сообщении и родительских коммитах. У него есть идентификатор — хеш, например `a7c8e91`. Это сокращение полного хеша. Коммит не меняется: «изменить старый коммит» означает создать другой и переставить указатель ветки.

Ветка — именованный указатель на коммит. При новом коммите текущая ветка передвигается вперёд. В обычном состоянии `HEAD` указывает на текущую ветку, а через неё — на текущий коммит. `main` не обладает особой магией.

История — граф, а не обязательно прямая линия: у обычного коммита один родитель, у начального нет родителей, у merge-коммита обычно два.

```text
A---B---C       main
     \
      D---E     feature/payment, HEAD
```

Здесь разработка платежей началась от B. Коммиты C и E пока не включают изменения друг друга. Переключение ветки меняет текущий указатель и приводит файлы к состоянию выбранного коммита; совместимые незакоммиченные изменения при этом могут сохраниться.

Git не хранит пустые директории. Файл `.gitkeep` иногда используют как заглушку, но специального смысла для Git у этого имени нет. Служебная директория `.git/` содержит базу репозитория; учебный каталог `docs/labs/git/` — обычные материалы.

Основа модели: [Pro Git на русском](https://git-scm.com/book/ru/v2).

## 2. Три места, между которыми движутся изменения

Представь, что готовишь посылку. Рабочие файлы — стол, индекс — коробка с выбранным содержимым, коммит — запечатанная сохранённая посылка.

```text
Рабочая директория -- git add --> Индекс (staging area)
                                        |
                                   git commit
                                        v
                                Локальная история -- git push --> Сервер
```

- **Working tree / рабочая директория**: файлы, которые редактируешь.
- **Index / stage / staging area**: содержимое будущего коммита. Здесь лежит именно выбранная версия файла.
- **Repository / история**: уже созданные локальные коммиты.

Состояния файла: `untracked` — ещё не отслеживается, `modified` — изменён относительно индекса, `staged` — подготовлен к коммиту. Один файл может одновременно иметь staged и unstaged изменения.

Пример: написал строки A и B, выполнил `git add notes.txt`, затем дописал C. В коммит попадут A и B. Чтобы включить C, нужно снова добавить файл. `commit` не собирает автоматически всё, что видно в редакторе.

Источник: [git add](https://git-scm.com/docs/git-add).

### Как увидеть каждую область

```powershell
git status
git status --short
git diff
git diff --staged
git diff HEAD
```

| Команда | Что показывает |
| --- | --- |
| `status` | Ветку, подготовленные, неподготовленные и новые файлы, незавершённые операции |
| `diff` | Изменения рабочей директории относительно индекса |
| `diff --staged` | Изменения индекса относительно HEAD: будущий коммит |
| `diff HEAD` | Итоговую разницу отслеживаемых файлов с последним коммитом |

Новые untracked-файлы обычный `diff` не показывает: смотри `status`, содержимое нового файла и затем `diff --staged` после добавления.

В коротком статусе первая колонка — индекс, вторая — рабочая директория: `M ` означает подготовленное изменение, ` M` — неподготовленное, `MM` — оба сразу, `??` — новый файл, `UU` — один из видов неразрешённого конфликта. Буква `D` означает удаление; удаление тоже нужно подготовить к коммиту.

Источники: [git status](https://git-scm.com/docs/git-status), [git diff](https://git-scm.com/docs/git-diff).

## 3. Настройка, создание и получение проекта

```powershell
git --version
git config --global user.name "Ivan Petrov"
git config --global user.email "ivan@example.com"
git config --show-origin --get user.email
```

Имя и почта записываются в будущие коммиты. Это сведения об авторстве, а не пароль и не вход на GitHub. `--global` задаёт настройку для пользователя компьютера. Внутри проекта команда без `--global`, например `git config user.email "work@example.com"`, задаёт локальное значение, перекрывающее глобальное.

Проверь адрес до первого рабочего коммита: он может стать видимым в истории. Для корпоративных проектов используй принятый в команде адрес. Не сохраняй токены в URL и не добавляй их в файлы проекта; способ входа зависит от сервера — обычно HTTPS с менеджером учётных данных либо SSH с ключом.

Источник: [git config](https://git-scm.com/docs/git-config).

### Если проект уже существует

```powershell
git clone URL project
Set-Location project
git remote -v
git branch -a
```

`clone` создаёт локальный репозиторий, скачивает историю, обычно называет сервер `origin` и открывает одну рабочую ветку. Это не создание нового проекта на сервере. У `clone` могут быть ограничения, например `--depth` скачивает неполную историю. Источник: [git clone](https://git-scm.com/docs/git-clone).

### Если создаёшь новый проект

Выполняй в новой папке проекта:

```powershell
git init -b main
git status
```

`init` создаёт репозиторий на диске; сервер он не создаёт. Не запускай его в случайной подпапке уже существующего проекта: можно получить вложенный репозиторий. [git init](https://git-scm.com/docs/git-init)

### Игнорирование файлов

Пример `.gitignore` для Java:

```gitignore
target/
*.log
.env
```

Игнорирование распространяется на ещё не отслеживаемые файлы. Уже закоммиченный `.env` продолжит отслеживаться. `git rm --cached .env` убирает его из индекса, сохраняя рабочий файл; затем коммитят удаление из репозитория и правило игнорирования. Старые коммиты всё ещё содержат файл. Если там был настоящий секрет, его нужно отозвать/заменить: удаление из текущей версии недостаточно.

`git check-ignore -v FILE` объясняет, какое правило игнорирует файл. `.gitignore` обычно коммитят, чтобы правила были общими. Переводы строк на Windows регулируются в том числе `.gitattributes`; не меняй настройки всего проекта наугад из-за предупреждения LF/CRLF.

Источник: [gitignore](https://git-scm.com/docs/gitignore), [gitattributes](https://git-scm.com/docs/gitattributes).

## 4. Повседневный коммит

```powershell
git status
git diff
git add src/main/java/example/OrderService.java
git diff --staged
git commit -m "Fix duplicate payment processing"
git status
```

Путь выше условный. Смысл последовательности: увидеть изменения → выбрать → проверить выбор → сохранить. Коммит остаётся локальным до push. Если ничего не подготовлено, обычный `git commit` не сохранит изменения.

| Команда | Когда нужна |
| --- | --- |
| `git add FILE` | Добавить текущую версию конкретного файла или его удаление |
| `git add -A` | Подготовить все изменения во всём репозитории, включая удаления; сначала проверь статус |
| `git add -p` | Интерактивно выбрать фрагменты: `y` — добавить, `n` — пропустить, `s` — попытаться разделить блок, `q` — закончить |
| `git commit -m "Message"` | Сохранить индекс в истории |
| `git commit -am "Message"` | Подготовить изменённые/удалённые отслеживаемые файлы и закоммитить; новые файлы не включает |
| `git mv old.txt new.txt` | Переименовать и подготовить изменение |
| `git rm FILE` | Удалить файл из рабочей директории и индекса |

Делай коммиты по смыслу: одна исправленная ошибка или одно законченное изменение. «Исправить двойное списание» полезнее, чем «changes». Перед коммитом запускай подходящие проверки проекта. Правильность кода Git не проверяет.

Источники: [git add](https://git-scm.com/docs/git-add), [git commit](https://git-scm.com/docs/git-commit), [git mv](https://git-scm.com/docs/git-mv), [git rm](https://git-scm.com/docs/git-rm).

## 5. Чтение истории и поиск причин

```powershell
git log --oneline -10
git log --graph --oneline --decorate --all
git show HASH
git log --oneline -- path/to/file
git log -p -- path/to/file
git blame path/to/file
git diff main...feature/payment
```

`log` показывает коммиты; `--graph --all` помогает увидеть расхождение веток; `show` — сведения и изменения конкретного коммита. Разделитель `--` отделяет пути от ревизий. `blame` показывает, какой коммит последним менял каждую строку: это начало расследования, а не доказательство виновности автора.

`git diff A B` сравнивает два снимка. `git diff main...feature/payment` сравнивает общий предок веток с концом feature: удобно видеть вклад задачи. У `git log A..B` другой смысл — коммиты, достижимые из B, но не из A. Не переноси значение точек из `diff` на `log` автоматически.

`HEAD~1` — первый родитель HEAD, `HEAD~2` — два шага по первым родителям. У merge-коммита `HEAD^2` — второй родитель. В PowerShell выражения с фигурными скобками бери в кавычки: `git show 'HEAD@{1}'`. Если открылся постраничный просмотр истории, нажми `q`, чтобы выйти.

Источники: [git log](https://git-scm.com/docs/git-log), [git diff](https://git-scm.com/docs/git-diff), [git show](https://git-scm.com/docs/git-show), [git blame](https://git-scm.com/docs/git-blame).

## 6. Ветки: изолировать задачу и вернуться обратно

```powershell
git branch
git branch -vv
git switch main
git switch -c feature/payment
# Теперь редактируешь и коммитишь в feature/payment
git switch main
```

`branch` перечисляет локальные ветки, звёздочка отмечает текущую. `branch -vv` дополнительно показывает upstream и известное расхождение. `switch -c` создаёт ветку от текущего коммита и переключает на неё; `git branch feature/payment` только создаёт указатель.

Незакоммиченные изменения не являются собственностью ветки: совместимые изменения могут перейти вместе с тобой. Если переключение перезапишет файлы, Git обычно откажет. Закончи коммит или используй stash; не добавляй принудительные флаги, чтобы убрать ошибку.

Старые инструкции часто используют `checkout`: `git checkout main` примерно соответствует `git switch main`, `git checkout -b feature/payment` — `git switch -c feature/payment`. У `checkout` есть и режим восстановления файлов, поэтому новые отдельные команды проще читать.

`git branch -d feature/payment` удаляет локальное имя ветки с проверкой слитости относительно upstream, а при его отсутствии — HEAD. `-D` пропускает проверку. Для команды после squash-merge Git может считать ветку неслитой: сначала убедись, что результат задачи сохранён.

Источники: [git switch](https://git-scm.com/docs/git-switch), [git branch](https://git-scm.com/docs/git-branch).

### Detached HEAD

`git switch --detach HASH` открывает старый коммит без текущей ветки. Можно посмотреть и запустить код. Если сделал здесь полезные коммиты, сохрани их командой `git switch -c investigation` до ухода: появится ветка, удерживающая результат.

## 7. Сервер: fetch, pull, push и upstream

Есть три разных имени:

| Имя | Что это |
| --- | --- |
| `main` | Твоя локальная ветка |
| `origin` | Локальное имя подключения к серверному репозиторию |
| `origin/main` | Локальная ссылка на последнее известное состояние серверной main |

`origin/main` не является прямой трансляцией сервера: без fetch её сведения могут устареть. `upstream` в настройках ветки — связанная ветка для обмена; обычно у локальной `main` это `origin/main`. В проектах с fork словом `upstream` также называют отдельный remote исходного проекта. Это разные употребления.

### Fetch: получить сведения и коммиты

```powershell
git remote -v
git fetch origin
git log --oneline main..origin/main
git diff main origin/main
```

В обычной настройке `fetch origin` обновляет ссылки `origin/*` и скачивает недостающие объекты, сохраняя текущие рабочие файлы и локальную ветку. `git fetch --prune origin` также убирает устаревшие ссылки на удалённые серверные ветки; локальные рабочие ветки он не удаляет. [git fetch](https://git-scm.com/docs/git-fetch)

### Pull: получить и встроить изменения в текущую ветку

```powershell
git switch main
git pull --ff-only
```

`pull` сначала получает историю, затем интегрирует выбранную ветку в **текущую**. Стратегию лучше указывать явно: обычный `pull` зависит от версии Git и настроек.

- `--ff-only`: разрешает только передвинуть указатель вперёд; при расхождении историй останавливается.
- `--no-rebase`: использует merge; если возможно и настройки позволяют, получится fast-forward.
- `--rebase`: переигрывает локальные коммиты поверх полученной истории.

Если на текущей feature-ветке сделать `git pull origin main`, Git встроит серверную main именно в feature. Это не переключение на main. Перед интеграцией сохрани незакоммиченные изменения. [git pull](https://git-scm.com/docs/git-pull)

### Push: передать локальные коммиты

```powershell
git push -u origin feature/payment
# В дальнейшем на этой ветке:
git push
```

`-u` связывает локальную ветку с серверной. Push не создаёт коммит из несохранённых файлов. Обычный push отклоняет обновление ветки, если оно потеряет доступную через неё серверную историю: это часто означает, что у коллеги появились новые коммиты.

При `non-fast-forward` сначала сделай fetch, посмотри граф, затем согласованно используй merge или rebase. После интеграции снова проверь код и отправь результат. Если отказ связан с правами, защищённой веткой или проверками сервера, rebase проблему не решит.

`git push --force-with-lease` нужен для согласованной отправки переписанной истории своей ветки. Он проверяет ожидаемое состояние серверной ссылки; обычный `--force` такой защиты не даёт. Lease не понимает, чьи изменения ценны, а фоновый fetch способен обновить локальное ожидание. Общую main обычно не переписывают.

`git push origin --delete feature/payment` удаляет ветку на сервере; локальная ветка при этом остаётся. [git push](https://git-scm.com/docs/git-push)

### Типичный рабочий день

1. Переключиться на `main`, убедиться через `status`, что нет незавершённой работы, выполнить `pull --ff-only`.
2. Создать ветку задачи: `git switch -c feature/payment`.
3. Менять код, проверять diff, запускать тесты, делать небольшие коммиты.
4. Отправить ветку через `push -u origin feature/payment`.
5. Открыть Pull Request / Merge Request в GitHub/GitLab, дождаться review и проверок, внести исправления.
6. После слияния обновить локальную main и убрать больше не нужную ветку.

PR/MR — возможность хостинга, отдельной универсальной команды `git pull-request` в базовом Git нет. Названия веток, стратегия слияния и требования к коммитам определяются командой.

## 8. Merge, fast-forward, squash и rebase

### Merge: соединить истории

Находясь в `main`, команда `git merge feature/payment` включает feature в main. Направление важно: **источник указываешь аргументом, получатель — текущая ветка**.

Если после точки ответвления main не менялась, возможен fast-forward: Git просто передвинет main, отдельный merge-коммит не нужен. Если обе ветки развивались, обычно появляется коммит с двумя родителями:

```text
До:                    После merge:
A---B---C main         A---B---C-------M main
     \                      \       /
      D---E feature          D---E--/  feature
```

`git merge --no-ff feature/payment` требует отдельный merge-коммит даже там, где возможен fast-forward. `git merge --squash feature/payment` подготавливает суммарные изменения без создания merge-коммита; затем нужен обычный commit. История связи веток при этом не записывается как при настоящем merge. [git merge](https://git-scm.com/docs/git-merge)

### Rebase: переиграть свои изменения на новой основе

```powershell
git switch feature/payment
git fetch origin
git rebase origin/main
```

```text
До:                    После rebase:
A---B---C main         A---B---C main
     \                        \
      D---E feature            D'---E' feature
```

Получаются новые D' и E'. Rebase удобен для подготовки своей ветки к review, но переписывание уже используемой коллегами истории требует согласования. Конфликт может возникнуть при каждом переносимом коммите.

`git rebase -i HEAD~3` позволяет обработать три последних коммита: `reword` меняет сообщение, `squash` объединяет с предыдущим, `fixup` объединяет с отбрасыванием сообщения, `drop` исключает. До этого убедись, что есть три предка, дерево чистое и работаешь со своей историей. Полезно заранее создать страховочную ветку: `git branch backup/before-rebase`.

При одинаковом итоговом содержимом merge и rebase всё равно дают разную историю. Выбирай по правилам команды. [git rebase](https://git-scm.com/docs/git-rebase)

## 9. Конфликт: Git просит принять решение о содержимом

Конфликт возникает, когда Git не может автоматически совместить изменения: например, обе стороны изменили одну строку, одна удалила файл, другая изменила. Конфликт — не повреждение репозитория.

Типичный фрагмент:

```text
<<<<<<< HEAD
timeout=30
=======
timeout=60
>>>>>>> feature/timeout
```

Нужно понять требуемое поведение, оставить правильный результат (возможно, третий вариант) и удалить маркеры. В IDEA это удобно делать в редакторе разрешения конфликтов, но «принять обе стороны» не гарантирует рабочий код.

### Если конфликт при merge

```powershell
git status
# Исправь конфликтующие файлы в редакторе
git diff --check
git add FILE
git merge --continue
```

Либо `git merge --abort`, чтобы отменить незавершённое слияние. Начинать merge с чистым деревом удобнее: восстановить существовавшие до него незакоммиченные изменения не всегда возможно. [git merge](https://git-scm.com/docs/git-merge)

### Если конфликт при rebase

```powershell
git status
# Исправь результат
git add FILE
git rebase --continue
```

Повторяй для следующих остановок. `git rebase --abort` возвращает состояние до rebase. `--skip` пропускает текущий переносимый коммит, поэтому это не универсальное исправление конфликта.

Во время rebase смысл `ours` и `theirs` непривычен: ours — уже собранная новая основа, theirs — переносимый коммит твоей ветки. Смотри содержимое и описание операции, не выбирай сторону по привычке. После разрешения запускай проверки: отсутствие текстового конфликта не означает отсутствие логической ошибки. [git rebase](https://git-scm.com/docs/git-rebase), [конфликты в IDEA](https://www.jetbrains.com/help/idea/resolve-conflicts.html)

## 10. Как отменить именно то, что нужно

Сначала ответь: изменения ещё в файлах, уже в индексе, в локальном коммите или опубликованы? От этого зависит команда.

| Задача | Команда | Что останется |
| --- | --- | --- |
| Убрать файл из будущего коммита | `git restore --staged FILE` | Рабочие изменения сохранятся; индекс вернётся к HEAD |
| Выбросить неподготовленные правки файла | `git restore FILE` | Рабочий файл станет как в индексе; неподготовленные правки потеряются |
| Взять файл из старого коммита | `git restore --source=HASH -- FILE` | Старая версия появится как рабочее изменение; ветка не передвинется |
| Исправить последний локальный коммит | `git commit --amend` | Будет создан заменяющий коммит |
| Убрать последний локальный коммит, оставив изменения в индексе | `git reset --soft HEAD~1` | Изменения можно сразу перекоммитить |
| Убрать последний локальный коммит, оставив изменения в файлах | `git reset --mixed HEAD~1` | Индекс сброшен, рабочие файлы сохранены |
| Отменить эффект обычного опубликованного коммита | `git revert HASH` | Новый обратный коммит; старая история сохранена |

`restore` работает с содержимым файлов/индекса. `reset` в форме с коммитом передвигает текущую ветку и по режиму меняет индекс и файлы. `revert` создаёт новый коммит с обратным изменением. Это три разных действия.

Источники: [git restore](https://git-scm.com/docs/git-restore), [git reset](https://git-scm.com/docs/git-reset), [git revert](https://git-scm.com/docs/git-revert).

### Amend

```powershell
git add forgotten-file.txt
git commit --amend --no-edit
```

Добавляет подготовленные изменения к замене последнего коммита и сохраняет сообщение. Для одного изменения сообщения: `git commit --amend -m "Clearer message"`. Проверь `diff --staged`, чтобы случайно не захватить чужую часть работы. После публикации amend потребует переписывания серверной ветки, поэтому согласуй это. [git commit](https://git-scm.com/docs/git-commit)

### Команды, у которых можно потерять работу

- `git reset --hard HASH`: двигает ветку и приводит индекс и отслеживаемые файлы к HASH. Убирает незакоммиченные изменения; также может удалить мешающие восстановлению untracked-файлы/каталоги.
- `git clean -nd`: только показывает неотслеживаемые файлы и директории, которые удалил бы clean.
- `git clean -fd`: действительно удаляет их. `-x` включает игнорируемые файлы, где могут лежать локальные настройки.

Перед destructive-командой проверь `status`, сохрани нужные изменения и проверь цель. Страховочная ветка удерживает коммиты, но не сохраняет незакоммиченные файлы. Reflog не вернёт обычный untracked-файл после clean. [git reset](https://git-scm.com/docs/git-reset), [git clean](https://git-scm.com/docs/git-clean)

`revert` тоже может конфликтовать: более новые изменения могут зависеть от отменяемых. После исправления используй `git add FILE` и `git revert --continue`; для отмены операции — `git revert --abort`. Отмена merge требует выбора родительской линии (`-m`) и влияет на будущие слияния: не применяй обычный рецепт вслепую. [git revert](https://git-scm.com/docs/git-revert)

## 11. Stash: временно освободить рабочую директорию

```powershell
git stash push -u -m "WIP payment validation"
git stash list
git stash show -p 'stash@{0}'
git stash apply 'stash@{0}'
# После проверки восстановленного результата:
git stash drop 'stash@{0}'
```

По умолчанию stash сохраняет подготовленные и неподготовленные изменения отслеживаемых файлов. `-u` добавляет untracked, но не ignored; `-a` включает также ignored. Обычный `apply` не обязательно восстанавливает прежнее разделение staged/unstaged; для попытки восстановить индекс есть `--index`.

`apply` оставляет запись stash, `pop` пытается применить и удалить её при успехе. При конфликте pop запись сохраняется. У stash нет команды `--continue`: разреши конфликт, подготовь результат и дальше работай как обычно; запись удаляй после проверки. Stash локальный, обычный push его не отправляет. Для длительной работы удобнее отдельная ветка и коммит. [git stash](https://git-scm.com/docs/git-stash)

## 12. Cherry-pick, reflog, tags и bisect

### Перенести отдельное исправление

```powershell
git switch release/1.0
git cherry-pick HASH
```

Команда применяет изменение выбранного коммита к текущей ветке; обычно создаёт новый коммит. Это удобно для переноса hotfix, но коммит может зависеть от предыдущих изменений. При конфликте: исправить → `add` → `git cherry-pick --continue`; отменить — `git cherry-pick --abort`. [git cherry-pick](https://git-scm.com/docs/git-cherry-pick)

### Найти потерянный коммит

```powershell
git reflog
git show HASH
git branch rescue/payment HASH
```

Reflog — локальный журнал перемещений ссылок, например после reset или rebase. Найди нужный коммит и сначала удержи его новой веткой, затем разбирайся. Это не вечная резервная копия: записи истекают, недостижимые объекты могут быть очищены. Reflog не содержит каждое сохранение редактора. [git reflog](https://git-scm.com/docs/git-reflog)

### Пометить выпуск

```powershell
git tag -a v1.0.0 -m "Release 1.0.0"
git show v1.0.0
git push origin v1.0.0
```

Тег отмечает конкретное состояние; в отличие от ветки, обычно не движется при новых коммитах. Аннотированный тег содержит отдельные метаданные и сообщение. Обычный push ветки не следует считать публикацией всех тегов: отправляй нужный явно. [git tag](https://git-scm.com/docs/git-tag)

### Найти коммит, который сломал поведение

```powershell
git bisect start
git bisect bad
git bisect good GOOD_HASH
# Git переключит на промежуточный коммит. Запусти проверку.
git bisect good
# Или git bisect bad — по фактическому результату; повторяй до нахождения.
git bisect reset
```

Начинай с чистого дерева. Нужны известный исправный и известный сломанный коммиты и воспроизводимая проверка. Bisect сужает диапазон примерно вдвое; обычно намного быстрее ручного просмотра сотни коммитов. Если ревизию невозможно проверить, используй `git bisect skip`, понимая, что ответ может стать неоднозначным. [git bisect](https://git-scm.com/docs/git-bisect)

## 13. Те же действия в IntelliJ IDEA

Интерфейс и названия пунктов зависят от версии и раскладки. Через Find Action можно искать действия по английским названиям. Понимание операции переносится между версиями.

| Действие в IDEA | Смысл в Git | На что смотреть |
| --- | --- | --- |
| Get from Version Control / Clone | `clone` | URL и локальная папка |
| Commit | Подготовить выбранное и создать локальный commit | Выбранные файлы/фрагменты, сообщение, проверки |
| Commit and Push | Commit, затем push | Успешный commit ещё не означает успешный push |
| Push | `push` | Какие коммиты и в какую серверную ветку уходят |
| Fetch | `fetch` | Обновляются сведения о сервере |
| Pull / Update Project | Получение и интеграция истории | Merge, rebase или другая выбранная стратегия; Update может охватывать несколько корней |
| New Branch / Checkout | Создать/переключить ветку | От какого коммита создаётся и куда переключаешься |
| Merge выбранной ветки into Current | `merge` | Получатель — текущая ветка |
| Rebase Current onto Selected | `rebase` | Текущая ветка переигрывается на выбранную основу |
| Show Diff / Log | `diff` / `log` | Что с чем сравниваешь |
| Amend Commit | `commit --amend` | Меняется последний коммит |
| Revert Commit в Log | `revert` | Создаётся обратный коммит |
| Reset Current Branch to Here | `reset` к выбранному коммиту | Режим Soft/Mixed/Hard определяет судьбу индекса и файлов |
| Rollback локальных изменений | Отбросить выбранные незакоммиченные изменения | Результат зависит от выбранных файлов; это не Revert Commit |
| Cherry-Pick | `cherry-pick` | Исправление применяется в текущую ветку |
| Stash Changes | `stash` | Какие файлы включены и где сохранены |
| Shelve Changes | Полка средствами IDE | Это отдельный механизм IDEA, не запись git stash |

Changelist — группировка изменений средствами IDE, а не ветка или коммит. В режиме без явного staging IDEA подготавливает выбранные изменения при коммите. Для знакомства с индексом можно включить Settings → Version Control → Git → Enable staging area. Это необязательное изменение рабочего процесса: сначала проверь текущие changelists и подсказки своей версии.

Перед Update Project посмотри выбранный метод обновления. Нельзя считать кнопку безусловным эквивалентом одной команды `git pull`: настройки определяют интеграцию.

Источники: [Commit и staging в IDEA](https://www.jetbrains.com/help/idea/commit-and-push-changes.html), [синхронизация](https://www.jetbrains.com/help/idea/sync-with-a-remote-repository.html), [ветки](https://www.jetbrains.com/help/idea/manage-branches.html), [отмена изменений](https://www.jetbrains.com/help/idea/undo-changes.html), [Shelve и stash](https://www.jetbrains.com/help/idea/shelving-and-unshelving-changes.html).

## 14. Шпаргалка «что делать в моей ситуации»

| Ситуация | Первый шаг | Дальше |
| --- | --- | --- |
| Не понимаю текущее состояние | `git status` | Посмотреть `diff`, `diff --staged` и граф истории |
| Хочу сохранить готовую часть | `git add -p` | Проверить staged diff и commit |
| Добавил лишний файл в индекс | `git restore --staged FILE` | Проверить status; содержимое останется |
| Нужно срочно сменить задачу | Commit в своей ветке или stash с понятным именем | Переключиться, затем восстановить работу |
| Push отклонён | Прочитать причину, выполнить fetch | Проверить расхождение, интегрировать, проверить, повторить push |
| Идёт конфликт | `git status` | Узнать операцию, исправить файлы, выполнить её `--continue` |
| Не хочу продолжать конфликтный rebase | `git rebase --abort` | Вернуться к планированию интеграции |
| Ошибка уже в общей ветке | Найти коммит и зависимости | Обычно revert через отдельную ветку и review |
| После reset исчез нужный коммит | `git reflog` | Проверить show и создать rescue-ветку |
| Неясно, почему файла нет в diff | `git status --short` | Может быть untracked, ignored или уже staged |

Рабочий минимум освоен, когда ты можешь своими словами объяснить состояние до и после команды, собрать коммит из выбранных изменений, обновить ветку, разрешить конфликт и отменить ошибку подходящим способом. Проверь это в [практикуме](../../labs/git/README.md).
