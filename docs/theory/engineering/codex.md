# Codex: практическое руководство

[Рабочие заметки](README.md) · [Общий процесс работы с ИИ](ai-workflow.md) · [Spec Kit](spec-kit.md)

Проверено по официальной документации **18 ноября 2026 года**. Примеры ориентированы на этот Java/Spring-репозиторий и Windows PowerShell. Codex есть в приложении, CLI и IDE; набор команд и инструментов зависит от клиента и версии. Блоки `text` ниже — запросы в чат, блоки `powershell` — команды терминала. Примеры конфигурации показаны для изучения: этот документ сам ничего не устанавливает и не меняет настройки агента.

## 1. С чего начать

Codex может читать проект, менять файлы, запускать доступные команды и проверять результат. Поэтому запрос «объясни» и запрос «исправь» имеют разный смысл: во втором случае ожидай изменений в рабочей копии. Перед большой задачей полезно посмотреть `git status`, чтобы понимать исходное состояние.

Начни с такого запроса:

```text
Изучи README.md, pom.xml и код ru.learn.delivery.
Объясни, как WalletLedger обеспечивает идемпотентность и что проверяют его тесты.
Ссылайся на конкретные методы. Файлы пока не меняй.
```

Затем можно перейти к действию:

```text
Проверь, есть ли у WalletLedger проблема с валидацией walletId.
Пустой или состоящий из пробелов идентификатор должен отклоняться
до обращения к БД с IllegalArgumentException.
Если проверки нет, добавь её и подходящий тест.
Сохрани обработку повторного eventId и поведение транзакции.
Запусти узкие тесты и покажи фактический результат.
```

Пример не утверждает, что здесь есть скрытая ошибка: он задаёт конкретное новое требование. Так агенту проще отличить требуемое изменение от произвольного «улучшения».

В этом проекте узкий запуск выглядит так:

```powershell
.\mvnw.cmd '-Dtest=WalletLedgerTest' test
```

Для Linux/macOS аналог — `./mvnw -Dtest=WalletLedgerTest test`. Наличие теста и успешная команда ещё не означают проверку на настоящем PostgreSQL: уточняй, какую БД использовал тест и какие гарантии это подтверждает.

## 2. Что куда записывать

Не нужно помещать всю информацию в один огромный промпт.

| Механизм | Для чего | Пример |
| --- | --- | --- |
| Запрос в текущем чате | Одна задача и её критерии | «Добавь проверку walletId» |
| `AGENTS.md` | Постоянные инструкции по работе с проектом | «Сохраняй Java 17, запускай релевантные тесты» |
| Skill, или навык | Повторяемая процедура | Проверка транзакционных границ по определённым шагам |
| `.codex/config.toml` | Настройки Codex для доверенного проекта | Настройки агентов и подключений |
| MCP / подключённое приложение | Доступ к внешним данным и действиям | Прочитать задачу из трекера через доступный коннектор |
| Plugin | Устанавливаемый пакет возможностей | Несколько навыков вместе с инструментами |
| Спецификация и план | Долговременный контекст конкретной большой задачи | Требования, решения, этапы, проверки |

Skill объясняет, **как выполнять работу**; инструмент даёт возможность **совершить действие**. Текст «проверь Jira» не создаст доступ к Jira. `AGENTS.md` тоже не выдаёт сетевые права и не меняет ограничения среды. Этот выбор механизмов соответствует [официальным рекомендациям по работе с Codex](https://learn.chatgpt.com/guides/best-practices).

## 3. «Общий промпт на всё приложение» — обычно AGENTS.md

### Три разных смысла слова «общий»

- **Для репозитория:** `AGENTS.md` в корне проекта. Его можно хранить в Git вместе с кодом.
- **Для всех твоих проектов:** личный `~/.codex/AGENTS.md`. На Windows при стандартном расположении это `C:\Users\limon\.codex\AGENTS.md`.
- **Для работы самого клиента:** `config.toml`. Это конфигурация, а не текстовое описание задачи.

`AGENTS.md` — инструкция агенту, а не системный промпт модели. Она не имеет безусловного приоритета над всеми остальными указаниями. Явное указание пользователя в задаче важнее правил этого файла, но не отменяет ограничения платформы и среды.

### Как работают уровни

```text
~/.codex/AGENTS.md           личные привычки
learn/AGENTS.md              правила всего проекта
learn/docs/AGENTS.md         правила документации
learn/src/test/AGENTS.md     правила тестов
```

Более локальные инструкции уточняют общие в своей области. В текущем механизме CLI цепочка собирается от корня до рабочей директории при запуске сессии; это не рекурсивная загрузка всех `AGENTS.md` из репозитория. Для вложенного модуля запускай Codex в нём или явно проси проверить применимые локальные инструкции. После изменения правил полезно начать новую сессию и проверить, какие файлы прочитаны.

В одной директории `AGENTS.override.md` выбирается раньше `AGENTS.md`: это замена файла данного уровня, а не второй дополняющий файл. По умолчанию объём собираемых инструкций ограничен 32 KiB. Подробности и параметры — в [документации AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

### Пример AGENTS.md для этого репозитория

Это образец содержимого, а не уже созданный корневой файл:

```markdown
# Правила работы с learn

## Назначение
Учебный Java/Spring-проект: примеры должны оставаться понятными.

## Ограничения
- Корневой проект использует Java 17; проверяй pom.xml конкретного модуля.
- Следуй существующим соглашениям и структуре пакетов.
- Не включай несвязанный рефакторинг в исправление ошибки.
- Не меняй публичный контракт без явной задачи на его изменение.

## Проверки
- Для изменений поведения добавляй или обновляй релевантные тесты.
- В PowerShell используй .\mvnw.cmd; начинай с узкого набора тестов.
- Для документации проверяй ссылки, примеры и согласованность с кодом.
- Сообщай, какие проверки выполнены, а какие недоступны и почему.

## Планирование
- Перед нетривиальной задачей кратко опиши план и критерии проверки.
- Для маленькой однозначной правки сразу переходи к выполнению.
- Задавай вопросы, если ответ существенно меняет требуемое поведение.

## Документация
- Пиши объяснения на русском.
- Новые конспекты добавляй в оглавление соответствующего раздела.
```

Плохие правила: «Всегда пиши идеальный код», «Используй все лучшие практики», «На любой запрос запускай десять агентов». Их трудно проверить, а пользы для конкретного проекта мало.

Лучше пополнять файл после повторяющейся ошибки: например, агент несколько раз предложил Java 21 для корневого проекта на Java 17 — добавь точное ограничение. Объёмный справочник вынеси в отдельный документ и укажи, когда его читать.

### Как создать и проверить

```text
Изучи проект и предложи короткий AGENTS.md для его корня.
Используй только подтверждённые команды и соглашения.
Отдели существующие правила от своих предложений. Пока не создавай файл.
```

После проверки можно попросить сохранить результат. В CLI есть `/init` для подготовки начального файла; его всё равно нужно прочитать. Для контроля спроси: «Перечисли загруженные файлы инструкций и кратко объясни применимые правила».

## 4. Зачем нужны skills

### Что это такое

Навык — каталог с `SKILL.md`: название, описание области применения и процедура. Рядом могут находиться скрипты, шаблоны и справочные материалы. Модель сначала видит название и описание, а полные инструкции загружает при использовании навыка. Это позволяет держать подробную процедуру отдельно от постоянных правил.

Навык не дообучает модель, не создаёт отдельного агента и не гарантирует правильность. Его ценность в повторяемости процесса. Например, вместо десяти абзацев о проверке транзакций ты пишешь:

```text
$spring-tx-review Проверь WalletLedger и связанные тесты.
Верни подтверждённые проблемы с указанием файлов; код не меняй.
```

Это сработает, только если навык с таким именем действительно создан и доступен. `spring-tx-review` здесь — наше учебное имя.

### Когда навык окупается

| Ситуация | Что выбрать |
| --- | --- |
| Один раз объяснить конкретный stack trace | Обычный запрос |
| Всегда сохранять совместимость с Java 17 | `AGENTS.md` |
| Регулярно проводить одинаковую проверку транзакций | Skill |
| Надёжно проверить формат по формальному правилу | Скрипт / линтер; skill может его запускать |
| Сделать одну крупную фичу | Спецификация и план; при необходимости Spec Kit |

Практический сигнал: ты третий раз вставляешь одну и ту же процедуру, она уже показала пользу и у неё понятные вход и результат.

### Где хранить и как запускать

Для навыка проекта используй `.agents/skills/<имя>/SKILL.md`, для личного — `~/.agents/skills/<имя>/SKILL.md`. В этой установке есть также системные и плагинные навыки в каталогах Codex; редактировать их кеш вместо собственного навыка не нужно.

В Codex навык можно явно упомянуть как `$имя-навыка`; в CLI и IDE есть выбор через `/skills`. Автоматический выбор зависит от описания навыка и политики его вызова. Если навык не виден, проверь структуру, YAML-заголовок и список доступных навыков; при необходимости перезапусти клиент. Формат и расположения описаны в [официальном руководстве по skills](https://learn.chatgpt.com/docs/build-skills).

### Минимальный собственный навык

Файл `.agents/skills/spring-tx-review/SKILL.md`:

```markdown
---
name: spring-tx-review
description: Проверка транзакций и идемпотентности в Spring-коде. Использовать для ревью JDBC/JPA-операций и обработчиков сообщений; не использовать для UI и форматирования.
---

# Проверка транзакционных границ

1. Прочитай указанные классы, вызывающий код, схему БД и тесты.
2. Определи фактическое начало и завершение транзакции.
   Для @Transactional проверь путь вызова через прокси.
3. Выясни, какие записи должны фиксироваться атомарно.
4. Проверь гонки, повторную доставку и ошибки между commit и ACK.
5. Сопоставь найденные риски с ограничениями и индексами БД.
6. Найди тесты на rollback и повторную обработку.
   Отдельно отметь ограничения H2 относительно PostgreSQL.
7. Верни находки: файл/метод, сценарий, последствие, способ проверки.
   Отделяй подтверждённые проблемы от предположений.

Без отдельной просьбы не меняй файлы.
```

Один лишь последний пункт не создаёт техническую песочницу только для чтения: это поведенческая инструкция. Ограничения доступа настраиваются отдельно.

Можно поручить подготовку встроенному навыку:

```text
$skill-creator Создай проектный навык spring-tx-review
в .agents/skills. Он должен проверять транзакции, идемпотентность
и повторную доставку в Java/Spring-коде.
По умолчанию только анализ. Результат: подтверждённые находки
с файлами, сценариями и предложением проверки.
```

Для установки готового навыка есть `$skill-installer`: укажи источник и назначение. Перед применением чужого навыка прочитай инструкции и скрипты: они могут запускать команды. Проверь свой навык на двух подходящих запросах и одном неподходящем; слишком широкое описание приводит к лишним срабатываниям.

## 5. Нужно ли каждый раз просить план

**Нет. Проси план там, где нужно принять решения до изменения кода.** Постоянное «сначала план, потом жди» замедляет даже простые задачи.

| Задача | Разумный процесс |
| --- | --- |
| Опечатка, ссылка, однозначная локальная проверка | Сразу исправить и проверить |
| Ошибка в нескольких связанных классах | Короткий план и выполнение в том же запросе |
| Неясная фича, миграция схемы, изменение API | Сначала исследование и отдельный план |
| Работа на несколько сессий | План и прогресс в файле |
| Несколько исполнителей | План, зависимости, распределение файлов, интеграция |

### План без обязательной остановки

```text
Перед изменениями коротко опиши план: что проверишь, что изменишь
и как докажешь результат. Если нет блокирующей неоднозначности,
сразу выполни его. Не жди отдельного подтверждения каждого шага.
```

### Только исследование и согласование

```text
Пока не меняй код. Изучи обработку повторных событий.
Предложи два варианта улучшения с компромиссами и рекомендуемый план.
Укажи изменяемые файлы, риски совместимости и проверки.
Остановись после плана: поведение выберем отдельно.
```

В поддерживающем клиенте можно включить **Plan mode**: в CLI — `/plan`; сочетания клавиш и элементы интерфейса проверь в своём клиенте. Режим предназначен для исследования и планирования до реализации. Текст «сначала составь план» в обычном режиме сам по себе не переключает интерфейсный режим. Официальные рекомендации по [планированию сложных задач](https://learn.chatgpt.com/guides/best-practices) также допускают обычную просьбу подготовить план.

### Как отличить полезный план от формальности

«Изучить → реализовать → проверить» почти ничего не сообщает. Полезный план называет неизвестное и способ его разрешить:

```text
1. Проверить, где eventId получает уникальность и как откатывается inbox.
2. Сформулировать требование для пустого walletId и выбрать тип ошибки.
3. Добавить проверку на входе без изменения транзакционных границ.
4. Проверить новые случаи и существующие тесты повторной обработки.
```

Для длинной задачи попроси `docs/plans/<задача>.md` с целью, критериями, решениями, этапами, проверками и оставшимися вопросами. Имя `PLANS.md` не имеет универсальной магии: если используешь его как шаблон, объясни в `AGENTS.md`, когда и как следовать ему. План можно менять, если исследование показало неверное предположение; причину изменения нужно назвать.

## 6. Приёмы написания промптов

Следующие приёмы — практические способы постановки задач, а не обязательный синтаксис Codex. Обычно достаточно нескольких предложений. Полный шаблон из [конспекта о работе с ИИ](ai-workflow.md) нужен для более сложных случаев.

### 6.1. Наблюдаемый результат и критерии готовности

Вместо «улучши обработку ошибок»:

```text
После неизвестного walletId операция должна завершаться ошибкой,
а inbox-маркер не должен мешать повтору после создания кошелька.
Проверь, покрыт ли сценарий тестом. Существующее поведение сохрани.
```

Критерий описывает поведение, а не количество написанных классов. Формат Given/When/Then помогает: «Дано… Когда… Тогда…». Для финансового примера отдельно задай единицы суммы, допустимость нуля и область уникальности идентификатора.

### 6.2. Контекст, ограничения, примеры

Укажи файлы, ошибку, команду воспроизведения и ожидаемый результат. Если точное место неизвестно, дай агенту искать. Не нужно вручную вставлять весь репозиторий в чат.

```text
Контекст: src/main/java/ru/learn/delivery и тесты того же пакета.
Ограничения: Java 17, без новых зависимостей и изменения схемы БД.
Примеры: walletId="" и "   " отклоняются; "alice" допустим.
Не обрезай пробелы у непустого идентификатора: это отдельное решение.
```

Один-два образца желаемого результата — **few-shot prompting**. Например, покажи хороший разбор ошибки с полями «причина / воспроизведение / проверка», если нужен такой же формат. Образцы должны быть согласованы с требованиями.

### 6.3. Разделение исследования и реализации

Когда причина неизвестна, сначала задай проверяемый вопрос. «У нас гонка, поставь synchronized» заранее навязывает возможное неверное решение.

```text
Два consumer иногда обрабатывают одно событие.
Построй гипотезы по коду и логам. Для каждой назови проверку,
которая может её опровергнуть. Сначала установи причину,
затем предложи минимальное исправление.
```

Это **hypothesis-driven debugging**: гипотеза → наблюдение → проверка → вывод. Проси доказательства, а не длинный внутренний монолог модели. Кратких причин решения, допущений и результатов команд достаточно.

### 6.4. Декомпозиция и маленькие порции

«Построй платёжную платформу» тяжело оценить. Сначала выдели один сквозной сценарий: запрос → сохранение → повтор → тест. Следующий слой добавляй после проверки первого. Это снижает стоимость исправления неверной трактовки.

### 6.5. Контрпримеры и критика

```text
Проверь решение на повторном событии, двух одновременных consumer,
ошибке БД и сбое после commit до ACK. Для каждого сценария объясни
состояние данных и укажи подтверждающий тест либо пробел проверки.
```

Повторная самопроверка полезна, но не является независимым доказательством. Тест, воспроизведение, проверка схемы и ревью другим агентом дают дополнительные сигналы. Несколько агентов тоже могут разделять одну неверную предпосылку.

### 6.6. Работа с неясными требованиями

```text
Сначала изучи проект. Задай одним сообщением только вопросы,
ответы на которые меняют контракт, данные или объём работы.
По обратимым техническим деталям назови допущения и продолжай.
```

Для сырой идеи полезнее интервью до пяти ключевых вопросов, чем огромный план из догадок. Для точной локальной задачи интервью обычно избыточно.

### 6.7. Формат отчёта

```text
В конце укажи: что изменено, какие команды реально выполнены,
их результат и что осталось непроверенным.
Если проверка упала из-за окружения, отдели это от ошибки реализации.
```

Не принимай «всё готово» за результат проверки. И не требуй недостижимого «гарантируй отсутствие любых багов»: задай конкретные сценарии и достаточную для задачи глубину проверки.

### 6.8. Что обычно не помогает

- «Ты лучший senior в мире» без конкретных условий: роль не заменяет требований.
- «Всегда делай TDD»: полезно для многих изменений поведения, но бессмысленно для исправления ссылки.
- «Никогда не задавай вопросов»: агент может выбрать неправильное продуктовое поведение.
- «Улучши всё, что увидишь»: размывает объём и затрудняет ревью.
- Один мегапромпт с противоречивыми запретами: оставь актуальные ограничения, а постоянные правила вынеси в `AGENTS.md`.

## 7. Субагенты и «рой агентов»

### Что происходит на самом деле

Главный агент получает задачу, делегирует ограниченные части другим агентам, собирает ответы и отвечает за итоговую интеграцию. Отдельный контекст помогает вынести подробное исследование из основного чата. Агент не обязательно работает в отдельной копии файлов: **отдельный контекст и отдельная рабочая директория — разные вещи**.

«Рой» — не обещание специальной кнопки или бесконечного числа исполнителей. В этом руководстве так называется несколько координируемых агентов. Для начала разумнее два-три узких исполнителя. Параллелизм имеет цену: дополнительные токены, ожидание зависимостей, возможные конфликты и общий запуск проверок.

В этой сессии инструменты субагентов доступны, но их запуск требует явной просьбы пользователя либо применимых инструкций проекта/навыка. Для этой документации агенты не запускались: просьба объяснить механизм не равна просьбе делегировать текущую задачу.

### Как запустить

Достаточно явной инструкции в чате. Не нужно самому вызывать внутреннюю функцию `spawn_agent`:

```text
Используй двух субагентов для анализа пакета ru.learn.delivery.
Первый проверяет транзакции и идемпотентность.
Второй изучает тесты и ищет непокрытые сценарии.
Обоим запрещено менять файлы. Дай каждому контекст и границы задачи.
Дождись обоих, сопоставь выводы с кодом и верни единый отчёт
с файлами и подтверждёнными проблемами. Реализацию пока не начинай.
```

Это настоящий параллельный анализ. Просьба одному агенту «ответь как архитектор, тестировщик и reviewer» задаёт несколько перспектив, но сама по себе не запускает независимые агентные сессии.

В поддерживаемом CLI есть `/subagents` для просмотра агентных потоков; приложение и IDE показывают активность в своём интерфейсе. Если инструментов нет или достигнут лимит, попроси явно сообщить об этом и выполнить части последовательно. Не считай придуманные «отчёты агентов» реальным запуском.

### Пример роя для разработки

```text
Используй до трёх субагентов для согласованной фичи экспорта истории.
Сначала сам зафиксируй контракт, границы модулей и зависимости.
1. Исследователь: только анализ текущей архитектуры и ограничений.
2. Исполнитель: реализация после фиксации контракта, только согласованные файлы.
3. Reviewer: после реализации проверка требований и негативных сценариев;
   файлы не меняет.
Независимые части выполняй параллельно, зависимые — после входных результатов.
Для параллельных изменений пересекающихся файлов используй отдельные worktree,
если среда это поддерживает; иначе выполняй такие изменения последовательно.
Ты отвечаешь за интеграцию, разрешение конфликтов и итоговые тесты.
```

Здесь не все три этапа параллельны: reviewer должен увидеть реализацию, исполнитель — контракт. Организация работы важнее числа агентов.

### Как предотвращать конфликты

| Работа | Как организовать |
| --- | --- |
| Два независимых исследования | Общая копия допустима, без изменений файлов |
| Изменение разных файлов с устойчивым контрактом | Явно назначить владельцев; учесть общие выходные файлы сборки |
| Изменение одних классов | Разные worktree с последующей интеграцией либо последовательно |
| Общий `pom.xml`, миграции, контракт DTO | Один ответственный за согласование |
| Сборка и интеграционные тесты | Учесть общие порты, БД, контейнеры и каталоги результатов |

Отдельные Git-ветки в **одной** рабочей директории не изолируют одновременные правки. Worktree даёт отдельную рабочую копию, но не отдельный Docker daemon или БД. Изоляцию нужно проверить, а не предположить. Подробнее о Git — в [соседнем конспекте](git.md).

### Собственный тип субагента

Обычного запроса достаточно для первого использования. Для повторяющейся роли текущие локальные клиенты поддерживают TOML-файлы в `.codex/agents/` для проекта или `~/.codex/agents/` для пользователя. Например, `.codex/agents/tx-reviewer.toml`:

```toml
name = "tx_reviewer"
description = "Проверяет транзакции и конкурентную обработку в Java/Spring."
developer_instructions = """
Анализируй код, схему БД и тесты. Не меняй файлы.
Проверяй атомарность, повторную доставку и гонки.
Возвращай подтверждённые проблемы с файлом, сценарием и последствием.
Отделяй ограничения окружения от ошибок кода.
"""
```

Затем: «Запусти субагента `tx_reviewer` для проверки `WalletLedger`». Модель можно не указывать: используются наследуемые настройки. Инструкция «не меняй файлы» не создаёт отдельного запрета записи на уровне ОС.

В текущей схеме конфигурации лимит можно задать так, например в `.codex/config.toml` доверенного проекта:

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 3
```

Этот лимит относится к одновременно открытым порождённым потокам, без главного. Он не выдаёт дополнительные квоты и не отменяет ограничения среды. Не переноси настройки из старых статей без сверки версии: устройство конфигурации менялось. Формат ролей, наследование прав и команды описаны в [официальной документации субагентов](https://learn.chatgpt.com/docs/agent-configuration/subagents).

## 8. Контекст и длинная работа

Большой чат не заменяет проектную документацию. Полезные решения могут потеряться среди логов; при продолжении сессии часть контекста может быть сжата.

Практический порядок:

1. Один чат — одна связная цель. Резко другую задачу начинай отдельно.
2. Для большой работы сохраняй цель, согласованные решения и прогресс в файл.
3. После смены чата проси прочитать этот файл и сверить состояние с кодом и `git diff`.
4. Не переноси тысячи строк логов, если достаточно команды, ошибки и релевантного фрагмента.
5. Постоянные правила храни в `AGENTS.md`, процедуры — в skills, требования фичи — в её спецификации.

Запрос для продолжения:

```text
Продолжи задачу по docs/plans/wallet-validation.md.
Сначала сопоставь план с текущим кодом и рабочим diff.
Не считай отмеченные этапы доказательством выполненных тестов.
Определи следующий незавершённый шаг и доведи задачу до критериев готовности.
```

## 9. Рекомендуемый набор привычек для этого проекта

Начни с короткого `AGENTS.md`, точных задач и проверки diff. Не нужно сразу заводить десяток навыков и ролей. Когда обнаружится повторяемая полезная процедура, вынеси её в один skill. Для сложного исследования попробуй двух субагентов без записи. Spec Kit подключай для достаточно большой фичи с неоднозначными требованиями.

| Если хочешь… | Напиши… |
| --- | --- |
| Разобраться | «Объясни по конкретным файлам, код не меняй» |
| Сделать локальную правку | «Вот поведение, границы и критерии; исправь и проверь» |
| Сначала выбрать подход | «Только исследование и план, после него остановись» |
| Уменьшить лишние согласования | «Краткий план и сразу выполнение, вопросы только по существенной неопределённости» |
| Повторять процедуру | «Создай проектный skill с понятными входом, шагами и результатом» |
| Получить параллельный анализ | «Запусти двух субагентов с разными вопросами, дождись и сверь выводы» |
| Проверить готовность | «Сопоставь каждый критерий с кодом и выполненной проверкой» |
