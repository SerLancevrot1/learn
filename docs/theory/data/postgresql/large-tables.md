# Большие таблицы PostgreSQL: секции, BRIN и цена изменения строки

[Хранилища](../README.md) · [Планы и составные индексы](performance.md) · [Реплики и VACUUM](recovery.md)

## Выбор зависит от работы, которую нужно убрать

Сервис хранит журнал заказов за три года. Типовые запросы читают события последних суток по клиенту. Политика хранения удаляет записи старше 180 дней. Один большой B-tree по времени помогает найти диапазон, но массовое удаление старых строк создаёт WAL и версии, которые позже нужно обработать. Секционирование по времени позволяет отделить выбранный диапазон и удалить его как объект по плану эксплуатации. Если главный запрос ищет запись по ID без времени, разбиение именно по дате может заставить проверять несколько секций. Сначала запиши распределение запросов, а затем выбери ключ.

| Подход | Какую работу уменьшает | С чем нужно считаться |
| --- | --- | --- |
| Составной B-tree | Поиск по ключу, сортировка и ограниченные диапазоны | Индекс на запись, место и обслуживание |
| BRIN | Проверку неинтересных диапазонов страниц в физически коррелированных данных | Возможные повторные проверки строк, зависимость от раскладки |
| Range partitioning | Сканирование неподходящих секций и удаление старых диапазонов | DDL, ключ уникальности и подготовка будущих секций |
| Архивная витрина | Нагрузку истории на рабочий кластер | Асинхронное копирование, полнота и запросы через отдельный интерфейс |

## Секционирование по времени

В PostgreSQL декларативное range partitioning маршрутизирует новые строки по интервалам ключа. Верхняя граница исключается. При временных значениях указывай явное смещение для границ, чтобы DDL не зависел от timezone сессии.

```sql
CREATE TABLE order_audit (
    happened_at timestamptz NOT NULL,
    event_id bigint NOT NULL,
    order_id bigint NOT NULL,
    kind text NOT NULL,
    PRIMARY KEY (happened_at, event_id)
) PARTITION BY RANGE (happened_at);

CREATE TABLE order_audit_2025_03 PARTITION OF order_audit
    FOR VALUES FROM ('2025-03-01 00:00:00+00') TO ('2025-04-01 00:00:00+00');

CREATE INDEX order_audit_order_time_idx
    ON order_audit (order_id, happened_at DESC);
```

В примере создали одну секцию. Вставка за апрель не найдёт секцию, пока она отсутствует. Можно создать нужные периоды заранее и проверять следующий диапазон отдельной проверкой. Default partition служит предохранителем, но может скрывать пропущенную ротацию. При подключении новой секции сервер проверяет, что default не содержит строки этого диапазона. Если там накопился большой объём, перед переключением понадобится работа по переносу и условиям проверки. Наблюдай фактическое число строк default.

### Partition pruning

Планировщик или исполнитель могут исключить секции, если условия запроса позволяют доказать, что нужных значений там нет. Запрос `WHERE happened_at >= ? AND happened_at < ?` выражает это ясно. Условие только по `order_id` не задаёт интервала времени. Преобразование колонки функцией может затруднить вывод ограничения. Проверь `EXPLAIN` и реально выполненные subplans для режима параметров приложения. Индексы помогают внутри выбранной секции. Само секционирование не превращает поиск в индексное чтение.

**Слишком много секций.** По одной секции на час за пять лет — десятки тысяч объектов. Планирование, метаданные, индексы и обслуживание уже заметны. Месячная секция для журнала может быть достаточной, если фильтр активен на сутки, а внутри действует индекс. Если удаление ежедневное и объём большой, более мелкая гранулярность может быть оправдана. Не выбирай размер по одному количеству строк: учитывай число реально затронутых секций и период удаления.

### Уникальность и независимая запись

У partitioned table PostgreSQL 17 ограничения PRIMARY KEY и UNIQUE должны включать соответствующие колонки ключа секционирования в поддерживаемой форме. Локальные индексы секций не могут сами сравнить `event_id` во всех секциях. Схема выше гарантирует уникальность пары `(happened_at, event_id)`. Для строгого `event_id` независимо от времени может потребоваться отдельная таблица ключей или иной дизайн владельца. Проверка `SELECT` по всем секциям без общей точки записи допускает гонку. Приложение также не должно само выбирать новый timestamp при повторе, если пара служит его дедупликации.

**Detach для архивирования.** Период можно отсоединить и оставить отдельной таблицей на время экспорта. Переключение выполняется с правилами блокировок, которые зависят от выбранной операции. Планируй подключение секций и очистку с короткой проверяемой процедурой. Перед удалением сверяй хранение, backup и потребителей старой истории. Физическое удаление диапазона означает смену контракта доступа к этому периоду.

[PostgreSQL 17, декларативные секции, pruning, ограничения и DDL](https://www.postgresql.org/docs/17/ddl-partitioning.html)

## BRIN и физическая корреляция

BRIN хранит компактные summary для диапазонов блоков. Для простого min/max по времени, если записи приходят примерно по мере возникновения, соседние страницы часто содержат близкие даты. Диапазон summary помогает отвергнуть многие страницы. Получив подходящий диапазон, запрос проверяет отдельные строки. Индекс может быть маленьким и полезным на большой таблице, где B-tree оказался дорог.

Пример: первый участок страниц покрывает даты 1–3 марта, второй 4–6 марта. Для запроса по 5 марта первый участок исключается. Если из-за хаотической загрузки на каждой странице перемешан весь год, min/max почти везде совпадает с запросом и страниц будет прочитано много. BRIN не решает поиск одной случайной строки по UUID так же, как B-tree. После backfill или UPDATE данных распределение может измениться. Сравни `BUFFERS`, recheck и количество реально пройденных heap blocks. Обычно полезно проверять разные интервалы, а не только один идеальный фильтр.

[PostgreSQL 17, устройство BRIN](https://www.postgresql.org/docs/17/brin.html)

## UPDATE, HOT и fillfactor

MVCC обновляет строку, создавая новую версию. Изменение может требовать новых записей в индексах. HOT (Heap-Only Tuple) допускает обновление без добавления новых индексных записей для обычных индексов, когда не меняются связанные с ними колонки по правилам PostgreSQL и на той же странице есть свободное место. Суммаризирующие индексы имеют особенности. Если в каждом UPDATE меняется индексируемый `updated_at`, вероятность HOT может снизиться, даже если бизнес-индекс использует только другой столбец.

Меньший `fillfactor` оставляет место на страницах для будущих версий. Это дополнительные страницы и I/O для чтения, поэтому его выбирают под реальную долю обновлений. Если таблица почти append-only, резерв большого пространства может оказаться лишним. Сопоставь `n_tup_upd` и `n_tup_hot_upd`, рост индексов, WAL и запросы выборки. Не вводи индекс на поле, по которому никто не фильтрует, только потому что он «часто меняется». Любой индекс нужен для реального запроса или ограничения.

[PostgreSQL 17, Heap-Only Tuples](https://www.postgresql.org/docs/17/storage-hot.html)

## Самопроверка

<details>
<summary>Сделали месячные секции, поиск по event_id стал дольше. Как объяснить?</summary>

Запрос не указал время, поэтому план может проверять несколько секций. Смотри фактический план. Если глобальный поиск обязателен, подумай о таблице ключей, хранящей время, или другом разбиении.

</details>

<details>
<summary>BRIN по времени занимал мало места, но после хаотичного импорта перестал ускорять запросы. Почему?</summary>

Физически соседние диапазоны могли получить большие пересекающиеся min/max. Тогда индекс не исключает большую часть страниц. Проверь recheck и buffers и сравни с размещением данных.

</details>

<details>
<summary>Почему создание индекса на частое поле ухудшило throughput записи?</summary>

Появилась работа по обслуживанию индекса, а обновления по этому полю могут мешать HOT. Измерь, какие запросы реально используют индекс и как изменились затраты записи.

</details>
