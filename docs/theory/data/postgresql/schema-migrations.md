# PostgreSQL: изменение схемы и перенос данных без остановки сервиса

[Базы данных](../README.md) · [SQL и ограничения](sql-and-schema.md) · [Выпуск в Kubernetes](../../operations/devops.md#выпуск-с-изменением-контрактов-и-данных)

## Схема живёт дольше одного релиза

Сервис хранит номер отправления в `orders.tracking_number`. Новый контракт поддерживает несколько посылок, поэтому появилась таблица `shipment`. Старый код читает колонку, новый хочет читать таблицу. Во время rolling update запросы попадут в обе версии, а rollback может вернуть старую. Если первым шагом удалить колонку, часть трафика сразу сломается.

Разложи задачу на три состояния. **Expand** добавляет новые данные и формы записи. **Migrate** переносит существующее состояние, переключает писателей и читателей, проверяет инварианты. **Contract** удаляет устаревшее, когда оно больше не требуется. У каждого шага есть наблюдаемый критерий окончания. «Команда завершилась без ошибки» сообщает об исполнении команды, для проверки нужны данные и нагрузка.

### Сценарий с новой колонкой

Пусть старое приложение хранит статус заказа в `state_text`, новое вводит `state_code`.

| Шаг | Что делает приложение | Что проверяем |
| --- | --- | --- |
| Появилась nullable `state_code` | Старый код читает и пишет старое поле | Действующий API работает во время DDL |
| Выпущен writer, понимающий обе формы | Новые экземпляры записывают оба представления в одной транзакции | Преобразование обратимо или ограничено общей областью значений |
| Старых writer больше нет или есть гарантированный механизм совместимости | Можно заполнить историю и отслеживать отставание | Каждая конкурентная правка тоже поддерживает новое поле |
| Новый reader использует новое поле | При необходимости проверяет обе формы в переходный период | Сходятся строки и бизнес-агрегаты |
| Старый контракт снят | Остановлена запись устаревшей формы, затем удалена колонка | Учитываем допустимый откат, отчёты, фоновые потребители и CDC |

В двойной записи в одной строке PostgreSQL атомарно сохраняет обе колонки. Двойная запись в разных системах создаёт окно сбоя. Например, можно сохранить колонку в PostgreSQL и забыть обновить документ поискового индекса. Для асинхронной индексации нужны сохраняемое намерение, повтор и сравнение версии. Если двухпроекционное чтение возвращает разные данные, собирай метрику расхождений. Несовпадение можно оставить в старой схеме как основной ответ до исправления и проверить расхождения на конкретных ID вне публичного запроса.

### Где возникает гонка в backfill

Worker прочитал старый статус `NEW`, приложение обновило заказ до `PAID` и записало обе формы. Если worker вычислит значение в Java и безусловно выполнит UPDATE позже, он вернёт новую колонку к NEW. Защити перенос от устаревшего входа. Например, заполняй только строки, где новое поле ещё NULL, или проверяй версию прочитанного состояния. Если преобразование помещается в SQL, вычисляй его из актуальной строки в самом UPDATE.

```sql
UPDATE orders
SET state_code = CASE state_text
    WHEN 'new' THEN 10
    WHEN 'paid' THEN 20
    WHEN 'sent' THEN 30
END
WHERE id >= :from_id AND id < :to_id
  AND state_code IS NULL
  AND state_text IN ('new', 'paid', 'sent');
```

Порция по диапазону первичного ключа ограничивает длительность транзакции. Условие NULL делает повтор безвредным для уже перенесённых строк. После ожидания конкурентного обновления PostgreSQL на READ COMMITTED перепроверяет условие для той же строки. При другой изоляции результатом может быть ошибка сериализации и новая попытка.

Пример предполагает, что NULL означает «ещё не перенесена». Неизвестный статус останется без значения, и его покажет проверка. Если NULL — допустимое бизнес-значение, храни прогресс отдельно или проверяй явную версию. Для сверки подсчитай необработанные строки и неэквивалентные значения. Выборку расхождений проверь по краевым случаям: пришедший позже заказ, отмена во время миграции, пустой старый статус.

Храни checkpoint после успешной фиксации порции. Сбой между фиксацией и записью checkpoint повторит безопасную порцию. Преждевременный checkpoint создаст пропуск. Ограничь скорость и смотри влияние на пользовательский p99, количество мёртвых версий, WAL и отставание реплик. Пауза worker проста, если он завершает короткую транзакцию и возобновляет её с последнего допустимого места.

## DDL и блокировки

DDL, которое работает только с метаданными, всё равно может запросить сильную блокировку таблицы. Если уже идёт длинная транзакция, ожидающая DDL способна удлинить очередь новых операций. Различай время ожидания блокировки и время фактической работы команды. В миграции можно установить небольшой `lock_timeout` и повторить в подходящее окно. `statement_timeout` ограничивает всю команду, а проверка большой таблицы может законно требовать большего бюджета.

### Добавление ограничения в два шага

Для PostgreSQL 17 некоторые ограничения, включая CHECK и FOREIGN KEY, поддерживают `NOT VALID`. Это позволяет установить правило для новых или изменяемых данных, пропуская первоначальную проверку существующих строк. Затем исправляй накопленные расхождения и вызывай `VALIDATE CONSTRAINT`. Проверка использует иной режим блокировки, который допускает обычные обновления таблицы. У внешнего ключа есть также объект в связанной таблице, учитывай его блокировки.

```sql
ALTER TABLE orders
    ADD CONSTRAINT orders_state_code_known
    CHECK (state_code IN (10, 20, 30)) NOT VALID;

ALTER TABLE orders VALIDATE CONSTRAINT orders_state_code_known;
```

CHECK в SQL принимает UNKNOWN, поэтому `state_code IN (...)` не запрещает NULL. Если новая колонка обязательна, проверь это явно. После ограничения, которое доказывает отсутствие NULL, PostgreSQL может выполнить `SET NOT NULL` без повторного сканирования. Это отдельный шаг и отдельно проверяемая блокировка.

Большая UNIQUE-проверка требует общей уникальности. Подход с `CREATE UNIQUE INDEX CONCURRENTLY` и последующим присоединением индекса как ограничения применим к подходящему индексу и типу таблицы. Создание индекса CONCURRENTLY не выполняется внутри транзакционного блока. Некоторые инструменты по умолчанию оборачивают changeset в транзакцию. Сделай для такого шага отдельную конфигурацию и обработай повтор. При сбое может остаться invalid index. Название объекта и `IF NOT EXISTS` не подтверждают пригодность или эквивалентность индекса.

### Быстрый DEFAULT и реальная перезапись

Современный PostgreSQL может добавить колонку с неволатильным DEFAULT без обновления каждой строки на месте. Вызов часов через volatile-функцию может потребовать перезаписи таблицы. При изменении типа проверяй, нужен ли rewrite и какой объём окажется затронут. Для большого изменения удобно добавить колонку подходящего типа и перенести данные контролируемо.

Изменение названия колонки быстрое на уровне схемы, но старый клиент сразу потеряет имя. Полная цена миграции включает обновление всех клиентов, старых подготовленных запросов, отчётов, CDC и возможность отката. Для больших таблиц schema migration — часть дизайна контракта поставки.

## Кто и когда запускает миграции

Если каждое из двадцати приложений на старте пытается менять одну схему, координация инструмента может пропустить одного runner. Остальные ждут, а долгий DDL влияет на время запуска и readiness. Отдельный контролируемый шаг релиза даёт явный результат, бюджет и одну точку наблюдения. Приложение затем стартует при наличии совместимой схемы. Успешный DDL сам по себе не устанавливает совместимость приложения со всеми состояниями схемы.

У миграции есть способ отмены или безопасного продолжения. При откате приложения после добавления nullable-колонки новую колонку обычно сохраняют до выяснения. После backfill простой `DROP COLUMN` может удалить данные, которые уже использует новый writer. Определи окно совместимости и что делать при частичном выполнении. Проверяй в тестовой БД реалистичный объём, старый и новый код одновременно, затем повторный запуск. Строки с ошибкой сериализации и необычными значениями полезнее идеальной пустой схемы.

## Самопроверка

<details>
<summary>Backfill поставил старый статус поверх нового. Как исправить границу записи?</summary>

Вычисляй из текущей строки в SQL. Для внешнего расчёта используй условие по ожидаемой версии или признак «ещё не заполнено». Приложение должно поддерживать согласованность обеих форм при каждой новой правке.

</details>

<details>
<summary>Почему добавление короткого DDL задержало HTTP, хотя команда почти ничего не вычисляет?</summary>

DDL может ждать сильную блокировку у длинной транзакции и стоять в очереди перед другими запросами. Проверь lock wait, blocker и время удержания. Раздели ожидание и работу команды.

</details>

<details>
<summary>Через NOT VALID добавили CHECK. Какие строки теперь могут нарушать правило?</summary>

Уже существовавшие строки могут ещё не пройти проверку. Правило применяется к новым записям и обновлениям. Исправь старые данные и выполни validate.

</details>

<details>
<summary>Колонку больше не читает новая версия. Что проверить перед удалением?</summary>

Старые экземпляры, фоновые задачи, отчёты, consumer CDC и окно rollback. Удаление означает завершение прежнего контракта для всех участников.

</details>
