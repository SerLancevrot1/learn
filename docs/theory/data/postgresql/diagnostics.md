# PostgreSQL из Java: запросы, блокировки и пул соединений

**Ответ за минуту.** Если выросло время доступа к БД, раздели ожидание соединения, исполнение SQL, ожидание блокировки и выдачу результата. Дальше выбери измерение: метрики JDBC-пула для первой части, `pg_stat_activity` для текущего ожидания, `pg_stat_statements` для истории и `EXPLAIN` для плана конкретного запроса.

## Инцидент: p99 вырос, CPU базы почти не изменился

Медленный HTTP-запрос из трёх секунд 2.8 с ждал соединение из пула. SQL завершился быстро. Чтение его плана мало скажет о проблеме. Ищи, почему соединения не возвращаются: слишком длинные транзакции, SQL в ожидании блокировки, внешний вызов внутри транзакции, параллельный импорт или разросшийся N+1. Сопоставь в одном временном окне:

| На стороне приложения | На стороне PostgreSQL |
| --- | --- |
| Время получения соединения и число ожидающих | Число подключений и активных сессий |
| Время SQL и транзакции | `state`, `wait_event_type`, `wait_event`, `xact_start` |
| Число запросов в одном бизнес-действии | `calls`, накопленное время исполнений, число обработанных строк |
| Загрузка пула на каждом экземпляре | Суммарный бюджет соединений для приложений и обслуживания |

Если приложение держит 20 соединений на экземпляр, шесть экземпляров могут открыть до 120. После масштабирования до двадцати это уже 400. Параллельно деплой может держать старые и новые экземпляры. Учитывай соединения других сервисов и оставляй место для обслуживания. Количество подключений и приемлемое число одновременно работающих тяжёлых запросов — разные ограничения.

## Найти блокировку и её владельца

```sql
SELECT pid,
       state,
       wait_event_type,
       wait_event,
       clock_timestamp() - xact_start AS transaction_age,
       pg_blocking_pids(pid) AS blockers
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid()
  AND (state = 'idle in transaction' OR wait_event_type = 'Lock')
ORDER BY xact_start NULLS LAST;
```

Допустим, PID 201 обновляет заказ и видит `Lock`; в `blockers` указан 199. PID 199 в состоянии `idle in transaction` пять минут. Он завершил прошлый SQL, но его транзакция всё ещё открыта. Проверь владельца соединения, последнюю операцию и код между началом и завершением транзакции. Частый пример — код сохранил заказ и ждёт HTTP к провайдеру до commit. Для обычного обновления это удерживает блокировку строки на всё ожидание. Прочитай [сценарий с outbox](../../messaging/delivery-patterns.md#9-outbox-и-cdc), если внешний шаг допускает отдельную обработку.

**State и wait event — разные измерения.** Сессия `active` исполняет запрос и может одновременно ждать, например блокировку транзакции. `idle` обычно просто ждёт новую команду. `idle in transaction` означает незавершённую транзакцию без текущего запроса. Длительная транзакция также может удерживать старый снимок и мешать vacuum убрать уже невидимые большинству версии строк.

| Ограничение | Что прерывает |
| --- | --- |
| Тайм-аут получения соединения | Ожидание свободного JDBC-соединения до отправки SQL |
| `lock_timeout` | Слишком долгое ожидание конкретного захвата блокировки |
| `statement_timeout` | Слишком длительную команду в PostgreSQL, включая ожидание внутри команды |
| `idle_in_transaction_session_timeout` | Соединение, которое слишком долго бездействует внутри открытой транзакции |

Подбирай значения под путь запроса. Короткий дедлайн HTTP сам по себе не освобождает соединение и не прекращает серверный SQL. После ошибки команды в явной транзакции PostgreSQL обычно нужно сделать rollback всей транзакции или откатиться к заранее поставленной точке сохранения. Для deadlock и serialization failure обычно повторяют всю команду с новой транзакции. Повтор после внешнего эффекта опирается на то, что этот эффект идемпотентен или уже сверён. [PostgreSQL 17, статистика и ожидания](https://www.postgresql.org/docs/17/monitoring-stats.html) · [Параметры клиента и тайм-ауты](https://www.postgresql.org/docs/17/runtime-config-client.html)

## Найти запрос с наибольшей стоимостью для сервиса

Расширение `pg_stat_statements` агрегирует статистику по нормализованным запросам. Нужна настройка сервера и установка расширения в нужной БД. Отдельный вызов может быть быстрым, хотя суммарно этот SQL тратит больше всего времени. Например, 800 000 запросов по 1 мс дают 800 с накопленного времени исполнения, а тридцать запросов по 700 мс — 21 с. Первый кандидат похож на N+1 или избыточные вызовы, второй может объяснить высокий хвост задержек конкретного API.

```sql
SELECT queryid,
       calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       rows,
       shared_blks_read,
       shared_blks_hit
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

Счётчики накопительные и могут обнуляться. Для интервала инцидента сравни два снимка и их время; среднее за всё время не отражает p99. `shared_blks_read` — чтения блоков, которых не было в shared buffers. Операционная система могла отдать их из своего кеша, поэтому сравни статистику I/O и время. Этим запросом легко выбрать кандидата, а чтобы найти форму входа, нужны трассы и репрезентативные параметры.

[PostgreSQL 17, pg_stat_statements](https://www.postgresql.org/docs/17/pgstatstatements.html)

## Разобрать план и проверить изменение

1. Возьми запрос с фактическими условиями, сортировкой и лимитом. Повтори для частого и редкого значения фильтра. На периоде нескольких лет план может разумно выбрать другой доступ, чем за один день.
2. Сравни `rows` в оценке и `actual rows` в соответствующем узле. При `loops > 1` фактические строки и время в узле усреднены на один проход. Например, `actual rows=120 loops=400` означает около 48 000 выходных строк за все проходы.
3. Найди первую крупную ошибку оценки по дереву. Причинами могут быть устаревшая статистика, различающаяся частота значений или зависимость колонок. `tenant_id` и `status` могут зависеть друг от друга. При подходящем типе запроса проверь расширенную статистику.
4. Посмотри на `Buffers`, сортировку, временные блоки, число проходов и `Rows Removed by Filter`. Большой seq scan может быть выгоден при чтении значительной части таблицы. Nested loop при небольшом внешнем наборе и быстром индексном поиске тоже может быть оптимальным.
5. После изменения измерь задержку, нагрузку на CPU, работу чтения и запись. Индекс ускоряет часть запросов, но влияет на вставку, обновление и обслуживание.

`EXPLAIN (ANALYZE, BUFFERS)` действительно выполняет SQL. Для тяжёлого SELECT используй репрезентативное окружение или ограничь эксперимент. Если анализируешь изменение данных, делай это на тестовой базе. Rollback защищает транзакционные изменения, но, например, значения последовательности уже могли сдвинуться.

### Почему частичный индекс иногда не выбирается

Частичный индекс `WHERE status = 'READY'` полезен, если готовых записей мало и запрос регулярно ищет их по дате. При планировании PostgreSQL должен вывести, что условие запроса включает предикат индекса. Литерал `status = 'READY'` это показывает. Обобщённый план с условием `status = $1` не может сделать вывод для всех возможных параметров. Конкретный план с известным значением может выбрать индекс. Проверь план с тем же режимом prepared statement, который использует Java-приложение. Разовый SQL из консоли с литералом может вести себя иначе.

При добавлении индекса на большую рабочую таблицу `CREATE INDEX CONCURRENTLY` позволяет продолжать обычные записи, но выполняет больше работы, ждёт завершения некоторых транзакций и не запускается внутри транзакционного блока. При ошибке проверь наличие invalid-индекса. Для миграции заранее оцени I/O, место, длительные транзакции и допустимый темп нагрузки.

## Самопроверка

<details>
<summary>Открытые соединения заняты, CPU базы низкий. Есть ли смысл увеличить пул?</summary>

Сначала проверю время ожидания пула, возраст транзакций и wait events. Если все ждут один PID, расширение пула добавит ждущих. Если запросы проводят время в приложении с открытой транзакцией, нужно пересмотреть жизненный цикл соединения.

</details>

<details>
<summary>EXPLAIN показывает actual rows=10 и loops=1000. Сколько строк выдал этот узел?</summary>

Примерно 10 000, поскольку строки указаны в среднем на один проход. Дальше посмотри, почему потребовалось 1000 проходов и насколько каждый из них дорог.

</details>

<details>
<summary>База замедлилась после роста нагрузки. Самый часто выполняемый SQL занимает 1 мс. Что проверишь?</summary>

Сопоставлю прирост числа вызовов и их суммарное время. Проверю, сколько одинаковых запросов на один HTTP-вызов, в том числе при сериализации. Если обнаружу N+1, сравню новый план по числу SQL, числу строк и длительности.

</details>
