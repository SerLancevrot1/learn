## Формулируй зерно результата

Зерно результата — чему соответствует одна строка. Для отчёта о выручке это может быть один день на магазин, для истории — один переход состояния заказа, для интерфейса — один заказ с последним статусом. Если не определить зерно, легко получить двойной счёт. Пример: у заказа две позиции и три попытки оплаты. Прямой join обеих связей породит шесть строк. Сумма по позициям увеличится втрое. Сумма статусов оплаты тоже перестанет означать ожидаемое число.

Если нужно вывести обе меры на заказ, сначала агрегируй позиции по `order_id`, отдельно агрегируй попытки по `order_id`, затем соединяй результаты. Для заказа без оплаты сохранение строки требует `LEFT JOIN`. Значение `NULL` после такого join означает отсутствие подходящего вычисленного результата. Преобразуй в 0 только там, где ноль предметно означает «операций нет».

### Мини-схема для чтения примеров

| Таблица | Поля |
| --- | --- |
| `order_event` | `id bigint`, `order_id bigint`, `status text`, `event_at timestamptz` |
| `merchant` | `id bigint`, `name text` |
| `payment` | `id bigint`, `merchant_id bigint`, `amount_cents bigint`, `status text`, `created_at timestamptz` |
| `category` | `id bigint`, `parent_id bigint`, `name text` |

ID — первичные ключи. Для примеров событий и платежей считаем бизнес-поля и времена известными. У корневой категории `parent_id` может быть `NULL`. Перед переносом в свою схему уточни типы ID, допустимость отсутствующих значений и названия статусов.

## Из событий к периодам действия

Пришли события одного заказа: `NEW` в 10:00, `PAID` в 10:12, `SHIPPED` в 11:30. Требуется узнать время нахождения заказа в каждом статусе. `lead` делает доступным время следующего события в окне этого заказа. Получится начало включительно и конец исключительно. Для последней строки конец неизвестен. В расчёте на момент отчёта ограничь историю и подставь этот момент для открытого конца.

```sql
WITH timeline AS (
    SELECT order_id,
           status,
           event_at AS valid_from,
           lead(event_at) OVER (
               PARTITION BY order_id
               ORDER BY event_at, id
           ) AS next_event_at
    FROM order_event
    WHERE event_at < TIMESTAMPTZ '2025-03-01 12:00:00+00'
)
SELECT order_id,
       status,
       valid_from,
       coalesce(next_event_at, TIMESTAMPTZ '2025-03-01 12:00:00+00') AS valid_to
FROM timeline
ORDER BY order_id, valid_from, valid_to;
```

Порядок внутри окна должен быть устойчивым. Добавили `id` при равном `event_at`, но ID здесь предполагается разрешением равенства по контракту. Если источник предоставляет номер версии, версия лучше описывает смысл. Для распределённого события различай время возникновения и время приёма. При поздней доставке повторный отчёт на ту же дату может пересчитать интервалы. Для воспроизводимого отчёта зафиксируй cutoff по приёму, снимок данных или версию витрины.

**Ошибка фильтра.** Если убрать события до начала выбранного дня перед расчётом окна, потеряется состояние, которое действовало на начале дня. Например, заказ стал PAID вчера и сегодня только SHIPPED. Чтобы посчитать, сколько времени сегодня он был PAID, возьми последнее событие до границы плюс события внутри интервала. После построения периодов обрежь их вычисленными границами и выброси непересекающиеся.

### Повтор статуса и смена статуса

Иногда два события подряд содержат одинаковый статус, например heartbeat или повторная доставка от источника с новым ID. Если отчёт считает время пребывания, хватает сложить соседние интервалы с тем же статусом. Если нужно посчитать число реальных переходов, используй `lag(status)`. Сравнение `previous_status IS DISTINCT FROM status` полезно при допустимом NULL. Для первой строки реши, является ли начальное присваивание переходом. В event-sourcing порядок и дедупликацию лучше поддерживать отдельно, чем восстанавливать только из timestamps.

## Несколько метрик из одной группы

Команда хочет видеть число попыток, число успехов и сумму успешных платежей за период. `FILTER` задаёт подмножество для отдельного агрегата. В отличие от фильтра в `WHERE`, остальные агрегаты сохраняют входы.

```sql
SELECT m.id,
       count(p.id) AS attempts,
       count(p.id) FILTER (WHERE p.status = 'PAID') AS paid,
       coalesce(sum(p.amount_cents) FILTER (WHERE p.status = 'PAID'), 0) AS paid_cents,
       count(p.id) FILTER (WHERE p.status = 'PAID')::numeric
           / nullif(count(p.id), 0) AS paid_ratio
FROM merchant m
LEFT JOIN payment p
       ON p.merchant_id = m.id
      AND p.created_at >= TIMESTAMPTZ '2025-03-01 00:00:00+00'
      AND p.created_at <  TIMESTAMPTZ '2025-04-01 00:00:00+00'
GROUP BY m.id
ORDER BY m.id;
```

У мерчанта без платежей `count(p.id)` равен 0, потому что `p.id` в искусственной строке join будет NULL. `count(*)` дал бы 1. Доля равна NULL, то есть знаменатель отсутствует. Соглашение «показывать 0% для пустого набора» можно применить на краю API. Тут важна последовательность: если позже сложить и усреднить проценты по мерчантам, магазины с одним и тысячей платежей получат равный вес. Общая доля считается как сумма успехов, делённая на сумму попыток.

**Статус на момент отчёта.** Пример берёт текущее значение `status`. Если в марте попытка была открыта, а в апреле стала PAID, пересчёт марта увидит успех. Бывают два разных бизнес-вопроса: состояние попыток, созданных в марте, сегодня или состояние на конец марта. Для второго нужен timestamp перехода, интервалы действия или материализованный снимок.

### Пустые дни в графике

Фактов может не быть, а графику нужна строка на каждый день. Сначала создай набор дней, затем left join факты по диапазону. Для PostgreSQL можно использовать `generate_series`. Индекс по времени обычно проще использовать с условием `created_at >= day_start AND created_at < next_start`, чем с преобразованием `created_at::date` у каждой строки. Для локального календаря вычисли UTC-границы каждого дня по зоне. [Java и границы местного дня](../../java/standard-library.md#несуществующий-и-неоднозначный-час)

Для большой истории можно агрегировать факты одним проходом по временному диапазону и затем присоединить готовые группы к календарю. Выбор зависит от числа групп, числа дней, предыдущей предагрегации и статистики. Проверь план на реалистичном объёме и границы интервала на днях с переходом часов.

## LATERAL для ограниченного поиска на каждый ключ

Для списка мерчантов нужно получить до двух последних успешных платежей каждого. `LEFT JOIN LATERAL` позволяет подзапросу видеть наружный `m.id`. С индексом по `(merchant_id, created_at DESC, id DESC)` и подходящим предикатом он может остановиться после первых совпадений. Если много мерчантов и нужны почти все строки, один проход с оконной функцией может быть выгоднее. Это вопрос измерения, а не общего правила.

```sql
SELECT m.id AS merchant_id, p.id AS payment_id, p.created_at
FROM merchant m
LEFT JOIN LATERAL (
    SELECT id, created_at
    FROM payment
    WHERE merchant_id = m.id AND status = 'PAID'
    ORDER BY created_at DESC, id DESC
    LIMIT 2
) p ON true
ORDER BY m.id, p.created_at DESC, p.id DESC;
```

Есть мерчанты без успеха, поэтому left join оставляет их с NULL в правых колонках. Ограничение действует для каждого мерчанта внутри подзапроса. Положение общего `LIMIT 2` снаружи поменяло бы смысл. Для больших запросов посмотрим `actual rows` и `loops` у внутреннего индекса. Если запрос много раз сканирует длинный список неподходящих статусов, нужен составной или частичный индекс, подходящий фильтру.

## Рекурсивный CTE и обход иерархии

Пусть дерево категорий хранит ссылку на родителя. Для вывода поддерева начинай с указанного ID и на каждой итерации добавляй его детей. PostgreSQL вычисляет рекурсивный CTE итеративно через рабочий набор. В примере путь хранится для обнаружения циклов и для заданной сортировки.

```sql
WITH RECURSIVE subtree(id, name, depth, path) AS (
    SELECT id, name, 0, ARRAY[id]
    FROM category
    WHERE id = 1

    UNION ALL

    SELECT c.id, c.name, s.depth + 1, s.path || c.id
    FROM subtree s
    JOIN category c ON c.parent_id = s.id
    WHERE NOT (c.id = ANY(s.path))
)
SELECT id, name, depth
FROM subtree
ORDER BY path;
```

Обычный внешний ключ гарантирует существование родителя, но сам по себе допускает цикл. Путь в примере обрывает ветку при повторе ID. Он не исправляет данные. Если цикл недопустим по бизнес-правилам, защищай операции изменения иерархии и проверяй существующие записи. Простой `UNION` удаляет только полностью совпадающие строки. При наличии depth или path повторный узел может иметь другие колонки, поэтому `UNION` не заменяет проверку цикла. При запросах по большим деревьям оцени размер поддерева и индекс по `parent_id`.

**CTE для читаемости и план.** Обычный CTE может быть встроен планировщиком в наружный запрос при определённых условиях. `MATERIALIZED` удерживает отдельное вычисление и может предотвращать проталкивание фильтра. `NOT MATERIALIZED` может дать больше возможностей/повторную работу, если CTE используется несколько раз. Не выводи стоимость по визуальному виду SQL. Сравни планы и длительность на тех же данных.

Оцени стоимость одного ограниченного индексного поиска и долю нужных результатов. Малый верхний N с подходящим индексом может быть эффективен. Для большой доли данных сравни с одним проходом через оконную функцию.

</details>

<summary>Создаём категории с внешним ключом на родителя. Получили бесконечный обход. Что позволило циклу появиться?</summary>
