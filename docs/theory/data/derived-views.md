## Зачем одному заказу три формы

В транзакционной БД заказ нужен для команд, уникальности и конкурентных переходов. Для личного кабинета нужен готовый документ, в котором вместе видны доставка, оплата и позиции. Аналитика регулярно читает миллионы заказов по времени и колонкам. Все запросы можно свести к исходной базе на ранней стадии. При независимой нагрузке производные представления позволяют выбрать свою форму хранения и режим восстановления. За это команда получает ответственность за свежесть и пересчёт.

| Слой | Источник результата | Как восстановить |
| --- | --- | --- |
| Транзакционный заказ | Команды владельца, ограничения и журнал изменений | Резервная копия и WAL по контракту БД |
| Документ кабинета | События заказа и связанные статусы | Снимок, повтор событий или новый построенный namespace |
| Витрина аналитики | Слой фактов по времени, версии схемы и преобразования | Повторяемый backfill и атомарная публикация снимка |

«Авторитетное хранилище» имеет смысл относительно конкретного решения. Платёж исполняется по данным владельца платежа. Витрина может показать последнее известное состояние, но задержка её обновления не должна разрешить повторное списание. Договорись, какие запросы читают cache/view, а какие обязаны проверить mutable state у владельца.

## MongoDB: событие и версия документа

Для read model удобно держать документ заказа целиком, если его данные ограничены и читаются вместе. Хранить бесконечную историю всех событий в массиве того же документа неудобно: ограничен размер документа, а частые обновления будут конкурировать за одну запись. В документе можно держать текущий статус и последние несколько записей, а полный журнал хранить отдельно. У доступа к списку заказов есть отдельный индекс, например `customerId, createdAt, _id`, согласованный с сортировкой и фильтром. Включи последний ID как разрешение совпавшего времени.

Представь, что обновление снапшота с версией 42 прилетело раньше 41. Атомарная операция обновляет один документ при условии `version < incomingVersion`. Тогда 41 не затрёт 42. Для первого создания нужно отдельно продумать конкурентный upsert: уникальность `_id` защитит от двух созданий, а конфликт после попытки создать должен привести к перечитыванию и проверке версии. Для дельт по `$inc` правило «старое пропускаем» может потерять существенный эффект. Дельта требует порядка или восстановимой проверки предыдущей версии.

**Полевые версии.** Если время доставки обновляется логистикой, а статус оплаты — платёжным сервисом, у двух потоков разные последовательности. Один числовой `version` для всего документа оправдан, когда есть единственный автор последовательности. Иначе версионируй части по источнику и обновляй только соответствующие поля. Штамп времени возможен как подсказка, но часы источников могут расходиться.

### Как читать владелец, только что создавший заказ

Даже при наличии записи с `writeConcern: "majority"` клиент может направить чтение на реплику, которая ещё не возвращает нужную запись без дополнительного протокола. В MongoDB причинные гарантии вроде read-your-writes описаны для causally consistent sessions и соответствующей пары read concern и write concern. Это договорённость внутри определённого контекста операций. Когда запись и чтение разделены HTTP и consumer, session БД сама по себе не догонит асинхронную витрину. Верни из команды минимальное состояние, которое уже известно, или ссылку на ресурс со статусом готовности. Для дальнейшего чтения можно задать ожидаемую версию и кратко ждать её в пределах дедлайна.

### Resume token и повтор после сбоя

Change Stream возвращает resume token. Его сохраняют как checkpoint после завершения эффекта. Если внешний эффект сохранили, а checkpoint нет, документ может прийти повторно при возобновлении. Сделай запись идемпотентной. Если сначала сохранить checkpoint и потерять эффект, возобновление пропустит запись. Для старого token может не хватать истории oplog. На этот случай выбери переснимок и правила переключения, при которых новое состояние не выдаётся как полное до построения. Token непрозрачен: не строи сортировку и бизнес-идентичность по его внутренней форме.

[MongoDB, causal consistency и concerns](https://www.mongodb.com/docs/manual/core/causal-consistency-read-write-concerns/) · [MongoDB, Change Streams и возобновление](https://www.mongodb.com/docs/manual/changestreams/)

## Parquet и Iceberg решают разные задачи

Parquet организует данные по колонкам и группам строк. Чтение запроса «сумма платежей по дню» может брать несколько колонок из широких файлов, минуя остальные. Метаданные групп строк и файлов помогают отфильтровать заведомо неподходящие диапазоны. Если день, мерчант и сумма перемешаны по всему набору, статистика не всегда позволяет эффективно отсечь чтение. Оцени распределение и форму запросов. Слишком мелкие файлы увеличивают число открытий и объектов метаданных. Очень большие группы могут уменьшать гранулярность пропуска данных и параллелизма.

Iceberg задаёт описание таблицы, снимки, список файлов, эволюцию схемы и партиционирования. У writer могут появиться новые data files до того, как они войдут в объявленный снимок. Reader, начавший с одного снимка, видит согласованный список файлов этого снимка. Если обходить объектный storage просто как директорию, можно взять старые и новые файлы одновременно. Используй метаданные таблицы, чтобы знать, какие файлы составляют выбранную версию.

### Несколько writer и конфликт публикации

Два job прочитали snapshot v1. Первый добавил партию A и зафиксировал v2. Второй хочет опубликовать B. Он должен проверить текущую версию и допустимость своей операции относительно новых изменений. Append независимых данных во многих сценариях можно повторить поверх v2. Если оба заменяют один partition, нужен конфликтный протокол и проверка, какую версию предполагалось заменить. Повторить commit старого переписывания без проверки означало бы потерять более свежие изменения. Реальное поведение зависит от типа операции, движка и параметров изоляции.

**Файл на диске ещё не факт таблицы.** Если приложение загрузило часть файлов, затем упало до публикации снимка, они могут остаться orphan. Их чистят отдельной процедурой с возрастным запасом и учётом работающих writer. Слишком агрессивная очистка удалит промежуточный файл, который ещё готовится к публикации. Удаление старых snapshots тоже влияет на возможность воспроизвести отчёт или сделать time travel.

### Эволюция схемы и партиции

Смена имени поля должна сохранять смысл старых файлов. В Iceberg колонки отслеживаются по идентификаторам полей. Смена partition spec позволяет новым файлам использовать иную разбивку, сохраняя возможность читать старые. Это полезно, если шардирование по дню стало слишком крупным и нужна дополнительная разбивка. Старые файлы не перераспределяются автоматически. Пока в таблице смешаны спецификации, планировщик работает с метаданными каждого файла. Если нужна однородная раскладка, потребуется перезапись с управлением стоимостью.

Схема хранит тип, но предметный смысл зависит от определения. Поле `price` с long может по-прежнему читаться после изменения рубли → копейки и искажать агрегаты. Правило изменения единиц прорабатывай как миграцию контракта. Введи новое явное поле, валидируй старые диапазоны и дату перехода. Подход аналогичен эволюции событий Kafka.

## Backfill и проверка результата

Нужно пересчитать март после уточнения правил комиссии. Сначала зафиксируй вход: список partition, cutoff поступления и версию исходного снимка. Подготовь расчёт в отдельном результатном наборе. Сверь количество уникальных платежей, контрольную сумму, распределение по валютам и известные краевые случаи. Валюты не смешивай в общей денежной сумме. Сравни плановую разницу с фактической, иначе успешный прогон может скрывать потерянные строки.

Изоляция выпуска полезна при исправлении больших данных. Новый результат можно проверить до смены указателя читаемой версии. Для замены ограниченного диапазона зафиксируй согласованность с записью новых опоздавших событий. Например, перед переключением обработай arrivals после cutoff или убедись, что следующий инкрементальный job возьмёт их с нужной позиции. Случай «новая витрина опять потеряла записи, которые появились пока она строилась» проверяй как отдельное окно. Для идемпотентности повтор задания с тем же диапазоном должен либо привести к той же логической версии, либо создать новую, которая заменяет старую, а не удваивает агрегаты.

## Самопроверка

<details>
<summary>В PostgreSQL заказ уже оплачен, а MongoDB UI показывает NEW. Где проходит гарантия?</summary>

Команда завершилась у владельца. MongoDB — производное состояние с отдельной задержкой. Проверь доступную версию и SLA свежести. Для read-your-writes нужен явно спроектированный путь после команды.

</details>

<details>
<summary>Job записал десять Parquet-файлов и упал до публикации Iceberg snapshot. Что увидит reader?</summary>

Читатель таблицы получает файлы из опубликованного снимка. Новые файлы могут остаться неиспользуемыми. Reader, обходящий хранилище по префиксу, рискует взять лишнее.

</details>

<details>
<summary>Восстановили consumer с новым snapshot. Как не потерять события в промежутке?</summary>

Определи согласованную точку snapshot и последующую позицию потока. Обработай накопившиеся после неё изменения, проверив повтор и удаление, прежде чем сменить читаемую версию.

</details>
