## 1. JVM: запуск, загрузка классов, JIT

`[ ]` **Короткий ответ:** JVM — виртуальная машина, исполняющая байт-код. JRE — JVM плюс стандартная библиотека. JDK — JRE плюс инструменты разработки (`javac`, `jcmd`, `jfr`, `jlink`). С JDK 11 отдельный JRE не поставляется Oracle/OpenJDK; минимальную среду собирают через `jlink` или берут JRE-сборки дистрибутивов.

### 1.1. От исходника до машинного кода

1. `javac` компилирует `.java` в байт-код `.class`.
2. JVM загружает нужные определения классов. Загрузка может произойти до первого активного использования.
3. При связывании JVM проверяет байт-код и подготавливает статические поля. Разрешение символических ссылок может происходить по мере необходимости.
4. При первом активном использовании запускаются статические инициализаторы класса.
5. HotSpot начинает исполнять байт-код и собирает профиль. В типичной многоуровневой компиляции C1 быстро компилирует код и помогает собрать профиль, а C2 применяет более дорогие оптимизации к достаточно горячему коду.

Оптимизации JIT: встраивание методов (inlining), escape-анализ (объект, не покидающий метод, можно не создавать в куче), удаление проверок, развёртывание циклов. Из-за JIT микробенчмарки без прогрева врут — нужен JMH.

### 1.2. Загрузка классов

`[ ]` **Короткий ответ:** загрузчики образуют иерархию: Bootstrap (ядро `java.base`) → Platform → Application (classpath). Загрузчик сначала делегирует запрос родителю и загружает сам, только если родитель не нашёл класс. Это защищает от подмены `java.lang.String` своим классом. Класс идентифицируется именем и загрузчиком: один и тот же `.class`, загруженный двумя загрузчиками, — два разных типа.

**Уточнение интервьюера:** «Когда выполняется статический блок?» — при инициализации класса: первое создание экземпляра, вызов статического метода, обращение к статическому полю (кроме констант времени компиляции), `Class.forName`. Обращение к `static final` константе времени компиляции класс не инициализирует — она встраивается в вызывающий код.

### 1.3. Предскажи, когда загрузится конфигурация

```java
class Settings {
    static final int DEFAULT_LIMIT = 100;
    static final Integer BOXED_LIMIT = 100;

    static {
        System.out.println("initialized");
    }
}

class InitDemo {
    public static void main(String[] args) {
        System.out.println(Settings.DEFAULT_LIMIT);
        System.out.println(Settings.BOXED_LIMIT);
    }
}
```

Сначала будет `100`. Константа типа `int` с константным выражением попадает прямо в байт-код вызывающего класса. Затем появятся `initialized` и ещё `100`. Поле `Integer` читается во время выполнения, поэтому к этому моменту JVM уже должна инициализировать класс. Такой же эффект встраивания возможен со строковой константой. Если значение из библиотеки поменяли, а клиент не пересобрали, клиент может продолжить использовать старый литерал.

Есть два способа получить объект `Class` без запуска статической инициализации самого класса: литерал `Settings.class` и `Class.forName(name, false, loader)`. Обычный `Class.forName(name)` инициирует инициализацию. Для диагностики HotSpot полезны отдельные события загрузки и инициализации, например `-Xlog:class+load=info,class+init=info`.

### 1.4. Похожее имя, разные сбои

| Симптом | Как рассуждать |
| --- | --- |
| `ClassNotFoundException` | Код явно попросил загрузить класс по имени. Проверь область поиска загрузчика и попадание зависимости в артефакт |
| `NoClassDefFoundError` | JVM не смогла получить нужное определение или использовать класс после неудачной инициализации. Найди первичную ошибку в более ранних логах |
| `ExceptionInInitializerError` | Инициализация завершилась исключением. Проверь причину и зависимости статического блока |
| `NoSuchMethodError` | Бинарный вызов ожидает конкретный метод. На runtime classpath могла попасть несовместимая версия библиотеки |
| `ClassCastException` с одинаковыми именами типов | Сравни определяющие загрузчики классов, особенно в плагинах и при горячей перезагрузке |

Если библиотека обновляется с двух сторон дерева Maven, посмотри `./mvnw.cmd dependency:tree`, затем состав собранного артефакта и классы, которые JVM реально загрузила. Разница между compile и runtime classpath объясняет, почему IDE компилирует код, а приложение падает при обращении к методу.

### 1.5. JIT, прогрев и измерение

JIT использует информацию о реальном выполнении. Если место вызова почти всегда видит один тип реализации интерфейса, HotSpot может встроить метод и добавить проверку своего предположения. При изменении профиля JVM способна перейти к менее оптимизированному коду и перекомпилировать его. Этот переход называется деоптимизацией. Поэтому короткий тест часто измеряет смесь прогрева, компиляции и полезной работы.

Например, ручной замер цикла `for (... ) new Point(1, 2);` может показать почти нулевую цену создания объекта. У объекта нет наблюдаемого использования, поэтому оптимизатор может убрать выделение вместе с телом цикла. Среднее время одного запуска также зависит от GC и фоновых задач. В JMH выдели прогрев, несколько измерений и отдельные JVM (forks), используй изменяемый вход, возвращай результат или передавай его в `Blackhole`. Для выбора реализации сравни условия реального приложения: размеры входа, распределение ключей, наличие конкуренции и аллокации на операцию.

[JVMS 17, загрузка и связывание](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-5.html) · [JLS 17, выполнение программы](https://docs.oracle.com/javase/specs/jls/se17/html/jls-12.html) · [Примеры JMH](https://github.com/openjdk/jmh/tree/master/jmh-samples/src/main/java/org/openjdk/jmh/samples)

## 2. Области памяти

`[ ]` **Короткий ответ:** **heap** — объекты и массивы, общая для всех потоков, управляется GC. **Стек потока** — кадры вызовов с локальными переменными и ссылками; у каждого потока свой. **Metaspace** — метаданные классов в нативной памяти. Статические поля хранятся не в Metaspace, а вместе с объектом `Class` в куче.

| Область | Что | Общая | Ошибка при нехватке |
|---|---|---|---|
| Heap | Объекты, массивы | Да | `OutOfMemoryError: Java heap space` |
| Стек потока | Кадры: локальные переменные, ссылки, промежуточные значения | Нет | `StackOverflowError` (глубокая рекурсия) |
| Metaspace | Метаданные классов | Да | `OutOfMemoryError: Metaspace` (утечка загрузчиков классов) |
| Code cache | Скомпилированный JIT-код | Да | Предупреждение, JIT отключается |
| Direct memory | `ByteBuffer.allocateDirect`, Netty | Да | `OutOfMemoryError: Direct buffer memory` |
| PC-регистр | Адрес текущей инструкции | Нет | — |

- Ссылка может лежать в стеке, а сам объект — в куче. Escape-анализ может вовсе убрать выделение объекта (скалярная замена).
- Поколения (young/old) и регионы — это способ организации кучи конкретным GC, а не отдельные области памяти JVM.
- В контейнере в лимит памяти входит всё: heap, metaspace, стеки, code cache, direct-буферы. См. [JVM в контейнере](../operations/devops.md#9-jvm-в-контейнере).

### 2.1. Used, committed, reserved и RSS

- **Used heap** — сколько кучи сейчас занято. До очередной сборки здесь есть и уже недостижимые объекты.
- **Committed** — объём памяти, который JVM предоставила для использования в конкретной области. Это может быть больше used.
- **Reserved** — диапазон виртуальных адресов, который JVM оставила для области. Он может быть заметно больше фактически использованных страниц.
- **RSS** — физические страницы процесса, находящиеся в памяти в этот момент. Включает нативную память, загруженные библиотеки и другие отображения. Для убийства процесса внутри контейнера сверяй причину завершения с потреблением памяти cgroup, поскольку лимит относится к её учёту.

Пример: контейнер ограничен 1024 МиБ, `-Xmx768m`, heap после GC около 400 МиБ, а под перезапустился как `OOMKilled`. JVM могла ещё держать ранее предоставленные страницы кучи. Кроме того, расходуются стеки platform-потоков, метаданные, память JIT, сетевые буферы и нативные библиотеки. Начни с графика по областям, количества потоков и прямых буферов, затем сравни два снимка NMT. NMT должен быть включён при старте и видит категории HotSpot, охват памяти сторонних нативных библиотек ограничен.

```powershell
# Замени 12345 на PID нужного Java-процесса.
$javaProcessId = 12345
jcmd $javaProcessId VM.native_memory baseline
# Повтори через несколько минут при той же нагрузке.
jcmd $javaProcessId VM.native_memory summary.diff
```

Свободное место в куче и доступная память процесса — разные числа. Увеличение `-Xmx` оставляет меньше места другим областям. После любого изменения посмотри память контейнера и задержки на том же профиле нагрузки. [Oracle, Native Memory Tracking](https://docs.oracle.com/en/java/javase/17/vm/native-memory-tracking.html)

## 3. Сборка мусора

### 3.1. Цели: throughput и latency

`[ ]` **Короткий ответ:** **throughput** — доля времени, которую приложение тратит на полезную работу, а не на GC (2 секунды GC из 100 → 98%). **Latency** — длительность пауз, которые видит пользователь. Чтобы сократить паузы, GC делает больше работы параллельно с приложением — это стоит CPU и памяти и снижает throughput. И наоборот: максимум throughput часто означает редкие, но длинные паузы.

Сборщик выбирают по измерениям: GC-логи (`-Xlog:gc*`), Java Flight Recorder, задержки p95/p99 приложения. Цель `-XX:MaxGCPauseMillis` — подсказка эвристике, а не гарантия.

<details>
<summary>Основы: поколения, достижимость, stop-the-world</summary>

- Объект жив, если достижим от **корней GC**: локальные переменные активных кадров, статические поля, активные потоки, JNI-ссылки. Циклические ссылки между недостижимыми объектами не мешают сборке (в отличие от подсчёта ссылок).
- **Гипотеза поколений:** большинство объектов умирает молодыми. Поэтому молодое поколение собирается часто и быстро, выжившие продвигаются в старое.
- **Stop-the-world** — пауза, когда потоки приложения остановлены. Есть у всех сборщиков, вопрос в длительности.
- **Allocation rate** — скорость выделения памяти. Высокая → частые сборки молодого поколения.

</details>

### 3.2. Сборщики

`[ ]` **Короткий ответ:** G1 — сборщик по умолчанию на многих серверных конфигурациях HotSpot. Он делит кучу на регионы и старается уложиться в целевую паузу. ZGC и Shenandoah спроектированы для низких пауз и могут требовать дополнительных ресурсов на конкурентную работу. Parallel ориентирован на высокую пропускную способность. Serial подходит для небольших куч и малого числа ядер.

| Сборщик | Флаг | Цель | Когда |
|---|---|---|---|
| Serial | `-XX:+UseSerialGC` | Минимальные накладные расходы | Маленькая куча, 1 CPU, короткоживущие утилиты |
| Parallel | `-XX:+UseParallelGC` | Пропускная способность | Пакетные задачи, где паузы не важны |
| G1 | `-XX:+UseG1GC` | Баланс, целевая пауза | Большинство серверных приложений |
| ZGC | `-XX:+UseZGC` | Низкие паузы за счёт преимущественно конкурентной работы | Большие кучи, жёсткие требования к задержкам |
| Shenandoah | `-XX:+UseShenandoahGC` | Низкие паузы | Есть не во всех сборках JDK |
| CMS | — | — | Устарел в JDK 9, удалён в JDK 14 |

<details>
<summary>Результат запуска: какой GC выбирает JVM</summary>

```text
$ java -Xlog:gc -version
[0.002s][info][gc] Using G1

$ java -XX:ActiveProcessorCount=1 -Xlog:gc -version
[0.002s][info][gc] Using Serial

$ java -XX:+UseZGC -XX:-ZGenerational -version
OpenJDK 64-Bit Server VM warning: Ignoring option ZGenerational; support was removed in 24.0
```

JVM выбирает Serial, если она не считает машину серверной (меньше 2 процессоров или мало памяти). В контейнере с лимитом в 1 ядро это случится незаметно — сборщик лучше задавать явно.

ZGC с JDK 21 умеет работать с поколениями, в JDK 24 режим без поколений удалён (JEP 490) — флаг `-XX:-ZGenerational` игнорируется ([OpenJDK: JDK 24](https://openjdk.org/projects/jdk/24/)). В JDK 25 Shenandoah с поколениями стал полноценной функцией (JEP 521), а компактные заголовки объектов (JEP 519) — продуктовой опцией `-XX:+UseCompactObjectHeaders`, по умолчанию выключенной ([OpenJDK: JDK 25](https://openjdk.org/projects/jdk/25/)).

</details>

**Уточнение интервьюера:** «Приложение тормозит раз в несколько минут на 2 секунды. Ваши действия?» — включить GC-логи, найти паузы и их причину: Full GC из-за переполнения старого поколения (утечка или мала куча), humongous-объекты в G1, промахи эвакуации. Сравнить allocation rate и размер кучи. Решение по данным: увеличить кучу, исправить утечку, уменьшить выделения, сменить сборщик.

### 3.3. Как G1 освобождает место

G1 делит кучу на регионы. Роли регионов меняются со временем, например область Eden для новых объектов или old для долгоживущих. Во время эвакуации живые объекты из выбранных регионов копируются, ссылки обновляются, а освобождённый регион можно использовать заново. Данные о ссылках извне помогают сканировать выбранные регионы без полного обхода кучи на каждой молодой сборке.

При высоком заполнении старого поколения G1 запускает цикл маркировки. Значительная часть маркировки идёт одновременно с приложением. Она оценивает, в каких старых регионах выгодно собрать мусор. Последующие **mixed collections** могут эвакуировать молодые и некоторые старые регионы вместе. Поэтому `Pause Young (Mixed)` в логе нормально видеть после маркировки. Если эвакуации недостаёт свободных регионов или куча заполняется слишком быстро, ищи соответствующие события в логах и причины давления. Full GC значительно дороже обычной эвакуации.

Крупный массив байтов размером от половины региона G1 размещает как **humongous object**. Такие объекты могут требовать непрерывной последовательности регионов. При регулярной конвертации больших файлов в один `byte[]` проверь размер объектов, частоту аллокаций и строки `Humongous regions` в логах. Потоковая обработка или меньшие чанки меняют профиль памяти, а выбор большего региона меняет правила размещения и требует отдельного измерения.

### 3.4. Разбор двух строк GC-лога

```text
GC(42) Pause Young (Normal) (G1 Evacuation Pause) 768M->211M(1024M) 19.5ms
GC(43) Pause Young (Normal) (G1 Evacuation Pause) 791M->215M(1024M) 18.1ms
```

В учебном примере `768M->211M` — занятость кучи до и после сборки, `1024M` — текущий размер кучи, `19.5ms` — длительность паузы. Много выделили и много освободили. Если такая картина повторяется при одинаковой нагрузке, проверь аллокации на запрос. По двум сборкам молодого поколения вывод об утечке ненадёжен: сравни уровень занятости после сопоставимых циклов, включая освобождение старых регионов.

Во втором сценарии после полных циклов остаётся 300, 410, 520 МиБ при прежней нагрузке. Проверь размер кешей, растущих очередей, batch-контекстов и данные по классам объектов. Растущая очередь может быть закономерной реакцией на то, что входная скорость выше обработки. Тогда увеличение heap отложит исчерпание памяти, а ограничение очереди и контроль входа изменят причину.

[Oracle, настройка G1 в JDK 17](https://docs.oracle.com/en/java/javase/17/gctuning/garbage-first-g1-garbage-collector1.html)

## 4. Ссылки: strong, soft, weak, phantom

`[ ]` **Короткий ответ:** обычная (strong) ссылка удерживает объект. **SoftReference** очищается при нехватке памяти — момент непредсказуем, поэтому как кеш он плох. **WeakReference** очищается при ближайшей сборке, если не осталось сильных ссылок — для метаданных к объектам (`WeakHashMap`). **PhantomReference** — уведомление о том, что объект собран, для освобождения внешних ресурсов (`Cleaner`).

<details>
<summary>Результат запуска</summary>

```java
Object strong = new Object();
WeakReference<Object> w = new WeakReference<>(strong);
System.gc();  System.out.println("with strong ref: " + (w.get() != null));
strong = null; System.gc();  System.out.println("after null+gc: " + (w.get() != null));

WeakHashMap<Object, String> m = new WeakHashMap<>();
Object k = new Object(); m.put(k, "v"); k = null; System.gc();
System.out.println("WeakHashMap size after gc: " + m.size());
```

```text
with strong ref: true
after null+gc: false
WeakHashMap size after gc: 0
```

`System.gc()` — лишь просьба, JVM может её проигнорировать; на демонстрации она сработала. Для прикладного кеша лучше библиотека с явными лимитами и TTL (Caffeine).

</details>

`finalize()` устарел и помечен к удалению: непредсказуем, замедляет GC, может «воскрешать» объекты. Вместо него — `try-with-resources` и `Cleaner`.

## 5. Диагностика и профилирование

### 5.1. Инструменты

| Задача | Инструмент |
|---|---|
| Список JVM-процессов | `jcmd` (без аргументов) или `jps` |
| Thread dump | `jcmd <pid> Thread.print`, `jstack <pid>` |
| Heap dump | `jcmd <pid> GC.heap_dump /tmp/heap.hprof`; автоматически: `-XX:+HeapDumpOnOutOfMemoryError` |
| Анализ heap dump | Eclipse MAT, VisualVM, IntelliJ |
| Гистограмма объектов | `jcmd <pid> GC.class_histogram` |
| GC-логи | `-Xlog:gc*:file=gc.log` |
| Нативная память | `-XX:NativeMemoryTracking=summary` + `jcmd <pid> VM.native_memory` |
| Запись профиля | `jcmd <pid> JFR.start duration=60s filename=rec.jfr`, анализ в JDK Mission Control |
| CPU и аллокации, flame graph | async-profiler |
| Флаги JVM | `jcmd <pid> VM.flags`, `java -XX:+PrintFlagsFinal` |

### 5.2. Профилирование

`[ ]` **Короткий ответ:** профилирование — измерение того, какие части кода потребляют ресурсы: время CPU, память, блокировки. Два подхода: **инструментирование** — в код встраиваются замеры входа и выхода из методов (точно, но дорого и искажает время); **сэмплирование** — профилировщик периодически снимает стеки потоков и строит статистику (дёшево, подходит для продакшена, но пропускает очень короткие методы).

Области:

- **CPU** — какие методы съедают процессор (например, 40% CPU в сериализации JSON).
- **Память** — кто выделяет много объектов, что удерживается в куче (heap dump: висящие сессии, неограниченный кеш).
- **GC** — частота и длительность пауз, сколько освобождается.
- **Потоки** — сколько их, в каком состоянии, где ждут (например, все 200 потоков Tomcat ждут внешний сервис).

Порядок работы: нагрузочный тест выявил проблему → метрики и GC-логи → профиль (JFR или async-profiler) → гипотеза → изменение → повторный замер.

**Safepoint bias:** многие профилировщики снимают стеки только в safepoint-ах, и горячий цикл без них «невидим». async-profiler и JFR этим страдают меньше.

### 5.3. От симптома к проверяемой гипотезе

| Симптом | Первый снимок | Что подтвердит гипотезу |
| --- | --- | --- |
| Высокий CPU, очередь запросов растёт | CPU-профиль, загрузка ядер, CPU throttling | Горячие стеки показывают, где выполняется работа, а число обработанных запросов растёт после изменения |
| p99 вырос, CPU низкий | Трейсы запросов, состояние пулов, несколько thread dumps | Потоки многократно ожидают одно соединение, монитор или внешний сервис |
| Частые young GC, занятость после сопоставимых циклов стабильна | GC-лог и JFR с событиями аллокации | Основные аллокации приходятся на конкретный путь, их объём на запрос снижается после изменения |
| Heap после сборок растёт | Сравнимые heap dump либо гистограммы и профиль | Путь до GC root показывает владельца удерживаемых объектов |
| Память процесса растёт при стабильном heap | Метрики cgroup, NMT diff, количество потоков | Рост согласуется с категорией Thread, Class, direct memory или внешней нативной библиотекой |

**Thread dump** — снимок стеков и состояния потоков. В Java `RUNNABLE` может наблюдаться и у потока в нативном I/O. `BLOCKED` означает ожидание входа в монитор `synchronized`. Поток, ожидающий `ReentrantLock`, часто находится в `WAITING` или `TIMED_WAITING` через park. Снимай несколько стеков с интервалом и сопоставляй с CPU и трассами, чтобы отличить переходное состояние от устойчивого узкого места.

**Heap dump** отвечает на вопрос «кто держит объект?». Shallow size учитывает размер объекта, retained size оценивает память, которая освобождается вместе с ним при отсутствии других путей. Маленькая коллекция в статическом поле может удерживать большое дерево. Начни с dominator tree, затем открой путь до корня GC, чтобы найти точку, где забыли убрать ссылку. Типичный пример — запись в `ThreadLocal` пережила запрос в долгоживущем worker-потоке пула. Удаление значения в `finally` завершает жизненный цикл. Перед heap dump учти его размер, возможность паузы и данные приложения, которые могут попасть в файл.

**JFR** полезен для совмещения событий во времени: CPU, ожидание мониторов, сетевые операции, GC и аллокации. Например, если GC-паузы составляют 10 мс, а медленные запросы ждут внешний HTTP по 1.8 с, смена GC вряд ли вернёт p99. В записи выдели интервал и проверь, какие события совпали с задержкой. Доступные команды и события зависят от JVM и настроек записи.

[Oracle, jcmd и команды JFR](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jcmd.html)

## Самопроверка

<details>
<summary>При новом деплое первый вызов падает с ExceptionInInitializerError, последующие — с NoClassDefFoundError. Как объяснить?</summary>

Класс загрузился, но статическая инициализация завершилась ошибкой. JVM запомнила неудачу для этого определения класса. Найди исходную причину первого исключения, например ошибку чтения конфигурации.

</details>

<details>
<summary>GC освободил 600 МБ, а RSS почти не уменьшился. Где искать?</summary>

Различи занятость объектов и объём страниц, предоставленных JVM. Проверь committed heap и нативные категории. Сопоставь RSS, cgroup, количество потоков и NMT на одном временном отрезке.

</details>

<details>
<summary>Паузы GC короткие, p99 вырос до секунды, HTTP-пул заполнен. Назови следующий измеримый шаг.</summary>

Сопоставлю медленные запросы с трассами зависимостей и временем ожидания соединения. Несколько thread dumps покажут, выполняют потоки работу или стоят в одной очереди. Дальше проверю гипотезу под одинаковой нагрузкой.

</details>

<details>
<summary>В JMH новая реализация работает почти бесплатно. Какие две причины проверишь?</summary>

Проверю, наблюдаем ли результат вычисления, и не может ли JIT вычислить его заранее на неизменном входе. Затем сравню профили аллокаций, разные размеры данных и результаты отдельных forks.

</details>
