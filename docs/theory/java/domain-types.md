## Когда long и String недостаточны

Два метода принимают `long`: один ожидает заказ, другой — идентификатор пользователя. Ошибка перестановки параметров скомпилируется, а проверка записей даст странный предметный результат. Небольшой тип `OrderId` или `UserId` переносит часть ошибок в компилятор. Задача такого типа — выражать границу, где идентификаторы действительно смешиваются. Для каждого вспомогательного числа делать обёртку необязательно.

Value object определяет ценность по своим полям. `Money` может состоять из числа минимальных единиц и валюты. `DateRange` хранит начало и исключающий конец. Два `Order` в разных состояниях могут иметь одинаковую идентичность, хотя содержимое отличается. В JPA identity и Java `equals` требуют отдельного решения, особенно при ID, полученном после сохранения. У value object создание всех полей и проверку можно провести вместе в конструкторе.

```java
record Money(long minorUnits, Currency currency) {
    Money {
        Objects.requireNonNull(currency, "currency");
    }

    Money plus(Money other) {
        if (!currency.equals(other.currency())) {
            throw new IllegalArgumentException("currency mismatch");
        }
        return new Money(Math.addExact(minorUnits, other.minorUnits()), currency);
    }
}
```

Этот фрагмент допускает отрицательные значения для сторно. Метод заказа может требовать положительную сумму по собственному правилу. Помести инвариант на тот уровень, где он действует. Глобальное правило «все Money положительны» усложнит поддержку вычитания и возвратов. Если цена должна быть положительной, используй проверку при создании или изменении цены. Преобразование курса требует отдельной операции с выбранными precision, округлением и временем.

### Record и защитная копия

Record задаёт поверхностную неизменяемость компонентов. Если компонент — `List<Line>`, принимаемая ссылка может вести к изменяемому списку. Для снимка состава сделай `lines = List.copyOf(lines)` в компактном конструкторе. Если `Line` сам изменяем, для настоящего снимка сделай его значение неизменяемым или скопируй его поля. Массив в record особенно требует внимания: accessor возвращает ссылку, а автоматически полученные `equals` и `hashCode` не сравнивают массивы поэлементно. Для массива, если он необходим, отдельно проектируй копирование на входе и выходе и содержательное равенство.

## Результат ожидаемого отказа выражается в API

Операция резерва может подтвердиться, обнаружить занятость или выявить недействительный период. Это варианты предметной команды. Внешний timeout — технический, иногда с неизвестным исходом. Если всё выражать boolean, вызывающий не знает, можно ли повторять и что показать. Если всё выражать исключениями одного типа, появляется похожая проблема. В Java 17 sealed interface позволяет ограничить набор ожидаемых результатов.

```java
sealed interface ReserveResult permits Reserved, Busy, OutsideHours {}
record Reserved(long reservationId) implements ReserveResult {}
record Busy(Instant tryAfter) implements ReserveResult {}
record OutsideHours(LocalDate date) implements ReserveResult {}
```

В обработчике Java 17 можно использовать pattern `instanceof`. В подходящей версии Java pattern switch помогает выразить исчерпывающий выбор по закрытой иерархии. На HTTP-границе варианты превращаются в согласованные статусы и JSON. В брокере формат события живёт независимо от Java-иерархии. Если добавляешь новую ветку, старый consumer должен понимать контракт неизвестного варианта или пройти отдельную миграцию.

**Ложный оптимизм `Optional`.** `Optional<Order>` выражает наличие или отсутствие одного значения. Для `not found`, `access denied`, `unavailable` и `stale version` одного empty недостаточно. Если mapper внутри `Optional.map` вернул null, результат станет пустым. Проверь, означает ли null предметное отсутствие или нарушенный контракт mapper. `orElse(expensive())` вычисляет аргумент сразу. Для ленивого fallback применяй `orElseGet`, когда он действительно нужен только при отсутствии. При нескольких вариантах ошибок выбери отдельный тип результата или корректно разобранное исключение.

## Интерфейс и поведение клиента

Представь интерфейс `OrderStore.load(id)`. Первая реализация читает локальную БД и возвращает актуальный заказ. Вторая использует отстающую проекцию. Они совпадают по сигнатуре, но могут обещать разные свойства. Сервис проверки права на возврат зависит от актуального состояния. В коде вырази, где нужен авторитетный read, а где разрешён снимок. Можно использовать разные входы или чёткий контракт структурированного результата со свежестью. Отдавать одну реализацию как полную замену другой допустимо, когда клиенты согласны с гарантиями.

`default`-метод в интерфейсе может помочь расширить интерфейс без немедленного изменения всех реализаций. Но добавление нового поведения требует осмыслить семантику. Например, реализация по умолчанию `reserveAll` вызывает `reserve` для каждого ресурса. Если часть операций прошла, а один ресурс занят, вызов уже создал частичный результат. Метод с именем и документацией «всё или ничего» не может дать такую реализацию без общей атомарной границы. Совместимость сигнатур и совместимость поведения проверяют отдельно.

### Домен, хранилище и транспорт

У транспорта есть требования к JSON, статусы HTTP и обратная совместимость. У хранения — ключи, nullability, ORM и DDL. Домен выражает допустимые переходы. Иногда для простого CRUD один тип удобно применить в нескольких местах. Когда по мере развития появились разные правила, адаптеры снимают связанность. Например, JPA хранит имя enum или отдельный код, API сообщает машиночитаемое значение, а доменная модель решает переход из PAID в SHIPPED. Переименование Java enum при привязке данных к `name` может затронуть БД и внешних читателей. Значения `ordinal` уязвимы для вставки нового enum в середину. Выбери стабильные сохранённые коды и мигрируй отдельно от переименования методов.

**Проверка состояния в одном месте.** Если `setStatus` доступен каждому коду, любой обработчик может обойти проверку перехода. Методы `markPaid` и `cancel` могут хранить правила вместе с данными. Но конкурентность на нескольких экземплярах приложения требует согласованной записи в авторитетном хранилище. Доменный метод контролирует одну модель в памяти. `@Version`, условный SQL или транзакция защищают совместное состояние.

<summary>Почему два OrderStore с одинаковыми методами не всегда взаимозаменяемы?</summary>

Разные гарантии свежести, атомарности и ошибки влияют на клиентов. Проверь, на какие свойства опирается вызывающий код, и отрази их в контракте.

</details>

<details>
<summary>External API вернул timeout, нужно ли подставить результат Busy?</summary>

Busy выражает установленный предметный отказ. Timeout оставляет неизвестный исход. Сохрани возможность сверки и повторяй запрос с тем же идентификатором по контракту.

</details>
