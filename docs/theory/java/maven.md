# Maven для Java-бэкенда: зависимости, тесты и итоговый артефакт

## Читай POM по двум осям

Одна ось — зависимости приложения, которые нужны компилятору, тестам или runtime. Другая — плагины, которые исполняют работу при сборке. Maven Compiler Plugin компилирует исходники, Surefire запускает обычные тесты, а Spring Boot Maven Plugin может перепаковать результат для запуска. Появление библиотеки в classpath не добавляет её как плагин. Зависимость сборочного плагина, в свою очередь, не появляется в обычном runtime classpath приложения.

### Фаза, goal и lifecycle

При `mvn verify` Maven выполняет предыдущие фазы default lifecycle до verify включительно. Например, раньше идут compile, test и package. Goals плагинов привязываются к фазам по типу упаковки и конфигурации. Вызов `mvn compiler:compile` обращается к конкретному goal и не означает автоматическое выполнение всего жизненного цикла до этой фазы. `clean` — отдельный lifecycle. `mvn clean verify` очищает выход сборки, затем полностью проходит проверки до verify.

| Команда | Что получает команда разработки |
| --- | --- |
| `test` | Сборку и выполнение положенных тестов фазы test |
| `package` | Артефакт проекта, например JAR |
| `verify` | Артефакт плюс проверки, привязанные к поздним фазам |
| `install` | Установку результата текущего проекта в локальный репозиторий |
| `deploy` | Публикацию Maven-артефакта в удалённый репозиторий по конфигурации |

Многомодульный проект собирается через reactor Maven. Если модуль сервиса зависит от библиотеки того же проекта, reactor учитывает зависимости при определении порядка. Повторный запуск только одного модуля вне reactor может взять старую установленную версию из локального репозитория. Для проверки модуля с зависимыми частями используй режим `-pl имя-модуля -am` из агрегатора. `-am` добавляет модули, необходимые выбранному. Проверка сборки с чистым локальным кешем в CI выявляет неописанные зависимости и неправильные ожидания о локальной установке артефактов.

**Parent и aggregator.** Parent передаёт наследуемые настройки, например версии и конфигурацию плагинов. Aggregator перечисляет модули для сборки вместе. Один POM может делать и то и другое, но child наследует через `parent`, а список `modules` лишь включает модули в сборку. Например, команда может использовать общий корпоративный parent и отдельный агрегатор конкретной системы.

[Apache Maven, жизненный цикл сборки](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle.html)

## Разрешение зависимостей

У зависимости есть координаты, обычно `groupId:artifactId:version`, при необходимости type и classifier. Транзитивно Maven подтягивает зависимости этих библиотек. Если к одному артефакту ведут пути с разными версиями, при обычном разрешении действует ближайшее объявление, а для равной глубины важен порядок объявлений. Поэтому добавление прямой зависимости или изменение дерева иногда выбирает более старый runtime, чем предполагал один из компонентов.

`dependencyManagement` задаёт сведения о версиях и параметрах, когда зависимость реально присутствует в графе. Он не добавляет все перечисленные зависимости в приложение. BOM — POM с согласованным набором версий, который можно импортировать в `dependencyManagement`. Например, Spring Boot BOM помогает держать версии всего стека в совместимой комбинации. Использовать BOM и использовать родительский POM — разные механизмы: наследование может добавить и настройку плагинов, а импорт BOM относится к зависимостям.

`pluginManagement` похож по идее для build plugins. Версия и настройки применяются при использовании соответствующего плагина. Для плагина с goal, который нужно дополнительно запускать в сборке, проверь, привязано ли нужное исполнение к фазе через конфигурацию. Тип упаковки также может задавать уже существующие привязки.

### Scope на примере серверного приложения

| Scope | Где ожидать зависимость |
| --- | --- |
| `compile` | В обычной компиляции и runtime, по правилам Maven доступна транзитивно |
| `provided` | В compile и test проекта, runtime ожидается от окружения |
| `runtime` | В исполнении и тестах, для компиляции основной части не требуется |
| `test` | Для компиляции и выполнения тестов |

JDBC-драйвер может быть runtime-зависимостью, когда приложение компилируется против стандартных интерфейсов, а реализацию обнаруживает при запуске. При тестах в IDE test scope может скрыть отсутствие нужной библиотеки в рабочей упаковке. `optional` управляет тем, будет ли downstream-проект автоматически получать зависимость транзитивно через данную библиотеку. `exclusions` исключают транзитивную зависимость на определённом ребре. Если к ней ведёт другой путь, её может всё равно выбрать Maven. После правки проверь эффективное дерево.

**Практический разбор.** Собранный сервис падает с `NoSuchMethodError`. Эта ошибка на этапе связывания может означать, что runtime нашёл класс известного имени, но загрузил версию без требуемого API. Сначала найди вызов и указанную сигнатуру. Сравни дерево зависимостей и состав поставляемого JAR или образа. Затем выясни, откуда JVM загрузила этот класс. Смена импорта в исходнике проблему не решит, если JVM уже получила несовместимую библиотеку. Когда совпали две библиотеки с одинаковыми классами под разными координатами, одного разрешения версий Maven тоже недостаточно.

```powershell
.\mvnw.cmd dependency:tree
.\mvnw.cmd help:effective-pom
.\mvnw.cmd -version
```

Первая команда отвечает, какие зависимости выбраны и через что они пришли, вторая показывает объединённые настройки родителей и профилей, третья сообщает реальную Java, на которой запущен Maven. При конфигурации toolchains Maven может использовать для компиляции другой JDK. Отдельно сверяй компилятор и runtime, особенно в многостадийном Dockerfile.

[Apache Maven, механизм зависимостей](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html)

## Java версии 17 на компиляторе версии 21

При `--release 17` компилятор проверяет синтаксис, генерирует байт-код для Java 17 и ограничивает доступный стандартный API соответствующим выпуском. Пара `source`/ `target` сама по себе не ограничивает весь API, который видит более новая JDK. В итоге код может содержать вызов метода, появившегося позже, и пройти сборку с подходящей версией class-файла, но сломаться на Java 17. Используй `maven.compiler.release` или явную настройку Compiler Plugin, если библиотека выпускается для определённой версии.

Совместимость собственных классов также не гарантирует совместимость всех зависимостей. Одна из библиотек в итоговой упаковке может быть собрана под более новую Java. Тогда при загрузке её класса возникает `UnsupportedClassVersionError`. Запусти smoke test именно на минимальной поддерживаемой JVM. Если используются preview-возможности, компиляция и запуск требуют настроек данной версии, а правила совместимости строже.

[Apache Maven, выбор целевой версии Java](https://maven.apache.org/guides/mini/guide-java-target.html)

## Почему тест иногда не запустился

Surefire обычно исполняет unit-тесты на фазе test. Failsafe предназначен для интеграционных тестов, его goals обычно привязывают к `integration-test` и `verify`. Плагин записывает результаты, а проверка статуса на verify даёт возможность сначала остановить поднятые зависимости в `post-integration-test`. Вызов одной фазы `integration-test` может не дойти до уборки. Перед тем как считать сборку зелёной, посмотри число найденных и реально выполненных тестов. Код без совпадения с правилами включения по имени может вообще не запуститься.

Параметры пропуска тоже различаются. `skipTests` обычно пропускает запуск, оставляя компиляцию тестов. `maven.test.skip` в стандартных плагинах также может пропустить компиляцию тестов. Профиль CI выбирай по цели. Быстрая локальная сборка без тестов годится для эксперимента, но результирующий релиз должен проходить нужные стадии.

**Что версия артефакта означает в CI.** Snapshot может изменяться по тем же координатам. Воспроизводимая релизная сборка фиксирует версии зависимостей и плагинов, версию JDK и команды сборки. Maven Wrapper обеспечивает выбор заданного Maven, но JDK нужно задать отдельно. При обновлении библиотеки проверяй не только компиляцию, но и сетевые контракты, сериализацию и запуск в настоящем контейнере.

[Apache Maven Failsafe, жизненный цикл интеграционных тестов](https://maven.apache.org/surefire/maven-failsafe-plugin/)

## Самопроверка

<details>
<summary>Добавили зависимость только в dependencyManagement. Почему импорт класса не компилируется?</summary>

Секция управляет версией и настройками, если зависимость вошла в дерево. Нужно объявить её в dependencies или понять, почему ожидаемый транзитивный путь отсутствует.

</details>

<details>
<summary>На CI test успешен, integration-кейсы никто не увидел. Что смотреть?</summary>

Проверь фазу запуска, конфигурацию плагина, имена тестов и число выполненных тестов. Для Failsafe в обычной конфигурации запускают verify, чтобы дойти и до проверки, и до очистки.

</details>

<details>
<summary>Сервис собрали на JDK 21 с target 17. Почему на Java 17 падает вызов метода JDK?</summary>

Один target управляет версией class-файла. Компилятор всё ещё мог видеть новые методы. Выбирай release и проверяй запуск на минимальной версии.

</details>
