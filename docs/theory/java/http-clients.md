## Из чего складывается один сетевой вызов

Клиент получает работу, ждёт свободный ресурс, при необходимости разрешает имя, открывает TCP, договаривается о TLS, отправляет запрос, получает заголовки и читает тело. Метрика «вызов 800 мс» может включать все эти фазы. Изменение connect timeout поможет только там, где задержка относится к подключению и правила клиента включают нужный этап. Для долгого ожидания ответа или чтения нужны соответствующие настройки и общий дедлайн команды.

| Фаза | Пример симптома |
| --- | --- |
| Ожидание места | Свободных соединений/стримов мало, вход большой |
| Соединение или TLS | Новый pod не может достичь upstream или проверить цепочку |
| Ожидание заголовков | Приложение upstream работает долго до первого ответа |
| Чтение тела | Большой результат, медленная отдача, непредвиденный поток |
| Разбор ответа | JSON или его декомпрессия занимают CPU и память Java |

Не создавай новый клиент на каждый вызов без особой причины. Долгоживущий клиент может переиспользовать соединения и ресурсы. Для нескольких направлений с разными доступами, сертификатами и бюджетами удобно задать отдельную конфигурацию. Параллельность контролируй доступной вместимостью зависимости и клиентских очередей. Если один пул общий для массового экспорта и пользовательских проверок, экспорт может занять его постепенно без высокой загрузки CPU.

## Стандартный HttpClient на Java 17

```java
HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofMillis(250))
    .build();

HttpRequest request = HttpRequest.newBuilder(URI.create("https://api.example.com/health"))
    .timeout(Duration.ofMillis(700))
    .GET()
    .build();

HttpResponse<Void> response = client.send(request, HttpResponse.BodyHandlers.discarding());
```

Фрагмент показывает ограничение подключения и тайм-аут запроса в API. В реальном сервисе `client` хранится и используется многократно. `send` блокирует вызывающего до результата по правилам body handler. `sendAsync` даёт future, завершение и отмена которого нужно трактовать по контракту. `CompletableFuture.orTimeout` ограничивает ожидание результата в Java и не даёт доказательства, что внешний сервер перестал работать. HTTP 404 или 503 обычно приходит как обычный response с кодом, а ошибка транспорта — отдельное исключение. Различай отсутствие предметной записи и неполученный ответ.

**Поток тела.** `BodyHandlers.ofInputStream()` выдаёт поток для чтения. После появления response вызов может ещё не скачать тело целиком. Ответственность вызывающего — читать и закрывать поток. Для общего бюджета учти чтение и разбор, а также отмену на этапе обработки данных. Если тело крупное, `BodyHandlers.ofString()` накапливает его в памяти. При интеграции с непредсказуемым ответом поставь лимиты на полезный размер и число данных после распаковки, а в ошибках не тащи целый payload в журналы.

[Java SE 17, HttpClient](https://docs.oracle.com/en/java/javase/17/docs/api/java.net.http/java/net/http/HttpClient.html) · [Java SE 17, HttpRequest.Builder](https://docs.oracle.com/en/java/javase/17/docs/api/java.net.http/java/net/http/HttpRequest.Builder.html)

## HTTP/1.1, HTTP/2 и перегрузка общего соединения

В HTTP/1.1 keep-alive позволяет переиспользовать TCP/TLS соединение. Многие клиенты для параллельной работы используют несколько соединений. HTTP/2 поддерживает несколько потоков поверх одного соединения, благодаря чему быстрый ответ не обязан ждать завершения предыдущего ответа на уровне HTTP. У потока и соединения есть flow control и согласуемые пределы. TCP-потери и общий отказ соединения способны затронуть все его стримы. «У нас HTTP/2» не делает параллелизм бесконечным.

Если сервер отправил GOAWAY, клиент учитывает, какие стримы сервер мог обработать. Детали retry зависят от протокола и библиотеки. На прикладном уровне особенно важно сохранять ID команды при неизвестном исходе. Повторять любой POST с новым ID, потому что протокол сообщил разрыв, означает создать потенциально вторую операцию. Для идемпотентных чтений также учитывай общий бюджет и перегрузку.

[RFC 9113, HTTP/2, streams, flow control и GOAWAY](https://www.rfc-editor.org/rfc/rfc9113.html)

## Прокси измеряет свой участок

Приложение видит, что Nginx уже вернул 504, а worker продолжал SQL ещё секунду. У прокси есть независимые ожидания upstream. Например, `proxy_read_timeout` в Nginx ограничивает время между последовательными чтениями из backend, а не всю длительность ответа. Долгий поток с регулярными порциями может идти дольше. Если клиент ждёт только 2 секунды, а каждый из двух промежуточных уровней не знает этот дедлайн, ненужная работа накапливается после отказов.

**Buffering.** При буферизации proxy может читать быстрее клиента и хранить ответ в буферах или временных файлах по настройке. Это позволяет backend раньше освободить активный ресурс для обычного ответа, но меняет расход диска/памяти и взаимодействие со streaming. Для потоковых событий настройка, подходящая для большого обычного JSON, может отложить доставку маленьких порций клиенту. Проверяй время до первого элемента и ссылку на конфигурацию выбранного маршрута.

**502 и 504.** Эти ответы могут сформироваться на прокси, при этом приложение не увидит собственного HTTP 5xx. Проверь gateway лог и upstream status, стадию ожидания, количество живых endpoints. 502 часто связан с неудачным получением пригодного ответа upstream, 504 с тайм-аутом ожидания в выбранной цепочке. По одному коду не выводи первопричину. Сопоставь trace ID, версию клиента, TCP/TLS и серверные интервалы.

[Nginx, proxy-read-timeout и buffering](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

## Самопроверка

<details>
<summary>Connect timeout 100 мс, но запрос ждёт четыре секунды. Может ли это соответствовать настройке?</summary>

Да. Соединение могло быть установлено быстро или переиспользовано, а время ушло на ожидание ответа, разбор тела или получение ресурса. Проверь тайм-ауты фаз и общий дедлайн.

</details>

<details>
<summary>Сервис начал возвращать response по заголовкам, но память и соединения не освобождаются. Что посмотреть?</summary>

Проверь, кто дочитывает или закрывает поток body и сколько хранится в очередях. Для ответа с большим телом отдельно измерь длительность записи и лимиты клиента.

</details>

<details>
<summary>Nginx вернул 504, после повтора операция выполнилась дважды. Какой контракт отсутствовал?</summary>

Прежняя команда могла продолжить работу после тайм-аута прокси. Нужен устойчивый ключ операции, который фиксируется с результатом и сохраняется на повторе.

</details>
