## Выбор типа даты и времени

Первый вопрос на собеседовании звучит просто: какое именно значение нужно сохранить? Встреча «по будням в 9:00 по Москве» и запись «платёж подтверждён в 06:00 UTC» описывают разные вещи.

| Тип | Что представляет | Где подходит |
| --- | --- | --- |
| `Instant` | Точку на шкале времени | Метка события, время выдачи токена, граница хранения |
| `LocalDate` | Календарные год, месяц и день | Дата рождения, отчётный день, дата поставки без времени |
| `LocalDateTime` | Календарную дату и показание часов | Время начала смены, пока зона известна из другого поля |
| `OffsetDateTime` | Дату и время с известным смещением от UTC | Внешний API прислал `2025-03-30T10:00:00+02:00` |
| `ZonedDateTime` | Дату и время с правилами выбранной зоны | Локальное расписание с переходами часов |
| `Duration` | Длительность в секундах и наносекундах | Тайм-аут и фактически прошедший интервал |
| `Period` | Календарный интервал в годах, месяцах и днях | Следующий месяц обслуживания |

Смещение `+02:00` описывает разницу часов для данного момента. `Europe/Berlin` содержит правила, по которым разница меняется с датой. Для повторяющегося события сохрани местное правило и идентификатор зоны. Для случившегося события сохрани фактический момент и, если нужен аудит исходного обещания, дополнительные поля представления.

### Несуществующий и неоднозначный час

В Берлине 30 марта 2025 переход с зимнего времени на летнее пропускает час от 02:00 до 03:00. Если пользователь выбрал 02:30, у местного значения нет соответствующего момента. Метод `atZone` по своему контракту сдвинет время вперёд на длину разрыва. Осенью часы переводятся назад, поэтому местное 02:30 может встретиться дважды. По умолчанию `atZone` выбирает раннее смещение при двусмысленности. Если расчёт относится к записи на приём или аукциону, выбери политику явно. Например, для пустого результата `zone.getRules().getValidOffsets(local)` попроси другое время, а при двух смещениях предложи выбрать первое или второе.

```java
ZoneId zone = ZoneId.of("Europe/Berlin");
ZonedDateTime start = LocalDate.of(2025, 3, 30).atStartOfDay(zone);
ZonedDateTime nextDay = start.plusDays(1);
ZonedDateTime after24h = start.plus(Duration.ofHours(24));
```

`nextDay` указывает на следующее местное начало дня, через 23 часа. `after24h` указывает на 01:00 следующего дня. Аналогично запрос «события за местный день» лучше строить по двум преобразованным границам `[start, nextDay)`. Так интервал включает весь нужный день и без пересечения стыкуется со следующим. Условия вида `time <= 23:59:59` теряют значения с дробной частью секунды. Если передать date/time с неверной зоной, индекс и идеальный SQL-план ускорят вычисление неверного ответа.

### UTC в БД и время в API

Значение Java `Instant` означает один момент. В PostgreSQL `timestamp with time zone` тоже хранит момент, показывая его в зоне сессии. Исходное имя зоны и смещение при записи не сохраняются. `timestamp without time zone` хранит календарные поля. Используй отдельную колонку `zone_id`, когда она часть предметной области, например исходное местное расписание. При выборе маппинга проверь поддерживаемый JDBC-тип и что конкретно делают драйвер и ORM при чтении.

API с `2025-02-03T12:30:00` требует договорённости о зоне, иначе два клиента могут интерпретировать одно поле по-разному. Для единого момента используй ISO 8601 с `Z` или смещением. Заранее договорись о точности: Java `Instant` умеет наносекунды, PostgreSQL timestamp поддерживает микросекунды. Если сравнивать значения из памяти и после round-trip, заключительные цифры могут измениться. Равенство в тесте стоит проверять после оговорённого преобразования или с оговорённым допуском.

### Часы в тестах и измерение длительности

Условия «токен истёк» и «время операции превысило бюджет» похожи, но требуют разных часов. Для календарного момента полезно принимать `Clock`, а в тесте использовать `Clock.fixed`. Измерение интервала внутри процесса использует `System.nanoTime()` и разность двух показаний. Начало отсчёта произвольно. Его не сохраняют в БД и не передают в другой процесс. Системные календарные часы могут корректироваться, поэтому разность двух `currentTimeMillis()` ненадёжна для монотонного бюджета.

```java
static boolean isExpired(Instant deadline, Clock clock) {
    return !clock.instant().isBefore(deadline);
}
```

Проверь три точки: наносекунда до границы, совпадение и наносекунда после. Если токен считается действительным до момента `expiresAt`, в самой точке истечения он уже недействителен. Тест сравнивает правило, а не скорость машины. При повторе сетевых попыток сначала вычисли общий бюджет, затем перед каждой попыткой получи остаток. Пара тайм-аутов по 200 мс плюс пауза 100 мс не помещаются в 350 мс, даже если рабочая машина обычно быстрая.

[Java SE 17, java.time](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/package-summary.html) · [Java SE 17, System.nanoTime](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/System.html#nanoTime()) · [PostgreSQL 17, типы даты и времени](https://www.postgresql.org/docs/17/datatype-datetime.html)

## Текст, байты и символы

В JSON пришло имя пользователя. По дороге оно существовало как байты HTTP-сообщения, как последовательность Unicode и как `String`. В каждой форме своё понятие длины. Для `"A🚀"` метод `length()` даёт 3 единицы UTF-16, `codePointCount(0, length())` даёт 2 кодовые точки, а кодирование в UTF-8 занимает 5 байт. В кластере эмодзи с соединителями даже несколько кодовых точек могут отображаться как один видимый знак. При ограничении длины API спроси, что именно важно: размер сетевого сообщения, лимит БД, количество кодовых точек или поведение интерфейса.

```java
String name = "A\uD83D\uDE80";
int units = name.length();                         // 3
int points = name.codePointCount(0, name.length());  // 2
int bytes = name.getBytes(StandardCharsets.UTF_8).length; // 5
```

`substring(0, 2)` здесь отделяет половину суррогатной пары от второй половины. Для ограничения по кодовым точкам сначала вычисли индекс через `offsetByCodePoints`. Для пользовательских знаков уточни требования к сегментации и протестируй комбинированные буквы и эмодзи. Простое разбиение через `charAt` подходит, когда условие задачи ограничивает алфавит ASCII или явно просит оперировать единицами UTF-16.

### Кодировка входит в контракт

`String` не хранит пометку о кодировке исходного файла. Кодировку выбирают на переходе между строкой и байтами. Если одна сторона пишет UTF-8, другая должна читать UTF-8. Укажи `StandardCharsets.UTF_8` на границе с сетью или файлом, если такой формат задан. Это важно и для сравнения хешей, поскольку хеш считается по байтам. API `getBytes()` использует кодировку по умолчанию. В Java 17 она могла зависеть от окружения, а JDK 18 сделал UTF-8 стандартом по умолчанию для большинства соответствующих API. Явный аргумент фиксирует договорённость и после миграции JDK.

Что делать с битым входом, решает контракт. Например, для строгого импорта у декодера можно настроить `CodingErrorAction.REPORT`. Подстановка символа замены удобна для просмотра, но может необратимо изменить идентификатор или содержание подписи. Если одни байты участвуют в подписи, а другой компонент пересобирает JSON, даже пробелы и перестановка полей могут поменять хеш. Принимай решение о канонизации и подписи вместе.

### Нормализация, регистр и пользовательские ключи

Визуально одинаковая «é» может быть одной точкой U+00E9 или парой «e» и комбинированного акцента. `String.equals` сравнивает точное содержимое, а не визуальный результат. NFC-нормализация полезна, когда контракт считает эти формы эквивалентными. Задай правило при записи ключа и поиске, проверь коллизии старых данных, прежде чем менять нормализацию в production. Для кодов протокола и имён системных ключей применяй `Locale.ROOT` при переводе регистра. Для пользовательской сортировки учитывай язык и правила сравнения, поскольку алфавитный порядок по языку отличается от порядка `String.compareTo`.

Для проверки регулярного выражения `matches` требует совпадения всей строки, а `find` ищет подходящую подстроку. Для многократной проверки компилируй `Pattern` один раз, а для каждого ввода создавай свой `Matcher`: он хранит состояние текущего поиска. Если текст шаблона должен трактоваться буквально, преобразуй его через `Pattern.quote`. Для структурированного формата вроде вложенного JSON бери соответствующий парсер с лимитами размера и глубины.

## Файлы, потоки ввода и ресурсы

Для маленького доверенного конфигурационного файла удобен `Files.readString`. Для большого файла обработка частями сохраняет ограниченное потребление памяти. `Files.lines(path, UTF_8)` открывает ресурс и лениво читает строки. При `findFirst` или исключении дальнейшее чтение может остановиться, поэтому stream должен закрыться через `try-with-resources`. То же правило касается `Files.walk` и `Files.list`.

```java
static long countErrorLines(Path path) throws IOException {
    try (var lines = Files.lines(path, StandardCharsets.UTF_8)) {
        return lines.filter(line -> line.startsWith("ERROR ")).count();
    }
}
```

Такая обработка ограничивает память примерно буферами и самой длинной строкой, если не накапливает выбранные данные. Когда вход может содержать одну гигантскую строку, лимит размера сообщения нужен ещё до создания `String`. Похожая проблема появляется при сборе всего ответа через `toList` или `readAllBytes`. Чтение порциями помогает только пока последующие шаги также сохраняют ограниченный объём состояния.

**Поток байтов и поток символов.** `InputStream` даёт байты, `Reader` — символы. `read(buffer)` возвращает число реально прочитанных элементов или −1 в конце. Один вызов не обязан заполнить буфер. Для заголовка фиксированной длины используй чтение до набора нужного размера, проверив неожиданный конец. При парсинге сети или файлов граница чтения из ОС не обязана совпадать с границами записей формата.

### Запись с атомарной заменой

Если сразу открыть конечный файл на перезапись, читатель может увидеть пустое или частичное содержимое. Для атомарной публикации сначала создай временный файл в том же каталоге, полностью запиши и закрой его, затем запроси `ATOMIC_MOVE` там, где файловая система поддерживает операцию. Поведение замены уже существующего имени при `ATOMIC_MOVE` зависит от реализации. Если поддержка требуется по контракту, отработай ошибку платформы и проверь формат размещения. Fallback на неатомарный move меняет гарантию для читателей.

Видимость целого файла и сохранность после внезапного сбоя питания — разные требования. Для сохранности нужны гарантии синхронизации данных и метаданных, зависящие от ОС и файловой системы. В документации Java `FileChannel.force` описывает принудительную запись обновлений файла на устройство для локального хранения. Сетевые и виртуальные накопители имеют отдельные условия. На собеседовании уточни, восстанавливается ли запись после падения JVM, процесса ОС или потери узла.

## Деньги и округление

`BigDecimal` хранит целое значение и масштаб. У `1.20` unscaled value равен 120, scale равен 2. Передавай сумму вместе с валютой. В разных валютах число минимальных единиц может отличаться. Отдельно зафиксируй правила для расчёта налога, курса, скидки и финального списания. Даже если в БД все суммы в целых минимальных единицах, промежуточные вычисления часто требуют большей точности.

**Когда округлять.** Три позиции по 0,05 со ставкой 10% дают по 0,005 налога. При округлении half-up до цента на каждой позиции получится 0,03. Округление общего результата 0,015 даст 0,02. Обе схемы вычислимы, правильная определяется контрактом расчёта. Если сумма строк обязана равняться итоговой, нужен явный алгоритм распределения разницы. Оставь тест на случай половины и на отрицательные сторнирующие значения. Например, `HALF_UP` округляет половины от нуля, а `HALF_EVEN` выбирает ближайшую чётную цифру.

`MathContext` ограничивает число значащих цифр результата. `setScale(2, mode)` задаёт число десятичных знаков после запятой при положительном масштабе. Если операцию `setScale(2, UNNECESSARY)` применить на входе, она явно отклонит значение, которое нельзя сохранить без потери. `longValueExact()` даёт исключение при дробной части или выходе за диапазон. У целых минимальных единиц тоже возможны переполнения. Применяй `Math.addExact`/ `multiplyExact`, если диапазон входов не доказан заранее.

**Равенство и сортировка.** `new BigDecimal("2.0").equals(new BigDecimal("2.00"))` даёт false, `compareTo` возвращает 0. `HashSet` может оставить оба, `TreeSet` с естественным порядком увидит один ключ. Если денежное значение должно быть стабильным ключом, нормализуй масштаб по валюте и включи валюту в ключ.

[Java SE 17, BigDecimal](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigDecimal.html)

## Самопроверка

<details>
<summary>Почему суточный отчёт за воскресенье в Берлине может выбрать события понедельника?</summary>

Если конец вычислили как начало плюс 24 часа, день перевода часов имеет другую длительность. Вычисли следующее местное начало дня через календарную дату и зону, затем преобразуй обе границы в Instant. Запрос фильтрует полуоткрытый интервал.

</details>

<details>
<summary>Время HTTP-запроса по замеру оказалось отрицательным. Где искать?</summary>

Проверь источник часов. При коррекции календарного системного времени разность двух значений wall clock может стать отрицательной. Для длительности используй разность показаний nanoTime внутри процесса. Историческое время события можно записывать отдельно.

</details>

<details>
<summary>У строки length() равен 3, а на экране два видимых знака. Может ли это быть корректно?</summary>

Да. String.length считает единицы UTF-16. Символ за пределами BMP занимает две единицы, а видимые кластеры могут объединять несколько кодовых точек. Уточни единицу длины у потребителя данных.

</details>

<details>
<summary>Чтение файла через Files.lines уже нашло первую строку. Зачем закрывать поток?</summary>

Поиск остановил обход, но ресурс файла всё ещё принадлежит потоку. Try-with-resources закроет его на всех выходах. В серверном процессе это защищает от постепенного исчерпания файловых дескрипторов.

</details>
