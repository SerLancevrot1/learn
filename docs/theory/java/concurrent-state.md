## Сначала назови инвариант

Потокобезопасность означает, что допустимые конкурентные вызовы сохраняют контракт типа. Для простого счётчика контракт может быть «каждый успешный вызов учитывается ровно один раз». Для ограничителя — «занятых мест не больше вместимости». Для загрузки настроек — «все поля одного чтения относятся к одной версии». Эти правила подсказывают границу атомарной операции.

Представь склад с двумя полями `available` и `reserved`. Обычный переход меняет первое на −1 и второе на +1. Даже если оба поля атомарные, читатель между двумя обновлениями увидит, что один товар исчез. Если допускается приблизительная телеметрия, это может быть нормой. Если читатель сверяет остаток, пара должна читаться и писаться как одно состояние. Возьми один lock на целую операцию или помести оба значения в неизменяемый объект и меняй одну ссылку.

### Неизменяемый снимок и публикация

```java
record Limits(int perUser, int global) {
    Limits {
        if (perUser < 1 || global < perUser) {
            throw new IllegalArgumentException("inconsistent limits");
        }
    }
}

final class LimitsHolder {
    private volatile Limits limits = new Limits(10, 100);

    Limits current() {
        return limits;
    }

    void replace(Limits fresh) {
        limits = Objects.requireNonNull(fresh);
    }
}
```

`volatile` здесь публикует полностью собранный объект. Поток сначала читает ссылку, затем использует оба значения из этой версии. Если вызовет `current()` дважды, между вызовами может пройти обновление. Поэтому на один логический запрос сохрани ссылку в локальной переменной. Если объект содержит изменяемые списки или массивы, защиту их состояния определяй отдельно.

Метод `replace` подходит для политики «последняя запись побеждает». Если два администратора редактируют поля поверх общей версии, сравни ожидаемую версию атомарно. `AtomicReference.compareAndSet(old, next)` обновит ссылку только при совпадении ожидаемого экземпляра. Для бизнес-правки, которая увеличивает `perUser` на 1, при неудачном CAS перечитай состояние и повтори проверку `perUser <= global`. Функция в `updateAndGet` может вызываться несколько раз под конкуренцией. Держи её без эффектов, которые нельзя повторить, например отправки уведомления. После успешной смены состояния решай, как обрабатывать сбой внешней отправки.

[Java SE 17, AtomicReference](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/atomic/AtomicReference.html)

### Когда помогает happens-before

Happens-before — отношение между действиями. Если A happens-before B, для видимости и допустимых наблюдений JVM соблюдает соответствующий порядок. Оно транзитивно, поэтому можно построить цепочку через синхронизацию и порядок инструкций в потоке. Например, родитель настраивает объект, вызывает `start`, дочерний поток обращается к объекту. Действия перед `start` упорядочены до действий нового потока. Когда родитель успешно дождался завершения через `join`, он может читать записанный дочерним результат.

Подобные границы у библиотек документируются. Действия до помещения задачи в `ExecutorService` предшествуют её исполнению. Действия задачи предшествуют успешному получению её результата через `Future.get` по контракту. Действия до передачи объекта через `BlockingQueue` предшествуют дальнейшему доступу к этому объекту после извлечения. Эти гарантии позволяют передать владение. Если producer после передачи продолжает менять поля обычными присваиваниями одновременно с consumer, эти новые изменения требуют дополнительной координации.

**Финальные поля.** При корректном построении объекта модель памяти даёт особые гарантии видимости его `final`-полей. Для собеседования удобно разделять две вещи. Состояние неизменяемого значения можно сделать стабильным после конструктора. Канал передачи ссылки и любые последующие изменения всё равно должны подчиняться контракту конкурентного доступа. Публикация через `volatile`, монитор, потокобезопасную коллекцию или инициализацию класса даёт явную границу. Если конструктор регистрирует `this` в listener или запускает работу, другой поток может получить ссылку до завершения инициализации. Вынеси регистрацию в шаг после создания.

## Счётчик, лимит и атомарная операция

| Требование | Подход | Где граница |
| --- | --- | --- |
| Метрика «сколько стартовало запросов» с частыми увеличениями | `LongAdder` | Сумма во время конкурентной записи приблизительна |
| Получать точные последовательные номера в одном JVM-процессе | `AtomicLong.incrementAndGet` | Значение теряется при перезапуске, следи за диапазоном |
| Разрешить не более N одновременных операций | `Semaphore` или эквивалент с проверкой состояния | Разрешение возвращается при завершении операции |
| Изменять согласованную группу полей | Lock или CAS снимка | Все чтения и записи участвуют в одной схеме |
| Учитывать состояние по ключам | `ConcurrentHashMap.compute`/ `merge` | Операция относится к ключу, бизнес-группы требуют общей координации |

**Сценарий с разрешением.** У сервиса десять слотов для обращения к медленной зависимости. Два потока видят, что свободен один слот. Если оба проверили `inFlight < 10` и затем сделали атомарное увеличение, оба войдут. Нужно сделать проверку и захват как одну операцию. `tryAcquire(timeout, unit)` ограничивает ожидание. После успешного захвата вызови `release` в `finally`. После неуспеха освобождать нечего. `Semaphore` не привязан к владельцу потока, поэтому при неправильном двойном release количество разрешений вырастет. В асинхронной ветке чётко определи, кто освобождает слот при отмене, исключении и нормальном завершении.

**Сценарий с лимитом по пользователю и глобально.** Если удерживать пользовательский слот при ожидании глобального, у запроса есть два этапа ожидания. Везде используй один порядок захвата и один бюджет. При неудаче второго захвата верни первый слот. Если у части кода обратный порядок, появится возможность взаимной блокировки. Когда все ограничения должны применяться мгновенно и вместе, легче защитить проверку обоих счётчиков короткой критической секцией.

## Lock, очередь и условие ожидания

Под монитором можно проверить условие, например наличие данных. Пока очередь пуста, `wait` отпускает монитор и позволяет producer добавить элемент. После пробуждения поток снова захватывает монитор и проверяет условие. Используй `while`, потому что возможны ложные пробуждения и потому что другой consumer успел забрать данные до получения монитора. `notifyAll` пробуждает кандидатов, а реальную работу определяет условие. У `Condition` доступны отдельные наборы ожидающих, например `notEmpty` и `notFull`. Для обычной producer-consumer схемы готовая `BlockingQueue` уже реализует эти правила.

Capture-параметры важны и в двухфазной последовательности. Возьми значения под lock, затем отпусти его и построй результат. Если дорогое вычисление зависело от состояния и позже понадобится записать результат, нужно проверить, что версия входа не изменилась. Так можно рассчитывать новый тариф вне блокировки и применять его только к той версии правил, для которой выполнен расчёт.

### Оптимистическое чтение StampedLock

`tryOptimisticRead` выдаёт stamp. Скопируй интересующие поля в локальные переменные и вызови `validate(stamp)`. Если параллельный writer успел получить write lock, повтори чтение под read lock. До validate данные могут быть несогласованными. Избегай действий, которым нужен валидный снимок, например доступа к вычисленному индексу или вызова внешнего кода. Пример из документации хорошо применим к паре простых координат. На изменяемом дереве безопасный оптимистический обход спроектировать сложнее. `StampedLock` также не реентерабелен. Вызов собственного метода с повторным захватом может зависнуть.

У `ReentrantReadWriteLock` read lock могут одновременно удерживать несколько читателей. Оптимизация окупается при измеримой доле длительных параллельных чтений. При очень коротких чтениях bookkeeping синхронизации может стоить больше последовательного монитора. При обновлении под обычным read lock захват write lock без отпускания read lock чреват ожиданием. Если отпустил read lock для перехода к write, перечитай условие после захвата.

[Java SE 17, StampedLock](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/locks/StampedLock.html)

## Отмена, тайм-аут и завершение

Interrupt — сигнал сотрудничества. `Thread.interrupt` устанавливает статус, а методы вроде `sleep`, `take` или `join` при определённых условиях выходят с `InterruptedException` и очищают его. Если не можешь передать проверяемое исключение выше и уровень выше должен узнать об остановке, восстанови статус через `Thread.currentThread().interrupt()` и заверши работу. Бесконечное игнорирование сигнала препятствует остановке. Само прерывание не откатывает внешние эффекты.

Многие задачи имеют три фазы: подождать вход, обработать и сохранить результат. Если сигнал пришёл в ожидании, можно выйти сразу. После сохранения эффект мог состояться. Если операция допускает повтор, новая попытка сверяет её состояние. При остановке сервиса срок завершения ограничен, поэтому для долгой работы храни прогресс в долговечном месте. `ExecutorService.shutdown()` прекращает приём, `shutdownNow()` пытается остановить выполняющиеся задачи и возвращает ожидавшие. Это попытка через механизм прерывания, а не обещание остановить любой код.

**Тест на гонку.** Сделай два worker и контрольные точки. Для потерянного обновления оба читают значение, останавливаются на барьере, затем продолжают запись. Для проверки корректного результата ожидание завершения имеет тайм-аут. Если надо проверить отсутствие гонок модели памяти, один удачный тест показывает лишь один наблюдавшийся исход. При необходимости используй специализированный stress test, а гарантию выводи из правил happens-before и атомарности операций.

## Самопроверка

<details>
<summary>Новый объект настроек дважды читают через volatile и получают несовместимые поля. Возможен ли такой случай?</summary>

Да. Каждое чтение ссылки может получить корректный объект, но между ними writer сменит версию. Прочитай ссылку один раз и используй поля этого экземпляра.

</details>

<details>
<summary>Поток не смог получить разрешение семафора по тайм-ауту, но в finally всегда выполняет release. Что сломалось?</summary>

Он возвращает разрешение, которого у него нет. Под нагрузкой лимит растёт. Начинай защищённый блок только после успешного acquire и возвращай разрешение лишь из этого блока.

</details>

<details>
<summary>В updateAndGet добавили отправку email и иногда она дублируется. Как связать это с CAS?</summary>

Функция пересчёта может выполняться повторно при неудачной попытке изменить ссылку. Сначала вычисляй новый снимок без эффекта и фиксируй успешную смену, затем выполняй внешнее действие с соответствующей гарантией.

</details>
