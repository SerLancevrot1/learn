# Java в рабочем окружении: загрузчики, runtime image и JFR

[Java](README.md) · [JVM и память](jvm.md) · [Maven и runtime classpath](maven.md)

## Почему один и тот же JAR запускается по-разному

Приложение в IDE видит классы исходников и зависимости по настроенной classpath. Запуск в контейнере использует сформированный артефакт, другой набор файлов и runtime. Если упал только контейнер, сравни команду запуска, рабочий каталог, содержимое артефакта, module path или classpath, файловую систему образа и доступность зависимостей. Код, загруженный в IDE, может потребовать стандартный модуль, которого нет в минимальном образе.

### Classpath, module path и рефлексия

Классы, загружаемые с classpath, относятся к unnamed module соответствующего loader. Именованные модули явно описывают зависимости и доступ к пакетам. `requires` объявляет читаемость другого модуля, `exports` открывает публичные типы пакета для обычного доступа. `opens` позволяет глубокую рефлексию согласно конфигурации. Если сериализатор не может отразить приватное поле именованного модуля, видимость публичного типа ещё не решает доступ к полю. Обычно лучше открыть ровно нужный пакет подходящему модулю или использовать публичные методы DTO.

**ClassCastException с двумя одинаковыми именами.** У plugin system один тип записан и в API приложения, и внутри упаковки plugin. Его определили разные загрузчики. Полное имя совпало, но JVM видит разные типы. Решение зависит от модели: общий API загружается родительским loader, plugin загружает реализацию. При проверке посмотри, какой loader определил каждый тип. Если метаданные классов накапливаются после перезагрузки plugin, изучи ссылки из статических коллекций, потоков, `ThreadLocal` и зарегистрированных callbacks. Они могут удерживать loader и все его классы.

Если библиотека находит реализацию через `ServiceLoader`, метаданные провайдера должны попасть в упаковку. Для classpath это файлы под `META-INF/services`, у модулей используются соответствующие объявления. При сборке плоского fat JAR одинаковые ресурсные имена могут перезаписать друг друга, если сборщик не объединяет их. Spring Boot executable JAR использует собственную структуру и загрузку вложенных библиотек. Поэтому проверяй фактический артефакт.

### jdeps и jlink

`jdeps` анализирует зависимости class-файлов и может вывести предполагаемый набор модулей. Путь с рефлексией, динамической загрузкой или сервисным провайдером может потребовать дополнительного модуля, который статический анализ пропустил. `jlink` собирает runtime image с выбранными модулями. После уменьшения проверь реальные пути: TLS, JDBC, локализацию, плагины сериализации и диагностику, которой пользуется дежурный. При выборе размера образа учитывай, что Java в нём должна регулярно получать обновления.

## JFR: отличаем ожидание от выполнения

Checkout обычно выполняется 80 мс, иногда дольше секунды. CPU всего сервиса 45%, время GC-пауз мало. JFR позволяет сопоставить события одного интервала. Возможны ожидания монитора, parking, сокетное I/O, аллокации, горячие стеки и GC. Набор событий зависит от настроек записи и версии JDK. Выбери нужный интервал и начни с пользовательского симптома.

| Картина | Вероятный вопрос | Второе измерение |
| --- | --- | --- |
| В flame graph доминирует сериализация | Откуда большие результаты или лишние преобразования? | Размер ответа и CPU на один класс запросов |
| Потоки паркуются в клиентском пуле | Почему ресурс занят так долго? | Active/pending и длительность запросов к зависимости |
| `Java Monitor Blocked` по одному классу | Кто держит монитор и какая работа выполняется внутри? | Thread dumps и длительность критической секции |
| Долгий `SocketRead` | Какая зависимость долго отдаёт данные? | Трейс, route, ответы и тайм-ауты |
| Высокие аллокации конкретного типа | Кто создаёт объекты и сколько их переживает циклы? | GC logs, аллокации на запрос, пост-GC занятость |

CPU-профиль показывает, что выполнялось на процессоре по выбранной методике. Он может почти не показать причину минуты ожидания. Wall-clock или события блокировок помогают увидеть задержки. Если участок занимает 80% CPU-профиля, это ещё не означает 80% задержки пользователя. Другие запросы могли ждать I/O, а снятый интервал мог быть нерепрезентативным.

### Память растёт на уровне контейнера

После импорта p99 вернулся к норме, occupancy после GC прежняя, потребление контейнера растёт. Посмотри число платформенных потоков, direct buffers, metaspace, committed heap и нативную память. Если число потоков выросло с 200 до 1500, возможен новый cached pool при каждом запросе или незакрытый executor. Стеки и нативные данные добавляют цену независимо от Java heap. Сними стеки в двух окнах и сгруппируй по типу работы.

Если растёт retained heap, сравни одинаковые фазы нагрузки и пути удержания. В очереди могут скапливаться объекты запросов. Большой retained size у одного executor объясняется цепочками pending tasks. Новая копия приложения иногда временно сократит очередь, но без ограничения входа перегрузка вернётся. Если JFR показывает аллокации короткоживущих объектов, уменьши избыточную работу на горячем пути, а проверку долгоживущих объектов проведи отдельно.

### Проверяем гипотезу на одном входе

Если меняешь сериализацию, сравни размер ответа, число элементов и итоговую схему, чтобы контракт сохранился. Затем посмотри CPU, аллокации на запрос, p95/p99 и throughput при сопоставимом входе. Отдельно проверь прогрев и холодный старт, если обе фазы важны. Изменение одновременно GC, пула и формата ответа затрудняет поиск причины. JFR-запись может содержать пути и сведения об окружении. Перед передачей файла проверь настройки и правила доступа.

[Oracle, диагностика performance с Flight Recorder](https://docs.oracle.com/en/java/javase/17/troubleshoot/troubleshoot-performance-issues-using-jfr.html)

## Самопроверка

<details>
<summary>Добавили jar, но сервис падает с ClassCastException двух одинаковых имён. Почему?</summary>

Проверь определяющие загрузчики. API мог попасть и к родителю, и к plugin. Вынеси общий контракт к общему loader и оставь реализации в изолированных частях.

</details>

<details>
<summary>Отчёт стал создавать меньше объектов, CPU ниже, но p99 прежний. Что проверить?</summary>

Проверь критический путь: ожидание пула, БД, сеть, запись результата. Снижение аллокаций улучшает одну часть, задержку может определять другая.

</details>

<details>
<summary>Образ jlink проходит Health, но TLS-клиент ломается. Почему smoke test это пропустил?</summary>

Health не прошёл реальную цепочку классов, провайдера и доверия. Запусти проверку каждого важного runtime-пути на том же образе и JDK.

</details>
