## Один заказ, три структуры данных

У сервиса есть очередь невыполненных заказов. Нужно найти запись по ID, быстро получить ближайший дедлайн и выгрузить стабильный список. Это три разных операции. Если положить все заказы в `ArrayList`, выгрузка проста, поиск по ID линейный, поиск текущего минимума требует обхода. `HashMap<Long, Order>` ускоряет поиск, но понятия «следующий дедлайн» у неё нет. `TreeMap<Instant, Order>` даёт доступ по времени, но одна точка времени может соответствовать нескольким заказам. Выбор ключа должен выражать уникальность домена.

Если для дедлайнов поправить ключ на `(Instant, id)`, порядок становится полным. При отмене заказа очередь приоритетов умеет быстро извлечь верхний элемент, но удаление произвольного объекта через общий API может быть линейным. Один подход для часто меняемых задач — хранить элементы с версией и проверять вершину по текущему состоянию в карте. Старые варианты удаляются лениво по мере извлечения. Цена — дополнительные записи и растущий объём очереди при частых обновлениях. Чтобы выставить предел, измеряй число устаревших записей и при необходимости перестраивай структуру.

Такая композиция создаёт инвариант между картой и очередью. Если обновить их раздельно из двух потоков, у worker могут разойтись версия и расписание. Под одним владельцем или короткой блокировкой можно выполнить обе правки вместе. Если сервис использует обычную БД и уже сортирует задачи запросом по индексу, память процесса может хранить лишь локальный снимок. Уточни, какая структура является источником истины после рестарта.

## Comparator решает, какой ключ один и тот же

`TreeSet` и `TreeMap` сравнивают элементы или ключи comparator. Если он возвращает 0 для двух различных заказов, для структуры они равны. Comparator по `deadline` оставит один ключ на момент. Сравнение сравниваемых полей должно быть согласованным и давать предсказуемый порядок, в частности соблюдать транзитивность. Сложи критерии через `thenComparing`.

```java
record Job(long id, Instant deadline, int priority) {}

Comparator<Job> nextFirst = Comparator
    .comparing(Job::deadline)
    .thenComparing(Comparator.comparingInt(Job::priority).reversed())
    .thenComparingLong(Job::id);
```

Сначала идёт ближайшее время. Для равных дедлайнов больший приоритет раньше. ID стабилизирует порядок при совпадении обоих условий. Если один ID может законно появиться одновременно с разными версиями, реши, дедуплицируешь ли версии отдельно или включаешь версию в критерии. `reversed()` после объединения всей цепочки перевернул бы и порядок дедлайнов. И ещё одна ловушка: `(a, b) -> a.priority() - b.priority()` может переполниться. Используй `Integer.compare` или `comparingInt`.

Общий контракт `Set` формулируется через `equals`. Если сортированный набор использует comparator, не согласованный с `equals`, сравнение с другим Set может дать неожиданные результаты. Поэтому для предметного равенства по ID обычно удобнее `Map<Long, Job>`, а сортировку по дедлайну строить отдельно. Для снимка списка простого `List.sort` достаточно, даже если у двух записей одинаковый порядок по части критериев.

## Копия и представление на конкретных примерах

| Операция | Что меняется, если потом правят оригинал |
| --- | --- |
| `Collections.unmodifiableList(original)` | Читатель увидит изменения в исходном списке, собственные mutator-операции через обёртку запрещены |
| `new ArrayList<>(original)` | Изменение состава исходного списка не меняет состав копии, элементы по-прежнему общие |
| `List.copyOf(original)` | Получается неизменяемый снимок состава, `null` отклоняется |
| `original.subList(from, to)` | Окно связано с исходным списком, внешний структурный mutator может нарушить контракт окна |
| `Arrays.asList(array)` | Список фиксированного размера, `set` меняет и массив |
| `map.keySet()` | Удаление ключа из представления удаляет запись из карты |

Представь, что сервис отдаёт на повторную отправку `subList` пяти задач, а позже чистит большой исходный список. Изменение исходного списка вне окна делает последующее поведение `subList` неопределённым по контракту List. На практике может появиться `ConcurrentModificationException`. Для передачи независимой партии сделай копию и зафиксируй границу владения. Представление маленького окна также может удерживать большой исходный список и все его элементы. При расследовании удержания памяти ищи реальную связь в heap dump.

Представление удобно для работы с частью одной структуры на коротком отрезке кода. Например, `list.subList(from, to).clear()` удалит диапазон из исходного списка. `NavigableMap.subMap` даёт карту диапазона. Вставка ключа вне границ представления приводит к ошибке. У окон независимо от типа проверь включительность обеих границ. Неизменяемая обёртка поверх окна разрешает читать текущий диапазон, а его содержимое может меняться через владельца.

У `Arrays.asList(new int[]{1, 2, 3})` размер равен 1. Единственный элемент — весь `int[]`, поскольку примитивы не распаковываются в varargs ссылочного типа. Для списка чисел используй `IntStream.of(array).boxed().toList()` или цикл. При большой обработке оцени цену boxing и используемую память.

[Java SE 17, List](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/List.html) · [Java SE 17, Arrays](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Arrays.html)

## Map.compute и граница атомарности

Обычная `HashMap` даёт быстрый поиск при хорошем распределении хеша. Это контракт ожидаемой стоимости на подходящих ключах. Операции `computeIfAbsent`, `merge` и `compute` описывают композицию «прочитать → изменить → записать». Реализация обычной Map не даёт общей конкурентной гарантии. В `ConcurrentHashMap` соответствующие вызовы имеют атомарный эффект для ключа. Выполняя функцию внутри, помни, что другие изменения могут ждать. Долгий I/O увеличивает критический путь и не подходит для такой функции. Попытка менять карту из её собственного callback может нарушать контракт.

**Карта списков.** Выполнение `groups.computeIfAbsent(id, k -> new ArrayList<>()).add(item)` с ConcurrentHashMap атомарно получает или создаёт список. `add` выполняется после него, два потока меняют обычный ArrayList одновременно. Для редких записей подходит `CopyOnWriteArrayList`, если устраивает дорогая запись. Для замены связанного снимка можно построить внутри `compute` новый неизменяемый список. Копия требует работы пропорционально длине списка, при частых больших обновлениях оцени очередь, отдельную блокировку для значения или модель владения одним потоком.

**Карта счётчиков.** С `computeIfAbsent(id, k -> new LongAdder()).increment()` работает потокобезопасный счётчик, пока запись не удаляется и не заменяется другим потоком. Если одновременно удалять «неактивный» ключ, producer может получить старый adder и увеличить уже удалённый объект. Уточни, допустимо ли потерять его вклад. Для строгого переноса бонусного остатка между ключами нужна единая граница, например короткая блокировка состояния или атомарная запись в БД.

**Обход во время записи.** Fail-fast итератор обычной коллекции призван заметить ошибки использования, работает по принципу best effort и не защищает поток. `ConcurrentHashMap` даёт слабосогласованный обход, который может увидеть часть конкурентных изменений. Если выгрузке нужен снимок одной версии, собирай его под соответствующим протоколом. Даже `new HashMap<>(concurrentMap)` строит новую карту обходом, а атомарного снимка времени сам по себе не обещает.

[Java SE 17, ConcurrentHashMap](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html)

## Самопроверка

<details>
<summary>У двух Job один дедлайн, TreeSet содержит одну запись. Где искать?</summary>

Посмотри на comparator. При результате 0 дерево считает их равными. Зафиксируй, что считается одним ключом, и добавь подходящий критерий разрешения равенства.

</details>

<details>
<summary>В API вернули unmodifiableList, клиент неожиданно видит новые элементы. Как объяснить?</summary>

Обёртка запрещает менять список через её API. Изменения оригинала видны в представлении. Для фиксированного состава в момент ответа создай копию и отдельно обеспечь неизменяемость элементов.

</details>

<details>
<summary>Почему ConcurrentHashMap со значениями ArrayList всё ещё теряет события?</summary>

Карта координирует изменения своих записей, а список — отдельное изменяемое значение. Добавление в него должно быть потокобезопасным, защищённым одним владельцем или заменено на атомарную замену снимка.

</details>
