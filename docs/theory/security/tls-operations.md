## Один пользовательский запрос может иметь несколько TLS-соединений

Внешний клиент вызывает `api.example.com`. Ingress принимает TLS и отправляет запрос сервису. Сервис вызывает платёжного провайдера по другому соединению. Эти отрезки имеют разные компоненты, ключи, trust stores и имена. Если внешний HTTPS отвечает, это говорит о первом отрезке. Соединение от ingress к pod может быть HTTP или отдельным TLS. Соединение от Java к провайдеру имеет собственную проверку имени и доверия.

| Граница | Кто представляет сертификат | Кто проверяет |
| --- | --- | --- |
| Браузер → ingress | Ingress для публичного домена | Браузер по своему набору доверия |
| Ingress → приложение с повторным TLS | Сервер приложения для имени upstream | Ingress по выбранному внутреннему CA и настройке имени |
| Java → внешний API | Внешний API, а при mTLS ещё и клиент Java | Java проверяет сервер, провайдер — Java-клиента |

Успешный TLS первого отрезка не устанавливает конфиденциальность на всех последующих. Если требования предусматривают шифрование и на пути до backend, выбери passthrough или повторную установку TLS по инфраструктуре. При passthrough точка proxy видит меньше прикладных сведений. При termination доступны маршрутизация и обработка HTTP, а следующая граница получает отдельную конфигурацию защиты.

### SNI и имя для проверки

Клиент с SNI сообщает, для какого имени нужен TLS-сеанс. Это позволяет выбрать сертификат соответствующего виртуального хоста. Проверка идентичности выполняется отдельно: клиент сравнивает ожидаемое имя с подходящим идентификатором в сертификате, обычно DNS SAN для DNS-имени. Например, клиент подключился по `https://payments.example.com`, балансировщик выбрал сертификат соседнего домена. Даже если подпись доверенного CA верна, проверка имени должна отвергнуть соединение.

Для соединения по IP нужно подходящее подтверждение IP-идентичности. Сертификат для DNS-имени не становится сертификатом для произвольного адреса, по которому это имя разрешается. При диагностике вручную сохраняй ожидаемое имя и SNI, иначе ручная проверка может получить другой сертификат и не воспроизвести проблему Java.

[RFC 9525, идентичность сервиса TLS](https://www.rfc-editor.org/rfc/rfc9525.html) · [RFC 8446, TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html)

## Что именно лежит в keystore и truststore

В поддерживаемом формате хранилища одинаковый контейнер может содержать разные роли. Keystore для собственной идентичности обычно содержит private key и соответствующую цепочку сертификатов. Truststore содержит доверенные сертификаты или якоря. Ошибка «наш клиент не доверяет провайдеру» требует настроить доверие к его цепочке, а не добавить его private key. Ошибка «провайдер не принимает наш mTLS» требует проверить клиентскую идентичность, подбор сертификата и правила его доверия на сервере.

В Spring Boot SSL Bundles позволяют описать согласованные trust и key материалы и использовать их в поддерживаемых клиентах и серверах. Проверь, какой bundle выбрал конкретный клиент. Один Java-процесс может иметь разные клиенты для внутреннего и внешнего API. Изменение системного truststore всего процесса может зацепить больше компонентов, чем один выбранный bundle. Reload поддерживается для определённых комбинаций версии и использования, поэтому обновление файла на томе ещё не доказывает, что живой клиент заменил SSL context.

[Spring Boot 3.4, SSL bundles](https://docs.spring.io/spring-boot/3.4/reference/features/ssl.html)

## Смена сертификата без несовместимого окна

При обычной замене leaf на том же CA порядок проще: подготовь новый ключ и цепочку, выпусти и проверь, затем замени предъявляемый сертификат. При смене CA части системы должны узнать о новом доверии до переключения. В mTLS обе стороны могут одновременно играть роли проверяющего и предъявляющего. Например, backend уже доверяет новому CA для ingress, а ingress ещё не доверяет новому сертификату backend.

1. Определи проверяющую сторону для каждого отрезка, включая фоновые worker, старую версию Java и клиентские интеграции.
2. Выпусти trust bundle, который на переходе допускает старую и новую ожидаемые цепочки согласно политике.
3. Убедись, что новые экземпляры и работающие клиенты реально прочитали bundle. Проверь холодное соединение.
4. Переключи сертификаты по частям. Наблюдай handshake errors на каждой стороне, идентичность leaf и незакрытые старые соединения.
5. Когда старые предъявления и пути rollback больше не допустимы, убери прежнее доверие по политике.

Истечение сертификата может скрываться за соединением в пуле. Пока TLS-сеанс уже установлен, запросы по нему ещё проходят. Новый pod или новый connection получил отказ первым. Проверяй не только живость сервиса, но и старт свежего доверенного handshake со стороны клиента. Если локальное время сильно сбилось, даже хороший сертификат может выглядеть ещё недействительным или истёкшим.

### TLS уже прошёл, вернулся 403

TLS подтверждает свойства соединения и при mTLS может дать удостоверенную клиентскую идентичность. Приложение своими правилами проверяет разрешение на метод и конкретный ресурс. Если proxy передаёт производный ID, downstream доверяет такому заголовку только на удостоверенной границе, а внешние одноимённые заголовки должны быть очищены при построении запроса. Для диагностики выясни, завершился ли handshake, кто сформировал HTTP-статус и какой principal проверялся. У ошибки доверия при handshake прикладного HTTP-ответа от удалённого приложения может вообще не быть.

## Самопроверка

<details>
<summary>Клиент получил ошибку только после рестарта хотя сертификат сменился утром. Что могло произойти?</summary>

Существующий пул держал прежние соединения, или процесс ещё не перечитал trust bundle. Новый handshake проверил изменившийся набор. Сравни предъявленный сертификат и состояние доверия после свежего подключения.

</details>

<details>
<summary>Внешний HTTPS работает, но ingress возвращает 502 после замены CA. Где проверить?</summary>

Отдельно проверь upstream TLS между ingress и pod, включая имя, SNI, цепочку и trust ingress. Успех внешнего сегмента удостоверяет лишь тот сегмент.

</details>

<details>
<summary>Доверенная подпись есть, но Java жалуется на hostname. Как трактовать?</summary>

Доверие к подписи и совпадение имени — независимые проверки. Сверь ожидаемый DNS/IP, SAN и выбранный через SNI сертификат.

</details>
