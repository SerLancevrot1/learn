# Прикладная безопасность Java-бэкенда и Spring Security

[Безопасность](README.md) · [TLS и mTLS](tls.md) · [Банк вопросов](../../interview/base/operations.md#безопасность)

## Что нужно знать разработчику

| Ситуация | Какую проверку спроектировать |
|---|---|
| Пользователь открыл кошелёк по ID | Подтвердить личность, проверить право на чтение и принадлежность кошелька пользователю |
| Сервис получил токен | Проверить, кто его выдал, кому он предназначен, срок действия и подпись |
| Браузер автоматически отправляет cookie | Защитить операции записи от CSRF, а для чтения между origin настроить CORS |
| В API пришли строка для SQL, URL или файл | Определить, где данные станут частью запроса, сетевого вызова или HTML, и применить защиту именно там |
| Нужно расследовать попытку доступа | Найти действие по audit log и trace ID, исключить токены и другие секреты из телеметрии |

## 1. Аутентификация, авторизация и доступ к объектам

**Аутентификация** подтверждает, от чьего имени выполняется запрос. **Авторизация** проверяет, что этому субъекту разрешено делать. У `GET /wallets/42` есть как минимум два условия доступа.

1. Клиент вправе вызывать операцию чтения, например у токена есть `wallet:read`.
2. Пользователь вправе читать именно кошелёк `42`. Правило обычно зависит от владельца, организации или явного разрешения.

Если Алиса с правильным токеном подставляет ID кошелька Бориса и получает баланс, это **BOLA** (Broken Object Level Authorization), часто называемая IDOR. UUID усложняет перебор, но ID может попасть в историю, ссылку или логи. Получай идентификатор пользователя из проверенного контекста, а принадлежность ресурса проверяй на сервере. Например, при модели с одним владельцем запрос может выглядеть так:

```sql
SELECT id, balance
FROM wallet
WHERE id = :wallet_id AND owner_id = :authenticated_user_id;
```

Для изменения данных аналогичное ограничение можно включить в `UPDATE` и проверить число изменённых строк. В приложении с несколькими организациями учитывай также границу tenant. Для списка применяй ту же политику к выборке и `count`. Для полей используй отдельные DTO: запрос на редактирование названия не должен принимать `ownerId`, `role` или `balance`, даже если эти поля есть в сущности. [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/)

**Статусы для Bearer API.** Без токена или с непригодным токеном ожидай `401` с `WWW-Authenticate`. С действительным токеном без нужного права ожидай `403`. Если политика скрывает существование чужих объектов, для чужого и несуществующего ID можно возвращать одинаковый `404`. [RFC 6750, ошибки Bearer](https://www.rfc-editor.org/rfc/rfc6750.html#section-3) · [RFC 9110, статус 403](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4)

## 2. Сессии, OAuth 2.0, OpenID Connect и JWT

| Механизм | Что происходит |
|---|---|
| Серверная сессия | Клиент хранит идентификатор, обычно в cookie. Сервер ищет состояние сессии. При выходе сессию можно инвалидировать на сервере |
| OAuth 2.0 | Сервер авторизации выдаёт access token для обращения к API с определёнными полномочиями. Access token может быть JWT или непрозрачной строкой |
| OpenID Connect (OIDC) | Клиент получает ID token и проверяет, кто вошёл. ID token адресован клиенту, который инициировал вход |
| JWT | Формат токена. Подписанный JWT можно прочитать без ключа, подпись позволяет обнаружить подмену |

Для входа пользователя разберись в **Authorization Code + PKCE**. Клиент отправляет браузер на сервер авторизации, получает короткоживущий код и обменивает его на токены. PKCE привязывает обмен к клиенту, начавшему операцию: сервер сравнивает исходный `code_challenge` с результатом преобразования предъявленного `code_verifier`. При вызове API клиент отправляет access token, а refresh token используется для получения нового access token у сервера авторизации. `client_credentials` подходит для вызовов от имени самого сервиса. [OAuth 2.0 Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html) · [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)

### Что проверяет API в JWT

- **Подпись и алгоритм.** Доверяй настроенным ключам издателя и разрешённому набору алгоритмов. Издатель может публиковать открытые ключи через JWKS и менять их при ротации. `kid` помогает выбрать ключ из доверенного набора.
- **Назначение.** Сверяй `iss` с доверенным издателем, `aud` с идентификатором своего API и различай профили токенов. Например, ID token и access token одного издателя требуют разных правил проверки.
- **Время.** Проверь срок действия `exp` и ограничение `nbf`, если оно задано. Требуй обязательные поля согласно профилю, который поддерживает API, и ограничь допуск на расхождение часов.
- **Полномочия.** После проверки токена сопоставь `scope` или другие согласованные claims с правилами приложения. Для пользователя при нескольких издателях учитывай пару `iss` и `sub`, поскольку `sub` задаётся в контексте издателя. Для `client_credentials` применяй отдельную политику сервисного доступа.

Если API проверяет JWT только локально, токен обычно пригоден до истечения срока, даже если клиент уже вышел. Для немедленного отзыва нужна дополнительная проверка, например denylist до истечения срока или introspection, если это поддерживает сервер авторизации. Короткий срок жизни ограничивает окно использования украденного токена. [JWT Best Current Practices](https://www.rfc-editor.org/rfc/rfc8725.html) · [Профиль JWT для access token](https://www.rfc-editor.org/rfc/rfc9068.html) · [OAuth Token Introspection](https://www.rfc-editor.org/rfc/rfc7662.html)

## 3. Что делает Spring Security

В Spring MVC запрос проходит через servlet-фильтры до контроллера. `FilterChainProxy` выбирает первую подходящую `SecurityFilterChain`. При Bearer-аутентификации фильтр извлекает токен, `JwtDecoder` участвует в проверке, а результат аутентификации доступен через `SecurityContext`. Правила `authorizeHttpRequests` проверяют доступ на уровне HTTP. Сервис проверяет принадлежность объекта и другие бизнес-ограничения. Для защиты на уровне метода можно включить `@EnableMethodSecurity` и задать правила через `@PreAuthorize`. При стандартном режиме на основе прокси учитывай [вызовы внутри того же bean](../spring/spring-framework.md#42-self-invocation). [Архитектура Spring Security](https://docs.spring.io/spring-security/reference/servlet/architecture.html) · [Защита методов](https://docs.spring.io/spring-security/reference/servlet/authorization/method-security.html)

**Учебный фрагмент для Spring Boot 3.4.** Допустим, это отдельное приложение с `spring-boot-starter-oauth2-resource-server`. Кошельки читают по Bearer access token, который клиент явно передаёт в `Authorization`. API не аутентифицирует запросы по cookie, HTTP Basic или сессии. Пример предполагает клиентов с того же origin или вне браузера.

```java
import jakarta.servlet.DispatcherType;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
class WalletSecurityConfig {
    @Bean
    SecurityFilterChain walletApi(HttpSecurity http) throws Exception {
        return http
                .sessionManagement(session -> session
                        .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
                .csrf(csrf -> csrf.disable())
                .authorizeHttpRequests(auth -> auth
                        .dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()
                        .requestMatchers(HttpMethod.GET, "/wallets/*")
                        .hasAuthority("SCOPE_wallet:read")
                        .anyRequest().denyAll())
                .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
                .build();
    }
}
```

```properties
spring.security.oauth2.resourceserver.jwt.issuer-uri=https://idp.example.com/realms/learn
spring.security.oauth2.resourceserver.jwt.audiences[0]=wallet-api
```

Spring Security по умолчанию преобразует scopes из `scope` или `scp` в authorities с префиксом `SCOPE_`. В примере издатель выделяет `wallet-api` как audience для access token этого API. Если профиль требует дополнительных проверок, например обязательного `exp` или отдельного типа токена, задай соответствующие валидаторы в `JwtDecoder`. Правило `GET /wallets/{id}` проверяет полномочие на уровне HTTP, а проверку владельца из [раздела 1](#1-аутентификация-авторизация-и-доступ-к-объектам) выполняет сервис. Правило для `ERROR` разрешает внутреннюю обработку ошибок Spring Boot. Если настроены несколько цепочек, различай `securityMatcher`, который выбирает цепочку, и `requestMatchers`, которые задают правила внутри неё. Предусмотри цепочку по умолчанию, если остальные покрывают только отдельные пути. [Spring Boot 3.4, Resource Server](https://docs.spring.io/spring-boot/3.4/reference/web/spring-security.html) · [Spring Security, JWT](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html)

## 4. Браузер и границы доверия

- **CSRF.** Чужой сайт заставляет браузер отправить запрос с учётными данными жертвы, например с cookie сессии. Для изменяющих состояние запросов в таком приложении нужен CSRF-токен. `SameSite` снижает риск, а `Secure` ограничивает отправку cookie защищённым транспортом. `HttpOnly` закрывает JavaScript доступ к значению cookie. JWT в cookie требует того же анализа CSRF, что и идентификатор сессии. [Spring Security, CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html) · [OWASP, управление сессиями](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- **CORS.** Браузер применяет правила доступа к ответам между origin. Для ряда запросов он предварительно отправляет `OPTIONS` (preflight). Часть запросов, например отправка обычной HTML-формы, может уйти без preflight. CORS нужно обработать до проверки аутентификации preflight, а для запросов с credentials задавать конкретные разрешённые origin. Сам API проверяет доступ независимо от CORS. [Spring Security, CORS](https://docs.spring.io/spring-security/reference/servlet/integrations/cors.html)
- **XSS.** Внедрённый скрипт выполняется с полномочиями страницы. Он может отправлять запросы от имени пользователя даже при `HttpOnly`. Используй экранирование под контекст вывода, безопасные API для DOM и санитайзер, если пользовательский HTML разрешён. Content Security Policy добавляет ещё один слой защиты. [OWASP, предотвращение XSS](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)

### Границы доверия между сервисами

Для каждой связи опиши вызывающего, получателя, защищаемое действие, данные и способ отзыва доступа. **Аутентификация** устанавливает участника; **авторизация** проверяет его право на конкретную операцию и объект. API Gateway может выполнять первичную проверку, а владелец ресурса всё равно проверяет права на конкретный платёж или организацию.

- **Доступ пользователя.** OpenID Connect сообщает приложению результат аутентификации пользователя; API получает предназначенный ему access token OAuth 2.0. JWT — формат токена, не отдельный протокол входа; access token может иметь и другой формат. Keycloak может выступать провайдером идентификации и сервером авторизации. [OpenID Connect](https://openid.net/developers/how-connect-works/) · [Keycloak](https://www.keycloak.org/securing-apps/overview).
- **Вызов от имени сервиса.** У процесса своя учётная запись и минимальные полномочия, например с OAuth Client Credentials. mTLS аутентифицирует стороны соединения при проверке сертификатов, а сетевые правила ограничивают доступность адресов. Разрешение на бизнес-действие задаётся отдельно. Ключи и сертификаты храни и ротируй управляемо.
- **Внешний callback.** Проверяй подлинность по контракту провайдера (например, подпись исходных байтов и допустимый возраст подписанной метки). Затем сопоставь внешний идентификатор с ожидаемой операцией и проверь допустимость перехода. Учитывай повтор легитимного сообщения: дедупликация или идемпотентный переход нужны даже при корректной подписи. Если обработка отложена, подтверждай приём после надёжной записи задачи. [Пример: требования к вебхукам Stripe](https://docs.stripe.com/webhooks).

См. [TLS и mTLS](tls.md) и [последовательность платёжного сценария](../architecture/cases/payments.md).

## 5. Уязвимости и эксплуатация

| Риск | Что проверять на ревью |
|---|---|
| SQL и JPQL injection | Передавать значения параметрами. Для `ORDER BY` сопоставлять публичные поля сортировки с заранее заданными колонками. Проверка типа или длины дополняет параметризацию |
| SSRF | При загрузке по пользовательскому URL по возможности ограничивать назначения списком разрешённых. Если разрешены произвольные домены, проверять IP, к которому фактически подключается клиент, в том числе после перенаправления. Закрывать исходящий доступ к внутренним адресам и облачным metadata endpoint на сетевом уровне |
| Загрузка файлов и десериализация | Ограничивать размер и тип, хранить загрузки вне каталога раздачи с серверными именами, проверять содержимое. Для JSON принимать DTO с известной структурой. Исключать Java native serialization и произвольный выбор класса из недоверенного ввода |
| Пароли и подбор | Для хранения применять парольный KDF с солью, например Argon2id, с настроенной стоимостью. Ограничивать попытки входа, использовать MFA для чувствительных учётных записей и защищать восстановление доступа |
| Секреты и зависимости | Хранить секреты в выделенном хранилище, выдавать минимальные права, уметь отозвать и ротировать ключ. Проверять прямые и транзитивные зависимости, планировать обновления с учётом того, где используется уязвимый код |
| Ошибки конфигурации и аудит | Закрывать служебные endpoint, исключать stack trace из ответа клиенту. Записывать субъект, действие, результат и trace ID. Фильтровать `Authorization`, cookie сессии, пароли и ключи также в прокси, трассировках и журналах ошибок |

Пароль проверяют сравнением результата KDF с сохранённым значением. Уникальная случайная соль мешает использовать одну заранее посчитанную таблицу для многих пользователей, а стоимость вычисления замедляет перебор после утечки базы. Для данных, которые нужно восстановить, применяют шифрование с управлением ключами. [OWASP, хранение паролей](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

[OWASP Top 10:2025](https://top10.owasp.org/2025/) · [SQL injection](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html) · [SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) · [Загрузка файлов](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) · [Безопасное логирование](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

## 6. Как проверить безопасность API

| Сценарий для `GET /wallets/{id}` | Что проверить |
|---|---|
| Нет токена | `401` и заголовок `WWW-Authenticate` |
| Токен просрочен, подписан посторонним ключом или предназначен другому API | `401`, бизнес-операция не выполнялась |
| Токен корректный, но без `wallet:read` | `403` |
| Алиса запрашивает свой кошелёк | `200`, ответ содержит только разрешённые поля |
| Алиса с тем же токеном запрашивает кошелёк Бориса | `404` при политике сокрытия существования, данные не раскрыты |
| Аналогичный запрос на изменение чужого объекта | Отказ, состояние объекта в БД не изменилось |

`MockMvc` с `jwt()` подходит для проверки правил доступа с заранее заданной аутентификацией. Чтобы проверить подпись, сроки, `iss` и `aud`, отправляй подписанный тестовым ключом токен через настоящий `JwtDecoder`. Для приложения с сессией добавь запросы с CSRF-токеном и без него. Для браузерного клиента с другого origin отдельно проверь разрешённый и запрещённый preflight. [Spring Security, тестирование OAuth 2.0](https://docs.spring.io/spring-security/reference/servlet/test/mockmvc/oauth2.html)

## 7. Вопросы для собеседования

Сначала ответь вслух. Объясни, какая граница нарушена, где поставить проверку и каким тестом подтвердить результат.

<details>
<summary>1. Почему валидный JWT с wallet:read не даёт доступ к любому кошельку?</summary>

Scope даёт доступ к операции чтения. Принадлежность объекта проверяется отдельно по субъекту из проверенного токена. Проверь два кошелька разных владельцев с одним и тем же токеном.

</details>

<details>
<summary>2. Токен выпущен нашим IdP, подпись верна. Когда API всё равно его отклонит?</summary>

Например, когда токен предназначен другому сервису, истёк или ещё не действует. Отдельно проверь, что приложение принимает нужный тип токена. Отсутствие права на операцию у успешно аутентифицированного клиента приводит к отказу в авторизации.

</details>

<details>
<summary>3. Зачем в OAuth код и PKCE? Какой токен послать в API?</summary>

Код обменивают на токены у сервера авторизации. PKCE требует при обмене секрет, созданный для этой попытки входа, и защищает от использования перехваченного кода. В API передают access token. ID token проверяет клиент, который организовал вход.

</details>

<details>
<summary>4. Пользователь вышел, но его access token всё ещё работает. Почему?</summary>

При локальной проверке API видит срок и подпись токена. Удаление токена у клиента и завершение сессии входа не меняют уже выданный JWT. Обсуди короткий срок действия и отдельный механизм отзыва, если отзыв должен вступать в силу сразу.

</details>

<details>
<summary>5. Можно ли выключить CSRF, если API использует JWT?</summary>

Зависит от того, как браузер передаёт учётные данные. При JWT в автоматически отправляемой cookie риск сохраняется. Для отдельного API, где клиент явно добавляет Bearer-токен в заголовок и других способов аутентификации нет, CSRF-защиту можно отключить для этой цепочки.

</details>

<details>
<summary>6. Почему запрос работает в curl, а браузер сообщает об ошибке CORS?</summary>

Браузер проверяет заголовки CORS и может отклонить preflight или запретить странице читать ответ. Проверь `Origin`, ответ на `OPTIONS` и настройки credentials. `curl` эту браузерную политику не применяет.

</details>

<details>
<summary>7. Защитят ли PreparedStatement и валидация от всех видов инъекций?</summary>

Параметры отделяют значения от SQL-кода. Динамические колонки сортировки выбирай из заданного списка. Для HTML, shell и других интерпретаторов нужны собственные безопасные способы передачи или вывода данных.

</details>

<details>
<summary>8. API принимает URL аватара. Почему проверки схемы HTTPS мало?</summary>

Имя может разрешиться во внутренний IP, а разрешённый адрес может перенаправить запрос на закрытый ресурс. Проверь назначение и переходы, ограничь исходящий доступ. Это SSRF: запрос делает сервер со своими сетевыми возможностями.

</details>

<details>
<summary>9. Зачем соль и медленный KDF, если пароль можно хешировать SHA-256?</summary>

Быстрый хеш позволяет очень быстро проверять догадки после утечки. Уникальная соль мешает переиспользовать результаты между аккаунтами. Парольный KDF повышает стоимость каждой догадки.

</details>

<details>
<summary>10. Как доказать, что Spring проверяет подпись, а пользователь не читает чужие данные?</summary>

Это две проверки. Отправь токен с неверной подписью через реальный декодер и ожидай `401`. Затем используй валидный токен с правом чтения для запроса к чужому объекту и проверь отказ по политике владения. `jwt()` в MockMvc может помочь со второй проверкой.

</details>

<details>
<summary>11. Почему @PreAuthorize может не сработать при вызове внутри того же сервиса?</summary>

В стандартном режиме правило применяет Spring-прокси. Вызов через `this` обходит прокси. Проверь, включена ли защита методов, где проходит вызов и какой тест воспроизводит именно этот путь.

</details>

<details>
<summary>12. В логах нашли действующий токен. Что делать?</summary>

Ограничь доступ к логам и оцени, куда они успели попасть. Отзови токен доступным способом и проверь связанные события аудита. Исправь место логирования и убедись, что секрет скрывается в приложении, прокси и трассировках. Если утёк ключ подписи, меняй сам ключ и пересмотри доверие к выпущенным им токенам.

</details>
