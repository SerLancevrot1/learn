# OAuth 2.0 и Spring Security: роли приложений и границы токена

## Три участника в одном запросе

Пользователь открывает кабинет, кабинет вызывает API заказов. **OAuth client** — приложение, запрашивающее токен. **Authorization server** — поставщик авторизации, выдающий токен. **Resource server** — API, принимающий токен для доступа к ресурсу. В OpenID Connect клиент может также аутентифицировать пользователя по ID token и протоколу входа. Совместная настройка на одном окружении не убирает этих ролей.

| Данные | Кто использует | Для чего |
| --- | --- | --- |
| ID token | OIDC client | Проверить результат аутентификации пользователя по договорённости OIDC |
| Access token | Resource server | Авторизовать вызов защищённого API |
| Refresh token | Клиент и authorization server | Обновить access token по поддерживаемому протоколу |
| Cookie сессии BFF | Браузер и сервер приложения | Найти локальную пользовательскую сессию |

ID token может быть подписан тем же ключом, что access token. Одной подписи мало. У токена есть назначение, аудитория и правила профиля. На Java API проверь issuer, audience, срок, ожидаемые алгоритмы и допустимый тип/признаки используемого профиля. Дальше проверь scopes и принадлежность объекта. «JWT распарсился» означает лишь, что получены поля.

## Пользовательский вход по Authorization Code + PKCE

1. Клиент подготавливает запрос к authorization endpoint и создаёт привязку к начатому сеансу. Он формирует случайный verifier для PKCE и передаёт challenge.
2. Пользователь аутентифицируется у authorization server и соглашается на доступ согласно политике. Сервер возвращает browser redirect с кодом на зарегистрированный URI.
3. Клиент проверяет, что возвращённый ответ относится к начатому потоку, и обменивает код вместе с verifier. Для confidential client используются удостоверяющие его реквизиты по конфигурации.
4. OIDC-клиент проверяет ID token. API принимает access token по своему договору, а сессия приложения хранит результат входа или связь с ним.

Code — краткоживущий промежуточный результат, который используется в обмене. PKCE связывает обмен с клиентом, создавшим challenge. Проверка redirect URI ограничивает, куда сервер отправляет ответ. `state` позволяет связать ответ с запросом клиента и поддерживает защиту от подмены потока. `nonce` в OIDC связывает ID token с начатым запросом и проверяется там, где предусмотрен профилем. Это разные проверки, поэтому один параметр не стоит просто заменять другим в своей библиотеке. Используй реализованный фреймворком клиентский поток, а тестом убедись, что он корректно отклоняет ответы без нужной привязки.

Для браузерного приложения две распространённые архитектуры. Публичный клиент работает с OAuth на стороне приложения, не может защищать статический client secret и должен учитывать жизненный цикл выпущенных токенов. BFF держит токены на сервере и выдаёт браузеру cookie сессии. Это переносит ответственность на защиту серверной сессии, CSRF и аккуратный срок жизни cookie. Выбери модель под угрозы и инфраструктуру приложения. Сама cookie без правильной настройки и серверной проверки авторизацию не задаёт.

## Прямой вызов сервиса и действие от лица пользователя

Сервис экспорта ночью читает агрегаты под своим служебным аккаунтом. Ему подходит токен клиента с доступом к конкретному API и необходимыми scopes. Человек в этой операции не участвовал. Для запроса «покажи мой заказ» инициатор — пользователь. Если Gateway просто заменит его токен общим привилегированным токеном, downstream потеряет сведения, по которым проверяет принадлежность заказа. Договорись о делегировании, доступной аудитории и объёме прав. Возможны propagation подходящего access token, токен для нужного ресурса через поддерживаемый обмен или отдельная проверяемая схема доверия между сервисами.

**Audience ограничивает получателя.** Токен для внутреннего API отчётов может иметь тот же issuer, что токен для оплаты. Успешная валидация подписи не означает разрешение вызывать платёжный endpoint. После общей проверки API сравнивает ожидаемую audience. Не выводи роль из имени сертифицированного клиента или произвольного заголовка, доступного внешней стороне. Проксируемые данные об идентичности принимаются только через доверенную границу, где proxy убирает пользовательское значение и создаёт свой атрибут.

**Tenant и субъект.** В многопользовательском API subject относится к issuer и профилю идентичности. Не считай строку `sub` глобальной между независимыми issuer. Строка пути `/tenants/A/orders/42` тоже не доказательство участия в A. Политика должна проверить членство, разрешённое действие и принадлежность заказа. Для mutating-запроса применяй авторизацию на фактическом выбранном объекте. У списков и поисковых фильтров такое же правило: отдельная проверка только на endpoint чтения по ID не защищает выгрузку списка.

## Токен истёк, ключ сменился, issuer недоступен

JWT может проверяться локально после получения доверенных ключей. Потеря доступности issuer не всегда немедленно приводит к отказу всех запросов, если нужный ключ уже закеширован, но холодный старт и появление нового `kid` зависят от модели получения ключей. При обнаружении нового ключа используй ожидаемый JWKS доверенного issuer. `kid` помогает выбрать ключ из доверенного набора и не является самостоятельной аутентификацией issuer.

При плановой ротации authorization server публикует новый публичный ключ. Клиенты начинают проверять подписи нового ключа после обновления набора, старый ключ сохраняется на период действия старых токенов по политике. Точный порядок зависит от кеша и настроек платформы. Проверь запрос со старым и новым ключом, холодный кеш и временный сбой JWKS. Устройство диагностики должно различать подпись неизвестным ключом, недопустимую audience, истечение и недоступность источника метаданных. Полные bearer tokens в логах не нужны.

**Отзыв роли.** Если роль убрали, уже выпущенный автономный access token может сохранять старые claims до истечения. Варианты зависят от требуемой скорости отзыва. Можно уменьшить TTL, использовать проверку активности server-side, хранить динамическую часть доступа в приложении или применять поддерживаемый механизм отзыва. Более жёсткая проверка привязывает время ответа к дополнительному источнику. Для платежей или прав администратора срок изменения доступа приходится фиксировать как отдельное требование.

**Refresh token rotation.** При каждом успешном refresh старое значение может заменяться новым по политике authorization server. Если два запроса одной сессии одновременно обновляют токен, оба могут взять прежнее значение, один получит отказ или механизм reuse detection. Координируй обновление на уровне сессии и проверяй вход после ошибки. Истечение access token не должно приводить к бесконечной волне refresh вызовов со всех вкладок.

[RFC 8725, рекомендации по проверке JWT](https://www.rfc-editor.org/rfc/rfc8725.html) · [Spring Security, JWT Resource Server](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html)

## Что проверять в Spring-тестах

Для проверки правил доступа полезно предоставить уже установленную test authentication и проверить 403 для чужого заказа, 200 для разрешённого и поведение списка. Такой тест проверяет mapping прав и запрос к данным. Чтобы проверить issuer, expiration, audience, подпись и ротацию, дай тестовому процессу собственные ключи и прогони настоящий decoder на позитивном и негативных случаях. Он должен отклонять токен по нужной причине. Для BFF проверь сессию, logout и защиту изменяющих методов. Раздельные тесты проще трактовать, если случайный тестовый decoder перестал получать ключ.

Различай отсутствие credential и недостаточные полномочия уже признанного пользователя. В зависимости от публичной политики доступ к чужому объекту может возвращать 403 или скрывать существование через 404. Политика должна быть однородна и для списков, и для деталей. Оператору нужны причина и ID запроса, а пользователю — ожидаемый ответ API без раскрытия внутренних правил.

<summary>API принимает валидный JWT для любого приложения того же issuer. Какой параметр учесть?</summary>

Проверь audience и профиль токена, затем доступ к операции и объекту. Подпись подтверждает источник, а audience ограничивает получателя.

</details>

<details>
<summary>Почему изменения ролей не всегда видно в следующем HTTP-запросе?</summary>

Прежний access token может быть локально валиден до истечения. Уточни требования отзыва и используй подходящую модель TTL, проверку активности или отдельное чтение динамических прав.

</details>

Такой тест подставляет аутентификацию для проверки доступа. Для ротации нужны настоящая проверка подписи, доверенный тестовый JWKS и сценарий смены ключа.

</details>
