# Массовый импорт файлов: прогресс, ошибки строк и повтор запуска

[Кейсы system design](../README.md#кейсы-system-design) · [Работа с файлами Java](../../java/standard-library.md#файлы-потоки-ввода-и-ресурсы) · [Миграции и backfill](../../data/postgresql/schema-migrations.md)

## Что обещать клиенту при приёме

Пользователь загружает CSV с миллионом изменений цен. Публичный HTTP имеет короткий дедлайн, обработка может занять минуты. Раздели приём файла и подтверждение применения. API возвращает ID импорта и состояние. Заказчик должен уточнить, допустима ли частичная загрузка, что делать с двумя строками для одного товара, можно ли отменить задачу и какое время обработки обещано для файла нужного размера.

Есть два основных контракта. Частичный импорт применяет корректные строки и сообщает подробности ошибок. Атомарная публикация строит новую версию набора, затем переключает читаемое состояние одной границей. Последовательный commit одного миллиона отдельных строк не выполняет атомарную публикацию. Одна большая транзакция может быть корректной для ограниченного размера, но держит больше state и усложняет восстановление. Промежуточное хранилище и публикация новой версии дают другой обмен затратами. Решения выбирают по бизнес-целостности, а не только по размеру файла.

### Устойчивое состояние задания

| Поле | Зачем нужно |
| --- | --- |
| `importId`, `tenantId` | Идентичность задания и граница доступа |
| `objectKey`, `checksum`, `formatVersion` | Зафиксировать загруженный вход |
| `state`, `createdAt`, `startedAt`, `finishedAt` | Управлять жизненным циклом и временем |
| `processedRows`, `appliedRows`, `rejectedRows` | Показывать результат и отличать прочитанные данные от сохранённых |
| `leaseVersion`, `checkpoint` | Возобновить обработку согласованно |
| `resultObjectKey` или ссылка на ошибки | Дать пользователю подробности без загрузки всех строк в одну транзакцию |

Сначала создай путь загрузки файла и после её завершения проверь, что доступен ожидаемый объект нужного размера и версии. Если приложение сохраняет задание и публикует событие в брокер, учти окно dual write. Можно использовать Outbox или поиск готовых задач в БД. Статус `QUEUED` должен обозначать, что система способна возобновить работу после рестарта. Если объект записан, но принятие задания не зафиксировано, нужен способ завершить протокол или очистить промежуточный файл после безопасного срока.

## CSV разбирается как поток записей

В полях CSV в кавычках могут быть запятые, экранированные кавычки и переносы строк. `line.split(",")` обрабатывает лишь часть допустимого формата. Договорись о кодировке, заголовках, разделителе, допустимом размере поля, форме десятичных чисел и дат. Используй parser с нужными настройками. Для неоднозначных чисел и пустых полей выбери одно явно проверяемое правило. Для loading job привяжи его к версии формата, чтобы повтор через неделю разобрал тот же файл так же.

Процессор читается порциями. В памяти держишь ограниченный chunk, валидируешь, преобразуешь в доменные типы, затем применяешь. Если результат ошибок может быть большим, записывай их в отдельную структуру. Прогресс и ошибки измеряй агрегатами, иначе лог из миллиона строк усложнит диагностику. Для адреса ошибки храни номер логической записи. Номер строки текста может отличаться при многострочных полях.

**Байтовый checkpoint и CSV.** Произвольный offset может попасть в середину UTF-8 символа, quoted record или буфера декодера. Перезапуск с такого offset сломает разбор. Один простой подход сохраняет номер записи и при повторе читает начало, пропуская уже зафиксированное. Это требует времени для очень большого файла. Более сложный splitter выделяет проверяемые границы отдельных файлов/partitions. Только после этого можно читать каждый кусок независимо. Сжатый поток тоже может не позволять произвольный доступ без собственного индекса.

## Возобновление порции

После чтения chunk 1–1000 worker пишет изменения в БД. Если состояние прогресса находится в той же БД и относится к той же работе, оно может фиксироваться в одной транзакции с эффектом. Тогда видимый checkpoint точно соответствует зафиксированным строкам. Если отметка и effect находятся в разных системах, между ними возможен сбой. Преждевременный checkpoint теряет строки, отложенный может повторить порцию. Повтор применяй по стабильному ключу, например `(importId, recordNo)` или доменной версии. Сохранённая версия должна относиться к первоначальному неизменяемому файлу.

### Две копии обрабатывают одно задание

Worker A получил lease и перестал продлевать его. Worker B продолжает с сохранённой позиции. Если A вернулся, он не должен обновить checkpoint после B. Для claim храни срок и поколение. Записи прогресса защищай условием по поколению. Применение цен также требует идемпотентности строк или общей транзакции с проверкой владения. Если импортированный файл каждый раз независимо добавляет одну и ту же скидку, повтор порции изменит сумму. Для замены «цена становится X» требуются версия и защита от старого файла, который пришёл после более свежей ручной правки.

**Отмена.** На пользовательский вызов выставляется `CANCEL_REQUESTED`, затем worker останавливается на понятной точке и отмечает `CANCELLED`. Уже зафиксированные порции частичного импорта остаются, если контрактом не задано обратное. Для атомарной подготовки версия может не стать видна. Не обещай одно действие отмены, если несколько worker уже обрабатывают разные части. Тестируй отмену до старта, во время записи chunk и около переключения опубликованной версии.

## Пропускная способность и контроль качества

Если типичный файл 200 МБ и хочется обрабатывать 20 таких файлов параллельно, входной I/O, дешифровка, проверка ссылок и write rate БД задают предел. Обработка 1000 записей в секунду даёт около 17 минут на миллион, без учёта доступа к файлу и прогрева. Запланируй отдельный ресурс и ограничение на арендатора. Если каждый chunk выполняет SELECT для каждой строки, база получает N+1. Для справочных данных загружай ограниченную пачку ключей, проверяя актуальность источника. Для предотвращения роста wall time наблюдай время разбора, проверки и записи отдельно.

Проверка успешного импорта должна смотреть итог, а не только число прочитанных строк. Сверь уникальные ID, число вставок и обновлений, пропуски по ошибкам, контрольные суммы по валютам и примеры конфликтов. Для повторного запуска проверяй, что применённых изменений не стало вдвое больше. Для файла с двумя updates одного SKU выбери заранее «последняя строка выигрывает», «ошибка дубля» или иной детерминированный порядок. При параллельной обработке порций порядок появления commit не обязан совпадать с порядком строк.

## Самопроверка

<details>
<summary>Импорт пережил рестарт, но строк стало вдвое больше. Где искать?</summary>

Проверь, какие эффекты были сохранены до checkpoint, и какие ключи повторяются. Скоординируй прогресс с записью либо добавь проверку идемпотентности.

</details>

<details>
<summary>Почему убеждение «offset показывает начало следующей строки» может сломать CSV?</summary>

Кавычки допускают перенос внутри поля, а кодировка — многобайтные символы. Checkpoint должен соответствовать границе записи парсера или безопасному куску входа.

</details>

<details>
<summary>Пользователь отменил импорт на 90%. Должны ли исчезнуть уже записанные цены?</summary>

Это зависит от обещания. Частичный импорт мог их зафиксировать. Для атомарной публикации ещё не включённая версия не действует. Статус должен показать, какие эффекты уже произошли.

</details>
