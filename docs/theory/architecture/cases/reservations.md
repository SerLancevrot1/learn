# Сервис бронирований: время, конкуренция и истечение резерва

[Кейсы system design](../README.md#кейсы-system-design) · [Транзакции PostgreSQL](../../data/postgresql/transactions.md) · [Время в Java](../../java/standard-library.md)

## Вопрос и инвариант

Нужно бронировать комнаты и оборудование по временным интервалам. Клиент видит доступность, может удержать комнату несколько минут и подтвердить бронь. Для одной комнаты две активные брони не могут перекрываться. У разных комнат перекрытие допустимо. В интерфейсе соседние интервалы `[10:00, 11:00)` и `[11:00, 12:00)` не конфликтуют. Уточни допустимую точность времени и требуется ли буфер на уборку. Если нужен десятиминутный буфер, предметный интервал использования и интервал блокирования ресурса различаются.

**Чтение доступности приблизительное по определению.** После ответа другому пользователю успели выдать бронь. Даже ответ от primary может устареть к моменту следующей команды. Подтверждение дают после атомарной проверки на записи. Сервис возвращает конфликт, если исход изменился. Это удобно тестировать двумя синхронными запросами одинакового интервала. По двум разным комнатам оба запроса должны завершиться независимо.

### Типы и границы

Пользователь вводит местное время в зоне комнаты. API преобразует его в начало и конец в UTC либо принимает ISO-времена с известным смещением. Для повторяющегося еженедельного бронирования отдельно хранит расписание и `ZoneId`, чтобы летнее время не смещало местные часы. Зона API-клиента может отличаться, что проверяется тестом. Для каждого созданного интервала `starts_at < ends_at`. При поиске пересечения полузакрытых интервалов проверка имеет вид `a.start < b.end AND b.start < a.end`.

## Защита интервала в одном PostgreSQL

При наивном `SELECT` «пусто ли это время» и последующем INSERT два вызова успевают получить пустой результат и оба вставляют строки. UNIQUE по комбинации «комната, начало» защищает только совпадающее начало. Перекрытие 10:00–11:00 и 10:30–11:30 оно пропустит. В PostgreSQL диапазон `tstzrange` и exclusion constraint выражают запрет совместного выполнения двух условий: одинаковая комната и пересекающееся время.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_booking (
    id bigint PRIMARY KEY,
    room_id bigint NOT NULL,
    starts_at timestamptz NOT NULL,
    ends_at timestamptz NOT NULL,
    state text NOT NULL CHECK (state IN ('HELD', 'CONFIRMED', 'EXPIRED', 'CANCELLED')),
    hold_until timestamptz,
    occupied tstzrange GENERATED ALWAYS AS (tstzrange(starts_at, ends_at, '[)')) STORED,
    CHECK (starts_at < ends_at),
    CHECK (state <> 'HELD' OR hold_until IS NOT NULL),
    EXCLUDE USING gist (room_id WITH =, occupied WITH &&)
        WHERE (state IN ('HELD', 'CONFIRMED'))
);
```

Схема учебная, в продукте также нужны ссылки на комнату, владельца и ключ команды. `btree_gist` даёт GiST-совместимый оператор равенства для bigint. Если активный интервал уже есть, PostgreSQL обнаружит конфликт, в том числе при конкурирующих вставках. При исключении обработай SQLState `23P01` по контракту предметной операции. Нельзя маскировать им любые другие ошибки базы.

Альтернативная модель блокирует короткую строку комнаты, затем проверяет и вставляет бронь в той же транзакции. Она требует, чтобы все писатели использовали один протокол и сравнивали актуальные данные. При популярной комнате проверка сериализуется даже для непересекающихся периодов. Выбор синхронизации можно сравнить по нагрузке. Для дискретных слотов по 15 минут можно восстановить UNIQUE на `(room_id, slot_start)`, резервируя весь диапазон слотов одной транзакцией. Цена — больше строк и меньше свободы времени.

## Переходы состояния и гонка deadline

Первый запрос создаёт `HELD` с `hold_until`. Подтверждение допускается, пока `state = 'HELD'` и срок действителен. Перед записью выбери, по чьим часам и в какой момент принимаешь решение. PostgreSQL `now()` возвращает начало текущей транзакции, `statement_timestamp()` начало команды, `clock_timestamp()` фактическое время вызова. Если долго ждать блокировку, эти моменты могут заметно различаться. Дай операции короткую транзакцию и опиши политику «срок оценивается после захвата актуальной записи» или другое осмысленное правило. Интерфейс не должен обещать, что запрос, отправленный в клиентскую миллисекунду до deadline, обязательно успешен.

Утверждение «резерв истёк по часам» не меняет сохранённое состояние автоматически. У exclusion constraint предикат описывает устойчивые поля строки. Пока строка HELD, она препятствует конкурирующей вставке. Background job меняет статус на EXPIRED после дедлайна. Для быстрого освобождения при новом резерве можно в короткой транзакции обработать обнаруженные истёкшие записи по подходящему протоколу, затем попытаться вставить новую. `CREATE INDEX WHERE hold_until < now()` не является заменой такого процесса: состав индекса не меняется с течением времени без изменения строк, и выражения предиката должны соответствовать ограничениям PostgreSQL.

### Оплата и отмена

При необходимости оплаты резерв ждёт результат провайдера до срока. Если провайдер подтвердил после того, как резерв истёк и комнату снова заняли, система не может честно подтвердить обе брони. Политика может вернуть деньги или отправить результат оператору, опираясь на ID платёжной попытки. Договорись об этом до интеграции. Условный переход "HELD → CONFIRMED" использует уже сохранённое состояние. Запись результата и исходящего события фиксируется одной транзакцией. Вызов провайдера занимает отдельный этап, он не должен держать блокировку комнаты во время сетевого ожидания.

## Рост и диагностика

Представим 20 тысяч доступных ресурсов и 300 запросов доступности в секунду. Сначала измерь распределение hot rooms и число интервалов на ресурс. Для запросов по месту и периоду полезен индекс, а старые снятые брони могут уйти в архив по политике. Архивирование не должно потерять ключи, предназначенные для защиты от повтора, или нужный аудит. Кеш доступности допустим для поискового экрана с явной валидностью на момент чтения. API бронирования проверяет непосредственно в авторитетном хранилище.

Горячий ресурс неизбежно имеет много отвергнутых попыток, даже если база работает быстро. Отдельно измеряй ожидаемый конфликт, тайм-аут БД и ошибку SQL. Высокий процент предметных конфликтов может быть свойством спроса. Полезны ещё возраст просроченных HELD, время освобождения, тайм-аут ожидания блокировок и задержка писем. Для групповой брони нескольких ресурсов выбери один порядок блокировки, если защищаешь их отдельными строками. При распределении по shard выбор ключа комнаты упрощает локальный инвариант. Бронирование группы комнат на разных shard требует отдельной политики принятия части, компенсации или общего владельца.

## Самопроверка

<details>
<summary>Почему два интервала с разным началом могут нарушить инвариант?</summary>

Уникальность начала не проверяет пересечение. Правило должно сравнивать начало и конец каждого интервала у одного ресурса с учётом выбора границ.

</details>

<details>
<summary>Срок резерва прошёл, но создать новую бронь не удаётся. Где искать?</summary>

Проверь фактическое состояние HELD, задержку процесса истечения и соответствие clocks. Истечение по времени требует зафиксированного перехода состояния, если именно состояние участвует в условии exclusion.

</details>

<details>
<summary>Новый сервис читает актуальный availability на primary. Почему всё равно нужен ответ о конфликте?</summary>

Другая команда может зафиксироваться после чтения. Право на бронь устанавливается проверкой и записью на одной согласованной границе.

</details>
