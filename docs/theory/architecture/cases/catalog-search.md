# Поиск по каталогу: индекс, релевантность и обновление без потери записей

[Кейсы system design](../README.md#кейсы-system-design) · [Производные витрины](../../data/derived-views.md) · [Пагинация API](../pagination-contracts.md)

## Какой запрос предстоит обслуживать

У каталога миллион товаров. Пользователь вводит «зимние ботинки», фильтрует по размеру и цене и ожидает полезные результаты. Нужно договориться, обязательны ли морфология, синонимы, автодополнение и опечатки, как измеряем качество первых результатов и через сколько изменения карточки должны стать видны. Требование «отсортировать по новизне» отличается от «найти максимально подходящее название». У одного товара несколько вариантов размеров. Если фильтр соединяет размер и цвет, уточни, должны ли они совпасть у одного варианта.

**Источник истины.** Для карточки из поиска можно показать индексируемый снимок. Цена и точный доступный остаток при оформлении проверяются у владельца. Если индекс отстаёт, покупатель может увидеть товар в поиске и получить предметный отказ в корзине. Контракт должен разъяснять момент подтверждения. У строгой авторизации опасно опираться только на отстающий индекс; ограничение доступа должно соответствовать требованиям на чтение.

## Инвертированный индекс и анализатор

В простом виде индекс хранит для каждого термина список документов и, по настройке, позиции термина. Для текста «кожаные зимние ботинки» задача анализатора разложить строку на термы и применить правила регистра, фильтров или языковой обработки. Запрос поиска проходит свою анализирующую схему. Если индекс и запрос используют несовместимые формы, видимое совпадение строки может не совпасть на уровне термов. Позиции позволяют выразить фразу или близость слов. Без них остаётся факт встречи слов в документе.

| Поле | Форма поиска | Почему нужна такая форма |
| --- | --- | --- |
| Название | Анализируемый текст | Ищем слова и фразы с правилами языка |
| Артикул | Точное значение | Идентификация по заданному коду |
| Размер, цвет | Структурированные фильтры | Проверяем доступные варианты |
| Цена, дата | Число и дата | Диапазоны и сортировка имеют числовой смысл |
| Tenant | Ограничивающий фильтр | Область поиска задаётся проверенным контекстом |

Точный запрос по анализируемому полю может искать конкретный уже сформированный терм. Для пользовательской фразы обычно нужно применить анализатор запроса. Запрос exact на артикул обязан учитывать договорённость о регистре и нормализации. Для поля цена хранение текстовых лексем приведёт к неправильной сортировке: строки `"100"` и `"99"` сравнятся иначе, чем числа. Настройка индекса — часть контракта данных.

### Фильтр и оценка релевантности

Размер и валюта обычно ограничивают множество документов. Совпадение по названию и описанию влияет на ранжирование. В индексах семейства Lucene распространён BM25, который учитывает, в частности, частоту терма в документе, распространённость терма в коллекции и длину поля. Часто встречающееся слово меньше помогает различать документы. Для товара точное совпадение артикула может быть важнее общих слов. Согласуй это правилами запроса. Не измеряй улучшение выдачи только уменьшением ответа в миллисекундах. Используй набор типичных запросов с ожидаемыми примерами и проверяй долю полезных результатов в первых позициях.

**Фильтры по массивам объектов.** У товара есть чёрный вариант 42 размера и белый 43. Документный поиск по двум независимым массивам «цвет» и «размер» может принять запрос «чёрный 43», хотя комбинации нет. Нужно хранить и запрашивать варианты как связанные записи или отдельные документы с понятным переходом к товару. Этот пример проверяет, что фраза «индекс содержит оба поля» не описывает сохранение связи между ними.

## Запись в БД, индексация и видимость в выдаче

Производитель сохранил карточку и outbox. Consumer применил изменение в индекс. После этого поиск ещё может не увидеть новую версию до refresh в near-real-time модели. Здесь три разных интервала: накопление outbox, обработка consumer и видимость поиску. Если метрика с API индексирования показывает успех, проверь отдельно запрос на чтение. Принудительный refresh каждой записи обычно увеличивает индексную работу. Для роли «увидеть мой новый товар» можно вернуть сохранённую карточку из команды и показать следующий шаг готовности.

При повторных и переставленных событиях индекс получает стабильный ID документа и доменную версию. Применяй изменения, которые не откатывают проекцию. Удаление должно переживать переиндексацию: если новый индекс наполнили старым snapshot, а поток tombstones не дочитан, удалённый товар появится снова. Для критичных исправлений проверь удаление как отдельную операцию на snapshot и на последующем догоне.

[Elasticsearch 8.19, момент видимости при refresh](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/near-real-time.html)

### Переиндексация при изменении анализатора

Для перехода создай новый индекс с новой схемой, загрузи версионированный snapshot, догони поток с согласованной позиции. Проверь количество документов, пропуски, удалённые записи, типы параметров и качество на наборе запросов. Затем переключи читаемое имя или alias. Пока обе версии читаются в разных местах, их выдача по одной фразе может отличаться. Откат alias возвращает старый индекс, но если он перестал получать актуальные записи, свежесть потеряется. Выбери срок, в течение которого обновления должны поддерживать обе версии, и измеряй отставание каждого writer.

### Глубокие страницы поиска

При выдаче с нескольких поисковых shard глубокий offset заставляет запрашивать больше кандидатов и объединять их. Для `search_after` нужен устойчивый sort и значения последнего результата. Чтобы индекс не менялся между страницами, в Elasticsearch можно использовать point in time согласно его правилам хранения и срока жизни. Tie-breaker важен при равном score или timestamp. Если API допускает свежую выдачу между страницами, явно оговори возможные смещения. Несколько минут работы старого контекста индекса имеют цену ресурсов, поэтому разумный TTL и пределы глубины остаются частью контракта.

[Elasticsearch 8.19, search_after и point in time](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/paginate-search-results.html)

## Самопроверка

<details>
<summary>Карточка изменилась в PostgreSQL, но поиск не показывает новое название. Какие три места проверишь?</summary>

Проверь, дошло ли намерение публикации, применил ли consumer нужную версию в индекс и появился ли документ в выдаче после refresh. Затем проверь анализатор и параметры запроса.

</details>

<details>
<summary>Почему переиндексация из snapshot могла вернуть уже удалённый товар?</summary>

Snapshot зафиксирован до удаления, а догон не обработал его до переключения. Нужна связанная позиция потока и проверка tombstone в целевой проекции.

</details>

<details>
<summary>В фильтре есть красный цвет и размер 45, а результат содержит только красный 42 и синий 45. Где ошибка модели?</summary>

Индекс подтвердил наличие двух независимых значений. Требование относится к одному варианту. Смоделируй совместное поле, вложенную запись или отдельный результат варианта и проверь эту комбинацию тестом.

</details>
