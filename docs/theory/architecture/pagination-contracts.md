# Пагинация API: устойчивый порядок, курсор и меняющиеся данные

## Что ожидает клиент

Кабинет показывает последние заказы по 20 за раз. Выданный список может обновляться, пока пользователь читает первую страницу. Важно определить, нужны ли переход на произвольный номер страницы, точное число элементов, согласованный снимок или достаточно продолжить вперёд с разумной свежестью. Разные требования дают разные расходы SQL и состояние между вызовами.

**OFFSET.** Запрос может пропустить первые 1000 подходящих строк и вернуть следующие 20. При большой глубине серверу приходится пройти пропускаемые записи. Если между двумя страницами в начале вставился заказ, последовательность сместится, и последняя строка первой страницы может повториться на второй. Если строку удалили в начале, возможен пропуск. Детерминированный `ORDER BY` нужен даже без конкурентных изменений. `ORDER BY created_at DESC` не определяет порядок при совпадении времени.

**Keyset.** Продолжение выражается «дай записи после последней уже выданной по выбранному порядку». Пусть сортировка `created_at DESC, id DESC`. Когда первая страница закончилась комбинацией `(12:00, 42)`, продолжение берёт меньшие комбинации. Новая строка выше этой границы появится при обновлении верхней страницы, но не сдвинет продолжение. Удаление прошлого элемента не мешает, потому что курсор содержит значения, а не ссылку на существующий объект.

## Вывести следующую страницу из SQL

```sql
SELECT id, created_at, status
FROM orders
WHERE tenant_id = :tenant
  AND (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT :fetch_size;
```

Предполагаются `NOT NULL` у обеих колонок сортировки и уникальный ID в нужной области. Для первой страницы предикат продолжения отсутствует. Индекс `(tenant_id, created_at DESC, id DESC)` может обеспечить поиск в подходящем порядке. `fetch_size` удобно задать на один больше размера страницы. Если получено 21 при размере 20, выдаём первые 20 и формируем курсор из двадцатого. Если взять курсор из 21-го и потом использовать строгий `<`, эта строка потеряется. При смешанных направлениях вроде `score DESC, id ASC` простое сравнение кортежей `<` не выражает нужный порядок. Используй явный предикат `score < lastScore OR (score = lastScore AND id > lastId)` и соответствующий индекс.

Избегай вычисления значения курсора из отображаемого округлённого времени. Две записи могут совпасть после округления. Сериализуй точное значение для БД по оговорённой точности. Также учитывай timezone и вид используемого timestamp. Курсор должен переносить порядок независимо от формата, выбранного клиентом для экрана.

## Курсор — часть публичного контракта

Полезно сделать токен непрозрачным для клиента. Внутри можно сохранить версию формата, последний ключ, параметры сортировки, область фильтра и срок действия. Кодирование base64 не скрывает содержимое и не проверяет подлинность. Если сервер доверяет полям токена, используй поддерживаемую проверку целостности или ссылку на состояние на стороне сервера. В любом случае повторно проверяй авторизацию, tenant и ограничения входа. Токен продолжения не удостоверяет право на просмотр.

Если клиент изменил фильтр `status=PAID` на `status=NEW`, прежняя позиция может не иметь нужного смысла. Можно привязать курсор к нормализованному запросу и попросить начать сначала при несовпадении. Поведение при истечении или смене формата сообщи стабильным кодом ошибки. Для внешнего интерфейса можно вернуть `nextCursor` или ссылку следующей страницы. Пользователю обычно не нужно вычислять `created_at` по последнему отображённому элементу.

## Конкурентные данные и снимки

Курсор на сортировке по неизменяемому ключу уменьшает пропуски из-за сдвига, но каждый HTTP-запрос читает свою версию данных. Заказ может измениться из `PAID` в `REFUNDED` и выпасть из фильтра. Если sort key изменяем, объект способен перейти через уже пройденную границу и появиться дважды или пропасть. Например, в сортировке по `updated_at` любое обновление меняет позицию. Договорись, допускается ли пользовательская лента с такими обновлениями. Для экспорта, который должен перечислить точный набор, используй snapshot или подготовительный materialized result.

**Граница по времени.** Поле `asOf` удобно ограничивает вставки с датой позже начала обхода. Оно не гарантирует единую версию всех полей, если существующие записи обновили позже или пришла запись задним числом. PostgreSQL `REPEATABLE READ` даёт согласованный снимок в одной транзакции, а удерживать одну открытую транзакцию между произвольными клиентскими HTTP-вызовами дорого. Варианты для длительных выгрузок: фоновая генерация артефакта, снапшот витрины или чтение версий в специально спроектированной модели.

### Список со связанными данными

В API нужно показать страницу заказов с позициями. SQL LIMIT должен применяться к заказам, а join размножает строки по позициям. Сначала выбери IDs страницы и курсор. Затем загрузи ограниченный набор деталей, сохрани порядок из первого запроса. Под одной транзакцией PostgreSQL Read Committed снимки двух операторов могут различаться. Если нужен общий снимок, согласуй изоляцию. Если можно показывать последние детали, обработай удалённый между фазами заказ и чётко реши, к чему относится курсор страницы.

Полный `COUNT(*)` иногда дороже самой страницы. Если UI нужен только признак следующей, достаточно дополнительной строки. Требование «показывать точно 1 645 231 совпадение для любого фильтра» имеет другую стоимость. Объясни, как влияет сложный фильтр, кеширование результатов и свежесть counts. Для Spring Data при выборе Page, Slice или скроллинга смотри, нужны ли метаданные общего количества и какой порядок поддерживается.

## Самопроверка

<details>
<summary>Курсор сделали только из created_at. Почему пропали заказы с одной секундой времени?</summary>

Метка времени не уникальна. Строгая граница исключила оставшиеся совпадающие строки. Добавь tie-breaker, используй оба значения в запросе и храни точную отметку времени.

</details>

<details>
<summary>Как проверить выдачу с fetchSize = pageSize + 1?</summary>

Проверь набор ровно из 20, из 21 и повтор одинакового времени. Для 21 выдаётся 20, курсор строится по последней выданной, следующая страница включает спрятанную строку.

</details>

<details>
<summary>Клиент просит выгрузить все заказы с неизменным результатом при каждом продолжении через сутки. Хватит keyset?</summary>

Keyset фиксирует позицию, но обычные страницы читают текущую БД. Нужен отдельный стабильный снимок или артефакт с правилами хранения и доступа.

</details>
