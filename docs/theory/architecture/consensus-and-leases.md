## Что именно должны согласовать узлы

Три копии хранят состояние каталога. Одна приняла цену 100, другая во время сетевого разделения приняла 110. Само копирование не отвечает, какую цену увидит следующий клиент и можно ли было обещать успех обеим записям. Один способ согласования — договориться о порядке изменений и применить одинаковые команды к одинаковому исходному состоянию. Для этого используют реплицированный журнал и протокол консенсуса, например Raft.

**Консенсус** нужен для выбора согласованного значения или последовательности команд при заданной модели отказов. **Репликация** переносит состояние между копиями. **Лидер** может координировать текущие операции. **Fencing** защищает общий ресурс от действий владельца, полномочия которого уже сменились. Эти понятия встречаются вместе, но отвечают на разные вопросы. Например, объектное хранилище может копировать файлы, а право обновить указатель версии определяется отдельным механизмом.

### Три момента записи в Raft

1. Лидер принимает команду и добавляет запись в локальный log.
2. Лидер реплицирует запись. При выполнении условия протокола она становится committed.
3. Узлы применяют зафиксированные записи к машине состояний в согласованном порядке.

У записи есть index и term. Term может изменяться при выборе лидера. Для зафиксированных записей протокол обеспечивает сохранение в дальнейшей истории. Незафиксированный хвост может быть исправлен новым лидером. Поэтому «вижу запись в файле одного узла» ещё не означает, что её нельзя потерять. В Raft правило продвижения commit index при репликации большинства учитывает term записи. Запись предыдущего term не объявляют committed только потому, что текущий лидер в данный момент видит её на большинстве. Commit записи текущего term также фиксирует соответствующий предшествующий префикс.

**Пример.** Из пяти узлов осталось доступно три. Они способны выбрать лидера при выполнении условий и обслуживать запись большинством. Два изолированных узла не могут переизбрать законного лидера для подтверждённого прогресса. Если из трёх доступных один тоже пропал, запись ждёт восстановления большинства. Такой отказ сохраняет согласованность при crash/network модели, ради которой протокол спроектирован. Протокол обычного Raft не рассчитан на произвольное злонамеренное поведение участника.

### Почему два большинства пересекаются

При N=5 любое большинство содержит минимум три узла. Два множества по три обязательно имеют хотя бы один общий узел. Это позволяет увязать новый выбор с прошлым состоянием, но пересечение само по себе не доказывает корректность реализации. Raft использует правило голосования: кандидат должен иметь достаточно свежий журнал, а узел голосует по правилам term. Плюс проверяются согласованность префиксов и порядок применения записей. Без этих правил узел из пересечения мог бы проголосовать за журнал, потерявший важное обновление.

**Чтение у лидера.** Клиент может выбрать узел, который ещё считает себя лидером после изоляции. Он способен вернуть локальное состояние до записи у нового лидера. Для линейризуемого чтения нужна проверка полномочий текущего лидера и того, что локальная машина состояний применена до правильной позиции, либо другой поддерживаемый механизм чтения. В реализации могут использовать ReadIndex или lease с предположениями о времени. Чтение отстающей копии допустимо только с контрактом соответствующей свежести. На собеседовании объясни, какую именно гарантию предлагает выбранный API, а не просто произнеси слово leader.

### Snapshot журнала и восстановление

Когда журнал растёт, узел может сохранить компактное состояние машины с привязкой к последней включённой позиции и term. После этого старый префикс можно удалить по протоколу. Узел, который слишком отстал, получит snapshot вместо всего исходного журнала, затем применит свежий хвост. Для детерминированной машины состояний команда «установи время записи» должна включать согласованное значение времени. Если каждый узел вызовет свои часы при применении, результаты разойдутся. Аналогично со случайными числами и внешним I/O.

Внешний эффект тоже требует границы. Применение одной команды на пяти узлах не должно пять раз отправить письмо. Машина состояний может записать намерение, а отдельный исполнитель выполнит его по ID с идемпотентностью. Рассмотри, что происходит после перезапуска лидера, когда внешний вызов завершился, но отметка об успехе ещё не сохранена.

## Почему R + W > N ещё надо объяснить

В модели реплик читающий ждёт R ответов, пишущий ждёт W. Если обе операции работают на одной фиксированной группе N, то при `R + W > N` множества должны пересечься. Чтобы вернуть свежайший результат, reader должен уметь определить подходящую версию, а write и read должны соблюдать правила сравнения и опубликованного состояния. При конкурирующих writers версии могут быть несравнимы, и пересечение не отвечает, как разрешить конфликт.

В Dynamo описан sloppy quorum: при недоступности ожидаемой копии запрос может использовать другой узел из более широкого выбора, а hinted handoff позже доставит запись на нужный узел. При этом простой расчёт пересечения по фиксированному N уже не переносится напрямую. Практические гарантии определяет конкретная реализация. Интервьюеру можно предложить пример сетевого разделения и показать, какие три ответа выберет каждая операция.

**Сравни два контракта.** Корзина интернет-магазина иногда допускает объединение независимых добавлений. Тогда выбрать и показать набор sibling-версий с последующим merge приемлемо. Для распределённого ограничения «у пользователя одно действующее платное право» одновременное подтверждение двух несовместимых операций опасно. Там нужна точка сериализации, например владелец записи с условной транзакцией. Грань проводят по конкретному инварианту, а не по маркетинговому типу СУБД.

[DeCandia и соавторы, Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)

## Аренда и fencing

Внешний worker получает lease на выполнение задачи. Lease истекает через 10 секунд, если worker не продлил его. Процесс A получил аренду, после долгой паузы JVM потерял связь, и её получил B. Когда A возобновился, в его памяти может остаться убеждение, что он всё ещё владелец. Проверка перед началом работы не защищает запись после паузы. Это применимо к GC, заморозке контейнера и сетевому разделению.

**Fencing token** — монотонно увеличивающийся номер владения, который принимает защищаемый ресурс. A получил 41, B получил 42. После появления 42 ресурс отклоняет запросы со старым 41. Проверка должна быть атомарной вместе с действием в хранилище. Например, запись может разрешать работу только для ожидаемого текущего `lock_version`. Простой случайный токен помогает условно снять собственную аренду, но сам по себе не выражает порядок смены полномочий для внешнего writer.

Представь, что B ещё не отправил ни одной записи в защищаемый ресурс. Если ресурс видел только 41, ему неизвестен новый владелец. Граница fencing зависит от протокола регистрации нового поколения и того, кто проверяет полномочия при операции. Правильно сформулированная гарантия начинается с конкретного механизма. Например, таблица задач сама хранит token, выдаёт следующее значение при перезахвате и проверяет его в UPDATE. Если ресурс — внешний платёжный API без такой проверки, номер lease сам его не защитит. Обращение делай через стабильный idempotency key или другой поддерживаемый контракт.

### Аренда для отложенной обработки

Relay Outbox может получить строку на аренду, отправить сообщение и затем выполнить `UPDATE ... WHERE id = ? AND lease_version = ?`. Старая копия после перезахвата не пометит результат нового владельца. Но брокер по-прежнему может принять два сообщения, если старая копия отправила свою запись с просроченной арендой. Fencing UPDATE защищает состояние строки. Идемпотентный consumer защищает итог. Проговори обе границы.

**ETA восстановления.** Если время аренды 60 с, зависшая работа может ожидать не меньше оставшегося времени аренды. Слишком малая аренда создаёт лишнее конкурентное исполнение на редких длинных задачах. Следи за возрастом ready, lease expirations и успешным процентом продлений. Для длинной задачи при потере аренды код может пытаться отменить работу, но безопасность итогового эффекта должна сохраняться даже при пропущенной отмене.

## Самопроверка

<details>
<summary>Лидер записал команду локально и пропал до отправки большинству. Что может увидеть клиент?</summary>

Команда могла не стать committed и может исчезнуть из авторитетной истории. Клиенту нужен способ повторить или проверить исход операции с прежним ID, если ответ не был получен.

</details>

<details>
<summary>Почему один узел в пересечении двух кворумов сам по себе не гарантирует свежесть прочитанного значения?</summary>

Нужно, чтобы он хранил нужную зафиксированную версию, а протокол правильно выбирал и принимал её. Конкуренция writers, меняющийся состав группы и особые режимы чтения влияют на результат.

</details>

<details>
<summary>Worker продлевает аренду каждые две секунды. Что произойдёт после минутной остановки JVM?</summary>

Другой worker мог получить полномочия. Старый может продолжить после паузы. Защищаемый ресурс должен проверять актуальную версию владения, а повтор внешнего эффекта требует независимой защиты.

</details>
