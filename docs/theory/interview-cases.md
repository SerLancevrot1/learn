# Сквозные разборы для собеседования по Java-бэкенду

[Конспекты](README.md) · [Банк вопросов и пробные сессии](../../INTERVIEW.md)

На интервью один инцидент часто затрагивает несколько тем. В этих разборах начни с наблюдаемого результата, объясни механизм, затем предложи измерение. После ответа прочитай разбор и поменяй одно условие. Например, перенеси точку сбоя с «перед commit» на «после commit» и объясни отличие своими словами.

## Java и SQL: перенос I/O не изменил SQL-бюджет

Сервис отображает список последних заказов. После перехода на виртуальные потоки CPU умеренный, число активных запросов удвоилось, p99 вырос. Логи JDBC показывают много запросов по одному клиенту. Новый разработчик предлагает ещё увеличить пул.

<details>
<summary>Почему стало медленнее и что измерять?</summary>

Виртуальные потоки позволили большему числу запросов одновременно ждать. Это могло поднять нагрузку на прежнее узкое место. У одного HTTP-ответа возможно несколько десятков SELECT, если сериализация трогает ленивые связи. Каждый отдельный SQL будет быстрым, а путь целиком увеличится из-за числа round-trip и ожидания соединения.

Сначала сравни число SQL при 1 и 30 заказах при том же сценарии. Смотри число ожидающих JDBC-ресурс и время реального SQL отдельно. Если связано с N+1, выбери проекцию или ограниченную загрузку графа. Измерь общий объём строк: join двух коллекций может заменить множество запросов большим произведением. Проверь, что порядок страницы и количество уникальных заказов сохранились. Только после сокращения лишней работы оцени, есть ли свободный бюджет для увеличения параллельности.

**Измени условие.** Число SQL осталось прежним, зато `pg_stat_activity` показывает ожидание одной долгой транзакции. Теперь искать N+1 в качестве главной причины слабее. Найди блокирующий запрос, время жизни его транзакции и источник. Увеличение пула в этом случае может добавить только ожидающих.

## Корректность и метрики: обработчик стал быстрее, результат устарел

Потребитель Kafka писал статусы в таблицу по одному. После оптимизации пачки p95 handler уменьшился вдвое, но пользователи периодически видят, как оплаченные заказы снова становятся новыми. Во внутренних сообщениях есть `eventId`, `orderId` и `version`.

<details>
<summary>Что могло нарушиться, хотя обработка формально стала быстрее?</summary>

В пачке или между worker события одного заказа могли завершаться не в порядке получения. Старое событие применилось после новой версии и перезаписало результат. Сравни список фактических версий в SQL и порядок действия обработчиков. Если каждое событие несёт полный снимок, можно выполнять условное обновление только при более высокой версии. Для дельт пропуск позднего события по версии способен потерять отдельный эффект, поэтому им нужны порядок или иной способ восстановления. Дедупликация по `eventId` защищает от повтора того же входа, но разные корректные события имеют разные ID даже при нарушенном порядке.

Проверь ещё и offset. Если работа 42 завершилась, а 41 ещё нет, фиксация следующей позиции 43 пропустит 41 после перезапуска. Измеряй не только handler latency, но и возраст элемента до бизнес-фиксации, а также число отклонённых устаревших обновлений. Дай тесту точку, которая удержит одну запись и отпустит следующую вперёд.

**Измени условие.** Новый статус корректный, а пользователь через секунду видит старый из другой реплики. Тогда проблема может быть в чтении с отставанием, а не в записи consumer. Сравни фактические версии по маршрутам и определи требование read-your-writes.

</details>

## Выкатка и сеть: Healthy не означает готовность всего пути

Деплой заменил сертификат клиента платежей. Новые pod успешно проходят readiness, `GET /actuator/health` зелёный. Через gateway доля 504 постепенно растёт. Заказ, который получил 504, всё же иногда появился в базе.

<details>
<summary>Как разделить маршрут, TLS и бизнес-эффект?</summary>

Найди, кто выдал 504. Прокси мог закончить ожидание раньше, чем приложение завершило транзакцию. Проверь трассу в сервисе и участок исходящего вызова к провайдеру. Readiness проверяет выбранное правило приложения, а не каждый используемый downstream. Новые копии открывают свежие соединения и первыми обнаруживают ошибку нового сертификата или trust bundle; старые копии могут переиспользовать открытые соединения. Раздели графики по версии и фазе, проверь успешность отдельного нового соединения и ошибку доверия на стороне проверяющего компонента.

Заказ проверяй по стабильному ключу предыдущей команды. Если API вернул 504 до ответа, оно не обязательно откатило запись. Клиент с тем же ключом должен увидеть прежний результат или состояние в ожидании. Повтор с новым ключом может создать второй заказ. При расследовании сверь, что фиксация результата и ключа происходят на одной границе.

**Измени условие.** TLS до провайдера проходит, но ошибок больше только у одной версии клиента. Проверь сеть, сроки ожидания и формат ответа, затем отдели проблему handshake от HTTP-авторизации и превышения дедлайна.

</details>

## Как повторять разборы

Дай себе 90 секунд на первоначальный ответ. Он должен назвать гарантию, объяснить причину наблюдения и предложить следующий измеримый шаг. После чтения повтори ответ без текста на изменённом условии. На следующий день восстанови его с пустого листа. Через несколько дней возьми соседний сценарий и сравни, в каком месте меняется граница ответственности. Ошибку формулируй конкретно, например «принял commit offset за commit БД», чтобы на следующем повторе проверить именно эту часть.
