# Camunda 7 и Camunda 8

[BPMN и Camunda](README.md) · [Зачем нужен BPMN-движок](bpmn.md) · [Вопросы для собеседования](../../interview/base/bpmn.md) · [Лабораторная](../../labs/camunda/README.md)

## Ответ за минуту

В **Camunda 8** движок **Zeebe** хранит прогресс процесса. Дошёл до «зарезервировать товар» — создал задание. **Job worker** (обработчик) забрал его по типу, вызвал склад и отправил `complete`. После подтверждения Zeebe ведёт процесс дальше. Если склад успел создать резерв, а worker пропал до `complete`, движок может выдать то же задание снова. Склад должен узнать тот же `reservationId` и оставить один резерв. [Job workers в Camunda 8](https://docs.camunda.io/docs/8.9/components/concepts/job-workers/)

## Из чего состоит Camunda 8

| Часть | Роль | Пример |
|---|---|---|
| Modeler | Редактор BPMN, DMN и форм | Описать ожидание оплаты и таймер |
| Zeebe Gateway | Принимает команды клиентов и направляет их брокерам | Деплой, старт, публикация сообщения, подтверждение задания |
| Zeebe Broker | Исполняет модель и хранит состояние. Партиции распределяют нагрузку, репликация защищает от потери отдельного узла при доступном кворуме | Зафиксировать, что заказ переходит на ожидание оплаты |
| Job worker | Клиент Zeebe, которому поручена прикладная операция | Java-сервис вызывает API склада. В Spring можно объявить обработчик через `@JobWorker` |
| Exporter и вторичное хранилище | Асинхронно выгружают состояние для запросов и интерфейсов | Operate покажет последнее действие с небольшой задержкой |
| Operate / Tasklist | Диагностика процессов / работа с ручными задачами | Разобрать incident / согласовать заявку |
| Connectors / Optimize | Типовые интеграции / аналитика процессов | Вызвать HTTP API стандартным коннектором / измерить время обработки по стадиям |

Zeebe записывает изменения в журнал партиции, а локальное состояние хранит в RocksDB. Начиная с Camunda 8.9 для вторичного хранилища есть поддерживаемые реляционные варианты наряду с Elasticsearch и OpenSearch. Поэтому при ответе уточни версию, когда говоришь про хранилище, клиент или доступные BPMN-элементы. [Архитектура Zeebe](https://docs.camunda.io/docs/components/zeebe/technical-concepts/architecture/) · [Вторичное хранилище в 8.9](https://docs.camunda.io/docs/8.9/reference/announcements-release-notes/890/whats-new-in-89/) · [Spring Boot Starter](https://docs.camunda.io/docs/8.9/apis-tools/camunda-spring-boot-starter/getting-started/)

## Что делать с результатом job

| Ситуация | Действие | Что увидим |
|---|---|---|
| Склад подтвердил резерв | `complete` и при необходимости переменные результата | Движок продолжает процесс |
| У склада 503, есть шанс восстановиться | `fail` с оставшимися попытками и задержкой перед повтором | Шаг ждёт повторного выполнения. При нуле попыток появится incident |
| Склад ответил «нет товара», в схеме есть такой исход | `throw error` с BPMN-кодом `OUT_OF_STOCK` | Граничное Error Event перехватывает код и переводит процесс на ветку отказа |
| Worker исчез после получения job | Истекает таймаут активации | Job доступна для повторной выдачи. Остаток попыток от самого таймаута сохраняется |
| Клиент ждёт callback слишком долго | BPMN Timer через Event-based Gateway или на границе задачи | Запускается видимая бизнес-ветка, например снятие резерва |

**Три разных таймаута.** Таймаут HTTP-вызова определяет время ожидания склада. Таймаут активации определяет время выдачи job конкретному worker. Таймер BPMN управляет ходом процесса, например даёт клиенту 15 минут на оплату. Отдельно существует `requestTimeout` при активации job — сколько запрос к Zeebe ждёт появления работы. [Job workers](https://docs.camunda.io/docs/8.9/components/concepts/job-workers/) · [BPMN Error Event](https://docs.camunda.io/docs/8.9/components/modeler/bpmn/error-events/) · [Таймеры BPMN](https://docs.camunda.io/docs/8.9/components/modeler/bpmn/timer-events/)

**Incident** — состояние, в котором конкретный шаг застрял и требует вмешательства. Причины включают нулевой остаток попыток, некорректное выражение или BPMN-ошибку без обработчика. Для job с нулём попыток исправь причину, добавь попытку и разреши incident. Если тип задания больше никто не обрабатывает, job может ждать без incident. [Инциденты в Camunda 8](https://docs.camunda.io/docs/8.9/components/concepts/incidents/)

### Где появляется повтор и как его пережить

1. Worker получил job «создай резерв `R-42`».
2. Склад уже сохранил `R-42`. Соединение оборвалось до того, как Zeebe принял `complete`.
3. По таймауту Zeebe выдаёт job ещё раз. Первый worker всё ещё может работать, если он завис и затем отмер.
4. Склад получает тот же `R-42`. Уникальный ключ и транзакция с изменением остатка дают один эффект. При повторе склад возвращает ранее сохранённый результат. Если с тем же ключом пришло другое количество, склад сообщает о конфликте.

Это **at-least-once** для доставки job. У бизнес-действия свой стабильный ID. Например, `orderId + reservationAttemptId` различает повтор одной операции и новое резервирование того же заказа. `jobKey` пригодится для диагностики конкретной job, а бизнес-ключ переживает также повторный запуск процесса. У внешнего платёжного API ищи поддержку idempotency key и запроса состояния операции после неоднозначного таймаута. [Как писать идемпотентные workers](https://docs.camunda.io/docs/8.9/components/best-practices/development/writing-good-workers/)

### Что писать в Spring Boot

На Service Task поставь тип `reserve-stock`. В приложении объяви метод с `@JobWorker(type = "reserve-stock")` и получи `orderId` как `@Variable(name = "orderId")`. Метод вызывает сервис склада, который фиксирует резерв, и возвращает небольшой результат, например `reservationId`. По умолчанию starter сам отправляет `complete` после успешного синхронного возврата из метода. Если отправляешь `complete` сам, например из callback, установи `autoComplete = false`. Сверь версию starter с версией Spring Boot. [Настройки worker](https://docs.camunda.io/docs/8.9/apis-tools/camunda-spring-boot-starter/configuration/) · [Таблица совместимости](https://docs.camunda.io/docs/8.9/apis-tools/camunda-spring-boot-starter/getting-started/)

### Saga и компенсации

Резервирование, списание и отправка фиксируются в разных системах. Если отправка невозможна, запускаются отдельные операции «вернуть деньги» и «снять резерв». Каждая может повториться или закончиться incident. Задай ключ идемпотентности и этим шагам. Если порядок важен, задай его явно. Camunda 8 поддерживает BPMN compensation events. Обычные Service Task на отдельной ветке тоже подходят, когда их хочется увидеть в маршруте, как в лабораторной со снятием резерва по таймеру. [Компенсация в Camunda 8](https://docs.camunda.io/docs/8.9/components/modeler/bpmn/compensation-events/) · [Saga и доставка событий](../architecture/service-architecture.md)

## Сообщения и переменные

- **Корреляция** связывает внешнее сообщение с ожиданием. Для заказа `A-42` модель открывает подписку на `PaymentReceived` с ключом `A-42`. Событие с таким же именем и ключом продолжит процесс. Стабильный ключ должен однозначно определять ожидающий экземпляр в выбранной модели.
- **TTL** определяет, сколько живёт раннее сообщение в буфере. При TTL 0 и отсутствии подходящей подписки опубликованное сообщение отбрасывается. Положительный TTL помогает пережить гонку «callback пришёл раньше ожидания». Успех публикации сам по себе означает приём сообщения, а результат корреляции можно проверять отдельно.
- **`messageId`** позволяет отсеивать дубликаты в рамках буфера при совпадении имени, ключа и ID. Для долговременной дедупликации входящего события используй прикладной ID и, где нужно, Inbox. Ключ экземпляра процесса, ключ корреляции и ID сообщения решают разные задачи.
- **Переменные** — JSON-данные экземпляра или локальной области. Храни идентификаторы и небольшие результаты для маршрута. Input mapping готовит вход для шага, output mapping выбирает, что уйдёт наружу. В параллельных ветках раскладывай результаты по разным переменным или используй локальную область, чтобы ветки случайно не перезаписывали друг друга.

[Сообщения](https://docs.camunda.io/docs/8.9/components/concepts/messages/) · [Переменные](https://docs.camunda.io/docs/8.9/components/concepts/variables/) · [Что экспортируется в хранилище](https://docs.camunda.io/docs/8.9/components/best-practices/architecture/data-flow/)

## Что меняется между Camunda 7 и 8

| Вопрос | Camunda 7 | Camunda 8 |
|---|---|---|
| Где движок | Java-библиотека в приложении или отдельный сервер | Zeebe работает как отдельный runtime. Приложение подключается по API |
| Как выполняется Service Task | `JavaDelegate`/expression в JVM либо External Task. External worker забирает по topic и блокирует на время через `fetchAndLock` | Job workers забирают задания по job type и подтверждают их через API |
| Где проходит транзакция | Синхронные шаги до ближайшего состояния ожидания могут пройти в одной транзакции. Встроенный движок может делить транзакцию с приложением при общей настройке менеджера транзакций и БД | Работа worker и подтверждение job идут через API. Запись склада и `complete` фиксируются независимо |
| Что дают `asyncBefore` / `asyncAfter` | Границу транзакции и продолжение через Job Executor до/после шага соответственно | Сервисная задача уже создаёт job для worker. Семантику старых транзакционных границ перепроверяют при переносе |
| Данные и выражения | Реляционная БД движка, в BPMN часто встречается JUEL `${...}` | Журнал и состояние Zeebe, вторичная проекция для чтения, в BPMN условия FEEL `= ...` |
| Интерфейсы и интеграция | Cockpit, Tasklist, Java API, `/engine-rest` | Operate, Tasklist, Camunda Java Client и Spring Boot Starter, REST `/v2` и gRPC |

Пример Camunda 7. Если встроенный процесс в одной транзакции дошёл до делегата и тот упал, выполнение текущей транзакции откатывается. С `asyncBefore` прогресс до задачи уже сохранён, задачу выполняет Job Executor с повтором. Успешный внешний HTTP-вызов от отката транзакции не отменится. При переходе на 8 проверь такие границы, конвертируй JUEL и делегаты, сопоставь `businessKey` с новой системой идентификаторов, проверь формы и маршруты ошибок, выбери подход для активных экземпляров. [Транзакции Camunda 7](https://docs.camunda.org/manual/7.24/user-guide/process-engine/transactions-in-processes/) · [External Tasks](https://docs.camunda.org/manual/7.24/user-guide/process-engine/external-tasks/) · [Различия и миграция](https://docs.camunda.io/docs/guides/migrating-from-camunda-7/conceptual-differences/)

## Версии, эксплуатация и тесты

- **Деплой v2.** Запущенный экземпляр продолжает на своей версии. Старт по ID без версии обычно берёт последнюю активную версию. Некоторые клиенты закрепляют конкретный ключ определения. Старым моделям могут ещё требоваться их типы job и форматы входа, поэтому держи совместимые workers до завершения или миграции активных экземпляров. Миграция требует проверить сопоставление активных элементов, переменные и подписки. [Версии](https://docs.camunda.io/docs/8.9/components/best-practices/operations/versioning-process-definitions/) · [Миграция экземпляра](https://docs.camunda.io/docs/8.9/components/concepts/process-instance-migration/)
- **Зависший заказ.** В Operate найди экземпляр по ключу, активный узел, версию и incident. На Service Task проверь тип, активность worker, количество незабранных job, задержку, лимит одновременных job и здоровье зависимости. На сообщении проверь имя, ключ и время доставки. При задержке UI проверь экспорт. Сопоставляй логи по `processInstanceKey`, `jobKey` и `orderId`. [Operate](https://docs.camunda.io/docs/8.9/components/operate/operate-introduction/)
- **Границы тестов.** Unit-тест worker проверяет прикладные ветки, отдельный тест с БД — один эффект при повторе. Тест процесса с реальным движком проверяет маршрут, событие, дедлайн и восстановление. В Java для этого есть Camunda Process Test с Testcontainers или внешним runtime. В лабораторной команды REST видны напрямую, а ожидание асинхронной истории ограничено таймаутом. [Camunda Process Test](https://docs.camunda.io/docs/8.9/apis-tools/testing/getting-started/)
- **SaaS и Self-Managed.** SaaS снимает с команды обслуживание кластера. Self-Managed даёт контроль над размещением и данными, а команда отвечает за доступность, обновления, резервное копирование и восстановление. Проверь условия производственной лицензии для выбранной редакции. [Лицензирование Camunda 8](https://docs.camunda.io/docs/8.9/reference/licenses/)
