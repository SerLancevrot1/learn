# Долгоживущие процессы: сообщения, таймеры и восстановление заданий

[BPMN и Camunda](README.md) · [Camunda 7 и 8](camunda.md) · [Резервирование ресурсов](../architecture/cases/reservations.md)

## Состояние владельца и состояние маршрута

Процесс заказа вызвал склад, получил резерв, ждёт оплату. Движок хранит, какая ветка активна, где таймер и кто должен выполнить следующую задачу. Склад хранит факт резерва и защищает количество товара. Платёжный сервис хранит фактический исход платежа. Активный шаг «ждём оплаты» не доказывает, что провайдер ещё не списал деньги: сообщение может отставать. При восстановлении сначала узнай состояние владельца по устойчивому ID.

Используй переменные для данных маршрута и минимальных ссылок. Если хранить в процессе полный JSON заказа со всеми документами, каждая версия схемы, история и экспорт требуют больше памяти и срока хранения. Переменные могут попасть в UI оператора или историю, где действуют свои правила доступа. Для обновляемого объекта достаточно ID и информации, необходимой текущему решению. Snapshot-решения, например курс на момент одобрения, сохраняются с явно обозначенной версией.

### Разложи исключения на бизнес и технику

| Ситуация | Типичный шаг процесса |
| --- | --- |
| Склад проверил остаток и отказал | Выбрать ветку предметного отказа |
| HTTP склада вернул временную ошибку | Повторить job с backoff в пределах политики |
| У задания неизвестный тип продукта из-за несовместимого релиза | Остановить экземпляр для исправления данных или worker |
| Оплата могла пройти, но ответ потерян | Оставить состояние неизвестного исхода и запустить сверку |

Business error уместна, когда отказ предусмотрен BPMN и нужно выбрать его ветку. Техническое исключение может исчерпать попытки и создать incident. Если каждую бизнес-проверку превращать в retry, нагрузка растёт без шанса на успех. Если техническую ошибку выдавать как «склад пуст», пользователь увидит неверный факт. Классификацию зафиксируй в контрактах наблюдения и обработчика.

## Повтор job при зависимости от внешнего API

Camunda 8 выдала worker job на возврат с timeout 30 секунд. Worker получил успешный ответ провайдера, но не успел подтвердить completion. После deadline движок может активировать job снова, даже если первый worker ещё работает. Timeout позволяет возобновить работу. Внешний вызов имеет свой жизненный цикл.

1. При первом старте возьми стабильный ID бизнес-попытки, например `refundId` и размер операции.
2. Используй этот ID при записи состояния и обращении к провайдеру по его контракту.
3. После получения результата сохрани фактический исход или возможность сверки. Затем заверши job.
4. При повторной активации проверь уже имеющийся результат. Если исход неизвестен, сверяй по прежнему ключу.

Job key помогает адресовать действие движку. Доменный ID выражает эффект, который должен пережить новое определение процесса, повторный старт или ручное решение. Для одного экземпляра процесса может быть несколько законных возвратов. Дедупликация по orderId пропустит новые возвраты. Если один возврат случайно запустил два экземпляра, дедупликация только по ID экземпляра пропустит оба денежных эффекта.

Размер batch активации, число worker и deadline определяют, сколько jobs будет одновременно начато. Если worker активирует сто задач на локальную очередь, но может выполнять десять, часть дождётся истечения срока ещё до старта. Ограничь число активированных jobs по фактической ёмкости зависимости. Измеряй queue age, время обработки и число повторных активаций. Продление timeout помогает управлять длительным ожиданием, но перезахват при сбое всё равно возможен.

[Camunda 8, job workers и timeout](https://docs.camunda.io/docs/components/concepts/job-workers/) · [Camunda 8, incidents](https://docs.camunda.io/docs/components/concepts/incidents/)

## Сообщение пришло до открытия подписки

Обработчик отправил запрос платёжной системе, она ответила мгновенно. Процесс ещё выполняет предыдущий шаг и не открыл catch event. Если сообщение без буфера, корреляция может не найти ожидающего экземпляра. При публикации Camunda 8 позволяет дать TTL, чтобы движок удержал сообщение до появления подписки согласно правилам корреляции. Если TTL не покрывает задержку, ожидание всё равно может зависнуть. Для важных результатов храни факт у владельца и предусмотренный механизм сверки.

**Ключ корреляции отвечает на вопрос «какое ожидание?».** Для платежа это может быть attemptId, а для возврата refundId. Использование только orderId опасно при повторной попытке и нескольких однотипных событиях. У сообщения есть имя, correlation key и при необходимости message ID. Дедупликация публикации движком действует в рамках его правил и окна. Обработчик бизнес-эффектов проверяет свой ID отдельно.

Путь «сначала открыть ожидание, затем отправить команду» уменьшает окно раннего callback, если механизм модели это позволяет. Команда требует сохраняемого намерения на случай сбоя между шагами. Гарантия строится вместе с producer и владельцем факта. Случайная пауза не задаёт устойчивого порядка.

[Camunda 8, буферизация и корреляция сообщений](https://docs.camunda.io/docs/components/concepts/messages/)

## Таймер и сообщение претендуют на один исход

Представь event-based gateway «оплата пришла» или «прошло пятнадцать минут». Модель выбирает, какой триггер сработал. Платёж мог завершиться у провайдера чуть раньше срока, а callback прийти позже. Порядок получения сигналов движком сам по себе не определяет денежный факт. Договорись, что означает срок. Например, по истечении снимаешь резерв, позднюю успешную оплату выявляет сверка и отправляет возврат по отдельному сценарию.

Таймер в BPMN делает работу доступной к указанному моменту при работающем движке. Он может исполниться позже под нагрузкой или после восстановления. Различай business deadline и время технического срабатывания. Если контракт требует результат пользователю за 30 секунд, установка timer на 30 секунд сама по себе SLO не обеспечивает. Измеряй разницу между scheduled и actual. Критичный deadline проверяй в доменном сервисе.

Некоторые boundary events прерывают активность, другие открывают параллельное продолжение. Напоминание сотруднику может быть непрерывающим, эскалация с отменой ожидания — прерывающей. Посмотри, какие jobs ещё выполняются во внешних системах. Прерывание маршрута не отзывает выполненный JDBC commit и не отменяет произвольную внешнюю команду. Компенсация должна оперировать ссылкой на конкретный эффект и переживать повторы.

[Camunda 8, timer events](https://docs.camunda.io/docs/components/modeler/bpmn/timer-events/) · [Camunda 8, compensation events](https://docs.camunda.io/docs/components/modeler/bpmn/compensation-events/)

## Версия процесса и уже работающие экземпляры

В версии 1 после скоринга работа ждёт согласование A. В версии 2 добавлен шаг проверки лимита и изменены сообщения. Новый деплой задаёт новую версию определения. Экземпляры старой версии продолжают жить по своему маршруту, пока не завершатся или не будут перенесены поддерживаемым способом. Worker должен понимать job старого типа, пока они существуют. Если убрали handler для job v1, старый процесс может пережить деплой и начать копить ошибки через неделю.

Для миграции экземпляра проверь поддерживаемые отображения активных элементов и ожиданий, а также признак, что шаг уже имел эффект. Переместить токен на новый шаг не означает подготовить отсутствующую переменную или повторить прежнее действие. Проверь на копии данных несколько маршрутов: уже оплачен, ещё ждёт, параллельные ветки, incident. Выбери, какие состояния можно оставить до завершения, а какие нуждаются в ручной корректировке или новом процессе.

[Camunda 8, ограничения миграции экземпляров](https://docs.camunda.io/docs/components/concepts/process-instance-migration/)

## Самопроверка

<details>
<summary>Job подтвердили у внешней системы, но Operate показывает повтор. Почему?</summary>

Внешний эффект и completion движка — разные записи. Работа может активироваться снова. Проверяй исход по бизнес-ID и отправляй completion по правилам текущей активации.

</details>

<details>
<summary>Таймер снял резерв, затем пришла оплата. Почему не вернуть процесс к прежнему узлу?</summary>

Ресурс уже мог перейти другому клиенту. Владелец определяет новый допустимый переход. Позднюю оплату сверь и компенсируй по контракту, сохранив аудит.

</details>

<details>
<summary>Новые экземпляры работают. Как проверить, что деплой безопасен для старых?</summary>

Найди ещё активные экземпляры старых версий, их типы job и открытые ожидания. Запусти пути, которые они выполнят позже, и проверь совместимость worker и сообщений.

</details>
