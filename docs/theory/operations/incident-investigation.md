# Диагностика Java-сервиса: от пользовательского симптома к причине

[Эксплуатация](README.md) · [Метрики и трассировки](observability.md) · [JVM и JFR](../java/jvm.md)

## Сначала измерь ущерб

Поступила жалоба «оформление заказа тормозит». Дежурному нужно установить путь, период, регионы и версии приложения. Выполни диагностический запрос из сопоставимой точки сети, посмотри latency и успешность именно целевой операции. Раздельно считай принятие команды и завершение бизнес-результата. API может вернуть 202 за 30 мс, а заказ после этого ждать час. Для такого процесса хорошая метрика — доля принятых операций, завершившихся за ожидаемый срок, а не только HTTP p95.

На время инцидента зафиксируй выбранную шкалу времени и начальную гипотезу. Отметь момент выкатки, изменение трафика и включение фоновой задачи. Корреляция по времени даёт направление, но совпадение события с падением ещё не доказывает причину. Например, HPA мог увеличиться потому, что сервис уже перегружен. После действия сравни показатели на том же классе трафика. Для rollback длительного процесса уточни совместимость данных.

## Случай 1: p99 вырос, среднее почти прежнее

У checkout на 1% запросов задержка более секунды, другие заканчиваются быстро. Среднее скрывает хвост. Найди метрику по route, статусу и версии. Если в labels положить каждый `orderId`, число временных рядов быстро вырастет. Используй ограниченный набор route templates и устойчивые категории статусов, конкретный ID сохраняй в журнале или трассе.

### Агрегировать счётчики, потом вычислять долю

Предположим, Micrometer экспортирует классическую гистограмму с бакетом 300 мс. Требуется доля запросов на checkout, уложившихся в порог. Пример с условными именами:

```promql
sum(rate(http_request_duration_seconds_bucket{route="/checkout",le="0.3"}[5m]))
/
sum(rate(http_request_duration_seconds_count{route="/checkout"}[5m]))
```

Этот вариант считает долю быстрых среди всех измеренных ответов. Если good event одновременно обязан быть успешным, добавь подходящий label-фильтр к числителю. В знаменателе сохраняй все события, которые учитываются SLO. Если трафика нет, отношение может стать NaN; это отдельное состояние, а не свидетельство 100% успеха. Набор labels должен совпадать с реальной конфигурацией метрик.

Для p99 по классическим histogram складывай rate соответствующих bucket с сохранением `le`, потом вызывай `histogram_quantile`. Квантили разных pod не складываются и не усредняются для получения квантили общего трафика. Если две версии имеют разные границы bucket, сведение классических гистограмм может перестать корректно описывать общий профиль. Для жёсткого SLO удобно заранее иметь бакет точно на его границе и считать долю напрямую.

[Prometheus, применение гистограмм](https://prometheus.io/docs/practices/histograms/)

### Проверить, где ушло время

1. Возьми медленные трассы для checkout. Уточни, покрывают ли они версии, регионы и типы входа. Запросы могут отличаться размером корзины.
2. Ищи продолжительный участок, например `jdbc.acquire` или ожидание внешнего RPC. Сумма длительностей дочерних spans может быть больше длительности родителя, если вызовы шли параллельно. Ищи критический путь.
3. Сверь с метриками ресурса. При JDBC ожидающих много, активных соединений много, часть транзакций ждёт lock. Простой SELECT из пула не представляет весь путь.
4. Проверь, что изменение действительно уменьшило нужное ожидание. Если p99 улучшился потому, что быстрых запросов стало вдвое больше, хвост дорогой операции мог сохраниться.

Отсутствие span не показывает, что операции не было. Инструментация может не покрывать конкретную библиотеку. Трасса может быть обрезана по sampling, а exporter отставать. Ищи невидимые промежутки: время до получения worker, сериализация до отправки, очередь клиента, DNS. Инструментируй только нужную границу и измеряй её стоимость.

## Случай 2: обработчик падает десять раз, итог записан один раз

Платёжный callback пришёл с тем же event ID несколько раз. В логах шесть исключений, в ledger ровно одна запись. Метрика «количество ошибок worker» важна для здоровья обработки, но пользовательская цель — один верный эффект и финальный статус. Построй цепочку сигналов:

| Сигнал | На какой вопрос отвечает |
| --- | --- |
| Входящие попытки и accepted commands | Сколько раз систему вызвали и сколько логических команд она приняла |
| Duplicate deliveries | Сколько входов уже имели обработанный ID |
| Effect commits | Сколько новых эффектов зафиксировали |
| Age oldest pending | Сколько уже ждёт незавершённая работа |
| DLQ и окончательные отказы | Какие работы не пройдут обычным догоном |

У одной логической команды может быть несколько trace ID. Один trace показывает конкретный проход вызова. Для связывания сохраняй устойчивые `requestId`, `eventId` и объектный ID в допустимых structured полях. В сообщении trace context может связывать отправителя и обработку. Для batch, где входов много или связь асинхронная, используют поддерживаемые span links. Инструментирование выбирает связь по тому, как реально устроена работа. Длительный экземпляр BPMN не обязательно должен держать один открытый span сутки.

Для HTTP стандарт W3C определяет представление trace context, но само значение `traceparent` — диагностические данные, а не идентичность пользователя. На внешней границе не принимай решения об авторизации по trace ID или baggage. Если через контекст передаёшь сведения для наблюдения, ограничь их длину и набор. Не помещай туда секреты или персональные данные, которые затем бесконтрольно попадут в разные системы.

[W3C, Trace Context](https://www.w3.org/TR/trace-context/) · [OpenTelemetry, spans и links](https://opentelemetry.io/docs/concepts/signals/traces/) · [OpenTelemetry, Context](https://opentelemetry.io/docs/specs/otel/context/)

### Откуда берутся неполные трассы

**Head sampling** принимает решение рано. Он экономит работу служб и экспорт, но может не сохранить редкую ошибку, которая обнаружится в конце. **Tail sampling** выбирает после наблюдения частей трассы. Он позволяет чаще сохранять медленные и ошибочные запросы, но требует буферов и аккуратного сбора соответствующих spans вместе. Слишком ранняя оценка пропустит поздние spans, а перегрузка collector может усилить неполноту. Для доли ошибок используй метрики общего трафика, а не подсчёт ошибочных трасс после целенаправленного отбора.

[OpenTelemetry, sampling](https://opentelemetry.io/docs/concepts/sampling/)

## Случай 3: алерт на 0,1% ошибок ночью

Один ошибочный запрос из ста дал 1% за пять минут. По какому правилу будить дежурного? Сначала определи цель и окно. Для SLO 99,9% бюджетом ошибок является 0,1%. При наблюдаемой доле 1% скорость расхода бюджета равна 10. Если это продолжается долго, запас уйдёт быстрее. Проблема короткого всплеска — зависимость от низкого объёма и малого окна.

Два окна помогают отличить продолжающийся расход от уже закончившегося. Длинное окно показывает существенный накопленный расход, короткое подтверждает, что ситуация всё ещё активна. Условия подбираются под окно SLO и допустимое время реакции. Для низкого трафика может понадобиться синтетическая проверка или канал с меньшей срочностью. Для партий по расписанию уместен срок получения полезного результата. Проверка алерта на исторических данных помогает понять шум и задержку.

**Пример расчёта.** За 30 дней было 3 млн учитываемых запросов. Бюджет 0,1% — 3000 плохих ответов. Выпуск дал 1500 плохих ответов за 10 минут. Потрачена половина бюджета, даже если средняя за месяц ещё выше цели. Для диагностики проверь ошибки по версии, наблюдай прекращение расхода после отката и сравни время восстановления, а не только текущий процент.

[Google SRE Workbook, Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)

## Самопроверка

<details>
<summary>Почему среднее из p99 двух pod не равно p99 сервиса?</summary>

Квантиль зависит от распределения всех измерений и их числа. Сначала агрегируй совместимые распределения или bucket, затем вычисляй квантиль.

</details>

<details>
<summary>Коллектор настроен хранить все ошибки и 1% хороших трасс. Можно ли долю ошибок считать из базы трасс?</summary>

Выборка смещена настройкой хранения. Используй счётчики всего трафика для доли, трассы — для объяснения конкретных путей.

</details>

<details>
<summary>Клиент получил 202, а очередь не успевает доставить уведомление. Какой показатель показывает ущерб?</summary>

Доля завершённых до требуемого срока и возраст старейшей подходящей работы. HTTP-успех говорит о приёме, а результат измеряется отдельно.

</details>
