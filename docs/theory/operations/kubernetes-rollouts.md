# Kubernetes: почему релиз, масштабирование и остановка меняют трафик

## Деплой из трёх состояний

Команда заменила образ с версии v1 на v2. API Kubernetes принял новый desired state, но пользователь может ещё получать v1. Deployment создаёт или масштабирует ReplicaSet, scheduler назначает pod на узел, kubelet запускает контейнер, а readiness определяет пригодность для трафика. В эксплуатационном ответе различай факты: образ желаемый, pod запущен, процесс готов принимать вход, прогресс релиза завершён, пользовательский запрос успешен.

Пусть желаемо 10 pod, `maxSurge=2`, `maxUnavailable=1`. В обычном rolling update контроллер ограничивает продвижение этими параметрами и пытается удержать доступность согласно настройкам. Уже завершающиеся pod могут некоторое время расходовать ресурсы сверх этой прикидки. Если у новых pod нет места из-за requests, они останутся Pending. Если старые уже остановлены до их готовности, останется меньше мощности на реальный трафик. Проверь отсутствие capacity до релиза и отдельный запас для временного сосуществования двух версий.

| Наблюдение | Какой этап проверить |
| --- | --- |
| `Pending` долго не меняется | Ресурсы, quota, affinity, taints, PVC и события scheduler |
| `ImagePullBackOff` | Имя и digest, доступ к registry, состояние pull |
| `Running`, но `Ready=False` | Readiness/startup, конфигурация, некорректная зависимость при прогреве |
| `CrashLoopBackOff` | Причина предыдущего завершения, логи прошлого контейнера, OOM и liveness |
| Есть Ready, но внешний трафик ошибается | Селектор Service, targetPort, EndpointSlice, ingress и TLS |

Число `Running` не равно доступной мощности. Например, readiness после cache warmup становится true, но только один из десяти pod имеет нужную локальную конфигурацию. Для релиза проверь API из точки, похожей на клиента, и метрики по версии приложения. В rollout endpoint обычно смешаны старая и новая версии. Deployment rollback возвращает шаблон pod, отдельно нужно учитывать состояние схемы и внешние эффекты.

## Готовность и завершение без обрыва сохранённой команды

**Startup probe** даёт приложению начинаться достаточно долго, прежде чем другие пробы будут применяться по правилам Kubernetes. **Readiness** управляет пригодностью endpoint для трафика. **Liveness** допускает перезапуск контейнера, когда процесс не восстанавливается сам. Проблема во внешней БД может сделать pod неготовым в зависимости от модели, но перезапуск всех приложений при общей недоступности зависимости может ухудшить восстановление. Ошибку readiness, исчерпание потока обработки, liveness и отказ зависимости различай в метриках.

### Что происходит с существующими соединениями

Клиент держит keep-alive или gRPC-стрим. Маршрутизация новых соединений и судьба уже установленных соединений различаются. После запроса удаления pod его endpoint может некоторое время присутствовать как terminating, обычно с `ready=false`, а контроллер балансировки узнает об этом по своему циклу. Старое соединение могло остаться. Даже после удаления endpoint приложение ещё получает ранее начатый запрос или трафик из кеша маршрута. Нужна штатная остановка listener и завершение in-flight согласно бюджету.

Kubernetes даёт `terminationGracePeriodSeconds` на завершение. Hook `preStop`, если настроен и применяется, входит в общий срок. Большой `sleep` в hook отнимает часть бюджета прикладной остановки. После сигнала Spring Boot может выполнить graceful shutdown и дождаться незавершённых запросов в пределах настроенной фазы. Если приложение не вышло, инфраструктура принудительно завершит процесс. На собеседовании разложи время: обновление endpoint, сигнал, обработка последней команды, закрытие клиентских пулов и запас на задержку.

**Сценарий с Kafka.** При остановке consumer перестаёт принимать новую работу, завершает или безопасно оставляет в повтор то, что уже получено. Подтверждай позиции после нужной фиксации. Если до истечения grace часть запросов завершилась без final commit offset, следующий consumer может снова получить их. Идемпотентность ожидается даже после штатной выкладки. Для RabbitMQ неподтверждённая доставка тоже может вернуться.

## HPA и предел нижней зависимости

Horizontal Pod Autoscaler периодически выбирает желаемое число копий по измерениям. Для CPU utilization важен requests, потому что измеряется использование относительно запрошенного. При отсутствии нужных requests или метрик HPA может не сделать ожидаемого расчёта. HPA не создаёт мгновенно рабочие pod: есть задержка метрик, планирования, загрузки образа и прогрева. Stabilization и ограничение изменения числа копий влияют на реакцию.

**Пример ожидания в БД.** CPU pod ниже порога, однако запросы стоят в пуле JDBC, p99 растёт. CPU HPA этого не увидит как насыщение приложения. Масштабирование по числу запросов в очереди может добавить pod, но суммарное число соединений возрастёт. При 12 соединениях на pod масштабирование с 5 до 30 потенциально открывает 360 соединений. БД может выдерживать меньше либо выполнять лишь ограниченное количество SQL одновременно. Считай `replicas × maxPoolSize` относительно бюджета, а полезное масштабирование доказывай ростом завершённых операций.

Для consumer Kafka число партиций ограничивает обычный параллелизм группы. Если есть 8 партиций и 16 идентичных pod в группе, часть экземпляров не получит свою партицию. Масштабирование имеет цену rebalance, прогрев клиента и восстановление локального state store. Метрики lag по партициям и возраст работы помогают отличить общий рост нагрузки от горячего ключа. Для автоскейла асинхронных задач полезна измеренная скорость обработки, а не только размер общей очереди.

## Лимиты, внезапный рестарт и выведение узла

Если значение памяти контейнера ограничено 1 ГиБ, JVM не может отдать всё под heap. Есть thread stacks, metaspace, JIT, буферы, нативные библиотеки и память файловой подсистемы по учёту среды. При OOMKilled команда сначала смотрит terminated reason, лимит и график cgroup. Java heap OOME может появиться при достижении ограничения JVM и оставить свой стек, даже когда контейнер ещё не превысил общий предел. Для JVM-процесса в контейнере нужны измерения обоих уровней.

CPU limit ограничивает используемое время процессора. Контейнер может использовать весь выделенный квант до конца периода и ждать следующего, что видно как throttling. Средняя загрузка за минуту скрывает короткие всплески. При p99 после введения limits сравни latency, исполнение CPU и throttling, а также garbage collection. Не выводи причину из одного процента CPU.

**PDB.** PodDisruptionBudget задаёт допустимый уровень добровольных нарушений через поддерживаемый механизм eviction. Например, он ограничивает одновременный drain при обслуживании узлов. Он не останавливает внезапную потерю узла, не делает доступной БД и сам по себе не задаёт стратегию rolling update. Согласуй PDB с доступностью реплик и зон. Если replicas=1 и разрешено потерять 0, node maintenance может ждать. Если все pod помещаются на одной машине и она исчезла, число номинальных реплик не помогает. Разнос по размещению требует отдельной настройки и готовой ёмкости.

## Самопроверка

<details>
<summary>Подняли maxSurge, но rollout застыл и новых Ready нет. Что смотреть?</summary>

Проверь Pending и события scheduling, затем readiness, image и ресурсные квоты. При большем surge может требоваться дополнительная ёмкость узлов и БД.

</details>

<details>
<summary>Удалили endpoint, а под всё равно получил запрос и вернул 502. Почему возможно?</summary>

Существующее соединение или задержка обновления маршрута оставили путь. Проверь grace period, поведение сервера при shutdown и время drain у балансировщика.

</details>

<details>
<summary>HPA поднял число pod в три раза, throughput остался прежним. Какую гипотезу проверишь первой?</summary>

Найди общее узкое место, например БД, лимит провайдера или партицию Kafka. Сравни число завершений и ожидание соответствующего ресурса до и после масштабирования.

</details>
