# Нагрузочное тестирование с k6

[Эксплуатация](README.md) · [Наблюдаемость](observability.md) · [Вопросы на собеседовании](#вопросы-на-собеседовании)

k6 запускает JavaScript-сценарии, отправляет запросы к сервису и измеряет скорость, задержки и ошибки. Например, можно проверить, выдерживает ли API 50 поисков в секунду при `p95 < 300 мс` и доле ошибок ниже 1%. Профиль нагрузки и допустимые пороги задаёшь ты. Для HTTP-скриптов из этого гайда нужен k6, а Node.js используется внутри учебного стенда. [Документация k6](https://grafana.com/docs/k6/latest/using-k6/)

## Первый прогон

Открой PowerShell в корне репозитория. Запусти приложение и Nginx из [стенда observability](../../labs/observability/README.md). Флаг `--no-deps` оставляет для первого упражнения только эти два сервиса. Для проверки дождись `200` от `/ok`.

```powershell
docker compose -f .\docs\labs\observability\compose.yaml up -d --no-deps app nginx
curl.exe -i http://127.0.0.1:8088/ok
```

Если k6 ещё не установлен, установи его через Windows Package Manager и открой новый PowerShell. Для Linux и macOS есть отдельные команды установки. [Установка k6](https://grafana.com/docs/k6/latest/set-up/install-k6/)

```powershell
winget install k6 --source winget
k6 version
```

Запусти [готовый скрипт](../../labs/observability/k6-load.js). Начни с одного запроса, затем запусти профиль из `options`. Последняя команда делает запрос к `/fail`, чтобы увидеть нарушение порогов.

```powershell
k6 run --vus 1 --iterations 1 .\docs\labs\observability\k6-load.js
k6 run .\docs\labs\observability\k6-load.js
k6 run --vus 1 --iterations 1 -e API_PATH=/fail .\docs\labs\observability\k6-load.js
$LASTEXITCODE
```

При исправном стенде первые два прогона проходят. В третьем `/fail` вернёт `500`, пороги `checks` и `http_req_failed` нарушатся и k6 завершится с ненулевым кодом. `-e` передаёт значение в скрипт, где оно доступно как `__ENV.API_PATH`. Аналогично через `-e BASE_URL=...` можно указать адрес своего стенда. [Запуск k6](https://grafana.com/docs/k6/latest/get-started/running-k6/) · [Переменные окружения](https://grafana.com/docs/k6/latest/using-k6/environment-variables/)

Если используешь k6 из Docker, выполни эту команду вместо локального `k6 run`. В одной Compose-сети имя `nginx` указывает на нужный контейнер, а порт `80` — его внутренний порт.

```powershell
docker run --rm --network learn-observability_default -v "${PWD}/docs/labs/observability:/scripts:ro" grafana/k6 run -e BASE_URL=http://nginx /scripts/k6-load.js
```

После упражнений останови поднятые сервисы командой `docker compose -f .\docs\labs\observability\compose.yaml stop app nginx`.

## Как писать скрипты

Начни с одного пользовательского действия. В [учебном скрипте](../../labs/observability/k6-load.js) итерация состоит из `http.get()`, проверки статуса через `check()` и паузы `sleep(1)`. **VU** (virtual user) — виртуальный пользователь. Каждый из пяти VU повторяет функцию `export default` в течение `20s`. **Итерация** — один запуск этой функции. Пауза имитирует время между действиями пользователя и входит в длительность итерации. [Жизненный цикл скрипта](https://grafana.com/docs/k6/latest/using-k6/test-lifecycle/)

При написании своего скрипта разложи его по шагам.

1. Задай адрес и профиль. В начале файла импортируй модули, прочитай `BASE_URL` из `__ENV`, а в `options` укажи профиль нагрузки и пороги. `k6 new` создаёт заготовку.
2. Перенеси в `default()` цепочку запросов, например «найти товар → открыть карточку». Доставай ID из ответа, проверяй его и используй в следующем запросе. Если обязательная проверка провалилась, `if (!check(...)) return` завершит текущую итерацию и не даст отправить следующий запрос с пустым ID.
3. Проверяй контракт API. Для чтения заказа это может быть `200` и нужный ID в JSON, для создания — `201` и непустой ID. `check` записывает результат каждой проверки. `threshold` задаёт условие для всего прогона по метрике и влияет на код завершения.
4. Подготовь тестовые аккаунты, токены и данные. `setup()` выполняется один раз до старта VU, а `teardown()` — после прогона. Значение, возвращённое из `setup()`, k6 передаёт в `default(data)` и `teardown(data)`. Логин включай в измеряемую цепочку, если он входит в пользовательский сценарий. Секреты передавай из окружения или хранилища CI.

Пример POST-запроса для собственного API. k6 отправит JSON и добавит Bearer-токен, если подставить значения `baseUrl` и `__ENV.API_TOKEN`.

```javascript
const response = http.post(`${baseUrl}/orders`, JSON.stringify({ productId: 'demo-42' }), {
    headers: {
        'Content-Type': 'application/json',
        Authorization: `Bearer ${__ENV.API_TOKEN}`,
    },
    tags: { name: 'POST /orders' },
    timeout: '5s',
});
check(response, { 'order created': (res) => res.status === 201 });
```

Для URL с динамическим ID задай стабильное имя запроса через `tags.name`, например `GET /orders/:id`. Так можно собрать задержку по маршруту в одном пороге `http_req_duration{name:GET /orders/:id}`. Уникальные ID в значениях тегов раздувают число временных рядов. [HTTP-запросы](https://grafana.com/docs/k6/latest/using-k6/http-requests/) · [Теги и группы](https://grafana.com/docs/k6/latest/using-k6/tags-and-groups/) · [Пороги](https://grafana.com/docs/k6/latest/using-k6/thresholds/)

## Как задавать нагрузку

| Задача | Настройка |
| --- | --- |
| Держать 5 одновременно работающих пользователей | `vus` и `duration` или `constant-vus`. Каждый VU ждёт завершения итерации и начинает следующую. При замедлении сервиса частота итераций падает. Это закрытая модель. |
| Плавно увеличить и затем снизить число пользователей | `stages` или `ramping-vus`. В каждой ступени укажи `duration` и целевое число VU в `target`. |
| Запускать 10 новых действий каждую секунду | `constant-arrival-rate`. k6 планирует начало итераций с заданной частотой, пока хватает VU. Это открытая модель. |
| Менять частоту новых действий по этапам | `ramping-arrival-rate`. Цель каждой ступени задаётся в итерациях за `timeUnit`. |

RPS — число HTTP-запросов в секунду. Один VU может выполнить много запросов, а в одной итерации может быть несколько запросов. Например, 10 итераций/с по два запроса дают примерно 20 RPS, если оба шага выполняются каждый раз и частота стабильна. [Модели нагрузки](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/) · [Executors](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/)

Чтобы попробовать фиксированную частоту на `/ok`, сделай копию учебного скрипта. В `options` замени строки `vus` и `duration` блоком ниже, сохрани `thresholds` и добавь в него `dropped_iterations: ['count<1']`. Убери `sleep(1)` и его импорт. Частоту старта здесь задаёт сам k6. Запусти копию через `k6 run`.

```javascript
scenarios: {
    read_api: {
        executor: 'constant-arrival-rate',
        rate: 10,
        timeUnit: '1s',
        duration: '20s',
        preAllocatedVUs: 5,
    },
},
```

`preAllocatedVUs` — число VU, подготовленных заранее. Для приблизительной оценки умножь частоту итераций на среднюю длительность итерации в секундах и добавь запас. При `10 итераций/с` и `200 мс` одновременно заняты в среднем около двух VU. Если в момент старта нет свободного VU, k6 увеличивает `dropped_iterations`. В этом примере любая пропущенная итерация нарушит порог. [Выделение VU для arrival-rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/arrival-rate-vu-allocation/)

## Как читать отчёт

В проверочном прогоне `/ok` на локальном стенде `checks` показала `100%`, `http_req_failed` — `0%`, а `p(95)` — около `2,5 мс`. Все три порога прошли. По `http_reqs` видно, под какой нагрузкой получен результат: 100 запросов за 20 секунд, около 5 RPS. На твоём стенде время ответа может отличаться.

| Метрика | Что смотреть |
| --- | --- |
| `http_reqs`, `iterations` | Число HTTP-запросов и завершённых итераций. Отчёт показывает и их среднюю частоту за прогон. |
| `http_req_duration` | Время отправки запроса, ожидания ответа и получения тела. DNS и установка соединения измеряются отдельно. `p95 = 180 мс` означает, что примерно 95% замеров укладываются в 180 мс. `p99` помогает увидеть более редкие задержки. |
| `http_req_failed` | Доля запросов, которые k6 счёл неуспешными. По умолчанию HTTP-статусы `200–399` считаются ожидаемыми. Ошибка бизнес-логики в ответе `200` видна через проверку содержимого ответа. |
| `checks` | Доля пройденных проверок. Один запрос может дать несколько результатов, если проверяешь и статус, и тело ответа. Посмотри, какая именно проверка упала. |
| `dropped_iterations` | Запланированные итерации, которые не стартовали. Для arrival-rate сначала проверь занятость VU, длительность итерации и ресурсы генератора. |

Для smoke достаточно одного запроса. Для оценки `p95` и `p99` нужна выборка из основного прогона. Чтобы вывести `p99` в отчёт, добавь флаг `--summary-trend-stats "avg,med,p(95),p(99),max"` в команду `k6 run`. [Встроенные метрики](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/) · [Ожидаемые HTTP-статусы](https://grafana.com/docs/k6/latest/javascript-api/k6-http/set-response-callback/) · [Настройки отчёта](https://grafana.com/docs/k6/latest/using-k6/k6-options/reference/#summary-trend-stats)

## Как проводить тест на работе

1. **Сформулируй цель.** Например, 50 поисков в секунду в течение 10 минут при `p95 < 300 мс` и доле ошибок ниже 1%. Возьми профиль трафика из метрик, а пороги — из требований к сервису. Для нескольких маршрутов задай долю чтений и записей, объём данных и распределение ID.
2. **Подготовь стенд и запусти smoke.** На согласованном окружении проверь адрес, авторизацию, корректность данных и один полный сценарий. Сверь первые запросы с логами сервиса. Если тест пишет данные, подготовь отдельные записи и способ очистки.
3. **Проведи основной прогон.** Прогрей сервис и кеши, затем измеряй на стабильной нагрузке. Для поиска ограничения повышай нагрузку ступенями. Для проверки устойчивости используй резкий всплеск (spike), длительную нагрузку (soak) или нагрузку выше ожидаемой (stress). [Типы нагрузочных тестов](https://grafana.com/docs/k6/latest/testing-guides/test-types/)
4. **Сверь клиент и сервер.** Сопоставь по времени RPS, задержки и ошибки k6 с CPU и памятью сервиса, GC, ожиданием соединений в пуле, метриками БД и прокси. Проверь CPU, память и сеть машины с k6, чтобы понять, смогла ли она создать заданную нагрузку. Для разбора скачков во времени используй метрики с временными рядами, например Grafana поверх Prometheus. [Наблюдаемость](observability.md) · [Экспорт результатов k6](https://grafana.com/docs/k6/latest/results-output/)
5. **Зафиксируй результат.** Запиши версию сервиса, профиль и фактический RPS, состояние стенда и данных, `p95`/`p99`, ошибки и пропущенные итерации. Сравни версии при одинаковых условиях. В CI можно запускать короткий smoke, а длительный прогон — отдельной задачей на подготовленном стенде. Пусть CI учитывает код завершения `k6 run`.

Для практики запусти учебный скрипт на `/limited` с `-e API_PATH=/limited`. Nginx ограничивает частоту запросов к этому маршруту. Сопоставь `429` в `docker compose -f .\docs\labs\observability\compose.yaml logs nginx --tail 20` с ростом `http_req_failed`. В логах приложения будут только запросы, которые прошли через прокси. [Как устроен лимит в стенде](../../labs/observability/README.md#ограничь-частоту-запросов)

## Вопросы на собеседовании

| Вопрос | Короткий ответ |
| --- | --- |
| 100 VU — это сколько RPS? | Зависит от длительности итерации, пауз и числа запросов. Если у 100 VU итерация занимает около двух секунд и содержит один запрос, получится около 50 RPS. Фактическое значение смотри в `http_reqs`. |
| Как проверить API под постоянным входящим потоком в 200 запросов/с? | В простом сценарии с одним запросом на итерацию задам 200 итераций/с через `constant-arrival-rate`. После прогона сверю `http_reqs`, `dropped_iterations`, задержки и ошибки. |
| Чем `check()` отличается от `threshold`? | `check()` проверяет конкретный ответ. `threshold` сравнивает агрегат метрики с критерием, например `checks: ['rate>0.99']`. Нарушение порога даёт ненулевой код выхода. |
| Среднее почти не изменилось, а `p99` вырос. Как разбирать? | Сначала проверю объём выборки и какие маршруты замедлились. Найду интервал роста и сопоставлю его с очередями, GC, пулом соединений и медленными запросами в БД. |
| Почему заданный темп не достигнут? | В arrival-rate проверю пропущенные итерации, свободные VU и ресурсы генератора. В закрытой модели проверю, насколько выросла длительность итерации и какие паузы заложены в скрипте. |
| Как оценить ёмкость сервиса? | Повышать нагрузку ступенями и измерять фактический RPS, задержки и ошибки на каждой. Ёмкость для заданных условий — максимальный устойчивый темп, при котором соблюдаются пороги и не растёт очередь. |
| Что запустить перед релизом, а что при поиске утечки памяти? | Для быстрой проверки сценария — smoke. Для сравнения производительности версий — одинаковый профиль ожидаемой нагрузки. Для утечек и накопления очередей — soak с наблюдением за ресурсами во времени. |
