# JDBC из Java: параметры, соединения, батчи и большие выборки

## Что получает Java-приложение

`DataSource` предоставляет соединения. `Connection` представляет сеанс взаимодействия с БД. `PreparedStatement` хранит SQL с параметрами и описание работы, которую можно выполнить на этом соединении. `ResultSet` — результат с курсором, который двигают через `next()`. Владение ресурсами вложено: чтение результата должно закончиться до закрытия statement и соединения.

Обычно пул выдаёт обёртку над физическим соединением. При вызове `close` обёртка возвращает ресурс пулу. Это позволяет быстро переиспользовать существующий сеанс. Если пользователь выгрузки закрыл ResultSet, но забыл закрыть Connection, исчерпание пула всё равно возможно. Используй try-with-resources для самостоятельного JDBC-кода. В Spring для работы в действующей транзакции используй управляющий JDBC API, который получает соединение из её контекста. Одноимённый DataSource сам по себе не гарантирует, что вручную открытый сеанс относится к текущей транзакции.

```java
Optional<String> findStatus(DataSource source, long id) throws SQLException {
    String query = "select status from orders where id = ?";
    try (Connection connection = source.getConnection();
         PreparedStatement statement = connection.prepareStatement(query)) {
        statement.setLong(1, id);
        try (ResultSet rows = statement.executeQuery()) {
            return rows.next()
                ? Optional.of(rows.getString("status"))
                : Optional.empty();
        }
    }
}
```

Пример предполагает, что `status` определён как NOT NULL, а `id` уникален. Для nullable-колонки учитывай разницу между «строки нет» и «строка есть, значение неизвестно». `ResultSet.getLong` при SQL NULL возвращает 0, поэтому после вызова нужен `wasNull()` или `getObject(..., Long.class)` при поддержке драйвером. Иначе отсутствующее значение может незаметно оказаться нулевым балансом.

### Параметр — значение выражения

Параметры `?` передают данные отдельно от текста SQL. Ими нельзя подставить имя таблицы, колонки или направление сортировки. Если пользователь выбирает сортировку, отобрази ограниченный enum на заранее определённые SQL-фрагменты. При произвольном идентификаторе проверка должна соответствовать предметным ограничениям. Правила безопасного связывания не зависят от того, создал JDBC-драйвер persistent prepared statement на сервере или ещё нет.

**Что делает pgJDBC.** У драйвера есть серверная подготовка и настройки, определяющие, после скольких повторов и в каком режиме она применяется. PostgreSQL может выбирать специальный план под конкретные значения или обобщённый план. Если у одного клиента 10 строк, а у другого 10 млн, оптимальный доступ может отличаться. Симптом «в psql с литералом быстро, из сервиса после нескольких вызовов плохо» требует сравнить plans для конкретных и общих parameters, актуальность статистики и реально выполняемый текст. Отдельный пример — частичный индекс, предикат которого общий план не может вывести для всех значений параметра.

Не смешивай три уровня кеша: переиспользованное соединение, подготовленное выражение и ORM-объект в контексте. Пул может держать соединение открытым при выдаче следующему запросу. Серверный план привязан к сеансу. Hibernate может вернуть уже управляемую сущность из контекста без нового SQL по первичному ключу. Для диагностики спроси, на каком уровне удалось избежать работы.

## Autocommit и несколько операторов

В autocommit обычный JDBC-сеанс фиксирует SQL-команды отдельными транзакциями по правилам драйвера и завершения statement. Если нужно связать UPDATE остатков и INSERT в журнал, выполни их в одной транзакции. В низкоуровневом варианте делаешь `setAutoCommit(false)`, проверяешь результаты операторов, вызываешь commit или rollback и освобождаешь ресурс. В большинстве Spring-сервисов это выполняет управляющая граница. Определи точку, где код решает, что вся бизнес-команда выполнена.

У условного обновления количество затронутых строк — часть протокола. `update ... where id = ? and version = ?` может вернуть 0. Для нового запроса «отменить заказ» это может означать потерю версии, отсутствие записи или текущее состояние, в котором действие уже недоступно. API переводит это в результат после проверки, а не считает любой выполненный SQL успешным бизнес-эффектом.

Подготовленный statement обычно переиспользуют на одном сеансе с разными параметрами. Batch сокращает число обменов по сравнению с отдельным round-trip каждого оператора, если драйвер и конфигурация это поддерживают. `BatchUpdateException` может содержать обновлённое число строк для отдельных команд, включая специальные статусы. Если всё выполняется в одной транзакции и при ошибке нужен атомарный откат, откатывай транзакцию целиком. Если autocommit или внешние ресурсы разделяют сохранения, заранее определи обработку частично пройденных элементов.

### Потоковая выборка

Запрос вернул пять миллионов строк. Даже если Java обходит их по одной, драйвер может заранее получить весь набор. У pgJDBC курсорное чтение с fetch size имеет условия, в том числе выключенный autocommit и подходящий режим ResultSet. `setFetchSize` задаёт порцию передачи данных, не ограничение общего количества строк. Для загрузки с ограничением нужна явная пагинация или `LIMIT`. В записи отчёта читай, обрабатывай и освобождай каждую порцию, следи, чтобы накопление в памяти не вернулось в следующем слое.

Долгий курсор занимает соединение, может удерживать транзакцию и снимок. Если HTTP-клиент читает результат медленно, источник и публикация могут оказаться связаны. Для дампа больших таблиц можно построить фоновые артефакты с отдельным бюджетом, а API вернуть ID и ссылку готового результата. Для сканирования частями по ключу укажи требования к консистентности: при отдельных транзакциях новые изменения могут появиться между страницами.

**Выбор размера порции.** Порция 1000 строк меняет количество сетевых переходов и сколько памяти занимает буфер. Строки по 200 байт и по 200 КБ ведут себя по-разному. Измеряй байты и длительность, включая обработку и время удержания соединения. Отдельный пул для тяжёлых задач ограничивает их воздействие на текущий пользовательский трафик, если общая БД выдерживает оба бюджета.

## Истёк тайм-аут или связь оборвалась

У Java-кода есть время ожидания пула, установки соединения, выполнения SQL и ожидания ответа. Для диагностического сообщения полезно назвать фазу. Если HTTP-клиент закрыл запрос, рабочий поток может всё ещё держать соединение и ждать PostgreSQL. Протокол отмены statement и серверные тайм-ауты имеют собственные границы. Измерь фактическую длительность SQL после клиентской отмены.

`SQLException` содержит SQLState. Например, `23505` обозначает нарушение уникальности, `40001` — ошибку сериализации, `40P01` — обнаруженный deadlock в PostgreSQL. Приложение может оборачивать это в исключения Spring. Не разбирай локализованный текст для принятия бизнес-решения. Если переподключение необходимо после проблемы с соединением, попытка может требовать чтения состояния команды по стабильному ID. Исключение в момент коммита не всегда позволяет клиенту заключить, применена ли транзакция.

**Привязка ресурса к потоку.** Один Connection и его ResultSet не предназначены для произвольного конкурентного использования несколькими worker. Если в методе `@Transactional` запустить десять параллельных задач, они не получают автоматически тот же ресурс. Обычно либо выполни последовательную запись одной транзакцией, либо дай каждому worker независимую границу и опиши консистентность общего результата.

[PostgreSQL 17, SQLSTATE](https://www.postgresql.org/docs/17/errcodes-appendix.html) · [Spring, программное управление транзакцией](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/programmatic.html)

## Самопроверка

<details>
<summary>setFetchSize(500) гарантирует, что отчёт вернёт максимум 500 записей?</summary>

Нет, это размер порции чтения по контракту драйвера. Ограничение общего результата задаётся SQL. Проверь, включилось ли порционное чтение и сколько ресурсов удерживает полный обход.

</details>

<details>
<summary>Как отличить утечку соединений от медленных транзакций?</summary>

Сопоставь acquired/returned и время удержания, количество активных ресурсов и состояние сеансов в БД. Постоянно занятый пул бывает и при корректном возврате, когда нагрузка выше пропускной способности.

</details>

<details>
<summary>Почему prepared statement с параметром не использовал частичный индекс, который psql выбрал с литералом?</summary>

При общем плане значение параметра заранее неизвестно и условие может не доказывать предикат индекса. Сравни фактический план в режиме приложения и проверь форму запроса.

</details>
