## Начни с наблюдаемого правила

Фраза «тест возврата проходит» не сообщает, что проверено. Сформулируй ожидаемое наблюдаемое свойство: для одного `refundId` после двух одинаковых запросов в ledger одна запись и доступный остаток уменьшился один раз. Отдельно проверь повтор с другой суммой, тайм-аут провайдера и перезапуск между commit и ACK. Тогда тесты охраняют результат, даже если в коде поменяли очередность внутренних вызовов без изменения контракта.

| Тест | Какой сбой увидит |
| --- | --- |
| Unit на модель состояния | Правило разрешило возврат из неверного статуса или переполнение суммы |
| Тест репозитория с PostgreSQL | Не тот предикат UPDATE, отсутствующий unique, неверное поведение конкурентной записи |
| Тест MVC/HTTP | Некорректное тело, валидацию, состояние ресурса и контракт ошибок |
| Контрактный тест клиента внешнего API | Неверный URL, ключ идемпотентности, единицы и трактовку статуса провайдера |
| Сквозной сценарий со сбоем | Потерю результата между независимыми границами и неверное возобновление |

Verification через Mockito полезен, если взаимодействие само является контрактом, например передать прежний ключ в повторную сетевую попытку. Утверждение «repository.save был вызван один раз» не доказывает наличие строки после commit, SQL-ограничение и массовый эффект. Проверяй эти вещи отдельно. Тест, который воспроизводит весь внутренний порядок мелких операций, хрупок к рефакторингу и часто ничего не говорит о результате пользователя.

## Две транзакции и предсказуемый порядок

Для уязвимого read-modify-write в тесте хочется, чтобы обе попытки прочитали остаток 1000, затем обе захотели записать. `Thread.sleep` не гарантирует, что нужный worker дошёл до чтения. Раздели сценарий на фазы и синхронизируй барьером или лэтчами.

1. В каждом worker открой собственную транзакцию и прочитай стартовое значение.
2. Сообщи тестовому потоку, что worker дошёл до точки. Дай тайм-аут каждому ожиданию.
3. Разреши двум worker продолжить согласно проверяемому порядку.
4. Получи результаты обеих задач и проверь состояние из новой транзакции.

Если правильный код захватывает lock до чтения, барьер «оба прочитали под lock» может быть невозможен. Для такой реализации сделай другую точку: первый захватил и временно удерживает, второй пытается выполнить операцию, затем первый освобождает. Проверяй наблюдаемый результат и при необходимости состояние ожидания на стороне БД, не требуй произвольного порядка планировщика. Если движок может выбрать любой победивший запрос, ожидай «один успешен, итог укладывается в лимит», а не конкретный ID победителя.

**Тестовая транзакция как скрытая причина.** Если тест пометили `@Transactional` и исходные данные ещё не зафиксировались, новые потоки могут их не увидеть. При полном HTTP-тесте сервер тоже работает в другом контексте. Подготовь и завершай данные явно. Для проверки deferred constraints и actions after commit нужен настоящий commit. Когда отдельная библиотека выполняет тест внутри ещё одного timeout-исполнителя, проверь, остаётся ли доступна транзакция, привязанная к исходному потоку.

## Отказ нужно поставить в точное окно

Сценарий «выключили брокер» покрывает публикацию в недоступную систему. Он не проверяет случай, когда брокер принял сообщение, а publisher не сохранил отметку. Для этого оформи проверяемую точку отказа между подтверждением и местной записью или выбери лабораторную, позволяющую скоординировать закрытие соединения. После восстановления проверь и отправителя, и окончательный эффект.

| Точка | Ожидаемое наблюдение после повтора |
| --- | --- |
| Бизнес-транзакция упала до commit | В локальной БД нет ни результата, ни outbox |
| После commit заказа, до publish | Новая копия relay увидит открытое намерение |
| После broker confirm, до отметки outbox | Повтор с тем же ID возможен. Итог обработки сохраняется по контракту |
| После commit обработчика, до ACK | Новый consumer может получить запись и обнаружить Inbox/ledger |
| После HTTP-успеха у провайдера, до обработки ответа | Локальная попытка может иметь неизвестный итог. Сверка не создаёт новый эффект |

В сквозном тесте выбирай конечный срок, до которого система должна увидеть соответствующее состояние, и проверяй условие до него. Фиксированный большой sleep делает тесты медленными и всё равно нестабильными под нагрузкой. Ожидание отдельной гарантии, например «зафиксирован один эффект», лучше связывает тест с контрактом. У теста должны быть понятные снимки результата при тайм-ауте: сколько работ в outbox, какие обработчики запустились, в какой транзакции нашли запись.

## Инварианты на последовательности команд

Unit-тест можно строить как небольшой набор таблиц состояний. У заказа состояния `NEW`, `PAID`, `SHIPPED`, `CANCELLED`. На каждой паре «состояние + команда» проверь ожидаемый переход, результат при повторе и допустимость позднего сообщения. Параметризованные тесты удобны, когда упражнения отличаются входом и ожидаемым исходом. Сохраняй пояснение для каждого ряда, иначе падение «case 7» мало говорит о правиле.

**Генерация последовательностей.** Для модели возвратов создай много небольших списков команд reserve, confirm, fail, retry и shuffle. Сохраняй seed при случайном запуске и сравнивай с простой моделью. После каждого шага проверяй неотрицательный остаток и отсутствие двойного эффекта. Если тест нашёл ошибку, сократи вход до минимального воспроизводимого примера и добавь его отдельной проверкой. Такое тестирование хорошо находит неочевидные комбинации событий, но не заменяет точную проверку SQL-изоляции и отказа внешней системы.

### Изоляция тестовых данных

Несколько тестов могут использовать один PostgreSQL-контейнер для скорости. Тогда раздели данные уникальным namespace, отдельной схемой или явной очисткой. Если тест использует заранее известные ID, параллельные тесты могут удалить записи друг друга. Общую повторно используемую инфраструктуру проверяй так, чтобы порядок тестов не менял результат. Для БД с миграциями тест должен поднять совместимую схему из штатного пути. Отдельный тест на обновление старой схемы нужен, когда основная ошибка возникает только на данных предыдущей версии.

<summary>Тест с mock проверил save после возврата. Что нужно добавить для защиты инварианта?</summary>

Убедись в единственной зафиксированной строке ledger и итоговом остатке. Прогони повторы и конкурентные попытки с настоящим ограничением БД.

</details>

<details>
<summary>Два потока должны прочитать один остаток, но один стартует позже. Как избежать нестабильного теста?</summary>

В непредусматривающей lock реализации используй контрольную точку после чтения. В реализации с lock наблюдай попытку второго и освобождение первой транзакции. У ожиданий должен быть предел времени.

</details>

<details>
<summary>При проверке before ACK дважды вызвался handler. Считать ли это провалом?</summary>

Смотри контракт. При at-least-once повтор handler допустим. Провал — двойной локальный эффект, потеря команды или неверное состояние после возобновления.

</details>
