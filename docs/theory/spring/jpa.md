## Состояния сущности и контекст

**JPA** (Jakarta Persistence) задаёт API и правила отображения объектов в БД. **Hibernate ORM** реализует спецификацию и добавляет свои возможности. **Spring Data JPA** строит репозитории поверх `EntityManager`. Если на интервью спрашивают про гарантии, сначала уточни слой. Например, `@Version` стандартизирована, а свойство `hibernate.jdbc.batch_size` относится к Hibernate.

**Persistence context** — набор управляемых сущностей. Внутри него одному типу и первичному ключу соответствует один управляемый экземпляр. Hibernate может отдать его из контекста при повторном `find`. JPQL-запрос при этом может снова обратиться в БД, чтобы определить, какие ID входят в результат. Кеш первого уровня хранит сущности по идентификатору. Кеш результатов запросов — отдельная возможность провайдера.

| Состояние | Откуда берётся | Что произойдёт с изменением объекта |
| --- | --- | --- |
| New, или transient | `new Order(...)` | Объект пока живёт только в памяти. `persist` сделает его управляемым |
| Managed | `find`, `persist`, результат `merge` | Изменения полей и связей могут превратиться в SQL при flush |
| Detached | Контекст закрыли или очистили через `clear`, объект отсоединили через `detach` | Текущий контекст больше его изменения не отслеживает |
| Removed | Вызвали `remove` на управляемой сущности | Удаление планируется к синхронизации с БД |

`persist(x)` присоединяет новый экземпляр `x`. `merge(x)` переносит состояние в управляемый экземпляр и возвращает его. При передаче detached-объекта меняй дальше результат `merge`, иначе оставшиеся правки могут не попасть в БД.

```java
// Внутри транзакции, после закрытия контекста, загрузившего detachedOrder.
Order managed = entityManager.merge(detachedOrder);
managed.setStatus(OrderStatus.PAID); // будет отслеживаться
detachedOrder.setStatus(OrderStatus.CANCELLED); // исходный объект detached
```

Spring Data JPA обычно выбирает `persist` или `merge` в `save` по признаку новизны. Сначала проверяет nullable-поле версии, если оно есть, иначе ID. При назначенном в приложении ID и отсутствии версии новый объект может уйти в `merge`. Для явного признака новизны есть `Persistable.isNew()`. Перед использованием результата `save` полезно помнить о том, что репозиторий может вернуть другой экземпляр.

### Обновляй только то, что входит в команду

Представь PATCH, в котором пользователь поменял лишь адрес доставки. Если собрать объект заказа из входящего JSON и вызвать `merge`, отсутствующие значения в объекте могут затереть поля. Надёжный сценарий — загрузить текущий заказ внутри транзакции, проверить право на изменение и состояние, вызвать `changeAddress(...)`. Состояние остальных полей сохраняется в управляемом экземпляре. Для конкурирующих изменений добавь версию или другой механизм защиты инварианта.

В пределах одной транзакции два компонента могут изменить один managed-объект, полученный из общего контекста. Это помогает сохранить единый набор изменений, но усложняет отладку, если каждый метод правит объект без явного контракта. В сервисе полезно назвать операцию на языке предметной области: `cancelOrder` с проверкой статуса проще объяснить и тестировать, чем набор универсальных сеттеров.

### Кеши, равенство и время жизни

- **Первый уровень** привязан к контексту. `clear()` отсоединяет все сущности, а `refresh(entity)` перечитывает состояние и может заменить несохранённые правки. Жизнь контекста и транзакции часто совпадает в Spring, но это независимые понятия.
- **Второй уровень** относится к фабрике и может использоваться разными контекстами. Согласованность зависит от стратегии кеширования и путей записи. Изменение строки вручную через SQL не обязано корректно обновлять ORM-кеш.
- **Равенство** важно, если сущность кладут в `HashSet` или используют как ключ. Поле, входящее в `hashCode`, должно оставаться стабильным, пока объект в коллекции. Генерируемый БД ID появляется после создания объекта. Подходы выбирают под доменную идентичность и проверяют на transient, managed, detached и прокси. Нельзя делать две новые сущности равными только потому, что оба ID равны `null`.
- **Потоки.** Сам контекст и `EntityManager` не предназначены для параллельного использования. Spring может внедрить прокси, который выбирает контекст текущей транзакции. Передача этого прокси в другой поток не переносит старый контекст. Передавай ID или DTO, а в worker открывай свою транзакцию.

## Flush, commit и пакетная запись

**Dirty checking** — обнаружение изменений управляемой сущности. Hibernate обычно сравнивает состояние со снимком, а при некоторых настройках использует информацию об изменениях из инструментированного класса. При `flush()` провайдер превращает изменения в SQL и синхронизирует контекст с БД. **Commit** завершает транзакцию. Даже успешно выполненный `UPDATE` внутри flush можно откатить. Ошибка с отложенным ограничением БД возможна и при самом commit.

1. `find(Order.class, id)` загрузил заказ.
2. `order.cancel()` поменял поля в Java.
3. Flush отправил `UPDATE orders ...` базе. Другие транзакции обычно продолжают видеть прежнюю зафиксированную версию по правилам изоляции.
4. Commit зафиксировал отмену. После rollback результат исчезнет из БД, хотя ссылаться на прежний Java-объект с изменёнными полями всё ещё возможно.

При `FlushModeType.AUTO` перед запросом в транзакции провайдер обеспечивает учёт изменений, которые могут повлиять на его результат. Он может выполнить flush раньше commit. `FlushModeType.COMMIT` откладывает обязательный flush до commit, влияние отложенных изменений на запросы по JPA не определено. С `IDENTITY` вставка часто нужна раньше ради получения ID. Поэтому привязывай ответ к фактическому SQL и выбранному провайдеру.

### Почему тест проходит, а сервис падает

В тесте с `@Transactional` репозиторий сохранил объект. Проверка полей прочитала экземпляр из того же контекста, а тестовая транзакция откатилась до flush. Нарушение внешнего ключа могло остаться незамеченным. Вызови `entityManager.flush()`, чтобы проверить обычные ограничения БД, затем `clear()` и перечитай строку для проверки маппинга. Если проверяешь deferred constraint или действие after commit, тесту нужно реально завершить транзакцию и наблюдать результат из другой. Подготовь изоляцию данных и их уборку. Для поведения PostgreSQL, включая блокировки и диалект SQL, используй PostgreSQL.

### Вставка большого числа объектов

Контекст удерживает managed-объекты и сведения для отслеживания. Импорт на миллион строк в одном контексте расходует память пропорционально объёму работы. Flush плюс clear через ограниченное число строк уменьшает объём удерживаемого состояния. Если вся загрузка остаётся одной транзакцией, блокировки и объём журнала до завершения всё равно могут быть велики. Коммит по частям меняет контракт импорта, поэтому при частичных коммитах продумай прогресс, идемпотентность и повтор.

JDBC batching снижает число обращений к драйверу для однотипных SQL-операторов. Hibernate должен поддерживать batching для выбранного сценария и стратегии ID. Например, `IDENTITY` мешает batching вставок сущностей в Hibernate. `saveAll` в Spring Data само по себе гарантии одного SQL не даёт. Проверяй объём вставок, число JDBC batch-исполнений и время транзакции на реалистичном наборе.

[Hibernate ORM, руководство по flush и batching](https://docs.hibernate.org/orm/6.6/userguide/html_single/Hibernate_User_Guide.html) · [Spring Test, управление транзакциями](https://docs.spring.io/spring-framework/reference/6.2/testing/testcontext-framework/tx.html)

## Связи, cascade и orphan removal

У `Order` есть список позиций, у `OrderLine` — ссылка на заказ. Если в БД внешний ключ `order_line.order_id`, `OrderLine.order` обычно является владеющей стороной, а `Order.lines` указывает на неё через `mappedBy = "order"`. Чтобы маппинг и Java-модель совпали, меняй обе стороны в одном методе.

```java
// Фрагмент класса Order, где lines — изменяемая коллекция позиций.
public void addLine(OrderLine line) {
    lines.add(line);
    line.setOrder(this);
}
```

У двусторонней связи правила записи определяет владеющая сторона. Если положить позицию только в `order.getLines()`, внешний ключ может не измениться ожидаемым образом. Противоположная ошибка — установить только `line.order`, а потом вернуть DTO из уже загруженного списка, в котором позиции пока нет.

| Механизм | Когда срабатывает | Подходящий пример |
| --- | --- | --- |
| `cascade = PERSIST` | При сохранении родителя распространяет операцию на связанные объекты | Создаём заказ с новыми позициями |
| `cascade = REMOVE` | При удалении родителя распространяет удаление | Позиции живут вместе с заказом |
| `orphanRemoval = true` | При разрыве отношения с управляемым дочерним объектом удаляет его при синхронизации | Убираем позицию из заказа |
| `ON DELETE CASCADE` | База обрабатывает удаление строки, на которую ссылается внешний ключ | Правило действует и для SQL снаружи ORM |

Определи жизненный цикл до выбора cascade. Клиент принадлежит своей предметной области, поэтому удаление одного заказа не должно удалять клиента. Для связи many-to-many удаление связи обычно означает удаление строки таблицы связей. Если у связи есть роль, дата, состояние или собственный жизненный цикл, её удобно представить отдельной сущностью.

## Конкурентность, версии и bulk update

При `@Version` ORM проверяет версию при обновлении. Упрощённая форма SQL выглядит так:

```sql
UPDATE orders
SET status = 'CANCELLED', version = version + 1
WHERE id = :id AND version = :loaded_version;
```

Две транзакции прочитали версию 7 и начали менять заказ. Первая зафиксировала версию 8. Вторая обновит ноль строк со старой версией и получит конфликт при синхронизации или commit. Повторяй бизнес-команду в новой транзакции, прочитав актуальное состояние. Для отменённого заказа повтор может вернуть текущий результат, а для уже отправленного — понятный отказ. Ошибка оптимистической блокировки требует заново оценить команду.

**Пессимистическая блокировка** полезна, когда критическая секция короткая и конфликты ожидаемы. Например, `PESSIMISTIC_WRITE` обычно приводит к блокирующему запросу в БД и удерживает блокировку до конца транзакции. Сетевое ожидание под блокировкой удлиняет очередь других транзакций. Блокировка отдельной сущности и проверка версии защищают конкретную запись. Для правила по нескольким строкам нужна другая точка сериализации или соответствующая изоляция. [Блокировки и write skew в PostgreSQL](../data/postgresql/transactions.md)

JPQL bulk `UPDATE` и `DELETE` изменяют данные напрямую в БД: обычный dirty checking, автоматический bump версии и обработка каждой уже загруженной сущности здесь не выполняются. Состояние контекста может устареть. Если надо сохранить ранние изменения, сначала flush. После bulk-операции используй новый контекст либо `clear`/осознанный `refresh`. Для репозиториев с `@Modifying` проверь параметры `flushAutomatically` и `clearAutomatically`. Очистка до flush способна отбросить несохранённую работу.

[Jakarta Persistence, жизненный цикл, блокировки и bulk update](https://jakarta.ee/specifications/persistence/3.1/jakarta-persistence-spec-3.1)

## 8. ORM и проблема N+1

**Короткий ответ.** N+1 — запрос за списком сущностей и серия дополнительных запросов при загрузке связей. Если пять заказов ссылаются на одного клиента, первый уровень кеша может сократить число обращений. Для проверки бери набор с разными клиентами. Важно измерить и число запросов, и объём результата.

```java
List<Order> orders = orderRepository.findAll();      // 1 запрос
for (Order order : orders) {
    order.getCustomer().getName();                    // + N запросов
}
```

`FetchType.LAZY` не устраняет проблему: он лишь откладывает загрузку до первого обращения.

| Способ | Когда подходит |
|---|---|
| DTO / projection | Нужны только отдельные поля, а не сущности целиком |
| `JOIN FETCH` | Нужна связь `to-one` или небольшая `to-many` без пагинации |
| `@EntityGraph` | То же, но декларативно, без переписывания JPQL |
| Batch fetching (`@BatchSize`, `hibernate.default_batch_fetch_size`) | Коллекции + пагинация: вместо N запросов — несколько запросов с `IN (...)` |

```java
@Query("select o from Order o join fetch o.customer where o.status = :status")
List<Order> findWithCustomerByStatus(@Param("status") OrderStatus status);
```

Подводные камни:

- `JOIN FETCH` для `to-many` размножает строки, а вместе с пагинацией Hibernate может выполнить её в памяти (предупреждение `HHH90003004` в Hibernate 6 / `HHH000104` в Hibernate 5).
- Два `JOIN FETCH` по коллекциям дают произведение строк. При одновременной загрузке нескольких связей, отображённых как bag (например, список без индекса порядка), Hibernate может выбросить `MultipleBagFetchException`.
- Один гигантский join может оказаться хуже нескольких ограниченных запросов.
- Не загружайте весь граф объектов «на всякий случай».

Как обнаружить: логирование SQL (`spring.jpa.show-sql`, `org.hibernate.SQL`), статистика Hibernate (`hibernate.generate_statistics`), подсчёт запросов в интеграционных тестах.

### LAZY, EAGER и открытый контекст

JPA по умолчанию задаёт `EAGER` для `@ManyToOne` и `@OneToOne`, `LAZY` для `@OneToMany` и `@ManyToMany`. `EAGER` требует загрузить связь, а точную форму SQL выбирает провайдер: возможны как join, так и отдельные select. `LAZY` в спецификации является подсказкой, реализация зависит от маппинга и возможностей провайдера. Переход на `EAGER` у всех связей увеличивает цену каждого запроса и усложняет настройку. Выбирай план под сценарий чтения.

В Hibernate `LazyInitializationException` возникает, когда фактическая загрузка нужна после закрытия соответствующей сессии. В веб-приложении Open Session in View может сохранить контекст до завершения HTTP-запроса. Тогда сериализация способна тихо запустить дополнительные SQL вне исходной сервисной транзакции. Для стабильного ответа загрузи требуемые данные в сервисе и верни DTO. У теста проверь путь до сериализации, включая режим без открытого контекста.

### Страница заказов и их позиции

Допустим, API возвращает 20 заказов на странице и для каждого позиции. Если сделать join заказов и позиций, лимит 20 SQL-строк относится к комбинациям `заказ × позиция`. В таком результате у последнего заказа мог бы оказаться лишь кусок коллекции. Hibernate при некоторых запросах с пагинацией загружает все подходящие строки, а лимит применяет в памяти. В Hibernate есть `hibernate.query.fail_on_pagination_over_collection_fetch`, чтобы ошибка обнаруживалась раньше.

Раздели чтение на два запроса.

1. Запрос ID страницы берёт только заказы и использует детерминированный порядок, например `created_at DESC, id DESC`.
2. Запрос графа загружает только эти ID с позициями. `IN (...)` сам по себе порядок первого запроса не сохраняет. Восстанови его по списку ID при построении ответа.
3. При необходимости общего количества выполни отдельный `count`. Если интерфейсу достаточно перехода вперёд, достаточно получить один лишний элемент и построить признак следующей страницы.

При `READ COMMITTED` запросы могут увидеть разные снимки. Заказ может исчезнуть между шагами, а состав позиций — измениться. Определи контракт чтения. Для согласованного снимка обоих запросов в PostgreSQL подойдёт одна транзакция с `REPEATABLE READ`. Для обычного списка часто допустима свежая версия деталей и обработка редких пропусков.

**Как оценить join.** У одного заказа 20 позиций и 6 заметок. Одновременный join двух коллекций может дать 120 строк с повтором полей заказа. Даже если ORM вернул один объект `Order`, база выполнила работу по соединению, а приложение получило 120 строк. Для двух небольших отдельных загрузок число SQL может стать больше, а трафик и время уменьшиться. Измерь обе характеристики.

[Hibernate ORM, HQL и fetch joins](https://docs.hibernate.org/orm/6.6/querylanguage/html_single/#explicit-fetch-join)

<details>
<summary>Вызвали find, поменяли поле managed-сущности и вышли из транзакции без save. Откуда берётся UPDATE?</summary>

При flush провайдер обнаружит изменение управляемого объекта. Если команда успешно зафиксируется, `UPDATE` сохранится. Если объект был detached к моменту изменения, такой механизм не сработает. Покажи в тесте SQL и перечитай запись из нового контекста.

</details>

<details>
<summary>В тесте весь импорт проходит. В приложении периодически растёт память и блокируется таблица. Что проверишь?</summary>

Измерю размер пакета и длительность транзакции, посмотрю объём managed-объектов и ожидания блокировок. Flush плюс clear уменьшают удержание Java-объектов. Укорочение транзакций освобождает блокировки раньше и требует договориться о частичном результате импорта.

</details>

<details>
<summary>После bulk update find вернул старый статус. Возможен ли такой результат?</summary>

Да. Уже загруженная сущность может остаться в контексте со старым значением. Проверь результат в новом контексте и реши, как синхронизировать текущий. Для последующих конкурентных правок проверь, обновляет ли bulk-запрос версию.

</details>

<details>
<summary>Как доказать, что исправил N+1 при добавлении поля customerName в API?</summary>

Подготовлю заказы разных клиентов и измерю SQL от контроллера до сериализации. Сравню 1 и 30 заказов. План загрузки должен давать ограниченный рост запросов, прогнозируемое число строк и прежний порядок выдачи. Для запроса большого списка отдельно посмотрю план БД.

</details>
