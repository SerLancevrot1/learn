# Spring Boot: как собирается приложение и откуда берутся настройки

[Spring](README.md) · [Контейнер, прокси и транзакции](spring-framework.md) · [Метрики и Actuator](../operations/observability.md#13-java-micrometer-и-actuator)

## Что происходит при запуске

В библиотеке виден класс, в контейнере виден bean. Путь между ними включает регистрацию определения, отбор условий, создание экземпляра и post-processing. Ошибки на разных этапах выглядят по-разному. Класс может быть доступен в runtime, но никогда не попасть в область scanning. Определение может существовать, но bean не удастся создать из-за зависимостей. Созданный объект может быть обёрнут прокси, и тогда вызывающие получают обёртку.

**Spring Framework** предоставляет контейнер, управление bean, AOP и интеграции. **Spring Boot** добавляет согласованный набор зависимостей, механизм автоконфигурации, запуск приложения и эксплуатационные возможности. Стартер — зависимость, подбирающая набор библиотек для сценария. Он может привести на classpath классы, по которым выполнится автоконфигурация. Механизм регистрации автоконфигурации при этом отдельный. Например, JDBC API в библиотеке сам по себе не означает, что приложение уже выбрало параметры DataSource и может успешно соединиться с базой.

### Три пути к bean

| Путь | Пример | Где искать причину отсутствия |
| --- | --- | --- |
| Component scan | `@Service` в пакете приложения | Корень scanning и правила включения пакетов |
| Явная конфигурация | `@Configuration` и фабричный метод `@Bean` | Где импортировали конфигурацию, какой профиль или условие сработало |
| Boot auto-configuration | Подготовленная библиотекой конфигурация | Runtime-зависимости, файл imports, результат условий и пользовательские bean |

`@SpringBootApplication` совмещает, среди прочего, запуск component scanning и автоконфигурации. Положение класса приложения обычно задаёт пакет, начиная с которого ищут компоненты. Контроллер в соседней ветке пакетов может остаться вне области, хотя исходник собрался. Для нескольких модулей лучше обозначить явные входные конфигурации, чем без необходимости расширять scanning на всё дерево организации.

### До и после создания экземпляра

`BeanDefinition` содержит описание того, что контейнер собирается создать. `BeanFactoryPostProcessor` работает с конфигурационными метаданными до создания обычных bean. `BeanPostProcessor` получает экземпляры в процессе инициализации и может возвращать обёртку. При диагнозе «в тесте у объекта есть аннотация, но действие не применяется» проверь, получен ли этот экземпляр из контекста, существует ли нужная инфраструктура и проходит ли вызов через выдаваемый контейнером объект.

Конструктор полезен для обязательных зависимостей. `@PostConstruct` полезен для инициализации после внедрения. Вызов внутри `@PostConstruct` нельзя считать полноценной точкой проверки внешнего AOP-вызова. Например, вызов транзакционного метода на `this` по-прежнему проходит напрямую. Большая сетевая загрузка на этапе инициализации делает запуск зависимым от удалённой системы. Если работа обязательна до готовности, укажи предел времени и наблюдай результат. Если она может идти после запуска, дай ей отдельное состояние и повтор.

### Обязательные, необязательные и множественные зависимости

Типичная ошибка — зарегистрировать две реализации `PaymentClient` и ожидать, что контейнер догадается о выборе для конкретного use case. `@Qualifier` уточняет семантическую роль, `@Primary` задаёт предпочтительного кандидата для одиночной зависимости. Инъекция `List<PaymentClient>` получает несколько подходящих bean, порядок при необходимости определяется средствами упорядочивания. Используй `Map<String, PaymentClient>` с учётом того, что ключами будут имена bean. Если внешний код принимает доменный идентификатор провайдера, можно построить собственную проверенную таблицу маршрутизации и явно обнаружить дубликаты на запуске.

`ObjectProvider<T>` позволяет получить зависимость по требованию, в том числе при необязательной конфигурации. Отложенная зависимость полезна для prototype или запроса вне обычного жизненного цикла, но может переместить ошибку с запуска в обработку запроса. Если сервис не способен работать без клиента, лучше обнаружить ошибку при запуске, а выключаемую функцию описать отдельно.

Singleton в Spring привязан к контейнеру и определению bean. Один экземпляр часто используют много запросов параллельно. Поэтому аргументы и промежуточные результаты должны оставаться локальными вызову. Поле `currentOrder` в singleton-контроллере может показать чужие данные. Prototype создаётся при получении из контейнера. Если внедрить его один раз в singleton напрямую, тот далее хранит один выданный экземпляр. Для выдачи нового можно использовать scoped proxy или provider по конкретному контракту.

## Как работает отбор автоконфигурации

Автоконфигурация задаёт типовой путь сборки, а приложение может переопределить его собственными bean. Условие `@ConditionalOnClass` проверяет наличие подходящих классов. `@ConditionalOnMissingBean` предназначено для того, чтобы конфигурация уступила пользовательской реализации. `@ConditionalOnProperty` проверяет настройки окружения. Порядок чтения определений важен, поэтому Boot предписывает использовать проверки bean преимущественно в auto-configuration, которая обрабатывается после пользовательских определений.

### Разбор отсутствующего клиента

Стартер конфигурирует `PricingClient` только если доступна HTTP-библиотека, включено свойство `pricing.enabled` и нет своего `PricingClient`. В IDE тест проходит, в контейнере — `NoSuchBeanDefinitionException`.

1. Сверь фактический артефакт и режим запуска. Тестовая зависимость может присутствовать в IDE и отсутствовать в приложении.
2. Определи, зарегистрировалась ли ожидаемая auto-configuration. Для собственной библиотеки Boot 3 проверь файл `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.
3. В отчёте условий найди конфигурацию и её negative match. Причина может быть в свойстве, отсутствующем классе или в том, что конфигурация уже уступила другому bean.
4. Если bean создан, проверь тип, qualifiers и область видимости контекста. Сообщение `NoUniqueBeanDefinitionException` требует разобраться с неоднозначностью, а не с отсутствием класса.

`debug=true` или запуск с `--debug` помогает получить отчёт условий. Actuator endpoint `conditions` может показать отчёт для живого процесса при нужных настройках. Условия, значения конфигурации и ссылки на окружение относятся к служебным данным. Доступ к диагностическим endpoints предоставляй оператору на отдельной границе.

### Проверка собственной автоконфигурации

У автоконфигурации полезны тесты на то, что она появляется при минимальных условиях, уступает пользовательской реализации и отсутствует при отключении. Для этих сценариев `ApplicationContextRunner` создаёт ограниченный контекст с нужными свойствами и определениями. Такой тест быстрее полного сетевого старта и точно показывает, какое условие проверено. Отдельный smoke test проверяет, что в итоговый JAR попали imports и нужные runtime-зависимости.

## Конфигурация и профили

Параметры приходят из нескольких источников. Упрощённый путь для развернутого сервиса: встроенные config data дают значения по умолчанию, внешние config data позволяют настроить окружение, environment variables и аргументы запуска могут переопределить значения. Точный порядок и отдельные режимы тестов сверяй с документацией версии. Ошибка «переменная есть в Deployment, а приложению пришло другое значение» решается изучением источника эффективного свойства, включая профили, arguments и подключённые config data.

### Типизированные настройки

Для набора связанных параметров лучше определить `@ConfigurationProperties`: Boot преобразует входы по типу, например `500ms` в Duration, а валидация остановит запуск при недопустимом значении. `@Value` полезен для отдельного параметра. Большая группа независимых строк в разных местах усложняет диагностику единиц измерения и проверку совместимости.

```java
@ConfigurationProperties("pricing")
@Validated
record PricingProperties(@NotNull URI baseUrl, @NotNull Duration timeout) {
    PricingProperties {
        if (timeout != null && (timeout.isZero() || timeout.isNegative())) {
            throw new IllegalArgumentException("pricing.timeout must be positive");
        }
    }
}
```

Фрагмент предполагает настройку binding через `@EnableConfigurationProperties` или scanning подходящих классов. Ограничения из Bean Validation требуют соответствующей зависимости. Для обязательного параметра заведи явную ошибку при старте. Если значения по умолчанию продиктованы бизнесом или эксплуатацией, опиши их рядом со свойством и проверь отдельным тестом. Тип Duration защищает от перепутанных миллисекунд и секунд, если формат источника задаёт единицу явно.

У relaxed binding существует соглашение по env: каноническое имя приводится к верхнему регистру, точки заменяются подчёркиваниями, дефисы убираются. Например, `pricing.connect-timeout` соответствует `PRICING_CONNECTTIMEOUT`. Частая ошибка — случайно добавить второе подчёркивание, изменив структуру свойства. Для списка элементы могут иметь индексы. При переопределении источником список обычно заменяется целиком, поэтому не предполагай автоматическое объединение элементов.

**Profiles.** Профиль помогает собрать набор условий для окружения. Один и тот же артефакт может запускаться с разными config data. Для бинарного свойства вроде `pricing.enabled` достаточно отдельной настройки. Для вариантов с разными типами адаптеров могут подойти профили или явные обе реализации с отбором.

**Диагностика конфигурации.** Если видишь, что тайм-аут оказался 30 с вместо 500 мс, сначала ответь, какой объект свойства создал контейнер и откуда взялся параметр. Затем проверь, что значение реально передано клиенту и относится к нужному этапу ожидания. Connect timeout и response timeout действуют на разные фазы. Не распечатывай все настройки: среди них могут быть секреты. Для оператора достаточно имени свойства, источника и отфильтрованного значения там, где это допустимо.

</details>
