# Reactor и WebFlux: границы выполнения, отмена и проверка

[Spring](README.md) · [Практикум Reactor](../../../reactor-demo/README.md) · [Виртуальные потоки и исполнители](../java/async.md)

## Когда MVC и WebFlux дают разную цену

Представь два API. Первый делает один короткий запрос JDBC и строит DTO. Второй читает много медленных внешних источников, нормализует поток событий и отправляет частями. Для первого последовательный код и пул ресурсов понятны. Для второго цепочка с управляемым спросом помогает не удерживать по отдельному платформенному потоку на каждое ожидание. Другой вариант для I/O — виртуальные потоки с ограничением на ресурсы. Выбери модель по месту, где появится ожидание, и по библиотекам на всём пути.

WebFlux позволяет обрабатывать запросы в реактивной модели, часто с небольшим числом event loop worker в выбранном сервере. Если на worker выполнить блокирующий JDBC, сотни других соединений могут ждать его освобождения. Перенос блокирующей операции на отдельный ограниченный scheduler защищает event loop, но оставляет требование к пропускной способности БД. В одной цепочке можно постепенно интегрировать существующий клиент, измеряя границу blocking.

```java
Mono<OrderView> getFromBlockingDao(long id) {
    return Mono.fromCallable(() -> dao.findView(id))
        .subscribeOn(Schedulers.boundedElastic());
}
```

Если написать `Mono.just(dao.findView(id))`, вызов DAO выполнится до сборки `Mono.just`, то есть уже может заблокировать тот поток, который строит цепочку. `fromCallable` откладывает исполнение. Если DAO вернёт null, Mono завершится без значения. Определи, чем в контракте является отсутствие, и обработай `switchIfEmpty`. У `boundedElastic` есть свои ограничения исполнения и очередей. Он не заменяет ограничитель запросов к зависимости.

## Партия заказов и ограничение параллельности

API читает список из ста заказов и для каждого запрашивает калькулятор доставки. `flatMap(this::quote, 8)` ограничивает число одновременно активных внутренних подписок в этом потоке. Если 50 HTTP-запросов одновременно используют схему, общий максимум порядка 400 внутренних работ при полном входе. Общий пул HTTP-клиента или отдельный bulkhead ограничивает доступ ко внешнему ресурсу. Локальное ограничение полезно, чтобы один большой запрос не занял все доступные слоты, но общей вместимостью системы управляют отдельно.

**Порядок.** Допустим, первый заказ медленный, а следующие семь быстрые. `flatMap` допускает выдачу быстрых раньше. `flatMapSequential` может начать работы конкурентно и держать готовые результаты, пока ждёт ранний. `concatMap` сохраняет последовательность подписок и результатов, уменьшая параллелизм. Если UI сопоставляет ответы по orderId, строгий порядок может быть лишним. Если нужно посчитать историю событий одного заказа, перестановка может нарушить инвариант.

**Backpressure.** Subscriber запросом `request(n)` сообщает допустимое число элементов. В цепочке операторы могут читать заранее порциями и хранить буферы. Источник, управляемый pull, способен замедлиться. Если внешняя система присылает данные по push и её нельзя замедлить, нужно выбрать ограниченный буфер, контролируемое отбрасывание, ошибку или долговечную очередь. Для метрик допустима выборка, для денежных команд пропуск элемента меняет результат.

### Отмена клиента и внешняя работа

Клиент закрыл HTTP-соединение во время чтения. Сигнал cancel может пройти вверх и позволить освободить ресурсы, если библиотека и источник поддерживают отмену. Синхронный JDBC или удалённое API может уже выполнять действие. Если отправляешь команду, для повторного запроса проверяй её результат по ключу. Метрику отмены отделяй от ошибки backend. Клиент отменил ожидание — серверная операция могла успешно закончиться.

Для callback очистки важна граница использования. Ресурс, открытый на время реактивной цепочки, должен освобождаться на complete, error и cancel. `usingWhen` позволяет связать асинхронное освобождение с жизненным циклом. `doFinally` подходит для синхронного наблюдения завершения, например увеличения счётчика с типом сигнала. Не запускай из callback независимую очистку с `subscribe()`, если ответ должен дождаться её завершения.

## Контекст запроса и реактивная транзакция

Одно выполнение может перейти между потоками. Обычный ThreadLocal связан с worker, а не с подпиской. Если в нём сохранить ID пользователя и считать его после смены scheduler, значение может пропасть или оказаться чужим при неочищенном локальном состоянии. Reactor Context привязан к подписке и читается в соответствующем месте цепочки, например через `deferContextual`. `contextWrite` влияет на операторов выше по направлению чтения контекста от subscriber к producer.

```java
Mono<String> requestId = Mono.deferContextual(context ->
    Mono.just(context.getOrDefault("requestId", "missing"))
);
Mono<String> enriched = requestId.contextWrite(context ->
    context.put("requestId", "req-42")
);
```

В примере `enriched` при подписке возвращает `req-42`. Запись в Context внутри одной вложенной ветки не делает её общей для независимых подписок. Для observability применяй поддерживаемую интеграцию propagation и проверяй реальную цепочку после смены scheduler, а не только значение в тесте без переключения потока.

Транзакция с реактивным клиентом открывается для выполнения цепочки и связывает ресурс с её контекстом. При `TransactionalOperator` помещай связанные шаги внутрь одной обёрнутой цепочки. `doOnNext(row -> repository.save(row).subscribe())` отделяет запись от исходной операции: транзакция и ошибка этой работы живут отдельно. Используй `flatMap` или `then`, чтобы сохранить жизнь работы внутри схемы. Параллельное использование одного транзакционного соединения требует поддержки драйвером. Последовательное исполнение проще соответствует транзакционному контракту.

## Возврат ошибки и проверка по сигналам

`onErrorResume` заменяет ошибку альтернативным publisher. Если поставить его снаружи всего `Flux`, ошибка одной записи может завершить исходный обход и выдать общий fallback. Если допустима ошибка отдельной карточки, обработай её внутри `flatMap` для этой карточки. Не заменяй ошибку обязательного расчёта нулём без явного контракта. Для empty состояние отдельное: Mono без элемента может означать отсутствие, которое не является ошибкой транспорта.

`retryWhen` повторно подписывается на вышестоящую часть. Если часть включает вставку и сетевой вызов, повтор может снова выполнить оба шага. Поставь границу retry рядом с операцией, которую безопасно повторить. Различай дедлайн всей операции и тайм-аут каждой попытки. Если `timeout` находится внутри повторяемой части, каждая попытка может получить полный свой бюджет. При общем дедлайне поставь его снаружи и ограничь обращения клиента. После тайм-аута эффект может иметь неопределённый исход.

**StepVerifier.** В тесте задай ожидаемые элементы, успешное завершение или ошибку. Для backpressure начни с нулевого спроса и запроси части через `thenRequest`. Для отмены проверь, что ожидаемый ресурс закрывается. Для виртуального времени цепочку с таймерами создавай внутри supplier, чтобы scheduler заменился к моменту сборки. Виртуальные часы тестируют Reactor-таймеры, а реальный сетевой тайм-аут конкретного клиента требует соответствующего интеграционного теста.

## Самопроверка

<details>
<summary>Почему Mono.just(blockingClient.get()) всё равно задержал event loop?</summary>

Java вычисляет аргумент при вызове just. Отложи вызов через fromCallable и назначь scheduler для блокирующего участка. Затем проверь бюджет самой зависимости.

</details>

<details>
<summary>Почему после flatMap с concurrency=4 провайдер всё равно может получить сотню одновременных запросов?</summary>

Лимит действует в одном экземпляре цепочки. Несколько подписок и серверных копий суммируются. Для общего ограничения нужен bulkhead на соответствующем уровне.

</details>

<details>
<summary>Почему транзакционный метод вернул успех, а вызванная вручную подписка на запись упала позже?</summary>

Внутренняя подписка живёт самостоятельно. Включи запись в возвращаемую цепочку и проверь propagation контекста и сигнал ошибки.

</details>
