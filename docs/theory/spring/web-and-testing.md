# Spring MVC и тесты: от HTTP-запроса до commit

[Spring](README.md) · [Контракты HTTP](../architecture/communications.md#http-кэш-и-конкурентные-изменения) · [JPA и Hibernate](jpa.md)

**Ответ за минуту.** Servlet-фильтры обрабатывают запрос до входа в Spring MVC, `DispatcherServlet` выбирает controller, параметры запроса преобразуются и проходят валидацию, controller вызывает сервис. Сервис проверяет бизнес-правила и задаёт границу транзакции. Для теста выбирай слой, на котором может нарушиться нужная гарантия.

## Что происходит с запросом

Представь `POST /orders/42/cancel` с JSON, в котором есть причина отмены.

1. Контейнер сервлетов передаёт запрос цепочке фильтров. Здесь часто выполняются аутентификация, проставление идентификатора запроса и другая обработка, общая для нескольких сервлетов.
2. `DispatcherServlet` через `HandlerMapping` находит обработчик по маршруту, методу HTTP и другим условиям. `HandlerAdapter` организует вызов метода controller.
3. Для аргументов разбираются `@PathVariable`, `@RequestParam`, заголовки и `@RequestBody`. `HttpMessageConverter` десериализует JSON. Для тела с `@Valid` применяются ограничения DTO.
4. Controller передаёт команду сервису. Сервис проверяет, может ли данный пользователь отменить этот заказ, читает его состояние, меняет сущность и сохраняет намерение для отправки события.
5. MVC преобразует результат в статус, заголовки и тело. Исключения этапов MVC обрабатываются через цепочку `HandlerExceptionResolver`, одним из путей является `@RestControllerAdvice`.

Фильтр работает с сырым запросом и ответом и может завершить обработку до MVC. `HandlerInterceptor` работает вокруг MVC-обработчика, который уже выбран. Spring AOP оборачивает вызовы методов bean, проходящие через proxy. У всех разный контекст. Например, servlet-фильтр видит запрос, но обычно ещё не знает, какой controller его обработает, а AOP может работать и для вызова сервиса из Kafka consumer, где HTTP отсутствует.

[Spring Framework 6.2, обработка запроса в DispatcherServlet](https://docs.spring.io/spring-framework/reference/6.2/web/webmvc/mvc-servlet/sequence.html)

### Ошибка входа, бизнес-правила или конфликт записи

| Что проверяем | Где | Пример |
| --- | --- | --- |
| Представление | MVC, десериализация и DTO | JSON читается, поле `reason` непустое, ID имеет нужный тип |
| Полномочие и бизнес-состояние | Сервис и правила домена | Пользователь вправе отменять этот заказ, заказ ещё не передан перевозчику |
| Конкурентная запись | Транзакция и БД | Из двух несовместимых изменений пройдёт допустимое по версии или блокировке |

DTO запроса задаёт форму входа, которую контролирует клиент. DTO ответа задаёт публичную форму результата. Прямое возвращение сущности из controller может запустить ленивые запросы во время сериализации. Обновление прямо из входной сущности усложняет защиту полей, которыми клиент управлять не должен, например текущего статуса или владельца. Преобразование DTO в команду оставляет правила на стороне сервиса.

В Spring MVC 6.2 на валидацию аргументов влияет форма сигнатуры. Ошибка валидации DTO с `@Valid @RequestBody` может дать `MethodArgumentNotValidException`. Ограничения прямо на параметрах метода могут запустить валидацию метода и привести к `HandlerMethodValidationException`. Если API обещает одинаковую форму ошибок, проверь обе ветки и отличи их от нечитаемого JSON. Ошибка аутентификации из security-фильтра возникает раньше MVC и обрабатывается средствами security-цепочки.

[Spring Framework 6.2, валидация MVC](https://docs.spring.io/spring-framework/reference/6.2/web/webmvc/mvc-controller/ann-validation.html)

### Commit и запись HTTP-ответа

Обычно commit происходит, когда управление выходит из транзакционной обёртки вызванного сервиса. MVC формирует HTTP-ответ после этого. Если commit прошёл, а сериализация упала или клиент потерял соединение, запись может существовать, хотя клиент увидел ошибку. Для команды с деньгами или резервом нужен идентификатор операции, по которому повторный запрос вернёт существующий результат. Для выполнения после commit можно использовать событие Spring, если потеря после остановки процесса допустима. Для сохраняемого намерения используется outbox. [Окна сбоя и повторная отправка](../messaging/delivery-patterns.md#9-outbox-и-cdc)

## Чем проверять каждый контракт

| Нужно проверить | Подход | Что реально выполняется |
| --- | --- | --- |
| Переход `NEW → CANCELLED` и отказ для `SHIPPED` | Обычный тест JUnit | Правила домена на собранных в тесте объектах |
| Статус `400`, валидацию, структуру ошибки и JSON | `@WebMvcTest` и MockMvc | MVC, настроенная сериализация и применимые фильтры, зависимость от бизнес-сервиса можно заменить |
| Репозиторий, ограничения, optimistic locking | `@DataJpaTest` с нужной БД | Репозитории, ORM и SQL. Для commit и конкуренции нужны явные границы |
| Сервис через proxy, запись заказа и outbox | `@SpringBootTest` и реальные репозитории | Контекст приложения и транзакции Spring |
| Настоящий сетевой обмен и проверка результата в БД | `@SpringBootTest(webEnvironment = RANDOM_PORT)` | Сервер и HTTP-клиент работают через сокет, запрос обслуживается в другом потоке |

MockMvc проводит запрос по цепочке MVC без открытия настоящего HTTP-порта. Обычный вызов метода controller напрямую полезен для ветвления в самом controller, но не проверяет маршрутизацию, чтение JSON и конвертацию ответа. Срез `@WebMvcTest` не загружает репозитории как обычный полный контекст, поэтому не докажет rollback или число SQL. Если важно проверить отказ неавторизованному запросу, убедись, что срез применяет нужную security-конфигурацию.

`@SpringBootTest` загружает полный контекст, но по умолчанию не запускает встроенный веб-сервер. При `RANDOM_PORT` тестовая транзакция и транзакция сервера независимы, так что rollback в тесте не уберёт запись сервера. Перед HTTP-запросом подготовь доступные серверу зафиксированные данные, а после явно убери результат или используй изолированную БД. Для PostgreSQL можно поднять реальный экземпляр через Testcontainers. В Spring Boot 3.4 `@ServiceConnection` связывает поддерживаемые контейнеры с конфигурацией приложения при наличии соответствующей тестовой зависимости.

[Spring Boot 3.4, тестирование приложений](https://docs.spring.io/spring-boot/3.4/reference/testing/spring-boot-applications.html) · [Spring Boot 3.4, Testcontainers](https://docs.spring.io/spring-boot/3.4/reference/testing/testcontainers.html)

### Проверь поведение, которое изменится при сбое

**Rollback.** Вызови настоящий bean через proxy и создай исключение после записи. Проверь из новой транзакции, что заказ и outbox либо оба появились, либо оба отсутствуют. Проверять только исключение недостаточно, потому что оно могло возникнуть после успешного commit второй операции.

**Конкуренция.** Создай две независимые транзакции и координируй шаги барьером. Например, обе должны прочитать версию 7 перед первой попыткой записи. Фиксированный `sleep` редко даёт воспроизводимый порядок. У ожиданий в тесте есть тайм-аут, иначе при ошибке одного worker тест может зависнуть.

**Внешние вызовы.** Для сценария «провайдер обработал, ответ потерялся» заглушка должна показать неизвестный исход, а тест — сохранить один и тот же ключ при повторе. Для проверки формы запроса и обработки статусов используй HTTP-заглушку. Для контракта команды проверь ещё и эффект в БД.

## Самопроверка

<details>
<summary>Почему 400 из MockMvc ничего не доказывает о проверке уникальности заказа?</summary>

Запрос мог остановиться при разборе JSON или валидации DTO до вызова сервиса. Уникальность проверяют на том слое, который её гарантирует. Для ограничения БД создай конфликт и дождись flush или commit, в зависимости от ограничения.

</details>

<details>
<summary>Тест @SpringBootTest с RANDOM_PORT и @Transactional оставляет записи. Откуда они берутся?</summary>

HTTP-запрос выполняется в серверном потоке и фиксирует отдельную транзакцию. Rollback тестового потока откатывает только его работу. Подготовь и убери данные явно или подними изолированное окружение.

</details>

<details>
<summary>Какой тест доказывает, что отмена заказа записывает outbox атомарно?</summary>

Интеграционный тест вызывает сервис через Spring proxy, использует реальную транзакцию и создаёт сбой между шагами. Из нового контекста проверяется состояние обеих таблиц. Добавь успешный сценарий, чтобы исключить ложный вывод «откат сработал», когда ни один шаг вообще не выполнялся.

</details>
