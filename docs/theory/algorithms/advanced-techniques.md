В каждой задаче сначала найди лишнюю повторяющуюся работу. Затем сформулируй, какая информация даёт ответ быстрее. Прогони один вход вручную и только после этого пиши код. Приведённые решения рассчитаны на Java 17.

## Разностный массив для многих обновлений диапазона

Дан массив из N значений, сначала нули. Есть M операций «прибавить `delta` ко всем значениям на полуоткрытом интервале `[l,r)`». После всех операций требуется вывести результат. Наивный обход каждого интервала может стоить `O(NM)`. У постоянной прибавки меняются только две границы. Введи `diff[l] += delta` и `diff[r] -= delta`. Префиксная сумма по diff вернёт действующее изменение в каждой позиции.

```java
record Update(int from, int to, long delta) {}

static long[] rangeAdds(int size, List<Update> updates) {
    long[] changes = new long[size + 1];
    for (Update update : updates) {
        changes[update.from()] += update.delta();
        changes[update.to()] -= update.delta();
    }

    long running = 0;
    long[] result = new long[size];
    for (int i = 0; i < size; i++) {
        running += changes[i];
        result[i] = running;
    }
    return result;
}
```

Предполагаются допустимые границы и суммы в диапазоне long. У `size=5`, обновлений `[1,4)+3` и `[3,5)-1` результат `[0,3,3,2,-1]`. Размер diff равен N+1, поэтому можно записать отмену на правой границе N. Пустой интервал даёт два взаимоисключающих изменения в одной позиции. Сложность `O(N+M)`, память `O(N)`. Если требуется чередовать обновления и запросы, заранее просуммировать diff не получится. Например, дерево Фенвика над diff позволяет обновлять его точки и получать префиксы по `O(log N)`.

**Инвариант.** После обработки позиции i переменная running содержит сумму всех обновлений, интервалы которых покрывают i. При переходе к следующей позиции учитываются явные начала и концы. Это же рассуждение работает в событиях времени. Для большой шкалы миллисекунд с небольшим числом событий храни только границы и отсортируй их, а не создавай массив на всю историю.

## Sweep line для нагрузки по времени

Нужно найти максимальное число параллельно выполнявшихся задач и первый момент пиковой нагрузки. У каждой задачи есть начало и исключающий конец. Запиши событие +1 в начале и −1 в конце, сгруппируй одинаковые моменты и обработай их по порядку. Накопленная сумма после применения всех событий времени t соответствует участку `[t, next_t)`. Если обработать начало раньше конца в той же точке и измерить мнимое промежуточное состояние, получится ложное перекрытие. Группировка изменений устраняет зависимость от порядка.

Пример с интервалами `[1,4)`, `[2,3)`, `[4,6)` даёт события 1:+1, 2:+1, 3:−1, 4:0, 6:−1. Максимум 2 держится на `[2,3)`. Задача, завершающаяся в 4, не перекрывается с начинающейся в 4. Если условия используют закрытые интервалы, поведение равных концов меняется. Сформулируй, что именно означает точное совпадение времени, до написания comparator.

Проектный вариант считает занятые ресурсы при неперекрывающихся по семантике временных интервалах. Если в задаче нужно также назначить номера комнат и быстро переиспользовать освободившуюся, нужна куча концов с ID комнаты. Sweep line только считает пик и его участки. Можно найти общую длительность превышения лимита, складывая длины участков между событиями при активном счётчике выше порога. Сортировка событий занимает `O(M log M)`, затем один проход.

## 0–1 BFS, когда часть переходов бесплатна

Задача: из вершины A попасть в B с минимальным числом платных переходов. Каждый переход имеет стоимость 0 или 1. Обычный BFS минимизирует количество рёбер. Он может предпочесть прямой путь стоимости 1 более длинному бесплатному. Для весов 0 и 1 вместо общей приоритетной очереди достаточно deque. При улучшении расстояния ребром веса 0 поставь вершину в начало, веса 1 — в конец.

```java
record Edge(int to, int cost) {}
record Visit(int node, int distance) {}

static int[] shortest01(List<List<Edge>> edges, int start) {
    int[] dist = new int[edges.size()];
    Arrays.fill(dist, Integer.MAX_VALUE);
    Deque<Visit> queue = new ArrayDeque<>();
    dist[start] = 0;
    queue.addFirst(new Visit(start, 0));

    while (!queue.isEmpty()) {
        Visit visit = queue.removeFirst();
        if (visit.distance() != dist[visit.node()]) {
            continue;
        }
        for (Edge edge : edges.get(visit.node())) {
            int candidate = visit.distance() + edge.cost();
            if (candidate < dist[edge.to()]) {
                dist[edge.to()] = candidate;
                Visit updated = new Visit(edge.to(), candidate);
                if (edge.cost() == 0) {
                    queue.addFirst(updated);
                } else {
                    queue.addLast(updated);
                }
            }
        }
    }
    return dist;
}
```

Предполагаются корректные номера вершин и веса из множества 0,1. Начальная метка равна нулю, неизвестная — MAX_VALUE. В очереди валидные метки отстают от текущего минимума максимум на единицу, поэтому добавление в начало и конец поддерживает нужный порядок. Устаревшие записи отбрасываются. Каждая вершина при финальном извлечении обрабатывает свои рёбра один раз, суммарная сложность `O(V+E)`. Для более общих неотрицательных весов нужна Dijkstra или другая подходящая структура.

**Проверь отказ от visited при добавлении.** Из A есть ребро веса 1 к C и бесплатное к B. Из B бесплатное к C. Если C пометили окончательно достигнутой сразу при добавлении с меткой 1, путь через B потеряется. Завершённая оптимальная метка определяется порядком извлечения, а не фактом первого добавления.

## Топологический порядок с уровнями работы

Известны зависимости миграций. Ребро A → B означает, что B можно выполнить после A. Для ответа «можно ли выполнить все» подойдёт алгоритм Кана. Считай входящие рёбра, положи вершины без зависимостей в очередь. После извлечения вершины уменьшай счётчик её последователей. Если обработано меньше V, в оставшейся части есть цикл. Граф может содержать независимые компоненты, поэтому положи в очередь все начальные вершины.

Если интересуют параллельные волны, обрабатывай текущий размер очереди как один уровень. Задачи, освобождённые внутри этой волны, попадут в следующий. Это минимальное число волн при одинаковой длительности задач и неограниченном числе worker. Для разной длительности вычисляй самое раннее время завершения как `duration(task) + max(finish(dependency))` в топологическом порядке. Максимум по графу даёт критический путь при неограниченном числе ресурсов. При ограничении по worker надо дополнительно решать расписание. Одного топологического порядка недостаточно для оптимального распределения.

Для воспроизводимого текстового результата можно держать допустимые вершины в `PriorityQueue` по имени. Тогда следующий минимальный доступный узел определяется явно. Это увеличивает стоимость добавления и извлечения. Если раннее завершение зависимости уже позволяет запустить следующую, жёсткое пакетное выполнение волнами может простаивать, ожидая последнюю длинную задачу предыдущей волны. Различай вычисление теоретической границы и реальное исполнение с обратной связью завершений.

## Куча для объединения нескольких отсортированных источников

Сервис получает K списков логов, каждый отсортирован по времени и локальному ID. Нужно последовательно построить один поток. Наивное объединение всех элементов и сортировка требует память под весь набор. В куче держи только текущую голову каждого непустого списка. Извлеки минимальную голову, выдай её и добавь следующую запись из её источника. Минимум среди голов — глобальный минимум среди ещё не выданных элементов, потому что за каждой головой находятся только такие же или более поздние.

Для N записей стоимость `O(N log K)`, память `O(K)` для кучи плюс состояние итераторов. Если нужно получить первые 50, цикл остановится после 50 выдач. Для воспроизводимости при одинаковых timestamp включи устойчивый tie-breaker, например ID источника и позицию. Если один файл ещё не дошёл, известные головы не гарантируют, что у медленного источника нет более ранней записи. Потоковая обработка неполных источников уже требует политики ожидания, watermark или обозначения неполного результата.

### Сортировка результатов по настоящему порядку

Итератор `PriorityQueue` не обходит элементы в порядке приоритета. Для получения порядка последовательно извлекай вершины или сортируй копию. В задаче Top-K часто на собеседовании выводят саму кучу и считают, что список уже упорядочен. Проверяй контракт результата: множество кандидатов и их отсортированный вывод — два шага.

## Как проверить готовый алгоритм

После обычного примера прогони минимум один случай, который ломает инвариант у наивного решения. Для разностного массива — правая граница N и отрицательная прибавка. Для топологического обхода — цикл во второй компоненте. Для кучи — пустой источник, одинаковое время и очень длинный одиночный источник. Для 0–1 BFS — путь с меньшей стоимостью и большим числом шагов. Добавь случаи задачи, где число элементов умещается в int, а сумма расстояний или денег требует long.

Если есть время, сравни на малых случайных входах с простым эталоном. Для обновлений массива эталон проходит каждый интервал поэлементно. Для расписания можно проверить каждую пару и события в фиксированной временной шкале. Такая проверка обнаруживает множество ошибок границ. На больших данных затем измеряй именно заявленную асимптотику, а не поведение одного малого списка.

## Самопроверка

<details>
<summary>Почему в разностном массиве значение в правой границе уменьшается?</summary>

Интервал полуоткрытый. Положительная прибавка действует после левой границы до правой. В точке правого конца нужно убрать её из префиксной суммы.

</details>

<details>
<summary>Почему 0–1 BFS не подходит для весов 0 и 2 без изменения рассуждения?</summary>

Если все ненулевые веса одинаковы 2, можно масштабировать их до 1 и потом умножить ответ. Для множества 0,1,2 одной очереди с добавлением в начало/конец недостаточно для доказанного порядка. Нужна структура для нескольких приоритетов или Dijkstra.

</details>

<details>
<summary>Граф без циклов имеет десять независимых задач и ещё одну задачу, ожидающую их все. Как найти теоретическое раннее завершение?</summary>

При достаточном количестве worker первые десять могут стартовать одновременно. Следующая стартует после самой долгой из них и выполняется своё время. При ограниченных worker учти расписание.

</details>

<details>
<summary>Для первых N записей объединяем десять больших файлов. Почему не хватит сначала взять первую строку только первого файла?</summary>

Самая ранняя запись может быть в любом источнике. Нужно знать голову каждого участвующего отсортированного потока. После этого извлекаешь глобальный минимум и продвигаешь только его источник.

</details>
