# Лабораторные по Git

[Теория](../../theory/engineering/git.md) · [Подсказки и решения](solutions.md) · [Вопросы на собеседовании](../../interview/base/git.md) · [Все лабораторные](../README.md)

Цель — понимать результат команды и уметь повторить действия через IntelliJ IDEA. Задания 0–12 проходи по порядку. На одно занятие достаточно 1–2 лабораторных по 20–40 минут. После каждого задания сначала объясни, что изменилось в файлах, индексе, истории и на сервере, затем проверь себя командами.

Инструкции рассчитаны на PowerShell, установленный Git 2.32+ и обычный текстовый редактор. Java, Docker, GitHub и доступ в интернет для выполнения не нужны. Текстовые файлы заменяют исходный код: механика Git одинаковая. Можно открыть папки `alice` и `bob` в разных окнах IDEA и повторять действия через интерфейс.

## Правила песочницы

Материалы лежат здесь, а учебные репозитории создаются **за пределами проекта learn**. Тогда команды reset, merge и clean относятся к учебной истории. Не выполняй команды лабораторных в корне `learn`.

Перед каждой лабораторной:

```powershell
Set-Location (Join-Path $gitLabRoot 'alice')
Get-Location
git rev-parse --show-toplevel
git status
```

Если открыл новое окно терминала, заново задай `$gitLabRoot` полным путём к созданной песочнице. Если `status` показывает незавершённый merge/rebase, закончи или отмени именно эту операцию, прежде чем продолжать. В заданиях, требующих чистого дерева, статус не должен содержать изменений. У всех учебных файлов содержимое выдуманное; не используй настоящие пароли.

`Set-Content` заменяет содержимое файла, `Add-Content` дописывает строку. В этих примерах содержимое файлов — ASCII, поэтому различия кодировки между версиями PowerShell не мешают упражнениям. Предупреждения LF/CRLF возможны; не меняй глобальную конфигурацию ради лабораторных.

## 0. Создать локальный сервер и двух разработчиков

**Теория:** разделы 1–3 и 7. **Время:** 15 минут.

Выполни подготовку один раз. Новый каталог не должен существовать; при совпадении имени выбери другое.

```powershell
$gitLabRoot = Join-Path $env:USERPROFILE ('git-lab-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
if (Test-Path -LiteralPath $gitLabRoot) { throw 'Choose a new sandbox path' }
New-Item -ItemType Directory -Path $gitLabRoot | Out-Null
Set-Location $gitLabRoot
git init --bare -b main remote.git
git clone remote.git alice
Set-Location alice
git config user.name 'Alice Student'
git config user.email 'alice@example.test'
Set-Content README.md '# Training project'
Set-Content notes.txt 'start'
Set-Content app.properties 'timeout=10'
git add README.md notes.txt app.properties
git commit -m 'Initial training project'
git push -u origin main
Set-Location $gitLabRoot
git clone remote.git bob
Set-Location bob
git config user.name 'Bob Student'
git config user.email 'bob@example.test'
Set-Location (Join-Path $gitLabRoot 'alice')
$gitLabRoot
```

Сохрани выведенный путь. `remote.git` — bare-репозиторий: в нём есть история и ссылки, но нет обычной рабочей директории. Он выполняет роль сервера на том же компьютере. Напрямую учебные файлы в нём не редактируй. Предупреждение о клонировании пустого репозитория при создании alice ожидаемо.

**Задания:**

1. Выполни `git remote -v`, `git branch -vv`, `git log --oneline`.
2. Объясни разницу между alice, bob, remote.git и origin/main.
3. Убедись, что у Alice и Bob одинаковый `git rev-parse HEAD` и чистый status.

**Готово, если:** в обоих клонах есть один начальный коммит, локальная main отслеживает origin/main. Настройки имени/почты заданы локально и не изменили твои глобальные настройки.

## 1. Собрать коммит и увидеть три версии файла

**Теория:** разделы 2 и 4. **Начало:** alice, main, чистое дерево.

1. Создай ветку `lab/staging`.
2. Допиши в notes.txt строку `prepared`, выполни `git add notes.txt`.
3. Допиши строку `later`, но больше не выполняй add.
4. До запуска команд запиши, что покажут `diff` и `diff --staged`. Проверь.
5. Создай коммит `Add prepared note`. Проверь `git show HEAD:notes.txt`: строки later в коммите быть не должно.
6. Добавь и закоммить оставшуюся строку отдельным коммитом.
7. Допиши `temporary`, добавь файл в индекс, затем убери его из индекса через `restore --staged`. Убедись, что строка осталась в файле. Удали только эту временную правку через `restore notes.txt`.
8. Перейди на main и слей lab/staging. Посмотри граф: это fast-forward. Отправь main на сервер.

**Готово, если:** два смысловых коммита, строка later только во втором, временной строки нигде нет, дерево чистое.

**Вопрос:** почему после add файл мог снова стать modified? В IDEA найди аналог выбранных staged-изменений.

## 2. Игнорирование и уже отслеживаемый файл

**Теория:** разделы 3–4. **Начало:** alice, main, чистое дерево.

1. Создай `lab/ignore`.
2. Создай fake.env с выдуманным значением `TOKEN=demo`, добавь и закоммить его.
3. Добавь fake.env в `.gitignore`, создай также debug.log и правило `*.log`. Закоммить `.gitignore`.
4. Измени fake.env. Почему status всё ещё его показывает, а debug.log не показывает?
5. Убери fake.env из отслеживания командой `git rm --cached fake.env`, закоммить.
6. Убедись, что файл физически остался, но `git ls-files fake.env` ничего не выводит. Используй `git check-ignore -v fake.env`.
7. Слей ветку в main и отправь main.

**Готово, если:** fake.env и debug.log игнорируются, в актуальном коммите их нет, а в раннем коммите fake.env по-прежнему виден через `git show HASH:fake.env`.

**Вопрос:** почему это не способ обезвредить опубликованный секрет?

## 3. Ветки и настоящее слияние двух историй

**Теория:** разделы 5–8. **Начало:** alice, main, чистое дерево.

1. Создай `lab/feature`. Создай feature.txt со строкой `new feature`, закоммить.
2. Вернись на main. Создай maintenance.txt со строкой `maintenance`, закоммить.
3. Нарисуй граф на бумаге. Предскажи, возможен ли fast-forward.
4. На main выполни `git merge lab/feature -m 'Merge training feature'`.
5. Найди merge-коммит и его родителей: `git show --no-patch --format='%h %p %s' HEAD`.
6. Проверь наличие обоих файлов, отправь main. Удали локальную ветку lab/feature через `branch -d`.

**Готово, если:** у merge-коммита два родителя, обе линии видны в графе, ветка задачи удалена, её изменения сохранены.

**Вопрос:** почему `git merge main` на feature означал бы другое направление операции?

## 4. Намеренно создать конфликт и разрешить его

**Теория:** раздел 9. **Начало:** alice, main, чистое дерево, app.properties содержит timeout=10.

1. Создай `lab/timeout`. Замени строку на `timeout=60`, закоммить.
2. Вернись на main, замени ту же строку на `timeout=30`, закоммить.
3. Попробуй слить lab/timeout. Ожидается конфликт и ненулевой код завершения команды.
4. Посмотри status и маркеры в app.properties. Не нажимай «принять всё».
5. Сначала отмени merge командой `git merge --abort`. Убедись, что вернулся timeout=30 и дерево чистое.
6. Повтори merge. По условию продукта итоговый timeout должен стать **45**. Отредактируй файл, подготовь его, заверши merge.
7. Проверь `git diff --check`, status и итоговый файл; отправь main.

**Готово, если:** в истории есть merge-коммит, в файле ровно timeout=45, маркеров нет, status чистый. Первый отменённый merge не создал коммит.

**Вопрос:** почему правильный результат не совпал целиком ни с одной стороной? Повтори разрешение через трёхпанельный редактор IDEA в отдельной учебной ветке по желанию.

## 5. Прервать задачу через stash

**Теория:** раздел 11. **Начало:** alice, main, чистое дерево.

1. Создай `lab/stash`. Измени notes.txt и создай новый draft.txt.
2. Сохрани работу через `stash push -u` с сообщением. Убедись, что draft.txt исчез из рабочей директории, а status чистый.
3. Перейди на main, посмотри историю, затем вернись в lab/stash.
4. Найди запись в stash list, посмотри её содержимое, восстанови через apply.
5. Проверь, что вернулись и старый файл, и новый. Убедись, что запись всё ещё существует.
6. Закоммить восстановленную работу. Затем удали именно проверенную запись stash через drop.
7. Слей lab/stash в main и отправь main.

**Готово, если:** оба изменения попали в коммит, stash пуст, рабочее дерево чистое.

**Вопрос:** что изменилось бы без `-u`? Почему stash — неудобное долговременное хранилище?

## 6. Два разработчика: fetch и отклонённый push

**Теория:** раздел 7. **Начало:** Alice на main, всё предыдущее отправлено, дерево чистое.

1. В bob перейди на main и выполни `git pull --ff-only`, чтобы получить результаты предыдущих работ.
2. В alice создай alice.txt, закоммить и отправь main.
3. Не обновляя bob, создай там bob.txt, закоммить и попробуй отправить main. Push должен быть отклонён.
4. В bob запиши хеш HEAD и содержимое alice.txt (его ещё нет). Выполни только `git fetch origin`. Изменились ли рабочие файлы и HEAD?
5. Посмотри `git log --graph --oneline --all` и `git log main..origin/main`.
6. Проверь, что `git pull --ff-only` отказывается объединять разошедшиеся истории. Затем интегрируй origin/main в bob через merge, отправь main.
7. Вернись в alice и обнови main через `pull --ff-only`.

**Готово, если:** оба клона и сервер указывают на общий коммит с обоими файлами; force push не понадобился. Проверка: одинаковый `git rev-parse HEAD` в обоих клонах.

**Вопрос:** чем отличается отказ по расхождению истории от отказа из-за отсутствия прав?

## 7. Rebase своей ветки и подготовка истории

**Теория:** разделы 8–9. **Начало:** alice, main, чистое дерево.

1. Создай `lab/rebase`, создай rebase.txt со строкой `first`, закоммить. Допиши `second`, создай второй коммит.
2. Сохрани страховочную ветку `backup/lab-rebase` на текущем коммите, запиши хеши двух коммитов.
3. Перейди на main, создай base.txt со строкой `new base`, закоммить. Вернись в lab/rebase.
4. Выполни `git rebase main`. Посмотри граф и новые хеши. Убедись, что обе строки сохранены и base.txt присутствует.
5. Выполни `git rebase -i HEAD~2`: первый коммит оставь pick, у второго поставь squash. Сохрани понятное общее сообщение.
6. Проверь, что `git rev-list --count main..lab/rebase` равно 1, а содержимое сохранилось.
7. Перейди на main, слей lab/rebase и отправь main. Backup пока сохрани для сравнения.

**Готово, если:** изменение задачи представлено одним коммитом поверх новой main; старые коммиты можно посмотреть через backup.

**Дополнительно:** повтори rebase в новой ветке, меняя timeout в обеих линиях. Разреши остановку через add и `rebase --continue`; в другой попытке проверь `rebase --abort`.

## 8. Restore, amend, reset и revert на одном примере

**Теория:** раздел 10. **Начало:** alice, main, чистое дерево. Вся работа — только в новой `lab/undo`; в main её не сливаем.

1. Создай undo.txt со строкой `version-1`, закоммить.
2. Замени строку на `version-2`, добавь в индекс. Выполни `restore --staged undo.txt`, проверь, что строка осталась. Затем `restore undo.txt` — теперь должна вернуться version-1.
3. Допиши `forgotten`, выполни add и `commit --amend --no-edit`. Проверь, что изменился хеш последнего коммита.
4. Создай extra.txt, закоммить. Выполни `git reset --soft HEAD~1`. Объясни, почему extra.txt находится в индексе; перекоммить его.
5. Выполни `git reset --mixed HEAD~1`. Убедись, что extra.txt остался на диске, но теперь untracked: до отменённого коммита его не существовало. Добавь и снова закоммить.
6. Отмени последний коммит через `git revert --no-edit HEAD`. Проверь, что extra.txt исчез, а история содержит исходный и обратный коммиты.
7. Вернись на main, сохрани ветку lab/undo для просмотра.

**Готово, если:** можешь объяснить разницу между всеми четырьмя операциями и показать её в status/log. Никакой общей истории не переписывалось.

## 9. Cherry-pick и тег выпуска

**Теория:** раздел 12. **Начало:** alice, main, чистое дерево.

1. Создай `lab/hotfix`. Создай unrelated.txt, закоммить как незавершённую будущую возможность.
2. Создай hotfix.txt со строкой `fixed critical bug`, закоммить отдельно. Скопируй хеш второго коммита.
3. Вернись на main и перенеси только второй коммит через cherry-pick.
4. Убедись, что hotfix.txt появился, unrelated.txt отсутствует, а у перенесённого коммита новый хеш. У него другой родитель, поэтому в этом сценарии хеш точно изменится.
5. Создай аннотированный тег `lab-v1.0.0`, отправь main и именно этот тег на локальный сервер.
6. В bob выполни fetch, проверь `git show lab-v1.0.0`.

**Готово, если:** main получила только исправление, а тег указывает на результат. Ветка lab/hotfix осталась отдельной.

## 10. Спасти коммит через reflog

**Теория:** разделы 10 и 12. **Начало:** alice, main, чистое дерево. Операция reset выполняется только в lab/rescue.

1. Создай `lab/rescue`, создай rescue.txt со строкой `valuable work`, закоммить.
2. Убедись через status, что незакоммиченных изменений нет. Выполни `git reset --hard HEAD~1`. Учебный файл исчезнет, ветка перестанет указывать на его коммит.
3. Через `git reflog` найди прежний коммит по сообщению, проверь `git show HASH`.
4. Создай `rescue/saved` на найденном хеше. Переключись на неё и проверь файл.
5. Вернись на main. Спасённую ветку сохрани.

**Готово, если:** полезный коммит снова доступен через имя ветки и файл читается. Случайное имя `HEAD@{1}` не подставляй без просмотра reflog: там могло быть другое действие.

**Вопрос:** помог бы reflog, если бы rescue.txt никогда не добавлялся и был удалён через clean?

## 11. Найти регрессию через bisect

**Теория:** раздел 12. **Начало:** alice, main, чистое дерево. Создай lab/bisect.

Создай последовательность из шести коммитов. Каждый меняет только price.txt:

| Сообщение | Содержимое price.txt |
| --- | --- |
| Price step 1 | `100` |
| Price step 2 | `100` и на следующей строке `note=2` |
| Price step 3 | `200` и `note=3` |
| Price step 4 | `200` и `note=4` |
| Price step 5 | `200` и `note=5` |
| Price step 6 | `200` и `note=6` |

Представь, что правильная цена — 100, а 200 означает ошибку.

1. Посмотри хеш первого коммита (`git log --oneline -6`). Последний объяви bad, первый — good.
2. Запусти bisect. На каждой остановке читай первую строку price.txt через `Get-Content price.txt -TotalCount 1` и отмечай good/bad.
3. Дождись сообщения о первом плохом коммите. Он должен иметь сообщение Price step 3.
4. Выполни `git bisect reset`, проверь возвращение к lab/bisect, затем перейди на main.

**Готово, если:** найден первый плохой коммит, а bisect завершён. Объясни, почему правило проверки должно быть воспроизводимым.

## 12. Итоговая задача без пошагового рецепта

**Начало:** оба клона на чистой main; обнови их с сервера. Используй собственные новые имена веток и файлов, чтобы не задеть предыдущие упражнения.

Сценарий: Alice делает проверку платежей, Bob одновременно исправляет конфигурацию. На review Alice заметила, что забыла один файл, а после интеграции обнаружена ошибка в одном из её изменений.

1. Alice создаёт ветку задачи, делает два коммита, исправляет последний через amend до публикации.
2. Bob делает и отправляет изменение main. Alice получает его, объясняет выбранную стратегию интеграции и обновляет свою ветку. Хотя бы одна правка должна затронуть ту же строку, чтобы возник конфликт.
3. Alice разрешает конфликт по смыслу, проверяет результат, отправляет ветку с upstream.
4. Из main слей ветку с отдельным merge-коммитом и отправь. Отмени эффект одного обычного коммита задачи через revert в новой ветке исправления; при необходимости разреши конфликт. Слей исправление и отправь.
5. Отметь итог тегом `lab-final`, отправь его. Обнови Bob, докажи одинаковое содержимое и HEAD.
6. Удали завершённую ветку задачи локально и на сервере. После fetch --prune покажи, что локальные ветки и remote-tracking ссылки — разные вещи.

**Отчёт:** сохрани вне учебных клонов короткий файл с графом истории, командами, причиной каждого решения и результатами проверок. Полный пример возможного решения есть в [подсказках](solutions.md), но сначала попробуй самостоятельно.

## Как оценить результат

За каждую лабораторную 1–11 поставь 0–2 балла: 0 — не получилось; 1 — получилось по решению; 2 — получилось самостоятельно и можешь объяснить состояние до/после. Итоговую задачу оцени отдельно: удалось ли довести весь сценарий до одинакового состояния двух клонов без потери работы?

Повтори задания с 0–1 баллом через несколько дней. Затем пройди [вопросы](../../interview/base/git.md): объяснение ответа важнее угаданной буквы.

Песочницу можно оставить для повторения. Этот практикум не меняет Git-настройки learn, не коммитит учебные изменения в learn и не отправляет ничего во внешние сервисы.

Источники механики: [официальный справочник Git](https://git-scm.com/docs), [bare-репозиторий](https://git-scm.com/docs/git-init), [Pro Git](https://git-scm.com/book/ru/v2). Сценарии и критерии проверки составлены для этого практикума.
