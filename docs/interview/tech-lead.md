## Как запускать стенды в Docker

**Образ** содержит программу и её окружение. **Контейнер** — экземпляр, запущенный из этого образа. **Сервис** — имя и настройки контейнера в `compose.yaml`. Например, `primary` обозначает сервис, а `postgres:17` — его образ. Docker запускает процессы, а Compose создаёт из описания весь набор сервисов, подключает их к общей сети и монтирует файлы и тома.

### Терминал и рабочий каталог

Открой PowerShell 7 в терминале IDE или Windows Terminal. Запусти Docker Desktop с Linux-контейнерами. Из любого каталога можно проверить клиент и движок.

```powershell
$PSVersionTable.PSVersion
docker version
docker compose version
```

Первая команда печатает версию PowerShell. В `docker version` должны быть сведения и о `Client`, и о `Server`. Если виден только клиент и сообщение `failed to connect`, дождись запуска движка Docker Desktop и повтори проверку. `docker compose version` проверяет наличие команды Compose.

Для каждой работы сначала перейди из корня репозитория в её каталог. Например, для Kafka выполни следующий блок. Для остальных работ поменяй последнюю часть пути на `observability`, `oauth` или `postgresql`.

```powershell
Set-Location .\docs\labs\kafka
Get-Location
Get-ChildItem compose.yaml
docker compose config --services
```

`Set-Location` (также `cd`) меняет текущий каталог. `Get-Location` показывает, где ты сейчас, а `Get-ChildItem compose.yaml` подтверждает наличие нужного файла. `docker compose config --services` печатает имена сервисов, включённых в текущую конфигурацию. Для Kafka это `controller` и три `broker`. Выполняй остальные команды этого стенда в том же каталоге. В новом окне PowerShell перейди туда ещё раз. После завершения работы выйди из каталога командой `Set-Location ..\..\..`, чтобы вернуться в корень.

### Что означают команды

| Команда | Что произойдёт |
| --- | --- |
| `docker compose config` | Показывает итоговую конфигурацию с раскрытыми общими блоками и подстановками. `config --quiet` проверяет её без печати. Эти проверки работают и при выключенном движке. |
| `docker compose up -d` | Подготавливает образы, создаёт сеть и контейнеры, запускает сервисы. `-d` оставляет их в фоне и возвращает приглашение терминала. При первом запуске образы могут скачиваться несколько минут. |
| `docker compose up -d --wait` | Дополнительно ждёт состояния `healthy` для сервисов с `healthcheck` и `running` для остальных. `--wait-timeout 180` ограничивает это ожидание 180 секундами. |
| `docker compose up -d --build` | Перед запуском собирает образы сервисов с `build`. В OAuth так собирается API из локального `Dockerfile`. |
| `docker compose ps -a` | Показывает контейнеры проекта, включая остановленные. Смотри на имя сервиса, `STATUS` и `PORTS`. `Up` означает работающий процесс, `healthy` — успешно пройденную проверку здоровья. |
| `docker compose logs app --tail 20` | Показывает до 20 последних строк от сервиса `app`. Можно указать несколько сервисов. С `-f` вывод продолжается до Ctrl+C, после которого сервисы продолжают работать. |
| `docker compose exec -T primary psql …` | Выполняет `psql` внутри уже работающего контейнера `primary`. После имени сервиса идёт команда Linux и её аргументы. `-T` отключает псевдотерминал, что удобно для команд с перенаправлением ввода, захватом вывода или единственным запросом. Для интерактивного `psql` оставь `exec` без `-T`. |
| `docker compose stop broker3` / `docker compose start broker3` | Останавливает и снова запускает существующий контейнер. Настройки и данные контейнера сохраняются. Используем это, чтобы воспроизвести отказ отдельного компонента. |
| `docker compose down` | Останавливает и удаляет контейнеры проекта и его сеть. Именованные тома остаются. Состояние в слое удалённого контейнера теряется. |
| `docker compose down -v` | Дополнительно удаляет тома проекта. В этих работах это сброс стенда с потерей индексов, данных БД или архива, если они были в томах. Перед командой проверь текущий каталог. |

В PostgreSQL параметр `--profile standby` или `--profile restore` стоит перед подкомандой. Он подключает сервисы, вынесенные в соответствующий профиль. Так `up` можно запустить с primary и standby, а восстановление запустить позже. [Команды Compose](https://docs.docker.com/reference/cli/docker/compose/) · [Профили Compose](https://docs.docker.com/compose/how-tos/profiles/)

### Как читать compose.yaml

| Поле или запись | Как читать |
| --- | --- |
| `name`, `services` | `name` задаёт имя проекта. В `services` каждый вложенный ключ — отдельный сервис. Это же имя указываешь в `logs`, `exec`, `stop` и `start`. |
| `image`, `build` | `image: postgres:17` указывает образ и его тег. `build: .` берёт текущий каталог проекта как контекст сборки и по умолчанию ищет в нём `Dockerfile`. |
| `command`, `entrypoint`, `environment` | `entrypoint` задаёт запускаемую программу, `command` — команду или аргументы, которые ей передают. `environment` задаёт переменные внутри контейнера. |
| `ports: ['127.0.0.1:8088:80']` | Запрос с компьютера на `127.0.0.1:8088` попадёт на порт `80` контейнера. `127.0.0.1` ограничивает публикацию loopback-интерфейсом. Внутри сети Compose сервисы используют имена друг друга и порты контейнеров, например `app:8080`. |
| `./nginx.conf:/etc/nginx/conf.d/default.conf:ro` | Монтирует конкретный файл с компьютера по заданному пути внутри контейнера. `:ro` разрешает контейнеру читать файл. |
| `elastic-data:/usr/share/elasticsearch/data` | Подключает именованный том. Docker хранит его отдельно от контейнера и подключает заново при пересоздании. Секция `volumes` верхнего уровня объявляет такие тома. |
| `depends_on`, `healthcheck` | `depends_on` задаёт порядок запуска. Условие `service_healthy` ждёт успешного `healthcheck` зависимости. При обычном списке зависимостей Compose ждёт запуска контейнера, а приложению внутри ещё может понадобиться время на подготовку. |
| `x-…`, `&common`, `*common`, `<<: *common` | `x-…` позволяет хранить общий блок вне списка сервисов. `&common` присваивает блоку имя, `*common` ссылается на него, а `<<:` подставляет поля этого блока в текущий объект. Поля, указанные там же явно, имеют приоритет. |

[Поля сервиса Compose](https://docs.docker.com/reference/compose-file/services/) · [Публикация портов](https://docs.docker.com/engine/network/port-publishing/)

В блоках PowerShell `$имя` хранит значение, `|` передаёт результат следующей команде, а обратная кавычка в конце строки переносит команду. Копируй блок целиком и оставляй обратную кавычку последним символом строки. Если блок начинается с `function`, сначала выполни его определение. В новом окне функции и переменные нужно задать заново. Строки с `#` в блоках PowerShell являются комментариями.

## Observability и Nginx

**Ответ про логи.** Контейнер пишет в `stdout` и `stderr`. Runtime сохраняет потоки в формате CRI на узле. Kubelet отдаёт локальный фрагмент через `kubectl logs` и управляет ротацией. Узловой Fluent Bit или Vector обычно работает как `DaemonSet`, читает файлы контейнеров, добавляет метаданные Kubernetes и отправляет записи в Elasticsearch или Loki. В Elasticsearch записи индексируются и ищутся по полям, Kibana показывает результат поиска. Logstash или ingest pipeline подключают при необходимости преобразований. Grafana может читать Loki как отдельный источник. [Архитектура логирования Kubernetes](https://kubernetes.io/docs/concepts/cluster-administration/logging/)

**Ответ про метрики.** В Spring Boot Micrometer собирает счётчики и таймеры, Actuator открывает `/actuator/prometheus`. Prometheus периодически забирает значения, хранит временные ряды и выполняет PromQL. Grafana запрашивает Prometheus для отображения графиков. Логи и трейсы связываю по trace ID. Для метрик оставляю ограниченные измерения вроде `route`, `method` и `status`. Уникальный `request_id` сделал бы отдельный временной ряд почти для каждого запроса. [Конспект по метрикам](../theory/operations/observability.md#13-java-micrometer-и-actuator)

**Если в Kibana пусто.** Сгенерируй запрос с известным ID и по очереди проверь `kubectl logs`, состояние collector на нужном узле, ошибки парсинга и отправки, документ напрямую в Elasticsearch и временное окно в Discover. Проверь буфер, повторную отправку и ротацию файлов. Если backend отстаёт дольше, чем хватает буфера или срока хранения файлов, часть записей может потеряться.

**Ответ про Nginx.** Это HTTP reverse proxy на пути от клиента к приложению. На L7 он завершает TLS, выбирает upstream по хосту и пути, балансирует запросы, управляет заголовками, лимитами, таймаутами и буферизацией. Может кэшировать подходящие ответы, сжимать данные и отдавать статику. Буферизация помогает освобождать upstream при медленных клиентах, а для SSE может задерживать события. Ограничение запросов работает в рамках настроенной зоны конкретного экземпляра Nginx. Правила WAF требуют отдельного компонента или модуля. [Proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html) · [Request limiting](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)

- **TLS.** При termination прокси расшифровывает HTTP и может устанавливать отдельное TLS-соединение к upstream с проверкой сертификата. При mTLS он также может проверять сертификат клиента. В режиме L4 passthrough TLS-сессия доходит до backend, где и проверяется клиентский сертификат. Прокси может использовать SNI из ClientHello, если он доступен, но маршрутизация по HTTP-пути требует доступа к расшифрованному HTTP. [TLS preread в Nginx](https://nginx.org/en/docs/stream/ngx_stream_ssl_preread_module.html)
- **Граница доверия.** На входе задай свои `X-Request-ID` и заголовки об исходной схеме. Клиентский IP извлекай из цепочки прокси с настроенным списком доверенных отправителей. Если приложение принимает произвольный `X-Forwarded-For` от клиента, лимит по IP и аудит будут ненадёжными. [Real IP module](https://nginx.org/en/docs/http/ngx_http_realip_module.html)
- **Диагностика.** `429` может появиться на самом прокси. При `502` проверь доступность upstream и ошибки протокола. При `504` проверь, на каком ожидании исчерпан таймаут. Сравни `status`, `upstream_status`, `request_time` и `upstream_response_time`. В Kubernetes дополнительно проверь `Service`, `EndpointSlice`, readiness и порт контейнера.

## Гарантии Kafka

**Партиция и группа.** Обычная consumer group назначает партицию одному активному участнику в рамках текущего назначения. Отдельная группа читает те же данные со своими offsets. Consumer может владеть несколькими партициями. При трёх партициях и пяти участниках два останутся без назначения. Порядок в журнале задан offset внутри партиции. Если передать записи в пул потоков, эффекты могут завершиться в другом порядке. При rebalance старый обработчик может всё ещё выполнять внешний вызов, а новый начнёт с committed offset. Групповое назначение само по себе не защищает этот внешний эффект от повторов.

**Offsets.** Position показывает, откуда продолжит `poll()` этого экземпляра, а committed offset группы указывает следующую запись для чтения после передачи партиции. Прочитал запись `42`, применил эффект и упал до commit `43` — запись `42` может прийти снова. Commit `43` до эффекта и падение в этом окне — пропуск эффекта. Зафиксируй inbox и изменение бизнес-данных в одной транзакции и подтверждай offset после неё. [Конспект по группам и offsets](../theory/messaging/kafka.md#5-consumer-groups-и-offset)

**RF, ISR и `acks`.** RF=3 означает три назначенные реплики партиции. В текущий ISR входит лидер и реплики, которые Kafka считает достаточно синхронизированными. `acks=all` ждёт репликации на весь текущий ISR. `min.insync.replicas=2` задаёт нижний порог. При ISR из трёх реплик ждём три, при ISR из двух ждём две, при ISR из одной получаем ошибку при `acks=all`. Порог можно нарушить до или после append. Таймаут producer означает неизвестный итог записи, поэтому безопасный retry требует идемпотентности. [Настройки брокера Kafka 3.9](https://kafka.apache.org/39/configuration/broker-configs/#min.insync.replicas) · [Гарантии репликации Kafka](https://kafka.apache.org/40/design/design/)

**KRaft.** Контроллеры ведут согласованный журнал метаданных кластера по Raft. В кворуме из трёх голосующих контроллеров для прогресса метаданных нужно большинство из двух. В конкретной партиции брокеры реплицируют пользовательские записи, а её ISR меняется независимо от состава кворума контроллеров. При падении лидера выбор новой реплики зависит от её состояния и политики выборов. Если разрешить unclean election, можно вернуть доступность ценой потери подтверждённых записей. [KRaft в Kafka 3.9](https://kafka.apache.org/39/operations/kraft/)

**Границы доставки.** `acks=1` подтверждает append лидером. Если он упадёт до репликации, подтверждённая запись может исчезнуть. Идемпотентный producer подавляет повтор одной отправки при транспортном retry в рамках гарантий producer. Два вызова `send` с одним payload создают две записи. Kafka-транзакция с `read_committed` может связать публикацию выходных записей и commit входных offsets для consume–process–produce внутри Kafka. Для эффекта в PostgreSQL используй собственную транзакцию и дедупликацию по ID. [Сценарии доставки и транзакций](../../src/main/java/ru/learn/kafka/README.md)

## OAuth 2.0 и OpenID Connect

**Роли.** Resource owner даёт доступ к своим ресурсам. Client запрашивает доступ от его имени. Authorization Server аутентифицирует пользователя, получает согласие при необходимости и выпускает токены. Resource Server принимает access token и решает, разрешить ли конкретный вызов. OIDC поверх OAuth 2.0 добавляет контракт аутентификации пользователя для клиента через ID token. [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)

1. Клиент генерирует случайные `state`, `code_verifier` и `nonce`. В браузерный redirect на authorization endpoint отправляет `client_id`, точный `redirect_uri`, `response_type=code`, `scope=openid ...`, `state`, `nonce` и `code_challenge=BASE64URL(SHA256(code_verifier))` с методом `S256`.
2. Пользователь входит на Authorization Server. Клиент получает callback с `code` и `state`, связывает его с исходной сессией, затем обменивает одноразовый `code` и исходный `code_verifier` на token endpoint. Confidential client также аутентифицируется. Публичный клиент, например SPA или мобильное приложение, не может хранить общий client secret как секрет.
3. Клиент валидирует ID token для своей аудитории и сверяет `nonce`. Access token идёт в `Authorization: Bearer …` к API. Refresh token используется на token endpoint и выдаётся по политике сервера.
4. API проверяет пригодность access token для себя и права на операцию. `401` соответствует отсутствующему или недействительному токену, `403` — принятому токену без требуемого разрешения. Scope задаёт делегированные права, а доступ к конкретному объекту проверяется в приложении. [OAuth 2.0 Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html) · [Bearer Token Usage](https://www.rfc-editor.org/rfc/rfc6750.html)

**JWT и opaque.** Подписанный JWT обычно можно декодировать без ключа. Для доверия проверь подпись доверенным JWKS, допустимый алгоритм, `iss`, `aud`, срок (`exp`, `nbf` при наличии), тип токена по контракту issuer и права. Кешируй ключи и учитывай ротацию `kid`. Для opaque token API обращается к introspection по аутентифицированному каналу. Проверяй `active`, аудиторию и права из ответа по контракту провайдера. JWT тоже можно интроспектировать. Локальная проверка экономит сетевой вызов, но обычно видит отзыв только после истечения токена или по дополнительному механизму. Introspection добавляет зависимость от Authorization Server и компромисс между кешем и свежестью решения. [Token Introspection](https://www.rfc-editor.org/rfc/rfc7662.html)

**Refresh.** Выдавай короткоживущие access tokens, защищай refresh token при хранении и исключай токены из логов. Для public client используй rotation или sender-constrained tokens. При rotation успешное обновление выдаёт новый refresh token. Обработай параллельные попытки обновления, иначе один клиент может сам вызвать повторное использование старого токена. [OAuth 2.0 Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)

## Надёжность PostgreSQL

**Репликация.** Primary пишет изменения в WAL. Физический standby получает WAL по streaming replication и воспроизводит его. Архив WAL также может служить источником сегментов для догоняющего standby и PITR. Логическая репликация или CDC передают изменения на уровне данных. Kafka с CDC может доставлять события в другие системы, но физический standby PostgreSQL строится на WAL.

| Режим | Чего ждёт успешный `COMMIT` | Что проверить |
| --- | --- | --- |
| Асинхронный standby, обычный локальный flush | Сохранения WAL на primary | При promote отстающего standby возможна потеря уже подтверждённых коммитов |
| Синхронный standby, `synchronous_commit=on` | Локальный flush и durable flush на выбранном standby по `synchronous_standby_names` | Запись подтверждена, но результат ещё может не читаться на standby |
| `remote_apply` | В том числе replay WAL на выбранном standby | Запись видна новым запросам на этом standby. Цена — ожидание replay |
| `remote_write` | Записи WAL в файловую систему standby без гарантии flush там | При сбое ОС standby несброшенные данные могут потеряться |

Если настроен обязательный synchronous standby и он недоступен, commit может ждать `SyncRep`. Уточни, какие узлы подходят для подтверждения и failover. Синхронный режим сам по себе не выполняет переключение клиентов и не останавливает прежний primary. При failover нужен fencing, иначе два узла могут начать принимать записи. [Синхронная репликация](https://www.postgresql.org/docs/17/warm-standby.html#SYNCHRONOUS-REPLICATION) · [Режимы synchronous_commit](https://www.postgresql.org/docs/17/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT)

**RPO и RTO.** RPO задаёт допустимую потерю данных во времени. RTO задаёт срок восстановления работы сервиса. Для RPO ≤ 5 минут проверь, до какого подтверждённого бизнес-события действительно хватает копии и WAL. Для RTO ≤ 30 минут замерь обнаружение, решение о переключении, подготовку узла, скачивание копии, replay, проверки данных и возврат трафика. Если сбой в 12:00, последняя восстановимая запись в 11:52, а сервис снова работает в 12:24, фактическая потеря по времени — 8 минут, восстановление — 24. RTO выполнен, RPO нарушен.

**Backup и PITR.** Физический base backup плюс непрерывная цепочка архивных WAL позволяют восстановить кластер на отдельном экземпляре до времени, LSN или именованной точки. Полный backup упрощает восстановление, но расходует место и I/O. В PostgreSQL 17 физический инкрементальный backup требует манифеста предыдущего backup и WAL summaries. Для запуска восстановления цепочку сначала собирают в полный backup через `pg_combinebackup`. `pg_dump` подходит для логического восстановления объектов, для PITR нужен физический backup. Реплика быстро воспроизведёт случайный `DELETE`, поэтому храни копии и WAL в отдельном домене отказа. [Continuous Archiving and PITR](https://www.postgresql.org/docs/17/continuous-archiving.html)

**Учения.** Восстанови на изолированном узле, дождись нужной точки, проверь прикладной инвариант, количество строк и контрольные операции, затем измерь RPO/RTO. `pg_verifybackup` помогает проверить содержимое копии по манифесту. Доступность всех нужных WAL и пригодность восстановленной базы подтверждает реальный запуск. Мониторь ошибки архивации, возраст последней восстановимой точки, lag в байтах и время replay. [pg_verifybackup](https://www.postgresql.org/docs/17/app-pgverifybackup.html)

## Outbox и планировщик

**Ответ на интервью.** `@Scheduled` срабатывает в каждой из десяти JVM. Для единственного периодического запуска нужна координация. Для публикации Outbox полезно масштабировать обработку по строкам. Бизнес-изменение и запись Outbox фиксируются одной транзакцией. ACK Kafka и отметка публикации в БД находятся в разных системах. Падение между ними даёт повтор, поэтому потребитель дедуплицирует по стабильному ID события.

| Подход | Когда подходит | Что остаётся проверить |
| --- | --- | --- |
| Quartz с кластерным JDBC JobStore или DB advisory lock | Нужен один исполнитель для конкретной задачи | Восстановление после сбоя, повторы при неопределённом исходе, область жизни блокировки |
| Redis lease или Kubernetes Lease | Нужно избрать активного исполнителя | После паузы старый владелец может продолжить работу. Для строгого эксклюзива защищай ресурс fencing token или проверяемой версией |
| Kubernetes CronJob или Argo Workflows | Есть самостоятельный периодический batch | `Forbid` ограничивает Jobs одного CronJob, запуск может пропуститься или повториться. Действие должно быть идемпотентным |
| Несколько polling-воркеров с `FOR UPDATE SKIP LOCKED` | Нужна параллельная обработка готовых строк | При долгой сетевой операции сокращай транзакцию через claim с lease и условное завершение. Проверь порядок по агрегату |
| Воркер с сигналом о готовой строке | Нужна малая задержка с сохранением Outbox | Уведомление будит воркер, а устойчивая таблица и повторный обход подбирают записи после пропущенного сигнала |
| Debezium CDC с Outbox Event Router | Уже умеешь эксплуатировать CDC и хочешь публиковать из WAL | Lag и удержание WAL replication slot, snapshot и повторная доставка при восстановлении, очистка Outbox |

[Kubernetes CronJob](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/) · [Debezium Outbox Event Router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)

**Практика.** Пройди [сценарии кошелька](../labs/spring-postgres-outbox.md#кошелёк-outbox-kafka-и-inbox). Предскажи число сообщений и баланс для падения до send и после ACK до отметки `sent`. Затем в двух окнах PowerShell перейди в каталог [стенда PostgreSQL](../labs/postgresql/README.md) с работающим primary. В каждом запусти `docker compose exec primary psql -U learn -d learn`. `exec` запускает интерактивный `psql` внутри контейнера, `-U learn` выбирает роль, `-d learn` — базу. Когда появится приглашение `learn=#`, вводи SQL в этом окне.

Выполни в каждой сессии `SELECT pg_try_advisory_lock(42);`. Это попытка взять блокировку с ключом `42` без ожидания. Первая сессия получает `t` (true), вторая — `f` (false). Введи `\q` в первой сессии, чтобы завершить `psql` и освободить блокировку, затем повтори запрос во второй. Объясни, что известно новому владельцу о публикации, которую начал старый.

Открой `psql` заново в первом окне той же командой `docker compose exec primary psql -U learn -d learn`. В одном сеансе создай `CREATE TABLE outbox_claim_drill (id int PRIMARY KEY);` и добавь две строки через `INSERT INTO outbox_claim_drill VALUES (1), (2);`. Затем в обоих сеансах по очереди запусти следующий блок, оставляя транзакции открытыми.

```sql
BEGIN;
SELECT id FROM outbox_claim_drill ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
```

Первый воркер получит `1`, второй — `2`. Сделай `ROLLBACK` в первом и запусти блок снова. Строка `1` снова доступна. Это упражнение проверяет захват строк. В реальном relay сравни окно между ACK и `sent`, возраст старейшей неопубликованной строки и число повторных отправок.

`BEGIN` открывает транзакцию. `ORDER BY id LIMIT 1` задаёт порядок выбора и размер порции. `FOR UPDATE` удерживает блокировку выбранной строки до конца транзакции. `SKIP LOCKED` пропускает занятую строку, поэтому второй сеанс берёт следующую. В конце выполни `ROLLBACK;` и `\q` в обоих окнах, чтобы освободить блокировки и вернуться в PowerShell.

## JPA и план загрузки

**Ответ на интервью.** `LAZY` обычно оставляет прокси или обёртку коллекции до доступа. Если связь ещё не инициализирована, а сессия уже закрыта, Hibernate выбросит `LazyInitializationException`. `EAGER` требует загрузить связь, а конкретный SQL выбирает ORM. Дополнительные `SELECT` дают N+1, join нескольких `to-many` размножает строки. Например, 100 заказов × 8 позиций × 5 платежей дают до 4000 строк SQL при одновременной загрузке обеих коллекций. В Hibernate некоторые комбинации bag-коллекций приводят к ошибке `MultipleBagFetchException`.

Для карточки используй точечный `fetch join` или entity graph и проверяй SQL. Для списка без полной сущности подойдёт DTO-проекция. При нескольких ленивых связях batch fetch сокращает число отдельных запросов. Для страницы с коллекциями сначала выбери ID корней с устойчивым порядком, затем загрузи нужные связи для этих ID и восстанови порядок страницы. Учитывай изменения между двумя запросами, если нужна согласованная страница. [Hibernate ORM 6.6 User Guide](https://docs.hibernate.org/orm/6.6/userguide/html_single/Hibernate_User_Guide.html#fetching)

**Практика.** Из корня запусти тест с H2. Прогноз для трёх заказов с двумя строками у каждого — `4` SQL-запроса при обходе lazy-коллекций, `1` при `fetch join`, `2` для страницы через ID. Тест также проверяет исключение после закрытия сессии и запрещает пагинацию поверх collection fetch join. Посмотри SQL и попробуй заменить `LAZY` на `EAGER` в `Purchase.lines`, затем объясни изменившийся результат. [JpaFetchLabTest](../../src/test/java/ru/learn/interview/JpaFetchLabTest.java)

```powershell
.\mvnw.cmd '-Dtest=JpaFetchLabTest' test
```

`mvnw.cmd` — Maven Wrapper из репозитория. `-Dtest=JpaFetchLabTest` выбирает класс тестов, `test` запускает компиляцию и тесты. Для упражнения достаточно JDK, база H2 запускается в памяти процесса. В выводе ищи строки `Hibernate: select …`, затем `Tests run: 5` и `BUILD SUCCESS`.
