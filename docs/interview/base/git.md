# Git: 30 вопросов с вариантами ответа

[Теория](../../theory/engineering/git.md) · [Практика](../../labs/git/README.md)

Это учебные вопросы для подготовки к собеседованию, а не подборка реальных вопросов конкретной компании. В каждом вопросе **один правильный ответ**. Сначала выбери вариант и объясни его вслух, затем открой разбор. Варианты полезны для самопроверки, но на собеседовании нужно уметь описать решение без них.

Предполагаются обычный репозиторий без специальных hooks, настроенный origin и команды без дополнительных алиасов. Если условие требует чистого дерева, незакоммиченных изменений нет.

## Основы и ежедневная работа

### 1. Чем Git отличается от GitHub?

A. Git работает только при подключении к GitHub.  
B. Git хранит и обрабатывает историю, GitHub предоставляет хостинг и средства совместной работы.  
C. Это два названия одной программы.  
D. GitHub — локальная staging area.

<details><summary>Ответ и объяснение</summary>

**B.** Локальные коммиты и ветки работают без GitHub. Аналогичную серверную роль может выполнять GitLab или bare-репозиторий из лабораторных. Уточнение: где находится история, если интернет недоступен?

</details>

### 2. Что такое ветка в Git?

A. Независимая полная копия всех файлов на сервере.  
B. Каталог, который нельзя переименовать.  
C. Именованный указатель на коммит, который движется при новых коммитах в этой ветке.  
D. Список незакоммиченных правок.

<details><summary>Ответ и объяснение</summary>

**C.** Рабочие файлы приводятся к состоянию выбранной ветки при переключении. Создать ветку обычно дёшево: копировать целый проект не требуется. Уточнение: куда обычно указывает HEAD?

</details>

### 3. Файл содержал A. Ты добавил B, сделал add, добавил C и сделал обычный commit. Что сохранено?

A. A и B.  
B. A, B и C.  
C. Только C.  
D. Git откажет, потому что файл менялся после add.

<details><summary>Ответ и объяснение</summary>

**A.** Коммит сохраняет содержимое индекса. C остаётся неподготовленным изменением. Покажи это через `diff`, `diff --staged` и `show HEAD:FILE`. Практика: лабораторная 1.

</details>

### 4. Что показывает git diff без аргументов?

A. Все изменения на сервере.  
B. Отличие индекса от HEAD.  
C. Все новые untracked-файлы.  
D. Отличие рабочей директории от индекса для отслеживаемого содержимого.

<details><summary>Ответ и объяснение</summary>

**D.** Для будущего коммита нужен `git diff --staged`. Untracked-файлы ищи через status. Уточнение: почему пустой diff ещё не означает чистое дерево?

</details>

### 5. Что произойдёт после git restore --staged notes.txt в репозитории с HEAD?

A. Файл удалится с диска.  
B. Индекс файла вернётся к HEAD, рабочее содержимое останется.  
C. Удалится последний коммит.  
D. Правки отправятся на сервер.

<details><summary>Ответ и объяснение</summary>

**B.** Это способ убрать изменение из следующего коммита, сохранив работу. Для нового staged-файла результатом может быть untracked. Уточнение: чем отличается `git restore notes.txt` без --staged?

</details>

### 6. Какой файл обычный git commit -am не добавит автоматически?

A. Изменённый отслеживаемый Java-файл.  
B. Удалённый отслеживаемый файл.  
C. Новый untracked-файл.  
D. Уже подготовленный файл.

<details><summary>Ответ и объяснение</summary>

**C.** `-a` подготавливает изменения и удаления уже отслеживаемых файлов. Для нового файла нужен add. Поэтому удобнее явно проверять состав коммита.

</details>

### 7. Уже отслеживаемый .env добавили в .gitignore. Что будет?

A. Он останется отслеживаемым.  
B. Он исчезнет из всех старых коммитов.  
C. Он автоматически удалится с диска.  
D. Git отменит последний push.

<details><summary>Ответ и объяснение</summary>

**A.** Игнорирование не прекращает существующее отслеживание. `git rm --cached .env` и commit уберут файл из актуальной версии, но не из истории. Настоящий опубликованный секрет нужно отозвать. Практика: лабораторная 2.

</details>

### 8. Что делает git switch -c feature/payments?

A. Переключает на существующую серверную ветку без создания локальной.  
B. Создаёт коммит.  
C. Удаляет все незакоммиченные файлы.  
D. Создаёт локальную ветку от текущей точки и переключает на неё.

<details><summary>Ответ и объяснение</summary>

**D.** Создание ветки не публикует её. Уточнение: чем отличается `git branch feature/payments`?

</details>

## Обмен историей и объединение веток

### 9. Что такое origin/main в обычном клоне?

A. Ветка, которая всегда мгновенно совпадает с сервером.  
B. Локальная ссылка на последнее известное состояние main сервера origin.  
C. Имя текущей рабочей директории.  
D. Учётная запись пользователя.

<details><summary>Ответ и объяснение</summary>

**B.** Её сведения обновляются при обмене с сервером. Без fetch ты можешь не знать о свежих коммитах коллег. Практика: лабораторная 6.

</details>

### 10. Что обычно делает git fetch origin?

A. Всегда сливает серверную main с текущей веткой.  
B. Создаёт commit из изменённых файлов.  
C. Получает объекты и обновляет remote-tracking ссылки, сохраняя текущую локальную ветку и рабочие файлы.  
D. Отправляет все локальные ветки на сервер.

<details><summary>Ответ и объяснение</summary>

**C.** Fetch позволяет сначала посмотреть новую историю, затем решить, как интегрировать. Уточнение: как увидеть новые для main коммиты origin/main?

</details>

### 11. Ты на feature. Что делает git pull origin main при разрешённой настройками интеграции?

A. Получает серверную main и интегрирует её в текущую feature.  
B. Только обновляет локальную main.  
C. Автоматически переключает на main.  
D. Удаляет feature.

<details><summary>Ответ и объяснение</summary>

**A.** Получатель — текущая ветка. Способ интеграции зависит от опций и конфигурации. Поэтому явно указывай стратегию и проверяй текущую ветку.

</details>

### 12. Что произойдёт при pull --ff-only, если локальная и серверная ветки разошлись?

A. Git выполнит rebase.  
B. Git удалит локальные коммиты.  
C. Git создаст merge-коммит.  
D. Git откажется интегрировать историю таким способом.

<details><summary>Ответ и объяснение</summary>

**D.** Fast-forward возможен, когда можно просто передвинуть указатель вперёд. При расхождении нужно осознанно выбрать merge/rebase. Практика: лабораторная 6.

</details>

### 13. Push отклонён из-за non-fast-forward. Какой первый разумный шаг?

A. Немедленно push --force в main.  
B. Fetch и просмотр расхождения истории.  
C. Удалить .git.  
D. Повторять commit без изменений.

<details><summary>Ответ и объяснение</summary>

**B.** Нужно узнать, какие изменения появились на сервере, затем интегрировать их и проверить результат. Уточнение: чем это отличается от отказа из-за protected branch?

</details>

### 14. На main выполняется git merge feature. Куда включаются изменения?

A. В feature, main остаётся прежней.  
B. В обе ветки всегда создаётся по коммиту.  
C. В текущую main, указатель feature обычно остаётся прежним.  
D. Только на сервер.

<details><summary>Ответ и объяснение</summary>

**C.** Аргумент — источник, текущая ветка — получатель. Main после merge может передвинуться fast-forward либо получить merge-коммит.

</details>

### 15. Что отличает обычный merge разошедшихся веток от rebase feature на main?

A. Merge обычно соединяет линии коммитом с двумя родителями, rebase переигрывает коммиты на новой основе.  
B. Rebase всегда сохраняет хеши переносимых коммитов.  
C. Merge стирает всю историю feature.  
D. Эти операции всегда дают одинаковый граф.

<details><summary>Ответ и объяснение</summary>

**A.** При rebase изменённый родитель приводит к новым коммитам. Поэтому переписывание используемой коллегами истории требует согласования. Практика: лабораторные 3 и 7.

</details>

### 16. После исправления конфликта rebase что нужно сделать?

A. Сразу push --force.  
B. Удалить конфликтовавший файл.  
C. Выполнить только обычный commit и забыть об операции.  
D. Подготовить разрешённые файлы через add и выполнить rebase --continue.

<details><summary>Ответ и объяснение</summary>

**D.** Rebase может остановиться снова на следующем коммите. `--abort` отменяет операцию, `--skip` исключает переносимый коммит и может потерять нужное изменение.

</details>

### 17. Как выбирать ours/theirs при конфликте rebase?

A. Ours всегда означает исходную версию твоей feature.  
B. Читать содержимое: ours — собранная новая основа, theirs — переносимый коммит.  
C. Всегда принимать обе стороны без проверки.  
D. Принимать более длинный файл.

<details><summary>Ответ и объяснение</summary>

**B.** Названия сторон во время rebase часто неожиданны. Правильный результат определяется поведением программы. Отсутствие текстовых конфликтов не заменяет тесты.

</details>

### 18. Что гарантирует push --force-with-lease по сравнению с обычным --force?

A. Невозможность потерять чужую работу при любых обстоятельствах.  
B. Отсутствие необходимости согласовывать переписывание main.  
C. Проверку, что серверная ссылка имеет ожидаемое значение; при несовпадении push отклоняется.  
D. Автоматическое слияние всех изменений.

<details><summary>Ответ и объяснение</summary>

**C.** Это проверка ожидания, а не анализ ценности коммитов. При неявном lease ожидание обычно основано на remote-tracking ссылке, которую может обновить фоновый fetch.

</details>

## Отмена, восстановление и рабочие ситуации

### 19. Как обычно отменять ошибочный обычный коммит в общей опубликованной истории?

A. Revert этого коммита, затем review/проверки и публикация обратного изменения.  
B. Reset --hard и force push без обсуждения.  
C. Удалить локальный клон.  
D. Добавить его хеш в .gitignore.

<details><summary>Ответ и объяснение</summary>

**A.** Revert сохраняет историю и добавляет обратное изменение. Зависимости новых коммитов могут вызвать конфликт, поэтому нужно проверить итог. Для merge-коммита требуются дополнительные решения.

</details>

### 20. Что делает reset --soft HEAD~1 в обычной ветке с родителем?

A. Удаляет все файлы с диска.  
B. Отправляет последний коммит в stash.  
C. Сбрасывает индекс и рабочие файлы.  
D. Передвигает ветку к родителю, оставляя индекс и рабочие файлы прежними.

<details><summary>Ответ и объяснение</summary>

**D.** Изменения снятого коммита обычно остаются staged относительно нового HEAD. Можно собрать коммит заново. Практика: лабораторная 8.

</details>

### 21. Что важно знать о reset --hard HASH?

A. Он всегда сохраняет незакоммиченные изменения.  
B. Он меняет ветку, индекс и отслеживаемые рабочие файлы, может уничтожить незакоммиченную работу.  
C. Он создаёт обратный коммит.  
D. Он автоматически сохраняет все файлы в reflog.

<details><summary>Ответ и объяснение</summary>

**B.** Коммиты иногда удаётся найти через reflog, а несохранённые правки — не обязательно. Мешающие восстановлению untracked-пути также могут быть удалены. Страховочная ветка защищает коммиты, а не каждую правку редактора.

</details>

### 22. Что означает commit --amend после изменения последнего коммита?

A. Содержимое существующего объекта commit отредактировано на месте.  
B. Создана только серверная копия.  
C. Создан заменяющий коммит; при изменении содержимого/метаданных его хеш другой.  
D. Изменения автоматически отправлены всем коллегам.

<details><summary>Ответ и объяснение</summary>

**C.** Объекты коммитов неизменяемы. Перед amend нужно проверить индекс, после публикации учитывать переписывание истории. Практика: лабораторная 8.

</details>

### 23. Как stash push -u отличается от обычного stash push?

A. Включает также untracked-файлы, но не ignored.  
B. Отправляет stash на сервер.  
C. Создаёт новую main.  
D. Включает только ignored-файлы.

<details><summary>Ответ и объяснение</summary>

**A.** Для ignored существует `-a`. Stash локальный; обычный push его не публикует. Практика: лабораторная 5.

</details>

### 24. Что произойдёт, если stash pop завершился конфликтом?

A. Запись stash обязательно удалится.  
B. Git автоматически откатит весь репозиторий на неделю назад.  
C. Нужно выполнить stash --continue.  
D. Нужно разрешить конфликт; запись stash сохраняется, автоматического удаления при неуспехе нет.

<details><summary>Ответ и объяснение</summary>

**D.** У stash нет отдельной команды continue. Проверь результат, подготовь/закоммить его и лишь затем осознанно удали нужную запись.

</details>

### 25. Для чего cherry-pick?

A. Для скачивания всех веток сервера.  
B. Для применения изменения выбранного коммита в текущей ветке.  
C. Для поиска автора каждой строки.  
D. Для гарантированного переноса всех зависимостей исправления.

<details><summary>Ответ и объяснение</summary>

**B.** Обычно создаётся новый коммит. Проверяй зависимости: один hotfix может требовать предыдущий рефакторинг. Практика: лабораторная 9.

</details>

### 26. После reset исчез полезный коммит. Что попробовать сначала?

A. Clean -fdx.  
B. Переустановить IDEA.  
C. Reflog, затем show найденного коммита и создание rescue-ветки.  
D. Restore случайного untracked-файла.

<details><summary>Ответ и объяснение</summary>

**C.** Reflog фиксирует локальные перемещения ссылок. Он имеет срок хранения и не заменяет резервные копии или сохранение файлов. Практика: лабораторная 10.

</details>

### 27. Что делать с полезными коммитами, созданными в detached HEAD?

A. Создать на них ветку до ухода, например switch -c investigation.  
B. Обязательно скопировать всю .git вручную.  
C. Добавить HEAD в .gitignore.  
D. Ничего: они автоматически опубликованы в main.

<details><summary>Ответ и объяснение</summary>

**A.** Ветка даёт результату устойчивое имя. После ухода его иногда можно найти по reflog, но лучше сразу удержать явной ссылкой.

</details>

### 28. Что нужно для полезного bisect?

A. Только знать автора последнего коммита.  
B. Иметь все коммиты в одной ветке без merge.  
C. Предварительно удалить тесты.  
D. Знать исправный и сломанный коммиты и иметь воспроизводимый критерий good/bad.

<details><summary>Ответ и объяснение</summary>

**D.** Bisect сокращает диапазон поиска. Нестабильная проверка может дать неверную классификацию. После расследования нужно `git bisect reset`. Практика: лабораторная 11.

</details>

### 29. Что верно про changelist в IDEA?

A. Это полноценная серверная ветка Git.  
B. Это группировка локальных изменений средствами IDE; она не заменяет ветку и коммит.  
C. Это всегда то же самое, что stash.  
D. Каждый changelist автоматически отправляется через push.

<details><summary>Ответ и объяснение</summary>

**B.** Ветку хранит Git, changelist организует IDE. Явную staging area можно включить в настройках Git. Уточнение: чем Shelve отличается от Git stash?

</details>

### 30. Что верно про Commit and Push и Update Project в IDEA?

A. Обе кнопки всегда выполняют только fetch.  
B. Commit and Push не создаёт локальных коммитов.  
C. Commit может пройти успешно при неуспешном push; стратегия Update Project зависит от настроек.  
D. Update Project всегда равен reset --hard origin/main.

<details><summary>Ответ и объяснение</summary>

**C.** Разделяй локальное сохранение и обмен с сервером. При Update Project заранее смотри, какой способ интеграции выбран, особенно перед rebase опубликованной ветки.

</details>

## Как использовать на собеседовании

После выбора варианта добавляй короткий пример: «Есть локальный коммит B и серверный C после общего A. Fetch только обновит origin/main, а merge соединит линии». Затем называй проверку: status, diff, log, тесты. Если состояние не задано, уточни текущую ветку, наличие незакоммиченных правок и опубликована ли история.

Ориентир для самопроверки: 25–30 ответов с объяснениями — хорошее усвоение этого конспекта; 18–24 — повтори ошибочные темы; меньше 18 — начни с индекса и обмена историей. Это учебная шкала, она не гарантирует результат найма и не определяет грейд.

Источники ответов: [официальный справочник Git](https://git-scm.com/docs), конкретные команды в [конспекте](../../theory/engineering/git.md), [Commit в IDEA](https://www.jetbrains.com/help/idea/commit-and-push-changes.html), [Update Project](https://www.jetbrains.com/help/idea/sync-with-a-remote-repository.html).
