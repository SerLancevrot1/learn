# MongoDB на практике

[Конспект по MongoDB](../theory/MongoDB.md)

Из корня проекта:

```powershell
docker compose --profile labs up -d --wait mongo
.\mvnw.cmd "-Dlabs.external=true" "-Dtest=MongoLabIntegrationTest" test
docker compose exec mongo mongosh --quiet --eval 'db.hello()'
```

[Интеграционные тесты](../../../../../test/java/ru/learn/mongo/MongoLabIntegrationTest.java) запускают операции через настоящий MongoDB Java Driver. Каждый тест создаёт собственную базу `lab_...` и удаляет её после завершения. URI по умолчанию — `mongodb://localhost:27017/?replicaSet=lab-rs`, переменная для переопределения — `LAB_MONGO_URI`. Compose инициализирует одноузловой replica set и ждёт primary. Стенд локальный, порт открыт на loopback, аутентификация не включена.

## 1. От запроса к модели и индексу

[OrderCatalog](OrderCatalog.java) хранит позиции заказа и исторические цены внутри документа. Заказ можно прочитать одним запросом, а изменение цены в каталоге не перепишет историю. Остаток SKU живёт в отдельной коллекции, потому что один остаток разделяют многие заказы.

- `revenueBySku()` выполняет `$match → $unwind → $group`. Сначала отбирает заказы клиента, затем разворачивает позиции и суммирует `quantity * unitCents`. Тест проверяет, что две покупки одного SKU по разным ценам дают правильную выручку.
- `page()` сортирует по `createdAt DESC, _id DESC`. Курсор включает оба значения. Если три записи имеют одинаковое время, вторая страница всё равно продолжает строго после последней записи первой. Курсор сам по себе не замораживает историю между запросами.
- `createIndex()` ставит поле равенства `customerId` первым и сохраняет порядок следующих полей сортировки. Тест сравнивает `executionStats` до и после индекса без `hint`. Смотри `winningPlan`, `totalDocsExamined`, `totalKeysExamined` и `nReturned`. [Составные индексы MongoDB](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-compound/)

Остановись в тесте после сравнения планов. Скопируй имя базы из `db.getName()` и выполни в `docker compose exec mongo mongosh`:

```javascript
use lab_ПОДСТАВЬ_ИМЯ_ИЗ_ОТЛАДЧИКА
db.orders.getIndexes()
db.orders.find({customerId: "alice"}).sort({createdAt: -1, _id: -1}).limit(2).explain("executionStats")
```

Убери `_id` из курсора и снова прогони тест с одинаковыми timestamps. Затем поменяй порядок полей индекса и сравни планы. Объясни, почему индекс ускоряет конкретный запрос и почему каждый дополнительный индекс стоит места и работы на записи.

## 2. Конкуренция, транзакции и повтор

[InventoryCheckout](InventoryCheckout.java) показывает две границы атомарности:

| Сценарий | Как защищена операция | Что проверяет тест |
|---|---|---|
| Два покупателя и одна единица SKU | Один `updateOne` с фильтром `available >= quantity` и оператором `$inc` | Списывает ровно один покупатель, остаток равен нулю |
| Два SKU и новый заказ | Один `ClientSession` и `withTransaction` | Недостаток второго SKU отменяет списание первого и заказ не появляется |
| Повтор после неизвестного результата | Стабильный `_id` заказа и сравнение содержимого | Повтор не уменьшает остатки дважды даже при двух одновременных вызовах, повтор с другим клиентом отклоняется |

В транзакции проследи, где в каждую операцию передаётся `session`. Поставь точку останова после первого списания и до ошибки второго SKU. Снаружи транзакции прежний остаток всё ещё виден. Затем попробуй убрать `session` у списания и посмотри, какой инвариант перестанет выполняться. Колбэк `withTransaction` может запускаться повторно. Для письма или HTTP-вызова нужна отдельная доставка после commit, например outbox. [Транзакции MongoDB](https://www.mongodb.com/docs/manual/core/transactions/)

`readConcern: snapshot` даёт транзакции согласованный снимок. `writeConcern: majority` относится к подтверждению записи. На одном узле нет опыта выбора нового primary и проверки сохранности при потере реплики.

## 3. Change Streams и CDC

Последний тест подписывается на изменения заказов, читает вставку, сохраняет resume token и закрывает курсор. Второй заказ создаётся в паузе. `resumeAfter(token)` продолжает после обработанной вставки и получает вторую. В рабочей системе токен сохраняют после надёжной записи результата. Если процесс завершится между этими шагами, запись может повториться. В сценарии экспорта держи устойчивый ID события и предусмотренный backfill на случай, если нужная история oplog уже недоступна. [Change Streams](https://www.mongodb.com/docs/manual/changeStreams/)

Для интервью разберись, где достаточно одного документа, где нужна транзакция, а где достаточно дедупликации в получателе. Затем представь, что история заказов нужна для аналитики, и сравни операционную коллекцию с [Data Lake](../datalake/README.md).
