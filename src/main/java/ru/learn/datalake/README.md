# Data Lake на практике

[Конспект по Data Lake и Lakehouse](../theory/DataLake.md)

**Стенд** — S3-совместимый SeaweedFS для хранения объектов, DuckDB для SQL и Parquet, Java для загрузки и публикации снимков. Вычисления идут в JVM с временными локальными копиями. Набор данных и каталог снимков хранятся в S3. [SeaweedFS](https://github.com/seaweedfs/seaweedfs) · [DuckDB и Parquet](https://duckdb.org/docs/stable/data/parquet/overview)

```powershell
docker compose --profile labs up -d --wait lake-s3
.\mvnw.cmd "-Dlabs.external=true" "-Dtest=OrderLakeIntegrationTest" test
```

[Тесты](../../../../../test/java/ru/learn/datalake/OrderLakeIntegrationTest.java) создают отдельный bucket на сценарий и удаляют его после проверки. Endpoint по умолчанию — `http://localhost:8333`, ключи стенда — `learn / learn-local-secret`. Переопределения — `LAB_S3_ENDPOINT`, `LAB_S3_ACCESS_KEY`, `LAB_S3_SECRET_KEY`.

## 1. От входного события до отчёта

Открой [OrderLake](OrderLake.java) и начни с теста `rawReplayIsIdempotentAndSilverDeduplicatesAndQuarantines`.

| Слой | Артефакт | Что проверить |
|---|---|---|
| Bronze | `bronze/{batchId}.ndjson` | Исходные байты сохраняются. Повтор с тем же ID и байтами пропускается. Тот же ID с новым телом вызывает ошибку. |
| Silver | `snapshots/{id}/silver/event_date=.../*.parquet` | Приводим типы, оставляем последнюю ревизию события, режем по дате самого события. `channel` — необязательное поле, старые данные читаются с NULL. |
| Карантин | `snapshots/{id}/quarantine.parquet` | Строки с ошибкой в данных сохраняются с `reject_reason`. Синтаксически повреждённый JSON останавливает чтение батча, а оригинал остаётся в Bronze. |
| Gold | SQL-результат `revenue()` | Число заказов и сумма в копейках по дням. При заданной дате Java выбирает пути из manifest до S3 GET. DuckDB восстанавливает дату из Hive-каталога. |

Дедупликация на входе и дедупликация событий решают разные задачи. Первая сравнивает batch ID и байты. Вторая обрабатывает дубли внутри файла или между файлами по `event_id` и `revision`. Одинаковая ревизия с разным содержимым считается конфликтом и блокирует публикацию. Поздний заказ попадает в прошлую партицию по event time. Исправление с большей ревизией меняет агрегат в новом снимке.

## 2. Окно отказа и конкурирующие сборки

1. `prepare()` читает текущий ETag каталога, фиксирует список входных файлов, преобразует данные и загружает файлы под уникальным ID. Manifest записывается после Parquet.
2. Если процесс упал здесь, `catalog/current` по-прежнему указывает на прежний снимок. В S3 могут остаться подготовленные файлы. Читатели берут состав снимка из manifest по одному ID.
3. `publish()` меняет `catalog/current` одним условным PUT. Для первого снимка используется `If-None-Match: *`, для следующего — `If-Match: <ETag>`. Два сборщика на одной базе не могут последовательно опубликовать поверх одной версии. Проигравший должен заново прочитать Bronze и текущий каталог. После сетевого таймаута проверь, указывает ли каталог на твой ID, прежде чем решать, повторять ли публикацию. [Условные записи S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)
4. Сохрани старый snapshot ID, опубликуй поздние данные и прочитай обе версии. Старый отчёт остаётся воспроизводимым, пока хранятся его файлы и manifest. Для очистки нужен срок хранения, который учитывает активных читателей и незавершённые записи.

Тест `staleBuilderCannotOverwriteSnapshotFromFresherInputs` публикует результат с новыми входами раньше запоздавшей сборки. Тест `twoFirstPublishersRaceForAnEmptyCatalog` одновременно отправляет два условных PUT к пустому каталогу. Тест `stagedFailureKeepsOldSnapshotAndLateCorrectionChangesOnlyNewView` оставляет подготовленный снимок без публикации и проверяет, что читатель его не подхватил.

## 3. Посмотреть объекты и поэкспериментировать

Останови тест после `prepare()`. Если установлен AWS CLI, подставь bucket из отладчика:

```powershell
$env:AWS_ACCESS_KEY_ID = 'learn'
$env:AWS_SECRET_ACCESS_KEY = 'learn-local-secret'
$env:AWS_DEFAULT_REGION = 'us-east-1'
aws --endpoint-url http://localhost:8333 s3 ls s3://ИМЯ_BUCKET/ --recursive
```

1. Сравни список объектов до и после `publish()`. Появится или изменится `catalog/current`. Объясни, почему glob по всему `snapshots/*` может смешать ревизии и недописанные снимки.
2. В тесте поздних данных перенеси время события на другой день. Проверь, что новая ревизия исчезает из старой даты и появляется в новой. При инкрементальной обработке это означало бы пересчёт обеих партиций.
3. Убери фильтр путей по дате и поставь breakpoint перед S3 GET. Сравни число скачиваний. Отдельно объясни разницу между отбором файлов по партиции, выбором колонок Parquet и отсевом row groups по статистике. [Hive partitioning в DuckDB](https://duckdb.org/docs/stable/data/partitioning/hive_partitioning.html)
4. Представь, что приходит тысяча маленьких файлов в час. Какие метрики покажут проблему, где нужна compaction и когда удалять исходные файлы? Обсуди компромисс между детализацией партиций и числом мелких объектов.

## Границы модели

В стенде полная пересборка Silver читает все Bronze-батчи, Gold считается запросом, а каталог реализован одним условным указателем. Это позволяет пройти цикл целиком без Spark и внешнего каталога. Для масштаба разбери инкрементальный пересчёт, эволюцию схемы и партиций, compaction, политику хранения и удаление невидимых файлов. В Apache Iceberg снимки, метаданные, manifest-файлы и оптимистичный commit формализованы спецификацией. [Спецификация Iceberg](https://iceberg.apache.org/spec/#optimistic-concurrency)

На интервью сравни **формат файла** (Parquet), **формат таблицы** (например, Iceberg), **хранилище** (S3 API), **вычислитель** (DuckDB или Spark) и **каталог**. Назови, где именно проходит граница commit и как повторить загрузку без двойного учёта.
