# Redis на практике

```powershell
docker compose --profile labs up -d --wait redis
.\mvnw.cmd "-Dlabs.external=true" "-Dtest=RedisLabIntegrationTest" test
```

Клиент Lettuce посылает реальные команды. [Тесты](../../../../../test/java/ru/learn/redis/RedisLabIntegrationTest.java) используют две независимые связи с одним сервером в опытах с конкуренцией. В тесте цена из источника имитируется Java-функцией, чтобы управлять временем чтения.

| Опыт | Код | Что увидишь |
|---|---|---|
| Cache-aside | [ProductPriceCache](ProductPriceCache.java) | Первый вызов читает источник и ставит TTL через `SET PX`. Повтор берёт кеш. Инвалидация и истечение TTL вызывают новую загрузку. |
| Устаревшее заполнение после `DEL` | [ProductPriceCache](ProductPriceCache.java) | Остановленный читатель уже держит старую цену. Обновление источника и `DEL` происходят раньше его `SET`. Старая цена возвращается до следующей инвалидации или TTL. |
| Общая квота | [FixedWindowLimiter](FixedWindowLimiter.java) | 20 запросов к двум экземплярам делят лимит 5. Скрипт ставит TTL при первом инкременте. При новом окне запрос снова проходит. |
| Смена владельца аренды | [RedisLease](RedisLease.java) | После истечения TTL ключ может захватить другой процесс. Запоздалый release старого владельца сохраняет новый ключ. |
| Последняя единица товара | [StockReservations](StockReservations.java) | Среди 20 конкурирующих покупателей один получает резерв. Повтор победителя распознаётся даже при нулевом остатке. |
| Падение обработчика Redis Streams | [WalletStream](WalletStream.java) | Worker A делает commit БД и исчезает до `XACK`. Worker B забирает pending-запись, пропускает дубль через inbox и подтверждает её. |

## Посмотреть команды и TTL

Открой интерактивную консоль через `docker compose exec redis redis-cli`. Введи команды по очереди:

```redis
SET demo:price:sku 100 PX 30000
GET demo:price:sku
PTTL demo:price:sku
DEL demo:price:sku
PTTL demo:price:sku
```

У `PTTL` положительное значение означает оставшееся время в миллисекундах. `-1` означает ключ без срока жизни, `-2` означает отсутствующий ключ.

### Конкурентное обновление с WATCH

В консоли A введи `SET demo:stock 1`, `WATCH demo:stock`, `GET demo:stock`. В консоли B введи `SET demo:stock 0`. Вернись в A и выполни `MULTI`, `SET demo:stock 0`, `EXEC`. `EXEC` вернёт пустой результат транзакции, потому что наблюдаемый ключ изменился. Клиент должен заново прочитать состояние и решить, есть ли товар. `WATCH` и `EXEC` выполняются на одной связи.

Проверь отличие от SQL rollback. Введи `MULTI`, `SET demo:counter text`, `INCR demo:counter`, `SET demo:after 1`, `EXEC`. Ошибка типа у `INCR` появится в результатах, а обе команды `SET` выполнятся. Удали учебные ключи через `DEL demo:stock demo:counter demo:after`. [Транзакции Redis](https://redis.io/docs/latest/develop/interact/transactions/)

## Что изменить и измерить

- Удали `PEXPIRE` из лимитера и запусти тест. Посмотри `PTTL`. Перенеси установку TTL из Lua в Java и объясни, что оставит падение процесса после `INCR`. При фиксированном окне возможен всплеск на границе двух окон.
- Замени проверку токена и удаление на отдельные команды. Нарисуй порядок GET старого владельца, истечение TTL, новый захват, DEL старого владельца. Даже атомарный release не останавливает зависшего владельца после TTL. Для критической внешней записи нужен механизм, например fencing token, который проверяет сама защищаемая система.
- Раздели проверку остатков и запись резерва на клиентские команды. Синхронизируй покупателей барьером после чтения и наблюдай гонку. В исходном варианте скрипт выполняет проверку и запись целиком, а все поля находятся в одном ключе. Lua блокирует другие команды на время выполнения, поэтому здесь скрипты короткие. [Lua в Redis](https://redis.io/docs/latest/develop/programmability/eval-intro/)
- Увеличь TTL кеша и повтори опыт с устаревшим заполнением. При строгом требовании к свежести обсуждай версию записи или отказ от кеширования на критическом пути. Для одновременных промахов отдельно обсуждай single-flight и разброс TTL.
- В тесте Streams остановись перед `XACK`. `XPENDING <stream> wallet` покажет незавершённую доставку, а чтение через `XREADGROUP ... >` её не вернёт. `XAUTOCLAIM` переносит запись другому worker. После `XACK` pending пуст, но `XLEN` по-прежнему равен 1. У журнала отдельная политика очистки, которую нужно согласовать со временем обработки и повторов. [XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/) · [XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/)

Маркер резерва в учебном hash живёт вместе с товаром. При длительной нагрузке продумай окно дедупликации и очистку, а для реальных остатков проверь требования к сохранности при failover и eviction. В Compose включён AOF, но все примеры работают на одном узле.
