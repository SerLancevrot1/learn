# Кеширование и Redis

## 1. Что такое кеш и зачем он нужен

**Кеш** — временное хранилище копий данных, которые можно получить из более медленного или дорогого источника: базы данных, удалённого сервиса, диска или вычисления.

Типичный путь без кеша:

`клиент → приложение → база данных → приложение → клиент`

С кешем:

`клиент → приложение → кеш → приложение → клиент`

Если нужных данных в кеше нет, приложение читает источник, сохраняет результат в кеше и возвращает его клиенту.

### Зачем кешируют

- **Снижение latency**: чтение из RAM обычно быстрее обращения к дисковой БД или удалённому сервису.
- **Снижение нагрузки** на базу и внешние API.
- **Повышение пропускной способности** при большом числе повторных чтений.
- **Сглаживание пиков** и временная защита источника данных.
- **Повторное использование дорогих вычислений**.

Кеш не бесплатен: он расходует память, усложняет систему и создаёт риск устаревших данных. Кеширование полезно, если повторные запросы достаточно часты, а цена чтения из источника заметна.

### Основные понятия и метрики

- **Cache hit** — ключ найден в кеше.
- **Cache miss** — ключ не найден; нужно обратиться к источнику.
- **Hit rate** — доля попаданий: `hits / (hits + misses)`.
- **Miss rate** — доля промахов: `1 - hit rate`.
- **Eviction** — вытеснение ключа из-за нехватки памяти согласно политике вытеснения.
- **Expiration** — удаление ключа по истечении TTL.
- **TTL (Time To Live)** — время жизни записи.
- **Freshness** — насколько данные свежие относительно источника.
- **Hit latency / miss latency** — задержка при попадании и промахе.

Высокий hit rate сам по себе не гарантирует пользу: если кеш медленный, дорогой в обслуживании или часто отдаёт некорректно устаревшие данные, система не стала лучше. Смотрите также p95/p99, нагрузку на источник, объём памяти и долю ошибок.

## 2. Где располагаются кеши

Кеши часто образуют несколько уровней:

1. **Кеш браузера / клиента** — статические ресурсы, HTTP-ответы, локальные данные.
2. **CDN / reverse proxy** — контент ближе к пользователю; обычно кеширует HTTP-ответы.
3. **Локальный кеш процесса** — память конкретного экземпляра приложения (например, Caffeine).
4. **Распределённый кеш** — общий для нескольких экземпляров сервис (например, Redis).
5. **Кеш самой БД или файловой системы** — страницы, индексы, данные в оперативной памяти ОС.

Близкий кеш обычно быстрее, но его копии труднее синхронизировать. Локальный кеш одного pod’а не разделяется с другими pod’ами; распределённый кеш общий, но требует сетевого обращения и отдельной эксплуатации.

## 3. Основные стратегии кеширования

### Cache-aside (lazy loading)

Приложение само проверяет кеш. При промахе читает источник, записывает результат в кеш.

```text
value = cache.get(key)
if value exists:
    return value

value = database.get(key)
if value exists:
    cache.set(key, value, ttl)
return value
```

**Плюсы:** просто внедрить; в кеш попадают только реально запрошенные данные; источник остаётся основным хранилищем.  
**Минусы:** первый запрос медленный; возможны конкурентные одинаковые промахи; кеш может устареть после изменения в БД.

Это самый частый паттерн для Redis и приложений, где допустима ограниченная устарелость.

### Read-through

Приложение обращается к кеширующему слою, а тот сам загружает данные из источника при промахе.

**Плюсы:** загрузка скрыта за абстракцией кеша.  
**Минусы:** нужен кеш/провайдер, умеющий обращаться к источнику; поведение может быть менее очевидным.

### Write-through

Запись проходит через кеширующий слой: данные синхронно записываются и в кеш, и в источник.

**Плюсы:** после успешной операции кеш содержит свежую версию.  
**Минусы:** запись дороже; остаётся вопрос атомарности между двумя хранилищами. Если запись в одно хранилище прошла, а во второе нет, требуется обработка частичного сбоя.

### Write-behind / write-back

Запись сначала подтверждается в кеше, а в источник переносится асинхронно позже.

**Плюсы:** низкая latency и возможность объединять записи.  
**Минусы:** при потере кеша можно потерять подтверждённые изменения; сложнее порядок, повторы и восстановление. Использовать только при осознанных требованиях к потере данных и надёжной очереди/журнале.

### Write-around

Записи направляются сразу в источник, минуя кеш. После записи кеш инвалидируется или обновляется отдельно.

**Плюсы:** одноразовые записанные данные не вытесняют полезный кеш.  
**Минусы:** первое чтение после записи будет промахом.

На практике стратегии комбинируют. Например, cache-aside для чтения и удаление ключа после успешной записи в БД.

## 4. Инвалидация и согласованность кеша

**Инвалидация** — удаление или обновление кешированной копии после изменения источника. Это одна из самых сложных частей кеширования: у системы появляются копии одних и тех же данных, и нужно решать, как долго они могут расходиться.

### Удалить ключ или обновить его?

Обычный безопасный вариант для cache-aside:

1. Записать изменение в БД.
2. После успешной записи удалить соответствующий ключ из кеша.
3. Следующее чтение загрузит актуальное значение из БД.

Если сначала удалить ключ, а затем записать БД, возможна гонка: запрос прочитает ещё старое значение из БД и положит его обратно в кеш. Если обновлять кеш до БД, ошибка записи в БД оставит кеш с несуществующим в источнике изменением.

Даже порядок «БД, затем удалить кеш» не решает абсолютно все гонки: конкурентное чтение могло прочитать старое значение до commit, а положить его в кеш уже после инвалидации. Для строгой согласованности нужны дополнительные механизмы (версии, блокировки, события с проверкой версии, чтение с обходом кеша); часто проще принять короткое окно устаревания и ограничить его TTL.

### Способы контролировать устаревание

- **TTL** — ограничивает максимальное время жизни копии, но не гарантирует мгновенную свежесть.
- **Инвалидация при записи** — ключ удаляют при изменении источника.
- **Обновление при записи** — кеш заменяют новой версией после commit.
- **События / CDC** — источник публикует изменения, потребители инвалидируют связанные ключи.
- **Версионирование ключа** — в ключ включают версию данных/схемы; старые ключи естественно истекают.
- **Короткий TTL + инвалидация** — распространённая комбинация: TTL служит страховкой от потерянного события.

Событие об изменении лучше отправлять надёжно. Если обновление БД и публикация события должны быть согласованы, применяют, например, **transactional outbox**: изменение и запись события фиксируются в одной транзакции, а отдельный процесс публикует событие.

### Кеширование отрицательных результатов

Промах источника тоже можно кешировать: например, «пользователь не найден». Это защищает БД от повторных запросов одного несуществующего ключа (**cache penetration**). Отрицательный результат обычно кешируют на более короткий срок. Нельзя смешивать «не найдено» и «ошибка источника» — временный сбой БД не должен превращаться в закешированный ответ «данных нет».

## 5. Типичные проблемы кеша

### Cache stampede / dogpile

TTL популярного ключа истёк, и множество запросов одновременно пошли в БД. Нагрузка на источник резко возрастает.

Решения:

- **Single-flight / лок** на загрузку конкретного ключа: один запрос загружает, остальные ждут или получают stale-значение.
- **Обновление заранее**: фоновая задача обновляет значение до истечения TTL.
- **TTL jitter**: случайно варьировать TTL, чтобы множество ключей не истекало одновременно.
- **Stale-while-revalidate**: пока одно обновление выполняется, отдавать ранее закешированное значение, если его устаревание допустимо.
- **Ограничить параллелизм** обращений к источнику и поставить таймауты.

Распределённый лок сам может стать узким местом; его нужно применять с ограниченным временем ожидания и понятным поведением при отказе.

### Cache penetration

Кеш не содержит данные, потому что их не существует. Злоумышленник или случайный клиент запрашивает множество разных несуществующих ID, и каждый запрос доходит до БД.

Решения: отрицательное кеширование, валидация допустимых ID до запроса, лимиты запросов. **Bloom filter** может быстро подсказать, что элемента точно нет (ложноположительный ответ возможен), но не заменяет источник истины.

### Cache avalanche

Большое число ключей истекает одновременно или целый кеш становится недоступен. Поток запросов обрушивается на источник.

Решения: случайный разброс TTL, прогрев кеша, постепенное включение/очистка, rate limiting, circuit breaker, ограниченная деградация и защита источника. Не сбрасывайте весь production-кеш без плана.

### Hot key

Один ключ получает непропорционально много запросов и перегружает одну ноду/шард.

Решения: локальный кеш поверх Redis, реплики для чтения, копирование/разбиение горячего значения, предварительное вычисление. Шардирование одного ключа требует корректно объединять части результата и усложняет инвалидацию.

### Большой ключ (big key)

Ключ содержит большой объект или коллекцию. Его чтение, запись, удаление, сериализация и репликация могут создавать задержки и блокировать обработку других команд.

Решения: ограничивать размер значения, делить его на части, использовать подходящую структуру данных и удалять большие структуры постепенно (`UNLINK` вместо синхронного `DEL`, когда применимо). Не считайте `SCAN` гарантией безболезненного обхода огромной коллекции: он уменьшает размер одного шага, но всё равно расходует ресурсы.

### Старые и несогласованные данные

Необходимо явно определить допустимое окно устаревания. Для каталога товаров оно может быть приемлемым, для баланса счёта — нет. **Кеш не должен становиться источником истины для критичных данных**, если не спроектирован как основное хранилище с соответствующими гарантиями.

## 6. Redis: что это

**Redis** — серверное хранилище структур данных типа key-value, обычно работающее преимущественно в оперативной памяти. Оно поддерживает TTL, атомарные команды над структурами данных, репликацию, персистентность и кластеризацию.

Redis часто используют как:

- распределённый кеш;
- хранилище сессий;
- счётчики, рейтинги и leaderboard;
- ограничитель частоты запросов;
- временное хранилище и дедупликацию;
- простую очередь или журнал событий (с учётом особенностей Lists/Streams);
- Pub/Sub для уведомлений, когда допустима потеря сообщения при отключённом подписчике.

Redis — не «просто быстрый кеш» и не замена реляционной БД для любой задачи. Для каждой роли нужно выбрать нужные гарантии, структуру данных, политику памяти и отказоустойчивость.

### Модель выполнения

- Команды Redis выполняются атомарно по одной: другая команда не вклинится посередине выполнения одной команды.
- Основная обработка команд традиционно организована вокруг одного потока выполнения; отдельные версии/конфигурации используют дополнительные потоки для сетевого ввода-вывода, а фоновые задачи persistence выполняются отдельно. Это не означает, что любая команда или весь сервер всегда «однопоточный».
- Длительная команда задерживает обработку последующих команд на том же узле. Поэтому важно избегать блокирующих операций и команд с большим объёмом работы.
- Большинство простых команд по ключу имеют сложность O(1), но команды над коллекциями могут быть O(N) или O(log N). Проверяйте сложность конкретной команды и фактический размер данных.
- Команды выполняются удалённо: сетевой RTT может оказаться дороже самой операции.

## 7. Структуры данных Redis

- **String** — строка, сериализованный объект, число или бинарные данные. Команды: `GET`, `SET`, `MGET`, `INCR`, `SETEX`.
- **Hash** — поля одного объекта. Команды: `HGET`, `HSET`, `HMGET`, `HGETALL`.
- **List** — упорядоченный список или простая очередь. Команды: `LPUSH`, `RPUSH`, `LPOP`, `BLPOP`, `LRANGE`.
- **Set** — уникальные элементы и операции над множествами. Команды: `SADD`, `SISMEMBER`, `SINTER`, `SMEMBERS`.
- **Sorted Set (ZSet)** — рейтинг, очередь с приоритетом, диапазоны по score. Команды: `ZADD`, `ZRANGE`, `ZRANK`, `ZINCRBY`.
- **Bitmap** — набор битов и флаги по числовому индексу. Команды: `SETBIT`, `GETBIT`, `BITCOUNT`.
- **HyperLogLog** — приближённое число уникальных элементов. Команды: `PFADD`, `PFCOUNT`, `PFMERGE`.
- **Stream** — журнал событий и группы потребителей. Команды: `XADD`, `XREAD`, `XREADGROUP`, `XACK`.
- **Geo** — географические точки и поиск рядом. Команды: `GEOADD`, `GEOSEARCH`.

Redis **JSON** обычно предоставляется модулем RedisJSON/совместимой платформой, а не является базовой структурой данных во всех сборках. Проверяйте доступность модулей в целевом Redis.

### String

Строка в Redis — бинарно-безопасное значение, а не только текст. Частые применения: JSON-объект, токен, счётчик, сериализованный результат.

```redis
SET user:42 '{"id":42,"name":"Анна"}' EX 300
GET user:42
INCR page:views
SET session:abc token NX EX 60
```

`SET key value EX seconds` записывает значение с TTL. `NX` означает «только если ключа ещё нет», `XX` — «только если ключ уже есть». В одной команде `SET` можно задавать условия и срок жизни, что предпочтительнее раздельных `SET` и `EXPIRE`.

### Hash

Подходит для полей объекта, если нужно читать/обновлять поля по отдельности.

```redis
HSET user:42 name "Анна" role "admin"
HGET user:42 name
HMGET user:42 name role
```

Hash не задаёт схему, типы или связи как реляционная БД. `HGETALL` возвращает все поля, поэтому не используйте его для неограниченно больших Hash.

### List

Список сохраняет порядок и удобен для простых очередей. Пара `LPUSH` + `BRPOP` позволяет организовать блокирующее чтение, но Lists не предоставляют полный набор гарантий брокера сообщений (подтверждения, повторная доставка, сложное управление потребителями).

```redis
LPUSH jobs '{"id":"job-1"}'
BRPOP jobs 5
```

При проектировании очереди учитывайте потерю/повторную обработку сообщения, подтверждение работы, dead-letter-поток и идемпотентность обработчика. Для более сложной обработки событий рассматривайте Streams или специализированный брокер.

### Set и Sorted Set

Set хранит уникальные элементы, полезен для тегов, участников и проверки принадлежности. Sorted Set хранит пары «элемент + числовой score», упорядоченные по score; это естественный выбор для рейтинга или временного окна.

```redis
SADD article:7:tags redis cache
SISMEMBER article:7:tags redis

ZADD leaderboard 1200 user:42
ZREVRANGE leaderboard 0 9 WITHSCORES
```

### Bitmap и HyperLogLog

Bitmap экономно хранит множество булевых признаков с целочисленными индексами, например ежедневную активность пользователя, если область индексов разумна.

HyperLogLog оценивает число уникальных элементов с малым фиксированным расходом памяти, но даёт приближённый результат и не позволяет получить сами элементы.

### Stream

Stream — сохраняемый упорядоченный журнал записей с ID. Consumer groups распределяют обработку между потребителями; сообщение можно подтвердить `XACK`, а необработанные сообщения остаются в pending entries list и требуют отдельной политики повторной обработки/перехвата.

```redis
XADD orders * orderId 1001 status created
XGROUP CREATE orders order-workers 0 MKSTREAM
XREADGROUP GROUP order-workers worker-1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders order-workers 1730000000000-0
```

Streams полезны для некоторых сценариев обработки событий, но не следует автоматически считать их полноценной заменой Kafka/RabbitMQ: отличаются масштабирование, долговечность, семантика доставки, инструменты и эксплуатационные свойства.

## 8. Ключи, TTL и управление памятью

### Именование ключей

Используйте читаемые, предсказуемые ключи с разделителями:

```text
user:42
user:42:profile
product:sku-123
session:random-token
```

Хорошее имя помогает диагностике, но длинные повторяющиеся префиксы увеличивают расход памяти. Не помещайте в ключ персональные секреты. Для Redis Cluster можно использовать hash tag в фигурных скобках, например `cart:{42}:items` и `cart:{42}:meta`: часть внутри `{}` задаёт общий hash slot и позволяет некоторым multi-key операциям выполняться на одном шарде. Не используйте один tag для всех ключей без необходимости — это создаст горячий слот.

### TTL и expiration

```redis
SET product:123 '{"price":10}' EX 60
TTL product:123
PTTL product:123
EXPIRE product:123 60
PERSIST product:123
```

- `TTL` возвращает оставшееся время в секундах; отрицательные значения различают отсутствие ключа и ключ без срока жизни.
- Ключ может удаляться **лениво** при обращении и **активно** фоновым процессом. Поэтому истечение TTL не означает, что в точный момент все связанные действия завершились.
- При перезаписи ключа учитывайте, сохраняется ли TTL: например, обычный `SET` без параметров срока жизни может убрать ранее установленный TTL. При необходимости задайте новый TTL в том же `SET`.
- TTL — политика свежести, а не механизм точного планировщика.

### Ограничение памяти и eviction

`maxmemory` задаёт лимит памяти для Redis (с учётом нюансов конфигурации и операционной системы). Когда лимит достигнут, результат зависит от `maxmemory-policy`:

- `noeviction` — не вытеснять ключи; команды, увеличивающие память, могут завершаться ошибкой.
- `allkeys-lru` / `allkeys-lfu` — выбирать кандидатов среди всех ключей.
- `volatile-lru` / `volatile-lfu` — выбирать только ключи с TTL.
- `allkeys-random` / `volatile-random` — случайное вытеснение.
- `volatile-ttl` — предпочитать ключи с меньшим оставшимся TTL.

LRU/LFU в Redis обычно реализованы приближённо, а не как точный глобальный список всех обращений. «Лучшей» политики для всех систем нет. Для кеша часто рассматривают `allkeys-lru` или `allkeys-lfu`; для хранилища, где потеря произвольных ключей недопустима, нельзя полагаться на eviction как на бизнес-механику.

Операционная система, фрагментация памяти, копирование страниц при fork для persistence и буферы репликации требуют дополнительного запаса сверх размера полезных значений. Планируйте лимит с запасом и наблюдайте за `used_memory`, `used_memory_rss`, фрагментацией и eviction.

## 9. Redis как кеш: типовой сценарий

Псевдокод cache-aside:

```text
getProduct(id):
    key = "product:" + id
    cached = redis.GET(key)

    if cached exists:
        return deserialize(cached)

    product = database.findProduct(id)
    if product does not exist:
        redis.SET(key, NOT_FOUND, EX shortTtl)
        return notFound

    redis.SET(key, serialize(product), EX ttlWithJitter)
    return product

updateProduct(product):
    database.update(product)  // commit сначала в источник истины
    redis.DEL("product:" + product.id)
```

Важно:

- сериализуйте и десериализуйте с явной версией формата; изменение схемы может потребовать версионированного префикса ключа;
- различайте «нет записи», «закешировано отсутствие» и «Redis недоступен»;
- задавайте TTL и таймауты;
- продумайте конкурентный промах для популярных ключей;
- при недоступности кеша выберите поведение явно: обход кеша, ограниченная деградация или ошибка. Не допускайте неконтролируемого переноса всей нагрузки на БД.

В Spring часто используют `@Cacheable` для чтения и `@CacheEvict`/`@CachePut` для записи:

```java
@Cacheable(cacheNames = "products", key = "#id")
public Product findById(long id) {
    return repository.findById(id).orElse(null);
}

@CacheEvict(cacheNames = "products", key = "#product.id")
public Product update(Product product) {
    return repository.save(product);
}
```

Это иллюстрация, а не универсальная конфигурация. Проверьте настройки TTL/serializer в выбранном `CacheManager`, поведение с `null`, прокси-семантику Spring Cache (вызов метода из того же объекта может не пройти через proxy), транзакционный порядок и инвалидацию связанных ключей. Аннотация сама по себе не решает гонки и согласованность.

## 10. Redis-команды и важные свойства

### Атомарность команды

Одна команда, например `INCR`, атомарна. Последовательность отдельных команд атомарной не становится:

```redis
GET counter
SET counter <new-value>
```

Два клиента могут прочитать одинаковое старое значение и потерять одно обновление. Используйте `INCR`, условный `SET`, `WATCH`/`MULTI` или Lua — в зависимости от операции.

### MULTI/EXEC и WATCH

`MULTI` собирает команды, `EXEC` выполняет их подряд как атомарную последовательность относительно других клиентов; команды внутри блока не перемежаются с командами других клиентов.

```redis
WATCH account:42
MULTI
DECRBY account:42 10
EXEC
```

`WATCH` реализует оптимистическую проверку: если наблюдаемый ключ изменился до `EXEC`, транзакция отменяется, и клиент должен повторить логику. У Redis-транзакций нет привычного SQL rollback: ошибка выполнения одной команды не откатывает уже выполненные команды блока. Валидацию и обработку конфликтов нужно проектировать явно.

Пример выше показывает только механизм `WATCH`/`EXEC`, а не полноценную проверку баланса: приложение должно прочитать значение после `WATCH`, проверить бизнес-условие и только затем сформировать транзакцию. Если `EXEC` отменил её из-за конфликта, логику проверки нужно повторить.

### Lua-скрипты и Redis Functions

Lua-скрипт выполняется атомарно относительно других команд, что удобно для короткой операции «прочитать → проверить → записать». Пока скрипт работает, он блокирует обработку других команд на узле, поэтому он должен быть коротким и ограниченным по объёму. Не выполняйте долгие циклы по большим данным.

Начиная с современных версий Redis доступны также Redis Functions для серверных функций. Возможности и команды зависят от версии и конфигурации.

### Pipeline

Pipeline отправляет много команд одной сетевой пачкой и уменьшает число RTT. Сам по себе pipeline **не делает** последовательность атомарной и не является транзакцией.

### Блокирующие команды и производительность

Осторожно с блокирующими командами (`BLPOP`, `XREAD BLOCK`) и командами, работающими со всей коллекцией (`KEYS`, крупный `HGETALL`, диапазон большого списка). Блокирующая команда блокирует ожидающий клиент/соединение по своим правилам, а тяжёлая вычислительная команда может задержать обработку команд узлом.

- Не используйте `KEYS *` в production для обхода базы ключей; для итерации применяют `SCAN`, учитывая повторяющиеся результаты и то, что данные могут меняться во время обхода.
- Учитывайте сложность команды и число возвращаемых элементов.
- Группируйте независимые запросы через pipeline или multi-key команды, если это поддерживается топологией.
- Настройте пул соединений, таймауты, лимиты и обработку ошибок в клиенте.

## 11. Персистентность Redis

Данные в памяти могут исчезнуть при сбое, поэтому Redis предлагает механизмы сохранения на диск. Конкретное поведение зависит от конфигурации и версии.

### RDB snapshots

RDB периодически создаёт снимок набора данных в файл.

**Плюсы:** компактный файл, удобен для резервной копии и загрузки; относительно малая нагрузка записи при подходящем расписании.  
**Минусы:** изменения после последнего снимка могут быть потеряны при аварии; снимок создаётся не непрерывно.

Создание снимка обычно использует fork и copy-on-write: при интенсивных записях копирование изменённых страниц может увеличить расход памяти и задержки.

### AOF (Append Only File)

AOF записывает команды изменения в журнал и при старте может восстановить состояние повторным воспроизведением.

Типичные режимы `appendfsync`:

- `always` — синхронизировать после каждой команды: выше надёжность, существенно выше стоимость записи.
- `everysec` — синхронизация примерно раз в секунду; распространённый компромисс, при аварии возможна потеря примерно последних секунд записей.
- `no` — момент синхронизации в основном оставлен ОС; максимальная неопределённость при сбое.

AOF может расти, поэтому применяют переписывание журнала (rewrite). Персистентность не заменяет проверенную стратегию резервного копирования: сохраняйте и проверяйте бэкапы отдельно.

### RDB и AOF вместе

Можно включить оба механизма: RDB для снимков/бэкапа, AOF для более полного восстановления последних изменений. Что именно будет источником восстановления при старте, зависит от версии и конфигурации. Перед эксплуатацией тестируйте восстановление на той же версии и настройках, что и production.

Если Redis используется **как чисто восстанавливаемый кеш**, персистентность часто можно отключить, чтобы снизить стоимость записи. Если Redis содержит сессии, очередь или единственную копию важных данных, решение нужно принимать по требованиям к RPO/RTO, репликации и бэкапам, а не по слову «Redis».

## 12. Репликация, Sentinel и высокая доступность

### Репликация

Redis поддерживает primary-replica репликацию. Реплика обычно асинхронно получает изменения от primary. Это повышает доступность чтения и позволяет иметь копию данных, но:

- реплика может отставать;
- сразу после записи чтение с реплики может вернуть старые данные;
- при аварии primary часть ещё не реплицированных изменений может быть потеряна;
- репликация сама по себе не является резервной копией и не гарантирует строгую согласованность.

Опция `WAIT` может ожидать подтверждения репликации заданным числом реплик, но не превращает Redis в полностью синхронную систему с гарантией отсутствия потери при любых отказах.

### Redis Sentinel

Sentinel используется для мониторинга не кластеризованной пары/группы primary и replicas, обнаружения отказа, автоматического выбора новой primary и предоставления клиентам актуального адреса primary.

Для надёжного кворума обычно запускают несколько Sentinel-процессов на независимых узлах/зонах. Sentinel не распределяет данные по шардам и не заменяет Redis Cluster. Failover может сопровождаться короткой недоступностью и потерей последних записей, если репликация отставала.

### Redis Cluster

Redis Cluster горизонтально распределяет ключи по **16 384 hash slots**. Для каждого ключа вычисляется слот, а узлы отвечают за диапазоны слотов; у primary могут быть replicas.

- `MOVED` говорит клиенту, что слот обслуживает другой узел, и обычно обновляет его карту слотов.
- `ASK` направляет временно на другой узел во время переноса слота; клиент выполняет `ASKING` перед командой.
- Мультиключевые команды и транзакции ограничены ключами одного слота. Hash tags (`{...}`) помогают поместить связанные ключи в один слот.
- Репликация в кластере также асинхронная; failover не означает нулевую потерю данных.
- Разделение на шарды повышает ёмкость, но добавляет маршрутизацию, ребалансировку и ограничения по операциям.

**Sentinel и Cluster решают разные задачи:** Sentinel обеспечивает обнаружение отказа/failover для одного логического набора данных; Cluster распределяет данные по шардам и также предоставляет failover реплик.

## 13. Pub/Sub, блокировки и очереди

### Pub/Sub

Publisher отправляет сообщение в канал, subscribers получают его, пока подключены. Сообщения не хранятся как журнал для отключённого потребителя и обычно теряются для него. Pub/Sub подходит для эфемерных уведомлений, но не для гарантированной доставки.

### Распределённая блокировка

Базовый шаблон для короткой аренды блокировки:

```redis
SET lock:resource unique-token NX PX 10000
```

- `NX` позволяет захватить блокировку только при отсутствии ключа.
- `PX` ограничивает срок аренды, чтобы блокировка не осталась навсегда после падения владельца.
- `unique-token` — случайный уникальный токен конкретного владельца.
- Освобождать блокировку нужно только если токен всё ещё принадлежит владельцу. Проверка и удаление должны быть атомарными (обычно короткий Lua-скрипт или соответствующая современная команда, если она доступна).

Нельзя просто делать `DEL lock:resource`: срок старой блокировки мог истечь, ключ уже захватил другой клиент, а старый владелец удалит чужую блокировку.

У этого шаблона есть важное ограничение: процесс может приостановиться дольше TTL и продолжить работу после потери блокировки. Для защиты критичной записи используют **fencing token** — монотонно возрастающий номер аренды, который ресурс-получатель проверяет и отклоняет старые операции. Распределённая блокировка не заменяет транзакцию в системе, где находится защищаемый ресурс. Redlock и его гарантии являются предметом дискуссии; выбирайте решение исходя из модели отказов, а не только по наличию библиотеки.

### Ограничение частоты запросов

Redis часто используют для общего между инстансами rate limiter. Распространённые алгоритмы:

- **Fixed window** — счётчик на интервал; прост и экономен, но на границе двух интервалов возможен всплеск почти вдвое больше лимита.
- **Sliding window log** — точные временные отметки, но больше память и операций.
- **Sliding window counter** — приближённая оценка с меньшими затратами.
- **Token bucket / leaky bucket** — позволяет контролировать среднюю скорость и допустимый burst.

Счётчик и установка TTL должны быть согласованы атомарно (Lua/Function или подходящий паттерн), иначе конкурентные запросы и частичный сбой могут нарушить лимит.

## 14. Многоуровневый кеш

Частая схема — локальный кеш процесса L1 + Redis L2 + БД:

```text
запрос → L1 (память инстанса) → L2 (Redis) → источник
```

L1 уменьшает latency и нагрузку на Redis, но копии между инстансами могут расходиться. Инвалидация L1 может выполняться событием, Pub/Sub или коротким TTL. Pub/Sub при отключении инстанса не гарантирует доставку, поэтому TTL/проверка версии остаются полезной страховкой.

Продумайте, что делать при отказе L2: локальный кеш, прямое чтение источника, ограничение нагрузки или отказ. Одновременный промах L1 и отказ L2 могут создать шторм запросов к БД.

## 15. Типичные ошибки при использовании Redis

- Считать Redis надёжным хранилищем без настройки persistence, репликации, резервного копирования и проверки восстановления.
- Использовать Redis как единственный источник критичных бизнес-данных, не определив допустимую потерю.
- Хранить всё без TTL и не настраивать `maxmemory`/политику eviction.
- Использовать `KEYS *`, огромные `HGETALL`/диапазоны и длинные Lua-скрипты на рабочем трафике.
- Считать `MULTI/EXEC` транзакцией с rollback как в SQL.
- Считать pipeline атомарным.
- Считать реплику мгновенно согласованной с primary.
- Публиковать важные события через Pub/Sub, предполагая, что они будут доставлены офлайн-потребителям.
- Реализовать lock через `SETNX` без TTL, уникального токена и безопасного освобождения.
- При недоступности кеша бесконтрольно отправлять все запросы в БД.
- Использовать ключ без tenant/user-префикса, создавая пересечение данных разных пользователей.
- Сериализовать объекты без версии формата и не иметь плана миграции.
- Логировать токены сессий, пароли и персональные данные.

## 16. Наблюдаемость и эксплуатация

### Что измерять

- hit/miss по каждому важному кешу и типу ключа;
- latency Redis p50/p95/p99, отдельно клиентскую сетевую задержку;
- частоту ошибок, таймаутов, reconnect и переключений primary;
- RPS команд и распределение по типам команд;
- `used_memory`, RSS, фрагментацию, свободную память;
- число вытеснений (`evicted_keys`) и истечений (`expired_keys`);
- число подключённых клиентов и использование connection pool;
- replication offset/lag, состояние реплик, состояние Sentinel/Cluster;
- latency источника и нагрузку на БД, особенно при росте miss rate;
- размер и возраст ключей, hot keys и большие значения.

`INFO`, `SLOWLOG`, `LATENCY` и `SCAN` полезны для диагностики, но команды диагностики тоже могут потреблять ресурсы. Не запускайте массовый обход/сканирование ключей без оценки нагрузки.

### Настройки клиента и отказоустойчивость приложения

- **Connect timeout** ограничивает время установления соединения.
- **Command/read timeout** ограничивает ожидание ответа.
- **Connection pool** не должен создавать неконтролируемое число соединений.
- **Retry** должен быть ограниченным, с backoff и jitter; не повторяйте бесконечно неидемпотентную операцию.
- **Circuit breaker / bulkhead** ограничивают каскадный отказ.
- **Fallback** должен соответствовать критичности данных и защищать источник от перегрузки.
- Клиент для Cluster/Sentinel должен знать соответствующий режим и уметь обновлять топологию.

## 17. Безопасность Redis

- Не выставляйте Redis в публичную сеть без необходимости; ограничивайте доступ сетевыми правилами.
- Используйте ACL с отдельными пользователями, минимальными разрешениями и ротацией секретов.
- Используйте TLS, если трафик пересекает недоверенные сети и конфигурация это поддерживает.
- Не считайте пароль единственной защитой при открытом сетевом доступе.
- Не помещайте секреты в ключи, значения диагностических метрик и логи.
- Ограничивайте команды и доступ приложений согласно роли.
- Разделяйте окружения и учитывайте, что Redis — общий ресурс: префиксы ключей помогают организации, но не заменяют ACL/изоляцию.

## 18. Как выбрать, что кешировать

Для каждого кандидата ответьте:

1. Дорого ли получать/вычислять значение?
2. Часто ли один и тот же ключ запрашивают повторно?
3. Каков размер данных и кардинальность ключей?
4. Какой hit rate реалистичен?
5. Насколько устаревшими данные могут быть и как долго?
6. Как и когда инвалидировать ключ?
7. Что случится при промахе, истечении TTL, отказе кеша или массовом вытеснении?
8. Не приведёт ли кеширование к утечке между пользователями/тенантами?

Не кешируйте механически каждый ответ. Персонализированные, приватные и быстро меняющиеся данные требуют аккуратного выбора ключа и политики свежести. Для HTTP-кеша учитывайте `Cache-Control`, `ETag`, `Last-Modified`, `Vary` и приватность ответа.

## 19. Частые вопросы на собеседовании

### Чем кеш отличается от базы данных?

Кеш обычно оптимизирует быстрый доступ к повторно используемым данным и допускает вытеснение/устаревание; база данных — источник истины с моделью долговременного хранения и запросов. Redis может быть основным хранилищем в отдельных сценариях, но тогда отдельно проектируют durability, восстановление, согласованность и ограничения модели.

### Что такое cache-aside и как он работает?

Приложение читает кеш, при промахе обращается к источнику, записывает результат с TTL и возвращает его. При записи в источник приложение инвалидирует/обновляет ключ. Главные сложности — устаревание и одновременные промахи.

### Почему кеш не всегда ускоряет систему?

Сетевое обращение к кешу само имеет цену; сериализация, высокая кардинальность или низкий hit rate могут сделать кеш бесполезным. Он также может добавить нагрузку, ошибки и операции инвалидации. Нужно сравнивать end-to-end latency и нагрузку до/после.

### Как избежать cache stampede?

Single-flight/lock на обновление ключа, предварительное обновление, jitter для TTL, stale-while-revalidate и ограничение параллельной нагрузки на источник.

### В чём разница между eviction и expiration?

Expiration происходит из-за TTL. Eviction — вытеснение из-за политики памяти при достижении лимита. Оба случая могут привести к промаху, но причины и метрики различны.

### Redis однопоточный?

Команды на одном узле традиционно выполняются последовательно основным потоком, что даёт атомарность отдельной команды, но означает, что тяжёлая команда задерживает другие. В современных версиях некоторые задачи, в том числе сетевой I/O при настройке, могут использовать дополнительные потоки. Поэтому ответ «Redis полностью однопоточный» слишком упрощён.

### Redis быстрее SQL-базы?

Для многих операций по ключу Redis может быть быстрее благодаря памяти и простой модели доступа. Но сравнение зависит от сети, запроса, индексов, объёма данных, дискового кеша БД, сериализации и требований к транзакциям. Это не универсальное правило.

### Чем отличаются RDB и AOF?

RDB — периодические снимки, удобны для компактного восстановления/бэкапа, но возможна потеря изменений после последнего снимка. AOF журналирует операции и обычно позволяет восстановить более свежие изменения, но требует управления журналом и имеет свою стоимость. Выбор зависит от допустимого RPO и нагрузки.

### Чем отличаются Sentinel и Cluster?

Sentinel мониторит primary/replicas и организует failover без шардинга. Cluster распределяет ключи по hash slots между узлами и масштабирует объём данных горизонтально; он также использует replicas и failover.

### Что произойдёт, если Redis станет недоступен?

Зависит от роли Redis и fallback приложения. Для кеша можно временно читать источник, но нужно ограничить нагрузку, иначе возникнет каскадный отказ. Для сессий или очереди деградация может означать отказ части функций. Нужны таймауты, circuit breaker, мониторинг и заранее выбранная политика.

### Почему `GET` + `SET` не является безопасным инкрементом?

Между чтением и записью другая операция может изменить значение. Используйте атомарный `INCR` или скрипт/транзакцию, подходящие для более сложной логики.

### Гарантирует ли Redis Cluster отсутствие потери данных при failover?

Нет. Репликация в Redis обычно асинхронная, поэтому подтверждённая primary запись может не успеть попасть на реплику, выбранную новой primary. Настройки и `WAIT` могут изменить вероятность/компромисс, но гарантии нужно обсуждать в рамках модели отказов.

### Когда Redis не подходит?

Когда необходимы сложные реляционные запросы и ограничения, строгая долговечность/транзакционность без соответствующей конфигурации, объём данных не помещается в доступную память с приемлемой стоимостью, либо система не может безопасно пережить потерю/устаревание значений.

## 20. Короткий чек-лист перед production

- Определены источник истины, допустимое устаревание и стратегия инвалидации.
- Для ключей заданы разумные TTL; политика памяти соответствует роли Redis.
- Есть connect/read timeout, ограниченные retries и поведение при отказе кеша.
- Защищены источник данных и приложение от stampede/avalanche.
- Проверены сериализация, версия формата и изоляция ключей.
- Для важных данных настроены persistence, репликация, бэкапы и проверенное восстановление.
- Sentinel/Cluster выбраны по нужной задаче; failover и потеря связи отрепетированы.
- Настроены метрики, алерты и диагностика hot/big keys.
- Redis недоступен извне без необходимости и настроены ACL/сетевые ограничения.
- Проведён нагрузочный тест с реалистичными ключами, hit rate, TTL и сценарием отказа.
