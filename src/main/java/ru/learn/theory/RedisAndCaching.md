## 1. Что такое кеш и зачем он нужен

`[ ]` **Короткий ответ:** кеш — временное хранилище копий данных, которые дорого или медленно получить из источника: БД, удалённого сервиса, вычисления. Он снижает latency, разгружает источник и сглаживает пики. Цена — копия может устареть, а система получает ещё один компонент, который может отказать. Кеш ускоряет только повторные чтения: если hit rate низкий, он добавляет сетевой переход и сериализацию на каждый запрос.

| Понятие | Значение |
|---|---|
| Hit / miss | Ключ найден / не найден, нужно идти в источник |
| Hit rate | `hits / (hits + misses)` |
| Expiration | Удаление по истечении TTL — политика свежести |
| Eviction | Вытеснение из-за нехватки памяти по `maxmemory-policy` |
| Freshness | Насколько копия отстаёт от источника |
| Hit latency, miss latency | Задержка при попадании и при промахе (промах = кеш + источник + запись в кеш) |

**Практика.** Счётчики попаданий Redis (реальный вывод):

```bash
redis-cli CONFIG RESETSTAT
redis-cli SET k v; redis-cli GET k; redis-cli GET k; redis-cli GET k; redis-cli GET miss
redis-cli INFO stats | grep keyspace_
```

```text
keyspace_hits:3
keyspace_misses:1
```

Это общие счётчики узла. Hit rate по каждому типу ключа (товары, профили, сессии) нужно считать в приложении — общий показатель скрывает кеш, который не работает.

## 2. Где располагаются кеши

1. **Браузер, клиент** — статика, HTTP-ответы (`Cache-Control`, `ETag`).
2. **CDN, reverse proxy** — HTTP-ответы ближе к пользователю.
3. **Локальный кеш процесса** — память экземпляра приложения, например Caffeine.
4. **Распределённый кеш** — общий для всех экземпляров, например Redis.
5. **Кеш БД и ОС** — buffer pool, page cache.

`[ ]` **Короткий ответ:** чем ближе кеш к потребителю, тем он быстрее, но тем труднее синхронизировать его копии. Локальный кеш одного пода не виден другим подам и после записи расходится с ними. Распределённый кеш общий, но это сетевой вызов и отдельная система в эксплуатации.

## 3. Стратегии кеширования

`[ ]` **Короткий ответ:** cache-aside — приложение само читает из кеша, при промахе идёт в БД и кладёт результат в кеш; самая распространённая стратегия. Read-through — то же, но загрузку делает сам кеш через загрузчик. Write-through — запись идёт и в кеш, и в источник синхронно. Write-behind — запись сначала в кеш, в источник позже асинхронно: быстро, но можно потерять подтверждённые данные. Write-around — запись только в источник, кеш заполнится при чтении.

| Стратегия | Чтение | Запись | Плюсы | Минусы |
|---|---|---|---|---|
| Cache-aside | Кеш → при промахе БД → положить в кеш | В БД, затем удалить ключ | Просто, в кеше только нужное | Первый запрос медленный, stampede, окно устаревания |
| Read-through | Кеш сам загружает при промахе | — | Загрузка скрыта за абстракцией | Нужен провайдер с загрузчиком, поведение менее очевидно |
| Write-through | — | Кеш и источник синхронно | После записи кеш свеж | Запись дороже, частичный сбой между двумя хранилищами |
| Write-behind | — | Кеш, потом источник асинхронно | Низкая latency, объединение записей | Потеря данных при отказе кеша, порядок, повторы |
| Write-around | — | Только источник | Одноразовые записи не вытесняют полезное | Первое чтение после записи — промах |

```text
cache-aside, чтение:
  v = cache.get(key)
  if v == null:
      v = db.load(id)
      cache.set(key, v, ttl)
  return v

cache-aside, запись:
  db.update(...)      // commit
  cache.delete(key)
```

Write-behind допустим только при осознанных требованиях к потере данных и с надёжным журналом изменений.

## 4. Инвалидация и согласованность

`[ ]` **Короткий ответ:** безопасный порядок для cache-aside — сначала записать в БД, после успешного commit удалить ключ; следующее чтение загрузит свежее значение. Удалять лучше, чем обновлять: две конкурентные записи могут обновить кеш в обратном порядке, и в нём навсегда (до TTL) останется старое значение. Удаление ключа до записи в БД открывает гонку: параллельное чтение возьмёт старое значение из БД и положит обратно. TTL нужен всегда — как страховка от потерянной инвалидации.

<details>
<summary>Гонка, которая остаётся даже при правильном порядке</summary>

```text
читатель R                          писатель W
cache miss
SELECT -> старое значение v1
                                    UPDATE -> v2, COMMIT
                                    DEL key
SET key v1        ← в кеше старое значение до истечения TTL
```

Окно маленькое: читатель должен прочитать до commit, а записать в кеш после инвалидации. Варианты защиты:

- короткий TTL — принять окно устаревания;
- отложенное повторное удаление (delayed double delete) — удалить ключ ещё раз через время, большее типичной длительности чтения;
- версия в значении и запись только если версия новее (`SET` через Lua со сравнением);
- инвалидация по событиям CDC из журнала БД — порядок событий совпадает с порядком commit.

Для строгой согласованности (баланс счёта) кеш не используют как источник ответа.

</details>

| Способ контролировать устаревание | Суть |
|---|---|
| TTL | Ограничивает максимальный возраст копии |
| Инвалидация при записи | Удалить ключ после commit |
| События, CDC | Источник публикует изменения, потребители удаляют связанные ключи |
| Версия в ключе | `product:v3:123`: смена версии схемы — старые ключи истекают сами |
| Короткий TTL + инвалидация | Распространённая комбинация |

**Отрицательное кеширование.** Ответ «не найдено» тоже кешируют, на более короткий срок, — это защита от cache penetration. Нельзя кешировать ошибку источника как «нет данных»: временный сбой БД превратится в закешированное отсутствие.

## 5. Типичные проблемы кеша

`[ ]` **Короткий ответ:**

| Проблема | Что происходит | Решения |
|---|---|---|
| Stampede (dogpile) | Истёк TTL популярного ключа, сотни запросов одновременно идут в БД | Single-flight или блокировка на загрузку ключа, обновление заранее, stale-while-revalidate |
| Penetration | Запросы несуществующих ключей всегда доходят до БД | Отрицательный кеш, валидация id, rate limit, Bloom filter |
| Avalanche | Массово истекли ключи или упал весь кеш | Jitter TTL, прогрев, circuit breaker, ограничение нагрузки на источник |
| Hot key | Один ключ перегружает один узел или шард | Локальный кеш L1, реплики для чтения, разбиение значения |
| Big key | Огромная коллекция или значение блокирует поток команд | Ограничить размер, разбить, `UNLINK` вместо `DEL` |
| Устаревание | Копия расходится с источником | Явно определить допустимое окно; критичные данные не кешировать |

**Практика.** 50 потоков одновременно запрашивают товар, которого нет в кеше; загрузка из БД занимает 200 мс. Без защиты и с блокировкой на загрузку ключа (реальный вывод, код ниже):

```text
cache-aside без защиты: 50 запросов, обращений к БД = 50, время = 0.25 с
cache-aside с блокировкой: 50 запросов, обращений к БД = 1, время = 0.22 с
```

Время для пользователя почти одинаковое, а нагрузка на БД упала в 50 раз. На популярном ключе это разница между нормальной работой и падением БД после каждого истечения TTL.

<details>
<summary>stampede.py — код эксперимента</summary>

```python
import threading, time, uuid, redis

r = redis.Redis(port=6390, decode_responses=True)
db_calls = 0
lock = threading.Lock()
release = r.register_script(open("release.lua").read())   # скрипт — в разделе 13

def load_from_db(pid):
    global db_calls
    with lock:
        db_calls += 1
    time.sleep(0.2)                      # медленный запрос к БД
    return f"product-{pid}"

def get_naive(pid):
    key = f"product:{pid}"
    v = r.get(key)
    if v is None:
        v = load_from_db(pid)
        r.set(key, v, ex=60)
    return v

def get_with_lock(pid):
    key, lk = f"product:{pid}", f"lock:product:{pid}"
    while True:
        v = r.get(key)
        if v is not None:
            return v
        token = str(uuid.uuid4())
        if r.set(lk, token, nx=True, px=5000):  # только один идёт в БД
            try:
                v = r.get(key)                 # повторная проверка после захвата
                if v is None:
                    v = load_from_db(pid)
                    r.set(key, v, ex=60)
                return v
            finally:
                release(keys=[lk], args=[token])     # снять только свою блокировку
        time.sleep(0.02)                       # остальные ждут прогрева

for name, fn in [("cache-aside без защиты", get_naive), ("cache-aside с блокировкой", get_with_lock)]:
    r.flushall(); db_calls = 0
    ts = [threading.Thread(target=fn, args=(1,)) for _ in range(50)]
    t0 = time.time(); [t.start() for t in ts]; [t.join() for t in ts]
    print(f"{name}: 50 запросов, обращений к БД = {db_calls}, время = {time.time()-t0:.2f} с")
```

</details>

<details>
<summary>Тонкости решений</summary>

- Внутри одного процесса single-flight дешевле распределённой блокировки: Caffeine `get(key, loader)` и `@Cacheable(sync = true)` в Spring гарантируют одну загрузку ключа на экземпляр. При 30 подах это до 30 загрузок вместо тысяч — часто достаточно.
- Распределённая блокировка сама может стать узким местом и точкой отказа: ограниченное время ожидания и понятное поведение, если Redis недоступен.
- Jitter: `ttl = base + random(0, base * 0.1)` — ключи, загруженные одновременно (прогрев), не истекут одновременно.
- Bloom filter отвечает «точно нет» или «возможно есть»; в Redis 8 он входит в базовую поставку (`BF.ADD`, `BF.EXISTS`).
- Не сбрасывайте весь production-кеш (`FLUSHALL`) без плана — это avalanche своими руками.

</details>

## 6. Redis: модель выполнения и версии

`[ ]` **Короткий ответ:** Redis — in-memory хранилище структур данных с TTL, атомарными командами, репликацией, персистентностью и кластеризацией. Команды выполняются одним основным потоком последовательно, поэтому каждая команда атомарна и блокировок нет. Но сервер не полностью однопоточный: сетевой ввод-вывод можно вынести в I/O-потоки, а сохранение на диск, `UNLINK` и другие фоновые задачи идут отдельно. Следствие однопоточного исполнения: одна медленная команда (`KEYS *`, `HGETALL` на миллион полей, долгий Lua) задерживает всех клиентов узла.

<details>
<summary>Что важно знать о версиях</summary>

- **Redis 8** (GA май 2025) включил в базовую поставку JSON, Query Engine (поиск, в том числе векторный), Time Series и вероятностные структуры (Bloom, cuckoo, count-min sketch, top-k, t-digest), ранее бывшие отдельными модулями Redis Stack, и добавил Vector Sets. Redis 8 доступен в том числе под AGPLv3, вдобавок к RSALv2 и SSPLv1 ([обзор Redis 8](https://university.kurz.fyi/databases/database-concepts/redis-8-stack-in-core-json-search-vectorsets-timeseries), [анонс Redis 8 GA](https://redis.io/blog/redis-8-ga.md)).
- **Redis 7.4** добавил TTL на отдельные поля hash (`HEXPIRE`, `HTTL`) — проверено ниже в разделе 8.
- **Redis 8.4** добавил атомарные compare-and-set и compare-and-delete для строк: `SET ... IFEQ` и команда `DELEX` ([release notes 8.4](https://github.com/redis/redis/blob/8.4/00-RELEASENOTES), [документация DELEX](https://redis.io/docs/staging/dev/commands/delex/)). Освобождение блокировки больше не требует Lua.
- На осень 2026 актуальны ветки 8.8 и 8.10 ([релиз 8.10.2](https://github.com/redis/redis/releases/tag/8.10.2)).
- После смены лицензии в 2024 году сообщество выпустило форк Valkey; в облаках часто встречается именно он, протокол и команды базовой части совместимы.

</details>

**Уточняющие вопросы:**

- Redis быстрее SQL-базы? Для простого чтения по ключу из памяти — обычно да. Но это не замена БД: нет произвольных запросов и join, данные ограничены памятью, долговечность настраивается и стоит производительности. Сравнивайте конкретную операцию с учётом сети: RTT часто дороже самой команды.
- Что значит сложность команды? Большинство операций по ключу O(1), `ZADD` O(log N), `LRANGE`, `SMEMBERS`, `HGETALL` — O(N). Проверяйте сложность и реальный размер коллекции.

## 7. Структуры данных Redis

`[ ]` **Короткий ответ:** выбор структуры — главный инструмент Redis: правильная структура делает операцию атомарной и дешёвой на сервере, без чтения-изменения-записи в приложении.

| Структура | Для чего | Команды |
|---|---|---|
| String | Значение, сериализованный объект, счётчик | `GET`, `SET`, `MGET`, `INCR`, `INCRBY` |
| Hash | Поля одного объекта, частичное обновление | `HSET`, `HGET`, `HMGET`, `HINCRBY`, `HEXPIRE` |
| List | Простая очередь, последние N событий | `LPUSH`, `RPOP`, `BLPOP`, `LRANGE`, `LTRIM` |
| Set | Уникальные элементы, пересечения | `SADD`, `SISMEMBER`, `SINTER`, `SCARD` |
| Sorted Set | Рейтинг, приоритетная очередь, окно по времени | `ZADD`, `ZRANGE`, `ZRANK`, `ZINCRBY`, `ZREMRANGEBYSCORE` |
| Bitmap | Флаги по числовому id (был ли пользователь онлайн в день) | `SETBIT`, `GETBIT`, `BITCOUNT` |
| HyperLogLog | Приближённое число уникальных (около 12 КБ на счётчик, ошибка порядка 0,8 %) | `PFADD`, `PFCOUNT`, `PFMERGE` |
| Stream | Журнал событий с consumer groups и подтверждениями | `XADD`, `XREADGROUP`, `XACK`, `XAUTOCLAIM` |
| Geo | Точки и поиск поблизости | `GEOADD`, `GEOSEARCH` |
| JSON, Vector Set, Bloom, Time Series | Документы, векторный поиск, вероятностные структуры (Redis 8) | `JSON.SET`, `VADD`, `BF.ADD`, `TS.ADD` |

**Практика.** Компактное кодирование: маленький hash хранится как listpack, после 512 полей Redis переводит его в hashtable (реальный вывод):

```text
HSET user:1 name Ann age 30       → OBJECT ENCODING: listpack,  MEMORY USAGE: 80 байт
user:2 c 200 полями               → listpack
user:2 c 600 полями               → hashtable, MEMORY USAGE: 32296 байт
CONFIG GET hash-max-listpack-entries → 512
```

Поэтому хранить объект пользователя одним hash выгоднее, чем десятком отдельных строковых ключей: меньше накладных расходов на ключ.

**Уточняющие вопросы:**

- Рейтинг игроков с топ-10? Sorted Set: `ZINCRBY leaderboard 10 user:42`, `ZREVRANGE leaderboard 0 9 WITHSCORES`.
- Уникальные посетители за день на миллионы пользователей? HyperLogLog, если допустима погрешность; Bitmap, если id — плотные числа и нужна точность.
- Объект JSON в String или в Hash? String — читаем и пишем целиком, проще сериализация. Hash — частичное обновление полей и TTL на поле, но вложенность только одного уровня.

## 8. Ключи, TTL и память

### 8.1. Именование ключей

```text
user:42
user:42:profile
product:sku-123
tenant:7:order:1842
```

Читаемые предсказуемые ключи с разделителями помогают диагностике. Длинные повторяющиеся префиксы расходуют память. Префикс тенанта или пользователя обязателен там, где данные персональные: ключ `profile:42` без тенанта — путь к утечке данных между клиентами. В ключ не кладут секреты.

### 8.2. TTL

`[ ]` **Короткий ответ:** `EX`/`PX` в `SET` или `EXPIRE` задают время жизни. `TTL` возвращает секунды, `-1` — ключ без TTL, `-2` — ключа нет. Ключи удаляются лениво при обращении и активно фоновым процессом выборочно, поэтому истёкший ключ может какое-то время занимать память. Главная ловушка: обычный `SET` без параметров срока жизни снимает TTL.

**Практика** (реальный вывод):

```text
SET product:1 v1 EX 100   → OK
TTL product:1             → 100
SET product:1 v2          → OK
TTL product:1             → -1      ← TTL пропал, ключ стал вечным
SET product:1 v3 EX 100
SET product:1 v4 KEEPTTL  → OK
TTL product:1             → 100     ← KEEPTTL сохранил срок
TTL nokey                 → -2
```

TTL на поле hash (Redis 7.4+):

```text
HSET session:1 token abc csrf xyz
HEXPIRE session:1 60 FIELDS 1 csrf   → 1
HTTL session:1 FIELDS 2 token csrf   → -1, 60
```

### 8.3. maxmemory и eviction

`[ ]` **Короткий ответ:** `maxmemory` — лимит памяти, `maxmemory-policy` — что делать при достижении. `noeviction` — отказывать в записи с ошибкой OOM (для хранилища, где ключи терять нельзя). `allkeys-lru` или `allkeys-lfu` — вытеснять давно или редко используемые из всех ключей (для чистого кеша). `volatile-*` — только среди ключей с TTL. LRU и LFU приближённые: Redis сравнивает случайную выборку ключей, а не держит точный глобальный список.

**Практика.** Лимит 3 МБ, пишем 5000 значений по 1 КБ (реальный вывод):

```text
maxmemory-policy noeviction:
   2067 OK
   2933 OOM command not allowed when used memory > 'maxmemory'.
DBSIZE → 2067

maxmemory-policy allkeys-lru, ещё 5000 значений:
   5000 OK
DBSIZE → 2030
evicted_keys:5037
EXISTS k1 k9999 → 1          ← старый k1 вытеснен, свежий k9999 на месте
```

С `noeviction` приложение получает ошибки записи — его нужно к этому готовить. С `allkeys-lru` записи проходят, но ключи без предупреждения исчезают: недопустимо, если в том же Redis лежат сессии или блокировки. Отсюда правило: кеш и данные с другим требованием к сохранности держат в разных экземплярах.

<details>
<summary>Сколько памяти планировать</summary>

`used_memory` — данные; `used_memory_rss` — то, что видит ОС, включая фрагментацию. Сверх данных нужен запас на буферы клиентов и репликации, фрагментацию и copy-on-write при `fork` во время сохранения RDB или переписывания AOF: при интенсивной записи изменённые страницы копируются, и потребление памяти может временно вырасти заметно. Наблюдайте `mem_fragmentation_ratio`, `evicted_keys`, `expired_keys`.

</details>

## 9. Атомарность: MULTI, WATCH, Lua, pipeline

### 9.1. MULTI/EXEC и WATCH

`[ ]` **Короткий ответ:** `MULTI` ставит команды в очередь, `EXEC` выполняет их подряд без вклинивания других клиентов. Но отката нет: если одна команда упала с ошибкой выполнения, остальные всё равно применяются. `WATCH` даёт оптимистическую блокировку: если наблюдаемый ключ изменился до `EXEC`, транзакция не выполняется (`EXEC` возвращает nil), и клиент повторяет попытку.

**Практика.** Ошибка в середине транзакции (реальный вывод):

```text
SET balance 100
MULTI
INCRBY balance 50     → QUEUED
LPUSH balance x       → QUEUED
INCRBY balance 1      → QUEUED
EXEC
  1) 150
  2) WRONGTYPE Operation against a key holding the wrong kind of value
  3) 151
GET balance           → 151      ← первая и третья команды применились
```

Конфликт с `WATCH`: клиент A следит за `stock`, клиент B меняет его до `EXEC`:

```text
A: WATCH stock;  GET stock → 5
B: DECR stock → 4
A: MULTI; DECR stock → QUEUED; EXEC → (nil)    ← транзакция отменена
GET stock → 4
```

Синтаксические ошибки (неизвестная команда) отлавливаются при постановке в очередь, и тогда `EXEC` отклоняет всю транзакцию. Ошибки выполнения — нет.

### 9.2. Lua и Functions

`[ ]` **Короткий ответ:** Lua-скрипт (`EVAL`, `EVALSHA`) или функция (`FCALL`, Redis 7+) выполняются атомарно целиком — это способ сделать «прочитать, проверить, изменить» одной операцией на сервере. Пока скрипт работает, узел не обслуживает другие команды, поэтому скрипты должны быть короткими. Все ключи, с которыми работает скрипт, передаются в `KEYS` — в кластере они должны быть в одном слоте.

### 9.3. Pipeline

`[ ]` **Короткий ответ:** pipeline — клиент отправляет пачку команд, не дожидаясь ответа на каждую, и экономит сетевые round-trip. Он не атомарен: между командами пачки могут выполниться команды других клиентов, и часть пачки может завершиться ошибкой. Нужна атомарность — `MULTI/EXEC` или Lua; нужна скорость — pipeline; можно совмещать.

### 9.4. Почему GET + SET — не инкремент

Два клиента читают `5`, оба записывают `6` — одно увеличение потеряно. Правильно: `INCR`/`INCRBY` (атомарная команда), `WATCH` + `MULTI`, или Lua.

## 10. Персистентность

`[ ]` **Короткий ответ:** RDB — периодический снимок всего набора данных в компактный файл: удобно для бэкапа и быстрого старта, но теряются изменения после последнего снимка. AOF — журнал команд записи; при `appendfsync everysec` при аварии теряется около секунды, при `always` — почти ничего, но запись сильно дороже. Часто включают оба. Для чистого кеша, который можно восстановить из источника, персистентность обычно отключают. Ни RDB, ни AOF, ни репликация не заменяют проверенные бэкапы.

| | RDB | AOF |
|---|---|---|
| Что пишется | Снимок по расписанию | Каждая команда записи |
| Потеря при аварии | С момента последнего снимка | `always` — минимум, `everysec` — около 1 с, `no` — на усмотрение ОС |
| Размер | Компактный | Растёт, нужен rewrite |
| Старт | Быстрый | Дольше, воспроизведение журнала |
| Цена | `fork` и copy-on-write | Нагрузка на диск при каждой записи |

Решение о персистентности принимают по RPO и RTO для данных в конкретном экземпляре, а не по слову «Redis». Восстановление нужно тестировать на той же версии и конфигурации, что в production.

## 11. Репликация, Sentinel, Cluster

### 11.1. Репликация

`[ ]` **Короткий ответ:** репликация primary → replica асинхронная. Реплика может отставать: чтение с неё сразу после записи может вернуть старое значение, а при отказе primary последние неотреплицированные записи теряются. `WAIT N timeout` ждёт подтверждения от N реплик, но не делает Redis строго консистентным: при failover может быть выбрана реплика без этих данных. Репликация — не бэкап: `FLUSHALL` реплицируется мгновенно.

### 11.2. Sentinel и Cluster

`[ ]` **Короткий ответ:** Sentinel — высокая доступность одного набора данных без шардирования: несколько процессов Sentinel следят за primary, по кворуму выбирают новую primary из реплик и сообщают клиентам адрес. Cluster — горизонтальное шардирование: ключи распределены по 16 384 hash slots, каждый primary отвечает за диапазон слотов и имеет свои реплики с автоматическим failover. Нужно больше памяти или throughput записи, чем у одного узла, — Cluster; хватает одного узла, нужна только отказоустойчивость — Sentinel.

| | Sentinel | Cluster |
|---|---|---|
| Шардирование | Нет | 16 384 слота по узлам |
| Failover | Да, по кворуму Sentinel | Да, встроенный |
| Мультиключевые операции | Любые | Только ключи одного слота |
| Клиент | Узнаёт primary у Sentinel | Карта слотов, обработка `MOVED` и `ASK` |
| Потеря при failover | Возможна (асинхронная репликация) | Возможна |

**Практика.** Hash slot вычисляется по ключу; hash tag в фигурных скобках задаёт часть, по которой считается слот (проверено на узле в режиме cluster):

```text
CLUSTER KEYSLOT user:1:cart        → 6211
CLUSTER KEYSLOT user:1:profile     → 12348     ← разные слоты, MULTI/MGET невозможны
CLUSTER KEYSLOT {user:1}:cart      → 10778
CLUSTER KEYSLOT {user:1}:profile   → 10778     ← один слот
```

Без режима cluster команда отвечает `ERR This instance has cluster support disabled`. Не ставьте один hash tag на все ключи — получится один горячий слот и один перегруженный шард.

<details>
<summary>MOVED и ASK</summary>

- `MOVED 3999 10.0.0.5:6379` — слот постоянно обслуживает другой узел; клиент обновляет карту слотов.
- `ASK` — слот переносится прямо сейчас; клиент разово идёт на указанный узел с командой `ASKING`, карту не обновляет.
- Клиент должен быть cluster-aware (Lettuce, Jedis в режиме cluster, redis-py `RedisCluster`), иначе каждая команда к «чужому» слоту закончится ошибкой.

</details>

## 12. Pub/Sub и Streams

`[ ]` **Короткий ответ:** Pub/Sub — эфемерная рассылка: сообщение получают только те, кто подписан в момент публикации, ничего не хранится. Отключился подписчик на секунду — сообщения за эту секунду потеряны. Подходит для уведомлений вроде «сбросьте L1-кеш» при наличии TTL как страховки. Streams — журнал с id сообщений, consumer groups, подтверждениями (`XACK`) и списком неподтверждённых (PEL), то есть at-least-once с возможностью перехватить зависшие сообщения.

**Практика.** Pub/Sub: `PUBLISH` возвращает число получателей (реальный вывод):

```text
PUBLISH events e1 → 0          ← подписчиков нет, сообщение исчезло
(подписчик подключился)
PUBLISH events e2 → 1
подписчик получил: message events e2      ← e1 он уже не получит никогда
```

Streams: worker `w1` взял два сообщения и «упал», не подтвердив; `w2` перехватывает их через `XAUTOCLAIM` после 1 секунды простоя:

```text
XADD orders * order 1 / 2 / 3
XGROUP CREATE orders billing 0
XREADGROUP GROUP billing w1 COUNT 2 STREAMS orders >   → 2 сообщения
XPENDING orders billing                                → 2 неподтверждённых, владелец w1
XAUTOCLAIM orders billing w2 1000 0-0 COUNT 10         → оба сообщения переданы w2
XPENDING orders billing - + 10
  1793001639734-0  w2  idle 4 мс  доставок: 2
  1793001639737-0  w2  idle 4 мс  доставок: 2
```

Счётчик доставок позволяет отправлять сообщение в отдельный stream-DLQ после N неудачных попыток. Streams в памяти: ограничивайте длину `XADD ... MAXLEN ~ 100000` или `XTRIM`. Для больших объёмов, долгого хранения и replay — Kafka.

## 13. Распределённая блокировка

`[ ]` **Короткий ответ:** захват — `SET lock:res <уникальный токен> NX PX 10000`: только если ключа нет, с ограниченным сроком аренды, чтобы блокировка не осталась навсегда после падения владельца. Освобождение — только если токен всё ещё наш, атомарно: Lua-скрипт или в Redis 8.4+ `DELEX key IFEQ token`. Простой `DEL` может удалить чужую блокировку. Принципиальное ограничение: процесс может «уснуть» (GC-пауза, сеть) дольше TTL и продолжить работу, уже не владея блокировкой; для защиты ресурса нужен fencing token, который проверяет сам ресурс.

**Практика.** A захватил блокировку на 1 с и завис; B получил её после истечения; A «просыпается» (реальный вывод):

```text
A: SET lock:order:42 token-A NX PX 1000    → OK
B: SET lock:order:42 token-B NX PX 1000    → (nil)    ← занято
   (прошло 1.2 с, срок A истёк)
B: SET lock:order:42 token-B NX PX 30000   → OK
A: DEL lock:order:42                       → 1        ← A удалил блокировку B
GET lock:order:42                          → (nil)    ← ресурс не защищён

(повтор с безопасным освобождением)
A: EVAL release.lua lock:order:42 token-A  → 0        ← не наш токен, ничего не удалено
GET lock:order:42                          → token-B
B: EVAL release.lua lock:order:42 token-B  → 1
```

```lua
-- release.lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

```redis
# Redis 8.4+ без Lua (не запускалось: в среде 8.0.5)
DELEX lock:order:42 IFEQ token-A
SET lock:order:42 token-A IFEQ token-A PX 10000     # продлить, только если блокировка наша
```

<details>
<summary>Fencing token и Redlock</summary>

- Fencing token — монотонно растущий номер аренды (например, `INCR lock:order:42:fence` при захвате). Каждая запись в защищаемый ресурс передаёт номер, и ресурс отклоняет операции со старым номером: `UPDATE ... WHERE fence < :token`. Тогда «проснувшийся» A с номером 33 не перезапишет работу B с номером 34.
- Redlock — захват на большинстве из N независимых узлов Redis. Его гарантии при паузах процессов и расхождении часов — предмет известной дискуссии; без fencing он не даёт корректности.
- Если ресурс — строка в БД, часто проще использовать саму БД: `SELECT ... FOR UPDATE`, advisory lock, оптимистическую версию. Распределённая блокировка не заменяет транзакцию в системе, где лежит ресурс.
- Блокировка в Redis хороша для эффективности (не делать одну работу дважды, как в stampede); для корректности (не списать деньги дважды) нужны fencing или идемпотентность.

</details>

## 14. Rate limiting

`[ ]` **Короткий ответ:** Redis — общий для всех экземпляров счётчик для ограничения частоты.

| Алгоритм | Как | Плюсы | Минусы |
|---|---|---|---|
| Fixed window | `INCR rl:user:42:<минута>` + `EXPIRE` | Просто, дёшево | На стыке окон возможен всплеск почти вдвое больше лимита |
| Sliding window log | Sorted Set с отметками времени, `ZREMRANGEBYSCORE` старых | Точно | Память и операции на каждый запрос |
| Sliding window counter | Взвешенная сумма текущего и прошлого окна | Почти точно, дёшево | Приближение |
| Token bucket | Токены пополняются с постоянной скоростью, запрос забирает токен | Контролирует среднюю скорость и burst | Сложнее, нужен Lua |

```lua
-- fixed window атомарно: инкремент и TTL одной операцией
local c = redis.call("INCR", KEYS[1])
if c == 1 then redis.call("EXPIRE", KEYS[1], ARGV[1]) end
return c
```

Если сделать `INCR` и `EXPIRE` двумя командами из приложения и упасть между ними, ключ останется без TTL, и пользователь будет заблокирован навсегда.

## 15. Многоуровневый кеш и Spring Cache

`[ ]` **Короткий ответ:** L1 — локальный кеш процесса (Caffeine), L2 — Redis, затем источник. L1 убирает сетевой переход и защищает от hot key, но копии на подах расходятся. Инвалидация L1 — событием через Pub/Sub или Streams плюс короткий TTL как страховка, потому что Pub/Sub не доставляет сообщения отключённым экземплярам. Нужно продумать отказ L2: одновременный промах L1 и недоступность Redis не должны обрушить весь трафик в БД.

```text
запрос → L1 (Caffeine, TTL 10 с) → L2 (Redis, TTL 10 мин) → БД
```

<details>
<summary>Spring Cache: что спросят</summary>

```java
@Cacheable(cacheNames = "products", key = "#id", sync = true)
public ProductDto get(long id) { return repository.findDto(id); }

@CacheEvict(cacheNames = "products", key = "#cmd.id")
@Transactional
public void update(UpdateProduct cmd) { ... }
```

Пример не запускался.

- Аннотации работают через прокси: вызов кешируемого метода из того же класса (`this.get(id)`) идёт мимо прокси, и кеш не используется.
- `sync = true` — одна загрузка ключа на экземпляр приложения (single-flight внутри JVM), не распределённая блокировка.
- `@CacheEvict` вместе с `@Transactional`: удаление может произойти до commit, и параллельное чтение положит старое значение обратно. Нужен порядок «commit, потом evict» — например, `TransactionAwareCacheDecorator` или инвалидация в `afterCommit`.
- Кешируйте DTO, а не JPA-сущности: прокси ленивой загрузки и сессия не переживут сериализацию.
- Сериализация: в значение добавляйте версию формата; после изменения класса старые записи в Redis должны либо читаться, либо игнорироваться (смена префикса ключа).

</details>

## 16. Эксплуатация и безопасность

`[ ]` **Короткий ответ на «что, если Redis недоступен»:** зависит от роли Redis. Для кеша — деградация: идём в источник, но ограниченно (circuit breaker, bulkhead, лимит параллельных загрузок), иначе вслед за Redis упадёт БД. Для сессий, блокировок, rate limiter — решаем заранее: отказывать (fail closed) или пропускать (fail open). Клиент обязан иметь connect и command timeout: без таймаутов недоступный Redis подвесит все потоки приложения.

| Что измерять | Зачем |
|---|---|
| Hit/miss по типам ключей | Работает ли кеш |
| Latency Redis p50/p99 и клиентская | Медленные команды, сеть |
| Ошибки, таймауты, reconnect, failover | Стабильность |
| `used_memory`, RSS, фрагментация | Запас памяти |
| `evicted_keys`, `expired_keys` | Хватает ли памяти, правильны ли TTL |
| Подключённые клиенты, пул соединений | Утечки и перегрузка соединений |
| Replication lag | Риск потерь при failover |
| Нагрузка на БД при росте miss rate | Эффект кеша на источник |
| Hot и big keys | `redis-cli --hotkeys` (нужна LFU-политика), `--bigkeys`, `MEMORY USAGE` |

Диагностика: `INFO`, `SLOWLOG GET`, `LATENCY DOCTOR`, `SCAN` вместо `KEYS *`. Диагностические команды тоже нагружают узел.

**Клиент:** connect timeout, command timeout, ограниченный пул, ограниченные ретраи с backoff и jitter (не повторять неидемпотентные операции бесконечно), режим Sentinel или Cluster, если он используется.

**Безопасность:**

- Не выставлять Redis в публичную сеть; сетевые политики.
- ACL с отдельными пользователями и минимальными правами, ротация паролей; опасные команды (`FLUSHALL`, `CONFIG`, `KEYS`) недоступны приложению.
- TLS при передаче через недоверенную сеть.
- Не хранить секреты в ключах, логах и метриках.
- Префиксы ключей — организация, а не изоляция; изоляция — ACL и отдельные экземпляры.

## 17. Пробное собеседование

<details>
<summary>1. Каталог товаров: 50 000 RPS чтения, БД не справляется. Спроектируйте кеш.</summary>

Cache-aside на Redis с ключом `product:v1:<id>`, значение — DTO с версией формата, TTL 10 минут с jitter. При изменении товара — commit, затем удаление ключа или событие CDC, которое удаляет ключ. Для топовых товаров — L1 Caffeine на 5–10 секунд (hot key). Защита от stampede — single-flight в JVM и при необходимости блокировка в Redis; от penetration — отрицательный кеш на 30 секунд. `allkeys-lru`, отдельный экземпляр под кеш. Метрики hit rate и нагрузки на БД, таймауты и circuit breaker на клиенте.

</details>

<details>
<summary>2. После деплоя hit rate упал с 95 % до 20 %. Что проверить?</summary>

Изменился ключ или сериализация (новый префикс, другой формат — старые записи не читаются); TTL стал меньше или пропал; новые параметры в ключе увеличили кардинальность; кто-то вызывает `FLUSHALL` или массовое удаление; память кончилась и растёт `evicted_keys`; кеш обходится из-за self-invocation в Spring.

</details>

<details>
<summary>3. Счётчик просмотров: GET, +1, SET теряет просмотры. Почему и как исправить?</summary>

Гонка read-modify-write: два запроса читают одно значение и оба пишут +1. Исправление — атомарный `INCR`. Для больших объёмов — `INCR` в Redis и периодический сброс накопленного в БД.

</details>

<details>
<summary>4. Сессии пользователей и кеш каталога в одном Redis с allkeys-lru. В чём риск?</summary>

При нехватке памяти Redis вытеснит и сессии — пользователи разлогинятся случайным образом. Разные требования к сохранности — разные экземпляры: кеш с `allkeys-lru` без персистентности, сессии с `noeviction` (или `volatile-*`), репликацией и, возможно, AOF.

</details>

<details>
<summary>5. Гарантирует ли Redis Cluster отсутствие потерь при failover?</summary>

Нет. Репликация асинхронная: primary подтвердил запись клиенту, упал до передачи на реплику — реплика стала primary без этой записи. `WAIT` уменьшает окно, но не устраняет. Если потеря недопустима, Redis не должен быть единственным хранилищем этих данных.

</details>

<details>
<summary>6. Когда Redis не подходит?</summary>

Данные больше разумного объёма памяти; нужны сложные запросы, join и строгие транзакции с откатом; критичные данные без допустимой потери и без продуманной репликации и бэкапов; долговременное хранение событий с replay — это Kafka; аналитика по большим объёмам.

</details>

<details>
<summary>7. Чем eviction отличается от expiration?</summary>

Expiration — ключ удаляется, потому что истёк его TTL: это решение приложения о свежести. Eviction — Redis удаляет ключ из-за нехватки памяти по `maxmemory-policy`, даже если TTL не истёк или его нет: это аварийный механизм нехватки ресурсов.

</details>

## 18. Чек-лист перед production

- Определены источник истины, допустимое устаревание и стратегия инвалидации.
- У ключей разумные TTL с jitter; `maxmemory` и политика соответствуют роли экземпляра.
- Есть connect и command timeout, ограниченные ретраи, понятное поведение при отказе Redis.
- Источник защищён от stampede и avalanche.
- Сериализация с версией формата, изоляция ключей тенантов и пользователей.
- Для важных данных — персистентность, репликация, бэкапы и проверенное восстановление.
- Sentinel или Cluster выбраны по задаче; failover отрепетирован.
- Метрики, алерты, диагностика hot и big keys.
- Redis недоступен извне, настроены ACL и TLS при необходимости.
- Нагрузочный тест с реалистичными ключами, hit rate, TTL и сценарием отказа.
