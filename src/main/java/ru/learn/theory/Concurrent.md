# Многопоточность и конкурентность

Процесс — изолированная среда выполнения, а поток — последовательность исполнения внутри процесса. Потоки одного процесса разделяют heap и файловые дескрипторы, но у каждого есть собственный стек и состояние выполнения. JVM обычно работает как процесс ОС и может создавать платформенные и виртуальные потоки.

## Java Memory Model и `happens-before`

`happens-before` — отношение порядка из Java Memory Model. Если действие A happens-before действия B, то эффекты A видимы B; это не утверждение о физическом времени исполнения. Между потоками без такого отношения возможны гонки данных и неожиданные наблюдения.

Основные гарантии:

- действия в одном потоке упорядочены по правилам программы;
- выход из `synchronized`-блока по монитору happens-before последующему входу в блок по тому же монитору;
- запись в `volatile`-поле happens-before последующему чтению этого поля;
- вызов `Thread.start()` happens-before действиям запущенного потока, а действия потока — успешному возврату из `join()`;
- публикация через потокобезопасные классы и синхронизаторы `java.util.concurrent` устанавливает свои гарантии видимости.

Безопасная публикация и неизменяемые объекты часто проще сложной синхронизации.

### Состояния потока
 - **NEW** — создан, но ещё не запущен;
 - **RUNNABLE** — выполняется или готов к исполнению; JVM отдельно не показывает состояние «работает на CPU»;
 - **BLOCKED** — ждёт захвата intrinsic-монитора;
 - **WAITING** — ждёт без таймаута (`wait`, `join`, `park`);
 - **TIMED_WAITING** — ждёт с таймаутом (`sleep`, timed `wait`/`join`/`park`);
 - **TERMINATED** — завершён.

Планировщик ОС/JVM и приоритеты не дают гарантий порядка или справедливости выполнения. `Thread.yield()` — лишь подсказка планировщику; на неё нельзя опираться для корректности.

Daemon-потоки не удерживают JVM от завершения: процесс может закончиться, когда остаются только демоны. Это не означает, что JVM корректно «прерывает» их или завершает их работу. Не используйте daemon для задач, которые обязаны завершить запись или очистку.

`i++` для общего `int` не является атомарной операцией: это чтение, вычисление и запись. Реальная видимость и переупорядочивание определяются JMM, а не упрощённой моделью «процессор читает и пишет память».

Double-checked locking допустим только при корректной публикации объекта, обычно с `volatile`-полем и синхронизированным созданием. Часто проще использовать инициализацию при загрузке класса или holder idiom.

- `synchronized` использует intrinsic-монитор объекта или класса. Монитор реентерабелен; выйти из него может только поток-владелец.
- `ReentrantLock` — явная блокировка с тем же принципом владения. Она добавляет `tryLock`, прерываемое ожидание, опциональную справедливость и условия; блокировку нужно освобождать в `finally`.
- **Semaphore** ограничивает число одновременных участников. Он не обязан быть бинарным и, в отличие от монитора/`Lock`, не привязан к потоку-владельцу.
- **Exchanger** позволяет двум потокам обменяться значениями в точке встречи.
- **Race condition** — результат зависит от порядка конкурентных операций. **Data race** по JMM — конфликтующие обращения к одной переменной из разных потоков без happens-before, где хотя бы одно обращение является записью.
- Deadlock — циклическое ожидание блокировок; помогает единый порядок захвата, уменьшение вложенных блокировок и диагностика thread dump. Timeout/`tryLock` могут предотвратить вечное ожидание, но не всегда восстанавливают корректное состояние.
- Livelock — потоки активны, но взаимно мешают прогрессу; starvation — поток долго не получает нужный ресурс/CPU.
- Классы `java.util.concurrent.atomic` предоставляют атомарные операции; многие опираются на CAS. Не следует утверждать, что любой атомарный алгоритм lock-free на любой платформе: это зависит от типа, реализации и операции.
- **ThreadLocal** хранит отдельное значение на поток и сам по себе не делает общие данные потокобезопасными. В пулах потоков очищайте значения (`remove()`), иначе контекст может утечь в следующую задачу. Для контекста, который должен переноситься между потоками, нужен отдельный механизм передачи.
- **CountDownLatch** позволяет одному или нескольким потокам ждать завершения заданного числа операций.
- **`volatile`** обеспечивает видимость записи и ограничения переупорядочивания для чтений/записей этого поля. Он не превращает составную операцию (`count++`, проверка-и-действие) в атомарную; для таких операций нужны атомики, блокировка или другой протокол синхронизации.

Как узнать что мы поймали `DeadLock`? Выгрузить `ThreadDump`. Там будет написан статус потоков, из которого мы сможем сделать вывод о блокировке.

**Когда использовать механизм?**
- **Volatile** — независимый флаг/ссылка с безопасной публикацией, когда не нужна атомарность нескольких действий.
- **Атомики** — атомарная операция над одной переменной; они не заменяют блокировку для инварианта из нескольких полей.
- **Синхронизация и блокировки** — критическая секция или согласованное изменение нескольких связанных значений.

#### Блокировки
- **Lock** Пакет `java.util.concurrent.locks` имеет интерфейс `Lock`. `ReentrantLock` предоставляет `tryLock()`, прерываемое ожидание и условия; всегда освобождайте его в `finally`.
- **ReadWriteLock** Пакет `java.util.concurrent.locks` также содержит интерфейс `ReadWriteLock` (и реализацию `ReentrantReadWriteLock`), который определяется парой блокировок для чтения и записи, обычно позволяя считывать одновременно нескольким читателям, но допуская только одного писателя.
- **CountDownLatch** — одноразовый барьер: `await()` ждёт, пока счётчик не станет нулём, `countDown()` уменьшает его. Для повторного использования обычно выбирают `CyclicBarrier` или `Phaser`.
- **CompletableFuture** является абстракцией для произведения асинхронных вычислений. В отличие от простого `Future`, где единственная возможность получить результат — блокировать, рекомендуется регистрировать обратные вызовы для создания конвейера задач, которые должны выполняться, когда доступен результат или исключение. Либо во время создания (через `CompletableFuture#supplyAsync/runAsync`), либо во время добавления обратных вызовов (методы семейства `*async`) может быть указан исполнитель, где должно выполняться вычисление (если он не указан стандартным глобальным `ForkJoinPool#commonPool`). Учтите, что если `CompletableFuture` уже завершен, обратные вызовы, зарегистрированные с помощью не `*async` методов, будут выполняться в вызывающем потоке. Если есть несколько `future`, вы можете использовать `CompletableFuture#allOf`, чтобы получить `future`, который будет завершен, когда все `future` будут завершены, или `CompletableFuture#anyOf`, который будет завершен, как только будет завершен какой-либо `future`.

#### CAS (compare-and-set)

CAS атомарно сравнивает текущее значение с ожидаемым и, если они совпадают, записывает новое. При конфликте цикл может повторить вычисление. Алгоритм должен учитывать ABA: значение могло измениться A→B→A, и простое сравнение этого не заметит; для версий используют, например, `AtomicStampedReference`.

#### Основные потокобезопасные коллекции

##### Списки
- ArrayList -> **CopyOnWriteArrayList**. Предоставляет семантику копирования при записи, где каждая модификация структуры данных приводит к новой внутренней копии данных (поэтому запись очень дорогая, тогда как чтение дешевое). Итераторы в структуре данных всегда видят снепшот данных с момента создания итератора.
- HashMap → **ConcurrentHashMap**. Обеспечивает потокобезопасные операции над отображением; детали реализации зависят от JDK. Составные сценарии «проверить, затем изменить» требуют атомарных методов (`compute`, `putIfAbsent`) или внешней синхронизации.

##### Множества
- TreeMap -> **ConcurrentSkipListMap** Обеспечивает параллельный доступ наряду функциональностью сортированного `Map`, подобной `TreeMap`. Границы производительности такие же как у `TreeMap`, хотя несколько потоков обычно могут читать и записывать из ассоциативного массива без конфликтов, если они не изменяют одну и ту же часть отображения.
- Set -> **CopyOnWriteArraySet** Подобно CopyOnWriteArrayList, он использует семантику copy-on-write для реализации интерфейса Set.
- Set -> **ConcurrentSkipListSet** Подобно ConcurrentSkipListMap, но реализует интерфейс Set.

##### Очереди
Очереди выступают в качестве труб между «производителями» и «потребителями». Элементы помещаются в один конец трубы и выходят из другого конца трубы в том же порядке «первый зашел, первый вышел» (FIFO). Интерфейс `BlockingQueue` расширяет `Queue`, чтобы предоставить дополнительные варианты того, как обрабатывать сценарий, где очередь может быть заполнена (когда производитель добавляет элемент) или пустой (когда потребитель читает или удаляет элемент). В этих случаях `BlockingQueue` предоставляет методы, которые либо блокируют навсегда, либо блокируют в течение определенного периода времени, ожидая изменения условия из-за действий другого потока.
- **ConcurrentLinkedQueue** Неограниченная неблокирующая очередь, поддерживаемая связанным списком.
- **LinkedBlockingQueue** Опционально ограниченная блокирующая очередь, поддерживаемая связанным списком.
- **PriorityBlockingQueue** Неограниченная блокирующая очередь, поддерживаемая минимальной кучей. Элементы удаляются из очереди в порядке, основанном на компараторе Comparator, связанном с очередью (вместо порядка FIFO).
- **DelayQueue** Неограниченная блокирующая очередь элементов, каждый из которых имеет значение задержки. Элементы могут быть удалены только тогда, когда их задержка прошла и удаляются в порядке старейшего истекшего элемента.
- **SynchronousQueue** Очередь о-длины, где производитель и потребитель блокируются до тех пор, пока не прибудет другой. Когда оба потока приходят, значение передается напрямую от производителя к потребителю. Полезно при передаче данных между потоками.


### Executors
Преимущества:
- Возможность переиспользовать уже созданные потоки
- Меньшие затраты по памяти
- Позволяют планировать и исполнять задачи

#### Что такое пул потоков?

Пул переиспользует worker-потоки и обычно принимает задачи через очередь. Важно настраивать не только число потоков, но и ёмкость очереди, таймауты, политику отклонения и метрики: неограниченная очередь может скрыть перегрузку и расти до исчерпания памяти.

Ключевые реализации
- `Executors.newSingleThreadExecutor()` выполняет задачи последовательно в одном worker-потоке.
- `Executors.newFixedThreadPool(n)` переиспользует `n` потоков, но стандартная очередь не ограничена; это не универсальный выбор для сервера.
- `ScheduledThreadPoolExecutor` планирует отложенные и периодические задачи.
- `Executors.newCachedThreadPool()` может создавать большое число потоков; без ограничения входной нагрузки опасен.
- `Executors.newVirtualThreadPerTaskExecutor()` (JDK 21+) запускает виртуальный поток на задачу, а не держит фиксированный пул. Виртуальные потоки облегчают масштабирование блокирующего I/O, но не увеличивают CPU и не отменяют лимиты БД/внешних сервисов.
- `Executors.newWorkStealingPool()` использует work-stealing, полезен для подходящих задач, разбиваемых на подзадачи.

Размер пула зависит от профиля нагрузки, целевых задержек и ограничений downstream-систем. `Runtime.getRuntime().availableProcessors()` даёт доступное JVM число процессоров; формулы вроде «CPU − 1» — только стартовая эвристика для CPU-bound задач, а не правило для I/O.

Реализации пула потоков
- **ThreadPoolExecutor** реализация по умолчанию с изменяющим размер пулом потока, одной рабочей очереди и настраиваемой политикой для отклоненных задач (через `RejectedExecutionHandler`) и создания потоков (через `ThreadFactory`).
- **ScheduledThreadPoolExecutor** расширение `ThreadPoolExecutor`, которое обеспечивает возможность планирования периодических задач.
- **ForkJoinPool** использует work-stealing и подходит для рекурсивно разделяемых CPU-bound задач. Блокирующий I/O может занять worker-потоки и снизить параллелизм; применяйте подходящий executor или явную поддержку блокировок.

Задачи отправляются с помощью `ExecutorService#submit`, `ExecutorService#invokeAll` или `ExecutorService#invokeAny`, которые имеют несколько перегрузок для разных типов задач.

### Fork-Join framework
- Реализация параллельной обработки для `ExecutorService`, использует принцип "разделяй и властвуй"
- Задачи должны быть независимы друг от друга (сумма элементов в массиве, поиск максимального элемента в массиве)
- Для того чтобы получить возвращаемое значение используем `RecursiveTask<T>` и переопределяем метод `compute()`
- Без возвращаемого значения используем `RecursiveAction`
- `Work-Stealing` - потоки "воруют" работу друг друга
- Создается фиксированный пул потоков (обычно - количество CPU)

### Поток, задача и исполнитель

`Runnable` описывает задачу без результата, `Callable<T>` — задачу с результатом/проверяемым исключением, `Thread` — поток выполнения. В прикладном коде обычно отделяют задачу от её исполнения и передают её в `ExecutorService`; прямое наследование от `Thread` редко необходимо.
