# Контейнеры и оркестрация

## Docker

Образ — неизменяемый шаблон файловой системы и метаданных; контейнер — запущенный из образа изолированный процесс. Контейнер не является виртуальной машиной и разделяет ядро хоста.

```bash
docker build -t nodeapp:latest .
docker run --rm -p 8080:80 nodeapp:latest
docker compose up
```

- `FROM` задаёт базовый образ (не обязательно образ ОС).
- `WORKDIR` задаёт рабочий каталог для последующих инструкций.
- `RUN` выполняется при сборке образа и создаёт слой.
- `EXPOSE` документирует порт контейнера, но сам по себе не публикует его на хосте.
- `CMD` задаёт команду по умолчанию при запуске; `ENTRYPOINT` задаёт основной исполняемый файл.
- `docker run -p hostPort:containerPort` публикует порт; без `-p` он не становится доступен через интерфейс хоста автоматически.
- `docker compose up` запускает описанные в Compose-файле сервисы; Compose обычно используют для локальной разработки и небольших окружений.

Для production важны минимальный базовый образ, non-root пользователь, health checks, лимиты ресурсов, сканирование образа и секреты вне image/layers.

### K8S

ПО для оркестрации контейнеризированных приложений

**Компоненты control plane:**

* **kube-apiserver** — API кластера; клиенты и компоненты обращаются к нему по Kubernetes API.
* **kube-controller-manager** — запускает контроллеры, которые сверяют желаемое и фактическое состояние ресурсов.
* **kube-scheduler** — назначает новые Pod на подходящие узлы с учётом ресурсов и ограничений.
* **etcd** — согласованное key-value-хранилище состояния control plane.
* **Cloud controller manager** — интеграция с облачной инфраструктурой, если она используется.

Control plane обычно состоит из нескольких компонентов/реплик для доступности; «единственный экземпляр» не является требованием Kubernetes. Объекты кластера хранятся в etcd, а не исполняются внутри него.

Deployment, Service, ConfigMap и Secret — объекты Kubernetes, которыми управляет API/control plane, а не отдельные встроенные «службы» etcd.

**Компоненты узла:**

* **WorkerNode** - контейнеризирует и запускает поды. Ниже - составляющие каждой ноды
    * **Pod** — минимальная развёртываемая единица Kubernetes; содержит один или несколько совместно размещённых контейнеров.
    * **kubelet** — агент узла, поддерживающий заданное состояние Pod.
    * **Container runtime** — запускает контейнеры через интерфейс CRI.
    * **kube-proxy** (если используется) реализует часть сетевой модели Service; в некоторых кластерах его функции заменяет CNI/eBPF-реализация.

**Дополнительные инструменты и службы**

* **NetworkPolicy** задаёт правила сетевого доступа, но их применение зависит от поддержки со стороны CNI-плагина.
* **Ingress** описывает правила HTTP(S)-маршрутизации, а Ingress Controller применяет их; без контроллера объект Ingress сам трафик не маршрутизирует. Для новых возможностей также существует Gateway API.
* **Service Discovery** обычно обеспечивается DNS и объектами Service; отдельный registry нужен не всегда.

**Объекты**

* **Namespace** - изолированная область в кластере
* **ServiceAccount** - техническая учетная запись
* **Pod** - минимальная величина в кубере, содержит один или несколько контейнеров
* **ReplicaSet** - следит за количеством под 
* **ConfigMap** - хранилище ключ-значение 
* **Secret** - объект для секретных конфигурационных данных. Base64-кодирование не является шифрованием; настройте encryption at rest, RBAC и безопасную доставку.
* **Service** даёт стабильную точку доступа к группе Pod. Типы: `ClusterIP` (внутренний адрес, по умолчанию), `NodePort` (порт на узлах), `LoadBalancer` (интеграция с внешним балансировщиком); headless Service (`clusterIP: None`) возвращает адреса Pod через DNS.
* **Ingress** — ресурс с правилами маршрутизации HTTP(S)-трафика; для их применения нужен Ingress Controller.
* **Job** - контроллер доводит число успешных завершений задачи до заданного; Pod может сохраниться после выполнения согласно политике очистки.
* **CronJob** - создаёт Job по расписанию; нужно учитывать возможные пропуски/повторы запусков и делать обработчик идемпотентным.
* **HorizontalPodAutoscaler** - регулирует кол-во под в зависимости от нагрузки
* **DaemonSet** - позволяет запустить поды на каждой ноде (логирование, журналирование)
* **StatefulSet** - управляет Pod со стабильной идентичностью и порядком/обновлением; постоянное хранение обычно обеспечивают отдельные PersistentVolumeClaim. Сам StatefulSet не делает данные приложения отказоустойчивыми.
* **LimitRange** - позволяет задавать дефолтные, минимальные и максимальные значения для параметров
* **ResourceQuota** - ограничивает совокупное потребление ресурсов/объектов в namespace.

### Probes, ресурсы и обновления

- **Readiness probe** определяет, готов ли контейнер принимать трафик; неготовый Pod исключается из endpoints Service, но не перезапускается только из-за этой проверки.
- **Liveness probe** определяет, нужно ли перезапустить контейнер. Слишком агрессивная проверка может вызвать цикл рестартов при временной перегрузке.
- **Startup probe** даёт медленно запускающемуся приложению время на старт и откладывает проверки liveness/readiness до успешного прохождения.
- **Requests** участвуют в планировании Pod и расчёте относительной нагрузки; **limits** ограничивают ресурсы контейнера. Превышение memory limit обычно приводит к `OOMKilled`, CPU limit — к throttling.
- **HPA** масштабирует число реплик по метрикам; для CPU utilization важны корректные CPU requests. Масштабирование не мгновенное и не заменяет лимиты нагрузки или autoscaling самих зависимостей.
- **Rolling update** постепенно заменяет Pod новой версией. Readiness checks помогают не направлять трафик в неготовые экземпляры; миграции приложения и схемы БД должны оставаться совместимыми во время перехода.
- Для JVM в контейнере учитывайте cgroup-лимиты: heap — лишь часть потребления памяти, рядом есть metaspace, стеки потоков, direct buffers и native memory. Не задавайте `-Xmx` равным всему memory limit контейнера.

### Вопросы на собеседовании

#### Чем `EXPOSE` отличается от `-p`?

`EXPOSE` — метаданные образа. `-p` настраивает публикацию порта контейнера через хост.

#### Чем Kubernetes Service отличается от Ingress?

Service даёт стабильную точку доступа к набору Pod и может иметь разные типы экспонирования. Ingress описывает HTTP(S)-маршруты; их применяет Ingress Controller.

#### Чем readiness probe отличается от liveness probe?

Readiness управляет тем, получает ли Pod трафик. Liveness решает, нужно ли перезапустить контейнер. Падение зависимости не всегда означает, что сам процесс нужно перезапускать; неудачная liveness-проверка может усугубить перегрузку.

#### Почему Kubernetes Secret не следует считать зашифрованным секрет-хранилищем?

Значение обычно лишь Base64-кодировано. Ограничьте RBAC, включите шифрование etcd at rest и используйте внешний secret manager, если требования того требуют.
