# SOLID и паттерны проектирования

**Назови проблему, которую решает паттерн, и укажи, какая часть кода меняется независимо от остальных.**

## SOLID

| Принцип | Смысл | Пример на интервью |
|---|---|---|
| SRP | У модуля одна причина изменяться | Расчёт цены и отправка уведомлений меняются по разным причинам |
| OCP | Добавляй варианты через стабильную точку расширения | Новый тариф реализует интерфейс стратегии |
| LSP | Подтип сохраняет контракт базового типа | Реализация коллекции сохраняет обещания интерфейса |
| ISP | Клиент зависит только от нужных операций | Раздели чтение каталога и управление каталогом |
| DIP | Политика приложения зависит от абстракции на её границе | Use case работает с интерфейсом репозитория, адаптер использует JDBC |

## Паттерны GoF

Все примеры запускаются через `main()`. В IDE открой `Main.java` по ссылке и запусти его.

### Порождающие паттерны

Отделяют создание объектов от кода, который ими пользуется.

| Паттерн | Когда применять и как работает пример |
|---|---|
| [Abstract Factory](../patterns/factory/abstractt/Main.java) | Клиенту нужно собрать объект из согласованного семейства деталей. `PhoneFabric` получает `PhonePartsFactory`, а фабрики Apple и Samsung предоставляют свои `Glass` и `Gpu`. Новое семейство добавляется отдельной фабрикой. Новый вид деталей потребует расширить общий интерфейс. |
| [Builder](../patterns/builder/Main.java) | У объекта есть обязательные и необязательные параметры. `Request.Builder` принимает путь, хранит значения по умолчанию и создаёт неизменяемый `Request`. В демо меняются таймаут и признак аутентификации. У короткого конструктора с очевидными аргументами меньше служебного кода. |
| [Factory Method](../patterns/factory/method/Main.java) | Последовательность заказа одинакова, а конкретная пицца зависит от магазина. `PizzaStore.orderPizza()` вызывает `createPizza()`, который переопределяют магазины Москвы и Лондона. Выбор продукта меняется через наследование. |
| [Prototype](../patterns/prototype/Main.java) | Новый объект удобно начать с настроенного образца. `Report.copy()` создаёт отчёт с независимым списком разделов. Добавление приложения к копии оставляет шаблон прежним. Политику копирования изменяемых вложенных объектов определяет прототип. |
| [Singleton](../patterns/singleton/Main.java) | Классу нужен один лениво создаваемый экземпляр в пределах загрузчика классов. `getInstance()` использует двойную проверку и `volatile` для безопасной публикации. Два вызова в демо возвращают одну ссылку. Глобальный доступ усложняет подмену зависимости в тестах. |

### Структурные паттерны

Определяют, как соединять объекты и классы.

| Паттерн | Когда применять и как работает пример |
|---|---|
| [Adapter](../patterns/adapter/Main.java) | Клиент ожидает `Duck`, а готовый объект реализует `Turkey`. `DuckAdapter` переводит `quack()` в `gobble()`, а `fly()` в `heightJump()`. Адаптеру важно сохранить обещания целевого интерфейса, включая смысл операций. |
| [Bridge](../patterns/bridge/Main.java) | Уведомления различаются по назначению и по каналу доставки. `Reminder` и `Alert` форматируют сообщения, а `Sender` доставляет их по email или SMS. Новые варианты добавляются независимо по каждой оси. В демо напоминание отправляется по обоим каналам. |
| [Composite](../patterns/composite/Main.java) | Клиенту нужна одна операция и для листа, и для группы. `FileEntry` возвращает свой размер, а `Folder` суммирует размеры вложенных `Entry`. В демо размер дерева с вложенной папкой равен 250. |
| [Decorator](../patterns/decorator/Main.java) | Добавки к напитку нужно комбинировать. `CondimentDecorator` оборачивает `Coffee`, а конкретные добавки дополняют стоимость и описание. Каждая обёртка сама реализует `Coffee`, поэтому может принять другую обёртку. В общем случае порядок обёрток влияет на результат. |
| [Facade](../patterns/facade/Main.java) | Для типового сценария приходится координировать несколько компонентов. `HomeCinema.watch()` запускает проектор, выставляет громкость и включает фильм. Детали порядка вызовов сосредоточены в фасаде, а у компонентов остаются собственные интерфейсы. |
| [Flyweight](../patterns/flyweight/Main.java) | У множества объектов повторяются одинаковые данные. `TreeStyles` выдаёт один неизменяемый `TreeStyle` для одного вида, а координаты хранятся в отдельных `Tree`. В демо два дерева с разными координатами ссылаются на один стиль. |
| [Proxy](../patterns/proxy/Main.java) | Дорогой объект нужен только при первом обращении. `LazyImage` реализует `Image`, создаёт `DiskImage` при первом `display()` и переиспользует его при втором. Загрузка в примере обозначена сообщением в консоли. Пример рассчитан на один поток. |

### Поведенческие паттерны

Распределяют алгоритмы и ответственность между объектами.

| Паттерн | Когда применять и как работает пример |
|---|---|
| [Chain of Responsibility](../patterns/chainofresponsibility/Main.java) | Заранее неизвестно, кто обработает запрос. Служба поддержки передаёт тикет по цепочке. Каждый обработчик принимает решение и при необходимости передаёт тикет дальше. Демо показывает обработку в начале и конце цепочки и случай без подходящего обработчика. |
| [Command](../patterns/command/Main.java) | Пульту нужно хранить действия и вызывать их позже. Каждая кнопка `DistantController` хранит `Command`, а ссылка на метод связывает команду с конкретным устройством. Пустые слоты используют `NoCommand`. Для отмены потребовались бы отдельная операция и данные для восстановления. |
| [Interpreter](../patterns/interpreter/Main.java) | Нужно вычислять выражения небольшого языка. `Add`, `Multiply`, `Variable` и `Number` образуют дерево и вычисляют его рекурсивно. Демо строит дерево `(x + 2) * 3` вручную и получает 18 при `x = 4`. С ростом грамматики растёт число типов узлов. |
| [Iterator](../patterns/iterator/Main.java) | Клиенту нужен единый способ обхода последовательности. `Range` реализует `Iterable<Integer>` и создаёт отдельный курсор для каждого обхода. Цикл `for-each` печатает числа от 2 до 4. После исчерпания `next()` бросает `NoSuchElementException`. |
| [Mediator](../patterns/mediator/Main.java) | Правила общения участников нужно сосредоточить в одном месте. `Participant` отправляет сообщение через `Mediator`, а `ChatRoom` доставляет его всем остальным участникам. Маршрутизацию можно поменять в комнате. При большом числе сценариев посредник может стать слишком сложным. |
| [Memento](../patterns/memento/Main.java) | Нужно восстановить предыдущее состояние объекта, сохранив его инкапсуляцию. `Editor` сохраняет и восстанавливает собственный `Snapshot`, а история хранит снимки в стеке. В демо отменяется дописывание текста. Размер истории влияет на расход памяти. |
| [Observer](../patterns/observer/Main.java) | Несколько экранов должны реагировать на обновление данных. `WeatherData` хранит подписчиков и вызывает `update()`, а экраны запрашивают актуальные данные. В демо уведомление запускается явно после каждого обновления. Вызовы синхронные, подписку можно снять через `removeObserver()`. |
| [State](../patterns/state/Main.java) | Одна кнопка должна действовать по-разному в зависимости от состояния плеера. `Player` делегирует нажатие текущему `PlaybackState`, который возвращает следующее состояние. Нажатия чередуют `Playing` и `Paused`. Правила переходов распределены по классам состояний. |
| [Strategy](../patterns/strategy/Main.java) | Объекту нужны взаимозаменяемые алгоритмы. `Duck` делегирует полёт и голос объектам `FlyBehaviour` и `QuackBehaviour`. Варианты можно комбинировать и менять независимо. Конфигурация клиента определяет, какую стратегию использовать. |
| [Template Method](../patterns/templatemethod/Main.java) | Порядок шагов алгоритма одинаков для нескольких вариантов. `ReportExporter.export()` фиксирует последовательность, а подклассы выбирают формат текста. В примере Factory Method метод `PizzaStore.orderPizza()` тоже задаёт шаблон, внутри которого один шаг создаёт продукт. |
| [Visitor](../patterns/visitor/Main.java) | К стабильному набору типов нужно добавлять операции. Фигуры вызывают подходящий `visit()` через `accept()`, а отдельные посетители вычисляют площадь и формируют описание. Для новой операции достаточно нового посетителя. Новый тип фигуры потребует обновить интерфейс и существующих посетителей. |

### Простая фабрика

[Simple Factory](../patterns/factory/simple/Main.java) сосредоточивает выбор реализации в одном месте. `PizzaFactory.getPizzaByCode()` выбирает пиццу по коду, а `PizzaStore` оформляет заказ. Чтобы добавить вид пиццы, нужно обновить фабрику. Этот приём дополняет каталог из 23 паттернов GoF.

### Как различать похожие паттерны

| Паттерны | Отличие по назначению |
|---|---|
| Adapter, Decorator, Proxy, Facade | Adapter переводит вызовы к другому интерфейсу. Decorator добавляет поведение через тот же интерфейс. Proxy управляет доступом к объекту. Facade предоставляет упрощённый интерфейс к подсистеме. |
| Simple Factory, Factory Method, Abstract Factory | Простая фабрика выбирает конкретный продукт в одном месте. Factory Method делегирует создание подклассу. Abstract Factory передаёт клиенту объект, создающий целое семейство продуктов. |
| Strategy, State, Template Method | Strategy подставляет алгоритм через композицию. State моделирует режимы работы и переходы. Template Method фиксирует порядок шагов и отдаёт отдельные шаги подклассам. |
| Observer, Mediator | Observer сообщает подписчикам об изменениях издателя. Mediator координирует взаимодействие участников. |

**Практика.** Добавь вариант полёта к Strategy и новую операцию к Visitor. Сравни, какие классы пришлось изменить, чтобы подключить новый вариант.

## 10. SOLID

`[ ]` **Короткий ответ:** пять принципов объектного дизайна, которые уменьшают связанность и стоимость изменений. Их применяют, когда это оправдано, а не механически: лишние абстракции тоже стоят денег.

| Принцип | Суть | Признак нарушения |
|---|---|---|
| **S** — Single Responsibility | У модуля одна причина для изменения | Класс `OrderService` и считает налоги, и шлёт письма, и формирует PDF |
| **O** — Open/Closed | Поведение расширяется без правки стабильного кода | Новый способ оплаты требует нового `case` в пяти `switch` |
| **L** — Liskov Substitution | Подтип выполняет контракт базового типа | `Square extends Rectangle`, и `setWidth` неожиданно меняет высоту |
| **I** — Interface Segregation | Клиент не зависит от ненужных методов | Реализация интерфейса бросает `UnsupportedOperationException` |
| **D** — Dependency Inversion | Политика и детали зависят от абстракций | Бизнес-логика создаёт `new PostgresOrderRepository()` |

<details>
<summary>Пример Dependency Inversion</summary>

```java
// Абстракция принадлежит бизнес-слою и описывает то, что нужно ему
interface OrderRepository {
    Optional<Order> findById(long id);
    void save(Order order);
}

// Бизнес-логика зависит только от абстракции
final class OrderService {
    private final OrderRepository orders;
    OrderService(OrderRepository orders) { this.orders = orders; }
}

// Деталь реализует абстракцию; направление зависимости в коде — к бизнес-слою
final class JdbcOrderRepository implements OrderRepository { /* ... */ }
```

Вызов идёт от `OrderService` к `JdbcOrderRepository`, а зависимость в исходном коде — наоборот. Это и есть «инверсия». Бонус — `OrderService` тестируется с фейковым репозиторием без БД.

</details>

<details>
<summary>Пример Liskov: почему квадрат не прямоугольник</summary>

Код, работающий с `Rectangle`, вправе ожидать: после `setWidth(5)` и `setHeight(4)` площадь равна 20. `Square` должен держать стороны равными, поэтому `setHeight(4)` меняет и ширину — площадь 16. Подстановка ломает ожидания клиента, хотя «квадрат является прямоугольником» в математике. Выход: неизменяемые фигуры или общий интерфейс `Shape` с методом `area()` без сеттеров.

</details>
