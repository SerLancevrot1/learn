## 1. Как проходить system design интервью

`[ ]` **Короткий ответ:** не рисовать архитектуру сразу. Порядок: требования → оценки нагрузки → API и модель данных → общая схема → углубление в одно-два узких места → отказы и компромиссы. Интервьюер оценивает, как вы обосновываете решения, а не количество квадратиков.

### 1.1. Шаги и время

| Шаг | Время из 45 минут | Что сказать |
|---|---|---|
| Функциональные требования | 3–5 мин | Что система делает. Что точно вне рамок. |
| Нефункциональные требования | 3–5 мин | RPS, задержка (p99), доступность, согласованность, объём данных, регионы |
| Оценки | 3–5 мин | Чтения и записи в секунду, объём за год, пропускная способность |
| API и модель данных | 5 мин | Основные эндпоинты, сущности, ключи доступа |
| Общая схема | 10 мин | Клиент → балансировщик → сервисы → хранилища, кеш, очередь |
| Углубление | 10–15 мин | Узкое место: горячий ключ, шардирование, консистентность, отказ |
| Итог | 2–3 мин | Что сделано, какие компромиссы, что улучшить дальше |

### 1.2. Оценки на салфетке

`[ ]` **Короткий ответ:** в сутках около 86 400 секунд, для оценок берут 10⁵. 1 млн запросов в сутки ≈ 12 RPS в среднем; пик обычно в 2–10 раз выше среднего.

<details>
<summary>Пример: сервис коротких ссылок</summary>

- 100 млн новых ссылок в месяц → ≈ 3,3 млн в сутки → ≈ 40 записей/с, в пике ~200/с.
- Чтений в 100 раз больше → ≈ 4 000/с, в пике ~20 000/с. Нагрузка преимущественно на чтение → кеш и реплики.
- Запись ≈ 500 байт × 100 млн × 12 мес. × 5 лет ≈ 3 ТБ. Помещается в один кластер, шардирование — не первая необходимость.
- Длина кода: 62 символа (`a-z`, `A-Z`, `0-9`), 62⁷ ≈ 3,5 × 10¹² — семи символов хватит с запасом.

Цифры не обязаны быть точными. Важно, что из них следует решение: «чтений в 100 раз больше — значит, кеш перед БД».

</details>

<details>
<summary>Порядки задержек, которые полезно помнить</summary>

| Операция | Порядок |
|---|---|
| Обращение к L1-кешу CPU | ~1 нс |
| Обращение к оперативной памяти | ~100 нс |
| Случайное чтение с NVMe SSD | десятки–сотни мкс |
| Круг внутри дата-центра | ~0,5 мс |
| Запрос к Redis в той же сети | < 1 мс |
| Простой запрос к БД по индексу | ~1–5 мс |
| Межконтинентальный круг | ~100–150 мс |

Вывод для интервью: сетевой вызов между сервисами дороже вызова метода на 4–5 порядков. Каждая новая граница сервиса — это задержка и новая точка отказа.

</details>

**Типичная ошибка:** сразу заявить «микросервисы, Kafka, Kubernetes» без требований. Хороший ответ начинается с вопроса «сколько пользователей, какая нагрузка на чтение и запись, что важнее — свежесть данных или доступность».

## 2. Масштабирование: рычаги

`[ ]` **Короткий ответ:** подход выбирают по измеренным узким местам и целям SLO, а не по целевой цифре пользователей. Основные рычаги: сделать приложение stateless и масштабировать горизонтально; кешировать подходящие данные с явным TTL и инвалидацией; отдавать статику через CDN; реплики — для чтения и доступности, шарды — для объёма и записи; асинхронная обработка через очереди; автоматизация развёртывания, мониторинга и восстановления.

### 2.1. Вертикальное и горизонтальное

| | Вертикальное (scale-up) | Горизонтальное (scale-out) |
|---|---|---|
| Что делаем | Больше CPU, памяти, диска на узле | Больше узлов |
| Плюсы | Просто, код не меняется | Почти без предела, отказоустойчивость |
| Минусы | Есть потолок, узел — единая точка отказа | Нужны stateless-узлы, балансировка, health checks, согласованность данных |
| Когда | Первый шаг, особенно для БД | Stateless-сервисы; БД — через реплики и шарды |

Несколько копий повышают доступность только при корректном failover и отсутствии общей точки отказа (одна БД, один балансировщик, одна зона доступности).

### 2.2. CDN

`[ ]` **Короткий ответ:** CDN — сеть точек присутствия, которые отдают закешированный контент ближе к клиенту. Обычно это статика, но можно кешировать и публичные HTTP-ответы. Важны ключ кеша, TTL и инвалидация, а не только «близость».

<details>
<summary>Подробности и подводные камни</summary>

- Ключ кеша: если в него попадают лишние параметры (`utm_*`, cookies), процент попаданий падает. Если не попадают нужные (язык, валюта) — пользователь видит чужой вариант.
- Персональные ответы кешировать нельзя. `Cache-Control: private` или `no-store` для них обязательны.
- Инвалидация: версионированные имена файлов (`app.3f9a.js`) с долгим TTL надёжнее ручной очистки.
- Географически ближайшая точка не обязательно самая быстрая и не обязательно содержит свежую копию.
- CDN снимает нагрузку с источника и защищает от части DDoS, но источник должен выдерживать промах кеша по всем точкам сразу (например, после очистки).

</details>

### 2.3. Несколько дата-центров

`[ ]` **Короткий ответ:** несколько ЦОД — это не «включить», а набор решений: как маршрутизировать и переключать трафик, кто принимает записи, какой допустим лаг репликации, какие RPO и RTO. Без регулярных учений по отказу региона второй ЦОД дорог и бесполезен.

<details>
<summary>Подробности</summary>

- **Маршрутизация и failover:** GeoDNS, глобальный балансировщик или anycast. У DNS есть TTL и кеширование у клиентов — переключение не мгновенное.
- **Данные:** один пишущий регион (single-writer) проще; несколько пишущих (multi-writer) требуют разрешения конфликтов. Асинхронная репликация может потерять последние подтверждённые записи при аварии; синхронная увеличивает задержку записи на межрегиональный круг.
- **RPO** (Recovery Point Objective) — сколько данных можно потерять. **RTO** (Recovery Time Objective) — за сколько нужно восстановиться.
- **Эксплуатация:** учения по отказу и обратному переключению, миграции схемы в двух регионах, бэкапы и проверка восстановления.

</details>

## 3. Репликация и шардирование

`[ ]` **Короткий ответ:** репликация копирует **одни и те же** данные на несколько узлов — для чтения и доступности. Шардирование делит данные на **разные** части по ключу — для объёма и записи. Это разные механизмы, их часто совмещают: каждый шард реплицируется.

### 3.1. Репликация

- Чтение можно распределить по репликам, если допустимы лаг и устаревшие данные. Запись обычно ограничена primary.
- Асинхронная репликация при failover может потерять последние изменения. Нужны мониторинг лага, выбор нового primary и защита от двух primary одновременно (split brain).
- **Реплика — не бэкап.** Ошибочный `DELETE` или повреждение данных реплицируется так же быстро, как полезная запись.

**Уточнение интервьюера:** «Пользователь сохранил профиль, обновил страницу и видит старые данные. Почему?» — чтение пошло на отстающую реплику. Решения: читать свои записи с primary некоторое время после изменения (read-your-writes), привязать сессию к primary, передавать позицию записи и ждать её на реплике.

### 3.2. Шардирование

`[ ]` **Короткий ответ:** все шарды имеют одну схему, но хранят разные строки. Главное решение — ключ шардирования: он определяет, какие запросы идут в один шард, а какие — во все сразу. Проблемы: решардинг, горячие шарды, межшардовые join и транзакции.

| Стратегия | Как | Плюсы | Минусы |
|---|---|---|---|
| По диапазону | `user_id 1–1M → шард 1` | Диапазонные запросы | Горячий «последний» шард при монотонных ключах |
| По хешу | `hash(key) % N` | Равномерно | Решардинг переносит почти все ключи |
| Consistent hashing | Кольцо хешей с виртуальными узлами | При добавлении узла переезжает ~1/N ключей | Сложнее, нужны vnodes для равномерности |
| По справочнику | Таблица «ключ → шард» | Гибко, можно переносить отдельных клиентов | Справочник сам должен быть доступен и быстр |

<details>
<summary>Три главные проблемы шардирования</summary>

**Решардинг.** Шард переполнился, или данные распределились неравномерно. Нужно изменить функцию распределения и перенести данные без простоя. Помогают consistent hashing и заранее созданные «логические» шарды (например, 1024 логических на 8 физических серверов: переносится логический шард целиком).

**Проблема знаменитостей (hot key).** Если данные нескольких очень популярных аккаунтов попали в один шард, он перегружен чтениями. Решения: кеш перед шардом, отдельный шард для таких ключей, разбиение ключа на под-ключи (`celebrity:42#0..#15`) с агрегацией при чтении.

**Join и транзакции.** Соединения и транзакции через несколько шардов дороги или невозможны. Решения: выбирать ключ так, чтобы связанные данные лежали вместе (все заказы клиента — в шарде клиента); денормализация; асинхронные проекции для отчётов.

</details>

### Лабораторная 1. Решардинг

`[ ]` Сравните, сколько ключей переезжает при переходе с 4 на 5 узлов для `hash % N` и consistent hashing.

<details>
<summary>Код (запуск: java Sharding.java)</summary>

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.*;

public class Sharding {
    static long hash(String s) {
        try {
            byte[] d = MessageDigest.getInstance("MD5").digest(s.getBytes(StandardCharsets.UTF_8));
            long h = 0;
            for (int i = 0; i < 8; i++) h = (h << 8) | (d[i] & 0xff);
            return h;
        } catch (Exception e) { throw new RuntimeException(e); }
    }

    static int modulo(String key, int shards) { return (int) Math.floorMod(hash(key), (long) shards); }

    static final class Ring {
        final TreeMap<Long, String> ring = new TreeMap<>();
        Ring(int nodes, int vnodes) {
            for (int n = 0; n < nodes; n++)
                for (int v = 0; v < vnodes; v++) ring.put(hash("node-" + n + "#" + v), "node-" + n);
        }
        String nodeFor(String key) {                       // первый узел по часовой стрелке
            var e = ring.ceilingEntry(hash(key));
            return (e != null ? e : ring.firstEntry()).getValue();
        }
    }

    public static void main(String[] args) {
        int keys = 100_000, movedMod = 0, movedRing = 0;
        Ring before = new Ring(4, 100), after = new Ring(5, 100);
        for (int i = 0; i < keys; i++) {
            String k = "user:" + i;
            if (modulo(k, 4) != modulo(k, 5)) movedMod++;
            if (!before.nodeFor(k).equals(after.nodeFor(k))) movedRing++;
        }
        System.out.printf("hash %% N: moved %.1f%%%n", 100.0 * movedMod / keys);
        System.out.printf("ring:     moved %.1f%%%n", 100.0 * movedRing / keys);
    }
}
```

</details>

<details>
<summary>Результат запуска</summary>

| Схема | Переехало ключей при 4 → 5 |
|---|---|
| `hash % N` | **80,1%** |
| Consistent hashing, 100 виртуальных узлов | **18,9%** (теоретически 1/5 = 20%) |

Распределение 100 000 ключей по 5 узлам:

| Виртуальных узлов на сервер | node-0 | node-1 | node-2 | node-3 | node-4 |
|---|---|---|---|---|---|
| 100 | 20 555 | 18 884 | 21 276 | 20 407 | 18 878 |
| 1 | 16 483 | 27 795 | 5 962 | 40 733 | 9 027 |

Вывод: consistent hashing уменьшает переезд с ~80% до ~1/N, но без виртуальных узлов распределение очень неравномерное — один узел получил 41% ключей, другой 6%.

</details>

## 4. Балансировка и состояние

`[ ]` **Короткий ответ:** чтобы масштабироваться горизонтально, экземпляр приложения не должен хранить в памяти состояние, нужное следующему запросу. Sticky sessions упрощают жизнь, но мешают масштабированию и failover: нагрузка распределяется неравномерно, а при падении узла его сессии теряются. Лучше хранить сессию во внешнем хранилище (Redis) или использовать подписанный токен.

<details>
<summary>Подробности: L4 и L7, алгоритмы, health checks</summary>

- **L4-балансировщик** распределяет TCP-соединения, не видит HTTP. Быстрый, но не умеет маршрутизировать по пути или заголовку.
- **L7-балансировщик** понимает HTTP: маршрутизация по пути, заголовкам, терминация TLS, ретраи.
- Алгоритмы: round robin, least connections, взвешенные, по хешу ключа (для локальности кеша).
- **Health checks** убирают больные узлы из ротации. Проверка должна отражать способность обслуживать запросы, но не тянуть за собой все зависимости — иначе сбой БД выведет из ротации все узлы сразу.
- При долгоживущих соединениях (gRPC, WebSocket) L4-балансировка по соединениям даёт перекос: новые узлы не получают нагрузку. Нужна балансировка по запросам на L7 или на клиенте.

</details>

**Уточнение интервьюера:** «А JWT вместо сессии — это бесплатно?» — нет. Токен нельзя мгновенно отозвать до истечения срока; нужны короткий срок жизни, refresh-токены и, при необходимости, список отозванных. См. Security.md.

## 5. Монолит, модульный монолит, микросервисы

`[ ]` **Короткий ответ:** это компромисс, а не шкала «старое → новое». Монолит проще разрабатывать, тестировать и эксплуатировать. Микросервисы дают независимые релизы, масштабирование и изоляцию отказов, но приносят сеть, распределённые данные и требования к DevOps и наблюдаемости. Частый разумный путь — модульный монолит с чёткими границами, из которого при необходимости выделяют сервисы.

### 5.1. Сравнение

| | Монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Развёртывание | Одно целиком | Одно целиком | Независимое для каждого сервиса |
| Вызовы между частями | Метод | Метод через публичный API модуля | Сеть: задержка, таймауты, отказы |
| Транзакции | Локальные ACID | Локальные ACID | Saga, outbox, eventual consistency |
| Масштабирование | Целиком | Целиком | По сервисам |
| Изоляция отказов | Слабая | Слабая | При правильной изоляции — сильная |
| Команды | Мешают друг другу на большом коде | Работают в своих модулях | Независимы |
| Инфраструктура | Минимальная | Минимальная | CI/CD, обнаружение сервисов, трассировка, мониторинг каждого |
| Технологии | Один стек | Один стек | Разные (и риск зоопарка технологий) |

<details>
<summary>Плюсы и минусы микросервисов подробнее</summary>

**Плюсы:**

- Независимое масштабирование нагруженных компонентов.
- Независимые релизы: обновление одного сервиса не требует развёртывания всей системы.
- Параллельная работа команд с меньшими конфликтами.
- Изоляция отказов: при правильной изоляции (таймауты, bulkhead, деградация) падение одного сервиса не роняет всё.
- Меньшая когнитивная нагрузка внутри одного сервиса.

**Минусы:**

- Сетевые накладные расходы: каждый вызов — задержка и потенциальный отказ.
- Распределённые данные: строгой согласованности (ACID) между сервисами нет, нужны Saga, outbox и идемпотентность.
- Сложная эксплуатация: версии, зависимости, контракты API, единые подходы к логированию и ошибкам.
- Требования к CI/CD, наблюдаемости (трассировка обязательна), дежурствам.
- Отладка и интеграционное тестирование сложнее.

</details>

<details>
<summary>Когда монолит — правильный выбор</summary>

- Небольшая или средняя команда, продукт ещё ищет свою модель предметной области.
- Нагрузка обслуживается несколькими экземплярами одного приложения за балансировщиком.
- Нет требования к независимым релизам разных частей.

Монолит тоже масштабируется горизонтально: несколько копий за балансировщиком. Проблемой становится не монолит, а **бесконтрольный монолит**: размытые границы, высокая связанность, отсутствие архитектурных правил.

**Минусы монолита:** нельзя масштабировать один перегруженный модуль; ошибка в одном модуле (утечка памяти) влияет на всё приложение; долгая сборка и развёртывание; смена технологий требует переписывания.

</details>

### 5.2. Модульный монолит

`[ ]` **Короткий ответ:** одно развёртываемое приложение, разделённое на модули с явными границами: модуль владеет своими данными и предоставляет другим только публичный API. Это даёт простоту монолита и дисциплину границ микросервисов, а также путь к выделению сервиса без переписывания.

<details>
<summary>Как обеспечить границы на практике</summary>

- Пакет `internal` или отдельные модули сборки (Maven/Gradle), чтобы другие модули физически не могли импортировать внутренности.
- Проверка зависимостей тестами архитектуры (ArchUnit, Spring Modulith).
- Свои таблицы или схема БД для каждого модуля; нет `JOIN` по таблицам чужого модуля.
- Взаимодействие через интерфейсы модуля или внутренние события.

</details>

### 5.3. Как выделять границы сервисов

`[ ]` **Короткий ответ:** начинают с бизнес-ответственности и владения данными (DDD, ограниченные контексты), затем проверяют по командам, частоте изменений и профилю нагрузки. Нельзя делить по техническим слоям: отдельные сервисы «контроллеры», «логика», «доступ к БД» дают распределённый монолит.

| Критерий | Вопрос |
|---|---|
| Бизнес-возможность (DDD) | Это самостоятельная функция бизнеса: каталог, оплата, доставка? |
| Владение данными | Кто единственный пишет в эти данные? |
| Команды (закон Конвея) | Может ли одна команда развивать и поддерживать это сама? |
| Частота и причины изменений | Это меняется независимо от остального? |
| Нагрузка | Профиль нагрузки сильно отличается? |
| Безопасность и регуляторика | Нужна особая изоляция (платёжные данные, персональные данные)? |

**Распределённый монолит** — микросервисы, которые нельзя развернуть по отдельности: общая БД, синхронные цепочки вызовов, обязательные одновременные релизы. Получаются все минусы обоих подходов.

**Типичная ошибка:** делить по существительным («сервис пользователей», «сервис заказов»), а не по сценариям. Если оформление заказа требует пяти синхронных вызовов по цепочке, доступность цепочки — произведение доступностей: \(0{,}999^5 \approx 0{,}995\).

---

## 6. CAP, PACELC и модели согласованности

### 6.1. CAP

`[ ]` **Короткий ответ:** CAP говорит о поведении **во время сетевого разделения**. Если узлы не могут связаться, система либо отклоняет часть запросов, чтобы не вернуть устаревшие или конфликтующие данные (сохраняет C), либо продолжает отвечать, допуская расхождение (сохраняет A). Без разделения выбирать «два из трёх» не нужно.

- **C** в CAP — линеаризуемость: чтение видит последнюю успешно завершённую запись.
- **A** — каждый запрос к работающему узлу получает ответ, а не ошибку или таймаут.
- **P** — способность работать при потере связи между узлами. В распределённой системе разделения неизбежны, поэтому P не «выбирают».

> Буква C в CAP и C в ACID — разные понятия. В ACID это соблюдение инвариантов и ограничений, в CAP — линеаризуемость.

<details>
<summary>Почему метки «CP» и «AP» вводят в заблуждение</summary>

Поведение зависит от операции, настроек и конкретного отказа. Одна и та же Cassandra с `QUORUM` ведёт себя иначе, чем с `ONE`. PostgreSQL с синхронной репликацией ведёт себя иначе, чем с асинхронной.

На интервью полезнее описать конкретный сценарий: какие запросы принимаются при потере кворума, можно ли читать устаревшую реплику, что произойдёт с подтверждёнными записями, как разрешаются конфликты после восстановления связи.

</details>

### 6.2. Модели согласованности

`[ ]` **Короткий ответ:** от сильной к слабой: линеаризуемость → причинная согласованность → согласованность в конечном счёте. Сильные гарантии требуют координации между узлами, а значит, задержки и меньшей доступности при отказах.

| Модель | Гарантия | Пример |
|---|---|---|
| Линеаризуемость | Операция выглядит атомарной в момент между вызовом и ответом; после завершения записи все её видят | Распределённая блокировка, лидер в etcd |
| Сериализуемость | Результат транзакций эквивалентен **какому-то** последовательному порядку | `SERIALIZABLE` в СУБД |
| Причинная (causal) | Причинно связанные изменения видны в правильном порядке; независимые — в любом | Ответ на комментарий не виден раньше самого комментария |
| Read-your-writes | Клиент видит свои записи | Профиль после сохранения |
| Монотонное чтение | Клиент не видит, как данные «откатываются» назад | Счётчик не уменьшается при обновлении страницы |
| В конечном счёте (eventual) | Если записи прекратятся, реплики сойдутся | DNS, кеши, проекции CQRS |

**Уточнение интервьюера:** «Чем линеаризуемость отличается от сериализуемости?»

<details>
<summary>Ответ</summary>

Сериализуемость — свойство транзакций из нескольких операций: результат эквивалентен некоторому последовательному порядку, но этот порядок может не совпадать с реальным временем. Линеаризуемость — свойство отдельных операций над одним объектом: порядок согласован с реальным временем. Сериализуемая система может вернуть устаревшее чтение, если это вписывается в допустимый порядок. Сочетание обоих свойств называют строгой сериализуемостью (strict serializability).

</details>

### 6.3. PACELC и кворумы

`[ ]` **Короткий ответ:** PACELC дополняет CAP: при разделении (P) — выбор между A и C, иначе (E) — между задержкой (L) и согласованностью (C). Например, чтение с ближайшей асинхронной реплики быстрее, но может вернуть устаревшие данные.

Кворум: `N` реплик, запись подтверждается `W` репликами, чтение опрашивает `R`. Если `R + W > N`, множества читающих и пишущих реплик пересекаются.

| N | R | W | R + W > N | Свойство |
|---|---|---|---|---|
| 3 | 1 | 1 | нет | Быстро, но можно прочитать старое |
| 3 | 2 | 2 | да | Сбалансированный кворум, выдерживает отказ 1 узла |
| 3 | 1 | 3 | да | Быстрое чтение, запись недоступна при отказе любого узла |
| 3 | 3 | 1 | да | Быстрая запись, чтение недоступно при отказе любого узла |

**Уточнение интервьюера:** «Значит, при `R + W > N` система линеаризуема?»

<details>
<summary>Ответ</summary>

Нет. Пересечение кворумов гарантирует, что чтение увидит хотя бы одну реплику с последней подтверждённой записью — при условии, что можно определить, какая версия новее. Линеаризуемость ломают конкурирующие записи с разрешением «последний по часам выигрывает» (часы расходятся), sloppy quorum и hinted handoff (запись приняли «чужие» узлы), частично выполненная запись (не набрала `W`, но осталась на части реплик), чтение без исправления реплик (read repair). Для линеаризуемости нужен консенсус (Raft, Paxos) или дополнительные механизмы.

</details>

### 6.4. Памятка: PACELC

`[ ]` **Короткий ответ:** PACELC (Дэниел Абади, 2010/2012) — «if **P** then **A** or **C**, **E**lse **L** or **C**». CAP описывает только редкий случай разделения сети, а PACELC добавляет компромисс, который есть **всегда**: как только данные реплицируются, приходится выбирать между быстрым ответом и согласованностью реплик.

**Формула в одну строку:**

```text
Разделение сети (P)?
├── да  → PA: отвечаем, допуская расхождение   | PC: отказываем части запросов
└── нет (E) → EL: подтверждаем сразу, реплицируем асинхронно | EC: ждём реплики (кворум/все), потом отвечаем
```

**Четыре класса:**

| Класс | При разделении | В норме | Примеры (по умолчанию) | Где уместно |
|---|---|---|---|---|
| PA/EL | Доступность | Низкая задержка, eventual | DynamoDB, Cassandra, Riak | Ленты, лайки, каталоги, кеши сессий, рекомендации |
| PC/EC | Согласованность | Согласованность, выше задержка | Spanner, HBase, CockroachDB, YugabyteDB | Деньги, остатки на складе, бронирование |
| PA/EC | Доступность | Согласованность | MongoDB (базовая конфигурация), Hazelcast | Обычно сильная согласованность, но failover важнее простоя |
| PC/EL | Согласованность | Низкая задержка | Yahoo PNUTS | Быстро в норме; при сбое — отключить операции, а не ухудшать гарантии |

**Что запомнить:**

- **CA-систем не бывает:** P не выбирают, а без разделения всё равно нельзя получить и нулевую задержку, и идеально согласованные реплики.
- **Eventual consistency — не только про аварии:** часто это сознательный выбор ради скорости при исправной сети.
- **Шкала, а не переключатель:** уровни `ONE` / `QUORUM` / `ALL` в Cassandra, 5 уровней в Cosmos DB (`Strong` ≈ PC/EC, `Session`/`Eventual` ≈ PA/EL), чтение со вторичных реплик в MongoDB двигают систему между EL и EC.
- **Классы смешиваются в одной системе:** каталог магазина — из кеша (EL), оплата и остатки — со строгой согласованностью (EC).
- **CAP → PACELC:** CP обычно становится PC/EC, AP — PA/EL.

<details>
<summary>Запись по шагам: PA, PC, EL, EC</summary>

| Режим | Что делает узел A при записи | Цена |
|---|---|---|
| PA | Реплика B недоступна → A принимает запись локально и отвечает `OK`; после восстановления связи — догоняющая репликация, read repair, anti-entropy, разрешение конфликтов (например, last write wins) | Расхождение данных, риск двойной продажи |
| PC | Реплика B не подтвердила → A возвращает ошибку или таймаут (или работает только кворум большинства, меньшинство ждёт) | Часть клиентов получает отказ |
| EL | Применяет локально → сразу отвечает → асинхронно отправляет в B | Чтение с B может вернуть старое |
| EC | Синхронно реплицирует в B (кворум или все) → ждёт подтверждения → отвечает | Задержка растёт на сетевой круг (межрегионально — десятки и сотни мс) |

</details>

<details>
<summary>Ограничения модели</summary>

- **Бинарность:** между строгой и eventual есть целый спектр (причинная, read-your-writes, монотонное чтение — см. [6.2](#62-модели-согласованности)).
- **Метки условны:** класс зависит от настроек и конкретной операции, как и с CP/AP в [6.1](#61-cap).
- **PA/EC и PC/EL запутывают:** PC у PNUTS не значит «абсолютная согласованность», а значит, что при сбое гарантии не опускаются ниже базовых (timeline consistency) — вместо этого отключается часть операций.
- **Модель молчит** о пропускной способности, стоимости координации, транзакциях и изоляции (ACID/BASE), механизмах консенсуса (Raft/Paxos).

</details>

**Уточнение интервьюера:** «Отнесите вашу систему к классу PACELC».

<details>
<summary>Как отвечать</summary>

Не называть одну метку на всю систему, а ответить на два вопроса для каждого типа данных: 1) что происходит с данными, если сеть разделится надвое — кто продолжает принимать записи и как потом сводятся конфликты; 2) на какие уступки в согласованности мы идём ради миллисекунд в обычном режиме. Пример: «Лента — PA/EL (Cassandra, `ONE`), платежи — PC/EC (PostgreSQL с синхронной репликацией или Spanner); для профиля пользователя достаточно read-your-writes».

</details>

### 6.5. Памятка: модели согласованности

`[ ]` **Короткий ответ:** модель согласованности — это гарантия того, в каком порядке и насколько свежими клиенты видят записи на разных репликах. Чем сильнее модель, тем больше координации между узлами, а значит, выше задержка и ниже доступность при разделении. Сильную модель включают точечно (деньги, блокировки), слабую — везде, где допустимо отставание.

**Шкала от сильной к слабой:**

```text
Строгая (линеаризуемость) → Последовательная → Причинная → Eventual
   реальное время           общий порядок      порядок только     только сходимость
   + общий порядок          без реального      для связанных      «когда-нибудь»
                            времени            событий
```

| Модель | Что гарантирует | Как достигается | Цена | Где применять |
|---|---|---|---|---|
| Строгая (linearizable) | Чтение видит последнюю завершённую запись; система ведёт себя как одна копия | Консенсус (Raft, Paxos), синхронная репликация, кворум большинства | Задержка на каждую запись, недоступность записи при разделении, ограниченная пропускная способность | Платежи, балансы, распределённые блокировки, выбор лидера, конфигурация кластера |
| Последовательная (sequential) | Все узлы видят операции в одном порядке; порядок каждого процесса сохранён; реальное время не учитывается | Глобальный порядок: секвенсор, рассылка с полным порядком (total order broadcast) | Возможны устаревшие чтения; секвенсор может стать узким местом | Многопользовательские игры, совместное редактирование |
| Причинная (causal) | Причина видна раньше следствия; параллельные операции — в любом порядке | Векторные часы, логические метки, отложенное применение до прихода зависимостей | Метаданные о зависимостях; конфликты параллельных записей решать самому | Мессенджеры, комментарии, вики, соцсети |
| Eventual | Если записи прекратятся, реплики сойдутся | Асинхронная репликация, gossip, разрешение конфликтов (LWW, слияние, CRDT) | Устаревшие и конфликтующие чтения; LWW теряет записи; трудно воспроизводимые баги | CDN и кеши, DNS, счётчики лайков и просмотров, связи между микросервисами |

**Сессионные (клиентские) гарантии** — надстройка над eventual: согласованность для одного клиента, а не для всех.

| Гарантия | Смысл | Пример |
|---|---|---|
| Read Your Writes | Клиент видит свои записи | Добавил товар — он сразу в корзине |
| Monotonic Reads | Чтения не «откатываются» назад | Баланс 100 не превращается обратно в 90 |
| Monotonic Writes | Записи клиента применяются в порядке отправки | Изменил, потом удалил — не наоборот |
| Writes Follow Reads | Запись применяется после того, что клиент уже прочитал | Комментарий не окажется раньше тех, на которые вы ответили |

Реализация: привязать сессию к реплике или передавать с запросом токен версии (например, LSN или session token в Cosmos DB), чтобы реплика ответила, только когда догонит эту версию. Второй способ лучше: он не создаёт проблем sticky sessions (см. [раздел 4](#4-балансировка-и-состояние)).

**Что запомнить:**

- **Последовательная ≠ строгая:** порядок общий, но может отставать от реального времени.
- **Причинная = eventual + зависимости:** почти так же быстро, но без эффекта «ответ раньше вопроса». Глобальные инварианты (например, «остаток ≥ 0») она не защищает.
- **BASE vs ACID:** Basically Available, Soft state, Eventual consistency — противоположность жёстких ACID-транзакций.
- **Микросервисы:** внутри сервиса — ACID в своей БД; между сервисами — eventual через события, Saga с компенсациями вместо 2PC (см. [8.3](#83-saga)), outbox/inbox для надёжной доставки, идемпотентные обработчики, периодические сверки.
- **Модели смешивают по доменам:** каталог и лента — eventual, корзина — сессионные гарантии, оплата и склад — строгая.

<details>
<summary>Пример: заказ в микросервисах</summary>

Сервисы Order, Inventory, Payment, Notification. Order сразу показывает пользователю «заказ создан» и публикует событие. Payment списывает деньги, Notification отправляет письмо — асинхронно, через секунды. Пользователь не ждёт и не получает ошибку, если Notification временно недоступен: событие обработается после восстановления. Важный инвариант «не уменьшать склад без оплаты» защищает сага: Inventory резервирует товар, а при отказе оплаты резерв снимается компенсирующим действием.

</details>

**Уточнение интервьюера:** «Пользователь сохранил профиль, обновил страницу и увидел старые данные. Что произошло и как исправить?»

<details>
<summary>Ответ</summary>

Запись ушла на лидера, а чтение — на асинхронную реплику, которая ещё не догнала: нарушен read-your-writes. Варианты: читать свои данные с лидера какое-то время после записи; передавать с запросом версию последней записи и ждать, пока реплика её догонит; использовать сессионный уровень согласованности СУБД. Делать всю систему линеаризуемой ради этого не нужно.

</details>

## 7. Паттерны устойчивости

`[ ]` **Короткий ответ:** в распределённой системе зависимость рано или поздно станет медленной или недоступной. Защита строится слоями: таймаут на каждый вызов → ограниченные ретраи с backoff и jitter только для идемпотентных операций → circuit breaker, чтобы не добивать больную зависимость → bulkhead, чтобы сбой не съел общие ресурсы → деградация (fallback) и ограничение входящей нагрузки.

### 7.1. Таймауты и дедлайны

- Без таймаута медленная зависимость занимает потоки и соединения, пока не кончится пул, — и падает уже вызывающий сервис. Так рождаются каскадные сбои.
- Таймаут ставят на подключение и на ответ. Значение выбирают от p99 зависимости и бюджета задержки запроса.
- **Дедлайн** передают по цепочке: если у клиента осталось 200 мс, нижний сервис не должен ждать 2 секунды.

### 7.2. Retry, backoff и jitter

`[ ]` **Короткий ответ:** повторять стоит только временные ошибки (таймаут, 503, 429) и только безопасные к повтору операции (идемпотентные или с ключом идемпотентности). Ограничить число попыток, задержку увеличивать экспоненциально и добавлять случайность (jitter). Без jitter все клиенты ретраят синхронно и добивают восстанавливающийся сервис.

```java
// Full jitter: случайная задержка в [0, min(cap, base * 2^attempt)]
static Duration backoff(int attempt, Duration base, Duration cap) {
    long exp = Math.min(cap.toMillis(), base.toMillis() * (1L << Math.min(attempt, 30)));
    return Duration.ofMillis(ThreadLocalRandom.current().nextLong(exp + 1));
}
```

<details>
<summary>Результат запуска (base = 100 мс, cap = 2 с, максимум из 10 000 выборок)</summary>

| Попытка | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| Максимальная задержка, мс | 100 | 200 | 400 | 800 | 1600 | 2000 (упёрлись в cap) |

`Math.min(attempt, 30)` защищает от переполнения сдвига: `1L << 63` уже отрицательное число.

</details>

<details>
<summary>Ретраи на нескольких уровнях</summary>

Если клиент, gateway и сервис делают по 3 попытки, нижняя зависимость получит до \(3 \times 3 \times 3 = 27\) запросов на один пользовательский. Ретраить нужно на одном уровне, обычно ближе к источнику ошибки, и ограничивать общий бюджет ретраев (например, не больше 10% от успешных запросов).

В Spring Framework 7 ретраи есть в ядре: `@Retryable` и `@ConcurrencyLimit` включаются через `@EnableResilientMethods`. По умолчанию — до 3 повторов после первой неудачи с задержкой 1 секунда ([Spring Framework: Resilience Features](https://docs.spring.io/spring-framework/reference/core/resilience.html)). См. Spring.md.

</details>

### 7.3. Circuit Breaker

`[ ]` **Короткий ответ:** автомат с тремя состояниями. CLOSED — запросы идут, ошибки считаются. После порога ошибок — OPEN: запросы сразу получают fallback, зависимость отдыхает. Через паузу — HALF_OPEN: пропускается пробный запрос; успех → CLOSED, ошибка → снова OPEN.

<details>
<summary>Минимальная реализация</summary>

```java
static final class CircuitBreaker {
    enum State { CLOSED, OPEN, HALF_OPEN }
    private final int failureThreshold;
    private final Duration openFor;
    private final Clock clock;                  // Clock — чтобы тестировать без sleep
    private State state = State.CLOSED;
    private int failures;
    private Instant openedAt;

    CircuitBreaker(int failureThreshold, Duration openFor, Clock clock) {
        this.failureThreshold = failureThreshold; this.openFor = openFor; this.clock = clock;
    }

    synchronized <T> T call(Supplier<T> action, Supplier<T> fallback) {
        if (state == State.OPEN) {
            if (Duration.between(openedAt, clock.instant()).compareTo(openFor) < 0)
                return fallback.get();          // быстрый отказ, зависимость не вызываем
            state = State.HALF_OPEN;            // пробный запрос
        }
        try {
            T result = action.get();
            state = State.CLOSED;
            failures = 0;
            return result;
        } catch (RuntimeException e) {
            if (state == State.HALF_OPEN || ++failures >= failureThreshold) {
                state = State.OPEN;
                openedAt = clock.instant();
            }
            return fallback.get();
        }
    }
}
```

Результат запуска с порогом 3 и паузой 10 с: после 5 неудачных вызовов состояние `OPEN`, реально зависимость вызвана **3 раза** — последние два запроса получили fallback без обращения к ней. Через 11 секунд пробный запрос успешен, состояние `CLOSED`.

`synchronized` на весь вызов здесь ради простоты: в реальной реализации действие выполняют вне блокировки. В продакшене используют Resilience4j: скользящее окно по количеству или времени, доля ошибок вместо подряд идущих, учёт медленных вызовов.

</details>

### 7.4. Bulkhead и ограничение нагрузки

- **Bulkhead** («переборки» на корабле) — отдельные пулы потоков, соединений или семафоры для разных зависимостей. Медленный сервис рекомендаций исчерпает свой пул, но не пул платежей.
- **Rate limiting** защищает от перегрузки на входе: лишние запросы получают `429`. Алгоритмы — в RedisAndCaching.md.
- **Load shedding** — при перегрузке отбрасывать часть запросов (низкоприоритетные) сразу, а не обслуживать все медленно.
- **Деградация** — вернуть упрощённый ответ: товары без персональных рекомендаций лучше, чем ошибка.

## 8. Паттерны данных и интеграции

### 8.1. Database per Service

`[ ]` **Короткий ответ:** каждый сервис владеет своими данными, другие получают их только через API или события. Это даёт независимость схемы и развёртывания, но запросы через несколько сервисов и согласованность становятся задачей архитектуры: API-композиция, проекции на событиях, Saga.

### 8.2. CQRS и Event Sourcing

`[ ]` **Короткий ответ:** CQRS разделяет модели записи (команды) и чтения (запросы). Полезен, когда у них очень разные требования: сложная валидация на записи и быстрые денормализованные выборки на чтении. Event Sourcing хранит не текущее состояние, а последовательность событий. Это независимые паттерны: CQRS не требует Event Sourcing.

<details>
<summary>Подробности и цена</summary>

**CQRS:** проекции для чтения обычно обновляются асинхронно → чтение отстаёт от записи (eventual consistency). Нужны мониторинг лага, перестроение проекций, объяснение пользователю, почему только что созданный объект ещё не виден.

**Event Sourcing:** полная история и аудит, можно восстановить состояние на любой момент, построить новые проекции задним числом. Цена: эволюция схемы событий (старые события живут вечно), снапшоты для быстрого восстановления, исправление ошибочных событий — через компенсирующие события, а не правкой истории. Это не механизм «отката».

</details>

### 8.3. Saga

`[ ]` **Короткий ответ:** Saga — последовательность локальных транзакций в разных сервисах. Если шаг не удался, выполняются **компенсирующие действия** для уже завершённых шагов. Это не rollback: списанные деньги возвращаются отдельной операцией «возврат», которая видна в истории и сама может не удаться.

| | Хореография | Оркестрация |
|---|---|---|
| Как | Сервисы реагируют на события друг друга | Оркестратор явно вызывает шаги и хранит состояние процесса |
| Плюсы | Нет центрального компонента, слабая связанность | Процесс виден в одном месте, проще отлаживать и менять |
| Минусы | Логику процесса трудно увидеть целиком, риск циклов | Оркестратор — дополнительный компонент |
| Когда | 2–3 шага | Много шагов, сложные ветвления |

<details>
<summary>Пример: оформление заказа</summary>

| Шаг | Действие | Компенсация |
|---|---|---|
| 1 | Создать заказ `PENDING` | Отменить заказ |
| 2 | Зарезервировать товар | Снять резерв |
| 3 | Списать деньги | Вернуть деньги |
| 4 | Подтвердить заказ | — (поворотная точка) |

Требования: каждый шаг и каждая компенсация идемпотентны (сообщения доставляются повторно); шаги публикуют события надёжно — через Transactional Outbox (см. MessageBrockers.md); промежуточные состояния видны другим (нет изоляции) — нужна семантическая блокировка вроде статуса `PENDING`. Если компенсация невозможна (письмо уже отправлено), шаг переносят после поворотной точки или предусматривают ручной разбор.

</details>

### 8.4. API Gateway и BFF

- **API Gateway** — единая точка входа: маршрутизация, аутентификация, rate limiting, TLS, наблюдаемость. Не должен быть единственным местом авторизации: сервисы сами проверяют права по проверенной идентичности. Gateway добавляет задержку и сам должен быть высокодоступен.
- **Backend for Frontend** — отдельный бэкенд под каждый тип клиента (веб, мобильный): агрегирует вызовы и отдаёт данные в удобной клиенту форме. Риск — дублирование логики между BFF.

### 8.5. Синхронное и асинхронное взаимодействие

| | Синхронно (REST, gRPC) | Асинхронно (очередь, события) |
|---|---|---|
| Связанность во времени | Оба сервиса должны работать | Получатель может быть недоступен |
| Ответ | Сразу | Позже или никогда (нужен отдельный канал) |
| Отказы | Каскадируют без таймаутов и breaker | Буферизуются в очереди |
| Сложность | Проще отлаживать | Дубликаты, порядок, DLQ, eventual consistency |
| Когда | Нужен ответ для пользователя прямо сейчас | Уведомления, интеграции, тяжёлая обработка |

**Smart endpoints, dumb pipes:** бизнес-логика — в сервисах, а брокер только доставляет сообщения. Логика маршрутизации в шине (как в классических ESB) создаёт скрытую связанность.

## 9. Паттерны развёртывания и миграции

### 9.1. Strangler Fig

`[ ]` **Короткий ответ:** постепенная замена старой системы. Перед монолитом ставится маршрутизатор; функции по одной переносятся в новый компонент, трафик переключается по маршрутам. Когда старый путь не получает трафика, его удаляют. Нужны совместимость данных, наблюдаемость и план отката для каждого шага.

### 9.2. Способы выкатки

| Способ | Как | Плюсы | Минусы |
|---|---|---|---|
| Rolling update | Экземпляры заменяются по одному | Без доп. ресурсов | Две версии одновременно — нужна совместимость |
| Blue-green | Две полные среды, переключение трафика | Мгновенный откат | Двойные ресурсы, миграции БД сложнее |
| Canary | Новая версия получает малую долю трафика | Риск ограничен, решение по метрикам | Нужны хорошие метрики и автоматизация |
| Shadow (dark launch) | Копия трафика идёт в новую версию, ответы отбрасываются | Проверка под реальной нагрузкой без риска | Побочные эффекты (запись, письма) нужно отключать |
| Feature flags | Код выкачен, функция включается флагом | Отделяет деплой от релиза | Долг: старые флаги нужно удалять |

**Уточнение интервьюера:** «Как выкатить изменение схемы БД без простоя?» — схема «расширить → мигрировать → сузить» (expand/contract): сначала добавить новую колонку, код пишет в обе, данные переносятся батчами, код переключается на чтение новой, и только потом старая удаляется. Каждый шаг совместим с предыдущей версией кода. См. DataBases.md.

### 9.3. Sidecar и контракты

- **Sidecar** — вспомогательный контейнер рядом с приложением: прокси service mesh (mTLS, ретраи, метрики), сборщик логов. В Kubernetes есть нативные sidecar-контейнеры — см. Devops.md.
- **Consumer-Driven Contracts** — потребители описывают, что они ожидают от API поставщика (Pact, Spring Cloud Contract). Поставщик проверяет эти контракты в своём CI и узнаёт о ломающем изменении до релиза.

## 10. SOLID

`[ ]` **Короткий ответ:** пять принципов объектного дизайна, которые уменьшают связанность и стоимость изменений. Их применяют, когда это оправдано, а не механически: лишние абстракции тоже стоят денег.

| Принцип | Суть | Признак нарушения |
|---|---|---|
| **S** — Single Responsibility | У модуля одна причина для изменения | Класс `OrderService` и считает налоги, и шлёт письма, и формирует PDF |
| **O** — Open/Closed | Поведение расширяется без правки стабильного кода | Новый способ оплаты требует нового `case` в пяти `switch` |
| **L** — Liskov Substitution | Подтип выполняет контракт базового типа | `Square extends Rectangle`, и `setWidth` неожиданно меняет высоту |
| **I** — Interface Segregation | Клиент не зависит от ненужных методов | Реализация интерфейса бросает `UnsupportedOperationException` |
| **D** — Dependency Inversion | Политика и детали зависят от абстракций | Бизнес-логика создаёт `new PostgresOrderRepository()` |

<details>
<summary>Пример Dependency Inversion</summary>

```java
// Абстракция принадлежит бизнес-слою и описывает то, что нужно ему
interface OrderRepository {
    Optional<Order> findById(long id);
    void save(Order order);
}

// Бизнес-логика зависит только от абстракции
final class OrderService {
    private final OrderRepository orders;
    OrderService(OrderRepository orders) { this.orders = orders; }
}

// Деталь реализует абстракцию; направление зависимости в коде — к бизнес-слою
final class JdbcOrderRepository implements OrderRepository { /* ... */ }
```

Вызов идёт от `OrderService` к `JdbcOrderRepository`, а зависимость в исходном коде — наоборот. Это и есть «инверсия». Бонус — `OrderService` тестируется с фейковым репозиторием без БД.

</details>

<details>
<summary>Пример Liskov: почему квадрат не прямоугольник</summary>

Код, работающий с `Rectangle`, вправе ожидать: после `setWidth(5)` и `setHeight(4)` площадь равна 20. `Square` должен держать стороны равными, поэтому `setHeight(4)` меняет и ширину — площадь 16. Подстановка ломает ожидания клиента, хотя «квадрат является прямоугольником» в математике. Выход: неизменяемые фигуры или общий интерфейс `Shape` с методом `area()` без сеттеров.

</details>

## 11. Пробное собеседование

Сценарии без единственного правильного ответа. Сначала проговорите решение вслух за 5–10 минут, потом сверьтесь.

<details>
<summary>1. Спроектируйте сервис коротких ссылок.</summary>

- **Требования:** создать короткую ссылку, перейти по ней (редирект), срок жизни, статистика переходов. Чтений в ~100 раз больше записей.
- **Оценки:** см. [1.2](#12-оценки-на-салфетке).
- **API:** `POST /links {url, ttl}` → `{code}`; `GET /{code}` → `301`/`302`.
- **Генерация кода:** счётчик + base62 (короткие коды, но предсказуемы — можно перебрать чужие ссылки), случайный код с проверкой уникальности через `UNIQUE`, заранее выделенные диапазоны счётчика для каждого экземпляра (без координации на каждую запись).
- **Хранение:** key-value или реляционная таблица `code → url`; ключ доступа один, шардирование по `code` при необходимости.
- **Чтение:** кеш `code → url` (Redis) с высоким процентом попаданий; CDN для популярных ссылок.
- **`301` или `302`:** `301` кешируется браузером — меньше нагрузки, но вы теряете статистику повторных переходов.
- **Статистика:** не писать в БД синхронно на каждый переход — событие в очередь, агрегация асинхронно.

</details>

<details>
<summary>2. Сервис выдерживает 1 000 RPS, через полгода ожидают 10 000. Ваш план?</summary>

1. Измерить, где узкое место сейчас: CPU приложения, пул соединений, БД, внешние зависимости. Нагрузочный тест.
2. Приложение — stateless и горизонтально масштабируемо? Сессии и файлы вынести наружу.
3. БД: индексы и медленные запросы, кеш для горячих чтений, реплики для чтения, пул соединений (PgBouncer).
4. Тяжёлые операции — асинхронно через очередь.
5. Шардирование — только если не хватает записи или объёма одного узла.
6. Наблюдаемость и автоскейлинг до роста, а не после.

</details>

<details>
<summary>3. Платёжный сервис иногда отвечает 30 секунд, и из-за него падает весь магазин. Что делать?</summary>

- Таймаут на вызов (например, 2 с) — потоки не будут висеть 30 секунд.
- Отдельный пул (bulkhead) для платёжного клиента, чтобы он не съел общий пул.
- Circuit breaker: при серии ошибок быстро отвечать «оплата временно недоступна».
- Ретраи — только с ключом идемпотентности, иначе возможно двойное списание.
- Асинхронная схема: заказ `PENDING_PAYMENT`, результат оплаты приходит событием или webhook.
- Метрики p99 и доли ошибок по зависимости, алерт.

</details>

<details>
<summary>4. Команда хочет разбить монолит на 15 микросервисов за квартал. Ваши вопросы?</summary>

- Какую проблему решаем: медленные релизы, конфликты команд, масштабирование одного модуля? Можно ли решить её модульностью внутри монолита?
- Есть ли CI/CD, трассировка, централизованные логи, дежурства для 15 сервисов?
- Где границы: по бизнес-возможностям и владению данным или по слоям?
- Как будут разделены данные? Общая БД после разделения — это распределённый монолит.
- Предложение: модульный монолит → выделить 1–2 сервиса с явной причиной (другой профиль нагрузки, независимая команда) по схеме Strangler → оценить → продолжать.

</details>

<details>
<summary>5. В системе с двумя регионами пропала связь между ними. Что произойдёт с данными?</summary>

Ответ зависит от модели записи — её и нужно назвать:

- **Single-writer, асинхронная репликация:** второй регион обслуживает чтения (устаревшие), записи отклоняются или идут в основной регион. Если основной регион недоступен и переключаемся — теряем записи, не успевшие реплицироваться (это RPO).
- **Single-writer, синхронная репликация:** записи блокируются, пока нет подтверждения второго региона — выбираем C, теряем A для записи.
- **Multi-writer:** оба региона принимают записи, после восстановления связи — разрешение конфликтов: «последний выигрывает» (теряет данные), CRDT, ручной разбор.
- Защита от split brain: только сторона с кворумом может быть лидером.

</details>

| **Circuit Breaker** | Не добивать больную зависимость, быстрый отказ | Настройка порогов, fallback |
| **Bulkhead** | Изолировать ресурсы разных зависимостей | Больше пулов, ниже утилизация |
| **Retry с backoff и jitter** | Пережить временные сбои | Дубликаты без идемпотентности, усиление перегрузки |
| **Timeout / Deadline** | Не ждать бесконечно | Нужно подобрать значение |
| **Rate Limiting** | Защита от перегрузки и злоупотреблений | Отказы легитимным клиентам при неверных лимитах |
| **Database per Service** | Независимость данных | Межсервисные запросы и согласованность |
| **Saga** | Бизнес-транзакция через несколько сервисов | Компенсации, нет изоляции |
| **Transactional Outbox** | Атомарно изменить БД и опубликовать событие | Ретранслятор, дубликаты на стороне получателя |
| **CQRS** | Разные модели чтения и записи | Eventual consistency проекций |
| **Event Sourcing** | История как источник истины | Эволюция событий, снапшоты |
| **Polyglot Persistence** | Разные хранилища под разные задачи | Больше технологий для эксплуатации |
| **Strangler Fig** | Постепенная миграция | Период двух систем |
| **Shadow Deployment** | Проверка на реальном трафике | Побочные эффекты нужно отключать |
| **Canary / Blue-green** | Безопасная выкатка | Метрики, ресурсы |
| **Sidecar** | Вынести инфраструктурные функции рядом с приложением | Ресурсы на каждый под, задержка прокси |

| **Smart Endpoints, Dumb Pipes** | Логика в сервисах, брокер только доставляет | — |
