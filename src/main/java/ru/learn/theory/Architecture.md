## 5. Монолит, модульный монолит, микросервисы

`[ ]` **Короткий ответ:** это компромисс, а не шкала «старое → новое». Монолит проще разрабатывать, тестировать и эксплуатировать. Микросервисы дают независимые релизы, масштабирование и изоляцию отказов, но приносят сеть, распределённые данные и требования к DevOps и наблюдаемости. Частый разумный путь — модульный монолит с чёткими границами, из которого при необходимости выделяют сервисы.

### 5.1. Сравнение

| | Монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Развёртывание | Одно целиком | Одно целиком | Независимое для каждого сервиса |
| Вызовы между частями | Метод | Метод через публичный API модуля | Сеть: задержка, таймауты, отказы |
| Транзакции | Локальные ACID | Локальные ACID | Saga, outbox, eventual consistency |
| Масштабирование | Целиком | Целиком | По сервисам |
| Изоляция отказов | Слабая | Слабая | При правильной изоляции — сильная |
| Команды | Мешают друг другу на большом коде | Работают в своих модулях | Независимы |
| Инфраструктура | Минимальная | Минимальная | CI/CD, обнаружение сервисов, трассировка, мониторинг каждого |
| Технологии | Один стек | Один стек | Разные (и риск зоопарка технологий) |

<details>
<summary>Плюсы и минусы микросервисов подробнее</summary>

**Плюсы:**

- Независимое масштабирование нагруженных компонентов.
- Независимые релизы: обновление одного сервиса не требует развёртывания всей системы.
- Параллельная работа команд с меньшими конфликтами.
- Изоляция отказов: при правильной изоляции (таймауты, bulkhead, деградация) падение одного сервиса не роняет всё.
- Меньшая когнитивная нагрузка внутри одного сервиса.

**Минусы:**

- Сетевые накладные расходы: каждый вызов — задержка и потенциальный отказ.
- Распределённые данные: строгой согласованности (ACID) между сервисами нет, нужны Saga, outbox и идемпотентность.
- Сложная эксплуатация: версии, зависимости, контракты API, единые подходы к логированию и ошибкам.
- Требования к CI/CD, наблюдаемости (трассировка обязательна), дежурствам.
- Отладка и интеграционное тестирование сложнее.

</details>

<details>
<summary>Когда монолит — правильный выбор</summary>

- Небольшая или средняя команда, продукт ещё ищет свою модель предметной области.
- Нагрузка обслуживается несколькими экземплярами одного приложения за балансировщиком.
- Нет требования к независимым релизам разных частей.

Монолит тоже масштабируется горизонтально: несколько копий за балансировщиком. Проблемой становится не монолит, а **бесконтрольный монолит**: размытые границы, высокая связанность, отсутствие архитектурных правил.

**Минусы монолита:** нельзя масштабировать один перегруженный модуль; ошибка в одном модуле (утечка памяти) влияет на всё приложение; долгая сборка и развёртывание; смена технологий требует переписывания.

</details>

### 5.2. Модульный монолит

`[ ]` **Короткий ответ:** одно развёртываемое приложение, разделённое на модули с явными границами: модуль владеет своими данными и предоставляет другим только публичный API. Это даёт простоту монолита и дисциплину границ микросервисов, а также путь к выделению сервиса без переписывания.

<details>
<summary>Как обеспечить границы на практике</summary>

- Пакет `internal` или отдельные модули сборки (Maven/Gradle), чтобы другие модули физически не могли импортировать внутренности.
- Проверка зависимостей тестами архитектуры (ArchUnit, Spring Modulith).
- Свои таблицы или схема БД для каждого модуля; нет `JOIN` по таблицам чужого модуля.
- Взаимодействие через интерфейсы модуля или внутренние события.

</details>

### 5.3. Как выделять границы сервисов

`[ ]` **Короткий ответ:** начинают с бизнес-ответственности и владения данными (DDD, ограниченные контексты), затем проверяют по командам, частоте изменений и профилю нагрузки. Нельзя делить по техническим слоям: отдельные сервисы «контроллеры», «логика», «доступ к БД» дают распределённый монолит.

| Критерий | Вопрос |
|---|---|
| Бизнес-возможность (DDD) | Это самостоятельная функция бизнеса: каталог, оплата, доставка? |
| Владение данными | Кто единственный пишет в эти данные? |
| Команды (закон Конвея) | Может ли одна команда развивать и поддерживать это сама? |
| Частота и причины изменений | Это меняется независимо от остального? |
| Нагрузка | Профиль нагрузки сильно отличается? |
| Безопасность и регуляторика | Нужна особая изоляция (платёжные данные, персональные данные)? |

**Распределённый монолит** — микросервисы, которые нельзя развернуть по отдельности: общая БД, синхронные цепочки вызовов, обязательные одновременные релизы. Получаются все минусы обоих подходов.

**Типичная ошибка:** делить по существительным («сервис пользователей», «сервис заказов»), а не по сценариям. Если оформление заказа требует пяти синхронных вызовов по цепочке, доступность цепочки — произведение доступностей: \(0{,}999^5 \approx 0{,}995\).

## 8. Паттерны данных и интеграции

### 8.1. Database per Service

`[ ]` **Короткий ответ:** каждый сервис владеет своими данными, другие получают их только через API или события. Это даёт независимость схемы и развёртывания, но запросы через несколько сервисов и согласованность становятся задачей архитектуры: API-композиция, проекции на событиях, Saga.

### 8.2. CQRS и Event Sourcing

`[ ]` **Короткий ответ:** CQRS разделяет модели записи (команды) и чтения (запросы). Полезен, когда у них очень разные требования: сложная валидация на записи и быстрые денормализованные выборки на чтении. Event Sourcing хранит не текущее состояние, а последовательность событий. Это независимые паттерны: CQRS не требует Event Sourcing.

<details>
<summary>Подробности и цена</summary>

**CQRS:** проекции для чтения обычно обновляются асинхронно → чтение отстаёт от записи (eventual consistency). Нужны мониторинг лага, перестроение проекций, объяснение пользователю, почему только что созданный объект ещё не виден.

**Event Sourcing:** полная история и аудит, можно восстановить состояние на любой момент, построить новые проекции задним числом. Цена: эволюция схемы событий (старые события живут вечно), снапшоты для быстрого восстановления, исправление ошибочных событий — через компенсирующие события, а не правкой истории. Это не механизм «отката».

</details>

### 8.3. Saga

`[ ]` **Короткий ответ:** Saga — последовательность локальных транзакций в разных сервисах. Если шаг не удался, выполняются **компенсирующие действия** для уже завершённых шагов. Это не rollback: списанные деньги возвращаются отдельной операцией «возврат», которая видна в истории и сама может не удаться.

| | Хореография | Оркестрация |
|---|---|---|
| Как | Сервисы реагируют на события друг друга | Оркестратор явно вызывает шаги и хранит состояние процесса |
| Плюсы | Нет центрального компонента, слабая связанность | Процесс виден в одном месте, проще отлаживать и менять |
| Минусы | Логику процесса трудно увидеть целиком, риск циклов | Оркестратор — дополнительный компонент |
| Когда | 2–3 шага | Много шагов, сложные ветвления |

<details>
<summary>Пример: оформление заказа</summary>

| Шаг | Действие | Компенсация |
|---|---|---|
| 1 | Создать заказ `PENDING` | Отменить заказ |
| 2 | Зарезервировать товар | Снять резерв |
| 3 | Списать деньги | Вернуть деньги |
| 4 | Подтвердить заказ | — (поворотная точка) |

Требования: каждый шаг и каждая компенсация идемпотентны (сообщения доставляются повторно); шаги публикуют события надёжно — через Transactional Outbox (см. MessageBrockers.md); промежуточные состояния видны другим (нет изоляции) — нужна семантическая блокировка вроде статуса `PENDING`. Если компенсация невозможна (письмо уже отправлено), шаг переносят после поворотной точки или предусматривают ручной разбор.

</details>

### 8.5. Синхронное и асинхронное взаимодействие

| | Синхронно (REST, gRPC) | Асинхронно (очередь, события) |
|---|---|---|
| Связанность во времени | Оба сервиса должны работать | Получатель может быть недоступен |
| Ответ | Сразу | Позже или никогда (нужен отдельный канал) |
| Отказы | Каскадируют без таймаутов и breaker | Буферизуются в очереди |
| Сложность | Проще отлаживать | Дубликаты, порядок, DLQ, eventual consistency |
| Когда | Нужен ответ для пользователя прямо сейчас | Уведомления, интеграции, тяжёлая обработка |

**Smart endpoints, dumb pipes:** бизнес-логика — в сервисах, а брокер только доставляет сообщения. Логика маршрутизации в шине (как в классических ESB) создаёт скрытую связанность.

## 9. Паттерны развёртывания и миграции

### 9.1. Strangler Fig

`[ ]` **Короткий ответ:** постепенная замена старой системы. Перед монолитом ставится маршрутизатор; функции по одной переносятся в новый компонент, трафик переключается по маршрутам. Когда старый путь не получает трафика, его удаляют. Нужны совместимость данных, наблюдаемость и план отката для каждого шага.

### 9.2. Способы выкатки

| Способ | Как | Плюсы | Минусы |
|---|---|---|---|
| Rolling update | Экземпляры заменяются по одному | Без доп. ресурсов | Две версии одновременно — нужна совместимость |
| Blue-green | Две полные среды, переключение трафика | Мгновенный откат | Двойные ресурсы, миграции БД сложнее |
| Canary | Новая версия получает малую долю трафика | Риск ограничен, решение по метрикам | Нужны хорошие метрики и автоматизация |
| Shadow (dark launch) | Копия трафика идёт в новую версию, ответы отбрасываются | Проверка под реальной нагрузкой без риска | Побочные эффекты (запись, письма) нужно отключать |
| Feature flags | Код выкачен, функция включается флагом | Отделяет деплой от релиза | Долг: старые флаги нужно удалять |

**Уточнение интервьюера:** «Как выкатить изменение схемы БД без простоя?» — схема «расширить → мигрировать → сузить» (expand/contract): сначала добавить новую колонку, код пишет в обе, данные переносятся батчами, код переключается на чтение новой, и только потом старая удаляется. Каждый шаг совместим с предыдущей версией кода. См. DataBases.md.

### 9.3. Sidecar и контракты

- **Sidecar** — вспомогательный контейнер рядом с приложением: прокси service mesh (mTLS, ретраи, метрики), сборщик логов. В Kubernetes есть нативные sidecar-контейнеры — см. Devops.md.
- **Consumer-Driven Contracts** — потребители описывают, что они ожидают от API поставщика (Pact, Spring Cloud Contract). Поставщик проверяет эти контракты в своём CI и узнаёт о ломающем изменении до релиза.

## Приложение: справочник паттернов

| Паттерн | Задача | Цена |
|---|---|---|
| **API Gateway** | Единая точка входа: маршрутизация, аутентификация, rate limiting | Задержка, точка отказа, риск «толстого» шлюза |
| **BFF** | API под конкретного клиента | Дублирование логики |
| **Service Discovery** | Найти живые экземпляры сервиса | Реестр или DNS; в Kubernetes — встроенный `Service` |
| **Circuit Breaker** | Не добивать больную зависимость, быстрый отказ | Настройка порогов, fallback |
| **Bulkhead** | Изолировать ресурсы разных зависимостей | Больше пулов, ниже утилизация |
| **Backpressure** | Согласовать скорость продюсера и потребителя, не переполнить буферы | Задержка, сложность протокола, подбор размера буферов |
| **Retry с backoff и jitter** | Пережить временные сбои | Дубликаты без идемпотентности, усиление перегрузки |
| **Timeout / Deadline** | Не ждать бесконечно | Нужно подобрать значение |
| **Rate Limiting** | Защита от перегрузки и злоупотреблений | Отказы легитимным клиентам при неверных лимитах |
| **Database per Service** | Независимость данных | Межсервисные запросы и согласованность |
| **Saga** | Бизнес-транзакция через несколько сервисов | Компенсации, нет изоляции |
| **Transactional Outbox** | Атомарно изменить БД и опубликовать событие | Ретранслятор, дубликаты на стороне получателя |
| **CQRS** | Разные модели чтения и записи | Eventual consistency проекций |
| **Event Sourcing** | История как источник истины | Эволюция событий, снапшоты |
| **Polyglot Persistence** | Разные хранилища под разные задачи | Больше технологий для эксплуатации |
| **Strangler Fig** | Постепенная миграция | Период двух систем |
| **Shadow Deployment** | Проверка на реальном трафике | Побочные эффекты нужно отключать |
| **Canary / Blue-green** | Безопасная выкатка | Метрики, ресурсы |
| **Sidecar** | Вынести инфраструктурные функции рядом с приложением | Ресурсы на каждый под, задержка прокси |
| **Consumer-Driven Contracts** | Ловить ломающие изменения API до релиза | Поддержка контрактов |
| **Smart Endpoints, Dumb Pipes** | Логика в сервисах, брокер только доставляет | — |
| **Stateless Services** | Горизонтальное масштабирование | Состояние во внешнем хранилище, которое само должно быть надёжным |
