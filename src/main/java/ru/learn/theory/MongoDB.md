## 1. Документная модель

`[ ]` **Короткий ответ.** MongoDB хранит типизированные BSON-документы. Вкладывай данные, которые читаются и меняются вместе и имеют предсказуемый размер. Выноси в отдельную коллекцию данные с собственным жизненным циклом, общие для многих агрегатов или растущие без естественной границы.

<details>
<summary>Подробности и компромиссы</summary>

- В заказе удобно хранить позиции, количество и цену покупки. При изменении цены товара история сохраняется. Остаток SKU общий для всех заказов и обновляется независимо.
- Встроенный массив комментариев подходит при известном ограничении числа элементов. При неограниченном росте отдельная коллекция с индексом по владельцу упрощает постраничное чтение. Лимит одного BSON-документа — 16 MiB.
- Гибкая схема допускает разные формы документа в одной коллекции. Для значимых типов и обязательных полей можно установить валидатор. При раскатке сначала обеспечь чтение старой и новой формы, затем обнови писателей и при необходимости выполни backfill.
- Определи типы идентификаторов и сумм. Строка и `ObjectId` с похожим представлением — разные BSON-значения. Деньги удобно хранить целым числом минимальных единиц или Decimal128, если бизнес требует десятичной шкалы.

</details>

**Уточнение.** Почему бы всегда не копировать имя и адрес клиента в заказ? Исторический адрес доставки может принадлежать заказу, а актуальные контактные данные — профилю. Для каждой копии назови источник истины и правила обновления. [Моделирование данных](https://www.mongodb.com/docs/manual/data-modeling/) · [Ограничения MongoDB](https://www.mongodb.com/docs/manual/reference/limits/)

## 2. Запросы и агрегация

`[ ]` **Короткий ответ.** `find` подходит для фильтра, проекции и сортировки. Aggregation pipeline преобразует данные по этапам. В отчёте по заказам сначала сузь вход через `$match`, затем разверни позиции через `$unwind` и агрегируй через `$group`.

<details>
<summary>Подробности и типичные ошибки</summary>

- `{status: null}` совпадает и с явным `null`, и с отсутствующим полем. Для различения используй `$type` или `$exists` в зависимости от условия.
- Чтобы оба условия относились к одной позиции, используй `{lines: {$elemMatch: {sku: "tea", quantity: {$gte: 2}}}}`. Два отдельных условия по `lines.sku` и `lines.quantity` могут найти разные элементы одного массива.
- `$unwind` меняет гранулярность с заказа на позицию. После него `$sum: 1` посчитает позиции. Для выручки суммируй произведение количества на историческую цену. Для числа заказов выбери отдельную агрегацию или группируй по ID заказа.
- `$sort`, `$group` и `$lookup` могут стать дорогими при большом входе. Смотри селективность начального фильтра, объём промежуточных данных и индекс на стороне присоединения.

</details>

**Практика.** Добавь заказ с двумя позициями и посчитай выручку по SKU, число заказов и число позиций. Покажи, на каком этапе эти три величины расходятся. [Агрегация в OrderCatalog](../mongo/OrderCatalog.java) · [Aggregation Pipeline](https://www.mongodb.com/docs/manual/core/aggregation-pipeline/)

## 3. Индексы и план запроса

`[ ]` **Короткий ответ.** Для истории клиента с сортировкой по времени подойдёт индекс `{customerId: 1, createdAt: -1, _id: -1}`. Поле клиента ограничивает диапазон ключей, следующие поля поддерживают порядок. Через `explain("executionStats")` сравни число просмотренных ключей и документов с числом возвращённых записей. [Правило ESR](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/)

<details>
<summary>Подробности и диагностика</summary>

| Наблюдение | Что проверить |
|---|---|
| `COLLSCAN` | Нужен ли индекс для этого запроса и достаточно ли селективен фильтр |
| `IXSCAN`, но много `totalKeysExamined` | Как индекс ограничивает диапазон и какие условия применяются позже |
| `FETCH`, большой `totalDocsExamined` | Какие поля фильтра или результата требуют чтения документа |
| Отдельный `SORT` | Соответствует ли порядок полей индекса фильтру и сортировке |

ESR — ориентир. Сначала равенства, затем сортировка и диапазон, если важно убрать отдельную сортировку. Очень селективный диапазон может быть выгоднее перед сортировкой. Сравни оба варианта на типичных запросах и объёме. Индекс по массиву становится multikey, поэтому один документ может породить несколько ключей. Каждый индекс добавляет работу при записи. [Multikey-индексы](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-multikey/)

Для глубокой пагинации используй keyset с полным порядком. При сортировке `createdAt DESC, _id DESC` после курсора идут записи с меньшим временем или с тем же временем и меньшим ID. Keyset ограничивает диапазон чтения, а данные между страницами всё ещё могут измениться.

</details>

**Практика.** Сравни планы из теста, затем мысленно убери `_id` из курсора и объясни пропуск при одинаковом времени. [Лабораторная по индексам](../mongo/README.md#1-от-запроса-к-модели-и-индексу)

## 4. Атомарность, транзакции и повторы

`[ ]` **Короткий ответ.** MongoDB атомарно обновляет один документ. Для остатка используй условие `available >= quantity` и `$inc` в одной операции. Если один инвариант связывает заказ и несколько остатков, используй транзакцию и передавай одну `ClientSession` во все её операции. [Атомарность операций](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/) · [Транзакции](https://www.mongodb.com/docs/manual/core/transactions/)

<details>
<summary>Подробности и два разных повтора</summary>

- Если условное обновление изменило ноль документов, не объявляй операцию успешной. Для optimistic locking можно включить в фильтр ожидаемую версию и увеличить её при записи.
- При `TransientTransactionError` удобный API драйвера может заново выполнить тело транзакции. При `UnknownTransactionCommitResult` нужно выяснить итог фиксации, обычно повтором commit по правилам драйвера. Таймаут ответа сам по себе не доказывает rollback.
- Повтор бизнес-запроса решается отдельно. Стабильный ID заказа позволяет найти зафиксированную запись, сопоставить её с запросом и вернуть результат без второго списания. Повтор того же ID с другой корзиной — конфликт.
- Держи транзакцию короткой. Письмо или HTTP-запрос внутри callback может выполниться повторно или пережить откат БД. Если нужен надёжный внешний эффект, запиши событие в outbox в той же транзакции и доставь его отдельно.

</details>

**Практика.** После первого успешного `$inc` доведи второй до ошибки. Проверь остатки и наличие заказа снаружи транзакции. Затем отправь одинаковый ID конкурентно. [InventoryCheckout](../mongo/InventoryCheckout.java) · [Outbox и CDC](MessageBrockers.md#9-outbox-и-cdc)

## 5. Репликация и согласованность

`[ ]` **Короткий ответ.** В replica set primary принимает записи, secondary применяют изменения из oplog. После потери primary участники могут выбрать новый, если есть нужное большинство голосов. Во время выборов возможна пауза в записях. Приложение должно учитывать задержку репликации и неизвестный исход запроса.

| Настройка | Вопрос, на который она отвечает | Пример |
|---|---|---|
| Read preference | На какой узел направить чтение? | Чтение с secondary может отставать |
| Read concern | Какие версии данных допустимо увидеть? | `local` может видеть данные до majority commit. `majority` ограничивает чтение подтверждёнными большинством данными |
| Write concern | Какого подтверждения записи ждёт клиент? | `w: "majority"` ждёт подтверждения по правилам большинства replica set |

<details>
<summary>Уточнения о свежести и failover</summary>

`readConcern: "majority"` сам по себе не обещает чтение самой свежей записи с любой реплики. Для read-your-writes при смене узла разберись в причинно согласованной сессии и требованиях к read/write concern. `snapshot` задаёт чтение из согласованного снимка, например в транзакции. Если запись с `w: 1` подтверждена только старым primary и не успела реплицироваться, после failover возможен rollback. При таймауте подтверждения запись могла примениться. [Изоляция, согласованность и свежесть](https://www.mongodb.com/docs/manual/core/read-isolation-consistency-recency/) · [Write Concern](https://www.mongodb.com/docs/manual/reference/write-concern/)

</details>

**Граница практикума.** Один узел в режиме replica set поддерживает транзакции и Change Streams. Для эксперимента с выборами и отстающей secondary нужен многоузловой стенд. [Распределённые данные](system/design/DistributedData.md)

## 6. Шардирование

`[ ]` **Короткий ответ.** Репликация поддерживает копии данных, шардирование делит данные между группами узлов. `mongos` маршрутизирует запрос по shard key. Без достаточного фильтра по ключу запрос может обратиться к нескольким или всем шардам, даже если на каждом есть локальный индекс. [Выбор shard key](https://www.mongodb.com/docs/manual/core/sharding-choose-a-shard-key/)

<details>
<summary>Как обсуждать выбор ключа</summary>

- Оцени кардинальность, частоту популярных значений и характер роста ключа. Монотонное время как ведущий ключ диапазонного распределения может направлять свежие записи в один диапазон.
- Диапазонное распределение удобно, когда запросы читают соседние диапазоны. Хеширование помогает разнести монотонные записи, но запрос по диапазону исходных значений обычно теряет локальность.
- Для истории клиента ключ по клиенту помогает целевым запросам. Один очень крупный клиент меняет картину нагрузки. Назови, какие чтения должны быть целевыми и где появятся горячие ключи или межшардовые транзакции.

</details>

## 7. Change Streams и CDC

`[ ]` **Короткий ответ.** Change Stream даёт поток изменений MongoDB. Resume token фиксирует позицию для восстановления. Сохраняй позицию после надёжного результата в приёмнике. Падение между результатом и сохранением позиции даёт повтор, поэтому в приёмнике нужен устойчивый идентификатор или идемпотентный merge. [Change Streams](https://www.mongodb.com/docs/manual/changeStreams/)

<details>
<summary>Уточнения о восстановлении и контракте</summary>

- Если нужная история oplog уже недоступна, нужен контролируемый backfill и новая позиция. При совмещении начального снимка и потока нужен согласованный рубеж, чтобы не потерять изменения между ними.
- Изменение документа описывает действие над хранилищем. Если потребителям важно доменное событие с устойчивым контрактом, модель outbox позволяет записать его явно вместе с изменением.
- Наблюдай отставание потока, возраст checkpoint и число повторов. Длительный простой опасен, если окно oplog меньше времени восстановления.

</details>

**Практика.** Сохрани токен первого заказа, закрой курсор, вставь второй и возобнови подписку. Затем объясни, что изменится, если получатель упадёт до записи токена. [Тест восстановления](../../../../../test/java/ru/learn/mongo/MongoLabIntegrationTest.java)

## 8. Эксплуатация и диагностика

`[ ]` **Короткий ответ.** При высоком p99 сначала отдели ожидание соединения и сети от работы MongoDB. Затем найди форму запроса, сравни план на характерных параметрах и проверь метрики primary и secondary. `MongoClient` обычно живёт долго и переиспользует пул соединений.

| Симптом | С чего начать |
|---|---|
| Запрос медленный только для крупных клиентов | Сравнить `nReturned`, просмотренные ключи и документы, наличие `SORT` |
| После записи с secondary видна старая версия | Проверить read preference, replication lag и требования к свежести |
| После переключения primary растут ошибки | Проверить время выборов, server selection, дедлайны и безопасные повторы |
| При росте нагрузки появилось ожидание пула | Проверить время удержания соединений, медленные операции и ограничения параллелизма |
| TTL-документ всё ещё читается после времени истечения | TTL-удаление работает в фоне. Для строгой бизнес-проверки учитывай `expiresAt` в запросе |

Перед эксплуатацией определи RPO/RTO, проверь восстановление из резервной копии и права доступа. Репликация помогает при сбое узла, но ошибочная запись или удаление тоже могут реплицироваться. [TTL-индексы](https://www.mongodb.com/docs/manual/core/index-ttl/) · [Надёжность](system/design/Reliability.md)
