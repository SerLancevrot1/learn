# Observability для собеседования: Prometheus, Grafana, Loki, Tempo, Alloy

> **Источник:** видео «Основы observability распределенных систем (Prometheus, Grafana, Alloy, Loki, Tempo)»  
> **Ключевая идея:** observability — это возможность понять внутреннее состояние системы по её внешним сигналам (метрикам, логам, трейсам), а не просто «смотреть на дашборды».

---

## 1. Observability vs Monitoring

| | Monitoring | Observability |
|---|---|---|
| **Вопрос** | «Работает ли система?» | «Почему она работает именно так?» |
| **Данные** | Заранее известные метрики | Любые сигналы, включая неизвестные заранее |
| **Подход** | Реактивный: алерт сработал → пошли смотреть | Исследовательский: можно задать новый вопрос без изменения инструментов |

**Тезис для собеседования:**  
Monitoring отвечает на вопросы, которые вы предусмотрели. Observability позволяет отвечать на вопросы, которые вы не предусмотрели[reference:0].

## 2. MELT: четыре столпа observability

**MELT** = **M**etrics, **E**vents, **L**ogs, **T**races.

| Столп | Что это | Примеры | Сильная сторона |
|---|---|---|---|
| **Metrics** | Числовые измерения во времени | CPU, RPS, latency, error rate | Агрегация, алертинг, тренды |
| **Events** | Дискретные факты | Деплой, логин, изменение конфига | Контекст, аудит |
| **Logs** | Детальные текстовые записи | Ошибки, stack trace, HTTP-запросы | Глубокий разбор инцидента |
| **Traces** | Путь запроса через сервисы | Span’ы, trace ID, latency по hop’ам | Поиск узкого места в распределённой системе |

**Важно:** на собеседовании часто просят объяснить, чем logs отличаются от traces.
- **Log** — «что произошло в этой точке».
- **Trace** — «как запрос прошёл через всю систему и где задержался»[reference:1].

## 3. Prometheus

### 3.1. Модель сбора данных: Pull, а не Push

Prometheus **сам опрашивает** (scrape) targets по HTTP по фиксированному интервалу (обычно 15–30 секунд)[reference:2].

**Почему pull — это осознанное решение:**
- Prometheus знает полный список целей → если target перестал отвечать, это явный `up == 0`, а не тишина.
- Нет проблемы «лавины» входящих соединений (fan-in).
- Любую цель можно проверить вручную через `curl`[reference:3].

**Ограничения pull:**
- Target должен быть достижим по сети от Prometheus (firewall/NAT — проблема).
- Короткоживущие batch-джобы, которые завершаются между scrape’ами, невидны → для них есть **Pushgateway**[reference:4].

### 3.2. Ключевые компоненты вокруг Prometheus

| Компонент | Роль |
|---|---|
| **Prometheus Server** | Scrape, хранение в TSDB, выполнение PromQL, вычисление alert-правил |
| **Exporters** | Превращают «не-Prometheus» систему в `/metrics` (node_exporter, blackbox_exporter, kube-state-metrics) |
| **Client libraries** | Приложение само отдаёт метрики в формате Prometheus |
| **Service Discovery** | Автоматически находит targets (Kubernetes, Consul, cloud API) |
| **Alertmanager** | Отдельный процесс: группировка, inhibition, silencing, маршрутизация алертов |
| **Pushgateway** | Приём метрик от короткоживущих джоб |

**Частая ошибка на собеседовании:** приписывать маршрутизацию алертов самому Prometheus.
> Prometheus **вычисляет** alert-правила и отправляет сработавшие алерты в **Alertmanager**, который уже занимается routing’ом[reference:5].

### 3.3. Типы метрик в Prometheus

| Тип | Что представляет | Пример |
|---|---|---|
| **Counter** | Монотонно возрастающее значение | `http_requests_total` |
| **Gauge** | Значение, которое может расти и падать | `memory_usage_bytes` |
| **Histogram** | Распределение значений по бакетам | `http_request_duration_seconds` |
| **Summary** | Квантили, вычисляемые на клиенте | `rpc_duration_seconds{quantile="0.99"}` |

**На собеседовании:** могут спросить, чем histogram отличается от summary.  
Histogram агрегируется на стороне Prometheus (можно суммировать по инстансам), summary — нет (квантили считаются на клиенте и плохо агрегируются).

### 3.4. PromQL: что нужно знать минимум

- **Селекторы:** `http_requests_total{job="api", status="500"}`
- **Range vectors:** `rate(http_requests_total[5m])`
- **Агрегация:** `sum by (service) (rate(http_requests_total[5m]))`
- **`up`** — базовая метрика доступности target’а.

**Кардинальность** — главный операционный риск Prometheus.  
Высокая кардинальность (много уникальных лейблов) «взрывает» TSDB и память. На собеседовании это стоит упомянуть **до того, как спросят**[reference:6].

## 4. Grafana

**Роль:** слой визуализации и единая точка входа для запросов к разным источникам данным (Prometheus, Loki, Tempo и др.).

**Что важно знать:**
- Grafana **не хранит** телеметрию — она только запрашивает её у data sources.
- Дашборды — это JSON-модели; их можно версионировать и хранить в Git.
- Аннотации (annotations) позволяют накладывать события (деплои, инциденты) на графики.
- Grafana Alerting может работать поверх разных источников, не только Prometheus.

## 5. Loki (логи)

**Идея:** «Prometheus для логов».

**Ключевое архитектурное решение Loki:** индексируются **только лейблы**, а не полный текст логов[reference:7].

| Плюс | Минус |
|---|---|
| Дешёвое хранение (особенно в объектном storage) | Полнотекстовый поиск дороже, чем в ELK |
| Быстрая запись | Нужно продумывать лейблы, иначе запросы будут медленными |

**Тезис для собеседования:**  
Loki trade-off’ит скорость полнотекстового поиска на стоимость хранения и простоту масштабирования. Если нужен сложный полнотекстовый поиск — это не сценарий Loki.

**LogQL** — язык запросов, похожий на PromQL, но для логов.

## 6. Tempo (трейсы)

**Роль:** распределённая трассировка, совместимая с OpenTelemetry.

**Ключевые особенности:**
- Tempo **не индексирует** содержимое трейсов; он хранит их в объектном storage (S3, MinIO) и ищет по trace ID или по лейблам.
- Дешёвое долговременное хранение трейсов.
- Интеграция с Grafana: из метрики или лога можно перейти к трейсу (exemplars / trace to logs).

**Что спросят:**  
«Почему Tempo дешевле, чем Jaeger с полнотекстовым индексом?»  
Потому что Tempo не строит тяжёлый индекс по всем span’ам, а полагается на объектное хранение и точечный поиск по ID[reference:8].

## 7. Grafana Alloy

**Роль:** универсальный агент сбора телеметрии (замена Grafana Agent / Promtail).

**Что важно:**
- Собирает **метрики, логи и трейсы** в одном агенте.
- Настраивается декларативно (River-конфигурация).
- Может выступать как:
    - scraper для Prometheus-метрик,
    - log shipper для Loki,
    - trace collector для Tempo.

**Тезис:** Alloy — это «OpenTelemetry Collector с уклоном в экосистему Grafana», единая точка сбора телеметрии на ноде/кластере.

## 8. Spring Boot Actuator + Micrometer (метрики Java-приложения)

### 8.1. Как это работает

1. **Micrometer** — фасад метрик (аналог SLF4J, но для метрик).
2. **Spring Boot Actuator** авто-конфигурирует endpoint `/actuator/prometheus`.
3. Prometheus scrape’ит этот endpoint по аннотации или через service discovery.

**Endpoint по умолчанию:** `/actuator/prometheus`  
**Формат:** plain text exposition format[reference:9].

### 8.2. Что автоматически попадает в метрики

- JVM: memory, GC, threads.
- HTTP-запросы: count, latency (histogram).
- Connection pools, cache, executors.
