## 1. SQL: запросы и задачи

### Учебная схема

Все задачи используют одну схему. Скопируйте её в `psql` целиком.

```sql
DROP TABLE IF EXISTS order_items, orders, products, customers CASCADE;

CREATE TABLE customers (
    id         int  PRIMARY KEY,
    name       text NOT NULL,
    email      text NOT NULL,
    city       text,                       -- может быть NULL
    created_at date NOT NULL
);

CREATE TABLE products (
    id       int  PRIMARY KEY,
    name     text NOT NULL,
    category text NOT NULL,
    price    numeric(10, 2) NOT NULL CHECK (price > 0)
);

CREATE TABLE orders (
    id          int  PRIMARY KEY,
    customer_id int  REFERENCES customers (id),   -- NULL = гостевой заказ
    status      text NOT NULL CHECK (status IN ('NEW', 'PAID', 'CANCELLED')),
    created_at  timestamptz NOT NULL,
    total       numeric(10, 2) NOT NULL            -- денормализованная сумма
);

CREATE TABLE order_items (
    order_id   int REFERENCES orders (id),
    product_id int REFERENCES products (id),
    quantity   int NOT NULL CHECK (quantity > 0),
    price      numeric(10, 2) NOT NULL,            -- цена на момент покупки
    PRIMARY KEY (order_id, product_id)
);

INSERT INTO customers VALUES
    (1, 'Анна',  'anna@example.com',  'Helsinki', '2025-01-10'),
    (2, 'Борис', 'boris@example.com', 'Moscow',   '2025-02-15'),
    (3, 'Вера',  'vera@example.com',  'Helsinki', '2025-03-01'),
    (4, 'Глеб',  'gleb@example.com',  NULL,       '2025-03-20'),
    (5, 'Дина',  'ANNA@example.com',  'Tallinn',  '2025-04-02');

INSERT INTO products VALUES
    (1, 'Клавиатура', 'periphery',  50.00),
    (2, 'Мышь',       'periphery',  20.00),
    (3, 'Монитор',    'display',   300.00),
    (4, 'Кабель',     'periphery',   5.00),
    (5, 'Проектор',   'display',   700.00);

INSERT INTO orders VALUES
    (101, 1,    'PAID',      '2025-05-01 10:00+00',  70.00),
    (102, 1,    'PAID',      '2025-05-03 12:00+00', 300.00),
    (103, 1,    'NEW',       '2025-05-07 09:00+00',  10.00),
    (104, 1,    'PAID',      '2025-05-09 18:00+00',  20.00),
    (105, 2,    'PAID',      '2025-05-02 11:00+00', 350.00),
    (106, 2,    'CANCELLED', '2025-05-04 15:00+00', 700.00),
    (107, 3,    'NEW',       '2025-05-05 08:00+00',  50.00),
    (108, NULL, 'PAID',      '2025-05-06 14:00+00',  25.00);

INSERT INTO order_items VALUES
    (101, 1, 1,  50.00), (101, 2, 1,  20.00),
    (102, 3, 1, 300.00),
    (103, 4, 2,   5.00),
    (104, 2, 1,  20.00),
    (105, 3, 1, 300.00), (105, 1, 1,  50.00),
    (106, 5, 1, 700.00),
    (107, 1, 1,  50.00),
    (108, 2, 1,  20.00), (108, 4, 2,   5.00);
```

В данных намеренно есть ловушки: клиент без города, гостевой заказ без клиента, дубликат email в другом регистре и заказ, у которого `total` не совпадает с суммой позиций.

Порядок логического выполнения `SELECT` полезно помнить для всех задач:

```text
FROM / JOIN → WHERE → GROUP BY → HAVING → оконные функции → SELECT → DISTINCT → ORDER BY → LIMIT / OFFSET
```

Отсюда следует, что в `WHERE` нельзя использовать агрегаты и псевдонимы из `SELECT`, а оконную функцию нельзя отфильтровать в том же запросе — нужен подзапрос или CTE.

### Задача 1. Клиенты без заказов

`[ ]` Найдите клиентов, у которых нет ни одного заказа. Решите двумя способами.

Ожидаемый результат: `4 Глеб`, `5 Дина`.

<details>
<summary>Решение</summary>

```sql
-- Способ 1: anti-join через LEFT JOIN
SELECT c.id, c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL
ORDER BY c.id;

-- Способ 2: NOT EXISTS — обычно самый читаемый и безопасный вариант
SELECT c.id, c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
)
ORDER BY c.id;
```

Проверять нужно колонку, которая в правой таблице не может быть `NULL` для существующей строки: первичный ключ `o.id` или колонку соединения.

</details>

**Уточнение интервьюера:** «А почему не `NOT IN`?»

<details>
<summary>Ответ</summary>

```sql
SELECT c.id, c.name
FROM customers c
WHERE c.id NOT IN (SELECT customer_id FROM orders);
-- 0 строк
```

В `orders` есть гостевой заказ с `customer_id = NULL`. Условие `4 NOT IN (1, 2, 3, NULL)` раскрывается в `4 <> 1 AND 4 <> 2 AND 4 <> 3 AND 4 <> NULL`, а `4 <> NULL` — это `UNKNOWN`. Итог не `TRUE`, и строка отбрасывается. Если подзапрос может вернуть `NULL`, используйте `NOT EXISTS` или явно отфильтруйте `WHERE customer_id IS NOT NULL`.

</details>

**Типичная ошибка:** `NOT IN` с подзапросом по nullable-колонке. Тесты проходят, пока в данных не появится первый `NULL`.

### Задача 2. Выручка по клиентам

`[ ]` Посчитайте выручку по оплаченным заказам (`PAID`) для каждого клиента и оставьте тех, у кого она не меньше 300.

Ожидаемый результат: `Анна 390.00`, `Борис 350.00`.

<details>
<summary>Решение</summary>

```sql
SELECT c.id, c.name, sum(o.total) AS revenue
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'PAID'               -- фильтр строк до группировки
GROUP BY c.id, c.name
HAVING sum(o.total) >= 300            -- фильтр групп после агрегации
ORDER BY revenue DESC;
```

`WHERE` отбирает строки до `GROUP BY`, `HAVING` — группы после. Условие без агрегата лучше писать в `WHERE`: в группировку попадёт меньше строк.

</details>

**Уточнение интервьюера:** «Теперь покажите всех клиентов, включая тех, у кого выручка 0».

<details>
<summary>Ответ</summary>

```sql
SELECT c.id, c.name, coalesce(sum(o.total), 0) AS revenue
FROM customers c
LEFT JOIN orders o
       ON o.customer_id = c.id
      AND o.status = 'PAID'           -- условие на правую таблицу — в ON
GROUP BY c.id, c.name
ORDER BY c.id;
-- 5 строк: у Веры, Глеба и Дины revenue = 0
```

Ловушка: если оставить `WHERE o.status = 'PAID'`, у клиентов без заказов `o.status` будет `NULL`, условие отбросит их строки, и `LEFT JOIN` фактически превратится во внутреннее соединение — останутся только 2 клиента.

</details>

**Типичная ошибка:** фильтр по правой таблице `LEFT JOIN` в `WHERE`.

### Задача 3. Проверка денормализованных данных

`[ ]` В `orders.total` хранится копия суммы заказа. Найдите заказы, где она расходится с суммой позиций.

Ожидаемый результат: `108 | 25.00 | 30.00`.

<details>
<summary>Решение</summary>

```sql
SELECT o.id, o.total, sum(oi.quantity * oi.price) AS items_total
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, o.total
HAVING o.total <> sum(oi.quantity * oi.price);
```

</details>

**Уточнение интервьюера:** «Почему такое вообще возможно и как это предотвратить?»

<details>
<summary>Ответ</summary>

Это цена денормализации: одна и та же информация хранится дважды, и никакое ограничение не связывает копии. Варианты: не хранить `total` и считать его при чтении; обновлять его в той же транзакции, что и позиции; использовать триггер; регулярно запускать такую сверку как проверку целостности. См. [7.5](#75-денормализация).

</details>

### Задача 4. NULL и COUNT

`[ ]` Не запуская запросы, предскажите результат:

```sql
SELECT count(*), count(city), count(DISTINCT city) FROM customers;
SELECT count(*) FROM customers WHERE city <> 'Helsinki';
```

<details>
<summary>Ответ</summary>

- `count(*) = 5` — считает строки;
- `count(city) = 4` — пропускает `NULL`;
- `count(DISTINCT city) = 3` — уникальные значения без `NULL`;
- `city <> 'Helsinki'` возвращает **2**, а не 3: у Глеба `city IS NULL`, и сравнение с `NULL` даёт `UNKNOWN`.

Чтобы учесть `NULL`, используйте `city IS DISTINCT FROM 'Helsinki'` — результат 3.

В `GROUP BY city` все `NULL` попадут в одну группу: для группировки они считаются равными, хотя `NULL = NULL` даёт `UNKNOWN`.

</details>

**Типичная ошибка:** считать, что `col <> 'x'` возвращает «всё остальное».

### Задача 5. Последние заказы каждого клиента

`[ ]` Для каждого клиента выведите два последних заказа. Это классическая задача «top-N в группе».

Ожидаемый результат — 5 строк: у Анны заказы 104 и 103, у Бориса 106 и 105, у Веры 107.

<details>
<summary>Решение через оконную функцию</summary>

```sql
SELECT customer_id, id, created_at
FROM (
    SELECT o.*,
           row_number() OVER (
               PARTITION BY customer_id
               ORDER BY created_at DESC, id DESC   -- id — для детерминизма
           ) AS rn
    FROM orders o
    WHERE customer_id IS NOT NULL
) t
WHERE rn <= 2
ORDER BY customer_id, created_at DESC;
```

Фильтровать по `rn` в том же `SELECT` нельзя: оконные функции вычисляются после `WHERE`.

</details>

<details>
<summary>Решение через LATERAL</summary>

```sql
SELECT c.id, c.name, last.id AS order_id, last.created_at
FROM customers c
CROSS JOIN LATERAL (
    SELECT o.id, o.created_at
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC, o.id DESC
    LIMIT 2
) last
ORDER BY c.id, last.created_at DESC;
```

С индексом `orders (customer_id, created_at)` этот вариант может читать только нужные строки для каждого клиента, а не нумеровать все заказы.

</details>

**Уточнение интервьюера:** «Чем `row_number`, `rank` и `dense_rank` отличаются при равных значениях?»

<details>
<summary>Ответ</summary>

Для значений `100, 90, 90, 80`:

| Функция | Результат | Смысл |
|---|---|---|
| `row_number()` | 1, 2, 3, 4 | Уникальный номер, порядок равных — произвольный, если не уточнить сортировку |
| `rank()` | 1, 2, 2, 4 | Равные делят место, следующее пропускается |
| `dense_rank()` | 1, 2, 2, 3 | Равные делят место, без пропусков |

</details>

### Задача 6. Рейтинг товаров в категории

`[ ]` Посчитайте выручку каждого товара по оплаченным заказам и его место внутри категории.

Ожидаемый результат:

```text
 category  |    name    | revenue | rnk
-----------+------------+---------+-----
 display   | Монитор    |  600.00 |   1
 periphery | Клавиатура |  100.00 |   1
 periphery | Мышь       |   60.00 |   2
 periphery | Кабель     |   10.00 |   3
```

<details>
<summary>Решение</summary>

```sql
SELECT p.category,
       p.name,
       sum(oi.quantity * oi.price) AS revenue,
       dense_rank() OVER (
           PARTITION BY p.category
           ORDER BY sum(oi.quantity * oi.price) DESC
       ) AS rnk
FROM order_items oi
JOIN orders   o ON o.id = oi.order_id
JOIN products p ON p.id = oi.product_id
WHERE o.status = 'PAID'
GROUP BY p.category, p.name
ORDER BY p.category, rnk;
```

Оконная функция может использовать агрегат, потому что выполняется после `GROUP BY`. «Проектора» нет: его единственный заказ отменён.

</details>

### Задача 7. Накопительный итог

`[ ]` Для каждого клиента выведите оплаченные заказы и накопленную сумму.

Ожидаемый результат для Анны: `70 → 370 → 390`.

<details>
<summary>Решение</summary>

```sql
SELECT customer_id, id, created_at::date, total,
       sum(total) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
       ) AS running_total
FROM orders
WHERE status = 'PAID' AND customer_id IS NOT NULL
ORDER BY customer_id, created_at;
```

</details>

**Уточнение интервьюера:** «Что изменится, если у двух заказов одинаковый `created_at` и в `ORDER BY` окна нет `id`?»

<details>
<summary>Ответ</summary>

По умолчанию рамка окна — `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, а в режиме `RANGE` строки с одинаковым ключом сортировки считаются «соседями» и попадают в рамку вместе. Обе строки получат одинаковый итог, уже включающий обе суммы. Чтобы считать строго построчно, добавьте уникальный ключ в сортировку или укажите `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

</details>

### Задача 8. Дубликаты

`[ ]` Найдите email, которые повторяются без учёта регистра, и предложите, как предотвратить такие дубликаты.

Ожидаемый результат: `anna@example.com | 2 | {1,5}`.

<details>
<summary>Решение</summary>

```sql
SELECT lower(email) AS email_norm,
       count(*)     AS cnt,
       array_agg(id ORDER BY id) AS ids
FROM customers
GROUP BY lower(email)
HAVING count(*) > 1;
```

Предотвращение — уникальный индекс по выражению:

```sql
CREATE UNIQUE INDEX customers_email_lower_uq ON customers (lower(email));
-- ERROR:  could not create unique index "customers_email_lower_uq"
-- DETAIL:  Key (lower(email))=(anna@example.com) is duplicated.
```

Индекс не создастся, пока в таблице есть дубликаты: сначала их нужно разобрать.

</details>

**Уточнение интервьюера:** «Почему проверки в коде приложения недостаточно?»

<details>
<summary>Ответ</summary>

Схема «проверить, что такого email нет → вставить» подвержена гонке: две параллельные транзакции обе увидят, что email свободен, и обе вставят. Гарантию даёт только ограничение в базе. Приложение при этом должно обрабатывать ошибку нарушения уникальности (`SQLSTATE 23505`) или использовать `INSERT ... ON CONFLICT`.

</details>

### Задача 9. Пагинация

`[ ]` Выведите заказы постранично по 3 штуки, новые сначала. Объясните, чем плох `OFFSET`.

<details>
<summary>Решение: keyset-пагинация</summary>

```sql
-- Первая страница
SELECT id, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 3;
-- 104, 103, 108

-- Следующая страница: передаём ключ последней строки предыдущей страницы
SELECT id, created_at
FROM orders
WHERE (created_at, id) < ('2025-05-06 14:00+00', 108)
ORDER BY created_at DESC, id DESC
LIMIT 3;
-- 107, 106, 102
```

Под этот запрос подходит индекс `(created_at, id)`: B-tree умеет читать его в обратном направлении.

</details>

**Уточнение интервьюера:** «Зачем `id` в сортировке и чем плох `OFFSET 100000`?»

<details>
<summary>Ответ</summary>

- `id` делает порядок детерминированным при одинаковом `created_at`. Без него строки могут пропадать или дублироваться между страницами.
- `OFFSET N` заставляет базу найти и отбросить N строк — чем дальше страница, тем медленнее. Кроме того, если между запросами страниц добавилась строка, `OFFSET` сдвинет выдачу.
- Keyset начинает чтение сразу с нужного места индекса. Минус: нельзя перейти «сразу на 50-ю страницу» — только «следующая / предыдущая».

</details>

### Задача 10. Товары без продаж

`[ ]` Найдите товары, которые ни разу не продавались в оплаченных заказах.

Ожидаемый результат: `5 Проектор`.

<details>
<summary>Решение</summary>

```sql
SELECT p.id, p.name
FROM products p
WHERE NOT EXISTS (
    SELECT 1
    FROM order_items oi
    JOIN orders o ON o.id = oi.order_id
    WHERE oi.product_id = p.id
      AND o.status = 'PAID'
);
```

</details>

### Короткие вопросы по SQL

<details>
<summary>Чем UNION отличается от UNION ALL?</summary>

`UNION` удаляет дубликаты — для этого нужны сортировка или хеширование. `UNION ALL` просто склеивает результаты и обычно дешевле. Если дубликатов быть не может или они нужны, используйте `UNION ALL`.

</details>

<details>
<summary>Чем CTE (WITH) отличается от подзапроса?</summary>

Чаще всего — только читаемостью. В PostgreSQL 12+ нерекурсивный CTE без побочных эффектов, на который ссылаются один раз, встраивается в основной запрос так же, как подзапрос. Явное `WITH ... AS MATERIALIZED` заставляет вычислить его отдельно. Рекурсивные CTE (`WITH RECURSIVE`) нужны для обхода иерархий.

</details>

<details>
<summary>Чем DELETE отличается от TRUNCATE?</summary>

`DELETE` удаляет строки по условию, срабатывают построчные триггеры, в MVCC остаются мёртвые версии строк для `VACUUM`. `TRUNCATE` очищает таблицу целиком, работает быстро, но берёт эксклюзивную блокировку таблицы. В PostgreSQL `TRUNCATE` транзакционен и откатывается через `ROLLBACK`.

</details>

## 2. Схема, ключи и ограничения

### 2.1. Короткий ответ

Ограничения — последняя линия защиты целостности данных. Приложение может содержать ошибки или работать в нескольких экземплярах параллельно, а ограничение в базе соблюдается всегда.

| Ограничение | Что гарантирует |
|---|---|
| `PRIMARY KEY` | Уникальность и `NOT NULL`; создаёт уникальный индекс |
| `UNIQUE` | Уникальность; создаёт уникальный индекс |
| `NOT NULL` | Значение обязательно |
| `CHECK` | Условие над значениями строки, например `price > 0` |
| `FOREIGN KEY` | Ссылка на существующую строку другой таблицы |
| `EXCLUDE` | Специфично для PostgreSQL: запрет пересечений, например бронирований одного ресурса на пересекающиеся интервалы |

### 2.2. Ключи

- **Естественный ключ** — атрибут предметной области: ИНН, код страны. Может меняться и бывает длинным.
- **Суррогатный ключ** — `bigint GENERATED ALWAYS AS IDENTITY` или UUID. Стабилен и не несёт смысла.
- Частая практика: суррогатный `PRIMARY KEY` + `UNIQUE` на естественный ключ. Тогда ссылки стабильны, а дубликаты всё равно запрещены.

<details>
<summary>UUID или bigint?</summary>

`bigint` компактнее и вставляется последовательно в конец индекса. UUID можно сгенерировать без обращения к базе, и он не раскрывает количество записей. Случайный UUIDv4 разбрасывает вставки по всему B-tree. Упорядоченные по времени UUIDv7 уменьшают эту проблему; в PostgreSQL 18 для их генерации есть функция `uuidv7()`.

</details>

### 2.3. Внешние ключи

`[ ]` **Вопрос:** создаёт ли `FOREIGN KEY` индекс автоматически?

**Короткий ответ:** в PostgreSQL — **нет**, на ссылающихся колонках индекс не создаётся. На колонках, на которые ссылаются, уже должен быть первичный ключ или уникальное ограничение.

<details>
<summary>Подробности</summary>

Индекс на ссылающейся колонке (`orders.customer_id`) часто нужен:

- при `DELETE` или изменении ключа в родительской таблице база ищет связанные строки в дочерней — без индекса это последовательное сканирование;
- запросы «заказы клиента» почти всегда фильтруют по этой колонке.

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
```

Индекс не создаётся автоматически, потому что он нужен не всегда и подходящих вариантов индекса может быть несколько — например, составной `(customer_id, created_at)` закроет и поиск, и сортировку.

Поведение при удалении родителя задаётся явно: `ON DELETE RESTRICT` / `NO ACTION` (по умолчанию — ошибка), `CASCADE`, `SET NULL`, `SET DEFAULT`.

</details>

### 2.4. NULL и уникальность

<details>
<summary>Можно ли вставить два NULL в колонку с UNIQUE?</summary>

По умолчанию — да: `NULL` не считаются равными, поэтому не конфликтуют. В PostgreSQL 15+ можно указать `UNIQUE NULLS NOT DISTINCT`, и тогда `NULL` допускается только один раз.

</details>

## 3. Индексы и планы выполнения

### 3.1. Типы индексов

| Тип | Для чего | Пример использования |
|---|---|---|
| **B-tree** | Равенство, диапазоны, сортировка, уникальность. Тип по умолчанию | `WHERE created_at > ...`, `ORDER BY name` |
| **Hash** | Только равенство | `WHERE token = ...` — но B-tree обычно не хуже |
| **GIN** | Инвертированный индекс: элементы массивов, JSONB, полнотекстовый поиск, триграммы (`pg_trgm`) | `WHERE tags @> ARRAY['sql']` |
| **GiST / SP-GiST** | Каркасы для специализированных типов: геометрия, диапазоны, ближайшие соседи | `WHERE period && tsrange(...)` |
| **BRIN** | Компактный индекс диапазонов блоков для огромных таблиц, где физический порядок строк коррелирует со значением | Журнал событий, упорядоченный по времени |

Какие операторы поддерживает индекс, зависит от типа данных и operator class.

> Все индексы в PostgreSQL вторичные: таблица (heap) хранится отдельно, а индекс указывает на версии строк в ней.

### 3.2. Цена индекса

`[ ]` **Короткий ответ:** индекс ускоряет подходящие чтения, но занимает место, замедляет запись и используется не всегда — планировщик выбирает самый дешёвый по своей оценке план.

<details>
<summary>Подробности</summary>

- Индекс занимает место на диске и в памяти.
- Каждый `INSERT`, `UPDATE` (если не сработал HOT-update) и `DELETE` обновляет индексы.
- Если запрос читает значительную долю таблицы, последовательное чтение может быть дешевле множества случайных обращений по индексу.
- Индекс не применяется, если условие не совпадает с тем, что проиндексировано: `WHERE lower(email) = ?` при индексе на `email`, `WHERE created_at::date = ?` при индексе на `created_at`, `LIKE '%abc'` при обычном B-tree.
- План зависит от статистики. После массовой загрузки данных выполните `ANALYZE`.

</details>

### 3.3. Составные индексы

`[ ]` **Короткий ответ:** порядок колонок важен. B-tree `(a, b)` упорядочен сначала по `a`, затем по `b` внутри каждого `a`, поэтому эффективнее всего работает при условиях на ведущую колонку.

| Условие запроса | Польза от индекса `(a, b)` |
|---|---|
| `WHERE a = ?` | Да |
| `WHERE a = ? AND b = ?` | Да |
| `WHERE a = ? ORDER BY b` | Да, отдельная сортировка может не понадобиться |
| `WHERE a > ? AND b = ?` | Диапазон сужается по `a`; условие на `b` проверяется в индексе, но не обязательно сокращает читаемую часть |
| `WHERE b = ?` | Зависит от данных: см. ниже |

**Условие только по второй колонке.** Раньше ответ был «индекс почти бесполезен». С PostgreSQL 18 B-tree поддерживает **skip scan**: база перебирает различные значения `a` и для каждого ищет `b = ?`. Это выгодно, когда различных значений `a` немного. Если их много, планировщик обычно предпочтёт последовательное сканирование или полный проход по индексу.

<details>
<summary>Проверка на тестовых данных (1 млн строк, PostgreSQL 18.6)</summary>

Таблица `orders_big` из [3.6](#36-разбор-explain-от-медленного-запроса-к-быстрому): 3 значения `status`, около 10 000 значений `customer_id`.

Ведущая колонка с 3 значениями — skip scan:

```sql
CREATE INDEX ON orders_big (status, created_at);

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders_big WHERE created_at >= now() - interval '1 day';
```

```text
Index Only Scan using orders_big_status_created_at_idx on orders_big
  Index Cond: (created_at >= (now() - '1 day'::interval))
  Index Searches: 4
```

`Index Searches: 4` — несколько точечных спусков по дереву, а не проход по всему индексу.

Ведущая колонка с 10 000 значений:

```sql
CREATE INDEX ON orders_big (customer_id, status);

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders_big WHERE status = 'CANCELLED';
```

```text
Parallel Index Only Scan using orders_big_customer_id_status_idx on orders_big
  Index Cond: (status = 'CANCELLED'::text)
  Index Searches: 1
  Buffers: shared hit=3094 read=924
```

Здесь `Index Searches: 1` при тысячах прочитанных буферов: индекс прочитан целиком, без пропусков. Он использован, но эффективного поиска нет.

Вывод для собеседования: «используется индекс» и «индекс эффективен» — разные утверждения.

</details>

```sql
CREATE INDEX idx_orders_customer_created
    ON orders (customer_id, created_at);
```

Учитывайте селективность, сортировку, покрытие запроса и стоимость поддержки. Не создавайте индекс на каждую колонку автоматически.

### 3.4. Полезные разновидности

```sql
-- Частичный индекс: индексируются только нужные строки
CREATE INDEX idx_orders_pending ON orders (created_at)
    WHERE status = 'PENDING';

-- Покрывающий индекс: делает возможным Index Only Scan (но не гарантирует его, см. 3.5)
CREATE INDEX idx_orders_customer_incl ON orders (customer_id)
    INCLUDE (total);

-- Индекс по выражению: запрос должен использовать то же выражение
CREATE INDEX idx_users_email_lower ON users (lower(email));

-- Создание без длительной блокировки записи
CREATE INDEX CONCURRENTLY idx_orders_status ON orders (status);
```

<details>
<summary>Особенности CREATE INDEX CONCURRENTLY</summary>

- Нельзя выполнить внутри блока транзакции.
- Работает дольше обычного создания: таблица сканируется дважды, и нужно дождаться завершения транзакций, которые могут использовать старое состояние.
- При ошибке, например при нарушении уникальности, остаётся индекс в состоянии `INVALID`. Его нужно удалить и создать заново.

</details>

### 3.5. Index Only Scan и visibility map

`[ ]` **Вопрос:** почему в плане `Index Only Scan`, но `Heap Fetches` больше нуля?

**Короткий ответ:** все нужные колонки есть в индексе, но PostgreSQL должен ещё проверить, что версия строки видна текущему снимку MVCC. Информация о видимости хранится в таблице, а не в индексе. Если страница таблицы не отмечена в visibility map как all-visible, базе приходится читать саму строку.

<details>
<summary>Подробности</summary>

- Visibility map — битовая карта: для каждой страницы таблицы отмечено, видны ли все её строки всем транзакциям.
- Бит сбрасывается при изменении строк на странице и снова выставляется `VACUUM`.
- Если бит не выставлен, `Index Only Scan` не выигрывает у обычного `Index Scan`.
- Отсюда практическое следствие: покрывающие индексы полезны прежде всего для таблиц, которые меняются редко или регулярно обрабатываются `VACUUM`.
- `INCLUDE`-колонки увеличивают размер индекса. Добавляйте их осторожно, особенно широкие.
- В уникальном индексе с `INCLUDE` уникальность проверяется только по ключевым колонкам.

Как воспроизвести — в [3.6](#36-разбор-explain-от-медленного-запроса-к-быстрому), шаги 4–6.

</details>

### 3.6. Разбор EXPLAIN: от медленного запроса к быстрому

Ниже — реальные планы на PostgreSQL 18.6. Время у вас будет другим: сравнивайте **форму плана, число строк и буферы**, а не миллисекунды.

**Подготовка: 1 млн заказов, около 10 000 клиентов.**

```sql
DROP TABLE IF EXISTS orders_big;
CREATE TABLE orders_big (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id int         NOT NULL,
    status      text        NOT NULL,
    created_at  timestamptz NOT NULL,
    total       numeric(10, 2) NOT NULL
);

INSERT INTO orders_big (customer_id, status, created_at, total)
SELECT (random() * 9999)::int + 1,
       (ARRAY['NEW', 'PAID', 'CANCELLED'])[1 + (random() * 2)::int],
       now() - random() * interval '365 days',
       round((random() * 1000)::numeric, 2)
FROM generate_series(1, 1000000);

ANALYZE orders_big;
```

**Запрос, который будем ускорять:** 20 последних заказов клиента.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, total
FROM orders_big
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

> `EXPLAIN ANALYZE` действительно выполняет запрос. Для `UPDATE`/`DELETE` оборачивайте его в `BEGIN; ... ROLLBACK;`.

Как читать узел плана:

```text
Seq Scan on t  (cost=0.00..13318.33 rows=42 width=22) (actual time=0.642..23.796 rows=33.00 loops=3)
```

- `cost=0.00..13318.33` — оценка стоимости до первой и до последней строки в условных единицах;
- `rows=42` — сколько строк ожидает планировщик;
- `width=22` — средний размер строки в байтах;
- `actual time=0.642..23.796` — фактическое время до первой и до последней строки, мс;
- `actual rows=33.00` — фактическое число строк **на одно выполнение** узла;
- `loops=3` — сколько раз выполнялся узел; общее число строк — `rows × loops`.

План читается изнутри наружу: самый вложенный узел выполняется первым.

#### Шаг 1. Индекса нет

```text
Limit  (actual time=31.362..33.016 rows=20.00 loops=1)
  Buffers: shared hit=8186
  ->  Gather Merge
        Workers Launched: 2
        ->  Sort
              Sort Key: created_at DESC
              ->  Parallel Seq Scan on orders_big  (rows=42) (actual rows=33.00 loops=3)
                    Filter: (customer_id = 42)
                    Rows Removed by Filter: 333300
Execution Time: 33.066 ms
```

`[ ]` Что вы видите?

<details>
<summary>Разбор</summary>

- `Parallel Seq Scan` + `Rows Removed by Filter: 333300` в каждом из трёх процессов: прочитана вся таблица, чтобы найти около 100 строк.
- `Buffers: shared hit=8186` — прочитано около 8 тыс. страниц по 8 КБ, то есть вся таблица.
- `Sort` — сортировка выполняется отдельно, после фильтрации.
- Оценка `rows=42` против фактических 33 на процесс — статистика адекватна, проблема не в ней.

Гипотеза: нужен индекс по `customer_id`.

</details>

#### Шаг 2. Индекс только по фильтру

```sql
CREATE INDEX idx_ob_customer ON orders_big (customer_id);
```

```text
Limit  (actual time=0.470..0.473 rows=20.00 loops=1)
  Buffers: shared hit=102 read=3
  ->  Sort
        Sort Key: created_at DESC
        Sort Method: top-N heapsort  Memory: 27kB
        ->  Bitmap Heap Scan on orders_big  (actual rows=99.00 loops=1)
              Recheck Cond: (customer_id = 42)
              Heap Blocks: exact=99
              ->  Bitmap Index Scan on idx_ob_customer  (actual rows=99.00 loops=1)
                    Index Cond: (customer_id = 42)
Execution Time: 0.511 ms
```

`[ ]` Что улучшилось и что осталось?

<details>
<summary>Разбор</summary>

- Буферов стало около 100 вместо 8 тыс.
- `Heap Blocks: exact=99` — 99 строк клиента лежат на 99 разных страницах таблицы. Это нормально для данных, вставленных вперемешку.
- `Bitmap Heap Scan`: сначала по индексу собирается битовая карта страниц, затем страницы читаются в физическом порядке.
- По-прежнему есть `Sort`: читаются все 99 строк клиента, хотя нужны 20.

Гипотеза: добавить `created_at` в индекс, чтобы строки сразу выходили в нужном порядке.

</details>

#### Шаг 3. Индекс под фильтр и сортировку

```sql
DROP INDEX idx_ob_customer;
CREATE INDEX idx_ob_customer_created ON orders_big (customer_id, created_at DESC);
```

```text
Limit  (actual time=0.038..0.151 rows=20.00 loops=1)
  Buffers: shared hit=20 read=3
  ->  Index Scan using idx_ob_customer_created on orders_big  (actual rows=20.00 loops=1)
        Index Cond: (customer_id = 42)
        Index Searches: 1
Execution Time: 0.187 ms
```

<details>
<summary>Разбор</summary>

- Узла `Sort` больше нет: индекс отдаёт строки уже отсортированными.
- `actual rows=20` — благодаря `LIMIT` чтение остановилось после 20 строк.
- Около 23 буферов: несколько страниц индекса и около 20 страниц таблицы.
- `DESC` в определении индекса здесь не обязателен: B-tree можно читать в обратном направлении. Направление важно, когда сортировка смешанная, например `ORDER BY a ASC, b DESC`.

</details>

#### Шаг 4. Ловушка: INCLUDE без нужной колонки

```sql
DROP INDEX idx_ob_customer_created;
CREATE INDEX idx_ob_cc_incl ON orders_big (customer_id, created_at DESC) INCLUDE (total);
```

```text
->  Index Scan using idx_ob_cc_incl on orders_big
```

`[ ]` Почему не `Index Only Scan`?

<details>
<summary>Разбор</summary>

Запрос выбирает `id`, а его нет в индексе. Чтобы получить `id`, всё равно нужно читать таблицу. Покрывающий индекс должен содержать **все** колонки, которые использует запрос.

</details>

#### Шаг 5. Покрывающий индекс

```sql
DROP INDEX idx_ob_cc_incl;
CREATE INDEX idx_ob_cc_incl ON orders_big (customer_id, created_at DESC) INCLUDE (total, id);
VACUUM orders_big;
```

```text
Limit  (actual time=0.024..0.026 rows=20.00 loops=1)
  ->  Index Only Scan using idx_ob_cc_incl on orders_big
        Index Cond: (customer_id = 42)
        Heap Fetches: 0
        Buffers: shared hit=4
```

`Heap Fetches: 0`, 4 буфера: обращений к таблице нет.

#### Шаг 6. Обновили строки — Index Only Scan снова читает таблицу

```sql
UPDATE orders_big SET status = status WHERE customer_id = 42;
-- повторить EXPLAIN
```

```text
->  Index Only Scan using idx_ob_cc_incl on orders_big
      Heap Fetches: 40
      Buffers: shared hit=44
```

<details>
<summary>Разбор</summary>

Узел по-прежнему называется `Index Only Scan`, но `Heap Fetches: 40`, а буферов в 10 раз больше. `UPDATE` создал новые версии строк, и их страницы больше не отмечены как all-visible в visibility map. После `VACUUM orders_big` снова `Heap Fetches: 0`.

Выводы:

1. Название узла не гарантирует, что таблица не читается — смотрите `Heap Fetches`.
2. Для часто обновляемых таблиц выгода от покрывающего индекса может быть небольшой.
3. Каждый следующий шаг — это компромисс: индекс шага 5 больше и дороже в поддержке, чем индекс шага 3. Выигрыш от него стоит проверять на реальной нагрузке.

</details>

## 4. Транзакции, ACID и MVCC

### 4.1. ACID

`[ ]` **Короткий ответ:** транзакция — группа операций, которая выполняется как единое целое. ACID — свойства, делающие её надёжной: атомарность, согласованность, изолированность, долговечность.

| Свойство | Суть | Чем обеспечивается (на примере PostgreSQL) |
|---|---|---|
| **Atomicity** — атомарность | Транзакция фиксируется целиком или не фиксируется вовсе | `COMMIT` / `ROLLBACK`, журнал WAL |
| **Consistency** — согласованность | Транзакция переводит базу из одного корректного состояния в другое, не нарушая ограничений | `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK`, а также логика приложения |
| **Isolation** — изолированность | Определяет, какие эффекты параллельных транзакций видны друг другу | Уровни изоляции, MVCC, блокировки |
| **Durability** — долговечность | После подтверждения `COMMIT` изменения переживут сбой | WAL, `fsync`, репликация |

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;  -- либо оба изменения, либо ни одного
```

> Буква **C** в ACID и **C** в теореме CAP — разные понятия. В ACID это соблюдение инвариантов и ограничений, в CAP — линеаризуемость чтений в распределённой системе.

<details>
<summary>Уточнение: можно ли ослабить Durability ради скорости?</summary>

Да. Например, `synchronous_commit = off` подтверждает `COMMIT` до записи WAL на диск: при сбое можно потерять последние подтверждённые транзакции, но целостность базы не нарушится. Это осознанный компромисс для некритичных данных.

</details>

### 4.2. MVCC, VACUUM и ANALYZE

`[ ]` **Короткий ответ:** MVCC (многоверсионность) — `UPDATE` создаёт новую версию строки вместо перезаписи старой. Каждая транзакция читает снимок данных, поэтому читатели не блокируют писателей, а писатели — читателей. Цена — накопление старых версий, которые убирает `VACUUM`.

<details>
<summary>Подробности</summary>

- **Мёртвые версии строк (dead tuples)** — старые версии, которые не видит уже ни одна транзакция. Они занимают место, пока их не очистит `VACUUM`.
- **Autovacuum** запускает `VACUUM` и `ANALYZE` автоматически по порогам изменений. Его не отключают, а настраивают.
- **`VACUUM`** освобождает место для повторного использования внутри таблицы и обновляет visibility map. Размер файла он обычно не уменьшает.
- **`VACUUM FULL`** переписывает таблицу целиком и возвращает место ОС, но берёт эксклюзивную блокировку — таблица недоступна на время работы.
- **`ANALYZE`** собирает статистику распределения значений, на которую опирается планировщик.
- **Долгая транзакция мешает очистке**: пока она открыта, версии строк, которые могли бы ей понадобиться, нельзя удалить. Отсюда раздувание таблиц (bloat) — ещё одна причина держать транзакции короткими.
- `UPDATE` в PostgreSQL обходится дороже, чем кажется: это фактически вставка новой версии + обновление индексов. Исключение — HOT-update: если не меняются индексируемые колонки и на странице есть место, индексы не обновляются.

</details>

**Чего MVCC не решает:** потерянное обновление в схеме «прочитать → посчитать в коде → записать» и write skew. Для них нужны подходящий уровень изоляции, блокировки или ограничения.

## 5. Аномалии и уровни изоляции

### 5.1. Аномалии параллельного доступа

Шпаргалка — подробные воспроизводимые сценарии в [разделе 6](#65-лабораторные-две-сессии).

| Аномалия | Что происходит | Пример |
|---|---|---|
| **Грязное чтение** (dirty read) | Чтение незафиксированных изменений, которые потом откатятся | Т1 пишет 200, Т2 читает 200, Т1 делает `ROLLBACK` |
| **Неповторяющееся чтение** (non-repeatable read) | Повторное чтение той же строки даёт другое значение | Т1 читает 100, Т2 меняет на 150 и коммитит, Т1 читает 150 |
| **Фантомное чтение** (phantom read) | Повторный запрос по условию возвращает другой набор строк | `count(*) WHERE balance > 50` дал 1, после вставки другой транзакцией — 2 |
| **Потерянное обновление** (lost update) | Два «прочитать → изменить → записать» затирают друг друга | Оба прочитали 100, записали 120 и 125, итог 125 вместо 145 |
| **Аномалия сериализации** (write skew) | Каждая транзакция корректна сама по себе, но вместе они дают результат, невозможный ни при каком последовательном порядке | Два врача одновременно уходят с дежурства, видя, что дежурят двое |

Отличие неповторяющегося чтения от фантомного: в первом меняется значение существующей строки, во втором — состав выборки.

### 5.2. Уровни изоляции в PostgreSQL

`[ ]` **Короткий ответ:** по умолчанию — `READ COMMITTED`: каждый запрос видит данные, зафиксированные на момент **его** начала. `REPEATABLE READ` — вся транзакция видит один снимок. `SERIALIZABLE` — результат эквивалентен некоторому последовательному выполнению; ценой могут быть ошибки сериализации, после которых транзакцию нужно повторить.

Стандарт SQL-92 задаёт четыре уровня, но описывает только допустимые аномалии, а не алгоритмы: разные СУБД реализуют уровни по-разному.

| Уровень | Dirty read | Non-repeatable read | Phantom read | Serialization anomaly |
|---|---|---|---|---|
| Read uncommitted | Нет* | Да | Да | Да |
| **Read committed** (по умолчанию) | Нет | Да | Да | Да |
| Repeatable read | Нет | Нет | Нет* | Да |
| Serializable | Нет | Нет | Нет | Нет |

\* Стандарт допускает эту аномалию на данном уровне, но PostgreSQL её не допускает.

<details>
<summary>Подробности по каждому уровню</summary>

- **Read uncommitted** в PostgreSQL ведёт себя как `READ COMMITTED`.
- **Read committed.** Каждый запрос получает свой снимок. Если `UPDATE`, `DELETE` или `SELECT ... FOR UPDATE` натыкаются на строку, изменённую ещё не завершённой транзакцией, они **ждут** её завершения. Если та зафиксировала изменение, операция применяется к **новой** версии строки, а условие `WHERE` перепроверяется на ней. Поэтому `SET balance = balance + 20` в двух параллельных транзакциях даёт корректный результат.
- **Repeatable read.** Снимок берётся при первом запросе транзакции. Если транзакция пытается изменить строку, которую после начала её снимка изменила и зафиксировала другая транзакция, она получает `ERROR: could not serialize access due to concurrent update` (`SQLSTATE 40001`). Транзакцию нужно повторить целиком.
- **Serializable.** Дополнительно отслеживает зависимости чтения и записи между транзакциями (SSI) и отменяет одну из них при опасной комбинации: `could not serialize access due to read/write dependencies among transactions`. Приложение **обязано** уметь повторять транзакции.

</details>

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ...
COMMIT;  -- может завершиться ошибкой SQLSTATE 40001: нужно повторить транзакцию
```

> Более высокий уровень изоляции — не замена ограничениям. `UNIQUE`, `FOREIGN KEY`, `SELECT ... FOR UPDATE` и явные блокировки решают свои задачи.

**Уточнения интервьюера:**

<details>
<summary>Почему бы не включить SERIALIZABLE везде?</summary>

Можно, и это упрощает рассуждения о корректности. Но: появляются ошибки сериализации, и каждая транзакция должна быть готова к повтору; растут накладные расходы на отслеживание зависимостей; при высокой конкуренции за одни данные часть работы будет выполняться повторно. Часто выбирают `READ COMMITTED` + точечные блокировки и ограничения там, где они нужны.

</details>

<details>
<summary>Что делать приложению при ошибке сериализации (SQLSTATE 40001)?</summary>

Повторить транзакцию **целиком**, с начала, ограничив число попыток и добавив небольшую случайную паузу. Повторяемая операция должна быть идемпотентной, а внешние побочные эффекты — письма, вызовы внешних API — выполняться только после успешного `COMMIT`.

</details>

## 6. Конкурентные изменения и блокировки

### 6.1. Способы защиты от потерянного обновления

`[ ]` **Короткий ответ:** не вычислять новое значение в приложении, а выразить изменение одним атомарным `UPDATE`. Если так нельзя — заблокировать строку (`FOR UPDATE`), проверять версию (оптимистическая блокировка) или использовать `REPEATABLE READ` / `SERIALIZABLE` с повтором.

| Способ | Как работает | Результат в лабораторной 1 |
|---|---|---|
| Атомарный `UPDATE ... SET x = x + ?` | В `READ COMMITTED` вторая транзакция ждёт и применяет изменение к новой версии строки | 145 |
| `SELECT ... FOR UPDATE` | Вторая транзакция ждёт на чтении и затем видит уже обновлённое значение | 145 |
| Оптимистическая блокировка (`version`) | Вторая запись обновляет 0 строк — приложение узнаёт о конфликте | 120 + сигнал о конфликте |
| `REPEATABLE READ` / `SERIALIZABLE` | Вторая запись получает ошибку `40001` | 120 + ошибка, нужен повтор |

### 6.2. Оптимистическая и пессимистическая блокировка

| | Оптимистическая | Пессимистическая |
|---|---|---|
| Идея | Конфликты редки — проверим при записи | Конфликты часты — заблокируем заранее |
| Механизм | Колонка версии (`@Version` в JPA) | `SELECT ... FOR UPDATE` |
| Когда конфликт виден | При `UPDATE`: версия не совпала → 0 изменённых строк | Вторая транзакция ждёт освобождения блокировки |
| Минусы | Нужно обрабатывать конфликт: повторить или вернуть ошибку | Ожидание, риск deadlock, хуже параллелизм |
| Когда выбирать | Редкие конфликты, важен параллелизм: редактирование карточки товара | Частые конфликты, повтор дорогой: списание остатков горячего товара |

```sql
-- Оптимистическая
UPDATE accounts
SET balance = 120, version = version + 1
WHERE id = 1 AND version = 7;
-- 0 строк обновлено → кто-то изменил запись раньше

-- Пессимистическая
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- строка заблокирована до конца транзакции
UPDATE accounts SET balance = 120 WHERE id = 1;
COMMIT;
```

Полезные варианты:

- `FOR UPDATE NOWAIT` — сразу ошибка, если строка занята;
- `FOR UPDATE SKIP LOCKED` — пропустить занятые строки; удобно для очередей задач;
- `FOR NO KEY UPDATE` / `FOR SHARE` / `FOR KEY SHARE` — более слабые режимы, которые меньше конфликтуют между собой.

### 6.3. Очередь задач на PostgreSQL

```sql
-- Несколько обработчиков параллельно берут разные задачи, не мешая друг другу
BEGIN;
SELECT id, payload
FROM jobs
WHERE status = 'READY'
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;

-- ... обработка ...

UPDATE jobs SET status = 'DONE' WHERE id = ANY(:ids);
COMMIT;
```

Если обработка долгая, лучше не держать транзакцию открытой: пометить задачи как `IN_PROGRESS` с временем захвата, зафиксировать и обработать вне транзакции. Задачи, «зависшие» дольше таймаута, возвращать в очередь.

### 6.4. Практические правила

- Не держите транзакцию открытой во время сетевого вызова или действий пользователя.
- Блокируйте ресурсы в одинаковом порядке — например, по возрастанию `id`, — чтобы избежать deadlock.
- Обрабатывайте deadlock (`40P01`) и ошибки сериализации (`40001`) ограниченным числом повторов; повторяемая операция должна быть идемпотентной.
- Задайте `lock_timeout` и `statement_timeout` для миграций и фоновых задач, чтобы они не висели бесконечно в ожидании блокировки.

### 6.5. Лабораторные: две сессии

Откройте два терминала с `psql` — это сессии **A** и **B**. Выполняйте шаги строго по номерам. Все результаты ниже проверены на PostgreSQL 18.6.

Общая подготовка:

```sql
DROP TABLE IF EXISTS accounts;
CREATE TABLE accounts (
    id      int PRIMARY KEY,
    balance int NOT NULL,
    version int NOT NULL DEFAULT 0
);
INSERT INTO accounts (id, balance) VALUES (1, 100), (2, 100);
```

Перед каждой лабораторной выполняйте подготовку заново.

#### Лабораторная 1. Потерянное обновление

**Цель:** увидеть, как теряется пополнение, и проверить четыре способа защиты.

**Вариант А. Ошибка: прочитать → посчитать в коде → записать.**

| Шаг | Сессия A | Сессия B |
|---|---|---|
| 1 | `BEGIN;` | |
| 2 | | `BEGIN;` |
| 3 | `SELECT balance FROM accounts WHERE id = 1;` → 100 | |
| 4 | | `SELECT balance FROM accounts WHERE id = 1;` → 100 |
| 5 | `UPDATE accounts SET balance = 120 WHERE id = 1;` | |
| 6 | `COMMIT;` | |
| 7 | | `UPDATE accounts SET balance = 125 WHERE id = 1;` |
| 8 | | `COMMIT;` |

**Ожидаемый результат:** `balance = 125` вместо 145. Пополнение на 20 потеряно.

**Вариант Б. Атомарный UPDATE.**

| Шаг | Сессия A | Сессия B |
|---|---|---|
| 1 | `BEGIN;` | `BEGIN;` |
| 2 | `UPDATE accounts SET balance = balance + 20 WHERE id = 1;` | |
| 3 | | `UPDATE accounts SET balance = balance + 25 WHERE id = 1;` — **ждёт** A |
| 4 | `COMMIT;` | |
| 5 | | Шаг 3 завершается; `COMMIT;` |

**Ожидаемый результат:** 145. Сессия B дождалась фиксации A и применила `+ 25` к новой версии строки.

**Вариант В. FOR UPDATE.** Как вариант А, но на шагах 3 и 4 — `SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;`.

**Ожидаемое поведение:** шаг 4 зависает, пока сессия A выполняет шаги 5–6, и после её `COMMIT` возвращает **120**. Приложение считает 120 + 25 и на шаге 7 пишет 145.

**Вариант Г. REPEATABLE READ.** Как вариант А, но `BEGIN ISOLATION LEVEL REPEATABLE READ;`.

**Ожидаемое поведение:** шаг 7 завершается ошибкой:

```text
ERROR:  could not serialize access due to concurrent update
```

Итог — 120. Сессия B должна выполнить `ROLLBACK` и повторить транзакцию целиком — тогда она прочитает 120 и запишет 145.

**Вопрос для самопроверки:** почему в варианте Г ошибка появляется на `UPDATE`, а не на `SELECT`?

<details>
<summary>Ответ</summary>

Чтение из снимка конфликтом не является: B законно видит снимок, где баланс равен 100. Конфликт возникает, когда B пытается изменить строку, у которой уже есть более новая зафиксированная версия, невидимая её снимку.

</details>

#### Лабораторная 2. Оптимистическая блокировка

| Шаг | Сессия A | Сессия B |
|---|---|---|
| 1 | `SELECT balance, version FROM accounts WHERE id = 1;` → 100, 0 | |
| 2 | | `SELECT balance, version FROM accounts WHERE id = 1;` → 100, 0 |
| 3 | `UPDATE accounts SET balance = 120, version = version + 1 WHERE id = 1 AND version = 0;` → `UPDATE 1` | |
| 4 | | `UPDATE accounts SET balance = 125, version = version + 1 WHERE id = 1 AND version = 0;` → `UPDATE 0` |

**Ожидаемый результат:** `balance = 120, version = 1`. Сессия B получила `UPDATE 0` — сигнал о конфликте. Приложение должно перечитать строку и повторить операцию или сообщить пользователю.

Здесь транзакции не держатся открытыми между чтением и записью — поэтому подход подходит для сценариев «пользователь открыл форму и через минуту нажал “Сохранить”».

#### Лабораторная 3. Deadlock

**Цель:** увидеть взаимную блокировку при разном порядке захвата строк.

| Шаг | Сессия A | Сессия B |
|---|---|---|
| 1 | `BEGIN;` | `BEGIN;` |
| 2 | `UPDATE accounts SET balance = balance - 10 WHERE id = 1;` | |
| 3 | | `UPDATE accounts SET balance = balance - 10 WHERE id = 2;` |
| 4 | `UPDATE accounts SET balance = balance + 10 WHERE id = 2;` — **ждёт** B | |
| 5 | | `UPDATE accounts SET balance = balance + 10 WHERE id = 1;` — ждёт A → цикл |

**Ожидаемое поведение:** примерно через секунду (`deadlock_timeout`) PostgreSQL обнаруживает цикл и отменяет одну из транзакций:

```text
ERROR:  deadlock detected
DETAIL:  Process 3570 waits for ShareLock on transaction 779; blocked by process 3571.
         Process 3571 waits for ShareLock on transaction 778; blocked by process 3570.
```

Код ошибки — `40P01`. Вторая транзакция продолжает работу и может зафиксироваться.

**Исправление:** всегда обновлять строки в одном порядке. Например, при переводе между счетами сначала блокировать меньший `id`:

```sql
SELECT id FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
```

Повторите лабораторную, где обе сессии сначала выполняют этот запрос: вторая просто дождётся первой, без deadlock.

#### Лабораторная 4. Write skew: врачи на дежурстве

**Правило:** на дежурстве должен остаться хотя бы один врач. Сейчас дежурят двое.

```sql
DROP TABLE IF EXISTS doctors;
CREATE TABLE doctors (name text PRIMARY KEY, on_call boolean NOT NULL);
INSERT INTO doctors VALUES ('A', true), ('B', true);
```

| Шаг | Сессия A (врач A) | Сессия B (врач B) |
|---|---|---|
| 1 | `BEGIN ISOLATION LEVEL REPEATABLE READ;` | `BEGIN ISOLATION LEVEL REPEATABLE READ;` |
| 2 | `SELECT count(*) FROM doctors WHERE on_call;` → 2 | |
| 3 | | `SELECT count(*) FROM doctors WHERE on_call;` → 2 |
| 4 | `UPDATE doctors SET on_call = false WHERE name = 'A';` | |
| 5 | | `UPDATE doctors SET on_call = false WHERE name = 'B';` |
| 6 | `COMMIT;` | |
| 7 | | `COMMIT;` |

**Ожидаемый результат на REPEATABLE READ:** оба `COMMIT` успешны, дежурных — **0**. Транзакции меняли **разные** строки, поэтому конфликта записи нет.

**Повторите с `SERIALIZABLE`:** шаг 7 завершится ошибкой

```text
ERROR:  could not serialize access due to read/write dependencies among transactions
```

Итог: A — `false`, B — `true`. Правило соблюдено.

**Альтернатива без SERIALIZABLE** — заблокировать строки, на которых основано решение, в `READ COMMITTED`:

```sql
SELECT name FROM doctors WHERE on_call FOR UPDATE;  -- FOR UPDATE нельзя сочетать с count(*): считаем строки в приложении
```

Сессия B на этом запросе ждёт, пока A не выполнит `COMMIT`, а затем получает **одну** строку — `B`. Приложение видит, что дежурный остался один, и отказывает в уходе.

**Вопрос для самопроверки:** а если правило «хотя бы один» проверяет условие, под которое пока не подходит ни одна строка — например, «не больше одного бронирования на интервал»?

<details>
<summary>Ответ</summary>

`FOR UPDATE` блокирует только существующие строки — заблокировать ещё не вставленную строку нельзя. Варианты: `SERIALIZABLE`; ограничение, которое гарантирует правило на уровне базы, — например, `EXCLUDE USING gist` для непересекающихся интервалов; блокировка «родительской» строки, например ресурса бронирования; advisory lock.

</details>

## 7. Нормализация и денормализация

`[ ]` **Короткий ответ:** нормализация устраняет избыточные зависимости между атрибутами, чтобы один факт хранился в одном месте. Это защищает от аномалий вставки, обновления и удаления. 1НФ — атомарные значения; 2НФ — нет зависимости от части ключа; 3НФ — нет транзитивных зависимостей.

Термины:

- **Функциональная зависимость** `X → Y` — значение `X` однозначно определяет значение `Y`.
- **Кандидатный ключ** — минимальный набор атрибутов, однозначно определяющий строку.
- **Ключевой атрибут** — атрибут, входящий хотя бы в один кандидатный ключ.

### 7.1. Первая нормальная форма (1НФ)

Значения атрибутов атомарны в контексте предметной области, повторяющиеся группы не хранятся в одной ячейке.

**Было:** нарушение — в одной ячейке список моделей:

| Фирма | Модели |
|---|---|
| BMW | M5, X5M, M1 |
| Nissan | GT-R |

**Стало:**

| Фирма | Модель |
|---|---|
| BMW | M5 |
| BMW | X5M |
| BMW | M1 |
| Nissan | GT-R |

> «Атомарность» зависит от задачи. JSON-колонка сама по себе не нарушает SQL-модель, но может скрывать элементы, которые нужно искать, индексировать или ограничивать отдельно.

### 7.2. Вторая нормальная форма (2НФ)

Отношение в 1НФ, и каждый неключевой атрибут зависит от **всего** кандидатного ключа, а не от его части. Актуально прежде всего для составных ключей.

Ключ — `(Фирма, Модель)`: модель уникальна только внутри фирмы.

**Было:** нарушение — скидка зависит только от фирмы, то есть от части ключа:

| Фирма | Модель | Цена | Скидка |
|---|---|---|---|
| BMW | M5 | 123 | 5% |
| BMW | X5M | 3213 | 5% |
| BMW | M1 | 12312 | 5% |
| Nissan | GT-R | 12323 | 10% |

Чем плохо: чтобы изменить скидку BMW, нужно обновить три строки; пропустив одну, получим противоречие.

**Стало:** скидка вынесена в отдельное отношение:

| Фирма | Модель | Цена |
|---|---|---|
| BMW | M5 | 123 |
| BMW | X5M | 3213 |
| BMW | M1 | 12312 |
| Nissan | GT-R | 12323 |

| Фирма | Скидка |
|---|---|
| BMW | 5% |
| Nissan | 10% |

### 7.3. Третья нормальная форма (3НФ)

Отношение во 2НФ, и неключевые атрибуты не зависят от ключа **транзитивно** — через другой неключевой атрибут.

Формально: для каждой нетривиальной зависимости `X → A` либо `X` — суперключ, либо `A` — ключевой атрибут.

**Было:** нарушение — ключ `Модель`, телефон зависит от магазина, а не от модели:

| Модель | Магазин | Телефон |
|---|---|---|
| M5 | Риал-авто | 87-33-98 |
| X5M | Риал-авто | 87-33-98 |
| GT-R | Некст-Авто | 94-54-12 |

Зависимости: `Модель → Магазин`, `Магазин → Телефон`, следовательно `Модель → Телефон` — транзитивная.

**Стало:**

| Модель | Магазин |
|---|---|
| M5 | Риал-авто |
| X5M | Риал-авто |
| GT-R | Некст-Авто |

| Магазин | Телефон |
|---|---|
| Риал-авто | 87-33-98 |
| Некст-Авто | 94-54-12 |

### 7.4. НФБК и дальше

- **Нормальная форма Бойса — Кодда (НФБК)** — строже 3НФ: для каждой нетривиальной зависимости `X → A` левая часть `X` должна быть суперключом. Различие с 3НФ проявляется, когда есть несколько пересекающихся составных кандидатных ключей.
- 4НФ и 5НФ касаются многозначных зависимостей и зависимостей соединения; на практике встречаются редко.

### 7.5. Денормализация

Схему иногда сознательно денормализуют: хранят готовые агрегаты, копии полей для быстрых чтений, материализованные представления. Это компромисс: чтение быстрее, но нужно поддерживать согласованность копий.

Пример в учебной схеме — `orders.total`. Задача 3 из [раздела 1](#задача-3-проверка-денормализованных-данных) показывает, как такие копии расходятся.

Денормализуйте осознанно и после измерений, а не заранее. Для каждой копии ответьте:

1. Где источник истины?
2. Кто и в какой транзакции обновляет копию?
3. Как обнаружить и исправить расхождение?

**Уточнение интервьюера:** «Нормализовали до 3НФ, а отчёт стал медленным из-за десятка join. Что делать?»

<details>
<summary>Ответ</summary>

Сначала посмотреть план: часто проблема не в количестве join, а в отсутствии индексов или неверных оценках. Затем, по нарастанию сложности: индексы под запрос; материализованное представление с регулярным `REFRESH MATERIALIZED VIEW CONCURRENTLY`; отдельная таблица-агрегат, обновляемая по событиям; вынос аналитики в OLAP-хранилище. OLTP-схему не стоит ломать ради отчёта.

</details>

## 8. ORM и проблема N+1

`[ ]` **Короткий ответ:** N+1 — один запрос за списком сущностей и ещё по одному на каждую связанную сущность. Обнаруживают по логам SQL или счётчику запросов в тестах. Решают загрузкой связей одним или несколькими запросами: DTO-проекция, `JOIN FETCH`, `@EntityGraph`, batch fetching.

```java
List<Order> orders = orderRepository.findAll();      // 1 запрос
for (Order order : orders) {
    order.getCustomer().getName();                    // + N запросов
}
```

`FetchType.LAZY` не устраняет проблему: он лишь откладывает загрузку до первого обращения.

| Способ | Когда подходит |
|---|---|
| DTO / projection | Нужны только отдельные поля, а не сущности целиком |
| `JOIN FETCH` | Нужна связь `to-one` или небольшая `to-many` без пагинации |
| `@EntityGraph` | То же, но декларативно, без переписывания JPQL |
| Batch fetching (`@BatchSize`, `hibernate.default_batch_fetch_size`) | Коллекции + пагинация: вместо N запросов — несколько запросов с `IN (...)` |

```java
@Query("select o from Order o join fetch o.customer where o.status = :status")
List<Order> findWithCustomerByStatus(@Param("status") OrderStatus status);
```

Подводные камни:

- `JOIN FETCH` для `to-many` размножает строки, а вместе с пагинацией Hibernate может выполнить её в памяти (предупреждение `HHH90003004` в Hibernate 6 / `HHH000104` в Hibernate 5).
- Два `JOIN FETCH` по разным коллекциям дают декартово произведение строк; для `List` Hibernate выбросит `MultipleBagFetchException`.
- Один гигантский join может оказаться хуже нескольких ограниченных запросов.
- Не загружайте весь граф объектов «на всякий случай».

Как обнаружить: логирование SQL (`spring.jpa.show-sql`, `org.hibernate.SQL`), статистика Hibernate (`hibernate.generate_statistics`), подсчёт запросов в интеграционных тестах.

<details>
<summary>Как N+1 выглядит на стороне базы?</summary>

Множество одинаковых коротких запросов, отличающихся только параметром: `SELECT ... FROM customers WHERE id = $1`. В `pg_stat_statements` у такого запроса огромное число вызовов при маленьком среднем времени. По отдельности каждый запрос быстрый — тормозит их количество и сетевые задержки.

</details>

## 9. Выбор хранилища

`[ ]` **Короткий ответ:** реляционная СУБД — разумный вариант по умолчанию, когда нужны связанные данные, ограничения целостности, произвольные запросы и транзакции. Специализированное хранилище оправдано, когда модель доступа и требования к масштабу явно совпадают с его сильными сторонами, а стоимость эксплуатации ещё одной системы приемлема.

Выбор не сводится к правилу «структурированные данные — SQL, неструктурированные — NoSQL». Многие NoSQL-хранилища имеют схему, индексы и транзакции, а реляционные СУБД умеют работать с JSON, массивами и полнотекстовым поиском.

| Вопрос | Почему важно |
|---|---|
| Как данные читаются и пишутся? | Модель доступа — по ключу, по диапазону, агрегаты, обход связей — определяет подходящий тип хранилища |
| Какая нужна консистентность? | Деньги и остатки требуют строгих гарантий, лента просмотров — обычно нет |
| Какие объём и нагрузка? | Влияют на необходимость шардирования, колоночного хранения, кэша |
| Нужны ли ad-hoc запросы? | Key-value и wide-column плохо подходят для запросов, не предусмотренных схемой |
| Сколько стоит эксплуатация? | Каждая дополнительная СУБД — это бэкапы, мониторинг, обновления и экспертиза команды |

> NoSQL уместна, когда модель доступа и требования к масштабированию хорошо совпадают с конкретным типом хранилища. Сама по себе она не гарантирует низкую latency, горизонтальное масштабирование или отсутствие связей в данных.

Подробная классификация с примерами продуктов — в [приложении](#приложение-классы-баз-данных).

### 9.1. Масштабирование: короткие ответы

<details>
<summary>Репликация: что даёт и чего не даёт?</summary>

Реплики масштабируют **чтение** и повышают доступность. Запись по-прежнему идёт на один primary. При асинхронной репликации реплика отстаёт: пользователь может не увидеть своё только что сделанное изменение (read-your-writes). Решения: читать критичные данные с primary, синхронная репликация ценой задержки записи, привязка сессии к primary после записи.

</details>

<details>
<summary>Партиционирование и шардирование — в чём разница?</summary>

**Партиционирование** — деление одной таблицы на части внутри одного сервера, например по месяцам. Помогает отсекать ненужные партиции в запросах и быстро удалять старые данные (`DROP` / `DETACH PARTITION` вместо `DELETE`). **Шардирование** — распределение данных по разным серверам. Масштабирует запись, но усложняет межшардовые запросы, транзакции и перебалансировку. Ключ шардирования выбирают так, чтобы типичный запрос попадал в один шард.

</details>

<details>
<summary>Что такое CAP и PACELC в одном абзаце?</summary>

CAP: при сетевом разделении (P) распределённая система вынуждена выбирать между консистентностью (C, линеаризуемость) и доступностью (A). PACELC дополняет: а без разделения (Else) приходится выбирать между задержкой (L) и консистентностью (C). Практический смысл: строгая согласованность в распределённой системе всегда стоит задержки или доступности.

</details>

## 10. Пробное собеседование

Сценарии без единственного правильного ответа. Сначала проговорите решение вслух за 3–5 минут, потом сверьтесь.

<details>
<summary>1. Страница «Мои заказы» стала открываться за 5 секунд. Ваши действия?</summary>

1. Найти медленный запрос: логи приложения, `pg_stat_statements`, `log_min_duration_statement`.
2. Проверить, не N+1 ли это: много мелких запросов или один тяжёлый.
3. Снять `EXPLAIN (ANALYZE, BUFFERS)` на реальных данных.
4. Найти, где время: `Seq Scan` с большим `Rows Removed by Filter`, `Sort` на диске, неверные оценки строк.
5. Предложить исправление: составной индекс `(customer_id, created_at)`, keyset-пагинацию вместо `OFFSET`, выборку только нужных колонок.
6. Измерить снова и проверить влияние нового индекса на запись.

См. [3.6](#36-разбор-explain-от-медленного-запроса-к-быстрому).

</details>

<details>
<summary>2. Пользователь дважды нажал «Оплатить», деньги списались дважды. Как предотвратить?</summary>

- Ключ идемпотентности: клиент генерирует `idempotency_key`, в таблице платежей на нём `UNIQUE`.
- Вставка через `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING`; если строка не вставилась — вернуть результат первой попытки.
- Списание с баланса — атомарным `UPDATE ... SET balance = balance - :amount WHERE id = :id AND balance >= :amount`, проверяя число изменённых строк.
- Вызов внешней платёжной системы — вне транзакции БД, с тем же ключом идемпотентности.

</details>

<details>
<summary>3. Нужно добавить колонку и индекс в таблицу на 500 млн строк без простоя.</summary>

- `ALTER TABLE ... ADD COLUMN` без значения по умолчанию или с константным значением по умолчанию в PostgreSQL 11+ не переписывает таблицу — меняются только метаданные. Но команда всё равно берёт эксклюзивную блокировку на короткое время: задайте `lock_timeout`, чтобы не встать в очередь за долгой транзакцией и не заблокировать всех остальных.
- Индекс — `CREATE INDEX CONCURRENTLY`, затем проверить, что он не остался в состоянии `INVALID`.
- Заполнение значений для существующих строк — батчами, а не одним `UPDATE` на всю таблицу: так меньше блокировок, нагрузки на WAL и bloat.
- `NOT NULL` на большой таблице — через `CHECK (col IS NOT NULL) NOT VALID`, затем `VALIDATE CONSTRAINT`, который не блокирует запись. После этого `SET NOT NULL` (PostgreSQL 12+) использует проверенное ограничение и не сканирует таблицу повторно.

</details>

<details>
<summary>4. На складе продают последний товар двум покупателям одновременно.</summary>

- Атомарное условное списание: `UPDATE stock SET qty = qty - 1 WHERE product_id = :id AND qty >= 1` и проверка `UPDATE 1` / `UPDATE 0`.
- Ограничение `CHECK (qty >= 0)` как страховка.
- Если логика сложнее одного `UPDATE` — `SELECT ... FOR UPDATE` строки товара.
- Для очень горячих товаров — резервирование с таймаутом или разбиение остатка на несколько строк-«ячеек», чтобы уменьшить конкуренцию за одну строку.

</details>

<details>
<summary>5. Аналитики запускают тяжёлые отчёты, и основное приложение тормозит.</summary>

- Краткосрочно: перевести отчёты на реплику, ограничить `statement_timeout` для их роли.
- Учитывать, что долгие запросы на реплике могут конфликтовать с применением изменений с primary (`hot_standby_feedback`, `max_standby_streaming_delay`).
- Долгосрочно: материализованные представления или вынос данных в OLAP-хранилище (ClickHouse и т. п.) через CDC или ETL.

</details>

<details>
<summary>6. Таблица растёт на диске, хотя число строк почти не меняется.</summary>

Признак bloat: много мёртвых версий строк, которые не успевают очищаться. Проверить `pg_stat_user_tables` (`n_dead_tup`, `last_autovacuum`), найти долгие транзакции в `pg_stat_activity` — особенно в состоянии `idle in transaction`. Решения: завершить зависшие транзакции, настроить autovacuum для этой таблицы агрессивнее. Чтобы вернуть место ОС — `VACUUM FULL` (с эксклюзивной блокировкой) или расширение `pg_repack`.

</details>

## Приложение: классы баз данных

Справочный материал: на собеседовании обычно достаточно понимать оси классификации и уметь привести пару примеров.

Один и тот же продукт может попадать в несколько групп: например, ClickHouse — это и OLAP-система, и колоночное хранилище. Поэтому классификацию удобнее читать по осям.

### А.1. По характеру нагрузки

| Класс | Назначение | Типичные свойства | Примеры |
|---|---|---|---|
| **OLTP** (OnLine Transaction Processing) | Много коротких транзакций в реальном времени | Построчное хранение, индексы, точечные чтения и записи | PostgreSQL, MySQL, Oracle, Microsoft SQL Server |
| **OLAP** (OnLine Analytical Processing) | Агрегация и анализ больших объёмов, часто исторических данных | Ориентация на чтение, колоночное хранение, кластер | ClickHouse, Greenplum, Apache Hive, Apache Druid |
| **HTAP** (Hybrid Transactional/Analytical Processing) | Транзакции и аналитика над актуальными данными в одной системе | Аналитика может конкурировать за ресурсы с OLTP | SAP HANA, SingleStore, TiDB |

HTAP не означает одинаково высокую производительность для обоих типов запросов. Возможности зависят от редакции и версии продукта.

### А.2. По модели данных (NoSQL)

| Модель | Как устроены данные | Когда подходит | Ограничения | Примеры |
|---|---|---|---|---|
| **Key-Value** | Значение по ключу | Кэш, сессии, счётчики, доступ строго по ключу | Запросы вне ключа ограничены; транзакционные гарантии зависят от продукта | Redis, Memcached, Amazon DynamoDB |
| **Документная** | JSON/BSON-документы | Агрегат читается и пишется целиком, схема меняется часто | Связи между документами и транзакции между ними — дороже | MongoDB, CouchDB, Couchbase |
| **Wide-column** | Строки по ключу с разреженным набором колонок, сгруппированных в семейства | Огромные объёмы записи, запросы известны заранее | Таблицы проектируются под запросы; join и произвольные фильтры ограничены | Apache Cassandra, ScyllaDB, Apache HBase |
| **Графовая** | Узлы и рёбра с атрибутами | Глубокий обход связей: рекомендации, антифрод, социальные графы | При простых связях хватит реляционной СУБД | Neo4j, Amazon Neptune, ArangoDB, JanusGraph |

> Не путайте **wide-column** (Cassandra, HBase) и **колоночное хранение** (ClickHouse). В первом случае это модель данных, во втором — способ физически хранить значения одной колонки рядом для быстрых агрегатов.

### А.3. Распределённые SQL / NewSQL

Нестрого стандартизированный термин для систем, сочетающих SQL и транзакции с распределённым хранением.

- **Google Spanner** — глобально распределённая SQL-СУБД; TrueTime помогает поддерживать строгие временные гарантии.
- **CockroachDB** — совместима с протоколом PostgreSQL, но совместимость не означает полного совпадения возможностей.
- **TiDB** — MySQL-совместимая распределённая СУБД.
- **YugabyteDB** — распределённая СУБД с PostgreSQL-совместимым API.

Оговорки:

- Горизонтальное масштабирование не даёт бесплатной линейной производительности: межузловые транзакции добавляют координацию и задержку.
- **Vitess** — слой шардирования и маршрутизации для MySQL, а не самостоятельная СУБД.
- **Amazon Aurora** — облачная реляционная СУБД с разделением compute и storage, а не автоматически шардированная NewSQL-система.
- **Azure Cosmos DB** поддерживает несколько API и моделей консистентности, но SQL-подобный API не делает её реляционной.

### А.4. Специализированные хранилища

**Time-Series DB (TSDB)** — хранят временные ряды «метка времени — значение»: метрики, показания датчиков, котировки. Оптимизированы под поток записи, сжатие с учётом временной корреляции, агрегацию по окнам, append-only-нагрузку и автоматическое удаление старых данных (retention). Примеры: Prometheus (мониторинг со встроенной TSDB, PromQL), VictoriaMetrics, InfluxDB, TimescaleDB (расширение PostgreSQL).

**Другие классы:**

- **Vector DB** — поиск по близости embedding-векторов (семантический поиск, RAG). Качество зависит от embedding-модели, метрики и индекса; векторный поиск не равен пониманию смысла. Примеры: Qdrant, Milvus, pgvector.
- **In-Memory DB** — данные в оперативной памяти; многие поддерживают persistence на диск. Примеры: Redis, Tarantool.
- **Search Engine** — полнотекстовый поиск, ранжирование, фасеты. Обычно вторичный индекс, а не источник истины. Примеры: Elasticsearch, OpenSearch.
- **Event Store** — хранит доменные события для Event Sourcing: порядок, версии потоков, идемпотентность. Kafka — платформа потоковой передачи событий; она может быть частью event-driven-системы, но не заменяет автоматически доменное хранилище событий.
