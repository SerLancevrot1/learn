# Базы данных

## Реляционные и нереляционные хранилища

Реляционная СУБД подходит для связанных данных, ограничений целостности, SQL и транзакций. Выбор не сводится к «структурированные данные — SQL, неструктурированные — NoSQL»: многие NoSQL-хранилища имеют схему, индексы и транзакции, а реляционные СУБД поддерживают JSON и другие типы. Оценивайте модель доступа, консистентность, объём, нагрузку и стоимость эксплуатации.

### Основные модели NoSQL
Бывают:
- Ключ-значение
- Графовые
- Столбцовые
- Документные

- NoSQL может быть уместна, если модель доступа и масштабирование хорошо соответствуют конкретному типу хранилища. Сама по себе она не гарантирует низкую latency, горизонтальное масштабирование или отсутствие связей.

## Индексы PostgreSQL

- **B-tree** — универсальный индекс для равенства, диапазонов и сортировки; поддерживает уникальность. Доступность конкретного оператора зависит от типа и operator class.
- **Hash** — индекс для сравнения на равенство; не поддерживает диапазоны и сортировку. B-tree часто остаётся предпочтительным универсальным вариантом.
- **GiST** и **SP-GiST** — инфраструктуры для operator class, в том числе для геометрии, диапазонов и других специализированных типов; возможности определяет расширение/тип данных.
- **GIN** — инвертированный индекс, полезен для полнотекстового поиска и поиска по элементам массивов/JSONB; для триграмм нужен подходящий operator class, например из `pg_trgm`.
- **BRIN** — компактный индекс диапазонов блоков, особенно эффективен на больших таблицах, где физический порядок строк коррелирует со значениями (например, временная метка).

Индекс ускоряет подходящие чтения, но занимает место и замедляет запись/обновление. Проверяйте реальный план через `EXPLAIN (ANALYZE, BUFFERS)`, а не предполагайте, что индекс будет использован.

### Составные индексы и планы запросов

Порядок колонок важен: B-tree `(a, b)` обычно особенно полезен для фильтров по `a` и по `a, b`; запрос только по `b` может не получить от него той же пользы. Учитывайте селективность, сортировку, покрытие запроса и стоимость поддержки индекса. Не создавайте индекс на каждую колонку автоматически.


### N + 1 в ORM

N+1 — один запрос за списком сущностей и по дополнительному запросу на каждую связанную сущность. `LAZY` не устраняет проблему автоматически: она лишь откладывает загрузку.

- Используйте DTO/projection, `EntityGraph` или `JOIN FETCH` для связей, действительно нужных сценарию.
- Для `to-many` fetch join может размножить строки, а вместе с пагинацией — дать неверную/неэффективную выборку; иногда лучше batch fetching или отдельный запрос.
- Проверяйте число SQL-запросов и план на реалистичных данных; не загружайте весь граф «на всякий случай».


### Конкурентные изменения и блокировки

- **Оптимистическая блокировка** хранит версию (`@Version` в JPA) и при обновлении проверяет, что версия не изменилась. Конфликт обнаруживается при записи; приложение решает, повторить операцию или вернуть ошибку.
- **Пессимистическая блокировка** (например, `SELECT ... FOR UPDATE`) удерживает блокировку строк/ресурсов. Она может уменьшить конфликты, но увеличивает ожидание и риск deadlock.
- Не держите транзакцию открытой во время сетевого вызова или долгой пользовательской работы. Обрабатывайте deadlock/serialization failure ограниченными повторами с идемпотентностью.

### ACID

В информатике акроним ACID описывает требования к транзакционной системе (например, к СУБД), обеспечивающие наиболее надёжную и
предсказуемую её работу.

#### Atomicity — Атомарность

Атомарность гарантирует, что никакая транзакция не будет зафиксирована в системе частично. Будут либо выполнены все её подоперации, либо не
выполнено ни одной.

#### Consistency — Согласованность

Каждая успешная транзакция по определению фиксирует только допустимые результаты.

#### Isolation — Изолированность

Изоляция задаёт, какие эффекты конкурентных транзакций могут наблюдаться. Реализация уровня и конкретные гарантии зависят от СУБД; MVCC позволяет многим читателям работать без блокирования писателей, но не устраняет все конфликты.

#### Durability — Долговечность

Если пользователь получил подтверждение от системы, что транзакция выполнена, он может быть уверен, что сделанные им изменения не будут
отменены из-за какого-либо сбоя.

### Проблемы параллельного доступа с использованием транзакций

**Потерянное обновление (англ. lost update)** — при одновременном изменении одного блока данных разными транзакциями одно из изменений
теряется;

| Транзакция 1                           | Транзакция 2                           |
|----------------------------------------|----------------------------------------|
| `UPDATE tbl1 SET f2=f2+20 WHERE f1=1;` | `UPDATE tbl1 SET f2=f2+25 WHERE f1=1;` |

**Грязное чтение (англ. dirty read)** — чтение данных, добавленных или изменённых транзакцией, которая впоследствии не подтвердится (
откатится);

| Транзакция 1                          | Транзакция 2                      |
|---------------------------------------|-----------------------------------|
| `UPDATE tbl1 SET f2=f2+1 WHERE f1=1;` |                                   |
|                                       | `SELECT f2 FROM tbl1 WHERE f1=1;` |
| `ROLLBACK WORK;`                      |                                   |

**Неповторяющееся чтение (англ. non-repeatable read)** — при повторном чтении в рамках одной транзакции ранее прочитанные данные оказываются
изменёнными;

| Транзакция 1                          | Транзакция 2                      |
|---------------------------------------|-----------------------------------|
|                                       | `SELECT f2 FROM tbl1 WHERE f1=1;` |
| `UPDATE tbl1 SET f2=f2+1 WHERE f1=1;` |                                   |
| `COMMIT;`                             |                                   |
|                                       | `SELECT f2 FROM tbl1 WHERE f1=1;` |

**Фантомное чтение (англ. phantom reads)** — одна транзакция в ходе своего выполнения несколько раз выбирает множество строк по одним и тем
же критериям. Другая транзакция в интервалах между этими выборками добавляет или удаляет строки, или изменяет столбцы некоторых строк,
используемых в критериях выборки первой транзакции, и успешно заканчивается. В результате получится, что одни и те же выборки в первой
транзакции дают разные множества строк.

| Транзакция 1                               | Транзакция 2                |
|--------------------------------------------|-----------------------------|
|                                            | `SELECT SUM(f2) FROM tbl1;` |
| `INSERT INTO tbl1 (f1,f2) VALUES (15,20);` |                             |
| `COMMIT;`                                  |                             |
|                                            | `SELECT SUM(f2) FROM tbl1;` |

### Уровень изолированности транзакций

**Уровень изоляции транзакций** определяет, какие аномалии конкурентного чтения/записи допускаются. Более высокий уровень не обязательно означает меньше параллелизма в каждой реализации: СУБД могут использовать MVCC, блокировки и обнаружение конфликтов по-разному.

Стандарт SQL-92 определяет шкалу из четырёх уровней изоляции: Read uncommitted, Read committed, Repeatable read, Serializable.
- **Read uncommitted** — стандарт допускает dirty read; PostgreSQL реализует его как `Read committed`.
- **Read committed** — не читает незакоммиченные изменения; два чтения в одной транзакции могут увидеть разные снимки.
- **Repeatable read** — повторные запросы в транзакции читают согласованный снимок; точные гарантии зависят от СУБД. PostgreSQL не допускает фантомного чтения на этом уровне, но возможны serialization anomalies и конфликты, выявляемые при записи.
- **Serializable** — результат эквивалентен некоторому последовательному порядку транзакций; СУБД может блокировать операции или отклонить транзакцию, которую нужно безопасно повторить.

Уровни SQL-стандарта не следует трактовать как одинаковые алгоритмы на всех СУБД. В PostgreSQL проверьте документацию к версии и учитывайте, что `SELECT ... FOR UPDATE`, уникальные ограничения и явные блокировки решают отдельные задачи.




### Нормальные формы

**Нормальная форма** — требование, предъявляемое к структуре таблиц в теории реляционных баз данных для устранения из базы избыточных
функциональных зависимостей между атрибутами (полями таблиц).

#### Первая нормальная форма

В классическом реляционном представлении значения атрибутов атомарны в контексте выбранной модели, а повторяющиеся группы не хранятся внутри одной ячейки. «Атомарность» зависит от предметной области: JSON-колонка сама по себе не нарушает SQL-модель, но может скрывать элементы, которые нужно искать или ограничивать отдельно.

Например, есть таблица «Автомобили»:

| Фирма  | Модели      |
|--------|-------------|
| BMW    | M5, X5M, M1 |
| Nissan | GT-R        |

Нарушение нормализации 1НФ происходит в моделях BMW, т.к. в одной ячейке содержится список из 3 элементов: M5, X5M, M1, т.е. он не является
атомарным. Преобразуем таблицу к 1НФ:

| Фирма  | Модели |
|--------|--------|
| BMW    | M5     |
| BMW    | X5M    |
| BMW    | M1     |
| Nissan | GT-R   |

#### Вторая нормальная форма

Отношение находится во 2НФ, если оно в 1НФ и каждый неключевой атрибут полностью зависит от каждого кандидатного ключа, а не только от его части. Это важно прежде всего для составных ключей.

| Модель | Фирма  | Цена  | Скидка |
|--------|--------|-------|--------|
| M5     | BMW    | 123   | 5%     |
| X5M    | BMW    | 3213  | 5%     |
| M1     | BMW    | 12312 | 5%     |
| GT-R   | Nissan | 12323 | 10%    |

Предположим, что ключ таблицы — `(Фирма, Модель)`, а модель уникальна только внутри фирмы. Цена зависит от полного ключа, а скидка — только от фирмы, то есть от части составного ключа. Исправление — вынести скидку фирмы в отдельное отношение.

| Модель | Фирма  | Цена  |
|--------|--------|-------|
| M5     | BMW    | 123   |
| X5M    | BMW    | 3213  |
| M1     | BMW    | 12312 |
| GT-R   | Nissan | 12323 |

| Фирма  | Скидка |
|--------|--------|
| BMW    | 5%     |
| Nissan | 10%    |

#### Третья нормальная форма

Отношение в 3НФ, если оно в 2НФ и неключевые атрибуты не зависят транзитивно от ключа. Формально для каждой нетривиальной функциональной зависимости `X → A` должно выполняться: `X` — суперключ или `A` — ключевой атрибут.

| Модель | Магазин    | Телефон  |
|--------|------------|----------|
| M5     | Риал-авто  | 87-33-98 |
| X5M    | Риал-авто  | 87-33-98 |
| GT-R   | Некст-Авто | 94-54-12 |

Таблица находится во 2НФ, но не в 3НФ.

В отношении атрибут «Модель» является первичным ключом. Личных телефонов у автомобилей нет, и телефон зависит исключительно от магазина.

Таким образом, в отношении существуют следующие функциональные зависимости: Модель → Магазин, Магазин → Телефон, Модель → Телефон.

Зависимость Модель → Телефон является транзитивной, следовательно, отношение не находится в 3НФ.

В результате разделения исходного отношения получаются два отношения, находящиеся в 3НФ:

| Модель | Магазин    |
|--------|------------|
| M5     | Риал-авто  |
| X5M    | Риал-авто  |
| GT-R   | Некст-Авто |

| Магазин    | Телефон  |
|------------|----------|
| Риал-авто  | 87-33-98 |
| Некст-Авто | 94-54-12 |

### Вопросы на собеседовании

#### Почему индекс не всегда ускоряет запрос?

Индекс имеет стоимость хранения и обновления. Для запроса, который читает значительную долю таблицы, последовательное чтение может быть дешевле; выбор зависит от статистики, селективности, порядка колонок и плана. Проверяйте `EXPLAIN (ANALYZE, BUFFERS)` на репрезентативных данных.

#### Что даёт MVCC?

Многоверсионность позволяет транзакциям читать снимок данных, не блокируя каждое чтение записью. Она не устраняет все аномалии: важны уровень изоляции, блокировки, конфликты записи и корректные ограничения.

#### Как устранить N+1?

Сначала подтвердить его логами/метриками запросов, затем выбрать данные под конкретный сценарий: projection/DTO, `JOIN FETCH`, `EntityGraph` или batch fetching. Один гигантский join может оказаться хуже нескольких ограниченных запросов.


### Основные классы баз данных

https://proselyte.net/db-types-for-devs/
Современные СУБД разнообразны, но их можно разделить на несколько основных классов по характеру нагрузок и модели данных:

- **OLTP** (OnLine Transaction Processing) – это системы управления базами данных, оптимизированные для обработки большого числа коротких транзакций в реальном времени. Пример _Oracle, PostgreSQL, MySQL, Microsoft SQL Server_
- **OLAP** (OnLine Analytical Processing) – системы онлайн-аналитики. Предназначены для агрегирования и анализа больших объёмов данных, выполнения сложных запросов. **Ориентирован на чтение и анализ данных**, часто исторических, с различных разрезов. Часто используют колонковое хранение данных и масштабирование на кластере. Пример: _Apache ClickHouse, Greenplum, Apache Hive (поверх Hadoop), Microsoft Analysis Services, Apache Druid._
- **HTAP** (Hybrid Transaction/Analytical Processing) — архитектура, в которой одна система поддерживает транзакционную и аналитическую нагрузку над актуальными данными. Это не означает одинаково высокую производительность для обоих типов запросов: аналитика может конкурировать за ресурсы с OLTP. Примеры и возможности зависят от редакции/версии; часто упоминают SAP HANA, SingleStore и TiDB.
- **NoSQL** базы данных – нереляционные хранилища, включающие несколько подтипов:
    - **Key-Value**. Доступ обычно оптимизирован под ключ; запросы вне этой модели ограничены, а транзакционные гарантии зависят от продукта (например, Redis и DynamoDB предлагают разные механизмы). Примеры: _Redis, Memcached, Riak, Amazon DynamoDB_.
    - **Document-oriented** Документные базы хорошо подходят, когда данные по природе слабо структурированы. Пример: _MongoDB_ (хранит документы BSON (бинарный JSON), имеет богатый язык запросов), _CouchDB_ (хранит JSON, использует MapReduce для вычисления представлений (views)), _Couchbase_ (сочетает возможности key-value (как Memcached) и документа, имеет SQL-подобный язык N1QL)
    - **Wide-column / column-family** — строки адресуются ключом и могут иметь разреженный набор колонок, сгруппированных в семейства; модель и гарантии различаются между системами. Примеры: _Apache HBase, Apache Cassandra, ScyllaDB, Amazon Keyspaces_.
    - **Graph**. Данные хранятся как **узлы** и **рёбра** с атрибутами. Графовая модель может быть удобна для запросов с обходом связей, например в некоторых рекомендательных сценариях; при простых связях может хватить реляционной СУБД. Примеры: _Neo4j, Amazon Neptune, OrientDB, ArangoDB, Apache JanusGraph_.
- **Распределённые SQL / NewSQL** — нестрого стандартизированный термин для систем, сочетающих SQL/транзакции с распределённым хранением. Горизонтальное масштабирование не означает бесплатную линейную производительность: межузловые транзакции добавляют координацию и задержку. Выбор определяется топологией запросов и отказными сценариями.
    - Распределённые SQL-совместимые решения и слои масштабирования различаются по архитектуре; например, Vitess — слой шардирования и маршрутизации для MySQL, а не самостоятельная NewSQL-СУБД.
    - Примеры NewSQL:
        - **Google Spanner** — глобально распределённая SQL-СУБД; TrueTime помогает поддерживать строгие временные гарантии, а фактические latency/доступность зависят от схемы и региона.
        - **CockroachDB** — распределённая SQL-СУБД с PostgreSQL wire/protocol compatibility; совместимость не означает полного совпадения возможностей PostgreSQL.
        - **VoltDB** — распределённая SQL-СУБД для транзакционных нагрузок; latency, durability и масштабирование зависят от конфигурации.
        - **TiDB** — MySQL-совместимая распределённая SQL-СУБД; масштабирование и транзакции имеют свои ограничения и стоимость межузловой координации.
        - **Amazon Aurora** — облачная реляционная СУБД с разделением compute/storage; это не автоматически шардированная глобальная NewSQL-система.
        - **Azure Cosmos DB** поддерживает несколько API и модели консистентности, но SQL API не делает её реляционной SQL-СУБД.
- **Time-Series DB** – специализированный тип СУБД для хранения и обработки временных рядов, то есть последовательностей значений во времени. Временной ряд – это набор пар «метка времени – значение», например: температура датчика каждую минуту, курс акции по дням, загрузка CPU сервера каждую секунду. Хотя временные ряды можно хранить и в реляционной или NoSQL базе, TSDB оптимизированы специально под эти нагрузки.
    - Обычно это выражается в следующих чертах:
        - **Эффективная запись** большого числа метрик в реалтайме (в секунду могут поступать тысячи/миллионы точек от датчиков).
        - **Сжатие данных** и хранение с учётом временной корреляции (значения во времени часто коррелированы, можно сжимать дельты).
        - **Быстрая агрегация** по интервалам: TSDB имеют встроенные функции downsampling, aggregation по окнам (hourly, daily).
        - **Хранение только аппендиксом** (append-only): данные добавляются по времени, редко обновляются прошлые точки (обычно данные иммутабельны после записи).
        - **Retention / TTL механизм**: часто старые данные автоматически удаляются или агрегируются, чтобы ограничить объем.
    - Примеры TSDB:
        - **InfluxDB** — TSDB; языки запросов и возможности зависят от версии/редакции.
        - **Prometheus** – СУБД для метрик мониторинга, сбор данных через pull, имеет свой язык PromQL.
        - **Graphite** – более старое решение, хранит ряды файловой системой (или Whisper DB), часто используется для мониторинга.
        - **TimescaleDB** – надстройка над PostgreSQL (расширение), превращающее его в TSDB: оптимизирует хранение серий, предлагает удобный синтаксис для интервалов.
        - **OpenTSDB** – распределенная TSDB поверх HBase.
        - **VictoriaMetrics** – высокопроизводительная TSDB, часто используется как замена Prometheus для долгого хранения.
        - **KDB+** – колоночная БД, популярна в финтехе для временных рядов (например, рынки).
        - **Облачные сервисы**: например, Amazon Timestream и managed monitoring/metrics-сервисы; продуктовые названия и статус меняются со временем.
- **Vector DB** — векторные хранилища для поиска по близости embedding-векторов. Часто используются в ML/семантическом поиске, но качество результата зависит от embedding-модели, метрики и индекса; векторный поиск не равен пониманию смысла.
- **In-Memory DB** — СУБД, оптимизированные для работы с данными в памяти. Конкретная система может поддерживать persistence или другие уровни хранения; RAM не означает автоматически отсутствие дисковой записи.
- **Event Store** хранит доменные события для Event Sourcing и поддерживает нужные приложению чтение, версии и идемпотентность. Kafka/Event Hubs — платформы потоковой передачи событий; они могут быть частью event-driven-системы, но не автоматически заменяют доменное хранилище событий.
- **Search Engine DB** – поисковые движки (Elasticsearch, OpenSearch и др.), специализированные на полнотекстовом поиске и анализе неструктурированных данных.
