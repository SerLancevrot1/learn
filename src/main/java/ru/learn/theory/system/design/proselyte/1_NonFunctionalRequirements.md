## 1. Что такое НФТ и как их формулировать

**Простыми словами.** Функциональное требование — что умеет лифт: возить людей между этажами. Нефункциональное — как он это делает: приезжает не дольше чем за 30 секунд, выдерживает 1000 кг, ломается не чаще раза в год и чинится за 2 часа. Два лифта с одинаковыми функциями могут быть очень разными по качеству — именно это качество и описывают НФТ.

`[ ]` **Короткий ответ:** функциональное требование отвечает на вопрос «что делает система», нефункциональное — «насколько хорошо и при каких условиях». НФТ должны быть измеримыми: метрика, порог, окно измерения, профиль нагрузки, область действия и исключения. Плохо: «API должен быть быстрым». Хорошо: «99% успешных запросов `GET /products` за скользящие 30 дней завершаются быстрее 200 мс на стороне балансировщика при нагрузке до 2000 rps; плановые работы не исключаются». НФТ сильнее функций влияют на архитектуру: одна и та же функция при 10 rps и при 100 000 rps проектируется совсем по-разному.

<details>
<summary>Анатомия измеримого требования</summary>

Любое НФТ разбирается на шесть частей. Если хотя бы одна не указана, требование можно трактовать по-разному, и споры начнутся после инцидента.

| Часть | Вопрос | Пример |
|---|---|---|
| Метрика (SLI) | Что измеряем? | Доля успешных запросов быстрее 200 мс |
| Порог | Какое значение приемлемо? | ≥ 99% |
| Окно | За какой период? | Скользящие 30 дней |
| Точка измерения | Где снимаем? | На балансировщике, а не внутри сервиса |
| Условия | При какой нагрузке и данных? | До 2000 rps, каталог до 10 млн товаров |
| Исключения и критерий успеха | Что не считается и что такое «успех»? | 4xx по вине клиента не считаются ошибкой; 5xx и таймауты — ошибка |

Точка измерения важнее, чем кажется. Время, измеренное внутри обработчика, не включает очередь перед пулом потоков, TLS, балансировщик и сеть до пользователя. Сервис может показывать p99 = 50 мс, а пользователь видит 400 мс.

</details>

<details>
<summary>Классификация: какие бывают НФТ</summary>

Стандарт ISO/IEC 25010:2023 описывает модель качества продукта из девяти характеристик с подхарактеристиками; в редакции 2023 года добавлена безопасность (safety), а масштабируемость стала подхарактеристикой гибкости ([ISO](https://www.iso.org/standard/78176.html), [превью стандарта](https://webstore.ansi.org/preview-pages/ISO/preview_ISO+IEC+25010-2023.pdf)). На собеседованиях по бэкенду и system design чаще всего обсуждают такую группу:

- **эксплуатационные**: доступность, надёжность, отказоустойчивость, восстанавливаемость (RPO/RTO), долговечность данных;
- **производительность**: latency, throughput, использование ресурсов;
- **масштабируемость и эластичность**;
- **сопровождаемость**: операбельность, простота, изменяемость, наблюдаемость;
- **безопасность и соответствие требованиям** (security, compliance, хранение персональных данных);
- **согласованность данных** (strong или eventual consistency);
- **стоимость**.

Мартин Клеппман в «Designing Data-Intensive Applications» сводит основу к трём заботам: надёжность, масштабируемость и сопровождаемость ([конспект главы 1](https://github.com/anelguel/designing-data-intensive-apps/blob/main/Chapter1.md)). Эта тройка — хороший каркас для ответа.

</details>

<details>
<summary>НФТ конфликтуют друг с другом</summary>

НФТ нельзя максимизировать одновременно — это всегда компромиссы:

- **Доступность против согласованности.** При сетевом разделении приходится выбирать: отвечать, возможно, устаревшими данными или отказывать (CAP). Даже без разделения синхронная репликация увеличивает задержку (PACELC).
- **Latency против стоимости.** Кеши, реплики ближе к пользователю и запас по мощности стоят денег.
- **Доступность против скорости изменений.** Каждый релиз — риск. Error budget превращает этот спор в число (раздел 5).
- **Безопасность против удобства и задержки.** Шифрование, проверка токенов, mTLS добавляют работу на каждый запрос.
- **Простота против гибкости.** Универсальная платформа сложнее в поддержке, чем решение под конкретную задачу.

Хороший ответ на собеседовании звучит так: «для этого сценария я жертвую X ради Y, потому что бизнесу важнее Y».

</details>

**Частые ошибки.**
- Требование без окна и точки измерения: «99,9% доступности» — за день, месяц, год? На клиенте или на сервере?
- Одно НФТ на всю систему. У чтения каталога и оплаты разная критичность; дешевле задать разные цели ([AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/understanding-availability-needs.html)).
- Цель «100%». Её нельзя ни достичь, ни проверить, и она блокирует любые изменения.

**Уточняющие вопросы.** Чем требование отличается от цели? Кто устанавливает НФТ — разработчики или бизнес? Как проверить НФТ до продакшена (нагрузочный тест, хаос-тест, ревью архитектуры)?

## 2. Доступность

**Простыми словами.** Доступность — это доля времени, когда магазин открыт и может вас обслужить. Если двери открыты, но кассир не пробивает товар или очередь на час, для покупателя магазин фактически закрыт. Поэтому «сервер отвечает на ping» — это не доступность.

`[ ]` **Короткий ответ:** доступность — доля времени или доля запросов, в которых сервис выполняет свою функцию с приемлемым качеством. Считают двумя способами: по времени (сколько минут сервис был «хорошим») и по запросам (успешные / все). «Успешный» нужно определить заранее: ответ без 5xx и быстрее порога. 99,9% — это около 43,8 минуты простоя в месяц, 99,99% — около 4,4 минуты. Каждая следующая девятка в 10 раз уменьшает бюджет простоя и обычно сильно увеличивает стоимость.

<details>
<summary>Бюджет простоя: таблица девяток</summary>

Расчёт для непрерывного измерения, год = 365,25 суток, месяц = год / 12 (≈ 30,44 суток). Проверено программой, раздел 1 вывода.

| Доступность | Сутки | Неделя | Месяц | Год |
|---|---|---|---|---|
| 99 % | 14,4 мин | 1,68 ч | 7,31 ч | 3,65 дня |
| 99,5 % | 7,2 мин | 50,4 мин | 3,65 ч | 43,8 ч |
| 99,9 % | 86,4 с | 10,1 мин | 43,8 мин | 8,77 ч |
| 99,95 % | 43,2 с | 5,0 мин | 21,9 мин | 4,38 ч |
| 99,99 % | 8,6 с | 60,5 с | 4,4 мин | 52,6 мин |
| 99,999 % | 0,86 с | 6,0 с | 26,3 с | 5,3 мин |

Как прикинуть в уме: 1% от суток — 14,4 минуты; дальше делите на 10 за каждую девятку. В месяце примерно 43 800 минут, значит 0,1% — около 44 минуты.

Практический смысл. При 99,99% месячный бюджет — 4,4 минуты. Если от срабатывания алерта до того, как человек откроет ноутбук, проходит 5 минут, любой инцидент с ручным восстановлением сам по себе нарушает SLO. Значит, 99,99% требует автоматического переключения и отката, а не дежурного инженера. Для 99,999% месячный бюджет около 26 секунд — меньше, чем задержка сбора метрик и доставки алерта во многих системах мониторинга ([Google SRE Workbook](https://sre.google/workbook/alerting-on-slos/)).

</details>

<details>
<summary>По времени или по запросам</summary>

**По времени.** Окно делят на интервалы (например, минуты); интервал «хороший», если доля ошибок в нём ниже порога. Доступность = хорошие интервалы / все. AWS описывает именно такой подход: успешные и неуспешные запросы считают за 1- или 5-минутные периоды, а период без запросов считается доступным на 100% ([AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html)).

**По запросам.** Доступность = успешные запросы / все запросы. Google рекомендует формулировать SLI как отношение «хороших событий ко всем событиям» ([SRE Workbook](https://sre.google/workbook/implementing-slos/)).

Методы дают разные числа. Модель из программы (раздел 13 вывода): за 30 дней сервис лежал 1 час ночью (10 rps) и 5 минут днём (1000 rps).

| Сценарий | По времени | По запросам |
|---|---|---|
| 1 ч простоя ночью, 5 мин днём | 99,850% | 99,974% |
| Тот же простой, но 1 ч днём, 5 мин ночью | 99,850% | 99,725% |

По времени оба случая одинаковы; по запросам второй в 10 раз хуже, потому что пострадало больше пользователей. Метрика по запросам ближе к опыту пользователя, но у сервиса с малым трафиком она шумная: 1 ошибка из 50 запросов — уже 98%.

</details>

<details>
<summary>Что считать «доступным»</summary>

- **Ошибки.** 5xx и таймауты — неуспех. 4xx обычно нет (клиент ошибся), но 429 из-за вашего rate limit, который сработал по ошибке, — это ваш отказ.
- **Скорость.** Ответ через 30 секунд для интерактивного API — тоже отказ. Часто доступность и задержку объединяют: успешный = «2xx и быстрее 1 с».
- **Корректность.** Пустой каталог с кодом 200 — отказ, хотя метрики HTTP зелёные.
- **Частичная деградация.** Работает чтение, но не работает оплата. Поэтому SLO задают для пользовательских сценариев, а не для «сервиса целиком».
- **Плановые работы.** Строгая трактовка AWS снижает доступность и при плановых, и при внеплановых перерывах ([AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html)). В SLA плановые окна часто исключают — это нужно прописать явно.

Значение 100% за прошедший месяц не доказывает, что система не может отказать: оно лишь говорит, что за этот период отказов не наблюдали.

</details>

**Частые ошибки.** Мерить доступность health-check'ом, который проверяет только то, что процесс жив. Мерить на сервере, когда пользователь не может до него дойти из-за DNS или балансировщика. Забывать о частичных отказах.

**Уточняющие вопросы.** Как мерить доступность сервиса с 10 запросами в час? Почему синтетические проверки (probes) дополняют, но не заменяют метрики по реальному трафику? Как учитывать недоступность одного региона из пяти?

## 3. Надёжность, MTBF и MTTR

**Простыми словами.** Машина А ломается раз в год, но ремонт занимает месяц. Машина Б глохнет каждую неделю, но заводится за 10 секунд. Первая надёжная, но часто недоступна; вторая ненадёжная, но почти всегда доступна. Надёжность — «как редко ломается», восстанавливаемость — «как быстро чинится», доступность — их общий итог.

`[ ]` **Короткий ответ:** надёжность — вероятность, что система выполнит функцию без отказа в течение заданного времени и при заданных условиях. Её характеризует MTBF — среднее время между отказами. MTTR — среднее время восстановления. Для простой ремонтируемой системы `A ≈ MTBF / (MTBF + MTTR)`: доступность можно повысить и реже ломаясь, и быстрее чинясь. Часто дешевле уменьшить MTTR (автооткат, автоматическое переключение), чем увеличить MTBF. Держите в паре три метрики: доступность (итог), частоту отказов (причина) и MTTR (скорость восстановления).

<details>
<summary>Определения и семейство MTTx</summary>

| Метрика | Расшифровка | Что показывает |
|---|---|---|
| MTBF | Mean Time Between Failures | Среднее время работы между отказами ремонтируемой системы |
| MTTF | Mean Time To Failure | Среднее время до отказа неремонтируемого компонента (диск, лампа) |
| MTTD | Mean Time To Detect | Сколько отказ длится до обнаружения |
| MTTA | Mean Time To Acknowledge | Сколько от алерта до того, как человек взялся |
| MTTR | Mean Time To Repair / Restore / Recover / Resolve | Среднее время восстановления — уточняйте, какое R имеется в виду |

Буква R в MTTR неоднозначна. «Restore» — сервис снова работает для пользователей (например, после отката). «Resolve» — устранена причина (баг исправлен, выкачен фикс). Restore может занимать 5 минут, а resolve — неделю. Для доступности важен restore.

MTTR полезно разложить на этапы, потому что ускорять их приходится разными средствами:

```text
MTTR ≈ обнаружение (MTTD) + реакция (MTTA) + диагностика + исправление или откат + проверка
       алерты по SLO       дежурства, эскалации   трейсы, логи, дашборды   автооткат, фичефлаги   мониторинг
```

</details>

<details>
<summary>Формула A = MTBF / (MTBF + MTTR) и её пределы</summary>

Примеры из программы (раздел 3 вывода):

| Сценарий | Доступность |
|---|---|
| MTBF 150 дней, MTTR 1 ч | 99,972% |
| MTBF 30 дней, MTTR 30 мин | 99,931% |
| Отказ раз в сутки, MTTR 10 с | 99,988% |
| Отказ раз в год, MTTR 8 ч | 99,909% |

Первую строку приводит и AWS: MTBF 150 дней и MTTR 1 час дают оценку 99,97% ([AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html)). Третья строка показывает главный урок: ежедневный отказ с автовосстановлением за 10 секунд даёт доступность выше, чем ежегодный отказ с ремонтом 8 часов.

Где формула не работает:
- **Частичные отказы.** Формула знает только «работает» и «не работает», а реальные системы часто деградируют: медленно, с частью ошибок, без одной функции.
- **Общие причины.** Две реплики на одной версии кода упадут от одного бага одновременно; формула для резервирования это не учитывает (раздел 4).
- **Среднее скрывает распределение.** MTTR = 30 минут может означать 59 инцидентов по 1 минуте и один на 28 часов. Смотрите и распределение, и максимум.
- **Нестационарность.** После крупного релиза частота отказов выше, чем в спокойный период.

</details>

<details>
<summary>Четыре комбинации и что с ними делать</summary>

| Надёжность | Доступность | Что происходит | Куда инвестировать |
|---|---|---|---|
| Низкая | Низкая | Часто падает и долго чинится | Сначала MTTR (откат, runbook), потом причины отказов |
| Высокая | Низкая | Редкие, но долгие аварии — узкое место в восстановлении | Автоматизация восстановления, учения, проверка бэкапов |
| Низкая | Высокая | Много сбоев, но быстрое автовосстановление | Причины сбоев: каждый сбой — риск, что автоматика не справится, и шум для команды |
| Высокая | Высокая | Цель | Поддерживать, не тратить лишнее на следующую девятку |

Какие метрики держать вместе:
- много отказов и маленький MTTR — доступность может быть высокой, надёжность низкая;
- мало отказов и большой MTTR — надёжность высокая, доступность проседает;
- мало отказов и маленький MTTR — целевое состояние.

</details>

**Частые ошибки.** Путать надёжность и доступность. Считать MTTR от момента алерта, а не от начала влияния на пользователей (так теряется MTTD). Гордиться высоким MTBF, не проверяя, как система восстанавливается.

**Уточняющие вопросы.** Что вы улучшите первым — MTBF или MTTR — и почему? Как уменьшить MTTD? Почему автоматический рестарт может маскировать проблему?

## 4. Доступность цепочки и резервирование

**Простыми словами.** Гирлянда, где лампочки соединены последовательно, гаснет, если перегорит любая — чем больше лампочек, тем чаще она тёмная. Две независимые гирлянды на ёлке гаснут одновременно очень редко. Но если обе включены в одну розетку, выбьет пробки — погаснут обе.

`[ ]` **Короткий ответ:** если сервису нужны все зависимости (жёсткие, последовательные), доступности перемножаются: три компонента по 99,99% дают около 99,97%, десять по 99,9% — около 99,0%. Если компоненты дублируют друг друга и отказывают независимо, перемножаются вероятности отказа: две реплики по 99,9% теоретически дают 99,9999%. На практике мешают общие причины (одна версия кода, одна конфигурация, один балансировщик, одна зона), поэтому реальный выигрыш меньше. Вывод: уменьшайте число жёстких синхронных зависимостей и превращайте их в мягкие.

<details>
<summary>Формулы и расчёты</summary>

Последовательная (жёсткая) зависимость: `A = A1 × A2 × … × An`.

Параллельное резервирование независимых компонентов: `A = 1 − (1 − A1) × (1 − A2) × …`.

Расчёты программы (раздел 4 вывода):

| Схема | Доступность |
|---|---|
| 3 × 99,99% последовательно | 99,970% |
| 10 × 99,9% последовательно | 99,004% |
| 2 × 99,9% параллельно | 99,9999% |
| 2 × 99% параллельно | 99,99% |
| 2 × 99,9% параллельно за общим балансировщиком 99,95% | 99,9499% |

Первый и третий примеры совпадают с расчётами AWS; там же приведено правило: для компонентов из одних девяток число девяток резервированной пары равно сумме девяток компонентов ([AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html)).

Последняя строка — главный урок. Пара реплик с шестью девятками за балансировщиком с 99,95% даёт 99,95%: итог определяет самое слабое последовательное звено. Резервировать нужно всю цепочку, включая балансировщик, DNS, конфигурацию и базу данных.

</details>

<details>
<summary>Почему независимость — сильное допущение</summary>

Формула параллельного резервирования верна, только если отказы независимы. Типичные общие причины:

- одинаковый код: баг или «запрос смерти» роняет все реплики сразу;
- одинаковая конфигурация, выкаченная одновременно везде;
- общая инфраструктура: одна зона доступности, один кластер, один DNS, одна база;
- общий сертификат с одной датой истечения;
- перегрузка: когда падает одна реплика, её трафик уходит на остальные, и они падают следом — это каскадный отказ, а не независимые события ([Google SRE Book](https://sre.google/sre-book/addressing-cascading-failures/)).

Чтобы приблизиться к независимости, используют домены отказа (зоны, регионы), постепенные выкатки (canary) с паузами между зонами, запас мощности N+1 или N+2 и разнообразие (diversity) там, где это оправдано.

</details>

<details>
<summary>Жёсткие и мягкие зависимости</summary>

Жёсткая зависимость — без неё сервис не выполняет функцию. Мягкая — сервис компенсирует её отказ: показывает кеш, значение по умолчанию, урезанный ответ или откладывает работу в очередь. AWS рекомендует превращать жёсткие зависимости в мягкие через graceful degradation и не строить одну функцию на цепочке из многих синхронных вызовов ([AWS Well-Architected, PDF](https://docs.aws.amazon.com/pdfs/wellarchitected/latest/reliability-pillar/wellarchitected-reliability-pillar.pdf)).

Примеры:
- рекомендации недоступны — страница товара показывается без блока рекомендаций;
- сервис скидок не ответил за 50 мс — цена без персональной скидки, но заказ можно оформить;
- письмо с подтверждением отправляется асинхронно через очередь, а не в транзакции оформления заказа.

Ещё один приём AWS — не зависеть в рантайме от control plane (создание ресурсов, изменение конфигурации), потому что у data plane цели доступности обычно выше ([AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/understanding-availability-needs.html)).

</details>

**Частые ошибки.** Обещать SLO выше, чем у жёсткой зависимости. Считать, что «у нас три реплики» означает «мы отказоустойчивы». Забывать про общий балансировщик и DNS.

**Уточняющие вопросы.** Ваш SLO 99,95%, база данных обещает 99,9%. Что делать? Как посчитать доступность, если зависимость нужна только для 20% запросов?

## 5. SLI, SLO, SLA и error budget

**Простыми словами.** SLI — спидометр (что показывает прибор). SLO — ваше внутреннее правило: «не больше 90 км/ч». SLA — договор со штрафом: «если опоздаю больше чем на час, верну деньги за билет». Error budget — сколько вам можно «опаздывать», не нарушив правило: пока запас есть, можно рисковать (выкатывать новое); кончился — едем осторожно.

`[ ]` **Короткий ответ:** SLI — измеряемый показатель качества, обычно доля хороших событий от всех: успешных запросов, запросов быстрее порога. SLO — целевое значение SLI за окно: 99,9% успешных запросов за 30 дней. SLA — внешнее обязательство с последствиями (деньги, кредиты); оно обычно мягче внутреннего SLO, чтобы был запас. Error budget = 1 − SLO: при 99,9% можно «потратить» 0,1% запросов, то есть 10 000 ошибок из 10 млн. Burn rate — скорость расходования бюджета: 1 — бюджет кончится ровно к концу окна, 14,4 — за двое суток. Алертят не на любую ошибку, а на быстрый расход бюджета.

<details>
<summary>Определения по Google SRE</summary>

- **SLI** — тщательно определённая количественная мера какого-то аспекта уровня сервиса; типичные SLI — задержка, доля ошибок, пропускная способность ([Google SRE Book](https://sre.google/sre-book/service-level-objectives/)).
- **SLO** — целевое значение или диапазон для SLI; естественная форма — «SLI ≤ цель» или «нижняя граница ≤ SLI ≤ верхняя» (там же).
- **SLA** — явный или неявный договор с пользователями, включающий последствия выполнения или невыполнения SLO. Простой способ различить: спросить «что будет, если SLO не выполнен?». Если явных последствий нет — это SLO (там же).
- **Error budget** — 100% минус SLO ([SRE Workbook](https://sre.google/workbook/implementing-slos/)).

Требовать выполнения SLO 100% времени нереалистично и вредно: это снижает скорость изменений или требует дорогих консервативных решений ([Google SRE Book](https://sre.google/sre-book/service-level-objectives/)).

</details>

<details>
<summary>Как написать хороший SLO</summary>

1. **Начните с пользователя.** Что ему важно в этом сценарии: что страница открылась, что заказ создан, что данные свежие? Google советует идти от желаемых целей к индикаторам, а не от того, что легко измерить ([Google SRE Book](https://sre.google/sre-book/service-level-objectives/)).
2. **Определите SLI как отношение:** хорошие события / все события.
3. **Укажите, где и как мерить**, и при каких условиях SLO действует. Пример Google: «99% вызовов `Get` RPC завершаются быстрее 100 мс, измеряется по всем бэкенд-серверам» (там же).
4. **Задайте несколько порогов**, если важна форма распределения: 90% быстрее 1 мс, 99% быстрее 10 мс, 99,9% быстрее 100 мс (там же).
5. **Разделите классы нагрузки.** Пакетной обработке важна пропускная способность, интерактивному клиенту — задержка (там же).
6. **Выберите окно.** Скользящее (последние 30 дней) лучше отражает опыт пользователя; календарное (месяц) удобнее для отчётов и SLA ([SRE Workbook](https://sre.google/workbook/implementing-slos/)).
7. **Задокументируйте и согласуйте**: авторы, утверждающие, дата пересмотра, обоснование чисел, политика error budget (там же).

Пример стартовых SLO из SRE Workbook: доступность 97%, 90% запросов быстрее 450 мс, 99% быстрее 900 мс ([SRE Workbook](https://sre.google/workbook/implementing-slos/)). Начинают с того, что система реально показывает, и ужесточают постепенно.

Другие типы SLO: свежесть данных (данные не старше N минут), полнота, корректность, долговечность (там же).

</details>

<details>
<summary>Error budget: расчёт и политика</summary>

Расчёт для SLO 99,9% за 30 дней (раздел 9 вывода программы):
- 10 млн запросов в месяц — бюджет 10 000 неуспешных запросов;
- по времени — 43,2 минуты полной недоступности.

Политика error budget — заранее согласованный документ о том, что происходит, когда бюджет кончился ([SRE Workbook](https://sre.google/workbook/implementing-slos/)). Типичные пункты:
- бюджет есть — команда выпускает фичи в обычном темпе, может экспериментировать;
- бюджет кончился — заморозка рискованных релизов (кроме исправлений надёжности), приоритет у задач по стабильности, постмортем;
- один инцидент съел больше определённой доли бюджета — обязательный постмортем.

Смысл: спор «разработка хочет выпускать, эксплуатация хочет стабильности» превращается в решение по числу, а не по настроению. Error budget — это фактически «SLO для выполнения других SLO» ([Google SRE Book](https://sre.google/sre-book/service-level-objectives/)).

</details>

<details>
<summary>Burn rate и алерты по SLO</summary>

Burn rate — скорость, с которой сервис расходует error budget относительно SLO ([SRE Workbook](https://sre.google/workbook/alerting-on-slos/)):

```text
burn_rate = наблюдаемая доля ошибок / (1 − SLO)
время до исчерпания бюджета = окно SLO / burn_rate
```

Расчёт для SLO 99,9% и окна 30 дней (раздел 9 вывода):

| Доля ошибок | Burn rate | Бюджет кончится за |
|---|---|---|
| 0,1% | 1 | 30 дней |
| 1,44% | 14,4 | 50 ч (≈ 2 дня) |
| 2% | 20 | 36 ч |
| 10% | 100 | 7,2 ч |
| 100% | 1000 | 43 мин |

Почему не алертить на «ошибок больше 0,1% за минуту»: такое правило реагирует на каждый короткий всплеск, как на серьёзную проблему, и будит людей зря. Почему не на «за сутки»: длинное окно долго помнит прошлое, и алерт горит часами после восстановления.

Рекомендуемый вариант — многооконный, с несколькими порогами burn rate. Алерт срабатывает, только если порог превышен и в длинном окне (событие значимо), и в коротком (проблема продолжается сейчас). Короткое окно — около 1/12 длинного ([SRE Workbook](https://sre.google/workbook/alerting-on-slos/)). Типичная таблица ([SoundCloud](https://developers.soundcloud.com/blog/alerting-on-slos/)):

| Реакция | Длинное окно | Короткое окно | Burn rate | Съедено бюджета |
|---|---|---|---|---|
| Пейджер | 1 ч | 5 мин | 14,4 | 2% |
| Пейджер | 6 ч | 30 мин | 6 | 5% |
| Тикет | 1 день | 2 ч | 3 | 10% |
| Тикет | 3 дня | 6 ч | 1 | 10% |

Проверка арифметики программой: 14,4 × 1 ч / 720 ч = 2%; 6 × 6 ч / 720 ч = 5%; 1 × 72 ч / 720 ч = 10%.

Не копируйте числа вслепую: при малом трафике или очень жёстком SLO схема требует подстройки ([SRE Workbook](https://sre.google/workbook/alerting-on-slos/)).

</details>

**Частые ошибки.** Делать SLA равным SLO (нет запаса). Ставить SLO на CPU или память — пользователю они не важны. Иметь SLO без политики error budget: тогда число ни на что не влияет. Иметь 50 SLO на сервис.

**Уточняющие вопросы.** Почему SLA мягче SLO? Что делать, если SLO постоянно выполняется с огромным запасом? Как задать SLO для асинхронной обработки (свежесть, задержка от события до результата)?

## 6. Отказоустойчивость

**Простыми словами.** В самолёте два двигателя, и он долетит на одном — это отказоустойчивость. Ещё важнее, чтобы отказ одного двигателя не вызвал пожар во втором. В софте то же самое: компоненты будут ломаться, задача — чтобы поломка одной части не уронила всё.

`[ ]` **Короткий ответ:** отказоустойчивость — способность продолжать работу, возможно в урезанном виде, когда отдельные компоненты отказывают. Различают fault (неисправность компонента) и failure (система в целом перестала обслуживать пользователя); цель — не дать fault превратиться в failure. Основные средства: резервирование в разных доменах отказа, таймауты, ретраи с экспоненциальной задержкой и jitter, идемпотентность, circuit breaker, bulkhead, ограничение и сброс нагрузки (load shedding), graceful degradation. Главная угроза — каскадный отказ, когда перегрузка одной части передаётся остальным через положительную обратную связь.

<details>
<summary>Fault, error, failure</summary>

- **Fault** — неисправность: упал диск, у сервиса утечка памяти, сеть теряет пакеты.
- **Error** — неверное внутреннее состояние, вызванное неисправностью.
- **Failure** — отказ: система перестала выполнять функцию для пользователя.

Клеппман формулирует надёжность как способность системы работать корректно, даже когда что-то идёт не так: отказы оборудования, ошибки ПО и ошибки людей ([конспект DDIA](https://github.com/anelguel/designing-data-intensive-apps/blob/main/Chapter1.md)). Отказоустойчивая система терпит определённые типы неисправностей — нужно явно сказать, какие: падение узла, зоны, региона, медленная зависимость, некорректные данные.

Важное следствие: неисправности стоит вызывать специально (chaos engineering, game days), чтобы проверить, что механизмы защиты работают.

</details>

<details>
<summary>Таймауты, ретраи, backoff и jitter</summary>

**Таймаут** — максимальное время, которое клиент ждёт ответа. Без таймаутов медленные запросы держат потоки, соединения и память, и сервер исчерпывает ресурсы ([Amazon Builders' Library](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf?did=ba_card-body&trk=ba_card-body)). Как выбрать: от перцентиля задержки зависимости (например, чуть выше p99.9) и от общего бюджета времени запроса. Таймаут нижнего уровня должен быть меньше верхнего, иначе верхний сдастся раньше, а нижний продолжит бесполезную работу. Лучше передавать дедлайн по цепочке (deadline propagation).

**Ретраи** помогают пережить частичные и кратковременные сбои. Но они небезопасны: если система уже перегружена, ретраи добавляют нагрузку (там же).

Усиление ретраев (раздел 8 вывода программы):

| Уровней в цепочке, каждый делает 3 попытки | Максимум нагрузки на нижний уровень |
|---|---|
| 1 | ×3 |
| 2 | ×9 |
| 3 | ×27 |
| 5 | ×243 |

Поэтому правила такие:
- ретраить на одном уровне (обычно ближе к пользователю), а не на каждом;
- ограничивать число попыток на запрос;
- вводить ретрай-бюджет на процесс или клиента, например не больше 10% от успешных запросов (тогда максимум ×1,1), или фиксированное число ретраев в минуту ([Google SRE Book](https://sre.google/sre-book/addressing-cascading-failures/));
- **экспоненциальная задержка (backoff):** пауза растёт после каждой попытки, с верхним пределом;
- **jitter:** случайная добавка к паузе, чтобы клиенты не ретраили синхронно. Без неё все неудачные вызовы повторяются в один момент и снова создают пик ([Amazon Builders' Library](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf?did=ba_card-body&trk=ba_card-body)). Варианты — full jitter и decorrelated jitter ([AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/));
- ретраить только то, что имеет смысл: таймауты, 503, 429 с `Retry-After`; не ретраить 400 и ошибки валидации.

**Идемпотентность.** Таймаут не означает, что операция не выполнилась: побочный эффект мог уже произойти. Поэтому повторяемые операции делают идемпотентными, например через ключ идемпотентности в запросе ([Amazon Builders' Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)).

</details>

<details>
<summary>Circuit breaker, bulkhead, load shedding, graceful degradation</summary>

- **Circuit breaker.** Если доля ошибок или медленных ответов зависимости выше порога, «размыкаем цепь» и сразу возвращаем ошибку или запасной ответ, не нагружая больную зависимость. Через паузу пропускаем пробные запросы (half-open) и закрываем цепь, если они успешны. Защищает и вызывающего (не тратит потоки на ожидание), и зависимость (даёт ей восстановиться).
- **Bulkhead (переборки).** Отдельные пулы потоков, соединений или очередей для разных зависимостей и классов клиентов. Медленный сервис отчётов исчерпает свой пул, но не пул оформления заказов.
- **Load shedding.** Под перегрузкой лучше быстро отказать части запросов (503 или 429), чем медленно обслуживать всех и упасть. Простой способ — ограничение по CPU, памяти или длине очереди ([Google SRE Book](https://sre.google/sre-book/addressing-cascading-failures/)). Сбрасывать стоит сначала менее важный трафик (пакетные задачи, предзагрузку), а не оплату.
- **Graceful degradation.** Отдавать урезанный, но полезный результат: из кеша, без персонализации, без второстепенных блоков.
- **Rate limiting и квоты.** Защищают от одного шумного клиента или тенанта.
- **Backpressure.** Потребитель сигнализирует производителю, что не успевает; ограниченные очереди вместо бесконечных.

</details>

<details>
<summary>Каскадные отказы</summary>

Каскадный отказ растёт со временем за счёт положительной обратной связи: отказ части системы повышает вероятность отказа других частей. Пример: одна реплика падает от перегрузки, её нагрузка уходит на оставшиеся, и они падают по цепочке ([Google SRE Book](https://sre.google/sre-book/addressing-cascading-failures/)). Самая частая причина — перегрузка (там же).

Типичный сценарий:

```text
зависимость замедлилась → таймауты → ретраи → нагрузка ×3
→ очереди растут → задержка ещё выше → больше таймаутов
→ потоки и память исчерпаны → реплики падают → оставшиеся получают больше трафика
→ поднявшиеся реплики сразу заваливает запросами, и они снова падают
```

Как предотвращать, в порядке приоритета по Google: нагрузочное тестирование до отказа и проверка поведения под перегрузкой; планирование мощности с запасом (пример: при пределе 5000 QPS на кластер и пиковой нагрузке 19 000 QPS нужно около шести кластеров для N+2); сброс нагрузки; ограничение ретраев ([Google SRE Book](https://sre.google/sre-book/addressing-cascading-failures/)).

Как выходить из каскада: добавить ресурсы, если сервис не в «спирали смерти»; перезапустить зависшие серверы, если причина понятна; резко сократить входящий трафик (например, пропускать 1%) и возвращать его постепенно; отключить пакетную нагрузку; заблокировать «плохие» запросы (там же).

</details>

**Частые ошибки.** Ретраи на каждом уровне. Таймаут по умолчанию «бесконечность» в HTTP-клиенте или драйвере БД. Неограниченные очереди. Circuit breaker без запасного поведения: пользователь всё равно получает ошибку, только быстрее. Отсутствие проверки, что резерв действительно работает.

**Уточняющие вопросы.** Как выбрать таймаут? Почему jitter помогает? Что будет, если ретраить неидемпотентный POST? Чем bulkhead отличается от rate limiter?

## 7. RPO, RTO и долговечность данных

**Простыми словами.** Вы пишете курсовую, и ноутбук сгорел. RPO — сколько работы вы готовы потерять: если копия делается раз в час, потеряете до часа. RTO — через сколько вы снова сможете работать: купить ноутбук, восстановить копию, настроить программы.

`[ ]` **Короткий ответ:** RPO (Recovery Point Objective) — максимально допустимая потеря данных, выраженная во времени: RPO 1 час — можно потерять изменения за последний час. RTO (Recovery Time Objective) — максимально допустимое время от прерывания до восстановления сервиса. Это цели для катастроф (регион, удаление данных, атака), а доступность — средний показатель за период. RTO — цель для одного события, MTTR — фактическое среднее по многим событиям. Доступность не гарантирует сохранность данных: сервис может быть доступен, но с потерянными данными. RPO и RTO определяет бизнес, а техника подбирает стратегию: бэкап, pilot light, warm standby, active/active.

<details>
<summary>Определения и отличия</summary>

- **RTO** — максимально допустимая задержка между прерыванием сервиса и его восстановлением ([AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/disaster-recovery-dr-objectives.html)).
- **RPO** — максимально допустимое время с последней точки восстановления данных; определяет приемлемую потерю данных (там же).
- **RTO и MTTR.** Оба измеряют время от начала отказа до восстановления, но MTTR — среднее по нескольким событиям за период, а RTO — цель, максимум для одного события (там же). MTTR — факт, RTO — желаемое ([AWS](https://aws.amazon.com/what-is/recovery-time-objective/)).
- **Disaster recovery и доступность.** DR — разовое восстановление после катастрофы (природное бедствие, крупный технический сбой, атака или ошибка человека), а доступность — средняя устойчивость за период к отказам компонентов, пикам нагрузки и багам ([AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/disaster-recovery-dr-objectives.html)).

Ориентиры AWS: для критичных приложений (tier 1) RTO около 15 минут и RPO почти ноль; для важных (tier 2) — RTO около 4 часов и RPO около 2 часов; для остальных — RTO 8–24 часа и RPO около 4 часов ([AWS](https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-of-on-premises-applications-to-aws/recovery-objectives.html)).

</details>

<details>
<summary>Чем достигаются RPO и RTO</summary>

| Механизм | Влияет на RPO | Влияет на RTO |
|---|---|---|
| Бэкап раз в сутки | До 24 ч потерь | Часы: восстановить и проверить |
| Непрерывная архивация WAL или журнала, point-in-time recovery | Минуты или секунды | Часы: накатить журнал |
| Асинхронная реплика | Секунды (отставание реплики) | Минуты: переключение |
| Синхронная реплика с кворумом | Около нуля | Минуты, при автопереключении секунды; цена — задержка записи |
| Active/active в нескольких регионах | Зависит от репликации | Почти ноль, но сложная согласованность |

Четыре стратегии DR у AWS, от дешёвой к дорогой: backup and restore, pilot light, warm standby, multi-site active/active ([AWS Whitepaper](https://docs.aws.amazon.com/pdfs/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-workloads-on-aws.pdf)).

Подводные камни:
- **Репликация не бэкап.** Ошибочный `DELETE` или повреждение данных реплицируются мгновенно. От логических ошибок спасают только точки во времени (снапшоты, PITR) и отложенные реплики.
- **Непроверенный бэкап — не бэкап.** RPO не достигается автоматически от того, что бэкап запланирован каждые 4 часа: нужно, чтобы он завершался, был согласованным и его можно было найти и восстановить ([AWS Builder Center](https://builder.aws.com/content/3Jki04sk2Acj9j55TKNxe41jv6l)).
- **RTO касается сервиса целиком,** а не одного компонента. Поднятая база не значит, что работают кеш, DNS, секреты, конфигурация и проверка приложения (там же).
- **Регулярные учения:** восстановление и переключение нужно проверять, иначе цифры RPO и RTO остаются на бумаге ([AWS Whitepaper](https://docs.aws.amazon.com/pdfs/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-workloads-on-aws.pdf)).

**Долговечность (durability)** — вероятность не потерять уже подтверждённые данные; это отдельное НФТ, не равное доступности. Хранилище может быть временно недоступно, но ничего не потерять, — и наоборот.

</details>

**Частые ошибки.** Считать, что высокая доступность даёт нулевой RPO. Не тестировать восстановление. Указывать RTO для базы, а не для пользовательского сценария.

**Уточняющие вопросы.** Как получить RPO около нуля и какова цена? Чем PITR лучше ежедневного снапшота? Как защититься от случайного удаления таблицы?

## 8. Latency, response time и throughput

**Простыми словами.** Вы заказали кофе. Время, которое бариста варит кофе, — время обработки. Время, которое вы стояли в очереди, — ожидание. От момента, когда встали в очередь, до момента, когда взяли стакан, — время ответа. Сколько чашек в час выдаёт кофейня — пропускная способность.

`[ ]` **Короткий ответ:** latency — время, которое занял некий этап; её всегда нужно уточнять: сетевая, ожидание в очереди, обработка в сервисе, end-to-end. Response time — то, что видит клиент: от отправки запроса до получения полного ответа, то есть сеть туда, очередь, обработка, сеть обратно. Throughput — сколько операций в единицу времени система завершает (rps). Latency и throughput связаны: при росте нагрузки к насыщению время ожидания в очереди растёт нелинейно, и response time увеличивается, даже когда время обработки не меняется.

<details>
<summary>Из чего складывается время ответа</summary>

```text
Response time = DNS + TCP + TLS (для новых соединений)
              + сеть до сервера
              + ожидание в очередях (балансировщик, accept-очередь, пул потоков, пул соединений к БД)
              + обработка (код, БД, кеш, внешние вызовы)
              + сеть обратно и передача тела
              (+ обработка на клиенте: парсинг, рендеринг)
```

| Термин | Что включает |
|---|---|
| Network latency | RTT, установка соединения, TLS, маршрутизация |
| Queueing latency | Ожидание свободного потока, соединения, блокировки |
| Service time (processing time) | Сама обработка запроса |
| Response time | Всё, что видит клиент |
| End-to-end latency | С точки зрения пользователя: от клика до результата, иногда через несколько систем и асинхронные этапы |

Ключевой момент: **response time = время ожидания + время обработки**. Метрика, снятая внутри обработчика, видит только время обработки. Когда сервер перегружен, растёт в основном ожидание, и внутренние метрики могут оставаться зелёными. Мерить нужно и на сервере, и как можно ближе к клиенту (балансировщик, синтетические проверки, RUM в браузере).

</details>

<details>
<summary>Throughput и его связь с задержкой</summary>

- **Throughput** — завершённые операции в секунду. Не путайте с нагрузкой: нагрузка — сколько пришло, throughput — сколько обработано. При перегрузке throughput упирается в потолок, а лишние запросы копятся в очереди или отклоняются.
- **Goodput** — полезная пропускная способность: успешные ответы, пришедшие до таймаута клиента. Под перегрузкой сервер может обрабатывать 1000 rps, но если ответы приходят после таймаута клиента, goodput почти ноль.
- **Пропускная способность и задержка не независимы.** Подробно — в разделе 11: при загрузке 50% среднее время ответа в 2 раза больше времени обработки, при 90% — в 10 раз.

На собеседовании задержку и пропускную способность всегда называют вместе: «p99 < 200 мс при 5000 rps». Задержка без нагрузки не имеет смысла.

</details>

**Частые ошибки.** Мерить задержку только внутри сервиса. Указывать задержку без нагрузки и перцентиля. Не учитывать установку соединений (холодный старт, TLS) в задержке первого запроса.

**Уточняющие вопросы.** Почему время ответа выросло, а время обработки нет? Как переиспользование соединений (keep-alive, пулы) влияет на задержку? Где мерить задержку для SLO?

## 9. Перцентили: как читать и как не ошибиться

**Простыми словами.** Выстройте 100 запросов по времени, от быстрого к медленному. Медиана (p50) — 50-й в строю: половина быстрее, половина медленнее. p99 — 99-й: только один запрос из ста медленнее. Среднее же — как «средняя температура по больнице»: один пациент с жаром 42 и девять здоровых дают среднее 37,5, хотя такой температуры нет ни у кого.

`[ ]` **Короткий ответ:** среднее чувствительно к выбросам и не описывает ни типичный, ни худший опыт. p50 — типичный запрос, p95 — «регулярно бывает плохо», p99 и выше — хвост: GC, блокировки, очереди, медленные зависимости. Перцентили нельзя складывать по этапам и нельзя усреднять по узлам — их считают по объединённому распределению, обычно из гистограмм. Чем выше перцентиль, тем больше нужно данных: p99.9 по 500 запросам — это по сути один запрос. Отдельная ловушка — coordinated omission: нагрузочный клиент, который ждёт ответа перед следующим запросом, не видит пауз сервера и сильно занижает хвост.

<details>
<summary>Пример: среднее против перцентилей</summary>

10 запросов, мс: `50, 52, 53, 54, 55, 56, 57, 58, 59, 500`.

Программа (раздел 2 вывода): среднее = 99,4 мс, медиана = 55,5 мс, p90 = 59 мс.

Среднее говорит «около 100 мс», хотя 9 из 10 пользователей видели 50–59 мс, а один — полсекунды. Ни один запрос не длился 100 мс. Среднее полезно для расчёта ёмкости (суммарная работа, закон Литтла), но не для описания опыта пользователей.

| Метрика | Что означает | Для чего |
|---|---|---|
| Среднее | Сумма / количество | Ёмкость, суммарная нагрузка; не для SLO |
| p50 | Половина быстрее | Типичный опыт |
| p95 | 5% медленнее | Регулярные проблемы |
| p99 | 1% медленнее | Хвост; часто основа SLO |
| p99.9, p99.99 | 0,1%, 0,01% медленнее | Системы с огромным трафиком и fan-out |
| max | Самый медленный | Сигнал, но очень шумный |

Почему хвост важен: один пользователь делает много запросов. Если страница вызывает 50 запросов, почти каждая загрузка задевает хвост хотя бы одного (раздел 10). Кроме того, медленными часто оказываются запросы самых ценных клиентов — с большими корзинами, историей и данными.

</details>

<details>
<summary>Перцентили не складываются и не усредняются</summary>

**Сложение.** Запрос проходит этапы A и B. Хочется сказать: p99 = p99(A) + p99(B). Программа (раздел 10 вывода, два независимых логнормальных распределения):

| Величина | Значение |
|---|---|
| p99(A) | 80,9 |
| p99(B) | 81,1 |
| p99(A) + p99(B) | 162,1 |
| Фактический p99(A + B) | 123,2 |
| p50(A) + p50(B) | 40,2 |
| Фактический p50(A + B) | 43,6 |

Сумма p99 завысила хвост на 32%, потому что редко бывает, чтобы оба этапа одновременно попали в свой худший 1%. Медианы тоже не складываются. Если этапы зависимы (общая причина, например GC на одной машине), ошибка будет другой — заранее её не угадать. Вывод: мерить end-to-end и через распределённые трассы.

**Усреднение.** Четыре узла, на одном из них мало запросов. Среднее p99 по узлам = 80,1, а честный p99 по всем запросам = 92,7 (раздел 10 вывода). Усреднение перцентилей не имеет математического смысла. Правильно — хранить гистограммы (счётчики по корзинам), складывать корзины и считать перцентиль по сумме. В Prometheus это `histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))`; summary с заранее посчитанными квантилями агрегировать между инстансами нельзя.

**Точность.** Перцентиль из гистограммы — приближение внутри корзины. Чтобы SLO «99% быстрее 200 мс» считался точно, граница 200 мс должна быть одной из корзин.

</details>

<details>
<summary>Coordinated omission: как нагрузочный тест врёт о хвосте</summary>

Термин ввёл Гил Тене. Нагрузочный клиент с закрытым циклом (closed loop) отправляет следующий запрос только после ответа на предыдущий. Когда сервер «замирает», клиент тоже перестаёт слать запросы, и запросы, которые реальные пользователи отправили бы во время паузы, вообще не попадают в статистику. Измерение «согласованно пропускает» именно плохие моменты ([ScyllaDB](https://www.scylladb.com/2021/04/22/on-coordinated-omission/)).

Модель из программы (раздел 11 вывода): сервис отвечает за 1 мс, но раз в 10 секунд замирает на 1 секунду; клиент должен слать 100 rps в течение 100 секунд.

| Способ измерения | Запросов | p50 | p99 | p99.9 | max |
|---|---|---|---|---|---|
| Закрытый цикл (ждёт ответа) | 9110 | 1,0 мс | 1,0 мс | 1,0 мс | 1000 мс |
| Открытый цикл (по расписанию, время от плановой отправки) | 10 000 | 1,0 мс | 902 мс | 992 мс | 1001 мс |

Сервер 10% времени не работает, а закрытый цикл показывает p99 = 1 мс. Видна только максимальная задержка, а 99-й перцентиль занижен почти в 900 раз.

Как избежать: генерировать нагрузку с постоянной частотой, не зависящей от ответов, и мерить задержку от запланированного момента отправки, как это делает wrk2 ([README примера с wrk2](https://github.com/judofyr/coordinated-omission-example/blob/main/README.md)). Использовать HdrHistogram или аналоги, умеющие корректировать такие пропуски.

</details>

**Частые ошибки.** SLO по среднему. Усреднение p99 по подам на дашборде. p99.9 при малом объёме данных. Нагрузочный тест с закрытым циклом как доказательство хорошего хвоста.

**Уточняющие вопросы.** Почему у сервиса p99 = 50 мс, а у клиента 300 мс? Как посчитать p99 по 200 подам? Зачем p99.9, если есть p99?

## 10. Хвостовая задержка

**Простыми словами.** Вы ждёте друзей в кафе. Каждый опаздывает редко — в 1 случае из 100. Но если вы ждёте 100 друзей и начинаете только когда пришли все, почти каждый раз кто-нибудь опоздает. Чем больше участников, от которых вы зависите, тем чаще редкая задержка становится обычной.

`[ ]` **Короткий ответ:** хвостовая задержка — медленные p99 и выше. Её причины — очереди и насыщение ресурсов, head-of-line blocking, GC и JIT, блокировки, фоновые задачи, ретраи, медленные зависимости. В крупных системах хвост доминирует из-за fan-out: если запрос ждёт ответа от n серверов и каждый медленный с вероятностью p, запрос медленный с вероятностью 1 − (1 − p)^n. При p = 1% и n = 100 медленными будут 63% запросов. Средства: уменьшать вариативность (приоритеты, мелкие порции работы, управление фоновыми задачами) и терпеть её (hedged и tied requests, исключение медленных узлов, частичные ответы).

<details>
<summary>Арифметика fan-out</summary>

```text
P(запрос медленный) = 1 − (1 − p)^n
```

Программа (раздел 5 вывода):

| Медленных ответов на звене (p) | Звеньев (n) | Медленных пользовательских запросов |
|---|---|---|
| 1% | 1 | 1,0% |
| 1% | 10 | 9,6% |
| 1% | 100 | 63,4% |
| 0,01% | 2000 | 18,1% |

Это примеры из статьи Дина и Баррозу «The Tail at Scale»: сервер обычно отвечает за 10 мс, но p99 = 1 с; если запрос собирает ответы со 100 таких серверов, 63% запросов будут медленнее секунды. Даже при одном медленном ответе из 10 000 на сервер система из 2000 серверов даст почти каждый пятый медленный запрос ([The Morning Paper](https://blog.acolyer.org/2015/01/15/the-tail-at-scale/)). В реальной системе Google ожидание самых медленных 5% ответов составляло половину общего p99 (там же).

Обратная задача: чтобы при fan-out 100 только 1% пользовательских запросов был медленным, каждое звено должно быть медленным лишь в 0,01% случаев (раздел 5 вывода). Поэтому у листовых сервисов в fan-out-системах SLO по p99.9 и p99.99.

Это касается и микросервисов: страница, которая последовательно или параллельно вызывает 20 сервисов, — тот же fan-out.

</details>

<details>
<summary>Откуда берётся хвост</summary>

- **Очереди и насыщение** — самая частая причина. Пока ресурс не насыщен, задержка стабильна; около насыщения p95 и p99 растут резко и нелинейно (раздел 11). Мало потоков — очередь растёт; мало соединений к БД — запросы ждут; БД перегружена — очередь на её стороне; внешняя система тормозит — ваши потоки «залипают».
- **Head-of-line blocking.** Один тяжёлый запрос держит поток, соединение или блокировку, и все за ним ждут. То же в HTTP/1.1 при конвейерной передаче и в TCP при потере пакета.
- **GC, JIT, прогрев, холодные кеши.** Редкие паузы влияют на хвост, а не на среднее.
- **Блокировки и конкуренция.** Короткие блокировки под конкуренцией превращаются в хвост.
- **Общие ресурсы и фоновые задачи.** Соседи по машине, компакции, бэкапы, cron, логирование, сброс на диск.
- **Ретраи и таймауты.** Медленная зависимость — таймауты — ретраи — нагрузка растёт — ещё медленнее; классический путь к каскадным отказам (раздел 6).
- **Неравномерные данные.** Горячие ключи и партиции, «тяжёлые» клиенты.

Дин и Баррозу называют общие локальные и глобальные ресурсы, фоновые демоны, очереди и ограничения железа (энергия, нагрев) ([Uwe Friedrichsen](https://www.ufried.com/blog/tail_at_scale/)).

</details>

<details>
<summary>Как бороться: уменьшать и терпеть вариативность</summary>

**Уменьшать вариативность** ([Uwe Friedrichsen](https://www.ufried.com/blog/tail_at_scale/)):
- разделять классы сервиса: интерактивные запросы важнее пакетных;
- держать низкоуровневые очереди короткими, чтобы приоритеты работали на уровне приложения;
- дробить длинные запросы, чтобы не было head-of-line blocking;
- управлять фоновыми задачами: ограничивать, распределять, иногда синхронизировать на всех машинах, чтобы они мешали в коротком окне, а не постоянно.

**Терпеть вариативность** (техники из статьи; [The Morning Paper](https://blog.acolyer.org/2015/01/15/the-tail-at-scale/)):
- **Hedged requests.** Если ответ не пришёл дольше, чем p95 для этого класса запросов, отправить копию на другую реплику и взять первый ответ. Дополнительная нагрузка — около 5%, а хвост сильно сокращается. Работает только для идемпотентных операций.
- **Tied requests.** Поставить запрос в очередь сразу к двум серверам и сообщить каждому о втором; кто начал обработку, отменяет копию у другого. В системе Google это снизило медиану на 16% и p99.9 на 40%.
- **Micro-partitions.** Партиций намного больше, чем серверов, чтобы перебалансировать нагрузку мелкими порциями.
- **Выборочная репликация** горячих данных.
- **Испытательный срок для медленных машин:** временно исключать узел с высокой задержкой из балансировки.
- **«Достаточно хороший» ответ:** вернуть результат без самых медленных листьев.
- **Canary-запросы:** сначала отправить запрос на несколько узлов и, только если он прошёл, на остальные — защита от «запроса смерти».

</details>

**Частые ошибки.** Оптимизировать среднее, когда проблема в хвосте. Включать hedging для неидемпотентных операций. Включать hedging сразу, а не после p95 — это удваивает нагрузку.

**Уточняющие вопросы.** Как p99 листового сервиса связан с p99 агрегатора? Чем hedged отличается от простого ретрая? Почему синхронизация фоновых задач может уменьшить хвост?

## 11. Очереди, насыщение и закон Литтла

**Простыми словами.** Кассир обслуживает покупателя за минуту. Если покупатели приходят раз в две минуты, очереди почти нет. Если раз в 65 секунд — кассир занят на 92%, и случайные «пачки» покупателей создают длинную очередь, которая не успевает рассосаться. Загрузка 90% звучит как «есть запас 10%», но на деле означает долгое ожидание.

`[ ]` **Короткий ответ:** когда загрузка ресурса приближается к 100%, время ожидания растёт не линейно, а гиперболически. Для простейшей очереди M/M/1 среднее время в системе `W = S / (1 − ρ)`, где S — время обслуживания, ρ — загрузка: при 50% время ответа в 2 раза больше времени обслуживания, при 90% — в 10 раз, при 95% — в 20 раз; хвост растёт так же. Поэтому сервисы, чувствительные к задержке, держат с запасом и ограничивают очереди. Закон Литтла `L = λ × W`: число запросов в системе = интенсивность × время в системе. По нему считают пулы и конкурентность: 200 rps × 50 мс = 10 одновременных запросов.

<details>
<summary>Модель M/M/1: задержка против загрузки</summary>

Программа моделирует очередь с одним обработчиком: обслуживание в среднем 10 мс (μ = 100 rps), случайные (пуассоновские) приходы, 200 000 запросов (раздел 6 вывода).

| Загрузка ρ | Среднее, мс | Теория S/(1−ρ), мс | p50, мс | p99, мс |
|---|---|---|---|---|
| 0,50 | 20,0 | 20 | 13,8 | 94 |
| 0,70 | 33,3 | 33 | 23,2 | 151 |
| 0,80 | 50,3 | 50 | 34,9 | 244 |
| 0,90 | 102,7 | 100 | 71,5 | 482 |
| 0,95 | 195,8 | 200 | 144,9 | 759 |
| 0,99 | 835 | 1000 | 712 | 3032 |

Что видно:
- время обслуживания не менялось (10 мс), а время ответа выросло в 10 раз при 90% и в 20 раз при 95% — весь рост дало ожидание;
- p99 при 90% загрузки — около 480 мс, в 48 раз больше времени обслуживания;
- переход с 80% на 90% удваивает задержку, с 90% на 95% — ещё раз удваивает;
- при 99% модель не выходит на установившийся режим даже за 200 000 запросов (835 против теоретических 1000; с другой случайной последовательностью результат бывает и заметно выше теории): очередь колеблется очень сильно, и любая пачка запросов надолго увеличивает задержку.

Реальные системы — не M/M/1 (много обработчиков, другие распределения), но форма кривой та же: резкий рост около насыщения. На MIT-лекции это называют высокой чувствительностью задержки при высокой загрузке ([MIT OCW](https://ocw.mit.edu/courses/1-203j-logistical-and-transportation-planning-methods-fall-2006/a9235f5e4e0aee12a55778e5beaf0ddb_lec5.pdf)). С несколькими обработчиками на одну очередь можно держать загрузку выше при той же задержке — один из аргументов за общий пул вместо разделения по узлам.

Практические выводы:
- целевая загрузка для чувствительного к задержке сервиса — заметно ниже 100%, конкретный порог определяют нагрузочным тестом;
- автомасштабирование по CPU 50–70% — не расточительство, а запас под пики и под потерю узла;
- очереди должны быть ограничены, иначе при перегрузке вместо быстрых отказов получится огромная задержка для всех.

</details>

<details>
<summary>Закон Литтла и расчёт пулов</summary>

`L = λ × W`: среднее число объектов в системе равно интенсивности прихода, умноженной на среднее время пребывания. Закон не зависит от распределений, порядка обслуживания и числа обработчиков; нужна только стационарность ([Wikipedia](https://en.wikipedia.org/wiki/Little's_law), [MIT](https://web.mit.edu/1.041/spring2023/lectures/L8-queuing-models-2023sp.pdf)).

Программа (раздел 7 вывода):

| Интенсивность | Время | Одновременно в работе |
|---|---|---|
| 200 rps | 50 мс | 10 |
| 200 rps | 500 мс | 100 |
| 1000 rps | 20 мс | 20 |

Применения:
- **Пул соединений к БД.** 200 rps, запрос держит соединение 50 мс — в среднем занято 10 соединений. Пул на 10 будет постоянно в очереди из-за колебаний; нужен запас, например 15–20. Пул на 200 не нужен и может перегрузить базу.
- **Зависимость замедлилась.** Те же 200 rps, но ответ 500 мс вместо 50 — нужно 100 потоков вместо 10. Если пул на 50 потоков, он исчерпан, и задержка растёт для всех запросов — включая те, которым эта зависимость не нужна. Отсюда bulkhead и таймауты (раздел 6).
- **Проверка нагрузочного теста.** 100 виртуальных пользователей, время ответа 200 мс, без пауз — максимум 500 rps. Если нужно 2000 rps, тест физически не сможет их создать.
- **Лаг очереди сообщений.** В очереди 60 000 сообщений, потребители обрабатывают 1000 в секунду — среднее ожидание около минуты.

</details>

<details>
<summary>Насыщение: какие метрики смотреть</summary>

Минимальный набор для API (продолжение исходного списка):

| Метрика | Что показывает |
|---|---|
| p50 | Типичный опыт |
| p95 | Регулярные проблемы |
| p99 | Хвост |
| Доля ошибок | Качество ответов |
| RPS | Нагрузка |
| Насыщение | CPU, занятость пулов потоков и соединений, длина очередей, GC |

Это пересекается с двумя известными наборами:
- **RED** для сервисов: Rate, Errors, Duration;
- **USE** для ресурсов: Utilization, Saturation, Errors.

Насыщение — ранний сигнал: длина очереди и ожидание соединения из пула растут раньше, чем задержка превысит SLO.

</details>

**Частые ошибки.** Планировать мощность на 100% загрузки. Неограниченные очереди и пулы. Увеличивать пул соединений, когда тормозит сама база: это добавит ей нагрузки.

**Уточняющие вопросы.** Почему при загрузке 90% задержка удваивается при каждом шаге к 100%? Как выбрать размер пула потоков? Что лучше при перегрузке: очередь или отказ?

## 12. Масштабируемость

**Простыми словами.** Пиццерия перестала справляться. Можно купить печь побольше и нанять более быстрого повара — это вертикальное масштабирование: просто, но печи бывают только до определённого размера, а самая большая стоит непропорционально дорого. Можно открыть ещё несколько пиццерий — горизонтальное: можно расти почти бесконечно, но нужно делить заказы, синхронизировать меню и склад. Если же все повара стоят в очереди к одному холодильнику, новые повара не помогут.

`[ ]` **Короткий ответ:** масштабируемость — способность справляться с ростом нагрузки (запросы, данные, пользователи, тенанты, регионы) с сохранением SLO и при разумном росте стоимости. Начинают с описания нагрузки: какие параметры растут (rps, соотношение чтения и записи, объём данных, размер ответа, число подписчиков). Вертикальное масштабирование простое, но упирается в потолок и цену; горизонтальное требует stateless-сервисов, шардинга, репликации, идемпотентности. Линейного роста почти не бывает: закон Амдала ограничивает выигрыш последовательной частью работы, а USL добавляет плату за координацию, из-за которой после некоторого числа узлов пропускная способность падает. Эластичность — отдельное свойство: быстро добавлять и убирать ресурсы под колебания нагрузки.

<details>
<summary>Сначала опишите нагрузку</summary>

Клеппман подчёркивает: масштабируемость — это не ярлык «система масштабируема», а вопрос «если нагрузка вырастет вот так, какие у нас варианты?». Сначала описывают нагрузку конкретными параметрами ([конспект DDIA](https://github.com/anelguel/designing-data-intensive-apps/blob/main/Chapter1.md)).

Параметры нагрузки:
- **запросы:** rps в среднем и на пике, конкурентность, соотношение чтения и записи;
- **данные:** объём, скорость роста, размер записи, распределение по ключам (горячие ключи и партиции);
- **сложность:** fan-out (сколько записей нужно прочитать или записать на один запрос), размер ответа;
- **организационная:** число команд и тенантов на общей платформе, квоты и лимиты;
- **география:** регионы, требования к задержке, законы о хранении данных.

Пример с лентой новостей. Если ленту собирать при чтении, нагрузка растёт с числом подписок у читателя. Если раскладывать посты по лентам при записи, нагрузка растёт с числом подписчиков автора: у знаменитости с 50 млн подписчиков одна публикация — 50 млн записей. Поэтому для «звёзд» используют гибрид. Одна и та же функция масштабируется по-разному в зависимости от того, какой параметр большой.

</details>

<details>
<summary>Вертикальное и горизонтальное масштабирование</summary>

| | Вертикальное (scale up) | Горизонтальное (scale out) |
|---|---|---|
| Что делаем | Мощнее узел: ядра, память, диски | Больше узлов, нагрузка распределяется |
| Плюсы | Не меняет архитектуру, нет распределённой согласованности | Почти неограниченный рост, резервирование, дешёвые узлы |
| Минусы | Потолок железа, нелинейная цена, один домен отказа | Шардинг, репликация, согласованность, сеть, сложность эксплуатации |
| Когда | Первый шаг, базы данных до определённого размера | Stateless-сервисы, большие данные, требования к отказоустойчивости |

Что нужно для горизонтального масштабирования:
- **stateless-сервисы:** состояние в БД, кеше или у клиента; любую реплику можно убить и добавить;
- **балансировка:** round robin, наименьшее число соединений, консистентное хеширование для привязки к данным;
- **репликация чтения:** масштабирует чтение, но добавляет отставание реплик;
- **шардинг:** масштабирует запись и объём; сложности — выбор ключа, горячие шарды, перебалансировка, запросы через несколько шардов;
- **асинхронность и очереди:** сглаживают пики, развязывают сервисы;
- **кеширование и CDN:** снимают нагрузку с источника;
- **идемпотентность:** при ретраях и повторной доставке операция не дублируется.

</details>

<details>
<summary>Амдал и USL: почему узлы не дают линейного роста</summary>

**Закон Амдала.** Если доля α работы выполняется последовательно, ускорение на N узлах не превысит 1/α. При α = 5% — не больше чем в 20 раз, сколько бы узлов вы ни добавили.

**Universal Scalability Law (Нил Гантер)** добавляет плату за координацию (когерентность):

```text
C(N) = N / (1 + α(N − 1) + βN(N − 1))
```

- α — конкуренция (contention): ожидание общих ресурсов, очереди, сериализация;
- β — когерентность (coherency): плата за согласование данных между узлами (кеши, блокировки, репликация); растёт квадратично, потому что пар узлов N(N − 1).

При β = 0 USL превращается в закон Амдала ([Performance Dynamics](http://www.perfdynamics.com/Manifesto/USLscalability.html), [CRAN usl](https://cran.r-project.org/web/packages/usl/vignettes/usl.pdf)). Из-за квадратичного члена после некоторой точки пропускная способность начинает падать с ростом N (там же).

Расчёт программы (раздел 12 вывода), относительная пропускная способность:

| N | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 |
|---|---|---|---|---|---|---|---|---|
| Линейно | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 |
| Амдал, α = 0,05 | 1 | 1,9 | 3,5 | 5,9 | 9,1 | 12,5 | 15,4 | 17,4 |
| USL, α = 0,05, β = 0,001 | 1 | 1,9 | 3,4 | 5,7 | 8,0 | 9,0 | 7,8 | 5,4 |

Пик USL — при `N* = √((1 − α)/β)` ≈ 31 узел, C ≈ 9. После этого добавление узлов уменьшает пропускную способность: 128 узлов дают меньше, чем 16.

Практический смысл: масштабируемость определяется не числом узлов, а тем, сколько в системе общих ресурсов (одна база, одна блокировка, один лидер) и координации (распределённые транзакции, синхронная репликация, широковещательная рассылка). Коэффициенты α и β получают регрессией по результатам нагрузочных тестов при разном числе узлов.

</details>

<details>
<summary>Масштабируемость, эластичность, производительность</summary>

- **Производительность** — как быстро система работает при текущей нагрузке.
- **Масштабируемость** — как меняются производительность и стоимость при росте нагрузки. Быстрая система может плохо масштабироваться, и наоборот.
- **Эластичность** — как быстро система добавляет и освобождает ресурсы под колебания нагрузки (автомасштабирование). Масштабируемая система может быть неэластичной: например, база, которую можно расширить, но только с ручной перебалансировкой за неделю.

Планирование мощности:
1. Нагрузочным тестом найти предел одного узла или кластера и то, как он отказывает.
2. Спрогнозировать пик (сезонность, акции, рост).
3. Добавить запас под потерю домена отказа (N+1, N+2) и под рост задержки около насыщения (раздел 11).
4. Учесть время запуска новых ресурсов: если автомасштабирование занимает 5 минут, а пик растёт за минуту, нужен запас.

Пример Google: предел кластера 5000 QPS, пиковая нагрузка 19 000 QPS — около шести кластеров для N+2 ([Google SRE Book](https://sre.google/sre-book/addressing-cascading-failures/)).

</details>

**Частые ошибки.** Говорить «добавим серверов» без указания узкого места. Шардить раньше, чем исчерпано вертикальное масштабирование и реплики чтения. Выбирать ключ шардирования, порождающий горячие шарды (дата, автоинкремент). Забывать, что база данных — общий ресурс для всех stateless-реплик.

**Уточняющие вопросы.** Как найти узкое место? Чем шардинг отличается от репликации? Что делать с горячим ключом? Как масштабировать запись?

## 13. Сопровождаемость

**Простыми словами.** Две машины одинаково ездят, но у одной для замены лампочки фары нужно снять бампер, а у другой — повернуть патрон. Второй дешевле владеть. Сопровождаемость — сколько стоит жить с системой: чинить, менять, обновлять, передавать новым людям.

`[ ]` **Короткий ответ:** сопровождаемость — насколько легко поддерживать систему в рабочем состоянии, исправлять дефекты, выпускать изменения и адаптировать её к новым требованиям. По Клеппману у неё три составляющие: операбельность (эксплуатации легко держать систему в рабочем состоянии), простота (новый инженер быстро понимает систему) и изменяемость (легко вносить непредвиденные изменения). Она напрямую влияет на MTTR, а значит, на доступность. Измеряют косвенно: метрики DORA (частота деплоев, время от коммита до продакшена, доля неудачных изменений, время восстановления после неудачного деплоя), MTTR, время диагностики, доля автоматических откатов.

<details>
<summary>Три составляющие по Клеппману</summary>

**Операбельность.** Хорошая эксплуатация может обойти ограничения плохого софта, но хороший софт не будет надёжно работать при плохой эксплуатации ([заметки по DDIA](https://github.com/anshulkhare7/notes/blob/main/books/designing-data-intensive-applications.md)). Что делает система для операбельности ([превью DDIA](https://api.pageplace.de/preview/DT0400.9781491903117_A29629813/preview-9781491903117_A29629813.pdf)):
- даёт видимость поведения и внутреннего состояния через мониторинг;
- поддерживает автоматизацию и интеграцию со стандартными инструментами;
- не зависит от отдельных машин: любую можно вывести на обслуживание;
- имеет документацию и понятную модель работы («если я сделаю X, произойдёт Y»);
- даёт хорошие значения по умолчанию, но позволяет их переопределить;
- самовосстанавливается, но позволяет вручную управлять состоянием;
- ведёт себя предсказуемо.

**Простота.** Цель — убрать случайную сложность (accidental complexity), то есть сложность, порождённую реализацией, а не самой задачей. Главный инструмент — хорошие абстракции, которые прячут детали за понятным фасадом (там же). Источники сложности: взрыв числа состояний, сильная связанность модулей, запутанные зависимости, непоследовательные имена, костыли для производительности, особые случаи ([заметки Daniel Imfeld](https://imfeld.dev/notes/book_designing_data_intensive_applications)).

**Изменяемость (evolvability)** — лёгкость изменений и адаптации к непредвиденным сценариям; её также называют расширяемостью и модифицируемостью ([конспект DDIA](https://github.com/anelguel/designing-data-intensive-apps/blob/main/Chapter1.md)). Тесно связана с простотой: простые системы легче менять. Практики: модульность и слабая связанность, версионирование контрактов и схем, обратная и прямая совместимость, миграции в несколько шагов (expand/contract).

</details>

<details>
<summary>Как измерять</summary>

**Метрики DORA.** Изначально четыре ключевые метрики: частота деплоев, время от коммита до продакшена, время восстановления, доля неудачных изменений. Исследование показало, что скорость не обязательно идёт в ущерб стабильности: лучшие команды сильны в обоих ([DORA](https://dora.dev/insights/dora-metrics-history/)). В актуальной модели пять метрик, а MTTR заменено на время восстановления после неудачного деплоя ([DORA](https://dora.dev/guides/dora-metrics/)):

| Группа | Метрика | Что показывает |
|---|---|---|
| Пропускная способность | Change lead time | Время от коммита до деплоя в продакшен |
| Пропускная способность | Deployment frequency | Как часто деплоим |
| Пропускная способность | Failed deployment recovery time | Время восстановления после деплоя, требующего немедленного вмешательства |
| Нестабильность | Change fail rate | Доля деплоев, потребовавших немедленного вмешательства (откат, хотфикс) |
| Нестабильность | Deployment rework rate | Доля внеплановых деплоев из-за инцидентов в продакшене |

**Операционные метрики:** MTTD, MTTR, время локализации причины, доля инцидентов, обнаруженных алертами, а не пользователями, доля автоматических откатов, число шагов ручного труда (toil) на типовую операцию.

**Метрики кода** (вспомогательные, легко подделать): связанность, сложность, покрытие тестами, время сборки, время ввода нового инженера.

Формально сопровождаемость определяют как вероятность восстановить работоспособность за заданный интервал — это аналог надёжности для ремонта.

</details>

<details>
<summary>Практики, которые делают систему сопровождаемой</summary>

- **Безопасные изменения:** маленькие релизы, фичефлаги, canary и blue-green, автоматический откат по SLO, миграции с возможностью отката.
- **Наблюдаемость:** метрики, структурированные логи, распределённые трассы, профилирование. Корреляционный идентификатор запроса во всех логах.
- **Runbook и автоматизация:** каждое повторяющееся ручное действие — кандидат на скрипт. Это превращает героизм в предсказуемый процесс.
- **Постмортемы без поиска виноватых** и выполнение задач из них.
- **Стандарты:** единые библиотеки для таймаутов, ретраев, метрик; шаблоны сервисов.
- **Документация решений** (ADR): почему выбрано так, а не иначе.

Связь с надёжностью. Надёжность отвечает на вопрос «как редко ломается», сопровождаемость — «как быстро и безопасно чинимся и меняемся». Вместе они определяют реальную доступность.

</details>

**Частые ошибки.** Считать сопровождаемость «качеством кода» и только. Мерить её строками кода или покрытием. Откладывать наблюдаемость «на потом» — до первого инцидента.

**Уточняющие вопросы.** Как сопровождаемость влияет на доступность? Как сократить MTTR в два раза? Чем DORA-метрики лучше «количества закрытых задач»?

## 14. Другие НФТ: короткая карта

**Простыми словами.** Кроме скорости и надёжности, у системы есть ещё десяток «как»: безопасна ли она, честны ли данные, сколько стоит, законна ли.

`[ ]` **Короткий ответ:** на собеседовании кроме доступности, задержки и масштабируемости обычно спрашивают про согласованность данных, долговечность, безопасность, наблюдаемость, стоимость и соответствие требованиям (персональные данные, место хранения). Для каждого нужна измеримая формулировка.

<details>
<summary>Таблица: требование и измеримая формулировка</summary>

| НФТ | Вопрос | Пример формулировки |
|---|---|---|
| Согласованность | Можно ли читать устаревшие данные? | После оплаты пользователь видит статус «оплачено» сразу (read-your-writes); счётчик просмотров может отставать до 1 минуты |
| Долговечность | Можно ли потерять подтверждённую запись? | Подтверждённый заказ не теряется при отказе одного узла или одной зоны |
| Свежесть | Насколько данные могут отставать? | 99% событий доступны в аналитике не позже чем через 5 минут |
| Безопасность | Кто и что может делать? | Все внешние вызовы по TLS 1.2+; доступ к PII только у ролей X и Y; аудит всех изменений |
| Соответствие требованиям | Какие законы и стандарты? | Данные граждан страны N хранятся только в регионе N; удаление по запросу за 30 дней |
| Наблюдаемость | Как узнать о проблеме? | 95% инцидентов обнаруживаются алертами до жалоб пользователей |
| Стоимость | Сколько готовы платить? | Не дороже $0,10 за 1000 запросов; инфраструктура не больше X в месяц |
| Эластичность | Как быстро масштабироваться? | Рост нагрузки в 3 раза за 10 минут без нарушения SLO |
| Переносимость | Насколько привязаны к платформе? | Запуск в любом Kubernetes без облачных управляемых сервисов |
| Удобство использования | Насколько легко пользователю? | Оформление заказа не больше 3 шагов |

</details>

## 15. НФТ на интервью по system design

**Простыми словами.** Архитектор, прежде чем рисовать дом, спрашивает: сколько этажей, сколько людей будет жить, в какой климатической зоне. Без этого любой чертёж — угадывание. На интервью по system design НФТ — это и есть такие вопросы.

`[ ]` **Короткий ответ:** после уточнения функций за 3–5 минут собирают НФТ: масштаб (пользователи, rps на чтение и запись, объём данных и рост), задержка (p99 для ключевых операций), доступность (какие сценарии критичны), согласованность (где нужна строгая, где допустима итоговая), долговечность, география, ограничения по безопасности и стоимости. Затем делают прикидку на салфетке (back-of-the-envelope) и явно говорят, какие компромиссы выбраны и почему. Интервьюер оценивает не точность чисел, а то, что решения вытекают из требований.

<details>
<summary>Чек-лист вопросов</summary>

1. **Масштаб:** DAU, пиковый rps, соотношение чтения и записи, размер объекта, объём данных через год и через пять лет.
2. **Задержка:** какие операции интерактивные и какой p99 им нужен; что можно сделать асинхронно.
3. **Доступность:** какие сценарии критичны (оформление заказа) и какие допускают деградацию (рекомендации).
4. **Согласованность:** что будет, если пользователь увидит устаревшие данные? Где нужен read-your-writes?
5. **Долговечность:** можно ли потерять запись? Каковы RPO и RTO?
6. **География:** один регион или несколько? Ограничения по месту хранения данных?
7. **Безопасность и соответствие требованиям:** персональные данные, платежи, аудит.
8. **Стоимость и сроки:** бюджет, размер команды, время до запуска.

</details>

<details>
<summary>Пример прикидки: сервис коротких ссылок</summary>

Допущения (их нужно проговорить): 100 млн новых ссылок в месяц, чтений в 100 раз больше, запись ≈ 500 байт, хранение 5 лет.

```text
Запись:  100 млн / (30 × 86 400 с) ≈ 40 rps в среднем; пик ×5 ≈ 200 rps
Чтение:  40 × 100 ≈ 4000 rps в среднем; пик ≈ 20 000 rps
Данные:  100 млн × 12 мес × 5 лет × 500 Б ≈ 3 ТБ
Кеш:     пусть горячие — ссылки за последний месяц: 100 млн × 500 Б ≈ 50 ГБ;
         по правилу 80/20 кешируем 20% из них ≈ 10 ГБ — помещается в память пары узлов кеша
```

Выводы из НФТ:
- чтение доминирует — кеш и CDN перед хранилищем, реплики чтения;
- редирект интерактивный — цель, например, p99 < 50 мс на стороне сервиса, значит, горячие данные в памяти;
- доступность чтения важнее доступности создания — при отказе хранилища отдавать из кеша, создание можно временно отключить;
- согласованность: новая ссылка должна сразу работать у автора (read-your-writes), у остальных допустимо отставание в секунды;
- 3 ТБ за 5 лет помещаются в шардированное KV-хранилище или даже в одну крупную базу с репликами — шардинг не обязателен с первого дня.

Числа порядка, а не точные: важно показать ход мысли и то, как из них следуют архитектурные решения.

</details>

## 16. Пробное собеседование

Отвечайте вслух, засекайте 2 минуты на вопрос. Потом сверьтесь с разделами.

<details>
<summary>1. Сформулируйте НФТ для API поиска товаров</summary>

Хороший ответ: «Для `GET /search`: 99% успешных запросов быстрее 300 мс, 99,9% быстрее 1 с, измеряется на балансировщике за скользящие 28 дней, при пиковой нагрузке до 5000 rps и каталоге до 50 млн товаров. Доступность — 99,9% запросов без 5xx и таймаутов. Свежесть индекса — изменения цены видны в поиске не позже чем через 5 минут. При недоступности персонализации поиск работает без неё». Затем назвать компромиссы: свежесть против нагрузки на индексацию.

</details>

<details>
<summary>2. У сервиса SLO 99,95%. Он синхронно вызывает три сервиса по 99,9%. Что скажете?</summary>

Произведение даёт около 99,7% даже при идеальном собственном коде, то есть SLO недостижим. Варианты: сделать часть зависимостей мягкими (кеш, значение по умолчанию, асинхронность), добавить резервирование в разных доменах отказа, договориться о более высоком SLO зависимостей или снизить свой SLO. Раздел [4](#4-доступность-цепочки-и-резервирование).

</details>

<details>
<summary>3. Доступность 99,99%, но пользователи жалуются. Почему так может быть?</summary>

Доступность меряют не там (на сервере, а проблема в DNS, CDN или клиенте); «успешный» определён без учёта задержки, и ответы 200 приходят через 10 секунд; ответы корректны по HTTP, но неверны по содержанию; проблема у части пользователей (один регион, один тенант), а метрика усреднена; доступность по времени скрывает дневной пик (раздел [2](#2-доступность)). Решение — SLI ближе к пользователю и по сценариям.

</details>

<details>
<summary>4. Что улучшать: MTBF или MTTR?</summary>

Обычно сначала MTTR: обнаружение по SLO-алертам, автооткат, фичефлаги, runbook — это быстро даёт результат и помогает при любых отказах, включая неизвестные. Затем MTBF по результатам постмортемов: устранять повторяющиеся причины. Но если сбои очень частые, автоматика — это тоже риск, и их причины нужно устранять (раздел [3](#3-надёжность-mtbf-и-mttr)).

</details>

<details>
<summary>5. После релиза p99 вырос с 200 до 800 мс, p50 не изменился. Ваши действия?</summary>

Сначала откатить, если SLO под угрозой и burn rate высокий. Затем: p50 не изменился — значит, проблема в части запросов. Смотреть трассы самых медленных запросов, разбивку по эндпоинтам, клиентам и подам (один «плохой» под?), насыщение (пулы, очереди, GC), новые вызовы зависимостей или N+1 запросов к БД. Проверить, не выросла ли нагрузка из-за ретраев. Разделы [10](#10-хвостовая-задержка), [11](#11-очереди-насыщение-и-закон-литтла).

</details>

<details>
<summary>6. Нагрузочный тест показал p99 = 5 мс, а в продакшене 300 мс. Почему?</summary>

Coordinated omission (тест с закрытым циклом не видит пауз); тест не создаёт реальную конкурентность и распределение запросов; тёплые кеши и маленький набор данных; нет fan-out и медленных зависимостей; измерение внутри сервиса, а не на клиенте. Раздел [9](#9-перцентили-как-читать-и-как-не-ошибиться).

</details>

<details>
<summary>7. Внешний сервис начал отвечать медленно. Как защитить свой сервис?</summary>

Таймаут ниже бюджета запроса; ретраи только на одном уровне, с backoff, jitter и бюджетом; circuit breaker с запасным ответом; отдельный пул потоков или соединений (bulkhead), чтобы медленный вызов не съел общий пул — по закону Литтла рост времени ответа в 10 раз требует в 10 раз больше потоков; при возможности — кеш или асинхронная обработка. Раздел [6](#6-отказоустойчивость).

</details>

<details>
<summary>8. Сервис на 8 узлах держит 8000 rps. Сколько узлов нужно для 16 000?</summary>

Не обязательно 16: проверить, где узкое место. Если общий ресурс (база, блокировка, лидер), добавление узлов может не дать прироста или даже ухудшить (USL). Нужно провести нагрузочный тест на 8, 12, 16 узлах и оценить α и β; учесть запас на потерю зоны (N+1) и на рост задержки около насыщения. Раздел [12](#12-масштабируемость).

</details>

<details>
<summary>9. Как объяснить продакт-менеджеру, зачем error budget?</summary>

«Мы договариваемся, что 99,9% запросов будут успешными. Оставшиеся 0,1% — это бюджет, который мы тратим на изменения: новые фичи, эксперименты, миграции. Пока бюджет есть, выпускаем быстро. Кончился — притормаживаем фичи и чиним надёжность. Так решение принимается по данным, а не в споре». Раздел [5](#5-sli-slo-sla-и-error-budget).

</details>

<details>
<summary>10. Нужен RPO = 0 и RTO = 1 минута. Что предложите и какова цена?</summary>

Синхронная репликация с кворумом в нескольких зонах (RPO около нуля) и автоматическое переключение (RTO — секунды или минуты). Цена: задержка записи растёт на RTT между зонами, при потере кворума запись недоступна, стоимость выше. Для межрегионального варианта задержка ещё больше. Плюс отдельная защита от логических ошибок (PITR, отложенные реплики), потому что репликация копирует и ошибочное удаление. И регулярные учения. Раздел [7](#7-rpo-rto-и-долговечность-данных).

</details>

## Приложение: программа расчётов на Java

Все числа в разделах получены этой программой. Нужна только JDK 11+ (проверено на OpenJDK 25), сборка не требуется — single-file запуск:

```bash
java -Dstdout.encoding=UTF-8 Lab.java
```

`-Dstdout.encoding=UTF-8` нужен, чтобы кириллица в выводе не превращалась в знаки вопроса на консолях с другой кодировкой.

Генератор случайных чисел — `new Random(42)`, поэтому вывод воспроизводится один в один. Детерминированные расчёты (девятки, MTBF/MTTR, зависимости, fan-out, закон Литтла, ретраи, burn rate, coordinated omission, USL, доступность по времени и запросам) от генератора не зависят. Случайные модели (M/M/1, сложение и усреднение перцентилей) при другом seed дают немного другие числа, но те же выводы.

Что стоит посмотреть в коде:
- `pct` — перцентиль методом ближайшего ранга: отсортировать и взять элемент с номером `ceil(p/100 × n)`;
- `expo` — экспоненциальное распределение через обратную функцию: `−ln(1 − U) / λ`; так моделируются пуассоновские приходы и время обслуживания;
- `mm1` — очередь с одним обработчиком: запрос начинает обслуживаться в `max(время прихода, момент освобождения обработчика)`; первые 10% запросов отбрасываются как прогрев;
- `coordinatedOmission` — два клиента к одному и тому же «замирающему» сервису: закрытый цикл ждёт ответа, открытый шлёт по расписанию и меряет от плановой отправки.

import java.util.*;
import java.util.function.DoubleUnaryOperator;

/** Расчёты и модели для конспекта по НФТ. Запуск: java Lab.java */
public class Lab {
    static final Random RND = new Random(42);

    /** Перцентиль методом ближайшего ранга. */
    static double pct(double[] xs, double p) {
        double[] s = xs.clone();
        Arrays.sort(s);
        int k = Math.max(0, (int) Math.ceil(p / 100 * s.length) - 1);
        return s[k];
    }
    static double pct(List<Double> xs, double p) { return pct(toArray(xs), p); }
    static double[] toArray(List<Double> xs) { return xs.stream().mapToDouble(Double::doubleValue).toArray(); }
    static double mean(double[] xs) { return Arrays.stream(xs).average().orElse(Double.NaN); }
    static double expo(double rate) { return -Math.log(1 - RND.nextDouble()) / rate; }
    static double lognorm(double mu, double sigma) { return Math.exp(mu + sigma * RND.nextGaussian()); }
    static String f(String fmt, Object... a) { return String.format(Locale.ROOT, fmt, a); }

    static String human(double s) {
        if (s < 1) return f("%.0f мс", s * 1000);
        if (s < 120) return f("%.1f с", s);
        if (s < 7200) return f("%.1f мин", s / 60);
        if (s < 2 * 86400) return f("%.2f ч", s / 3600);
        return f("%.2f дн", s / 86400);
    }

    public static void main(String[] args) {
        downtime();
        meanVsPercentiles();
        mtbfMttr();
        dependencies();
        fanOut();
        mm1Table();
        little();
        retries();
        errorBudget();
        percentilesDoNotAdd();
        coordinatedOmission();
        usl();
        timeVsRequests();
    }

    static void downtime() {
        System.out.println("== 1. Бюджет простоя (год = 365.25 дня, месяц = год/12)");
        double year = 365.25 * 86400;
        String[] names = {"сутки", "неделя", "месяц", "год"};
        double[] periods = {86400, 7 * 86400, year / 12, year};
        for (double a : new double[]{99, 99.5, 99.9, 99.95, 99.99, 99.999}) {
            StringJoiner j = new StringJoiner(", ");
            for (int i = 0; i < names.length; i++) j.add(names[i] + " " + human((1 - a / 100) * periods[i]));
            System.out.println(f("%s%%: %s", trim(a), j));
        }
    }
    static String trim(double a) { return a == Math.rint(a) ? String.valueOf((long) a) : String.valueOf(a); }

    static void meanVsPercentiles() {
        System.out.println("\n== 2. Среднее против перцентилей");
        double[] xs = {50, 52, 53, 54, 55, 56, 57, 58, 59, 500};
        double[] s = xs.clone(); Arrays.sort(s);
        double median = (s[4] + s[5]) / 2;
        System.out.println(f("avg = %.1f median = %.1f p90 = %.0f", mean(xs), median, pct(xs, 90)));
    }

    static void mtbfMttr() {
        System.out.println("\n== 3. MTBF/MTTR");
        Object[][] cases = {
            {150 * 24.0, 1.0, "MTBF 150 дн, MTTR 1 ч"},
            {30 * 24.0, 0.5, "MTBF 30 дн, MTTR 30 мин"},
            {24.0, 10 / 3600.0, "отказ раз в сутки, MTTR 10 с"},
            {365 * 24.0, 8.0, "отказ раз в год, MTTR 8 ч"}};
        for (Object[] c : cases) {
            double mtbf = (double) c[0], mttr = (double) c[1];
            System.out.println(f("%s: A = %.4f%%", c[2], mtbf / (mtbf + mttr) * 100));
        }
    }

    static void dependencies() {
        System.out.println("\n== 4. Последовательные и параллельные зависимости");
        System.out.println(f("3 x 99.99%% последовательно: %.4f%%", Math.pow(0.9999, 3) * 100));
        System.out.println(f("10 x 99.9%% последовательно: %.3f%%", Math.pow(0.999, 10) * 100));
        System.out.println(f("2 x 99.9%% параллельно: %.4f%%", (1 - 0.001 * 0.001) * 100));
        System.out.println(f("2 x 99%% параллельно: %.4f%%", (1 - 0.01 * 0.01) * 100));
        System.out.println(f("2 x 99.9%% параллельно + общий балансировщик 99.95%%: %.4f%%", (1 - 0.001 * 0.001) * 0.9995 * 100));
    }

    static void fanOut() {
        System.out.println("\n== 5. Fan-out: доля медленных пользовательских запросов");
        for (int n : new int[]{1, 10, 100})
            System.out.println(f("p=1%%, n=%d: %.1f%%", n, (1 - Math.pow(0.99, n)) * 100));
        System.out.println(f("p=0.01%%, n=2000: %.1f%%", (1 - Math.pow(0.9999, 2000)) * 100));
        System.out.println(f("чтобы при n=100 медленным был 1%% запросов, звено должно быть медленным с p = %.4f%%",
                (1 - Math.pow(0.99, 1.0 / 100)) * 100));
    }

    /** Очередь M/M/1: пуассоновские приходы, экспоненциальное обслуживание, один обработчик. */
    static double[] mm1(double lambda, double mu, int n) {
        double t = 0, freeAt = 0;
        double[] lat = new double[n];
        for (int i = 0; i < n; i++) {
            t += expo(lambda);
            double start = Math.max(t, freeAt);
            freeAt = start + expo(mu);
            lat[i] = (freeAt - t) * 1000;
        }
        double[] warm = Arrays.copyOfRange(lat, n / 10, n); // отбрасываем прогрев
        return new double[]{mean(warm), pct(warm, 50), pct(warm, 99)};
    }

    static void mm1Table() {
        System.out.println("\n== 6. Очередь M/M/1: задержка против загрузки (μ = 100 rps, обслуживание 10 мс в среднем)");
        for (double rho : new double[]{0.5, 0.7, 0.8, 0.9, 0.95, 0.99}) {
            double[] r = mm1(rho * 100, 100, 200_000);
            System.out.println(f("ρ=%.2f: среднее %6.1f мс (теория %6.1f), p50 %6.1f, p99 %7.1f",
                    rho, r[0], 10 / (1 - rho), r[1], r[2]));
        }
    }

    static void little() {
        System.out.println("\n== 7. Закон Литтла");
        double[][] cases = {{200, 0.050}, {200, 0.500}, {1000, 0.020}};
        for (double[] c : cases)
            System.out.println(f("%.0f rps x %.0f мс = %.0f одновременных запросов", c[0], c[1] * 1000, c[0] * c[1]));
    }

    static void retries() {
        System.out.println("\n== 8. Ретраи");
        for (int layers : new int[]{1, 2, 3, 5})
            System.out.println(f("%d уровня по 3 попытки: до x%d нагрузки на нижний уровень", layers, (long) Math.pow(3, layers)));
        System.out.println("Ретрай-бюджет 10%: максимум x1.1");
    }

    static void errorBudget() {
        System.out.println("\n== 9. Error budget и burn rate (SLO 99.9%, окно 30 дней)");
        double budget = 1 - 0.999, windowH = 30 * 24;
        System.out.println(f("10 млн запросов в месяц -> бюджет %.0f ошибок; по времени %.1f мин", 10_000_000 * budget, windowH * 60 * budget));
        for (double err : new double[]{0.001, 0.0144, 0.02, 0.10, 1.0}) {
            double br = err / budget;
            System.out.println(f("ошибок %5.2f%% -> burn rate %6.1f, бюджет кончится за %7.1f ч (%.2f дн)",
                    err * 100, br, windowH / br, windowH / br / 24));
        }
        System.out.println(f("burn rate 14.4 за 1 ч съедает %.1f%% бюджета; 6 за 6 ч -> %.1f%%; 1 за 3 дня -> %.1f%%",
                14.4 / windowH * 100, 6 * 6 / windowH * 100, 72 / windowH * 100));
    }

    static void percentilesDoNotAdd() {
        System.out.println("\n== 10. Перцентили не складываются");
        int n = 100_000;
        double[] a = new double[n], b = new double[n], s = new double[n];
        for (int i = 0; i < n; i++) { a[i] = lognorm(3, 0.6); b[i] = lognorm(3, 0.6); s[i] = a[i] + b[i]; }
        System.out.println(f("p99(A)=%.1f p99(B)=%.1f сумма p99=%.1f p99(A+B)=%.1f",
                pct(a, 99), pct(b, 99), pct(a, 99) + pct(b, 99), pct(s, 99)));
        System.out.println(f("p50(A)+p50(B)=%.1f p50(A+B)=%.1f", pct(a, 50) + pct(b, 50), pct(s, 50)));

        // три узла по 1000 запросов и один узел с 10 запросами, время ~ экспоненциальное со средним 20 мс
        int[] sizes = {1000, 1000, 1000, 10};
        List<Double> all = new ArrayList<>();
        double sumP99 = 0;
        for (int size : sizes) {
            double[] node = new double[size];
            for (int i = 0; i < size; i++) { node[i] = expo(1 / 20.0); all.add(node[i]); }
            sumP99 += pct(node, 99);
        }
        System.out.println(f("среднее p99 по 4 узлам = %.1f, честный p99 по всем запросам = %.1f", sumP99 / sizes.length, pct(all, 99)));
    }

    static void coordinatedOmission() {
        System.out.println("\n== 11. Coordinated omission (сервис 1 мс, раз в 10 с пауза 1 с, клиент 100 rps, 100 с)");
        // сервис замирает на интервалах [10k, 10k+1) секунд, k >= 1
        DoubleUnaryOperator serviceEnd = start -> {
            double sec = start % 10;
            if (sec < 1.0 && start >= 1) start = start - sec + 1.0;
            return start + 0.001;
        };
        double rate = 100, total = 100;

        List<Double> closed = new ArrayList<>(); // клиент ждёт ответа перед следующим запросом
        double t = 0;
        while (t < total) {
            double e = serviceEnd.applyAsDouble(t);
            closed.add((e - t) * 1000);
            t = Math.max(e, t + 1 / rate);
        }

        List<Double> open = new ArrayList<>(); // запросы по расписанию, время от плановой отправки
        double free = 0;
        for (int i = 0; i < (int) (total * rate); i++) {
            double sched = i / rate, st = Math.max(sched, free);
            double e = serviceEnd.applyAsDouble(st);
            free = e;
            open.add((e - sched) * 1000);
        }
        print("closed loop (ждёт ответа)", closed);
        print("open loop (по расписанию)", open);
    }
    static void print(String name, List<Double> xs) {
        System.out.println(f("%s: n=%d p50=%.1f p99=%.1f p99.9=%.1f max=%.0f мс", name, xs.size(),
                pct(xs, 50), pct(xs, 99), pct(xs, 99.9), Collections.max(xs)));
    }

    static double usl(double n, double alpha, double beta) {
        return n / (1 + alpha * (n - 1) + beta * n * (n - 1));
    }

    static void usl() {
        System.out.println("\n== 12. USL: относительная пропускная способность C(N)");
        Object[][] models = {{0.0, 0.0, "линейно"}, {0.05, 0.0, "Амдал α=0.05"}, {0.05, 0.001, "USL α=0.05 β=0.001"}};
        for (Object[] m : models) {
            StringJoiner j = new StringJoiner(" ");
            for (int n : new int[]{1, 2, 4, 8, 16, 32, 64, 128}) j.add(f("%.1f", usl(n, (double) m[0], (double) m[1])));
            System.out.println(m[2] + ": " + j);
        }
        double a = 0.05, b = 0.001, nStar = Math.sqrt((1 - a) / b);
        System.out.println(f("пик при N* = sqrt((1-α)/β) = %.1f, C(N*) = %.2f; предел Амдала 1/α = %.0f", nStar, usl(nStar, a, b), 1 / a));
    }

    static void timeVsRequests() {
        System.out.println("\n== 13. Доступность по времени против доступности по запросам");
        // 30 дней: 12 ч в сутки по 1000 rps (день) и 12 ч по 10 rps (ночь)
