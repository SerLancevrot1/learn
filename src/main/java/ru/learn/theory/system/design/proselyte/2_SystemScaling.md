## 1. Масштабирование систем

### Определение

**Масштабируемость** — способность системы увеличивать пропускную способность и/или объём обрабатываемых данных, сохраняя заданный уровень качества:

- задержки в пределах SLO, включая p95/p99;
- допустимую долю ошибок;
- требуемую доступность.

При обсуждении масштабирования нужно ответить на два вопроса:

1. Что именно должно расти: число запросов, объём данных или количество пользователей?
2. Какие показатели качества должны сохраниться?

### Вертикальное и горизонтальное масштабирование

| Подход | Что изменяется | Когда подходит | Основное ограничение |
|---|---|---|---|
| Вертикальное — scale-up | Один узел получает больше CPU, RAM, IOPS или сетевой пропускной способности | Узкое место находится в компоненте, который сложно распределить между узлами | Усиление одного узла не устраняет узкие места в остальных компонентах |
| Горизонтальное — scale-out | Добавляются узлы, нагрузка распределяется между ними | Работу можно разделить между экземплярами | Общие ресурсы могут остаться узким местом |

### Вертикальное масштабирование: когда выбирать

- Узкое место — один компонент, который сложно реплицировать или разделить, например основной узел записи БД.
- Важна минимальная задержка: меньше сетевых переходов и RPC между частями логики.
- Простота эксплуатации важнее гибкости: меньше компонентов и взаимодействий между ними.

### Горизонтальное масштабирование: когда выбирать

- Нагрузку можно распределить между несколькими экземплярами.
- Компонент можно сделать stateless либо вынести состояние — сессии, файлы, данные — во внешнее хранилище.
- Нужны дополнительная ёмкость и изоляция отказов.

> Добавление узлов не гарантирует линейного роста производительности. Общая БД, сеть, блокировки или горячие ключи могут остаться узким местом.

### Масштабируемость и эластичность

| Понятие | На какой вопрос отвечает |
|---|---|
| Масштабируемость | Может ли система обслуживать больше нагрузки при добавлении ресурсов без нарушения SLO? |
| Эластичность | Может ли система автоматически добавлять и освобождать ресурсы под текущую нагрузку? |

### Оценка конкурентности: закон Литтла

Закон Литтла связывает среднюю пропускную способность, среднее время пребывания запроса и среднее число запросов в системе:

    L = λ × W

Где:

- `L` — среднее число запросов в системе;
- `λ` — средняя пропускная способность, запросов в секунду;
- `W` — среднее время пребывания запроса в системе, секунд.

Пример:

    Пропускная способность:       200 RPS
    Среднее время в системе:     0,2 с
    Среднее число запросов:      200 × 0,2 = 40

Это оценка средней конкурентности, а не необходимого числа потоков.

Важно различать:

- запросы, которые выполняются;
- запросы, которые ожидают I/O;
- запросы, которые стоят в очереди.

Очереди и насыщение ресурсов нужно измерять отдельно. В формуле используется среднее время, а не p95 или p99.

### Ответ на собеседовании

> Вертикальное масштабирование — увеличение ресурсов одного узла, горизонтальное — добавление узлов и распределение нагрузки. Выбор зависит от узкого места и возможности разделить работу и состояние. Добавление экземпляров не даст линейного роста, если все они упираются в общую БД, блокировки или другой общий ресурс. Результат оценивают не только по RPS, но и по сохранению SLO.

## 2. Rate Limiter

### Определение

Rate limiter ограничивает частоту операций для выбранного субъекта:

- IP-адреса;
- пользователя;
- API-ключа;
- tenant — клиента в многопользовательской системе;
- сервиса.

Пример ограничения:

> Не более 500 запросов в минуту на один API-ключ.

При превышении лимита запрос отклоняется или замедляется — в зависимости от выбранной политики.

Для HTTP типичный ответ при отклонении — `429 Too Many Requests` с заголовком `Retry-After`.

### Почему недостаточно указать только лимит

Формулировка «500 запросов в минуту» не описывает полностью поведение системы. Нужно выбрать алгоритм и определить допустимые всплески.

| Алгоритм | Особенность |
|---|---|
| Fixed window — фиксированное окно | Может допустить всплеск на границе соседних интервалов |
| Token bucket — корзина токенов | Допускает всплеск заданного размера |

### Отклонение и очередь — разные политики

| Политика | Что происходит при превышении |
|---|---|
| Отклонение | Клиент получает ошибку, обычно `429` |
| Ожидание в очереди | Запрос остаётся ждать обработки |

Очередь требует отдельных ограничений:

- максимального размера;
- максимального времени ожидания;
- поведения при переполнении.

> Нельзя считать, что rate limiter автоматически обеспечивает безопасное ожидание запросов.

### Ответ на собеседовании

> Rate limiter ограничивает частоту операций по выбранному ключу: например, по API-ключу или пользователю. Важно определить не только лимит, но и алгоритм, допустимый burst и поведение при превышении. Обычно превышение отклоняют с `429` и `Retry-After`; если используют очередь, отдельно ограничивают её размер и время ожидания.

## 3. API Gateway

### Определение

API Gateway — пограничный программный слой, через который проходит трафик к бэкенд-API.

Его основная задача — применять общие политики к запросам перед передачей в сервисы.

Упрощённая схема:

    Клиент
       ↓
    API Gateway
       ├── Аутентификация и авторизация
       ├── Rate limiting и квоты
       ├── Маршрутизация
       ├── Трансформации
       ├── Политики надёжности
       └── Наблюдаемость
       ↓
    Бэкенд-сервисы

### Основные функции

| Группа | Возможности |
|---|---|
| Безопасность | OAuth2/OIDC/JWT, API-ключи, mTLS, RBAC/ABAC |
| Маршрутизация | Выбор сервиса и версии API, маршрутизация по path/header |
| Ограничение нагрузки | Rate limiting, квоты, защитные политики |
| Трансформации | Изменение headers/body, REST ↔ gRPC, нормализация ошибок |
| Надёжность | Таймауты, ограниченные ретраи, circuit breaker, bulkhead |
| Производительность | Кэширование и компрессия |
| Наблюдаемость | Трассировка, метрики RED, структурированные логи |
| Управление трафиком | Canary, blue-green, A/B, mirroring/shadowing |

### Логический порядок обработки запроса

Это ориентир для обсуждения архитектуры, а не обязательный для любой реализации порядок.

#### 1. Приём защищённого соединения

- TLS termination.
- ALPN и SNI-routing.
- При необходимости — переход с HTTP/2 или HTTP/3 на HTTP/1.1 для upstream.
- Политика HSTS.

#### 2. Ранняя защита от перегрузки

- Сетевые и L7-лимиты.
- Проверка подозрительного трафика в соответствии с политикой приватности.

Ранние защитные ограничения нужно отличать от последующих лимитов по подтверждённому пользователю или tenant.

#### 3. Аутентификация

Проверка того, кто отправил запрос:

- OAuth2/OIDC;
- JWT;
- API-ключ;
- mTLS.

Для JWT проверяются:

- подпись;
- issuer;
- audience;
- срок действия.

Также необходимо учитывать ротацию ключей. Проверка JWT может выполняться локально с использованием ключей из JWKS.

#### 4. Авторизация

Проверка того, что субъекту разрешено делать:

- scopes;
- роли;
- права доступа.

Где необходимо, сервис повторно проверяет бизнес-права: наличие gateway не отменяет такую проверку.

#### 5. Rate limiting и квоты

Лимиты применяются по проверенной идентичности:

    tenant / user / route

При превышении — `429` и `Retry-After` согласно выбранной политике.

#### 6. Маршрутизация и версии API

- Выбор upstream по path/header.
- Выбор версии API.
- Canary- или weighted-маршрутизация.

Клиентские заголовки не должны позволять обходить авторизацию.

#### 7. Трансформации и нормализация

- Очистка и нормализация headers/body.
- REST ↔ gRPC transcoding.
- JSON ↔ Protobuf.
- Обработка CORS.

#### 8. Политики надёжности

- Таймауты для отдельных маршрутов.
- Ретраи только для безопасных к повтору операций.
- Backoff и jitter.
- Circuit breaker.
- Bulkhead.

> Политику повторов нельзя задавать без учёта семантики операции.

#### 9. Кэширование и компрессия

- `Cache-Control`.
- `ETag` / `If-None-Match`.
- Response cache для запросов, допускающих кэширование.

#### 10. Наблюдаемость

- Передача trace context: `traceparent` / B3.
- Проверенный request ID.
- Метрики и структурированные логи.
- Бизнес-метки с ограниченной cardinality — количеством уникальных значений.

Наблюдаемость должна охватывать весь путь запроса, а не только его завершение.

### Нефункциональные требования и SLO

Требования к gateway выводят из пользовательского SLO и профиля нагрузки.

| Что определить | На какой вопрос ответить |
|---|---|
| Latency overhead | Какую дополнительную задержку gateway может вносить на p95/p99? |
| Доступность | Какой уровень доступности требуется от этого слоя? |
| Throughput | Какой поток запросов нужно обслуживать? |
| Профиль запросов | Каковы размеры и сложность обработки headers/body? |
| Отказ control plane | Что произойдёт при потере канала конфигурации? |
| Отказ upstream | Как gateway поведёт себя при недоступности бэкенда? |
| Отказ gateway | Как будет проверяться устойчивость самого пограничного слоя? |

Значения вроде «не более 5 мс» или «доступность 99,99%» не универсальны: они должны следовать из требований конкретной системы.

### Безопасность: что нельзя упустить

- Изолировать квоты по проверенному tenant/user/route identity.
- Проверять JWT полностью, а не только его подпись.
- Не записывать в логи токены, API-ключи и лишние персональные данные.
- Не считать клиентский request ID подтверждением личности.
- Не использовать клиентские заголовки как способ обхода авторизации.
- Заранее определить безопасное поведение при отказе gateway, upstream и конфигурационного канала.

### Ответ на собеседовании

> API Gateway — пограничный слой перед API, который централизованно применяет политики: аутентификацию, часть авторизации, маршрутизацию, rate limiting, трансформации и наблюдаемость. Для него важно задать бюджет задержки и поведение при отказах. При этом gateway не отменяет проверку бизнес-прав в сервисах, а ретраи и кэширование должны учитывать семантику операций.

## 4. Краткая памятка перед собеседованием

| Тема | Главная мысль | Типичная ошибка |
|---|---|---|
| Scale-up | Усиливаем один узел | Считать, что усиление узла решит все узкие места |
| Scale-out | Добавляем узлы и распределяем работу | Ожидать линейного роста при наличии общего bottleneck |
| Эластичность | Автоматически меняем ресурсы под нагрузку | Путать с самой возможностью масштабирования |
| Закон Литтла | Средняя конкурентность: `L = λ × W` | Подставлять p99 или считать результат числом потоков |
| Rate limiter | Ограничиваем частоту по выбранному ключу | Не определить алгоритм, burst и политику превышения |
| API Gateway | Применяем общие политики перед сервисами | Считать его заменой всем проверкам внутри сервисов |
| Ретраи | Повторяем только безопасные к повтору операции | Повторять любой запрос без учёта последствий |
| SLO | Оцениваем качество при заданной нагрузке | Смотреть только на RPS, игнорируя задержки и ошибки |

## 2. Масштабирование: рычаги

`[ ]` **Короткий ответ:** подход выбирают по измеренным узким местам и целям SLO, а не по целевой цифре пользователей. Основные рычаги: сделать приложение stateless и масштабировать горизонтально; кешировать подходящие данные с явным TTL и инвалидацией; отдавать статику через CDN; реплики — для чтения и доступности, шарды — для объёма и записи; асинхронная обработка через очереди; автоматизация развёртывания, мониторинга и восстановления.

### 2.1. Вертикальное и горизонтальное

| | Вертикальное (scale-up) | Горизонтальное (scale-out) |
|---|---|---|
| Что делаем | Больше CPU, памяти, диска на узле | Больше узлов |
| Плюсы | Просто, код не меняется | Почти без предела, отказоустойчивость |
| Минусы | Есть потолок, узел — единая точка отказа | Нужны stateless-узлы, балансировка, health checks, согласованность данных |
| Когда | Первый шаг, особенно для БД | Stateless-сервисы; БД — через реплики и шарды |

Несколько копий повышают доступность только при корректном failover и отсутствии общей точки отказа (одна БД, один балансировщик, одна зона доступности).

### 2.2. CDN

`[ ]` **Короткий ответ:** CDN — сеть точек присутствия, которые отдают закешированный контент ближе к клиенту. Обычно это статика, но можно кешировать и публичные HTTP-ответы. Важны ключ кеша, TTL и инвалидация, а не только «близость».

<details>
<summary>Подробности и подводные камни</summary>

- Ключ кеша: если в него попадают лишние параметры (`utm_*`, cookies), процент попаданий падает. Если не попадают нужные (язык, валюта) — пользователь видит чужой вариант.
- Персональные ответы кешировать нельзя. `Cache-Control: private` или `no-store` для них обязательны.
- Инвалидация: версионированные имена файлов (`app.3f9a.js`) с долгим TTL надёжнее ручной очистки.
- Географически ближайшая точка не обязательно самая быстрая и не обязательно содержит свежую копию.
- CDN снимает нагрузку с источника и защищает от части DDoS, но источник должен выдерживать промах кеша по всем точкам сразу (например, после очистки).

</details>

### 2.3. Несколько дата-центров

`[ ]` **Короткий ответ:** несколько ЦОД — это не «включить», а набор решений: как маршрутизировать и переключать трафик, кто принимает записи, какой допустим лаг репликации, какие RPO и RTO. Без регулярных учений по отказу региона второй ЦОД дорог и бесполезен.

<details>
<summary>Подробности</summary>

- **Маршрутизация и failover:** GeoDNS, глобальный балансировщик или anycast. У DNS есть TTL и кеширование у клиентов — переключение не мгновенное.
- **Данные:** один пишущий регион (single-writer) проще; несколько пишущих (multi-writer) требуют разрешения конфликтов. Асинхронная репликация может потерять последние подтверждённые записи при аварии; синхронная увеличивает задержку записи на межрегиональный круг.
- **RPO** (Recovery Point Objective) — сколько данных можно потерять. **RTO** (Recovery Time Objective) — за сколько нужно восстановиться.
- **Эксплуатация:** учения по отказу и обратному переключению, миграции схемы в двух регионах, бэкапы и проверка восстановления.

</details>

## 4. Балансировка и состояние

`[ ]` **Короткий ответ:** чтобы масштабироваться горизонтально, экземпляр приложения не должен хранить в памяти состояние, нужное следующему запросу. Sticky sessions упрощают жизнь, но мешают масштабированию и failover: нагрузка распределяется неравномерно, а при падении узла его сессии теряются. Лучше хранить сессию во внешнем хранилище (Redis) или использовать подписанный токен.

<details>
<summary>Подробности: L4 и L7, алгоритмы, health checks</summary>

- **L4-балансировщик** распределяет TCP-соединения, не видит HTTP. Быстрый, но не умеет маршрутизировать по пути или заголовку.
- **L7-балансировщик** понимает HTTP: маршрутизация по пути, заголовкам, терминация TLS, ретраи.
- Алгоритмы: round robin, least connections, взвешенные, по хешу ключа (для локальности кеша).
- **Health checks** убирают больные узлы из ротации. Проверка должна отражать способность обслуживать запросы, но не тянуть за собой все зависимости — иначе сбой БД выведет из ротации все узлы сразу.
- При долгоживущих соединениях (gRPC, WebSocket) L4-балансировка по соединениям даёт перекос: новые узлы не получают нагрузку. Нужна балансировка по запросам на L7 или на клиенте.

</details>

**Уточнение интервьюера:** «А JWT вместо сессии — это бесплатно?» — нет. Токен нельзя мгновенно отозвать до истечения срока; нужны короткий срок жизни, refresh-токены и, при необходимости, список отозванных. См. Security.md.

## Шлюз и BFF в архитектуре сервисов

### 8.4. API Gateway и BFF

- **API Gateway** — единая точка входа: маршрутизация, аутентификация, rate limiting, TLS, наблюдаемость. Не должен быть единственным местом авторизации: сервисы сами проверяют права по проверенной идентичности. Gateway добавляет задержку и сам должен быть высокодоступен.
- **Backend for Frontend** — отдельный бэкенд под каждый тип клиента (веб, мобильный): агрегирует вызовы и отдаёт данные в удобной клиенту форме. Риск — дублирование логики между BFF.
