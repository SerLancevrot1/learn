### Масштабирование систем

**Масштабируемость** - способность системы увеличивать пропускную способность и/или объём данных без потери заданного уровня качества (SLO по p95/p99, ошибкам, доступности).

**Вертикальное масштабирование (scale-up)** - усиление одного узла: больше CPU/памяти/IOPS/сети. Горизонтальное масштабирование (scale-out) - увеличение количества узлов и распределение нагрузки между ними.

**Эластичность** - способность автоматически менять мощность (вверх/вниз) под актуальный трафик.

**Практическая оценка нагрузки**. Закон Литтла: среднее число запросов в системе `L = λ × W`, где `λ` — пропускная способность, а `W` — среднее время пребывания. Пример: 200 RPS × 0,2 с ≈ 40 запросов одновременно в системе. Это оценка средней конкурентности, не требуемого числа потоков: потоки могут ждать I/O, а очередь и насыщение нужно измерять отдельно.


#### Вертикальное масштабирование (Scale-Up)

Когда уместно:
- Узкое место - один компонент, который сложно реплицировать (часто - write-master БД, OLTP-узел, stateful кэш).
- Требуется минимальная латентность (меньше хопов, отсутствие сетевых RPC между "кусочками" логики).
- Простой SLA/эксплуатация важнее гибкости (меньше движущихся частей).

#### Горизонтальное масштабирование (Scale-Out)

Когда уместно:
- нагрузку можно распределить между несколькими экземплярами и узким местом не остаётся общий ресурс;
- компонент можно сделать stateless либо вынести состояние (сессии, кэш, файлы) во внешнее хранилище;
- нужны ёмкость и изоляция отказов. Линейный рост не гарантирован: БД, сеть, блокировки и горячие ключи могут стать общим bottleneck.


### Rate Limiter

**Rate limiter** ограничивает частоту операций: сколько запросов/сообщений может выполнить субъект (IP, пользователь, API-ключ, сервис) за единицу времени. При превышении порога запрос замедляется или отклоняется (обычно `HTTP 429 Too Many Requests` + `Retry-After`).

**Пример**. Для квоты «500 запросов в минуту на API-ключ» поведение зависит от алгоритма: fixed window может допустить всплеск на границе интервалов, а token bucket — burst заданного размера. Лимитер обычно отклоняет превышение (`429` + `Retry-After`), а постановка в очередь требует явного ограничения и политики ожидания.

### API Gateway

**API Gateway** - это программный пограничный слой, через который проходит внешний (и часто внутренний) трафик к бэкенд-API. Его задача - применять политики к запросам перед тем, как они попадут к микросервисам:
- аутентификация/авторизация (OAuth2/OIDC/JWT, mTLS, RBAC/ABAC),
- маршрутизация и версионирование API,
- ограничение частоты (rate limiting), квоты, анти-DDoS,
- трансформации (headers/body, REST↔gRPC, нормализация ошибок),
- кэширование и компрессия,
- ограниченные таймауты и политики надёжности для upstream; ретраи — только для безопасных к повтору операций,
- наблюдаемость: трассировка, метрики RED, структурированные логи,
- трафик-менеджмент: canary/blue-green, A/B, mirroring/shadowing.

#### НФТ и SLO для API Gateway

Задайте требования от пользовательского SLO и профиля нагрузки: latency overhead (p95/p99), доступность, throughput, размер/сложность запросов и поведение при потере конфигурационного control plane. Значения вроде «5 мс» или «99,99%» не являются универсальными целями.

- Изолируйте квоты и rate limits по проверенному tenant/user/route identity.
- В JWT проверяйте подпись, issuer, audience, срок действия и ротацию ключей; не логируйте токены/API-ключи.
- Протестируйте отказ самого gateway, upstream и конфигурационного канала; задайте безопасное поведение при каждом сбое.
- Прокидывайте trace context и request ID, но не доверяйте клиентскому идентификатору как подтверждённой личности.

#### Типичные функции и порядок применения политик
Рекомендуемый конвейер (edge path):

1. TLS termination (H2/H3→H1.1 upstream при необходимости), HSTS, ALPN, SNI-routing.

2. Защита от перегрузки: сетевые/L7 лимиты и проверка подозрительного трафика в соответствии с политикой приватности.

3. Аутентификация: OAuth2/OIDC (JWT verify по JWKS локально), API-keys, mTLS.

4. Авторизация: проверка scope/role и бизнес-прав на gateway и, где необходимо, повторная проверка в сервисе.

5. Rate limiting/Quotas: per-tenant/user/route; ответ `429` + `Retry-After`.

6. Роутинг/версии: path/header-based, canary/weighted при необходимости; не используйте клиентские заголовки для обхода авторизации.

7. Трансформации: sanitize/normalize, REST↔gRPC transcoding, JSON↔Protobuf, CORS.

8. Надёжность: пер-роут timeouts, retry (идемпотентные), backoff+jitter, circuit-breaker, bulkhead.

9. Кэш/компрессия: `Cache-Control`, ETag/If-None-Match, встроенный response-cache (для GET/idempotent).

10. Наблюдаемость: `traceparent`/b3, проверенный request ID и ограниченные по cardinality бизнес-метки. Не записывайте API-ключи, токены и лишние персональные данные.
