# Паттерны устойчивости распределённых систем

[Оглавление](../../README.md) · [Нефункциональные требования и расчёты](proselyte/1_NonFunctionalRequirements.md) · [Таймауты, повторы и backpressure](#7-паттерны-устойчивости)

**Формулируй требование через пользовательский сценарий, метрику, порог и окно измерения.** Например, «за 30 дней 99,9% валидных запросов на создание заказа завершаются успешно за ≤ 300 мс».

## Связь с НФТ: SLI, SLO, SLA и error budget

| Термин | Что сказать |
|---|---|
| SLI | Измеряемый показатель. Например, доля запросов, уложившихся в 300 мс |
| SLO | Целевое значение SLI за окно. Например, ≥ 99,9% за 30 дней |
| SLA | Договорное обязательство с последствиями за нарушение |
| Error budget | Допустимая доля плохих событий. При SLO 99,9% и 1 млн событий бюджет равен 1 000 |
| Burn rate | Отношение текущей доли плохих событий к допустимой. При 1% ошибок и бюджете 0,1% расход идёт в 10 раз быстрее |

**Доступность по запросам** и **доступность по времени** имеют разные знаменатели. Для временного SLO 99,9% за 30 дней бюджет простоя около 43 минут. Для SLO по запросам считай плохие запросы.

## Задержка, надёжность и восстановление

- **Latency** — время операции. **Throughput** — число завершённых операций за единицу времени. **p99 = 300 мс** означает, что около 99% наблюдений укладываются в 300 мс. Для общего p99 агрегируй наблюдения или совместимые гистограммы, поскольку среднее локальных p99 даёт другую величину.
- **Хвостовая задержка.** Если ответ ждёт все вызовы при fan-out, время определяет самый медленный вызов. Ищи насыщение, очереди и медленные зависимости.
- **Надёжность** описывает способность работать без отказа на интервале. **Доступность** учитывает также скорость восстановления. В простой модели ремонтируемого компонента доступность ≈ MTBF / (MTBF + MTTR), где MTBF — среднее время работы между отказами, а MTTR — среднее время восстановления.
- **RPO** — сколько данных по времени можно потерять. **RTO** — за какое время нужно восстановить сервис. Измеряй фактическое восстановление на учениях. Репликация помогает с отказом узла, резервные копии нужны и на случай ошибочного удаления.
- **Цепочка зависимостей.** Для независимых обязательных компонентов доступности перемножаются. Три компонента по 99,9% дают ≈ 99,70%. Для резерва проверь общие причины отказов и механизм переключения.
- **Другие НФТ.** Уточни ожидаемый рост нагрузки, время отката и диагностики, доступ к данным, срок хранения и стоимость на операцию.

## Шпаргалка по отказам

| Паттерн | Когда применять |
|---|---|
| Timeout и deadline | Ограничить время отдельного вызова и весь путь запроса. Передавай оставшийся бюджет вниз |
| Retry + backoff + jitter | Повторять временные сбои в пределах дедлайна. Ограничь число попыток и выбери слой повторов. Запись должна быть идемпотентной |
| Circuit breaker | Временно прекратить вызовы сбойной зависимости. После паузы проверить восстановление ограниченным числом пробных вызовов |
| Bulkhead | Разделить ресурсы по зависимостям или классам трафика, чтобы один поток нагрузки не занял все соединения и потоки |
| Load shedding и backpressure | Ограничить очередь. Сбросить лишнюю нагрузку или дать источнику сигнал замедлиться |
| Graceful degradation | Вернуть допустимый результат без части данных. Укажи, какой сценарий останется рабочим |
| Health checks и failover | Убрать неготовый узел из балансировки и проверить, выдержат ли остальные узлы нагрузку |

**Контрольный вопрос.** Клиент получил таймаут при оплате. Можно ли повторить? Сервер мог уже провести операцию. Повтори с тем же ключом идемпотентности и выясни результат исходной попытки.

## 7. Паттерны устойчивости

`[ ]` **Короткий ответ:** в распределённой системе зависимость рано или поздно станет медленной или недоступной. Защита строится слоями: таймаут на каждый вызов → ограниченные ретраи с backoff и jitter только для идемпотентных операций → circuit breaker, чтобы не добивать больную зависимость → bulkhead, чтобы сбой не съел общие ресурсы → деградация (fallback) и ограничение входящей нагрузки.

### 7.1. Таймауты и дедлайны

- Без таймаута медленная зависимость занимает потоки и соединения, пока не кончится пул, — и падает уже вызывающий сервис. Так рождаются каскадные сбои.
- Таймаут ставят на подключение и на ответ. Значение выбирают от p99 зависимости и бюджета задержки запроса.
- **Дедлайн** передают по цепочке: если у клиента осталось 200 мс, нижний сервис не должен ждать 2 секунды.

### 7.2. Retry, backoff и jitter

`[ ]` **Короткий ответ:** повторять стоит только временные ошибки (таймаут, 503, 429) и только безопасные к повтору операции (идемпотентные или с ключом идемпотентности). Ограничить число попыток, задержку увеличивать экспоненциально и добавлять случайность (jitter). Без jitter все клиенты ретраят синхронно и добивают восстанавливающийся сервис.

```java
// Full jitter: случайная задержка в [0, min(cap, base * 2^attempt)]
static Duration backoff(int attempt, Duration base, Duration cap) {
    long exp = Math.min(cap.toMillis(), base.toMillis() * (1L << Math.min(attempt, 30)));
    return Duration.ofMillis(ThreadLocalRandom.current().nextLong(exp + 1));
}
```

<details>
<summary>Результат запуска (base = 100 мс, cap = 2 с, максимум из 10 000 выборок)</summary>

| Попытка | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| Максимальная задержка, мс | 100 | 200 | 400 | 800 | 1600 | 2000 (упёрлись в cap) |

`Math.min(attempt, 30)` защищает от переполнения сдвига: `1L << 63` уже отрицательное число.

</details>

<details>
<summary>Ретраи на нескольких уровнях</summary>

Если клиент, gateway и сервис делают по 3 попытки, нижняя зависимость получит до \(3 \times 3 \times 3 = 27\) запросов на один пользовательский. Ретраить нужно на одном уровне, обычно ближе к источнику ошибки, и ограничивать общий бюджет ретраев (например, не больше 10% от успешных запросов).

В Spring Framework 7 ретраи есть в ядре: `@Retryable` и `@ConcurrencyLimit` включаются через `@EnableResilientMethods`. По умолчанию — до 3 повторов после первой неудачи с задержкой 1 секунда ([Spring Framework: Resilience Features](https://docs.spring.io/spring-framework/reference/core/resilience.html)). См. Spring.md.

</details>

### 7.3. Circuit Breaker

`[ ]` **Короткий ответ:** автомат с тремя состояниями. CLOSED — запросы идут, ошибки считаются. После порога ошибок — OPEN: запросы сразу получают fallback, зависимость отдыхает. Через паузу — HALF_OPEN: пропускается пробный запрос; успех → CLOSED, ошибка → снова OPEN.

<details>
<summary>Минимальная реализация</summary>

```java
static final class CircuitBreaker {
    enum State { CLOSED, OPEN, HALF_OPEN }
    private final int failureThreshold;
    private final Duration openFor;
    private final Clock clock;                  // Clock — чтобы тестировать без sleep
    private State state = State.CLOSED;
    private int failures;
    private Instant openedAt;

    CircuitBreaker(int failureThreshold, Duration openFor, Clock clock) {
        this.failureThreshold = failureThreshold; this.openFor = openFor; this.clock = clock;
    }

    synchronized <T> T call(Supplier<T> action, Supplier<T> fallback) {
        if (state == State.OPEN) {
            if (Duration.between(openedAt, clock.instant()).compareTo(openFor) < 0)
                return fallback.get();          // быстрый отказ, зависимость не вызываем
            state = State.HALF_OPEN;            // пробный запрос
        }
        try {
            T result = action.get();
            state = State.CLOSED;
            failures = 0;
            return result;
        } catch (RuntimeException e) {
            if (state == State.HALF_OPEN || ++failures >= failureThreshold) {
                state = State.OPEN;
                openedAt = clock.instant();
            }
            return fallback.get();
        }
    }
}
```

Результат запуска с порогом 3 и паузой 10 с: после 5 неудачных вызовов состояние `OPEN`, реально зависимость вызвана **3 раза** — последние два запроса получили fallback без обращения к ней. Через 11 секунд пробный запрос успешен, состояние `CLOSED`.

`synchronized` на весь вызов здесь ради простоты: в реальной реализации действие выполняют вне блокировки. В продакшене используют Resilience4j: скользящее окно по количеству или времени, доля ошибок вместо подряд идущих, учёт медленных вызовов.

</details>

### 7.4. Bulkhead и ограничение нагрузки

- **Bulkhead** («переборки» на корабле) — отдельные пулы потоков, соединений или семафоры для разных зависимостей. Медленный сервис рекомендаций исчерпает свой пул, но не пул платежей.
- **Rate limiting** защищает от перегрузки на входе: лишние запросы получают `429`. Алгоритмы — в RedisAndCaching.md.
- **Load shedding** — при перегрузке отбрасывать часть запросов (низкоприоритетные) сразу, а не обслуживать все медленно.
- **Деградация** — вернуть упрощённый ответ: товары без персональных рекомендаций лучше, чем ошибка.

### 7.5. Памятка: Backpressure

`[ ]` **Короткий ответ:** backpressure (обратное давление) — обратная связь от потребителя к производителю: «притормози, я не успеваю». Если продюсер быстрее потребителя, разница копится в буфере: ограниченный переполнится (потеря данных), неограниченный съест память (отказ). Есть три стратегии — замедлить источник, буферизовать (только в ограниченный буфер), отбрасывать лишнее. Лучшая — управлять скоростью источника: данные не теряются, поток просто растягивается во времени. На практике стратегии комбинируют, но сигнал «стоп», явный или неявный, всё равно должен дойти до источника.

**Оценка на салфетке:** продюсер — 10 000 событий/с, потребитель — 7 500 событий/с. Очередь растёт на 2 500 событий/с, это 9 млн за час. Никакой буфер это не «переждёт», если пик не заканчивается.

**Три стратегии:**

| Стратегия | Как | Плюс | Минус | Когда |
|---|---|---|---|---|
| Замедлить источник | Pull / `request(n)`, блокировка при полной очереди, `429` | Без потерь, без больших буферов | Растёт задержка; не всякий источник можно замедлить (датчик с фиксированной частотой) | По умолчанию |
| Буферизовать | Очередь, брокер, временное хранилище | Сглаживает всплески | Память и задержка; буфер обязательно ограничен по размеру или времени | Короткие пики |
| Отбрасывать (drop) | Не принимать новые или вытеснять старые; сэмплирование | Система жива | Данные теряются | Метрики, телеметрия, когда свежесть важнее полноты |

**Где встречается:**

| Уровень | Механизм |
|---|---|
| TCP | Скользящее окно: получатель сообщает, сколько байт готов принять; плюс управление перегрузкой |
| Reactive Streams | `Flow.Subscription.request(n)` (Java 9+), Project Reactor, RxJava, Akka Streams: потребитель сам запрашивает n элементов, сигнал идёт вверх по цепочке операторов |
| Kafka | Pull: потребитель читает в своём темпе, но продюсера **не тормозит** — отставание (consumer lag) копится в топике до retention (потеря старых сообщений) или до заполнения диска |
| RabbitMQ | Push + `prefetch` (QoS): не больше N неподтверждённых сообщений на потребителя; при переполнении очереди — отказ продюсеру или dead letter queue |
| HTTP / gRPC | Rate limiting и `429 Too Many Requests`, circuit breaker ([7.3](#73-circuit-breaker)), семафор на одновременные запросы ([7.4](#74-bulkhead-и-ограничение-нагрузки)) |

**Что запомнить:**

- **Неограниченный буфер — не решение,** а отложенный OOM. У каждой очереди должен быть предел и политика на переполнение.
- **Брокер ≠ backpressure:** Kafka развязывает по времени, но не замедляет продюсера. Следить за consumer lag и масштабировать потребителей или партиции.
- **Масштабирование лишь сдвигает предел:** больше потребителей или партиций временно сглаживает разницу скоростей, но ресурсы не бесконечны.
- **Виртуальные потоки (Loom) не дают backpressure.** Раньше пул из N потоков неявно ограничивал нагрузку; теперь тысячи дешёвых потоков одновременно идут в БД — узкое место уходит за пределы JVM. Ограничивать конкурентность явно: `Semaphore`, ограниченные очереди, bulkhead (так делает, например, Helidon 4). Loom и реактивность дополняют друг друга, а не заменяют.
- **Цена:** сложнее архитектура, сознательно добавленная задержка (критично для real-time), служебные сигналы, единообразная политика в разнородных сервисах, подбор размера буфера под всплески (не слишком мал и не слишком велик).
- **Backpressure не заменяет fallback:** если узел умер совсем, нужны circuit breaker, резервный сервис или отбрасывание с логированием. Зато растущая очередь — хороший ранний индикатор проблемы.

<details>
<summary>Сценарии: сбой сети и медленная БД</summary>

- **Сбой сети между A и B.** Без backpressure A продолжает слать запросы, копятся повторы, память и потоки — A падает по таймаутам или от переполнения буферов. С backpressure: B (или TCP) не подтверждает приём — A замедляется вплоть до остановки; на уровне приложения circuit breaker прекращает новые запросы. Бесполезная работа не накапливается, у системы есть время восстановить связь.
- **Медленная БД.** Без контроля сервис открывает всё новые транзакции: пул соединений исчерпан, время ответа растёт, система виснет. С backpressure: семафор на N одновременных операций, входящие задачи ждут в ограниченной очереди, внешним клиентам — `429`. БД работает на пределе, но не сверх него: медленно, но стабильно.

</details>

<details>
<summary>Лабораторная: виртуальные потоки, Semaphore, ограниченная очередь, Flow</summary>

```java
// «Медленная БД» на 50 мс, счётчик одновременных запросов
static final AtomicInteger inFlight = new AtomicInteger(), maxInFlight = new AtomicInteger();

static void slowDb() throws InterruptedException {
    maxInFlight.accumulateAndGet(inFlight.incrementAndGet(), Math::max);
    try { Thread.sleep(Duration.ofMillis(50)); } finally { inFlight.decrementAndGet(); }
}

static int run(int tasks, Semaphore limit) throws Exception {
    maxInFlight.set(0);
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        for (int i = 0; i < tasks; i++) {
            executor.submit(() -> {
                if (limit != null) limit.acquire();       // ждём свободный слот
                try { slowDb(); } finally { if (limit != null) limit.release(); }
                return null;
            });
        }
    }                                                     // close() ждёт все задачи
    return maxInFlight.get();
}

// run(1_000, null)               → одновременно в БД 1000
// run(1_000, new Semaphore(20))  → одновременно в БД 20

// Ограниченная очередь: при переполнении — отказ, а не рост памяти
var queue = new ArrayBlockingQueue<Integer>(100);
// 150 × queue.offer(i)           → принято 100, отклонено 50

// Reactive Streams: подписчик запрашивает по одному элементу
try (var publisher = new SubmissionPublisher<Integer>(ForkJoinPool.commonPool(), 16)) {
    publisher.subscribe(new Flow.Subscriber<Integer>() {
        Flow.Subscription s;
        public void onSubscribe(Flow.Subscription s) { this.s = s; s.request(1); }
        public void onNext(Integer item) { /* обработка */ s.request(1); }
        public void onError(Throwable t) { }
        public void onComplete() { }
    });
    for (int i = 0; i < 1_000; i++) publisher.submit(i);  // блокирует, когда буфер полон
}
```

Результат запуска на OpenJDK 25:

| Вариант | Результат |
|---|---|
| 1 000 виртуальных потоков без ограничения | 1 000 одновременных запросов в «БД» |
| То же с `Semaphore(20)` | 20 одновременных запросов |
| `ArrayBlockingQueue(100)`, 150 × `offer` | принято 100, отклонено 50 |
| `SubmissionPublisher`, буфер 16 | отставание подписчика не выше ~16–17 элементов, получено 1 000 из 1 000 |

`offer` не блокирует и сразу возвращает `false` — это стратегия drop/reject; `put` ждал бы места — это замедление источника. `submit` у `SubmissionPublisher` блокирует продюсера, пока подписчик не запросит новые элементы.

</details>

**Уточнение интервьюера:** «Мы перешли на виртуальные потоки, и база начала падать под нагрузкой. Почему и что делать?»

<details>
<summary>Ответ</summary>

Раньше пул платформенных потоков (скажем, 200) неявно ограничивал число одновременных запросов к БД. С виртуальными потоками на каждый запрос — свой поток, и все они одновременно идут в базу: узкое место переехало из JVM в БД. Пул соединений частично спасает, но тысячи потоков выстраиваются к нему, держат память и ждут до таймаута. Решение — явный backpressure: `Semaphore` на число одновременных операций под ёмкость БД, ограниченная очередь задач с отказом (`429`/`503`) при переполнении, дедлайны ([7.1](#71-таймауты-и-дедлайны)), load shedding низкоприоритетных запросов.

</details>
