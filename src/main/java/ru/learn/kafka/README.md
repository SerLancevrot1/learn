# Kafka: producer, consumer и транзакции

В примере используются Spring Kafka и строки в формате `key=orderId`, `value=payload`.

## Запуск

1. Поднимите локальный брокер командой `docker compose up -d kafka`.
2. Создайте топики:
   `docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic learn.orders --partitions 1 --replication-factor 1`
   Повторите команду с `learn.orders.processed` вместо `learn.orders`.
3. Запустите приложение. Отправить событие можно через `OrderProducer.send("order-1", "created")`.
4. Запустить интеграционный тест: `.\mvnw.cmd -Dtest=KafkaExactlyOnceIntegrationTest test`.

Адрес брокера можно переопределить переменной `KAFKA_BOOTSTRAP_SERVERS`.

## Что смотреть в коде

- `OrderProducer` показывает асинхронную отправку внутри явной Kafka-транзакции; вызывающий код получает `CompletableFuture` и может обработать подтверждение или ошибку.
- `consumeAtLeastOnce` подтверждает offset только после обработки. При сбое до ack запись будет прочитана повторно — реальный прикладной обработчик должен обеспечивать идемпотентность, например хранить обработанные `orderId` в БД с уникальным ограничением.
- `consumeExactlyOnce` обрабатывает вход и отправляет результат в выходной топик внутри транзакции контейнера. Транзакция атомарно фиксирует выходные записи и offset входной группы.
- `KafkaExactlyOnceIntegrationTest` вручную моделирует abort и повтор: выход первой попытки виден `read_uncommitted`, но невидим `read_committed`-консьюмеру; затем фиксируются результат и offset, и проверяется, что именно зафиксированный результат виден ровно один раз.

## Как читать пример по шагам

1. Начните с `KafkaTopics`: это просто имена входного и выходного топиков.
2. В `OrderProducer.send` проследите, как key/value передаются в `KafkaTemplate`, а `executeInTransaction` обрамляет публикацию транзакцией.
3. В `KafkaListenerConfiguration` сравните две фабрики: первая ждёт ручной ack, вторая связывает контейнер с менеджером Kafka-транзакций.
4. В `OrderListeners` найдите две аннотации `@KafkaListener`. У них разные `groupId`, поэтому обе группы независимо получают каждое входное событие. Это специально для демонстрации, а не шаблон настройки двух рабочих обработчиков одного процесса.
5. В интеграционном тесте следите за порядком: отправка входа → aborted попытка → разница `read_uncommitted`/`read_committed` → повтор → атомарный commit результата и offset.

Exactly-once здесь означает атомарность Kafka-записей и offset в пределах Kafka. Это не защищает внешние побочные эффекты (например, вызовы HTTP или запись в отдельную БД); для них нужны идемпотентность, outbox/inbox или распределённая координация. Для локального одноброкерного теста повторная доставка Kafka задана как `read_committed`.
